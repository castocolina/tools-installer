<objective>
Replace the single tool-level skill status operation with a per-harness, closed-table status probe
model, and give it a batching entry point a background worker can call (plan 16-12 wires it).

Purpose: D-10/D-11/D-14. Today `inspect_status` has zero production callers, supports two hard-coded
operation ids, and returns ONE status per tool. D-13 needs per-host answers. RESEARCH.md Pattern 3
recommends a `HOST_SETUPS`-shaped closed table. Live checks during planning found two facts the
mechanism must respect:
- `codex plugin list` lists every marketplace plugin with an `installed`/`not installed` column, so
  the existing substring match is wrong.
- `claude plugin list` prints `❯ <name>@<marketplace>` rows.
- `pi list` prints the package source (`git:github.com/obra/superpowers`).
- softaworks/matt-pocock skills are recorded in `~/.agents/.skill-lock.json` (`skills` map,
  per-skill `source` like `softaworks/agent-toolkit`).
- opengsd writes `<runtime-config-dir>/gsd-install-state.json` (`~/.claude`, `~/.codex`,
  `~/.config/opencode` verified on this host).

Output:
- `SkillStatusProbe` model and `status_probes` parsing.
- Widened `SKILL_HARNESSES`.
- Removal of the two-op `codex_plugin_status`/`pi_package_status` machinery.
- `HARNESS_CLI_STATUS`, `SKILL_LOCK_HARNESS_DIRS`, `INSTALL_STATE_HARNESS_DIRS` closed tables.
- `inspect_skill_packs`.
- Migrated registry rows for ponytail and superpowers. The full per-pack audit is plan 16-07.

Discretion (A2 resolved): one generic per-harness probe shape (option b), not one dataclass per
harness.

Output harness note: if `uv run pytest` prints a false "No tests collected", re-run via `.venv/bin/pytest`.
</objective>
