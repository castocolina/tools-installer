<objective>
Make a full uninstall leave nothing behind. `plan_uninstall` walks only download/raw/app artifacts,
so `tools-installer-wait-time` -- a real executable this installer copied into `~/.local/bin` --
survives an uninstall, and so does the `~/.myshellrc` block that calls it. This plan sweeps both,
for every tweak that is still enabled, through the exact disable path the Policies view already
uses.

Purpose: ROADMAP Phase 3 SC#2 -- "Running a full uninstall removes every tweak-managed executable
(e.g. `tools-installer-wait-time`), not only `Tool`-shaped artifacts." That is
REQ-uninstall-sweep-tweak-executables, which `.planning/PROJECT.md` records as a code-review finding
against commit `431a0a9`. CONTEXT D-04 widens it from the requirement's literal wording to a
symmetric teardown, and gives the reason: deleting the executable while leaving its shellrc block
would leave a shell function pointing at a file that no longer exists -- a strictly worse state than
before the uninstall. The user's stated motivation makes the direction concrete: this exists so a
full machine restore starts from a genuinely clean state.

Output: a `tweak_executables_present` predicate in `installer/tweaks.py`; `active_tweak_ids` and
`sweep_tweaks` in `installer/uninstall.py`, both composing the existing `tweak_policy` /
`omz_plugins_policy` remove paths; a `remove_tweaks` lever on `UninstallDecision` threaded through
both uninstall entry points; a third env row in the Uninstall view; the `setup.py` wiring; and the
single consolidated `.claude/architecture.md` section for all of Phase 3.
</objective>

<design_decisions>
**Sibling functions, not a widened `plan_uninstall`.** CONTEXT.md's integration note says
`plan_uninstall` "needs a new code path enumerating active tweaks alongside the existing `Tool`-shaped
artifact walk". It gets one -- as siblings in the same module, not inside that function. Three reasons:
`plan_uninstall` returns `list[Path]` and is consumed per-tool by `classify_tools` to decide a tool's
removability, so tweak paths leaking into its return would make every tool look removable; the caller
already deletes its result with `remove_paths`, but a tweak needs `strip_block` on an rc file too,
which is not a path deletion; and D-04 explicitly requires reusing `tweak_policy(...).remove()`
rather than reinventing removal, which is a policy call, not a path list. `plan_uninstall` and
`classify_tools` are therefore untouched.

**`sweep_tweaks` composes the policy, it does not reimplement it (D-04).** The body calls
`tweak_policy(bundle, rc_path=..., bin_dir=...).remove()` for each active bundle and
`omz_plugins_policy(...).remove()` for the Oh-My-Zsh tweak. Not `remove_tweak` + `remove_tweak_executables`
directly, even though that is what those closures do: going through the policy is what makes "full
uninstall" and "toggle off in Policies" the same operation by construction, so a future change to
one is automatically a change to the other. This is exactly what D-04 asks for and it is the reason
`installer/uninstall.py` imports `installer/policy.py` (no cycle: `policy` imports `guards`, `tweaks`
and `omz`, none of which import `uninstall`).

**"Active" means block present OR owned executable present.** D-04 says "every tweak that is still
enabled". The REQ's literal wording is narrower -- orphaned executables. The disjunction covers both
and is strictly safer: a user who hand-deleted the `~/.myshellrc` block still has a real file in
`~/.local/bin` that this installer put there, and that file is precisely what SC#2 names. A
block-only predicate would miss it; an executable-only predicate would miss every bundle that has no
helper. Task 2 pins both halves separately so neither can be dropped.

**The Oh-My-Zsh sweep is NOT gated on the presence probe.** `omz_plugins_policy` takes
`present: bool` to drive `missing_requires`, which gates ENABLING (D-05/D-06). `sweep_tweaks` passes
`present=True` unconditionally, with a comment saying why: a machine being uninstalled may have had
oh-my-zsh removed already, and refusing to undo our own `.zshrc` edit because the thing we edited it
for is gone would strand exactly the stray state this plan exists to remove. Removal is total either
way -- `remove_plugins` no-ops on a missing file or missing array (plan 03-02's deliberate
asymmetry), so passing `present=True` can never raise.

**`zshrc_path` is optional and defaults to `None`.** Callers that do not care about the Oh-My-Zsh
tweak (unit tests, and any future caller working only with bundles) pass nothing and get bundle-only
behaviour. `setup.py` always passes the real path. The alternative -- a required parameter -- would
force every existing test construction to learn about a feature it is not testing.

**`preview == effect` by construction.** `sweep_tweaks` calls `active_tweak_ids` rather than
re-deriving the set, so the CLI's "these will also be disabled" line, the TUI row's label and the
actual removal cannot drift. Task 2 asserts the returned tuple equals the previewed tuple, which is
cheap and would catch a future refactor that duplicates the predicate.

**A third env row rather than a hidden always-on behaviour.** The Uninstall view already models
non-`Tool` teardown as selectable pseudo-rows (`#ban`, `#path-block`). A third one keeps the mental
model intact, keeps `a` (select all) meaning "tear down everything" -- which is the machine-restore
case CONTEXT's `<specifics>` describes -- and keeps a partial selection honest: a user removing one
tool does not silently lose their shell tweaks. Making the sweep unconditional inside
`perform_uninstall` would have been fewer lines and a worse product.

**`tweak_ids` is a `tuple[str, ...]`, not a `list[str]` like its `UninstallInputs` neighbours.** The
dataclass is frozen and the field needs a default so every existing construction in
`tests/test_uninstall_e2e.py`, `tests/test_policies_e2e.py` and `tests/test_wizard_app.py` stays
valid; a `list` default would need `field(default_factory=list)` for no benefit, and the value comes
straight from `active_tweak_ids`, which returns a tuple. Same reasoning for `_UninstallEntry.is_tweaks`
defaulting to `False`: only `_tweak_entry` sets it, so the two existing env builders need no edit.

**The sentinel check is the safety property, and it already exists.** `remove_tweak_executables`
deletes `bin_dir / executable.command` only when `_is_our_executable` finds the bundle's sentinel
inside it. That is the single thing preventing this feature from deleting an unrelated user file out
of `~/.local/bin`, so `tweak_executables_present` reuses the same check rather than testing mere
existence -- otherwise the preview would promise to remove a file the removal correctly refuses to
touch. Task 2 pins it from both directions and Task 3 proves it against a real filesystem.

**No `checkpoint:human-verify` task.** `.planning/config.json` sets
`workflow.human_verify_mode: "end-of-phase"`, so verification consolidates at phase close. The
TUI-surface check ONESHOT checklist item 7 requires is Task 3's `tmux` script, which the executor
runs itself -- it is a text match on a monospace TUI, navigation-only, and mutates nothing.
</design_decisions>
