<objective>
Installing Oh-My-Zsh writes the bundled plugins at install and prints the reviewed login-shell handoff, with no question; installing starship, direnv, zoxide, fzf, fnm or volta writes its shell-init block at install with no question; each gets the `≈ apply install tuning` step when present but never tuned, and is reverted with the tool (OMZ plugins through the full-uninstall sweep). No install-time question is left.

Purpose: SPEC R4, R5, R8 (TUNE-02; the `--yes` left-off note is part of TUNE-03's run-option cleanup); D-07, D-08, D-12, D-13, D-14, D-15. Extends 23.2-03's `apply_install_tuning` and `_tuning_fact` to the two remaining tuning kinds.
Why OMZ plugins, shell init and the sensitive tables stay in one plan (~165k, 25 files): the coupling is concrete, not thematic.
- (1) The two sensitive tables hold exactly `set_login_shell` (Oh-My-Zsh's action) and `source_shell_init` (the shell tools' action). D-13 empties them as one contract, and the model loader's `default_enabled_sensitive_actions` reads that same tuple.
- (2) The prompt is shared: `omz.default_theme` returns `""` when the starship shell-init block is present, starship's shell init writes `ZSH_THEME=""`, and `write_plugins` applies the default theme. Either install order (starship before or after Oh-My-Zsh) must end with exactly one prompt, so one plan owns both writers.
- (3) The shell-init record reuses the Oh-My-Zsh record reader, moved from `omz._record` to `shellrc.read_record`.
- (4) All three extend the same `TUNING_ACTIONS`, `apply_install_tuning` dispatch and `_tuning_fact` in `post_install.py`, `model.py` and `version_status.py`.

A split would put those shared files into two sequential waves with no parallel gain, and push 23.2-08 to wave 5.
Output: `set_omz_plugins`, the shell-init written-once record, the non-sensitive `source_shell_init` and `set_login_shell`, the emptied sensitive tables, and the tests.
</objective>
