<objective>
A present tool that never got its install tuning shows `≈` with the step "apply install tuning", and RECONFIGURE writes the missing keys under the install rules; a key the user deleted after the installer wrote it is the user's choice and is neither flagged nor rewritten (an explicit reinstall still rewrites it).

Purpose: SPEC R2 (part of TUNE-01) and the R6 pending case; D-03, D-04, D-05, D-06. Built on 23.2-01's `TUNING_GROUPS` and `apply_agent_tuning`; 23.2-06 extends the same `apply_install_tuning` and `_tuning_fact` to Oh-My-Zsh plugins and shell init.
Why this plan stays whole (~120k, 9 files): the pending fact and RECONFIGURE are one contract, a user-choice rule ("absent and unrecorded"). `SettingFacts.absent` defines what `≈` shows, and `skip_recorded` defines what RECONFIGURE writes; they must agree key for key. Splitting would leave a commit where `≈` offers a step whose branch does not exist (`_run_step` refuses unknown kinds), or a branch nothing triggers. Task 2 is only the edge tests of that same rule.
Output: `SettingFacts.absent`, `apply_setting(skip_recorded=...)`, `ConfigStepKind "install_tuning"`, `post_install.apply_install_tuning`, the RECONFIGURE branch, and `version_status._tuning_fact` replacing `_settings_facts`.
</objective>

Decisions this plan implements:
- D-03: one new `ConfigStepKind` `"install_tuning"`, step text `apply install tuning`; the `_run_step` branch calls the same tuning functions as the install action (D-01); `_StepResult` and `_run_reconfigure` carry the `FileResult`s; `apply_setting` gains `skip_recorded` (RECONFIGURE passes True, install and reinstall do not). One writer (RESEARCH Pattern 3 and Pitfall 4: a skipped recorded key yields no `KeyResult`).
- D-04: pending = absent keys the ledger does not record (`SettingFacts.absent`, RESEARCH Pattern 2), computed per tool inside the pass loop next to `_hook_fact`, only when present; one `ConfigStep` per pending tool. Claude's discretion: the `≈` reason reads `install tuning not applied`.
- D-05: a present agent whose settings file does not parse shows the O7 reason (`≈`, no step), ledger or not; the untrusted-ledger handling stays (same text). Decided here (RESEARCH Pitfall 6): `_settings_facts` is folded into `_tuning_fact`, which owns every per-agent settings fact: the untrusted-ledger reason (any presence; `tool_state` moves an absent tool's reason into notes, as today), the ledger-managed unreadable reason for an absent agent (today's behavior), and, for a present agent, the O7 reason or the pending step. Any other exception stays an `unchecked` note (a read-only secondary fact never fails the pass). A conflict reported by `file_problem` (both opencode.json and opencode.jsonc) is shown the same way as O7: a reason, no step, because the step would only be refused.
- D-06: a cursor key holding `cli_default` does not raise `≈` alone (falls through both lists, no extra code); RECONFIGURE still replaces it, since `skip_recorded` skips recorded keys only.
