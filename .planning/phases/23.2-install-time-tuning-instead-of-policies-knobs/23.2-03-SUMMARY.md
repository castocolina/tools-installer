# Phase 23.2 Plan 03: Pending install-tuning step and RECONFIGURE Summary

**A present claude, codex, opencode, cursor-agent or VS Code that never got its install tuning now reads `≈ install tuning not applied` with one `apply install tuning` step; RECONFIGURE writes only the keys that are absent and unrecorded, through the one `apply_setting` writer, and reports them in the settings block. A key the user deleted after the installer wrote it is neither flagged nor rewritten (a reinstall still rewrites it).**

## Deviations from Plan

### Auto-fixed issues

None. The plan's gates and decisions were followed as written.

### Notes and small divergences

1. **Ledger-managed unreadable check is kept for every CONFIG_AGENT tool, declared tuning or not.** The old `_settings_facts` ran for every agent in `receipts.CONFIG_AGENTS`; `_tuning_fact` keeps that for any tool whose id is in that tuple, and adds the O7-without-ledger reason and the pending step only for a present tool that declares `apply_agent_tuning`. Existing tests whose `_agent_tool()` declares nothing therefore read exactly as before.
2. **Tuning actions are dispatched by membership, not a table.** `apply_install_tuning` loops `tool.post_install` and runs `_tune_agent` for names in `TUNING_ACTIONS`. With one tuning action that is all it needs; 23.2-06 adds `set_omz_plugins` and `source_shell_init` and will split the dispatch there.
3. **`_apply_pass` and `_apply_once` take the skip set as a plain `frozenset[KeyPath]`** (default empty), so the revert and facts callers are untouched.
4. **Plan-head ledger file.** See the Commits note: the file is in the shared git dir and could not be written from the worktree; `plan_head_before` is the brief's base SHA.
