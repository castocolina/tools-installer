<objective>
Installing claude, codex, opencode, cursor-agent, copilot or VS Code writes that tool's tuning keys at once, with no question, on every route, through the engine's plural `post_install` dispatcher; the writes reach the run summary, are recorded in the agent's config-write ledger, and are reverted by the tool's removal.

Purpose: SPEC R1, R3 and R6; D-01, D-02, D-21 (the copilot settings surface). This is the phase's tracer: one claude install proves registry -> app -> session -> engine -> post_install -> agent_settings -> ledger -> render end to end before the other agents, the pending step (23.2-03) and the OMZ/shell-init tuning (23.2-06) build on it.
Why this plan stays whole (~150k, 18 files; user rule "justify big plans instead of splitting"): the tracer necessarily crosses every layer, and Tasks 2-3 change the same contract it creates. `PostInstallOutput`, `InstallOutcome.settings`, `TUNING_GROUPS` and the `environ` keyword on the `agent_settings` signatures form one API that 23.2-03, 23.2-04 and 23.2-06 consume. Splitting it would ship a half-threaded `environ`, with callers resolving copilot's file two different ways. It would also force the pieces into sequential waves over the same files (`agent_settings.py`, `post_install.py`, `app.py`), so nothing would run in parallel and the phase would grow by a wave.
Output: `PostInstallOutput`, the `apply_agent_tuning` action, `InstallOutcome.settings`, `TUNING_GROUPS`, the copilot adapter and keys, `COPILOT_HOME` cleared in the sandbox, and the install/removal test matrix.
</objective>
