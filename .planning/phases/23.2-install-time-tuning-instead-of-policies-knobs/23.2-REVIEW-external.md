### EX-01 (Medium) CONFIRMED: PATH repair ignores the installer's own pnpm wrapper

- Scenario: the pip/npm ban is on, so `~/.local/bin/pnpm` is the installer's wrapper and is first on PATH. A real pnpm sits in `~/.local/share/pnpm/bin`, which the shell started before it was installed does not have on PATH.
- `_put_present_bin_dir_on_path` guards with `shutil.which(tool.cmd) is not None`. That finds the wrapper, so the function returns early and never prepends the real pnpm dir.
- `_node` then calls `real_pnpm()`, which refuses the wrapper by design (`guards.real_binary`) and returns None. `_pnpm_left_behind()` finds the real pnpm, so `_node` raises "open a new terminal". That is UAT F-1 again, on ban-on hosts.
- The codebase already treats this case elsewhere: `status.present_bin_dir` and `is_installed` both exclude `guards.is_our_shim` hits. D-24 says `shutil.which(cmd)` is None, but that wording does not cover a shim hit.
- Precondition: wrapper on PATH and real pnpm off PATH. This is narrow but ordinary after a headless `pkg-mgr` run in the same shell. The reviewer says no test has a wrapper on PATH.
- Fix: treat a `which` hit that `is_our_shim` flags as "not found". Alternatively, let `_node` run the left-behind pnpm by its absolute path.

### EX-02 (Medium) PARTIAL: a copilot self-update voids uninstall proof

- Mechanics confirmed. A changed dir artifact makes `receipts.drifted` non-empty, so `_receipt_proof` returns `()` and uninstall deletes nothing. The registry comment says the tarball "self-updates in place, which reads as directory drift, never BROKEN".
- This is the Phase 19 review-H7 safe-fail design, not a regression introduced by 23.2, and it applies to every receipt-backed tool. The premise is unverified: nobody checked that copilot rewrites files inside `~/.local/opt/copilot`.
- It does limit the spec claim that removal is clean, once copilot has updated itself.
- Suggested follow-up: confirm copilot's update path. If it self-updates in place, show a manual removal command for drift, or record the limit in the phase summary. Not a gate blocker.

### EX-03 (Low) PARTIAL: an Oh-My-Zsh theme-step error drops all post-install output

- `_set_omz_theme` (`post_install.py:183`) can raise. `ensure_zshrc_template` and `apply_theme` are not wrapped, and `omz.py:683-688` re-raises `OSError`. `run_post_install` has no per-action guard, so the failure is caught only by `engine._dispatch_post_install`.
- Effect: the earlier `set_login_shell` lines and the later `set_omz_plugins` step are lost, and the user sees one "post-install actions crashed" warning. No data is corrupted. The install row stays done.
- The 23.2 plugin step already isolates its own errors. Wrapping the theme step the same way is a cheap hardening.

### EX-04 (Low) PARTIAL: the pending fact skips a key that holds the CLI default

- `setting_facts` (`agent_settings.py:1042-1051`) counts only ABSENT keys as pending.
- A key holding `cli_default` (cursor-agent attribution keys, `agent_settings.py:543-544`) is not pending, although `apply_setting` replaces it (`agent_settings.py:697-702`).
- This matches CONTEXT D-04 literally ("pending = absent keys"), so it is a spec gap and not an implementation bug. The effect is only a missing `≈` marker. Apply behavior is correct.
