## Summary

The settings writer changes hold up. `skip_recorded` drops only keys recorded for the same setting and file. The ledger keeps those entries, so a RECONFIGURE never rewrites a key the user deleted, and an install or reinstall still does. All 11 call sites of `adapters`, `settings_file` and the revert path pass `environ`. A COPILOT_HOME change between install and removal fails closed, as D-21 accepts (scratch repro: both groups refused with `NOT_A_SETTINGS_FILE`, and the file is left alone). The shell-init written-once record is set after the block write, cleared per tool in `_after_removal` only when the sweep did not fail, and cleared on both full-uninstall routes. The 23.2-02 indicator hides while a prompt is open and re-arms only on close. The 23.2-06 `docker`-only record is correct, because the template already wrote `git`. Dropping the 23.2-08 78-character cap is safe, since `StatusLine` uses `height: auto` and wraps. The test sandbox clears `COPILOT_HOME`. No `sudo`, `pkexec`, `doas` or `chsh` call was added. A grep finds none of the deleted run-option or Policies symbols left in `installer/` or `setup.py`. `tests/test_post_install.py`, `tests/test_agent_settings.py` and `tests/test_session.py` pass.

## Critical Issues

### CR-01 (High): F-1 PATH repair is skipped when the ban's pnpm redirect shim is on PATH

**File:** `installer/session.py:507-514` (`_put_present_bin_dir_on_path`), interacting with `installer/guards.py:429-446` (`real_pnpm`) and `installer/guards.py:510-544` (`install_global_redirect_shims`)
**Issue:** The repair is guarded by `if shutil.which(tool.cmd) is not None: return`. With the ban on and volta present, `install_global_redirect_shims` writes a `pnpm` redirect shim into `~/.local/bin`, which is on PATH. `shutil.which("pnpm")` returns that shim, so the repair returns early and never puts `~/.local/share/pnpm/bin` on PATH. `executors._node` then calls `real_pnpm()`, which deliberately refuses the installer's own shim and returns `None`. The mmdc/puppeteer row fails again, now with the new "pnpm is installed at … open a new terminal" message. This is the UAT F-1 scenario on a ban plus volta host, so SPEC R12 ("the dependent install in the same session finds and runs it") is not met there. The unit test only covers a PATH with no shim.
**Reproduction (scratch HOME):**
```
shim is ours: True
shutil.which(pnpm): /tmp/cr232-deep-home-…/.local/bin/pnpm
PATH after repair: /tmp/cr232-deep-home-…/.local/bin:/usr/bin:/bin   # unchanged
real_pnpm(): None
```
**Fix:** use the same shim-aware question that `present_bin_dir` and `real_pnpm` already answer:
```python
from installer.guards import real_binary
from installer.locations import bin_dir

def _put_present_bin_dir_on_path(outcome: RowOutcome, ctx: RunContext) -> None:
    tool = ctx.catalog.get(outcome.row.tool_id)
    if outcome.result not in {"skipped", "done"} or tool is None:
        return
    path_value = os.environ.get("PATH", "")
    if real_binary(tool.cmd, shim_dir=bin_dir(None), path_value=path_value) is not None:
        return  # a real binary, never our own shim, already answers
    found = present_bin_dir(tool)
    if found is not None:
        prepend_path(found)
```
Add a test with a redirect-sentinel `~/.local/bin/pnpm`, a real `~/.local/share/pnpm/bin/pnpm`, and a pnpm SKIP + mmdc plan. Assert that the runner receives the real pnpm path.

## Warnings

### WR-01 (Medium): a non-object parent shows a `≈` that RECONFIGURE never clears

**File:** `installer/agent_settings.py:1039-1052` (`setting_facts`), compared with `installer/agent_settings.py:681-684` (`_apply_pass`)
**Issue:** `setting_facts` classifies each key through `lookup`, which returns `ABSENT` when a parent is not an object. `_apply_pass` checks the parent first and reports the key as `set_by_you`, with no write and no ledger entry. So a file such as cursor-agent `{"attribution": false}` or claude `{"permissions": "…"}` reads `absent` on every state pass. `_agent_tuning_fact` raises `≈ install tuning not applied` with the step, and RECONFIGURE writes nothing and records nothing, so the next pass shows `≈` again. This breaks SPEC R2 ("A key 'set by you' never raises `≈`").
**Reproduction:** two rounds of facts then `apply_setting(..., skip_recorded=True)` on `{"attribution": false, "approvalMode": "unrestricted"}`: each round prints `absent=('attribution.attributeCommitsToAgent', 'attribution.attributePRsToAgent')`, and the apply returns `set_by_you` for both. The ledger stays `None`.
**Fix:** use `_apply_pass`'s parent rule in `setting_facts`:
```python
for key in setting_keys(agent, setting, platform_os):
    if key.path in recorded:
        continue
    parent = lookup(doc, key.path[:-1])
    if parent is not ABSENT and not isinstance(parent, dict):
        set_by_you.append((".".join(key.path), _dump(parent)))
        continue
    current = lookup(doc, key.path)
    ...
```
Add a regression test that runs `_agent_tuning_fact` on that fixture and expects no step.

### WR-02 (Medium): a pre-existing empty settings file does not revert byte-identical

**File:** `installer/agent_settings.py:637-646` (`_text_of`), `installer/agent_settings.py:861-877` (`_revert_once`)
**Issue:** A 0-byte or whitespace-only file is read as `new_file_text(fmt)` (`"{}\n"`) and written with the keys. Because the file existed (`snap is not None`), it is not added to `created_files`. On removal the keys are cut, the result is not deleted, and `{\n}\n` is written. Before this phase, this edge needed an explicit opt-in. Now every agent install hits it, and an agent that touches an empty `settings.json` on first launch makes it a normal case. This breaks SPEC R3 ("a file whose only change was the installer's keys returns byte-identical").
**Reproduction:** claude and copilot with a 0-byte `settings.json`: install both groups, then `revert_agent`. Result: `after revert exists: True bytes: b'{\n}\n'` for both agents.
**Fix:** record a blank original the same way a created file is recorded, for example a `blank_files` tuple in `ConfigLedger` set when `snap is not None and not snap.data.strip()`. In `_revert_once`, when the result is bare (`{}`) and the file is in `blank_files`, write back the original bytes (or `b""`) with `write_if_unchanged`. Add a test for each format, including codex TOML, where `new_file_text` is `""`.

### WR-03 (Low): the settings notes fire for updates, removals and reconfigures

**File:** `installer/render.py:343-350` (`_settings_lines`)
**Issue:** `done = {… if outcome.result == "done"}` does not check the disposition. An UPDATE, REMOVE or RECONFIGURE of cursor-agent, codex, opencode or pi that ends `done` prints the "Agent and editor settings" header with "cursor-agent: the Cursor CLI ignores the commit opt-out", "codex, opencode, pi: no documented attribution key; nothing written" or "pi: nothing written …". Nothing was tuned in that run. A removal can print a tuning note for the tool it just removed. The old code limited these notes to runs where the option was chosen.
**Fix:** limit the notes to install-route rows:
```python
installed = {
    o.row.tool_id for o in outcomes
    if o.result == "done"
    and o.row.disposition in {Disposition.INSTALL, Disposition.REPAIR, Disposition.REINSTALL}
}
```
Add a render test with a done UPDATE of codex that expects no settings section.

### WR-04 (Low): RECONFIGURE reports `done` when the Oh-My-Zsh plugin write was refused

**File:** `installer/session.py:359-366` (`_install_tuning_step`), `installer/post_install.py:210-224` (`_tune_omz_plugins`)
**Issue:** `_install_tuning_step` fails the step only for a refused `FileResult`. `_tune_omz_plugins` turns every `OSError`, including `OmzPluginsError` for "changed while it was being written", an unwritable `.zshrc` or a refused array, into a `Plugins not changed: …` line. That line becomes a warning, and the row ends `✓ done`. `plugins_refusal` only predicts the array refusal, so for the other causes the next state pass shows `≈ apply install tuning` again. The run log says the tuning succeeded, and the user can loop with no failure signal.
**Fix:** have `_tune_omz_plugins` return its refusal as data, for example `PostInstallOutput(lines=…, refused=reason)`, or let `apply_install_tuning` collect it. Make `_install_tuning_step` fail on it the way it fails on a refused settings file. Install-time dispatch can still treat it as a warning.

### WR-05 (Low): post-install actions are not isolated from each other, so one crash drops the chsh handoff and later tuning

**File:** `installer/post_install.py:312-329` (`run_post_install`), `installer/engine.py:386-396` (`_dispatch_post_install`), `installer/tweaks.py:395` (`_store_shell_init_record`)
**Issue:** `run_post_install` builds its lines in a local list. Any exception escapes to `_dispatch_post_install`, which returns an empty `PostInstallOutput()`. For oh-my-zsh (`set_login_shell`, `set_omz_theme`, `set_omz_plugins`), an `OmzPluginsError` from `apply_theme`'s new `_snapshot_text` has several causes: a non-UTF-8 `.zshrc`, a `.zshrc` over 16 MiB, or one that is not a regular file. Any of them discards the R8 `chsh` handoff that was already produced and skips `set_omz_plugins`. Separately, `_store_shell_init_record` uses `rc_path.read_text()`, which raises `UnicodeDecodeError`, a `ValueError` and not an `OSError`, on a non-UTF-8 `~/.myshellrc`. That happens after `tweak_policy(...).apply()` has already written the block, so the row reports a crash for a write that succeeded. Elsewhere `bundle_marker_present` reads the same file with `errors="replace"`.
**Fix:** isolate each action inside `run_post_install`. Wrap each `action(...)` call, keep the output already gathered, and add one `"<action> crashed: <first line>"` warning per failure. In `_store_shell_init_record`, read through `read_capped(..., follow_symlinks=True)` and decode the way the rest of `tweaks.py` does.

### IN-01: `omz_plugins_policy` and `TUNING_ACTIONS` have no production caller

**Category:** necessity
**File:** `installer/policy.py:730`, `installer/post_install.py:289`
**Issue:** D-09 says `omz_plugins_policy` "stays as the writer and remover closures behind those paths". A search finds no caller in `installer/` or `setup.py`. The full-uninstall sweep uses `uninstall._omz_policy` (`uninstall.py:621`), and the only remaining callers are 8 tests. `TUNING_ACTIONS` is referenced nowhere, since `apply_install_tuning` branches on literal names. vulture at `min_confidence = 80` misses both, as D-10 warned.
**Fix:** delete `TUNING_ACTIONS`. Either delete `omz_plugins_policy` and point its tests at `write_plugins` and `uninstall._omz_policy`, or record it for the Phase 25 dead-code sweep.

### IN-02: a relative COPILOT_HOME silently moves tuning to a file copilot does not read

**File:** `installer/agent_env.py:40-43`
**Issue:** A relative `COPILOT_HOME` is ignored and `~/.copilot/settings.json` is tuned, while copilot itself reads the directory relative to its working directory. Nothing tells the user, and the summary names a file the agent will not read.
**Fix:** when `COPILOT_HOME` is set but not absolute, return a refused `FileResult` such as "COPILOT_HOME is relative; nothing written", instead of falling back to the default.

### IN-03: heartbeats catch up one per tick after a stalled event loop

**File:** `installer/execute_screen.py:818-828`
**Issue:** `if elapsed >= HEARTBEAT_SECONDS * (heartbeats + 1)` adds one heartbeat per tick. If the loop stalls, for example under a heavy RichLog burst or a suspended terminal, and the next tick sees 21 s, the screen writes "still running (21s)" and one second later "still running (22s)". SPEC R10 asks for one line per further 10 s.
**Fix:** `self._silence_heartbeats = int(elapsed // HEARTBEAT_SECONDS)` when writing, so a late tick writes one line for the current 10 s window.

### IN-04: the container revert probe no longer checks byte identity or file removal

**File:** `scripts/container-e2e-verify.sh` (`settings_probe_revert`, around lines 905-935)
**Issue:** The probe checks only that each tuning key is absent, or holds its CLI default. The container starts with no settings files, so every tuned file is installer-created and should be gone after the uninstall. A leftover `{\n}\n` or a file with stray bytes still passes. The SPEC R3 byte-identity acceptance therefore rests only on unit tests.
**Fix:** for each checked agent, also print a finding when `settings_file(...)` still exists. In this container every such file was created by the installer.

### IN-05: the D-24 repair puts the whole bin dir in front of PATH

**File:** `installer/session.py:513-514`, `installer/locations.py:132-137`
**Issue:** `prepend_path` puts the dir first. For a SKIP volta row, `~/.volta/bin` holds `node`, `npm`, `npx`, `pnpm` and `yarn` shims, and they now come before the ban dir `~/.local/bin` for the rest of the run. A fresh install already does the same through the engine, and `shell_path` demotes the managed dir for spawned scripts, so this is consistent and not a regression. Still, "never reorders a working PATH" only holds for `tool.cmd`.
**Fix:** none required. Optionally append the dir instead of prepending it when the tool's own command is the only one needed.

## Checked and found correct

- `skip_recorded`: filtered by `entry.setting == setting and entry.file == file`. Skipped keys produce no result, no write and no ledger change. An install or reinstall (`False`) rewrites a deleted recorded key and replaces its entry.
- COPILOT_HOME threading: every writer, reader and revert call site passes `environ`. A COPILOT_HOME that changed by removal time is refused per file, and the ledger is kept (repro 2).
- Revert order and created-file deletion across the two claude groups that share one file: the first revert writes, and the last one deletes the bare created file.
- Shell-init record: comment-only closed block, `read_record` orphan rule, `forget_shell_init` only when the sweep did not fail, `clear_shell_init_record` on both full-uninstall routes, and `remove_managed_block` never deletes the file.
- 23.2-02: on prompt open, the generation is bumped, the timer stopped and the indicator hidden. On close, the window is reset and re-armed once. A late close after the run ends arms a timer that returns at once.
- 23.2-06: the record holds `docker` because the theme action's template already wrote `plugins=(git)`. Removal therefore restores the template's `plugins=(git)`. The record-before-refusal order never flags a host that is already tuned.
- 23.2-08: the 78-character cap is not a render contract (`StatusLine { height: auto }`). The narrowed 80x20 test still covers the only Phase 23 row that remains.
- Copilot `github_release`: `{arch.x64}` renders `x64` or `arm64` (`installer/assets.py:17-21`), matching `copilot-linux-{x64,arm64}.tar.gz`. A Linux cask resolves only for ownership. Upstream asset contents were not re-downloaded in this lane.
- Host safety: `COPILOT_HOME` was added to `CLEARED_ENV_NAMES`. HOME and PATH are restored through monkeypatch, so the PATH change from `prepend_path` does not leak between tests. The diff adds no `sudo`, `pkexec`, `doas` or `chsh` call.
