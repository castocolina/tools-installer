## Summary

The phase is mostly re-plumbing, not new machinery. The writer, ledger, revert, pending-fact and RECONFIGURE patterns all exist (`agent_settings.apply_setting`, `setting_facts`, `_hook_fact`, `session._run_step`). The work is: (1) a new richer post-install action result that carries `FileResult`s, (2) a ledger-aware `skip_recorded` flag, (3) a per-tool pending fact, (4) deleting a large, enumerated body of run-option/Policies code and rewriting its tests, (5) an execute-screen indicator rewrite, (6) a generic PATH repair for present dependencies, (7) one catalog entry.

Three findings the planner must act on that CONTEXT does not state: (a) CONTEXT's line anchors for `version_status.py` are stale (the file shifted); use the anchors below. (b) D-20's `requires = ["pnpm"]` is tool-level and OS-agnostic (`installer/deps.py:67-75` walks `tool.requires` with no method filter), so copilot on macOS (cask) would still drag pnpm into the plan; upstream also ships standalone, checksummed release tarballs that need neither Node nor pnpm (Q1). (c) The npm package carries no `engines` field and the current upstream README no longer states a Node floor, so D-20's "Node 22+ floor" is UNVERIFIED.

**Primary recommendation:** Build in the CONTEXT wave order; make `post_install` actions return a small `PostInstallOutput(lines, settings)` dataclass; add one `agent_settings.TUNING_GROUPS` table and an `absent` field on `SettingFacts` so install, RECONFIGURE and the pending fact share one definition; thread an explicit `environ` only through the five surviving agent_settings call sites for `COPILOT_HOME`; resolve Q1 with the user before writing copilot's registry entry.

### Pattern 1: One tuning definition shared by install, pending fact, RECONFIGURE
**What:** `TUNING_GROUPS: dict[str, tuple[str, ...]]` in `agent_settings` (claude: auto-approve, no-attribution; codex: auto-approve; opencode: auto-approve; cursor-agent: auto-approve, no-attribution; copilot: auto-approve, no-attribution; vscode: vscode-lean, vscode-ai-off, vscode-ext-updates-off). `setting_keys(agent, group, os)` is already the per-group key table. `vscode-lean` is not in `_KEYS` (it is built by `_vscode_lean(platform_os)`), so derive `TUNING_GROUPS` explicitly rather than from `_KEYS.keys()`.
**When:** install action, `install_tuning` step, pending fact, tests ("exactly its keys").

### Pattern 2: Pending = absent and unrecorded
Add `absent: tuple[str, ...]` to `SettingFacts` (`agent_settings.py:924-931`), filled in the existing loop at `:965-973` where `current is ABSENT and key.path not in recorded`. `drifted` (recorded then changed or deleted, `:957-961`) and `set_by_you` never raise `≈`. A cursor key holding `cli_default` is neither absent nor set-by-you at `:971`, so it does not raise `≈` (D-06) with no extra code.

### Pattern 3: `skip_recorded` inside `_apply_pass`
`_apply_pass(text, fmt, setting, file, keys)` (`:644-678`) branches on `current is ABSENT` at `:658`. Add a `recorded: frozenset[KeyPath]` parameter (from `ledger.entries` filtered by setting+file, read in `_apply_once` at `:700`) and `continue` (no result entry, or a new `KeyKind`? see Pitfall 4) when `skip_recorded and key.path in recorded`. Install/reinstall pass `False` so an explicit reinstall rewrites a deleted key (SPEC R2).

### Anti-Patterns to Avoid
- **Second writer for RECONFIGURE:** D-03 forbids a pre-filtering caller; keep one writer.
- **Reading `os.environ` inside `agent_settings`:** inject (see COPILOT_HOME below).
- **Renaming setting groups:** orphans ledger entries written by the old Policies rows (D-02).
- **Dispatching tuning on the ALREADY_INSTALLED path:** `engine.py:199-201` returns before any dispatch; RECONFIGURE is the route for present tools, by design.

### Applicable ASVS Categories (level 1, `security_enforcement: true`)

| ASVS Category | Applies | Standard Control |
|---------------|---------|-----------------|

### Known Threat Patterns

| Pattern | STRIDE | Standard Mitigation |
|---------|--------|---------------------|
| Tuning overwrites a user's value or deletes a user-changed key | Tampering | absent-only rule, "set by you", revert only values still equal to ours (`key_held`) |
| Write through a symlinked or concurrently edited settings file | Tampering | compare-before-commit `write_if_unchanged`, symlink refusal, retry-once on `SettingsChanged` |
| Tuning targeted at project/local scope | Elevation | adapters return user paths only; test pins it |
| `chsh`/sudo run by the installer | Elevation | action prints text only; test asserts no `chsh` runner call |
| Hostile `COPILOT_HOME` pointing at an arbitrary file | Tampering | the writer only edits the JSONC `settings.json` named by the adapter; revert refuses a ledger file not equal to the current adapter path (`NOT_A_SETTINGS_FILE`); do not follow `COPILOT_HOME` into a path outside the user's home without a check (decide at plan time; recommend rejecting a `COPILOT_HOME` that is not under home) |
| Auto-approve/bypass keys widen agent power | Elevation | user decision (TUNE-01); never write project scope; `defaultPermissionMode` is ignored in non-interactive runs per upstream docs |
| Logging settings contents/tokens | Information disclosure | log key names only; secret handling owned by bandit and `/gsd-secure-phase` |
