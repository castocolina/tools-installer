## Should fix

### PT-01 (Medium) The PATH repair for a present dependency does nothing when the installer's own pnpm shim is on PATH
- **File:** `installer/session.py:501-514` (`_put_present_bin_dir_on_path`, guard at `:510`)
- **What this is:** SPEC R12 / UAT F-1. After a SKIP or done row, the tool's declared `bin_dir`
  is put on the process PATH so dependents (mmdc needs pnpm) find it.
- **Problem:** The guard is `shutil.which(tool.cmd) is not None`. When the Policies `ban` row is
  on, `~/.local/bin/pnpm` is this installer's redirect shim (`guards.GLOBAL_REDIRECTED["pnpm"]`),
  so `which` finds the shim and the repair returns early. `guards.real_pnpm()` then skips the
  shim and finds nothing. Reproduced: shim in `~/.local/bin`, real pnpm in
  `~/.local/share/pnpm/bin`, PATH without it -> PATH unchanged after the SKIP row,
  `real_pnpm()` is `None`. The mmdc row still fails, now with "open a new terminal" instead of
  the old wrong advice. `status.present_bin_dir` already treats the shim as not-the-tool, so
  the two halves of D-24 disagree. No test plants a shim (`tests/test_session.py:1677-1790`).
- **Fix:** Treat our shim as not found: replace the guard with
  `found = shutil.which(tool.cmd); if found is not None and not is_our_shim(Path(found)): return`
  (`guards.is_our_shim`). Add one session test that plants a redirect-sentinel `pnpm` first on PATH.
- **If we skip it:** F-1 stays open for every user who has the ban on, which is this
  installer's headline feature.

### PT-02 (Medium) A non-object parent key leaves `≈` on forever and RECONFIGURE cannot clear it
- **File:** `installer/agent_settings.py:1038-1049` (`setting_facts`), against `:683-712` (`_apply_pass`)
- **What this is:** `setting_facts` decides which keys are "absent and never recorded", and
  that drives the `≈` + "apply install tuning" step.
- **Problem:** For `{"attribution": "none"}` (or `"permissions": null`), `lookup()` returns
  ABSENT for `attribution.commit` because the parent is not an object, so `setting_facts` calls
  it absent. `_apply_pass` sees the same file differently: parent not a dict -> `set_by_you`,
  nothing written, nothing recorded. Reproduced on claude: round 1 and round 2 both report
  `attribution.commit` and `attribution.pr` as pending, after RECONFIGURE ran in between.
  SPEC R2 says a key "set by you" never raises `≈`.
- **Fix:** Mirror `_apply_pass` in `setting_facts`: before the `current is ABSENT` branch,
  `parent = lookup(doc, key.path[:-1])`; if `parent is not ABSENT and not isinstance(parent, dict)`
  append to `set_by_you` and `continue`. Add one test with a string-valued `attribution`.
- **If we skip it:** The row shows `≈` on every refresh, the user selects it, the step reports
  done, and the `≈` returns. It reads as a broken installer.

### PT-03 (Medium) One action that raises discards every other action's output
- **File:** `installer/post_install.py:311-329` (`run_post_install`), triggered by `:183-206` (`_set_omz_theme`)
- **What this is:** `run_post_install` loops over a tool's actions and collects lines and
  settings. This phase put three more actions (plugins, shell init, agent tuning) in the same loop.
- **Problem:** `_set_omz_theme` has no `OSError` guard (`_tune_omz_plugins` has one). With a
  non-UTF-8 `.zshrc` (a Latin-1 comment, which `omz._read_rc` documents as realistic),
  `ensure_zshrc_template`/`apply_theme` raise `OmzPluginsError`. The exception leaves
  `run_post_install`, `engine._dispatch_post_install` turns it into one "crashed" warning and
  returns an empty `PostInstallOutput`. Reproduced: `run_post_install(oh-my-zsh)` raised.
  SPEC R8 says the `chsh` handoff prints on every route, but that line (returned by the earlier
  `set_login_shell`) is lost, and `set_omz_plugins` never runs. Same shape for any tool that
  lists `apply_agent_tuning` before another action: settings already written vanish from the summary.
- **Fix:** Isolate per action inside `run_post_install`: `try: produced = action(...)` /
  `except Exception as exc: lines.append(f"{name} failed: {first line}")` and continue. Keep the
  engine-level catch as the backstop. One test: a raising action between two good ones.
- **If we skip it:** A hand-edited `.zshrc` silently drops the login-shell instructions and the
  plugins, and shows one vague crash line.

### PT-04 (Low) `setting_state` and most of `SettingFacts` are dead since the Policies rows went

### PT-05 (Low) `TUNING_ACTIONS` is unused, and the tuning dispatch is written twice
- **File:** `installer/post_install.py:288-309`, wrappers at `:166-172`, `:226-232`, `:259-265`
- **What this is:** `apply_install_tuning` (RECONFIGURE) walks `tool.post_install` with an
  `if name == ...` chain; `run_post_install` walks the same list through `POST_INSTALL_HOOKS`.
- **Problem:** `TUNING_ACTIONS` has no reader (verified by reference scan: one hit, its own
  definition). The three wrapper functions (`_source_shell_init`, `_set_omz_plugins`,
  `_apply_agent_tuning`) only call `del confirm` and forward `skip_recorded=False`. A fourth
  tuning action means editing two dispatchers.
- **Fix:** Delete `TUNING_ACTIONS`. Make one table
  `_TUNING = {"apply_agent_tuning": _tune_agent, ...}` with one signature taking `skip_recorded`;
  `run_post_install` calls it with `False`, `apply_install_tuning` with the caller's value.
  That removes the three wrappers and the `isinstance(produced, PostInstallOutput)` branch.
- **If we skip it:** Harmless today; the next tuning action (24.1 adds neovim shell init) must
  be wired in two places and one will be forgotten.

### PT-06 (Low) "no documented attribution key" notes print after any plain update
- **File:** `installer/render.py:343-350` (`_settings_lines`)
- **What this is:** The summary's "Agent and editor settings" block, after the run options went.
- **Problem:** The notes key on `outcome.result == "done"` for any disposition. A `u` update
  of codex ends "done" (`session.py:622-628`), so `codex, opencode: no documented attribution
  key; nothing written` and the cursor-agent line print under a header although no tuning ran.
  The old code gated them on a chosen run option.
- **Fix:** Build `done` only from outcomes whose disposition is INSTALL, REPAIR, REINSTALL or
  RECONFIGURE (the rows that can tune). One test: an UPDATE row prints no settings block.
- **If we skip it:** Noise after every agent update, saying "nothing written" when nothing was
  meant to be.
