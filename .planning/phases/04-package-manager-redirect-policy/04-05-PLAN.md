<objective>
Ship the snapshot-and-reinstall mitigation for the pnpm-managed global set that survives
the Volta split, as a manually-invokable Doctor remediation: a read-only audit that
reports when a `pnpm add -g`-installed command has gone missing, and an explicit action
that reinstalls the whole set in one `pnpm add -g` call.

Purpose: D-08 and R-03. The residual set is NOT empty — `mmdc` is the registry's only
`kind="node"` tool and moving it off pnpm is Phase 5's decision, not this phase's — so
the requirement cannot be closed by elimination. `installer/executors.py::_node` calls
`pnpm add -g` directly through the `Runner` seam and never resolves through the PATH
shims, so plans 04-01 and 04-03 do not cover it.

Decisions implemented:
- D-08: the residual `pnpm add -g` set is determined after the volta split rather than assumed empty, is found to contain `mmdc`, and the requirement's original snapshot-reinstall mechanism is implemented for it in this phase.
- D-06: the volta split removes user-typed global installs from pnpm, which is precisely why the remaining exposure is the internal `kind="node"` executor and not the shell layer.
- R-03: the mechanism ships as a manually-invokable Doctor remediation, audit-only until invoked, taking no dependency on Phase 12's not-yet-built update action.

Output: `installer/pnpm_globals.py`, its guidance/render surface, and a second explicit
action on the Doctor view, wired through `VIEWS`, `run_live` and `setup.py`.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| registry → `pnpm add -g` argv | Package names read from the registry become subprocess arguments. |
| user keypress → real installation | A single key in the Doctor view triggers a real package install on the machine. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-04-16 | Tampering | `reinstall_argv` package names | medium | mitigate | Names come only from the trusted, in-repo `registry.toml`, are validated non-empty by `load_tools`' `kind="node"` check, and are passed as a discrete argv list through the `Runner` seam — never a shell string. |
| T-04-17 | Elevation of Privilege | an unintended keypress installing packages | medium | mitigate | The remediation is explicit and single-purpose: it reinstalls exactly the registry's own `kind="node"` set and nothing else, it is a no-op on an empty set, and there is no automatic trigger (R-03). ONESHOT-RULES Rule 5 forbids pressing it during the phase's TUI review. |
| T-04-18 | Denial of Service | a failed reinstall leaving the screen wedged | low | mitigate | The action goes through `ui_common.run_live`, which is the codebase's existing error boundary; the screen records the error and stays usable, mirroring `action_apply`'s failure branch. |
| T-04-19 | Elevation of Privilege | npm/pnpm postinstall scripts during the reinstall | medium | accept | The reinstall uses pnpm, whose postinstall gating (pnpm v10+, `pnpm.io/supply-chain-security`) is the stronger of the two models available here — this is exactly the security property the phase preserves by keeping `kind="node"` tools on pnpm rather than moving them to volta. |
| T-04-SC | Tampering | npm/pip/cargo installs | high | mitigate | The reinstall installs `registry.toml`'s existing `kind="node"` packages, which were vetted when their entries were authored; this plan adds no new package. 04-RESEARCH.md's Package Legitimacy Audit records that the phase introduces no new PyPI/npm/crates dependency. |
</threat_model>
