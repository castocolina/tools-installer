## Summary

Neovim fits the existing machinery with no new method kind. Upstream v0.12.6 (published 2026-10-09) is still `latest`. It ships `nvim-{linux,macos}-{x86_64,arm64}.tar.gz`. Each asset has a GitHub API `sha256` digest, and the release has **no checksum file**. Each tarball has one top directory holding `bin/ lib/ share/`, so `strip = 1`, `member = "bin/nvim"` installs into `~/.local/opt/nvim` with a `~/.local/bin/nvim` link through the generic `artifact_paths` and receipt path. herdr is the registry precedent for API-digest verification without a checksum file. The resolver sorts by `_RANK`, so the effective order is release, then native handoff, then brew on mutable Linux, and release, then brew on Bazzite and macOS.

The `EDITOR`/`VISUAL` line belongs in the existing `SHELL_INIT_TOOLS` path. Most work comes from three small consequences:
- The bundle guard is `command -v nvim`, not `command -v neovim`, which breaks a parametrized test that assumes guard name equals tool id.
- The D-14 yield gate has to be consulted by both the writer (`_tune_shell_init`, used by install and RECONFIGURE) and the pending fact (`_shell_init_tuning_fact`). Otherwise a user with `export EDITOR=vim` sees a permanent `≈`.
- The scan has to treat the installer's own *consolidated shellrc* block as user content. That block holds lines moved out of the user's `~/.shellrc`.

`path_scan_rc_paths()` is already the read-only set of every login and interactive startup file. Reuse it as the scan set.

The kickstart pin `8e35dbed…` is still `master` HEAD. A one-line patch (`servers = {}` after the table) passes `git apply --check` at the pin. It empties Mason's `ensure_installed` (computed from `servers`) and the `vim.lsp.enable` loop. A disposable Debian 13 container ran the product-shaped flow: tarball, pinned clone, patch, headless first launch (18 plugins in 43 s, exit 0, because `vim.fn.confirm` returns its default `Yes` headless), then opening py/lua/ts/go/java. It measured **0 LSP clients, 0 server processes, and no Mason packages dir**. Two facts change the e2e plan:
- `nvim --version` (the D-06 smoke and the status probe) creates `~/.local/state/nvim/nvim.log`. The shared passes therefore need a residue-allowlist entry.
- A real launch creates `~/.local/share/nvim`, `~/.local/state/nvim/shada` and `~/.cache/nvim`. The LSP check should point `XDG_DATA_HOME`/`XDG_STATE_HOME`/`XDG_CACHE_HOME` at a temp dir.

**Primary recommendation:** Add the registry entry, append a `neovim` shell-init bundle with a data-driven yield list, and add one starter action plus one static-hints action. Leave the receipt/removal code untouched. Prove the git paths only in the container, with the XDG-redirected headless check.

### Anti-Patterns to Avoid
- **Reading `os.environ["EDITOR"]` for the yield gate.** It reports OS defaults, such as `/etc/profile.d/nano-default-editor.sh`'s `-z`-guarded export, as if they were the user's.
- **A receipt record for the starter tree.** A default removal would delete the user's config (D-18).
- **Adding `git` to the sandbox allowlist** to test the starter. 23.1 forbids it. Fake the runner.
- **A Policies row for either item.** TUNE-04.
- **A hand clone in the LSP check.** D-20: the check must use the tree the installer produced.

## Common Pitfalls

### Pitfall 1: Guard name ≠ tool id breaks a parametrized test
**What goes wrong:** `test_each_shell_init_body_is_guarded_and_parses` asserts `bundle.body.split("\n")[0] == f"if command -v {tool} >/dev/null; then"` for every id in `SHELL_INIT_TOOLS` (`tests/test_tweaks.py:355-366`). For `neovim` the guard is `command -v nvim`.
**How to avoid:** Derive the expected guard from the registry `cmd` (or a bundle-level command), not the id. Update the test in the same commit.
**Warning sign:** red `test_tweaks.py[neovim]`.

### Pitfall 2: Permanent `≈` for a user who set their own editor
**What goes wrong:** `_shell_init_tuning_fact` raises `≈` whenever the block is absent and the id is unrecorded (`version_status.py:660-670`). A yielded neovim has neither.
**How to avoid:** Run the same yield helper there. Add a test: user `export EDITOR=vim` plus nvim present gives no `≈`. Removing the export gives `≈` with the step.

### Pitfall 3: The consolidated block is user content
**What goes wrong:** A blanket "skip every `tools-installer` block" rule ignores an `export EDITOR=…` that consolidation moved from `~/.shellrc` into `~/.myshellrc`. Neovim would then override the user.
**How to avoid:** Skip only blocks the installer generates. Treat `# >>> tools-installer consolidated shellrc >>>` as user content. Add a test.

### Pitfall 4: `nvim --version` leaves `~/.local/state/nvim/nvim.log`
**What goes wrong:** The D-06 smoke and every status probe run `nvim --version`. The container showed it creates `~/.local/state/nvim/nvim.log`. The shared-pass leftover check (`new_leftovers`) flags any new path outside `config_paths` and the allowlist.
**How to avoid:** Add `.local/state/nvim  # nvim's log dir, written by its own --version run (smoke and status probe)` to `scripts/e2e-residue-allowlist.txt`, mirroring `.local/state/gh` (line 26). `[VERIFIED: container probe Q2]`

### Pitfall 5: A real nvim launch writes data, state and cache
**What goes wrong:** A first launch creates `~/.local/share/nvim` (18 plugins), `~/.local/state/nvim/shada`, `~/.cache/nvim/*` and `~/.config/nvim/nvim-pack-lock.json`.
**How to avoid:** The LSP check exports `XDG_DATA_HOME`, `XDG_STATE_HOME` and `XDG_CACHE_HOME` to one `mktemp -d` outside HOME and removes it. Nvim honors these (`runtime/doc/starting.txt:1378-1411`). Only `nvim-pack-lock.json` remains, inside `~/.config/nvim`, which `config_paths` already allows. The Mason assertion then reads `$XDG_DATA_HOME/nvim/mason/packages`. `[VERIFIED: container Q4/Q6; starting.txt]`

### Pitfall 6: The Mason dir does not exist at all
**What goes wrong:** An assertion such as "Mason packages dir is empty" that requires the dir fails, because after launch `stdpath("data")/mason/packages` was **absent** (`exists=0`).
**How to avoid:** Assert "absent or empty". `[VERIFIED: container Q7]`

### Pitfall 7: Treesitter noise is not a failure
**What goes wrong:** nvim-treesitter `main` downloads parsers and calls the `tree-sitter` CLI. The containers lack it: Fedora/Debian/Arch prereqs install a compiler and make, not `tree-sitter`. Stderr fills with `ENOENT … 'tree-sitter'`, and with tar errors from concurrent downloads, but nvim exits 0.
**How to avoid:** Parse the check's own marker lines (`clients=`, `mason=`) and never assert clean stderr. Bound the run with `timeout`. `[VERIFIED: container Q7; scripts/container-e2e-verify.sh:181-199]`

### Pitfall 8: Starter target vs `XDG_CONFIG_HOME` / symlink
**What goes wrong:** `config_paths` is the literal `~/.config/nvim` (`config_targets` expands it with `Path(entry).expanduser()`, `uninstall.py:119-121`). With an absolute `XDG_CONFIG_HOME` elsewhere, nvim reads a different dir, so a clone into `~/.config/nvim` would sit there unused. A symlinked `~/.config/nvim` is the user's.
**How to avoid:** Skip the starter with a reason when `xdg_config_base(home, os.environ) != home / ".config"` (`locations.py:57`) or when the target is a symlink. Discretion; flagged as A3.

### Pitfall 9: The resolver does not keep the declared order
**What goes wrong:** The SPEC edge row says "the resolver keeps the declared order". In code, `resolve_methods` sorts by `_RANK` (`resolve.py:95-98`): `"github_release": 20`, `"dnf": 30`, `"apt": 30`, `"pacman": 30`, `"brew": 40` (`resolve.py:13-27`). On a mutable distro the native handoff therefore ranks before brew.
**How to avoid:** Pin the *resolved* order in the test, not the declared order:
- mutable Fedora: `[github_release, dnf, brew]`
- Bazzite: `[github_release, brew]`, because native kinds return False when immutable (`resolve.py:89-91`)
- macOS: `[github_release, brew]`

`[VERIFIED: resolve.py]`

### Pitfall 10: Post-install never runs after a MANUAL handoff
**What it means:** A native handoff (Fedora 43's 0.11.6, Debian's 0.10.4) returns MANUAL_REQUIRED before `_dispatch_post_install` (`engine.py:258-268`). The starter therefore only ever runs after the installer itself placed a 0.12.x nvim (release or brew). A hand-installed old nvim is a SKIP, so no starter is placed. No version check is needed in the action. `[VERIFIED: engine.py]`

## Open Questions (RESOLVED)

1. **Does `vim.fn.confirm` in `vim.pack.add` block headless?** RESOLVED.
   In the container, `timeout 90 nvim --headless +qa </dev/null` on the patched pin exited 0 after 43 s. It printed `These plugins will be installed:` and installed 18 plugins (`LuaSnip blink.cmp conform.nvim fidget.nvim gitsigns.nvim guess-indent.nvim mason-lspconfig.nvim mason-tool-installer.nvim mason.nvim mini.nvim nvim-lspconfig nvim-treesitter plenary.nvim telescope-ui-select.nvim telescope.nvim todo-comments.nvim tokyonight.nvim which-key.nvim`). Source: `pack.lua:584` `vim.fn.confirm(confirm_msg, 'Proceed? &Yes\n&No\n&Always', 1, 'Question')` at v0.12.6, where the default is 1 (Yes) and headless returns it. The D-13 check can therefore drive the first launch headless. Interactive users still see the prompt, so keep the "open nvim once" summary line.
2. **Do `nvim --version` or a first launch create state/data dirs?** RESOLVED.
   `--version` creates `~/.local/state/nvim/nvim.log`. A headless start with no config adds `~/.local/share/nvim` and `~/.local/state/nvim/shada/main.shada`. The starter's first launch adds `~/.cache/nvim/*` and `~/.config/nvim/nvim-pack-lock.json`. Action: one allowlist line (Pitfall 4) plus an XDG redirect in the LSP check (Pitfall 5).
3. **What does nvim-treesitter `main` need in the containers?** RESOLVED.
   It needs the `tree-sitter` CLI (kickstart README:35 lists it, together with `git`, `make`, `unzip` and `gcc`). Without it the parser builds fail with `ENOENT … 'tree-sitter'`, nvim still exits 0, and LSP counts are unaffected. Don't install it in the e2e (not in scope). Tolerate the noise (Pitfall 7).
4. **Does zero-LSP stay stable as plugins float (no lockfile at the pin)?** RESOLVED (MEDIUM).
   The patch empties the only server sources: the `servers` table, which feeds `ensure_installed` and the enable loop. `automatic_enable = false` is pinned in init.lua, and nvim-lspconfig enables nothing by itself. A future plugin release cannot start a server that nothing enables or installs. The residual risk is only a kickstart re-pin, which is out of scope (a data change with a fresh `verified`). Measured: 0 clients, no server process, no Mason dir.
5. **Which shell files does the D-14 scan read?** RESOLVED.
   `path_scan_rc_paths()` (Pattern 2): `.myshellrc`, `.shellrc`, `$ZDOTDIR`-aware `.zshrc/.zprofile/.zshenv/.zlogin`, `.bashrc`, `~/.bashrc.d/*`, `.bash_profile`, `.profile`, on Linux and macOS alike. Managed blocks are skipped except the consolidated one. On this host, none of these files exports `EDITOR` or `VISUAL` (read-only grep this session).
6. **Should neovim keep `requires = ["git"]` (D-17)?** RESOLVED (provisional: CONTEXT D-17 amended 2026-11-13, needs user confirmation). Recommendation: drop it.
   `resolve_dependencies` drags a required tool into the plan and blocks the dependent when the dependency is unavailable and not installed (`deps.py:82-115`). git is a native handoff on mutable Linux (`registry.toml:294-317`). So on a mutable host without git and without brew, the nvim *binary* would be held behind git, though only the optional starter needs it. The best design has no tool-level `requires`; the starter checks `shutil.which("git")` and, when it is absent, returns the reason plus the manual commands, which D-15 already allows. The oh-my-zsh precedent differs: omz *itself* is a git clone. This amends D-17's last sentence. If the user declines, plan D-17 as written. Every supported host in practice has git (Bazzite base image, the macOS CLT, and the e2e prereqs at `container-e2e-verify.sh:181-199`).
7. **Which `verified` date?** RESOLVED (recommendation).
   The skill defines `verified = YYYY-MM-DD` as the date of the check (SKILL.md §9). D-02's `2026-10-13` predates this re-verification. Use the date of the executor's own live re-check, 2026-11-13 if it runs now, and keep 2026-10-13 in the `# Verified` history line.
8. **D-14 / D-15 confirmation.** RESOLVED (provisional: D-14/D-15 planned as written, raised by the 24.1-05 SUMMARY for confirmation).
   This is a decision, not a fact, so no research can close it. Plan as written. The plan should carry a `checkpoint:human-verify` before execution, or note that a reversal means re-adding a sensitive action (D-21).
9. **Where does `cmd_verify_nvim_lsp` run so that it "reuses the installer's tree" (D-20) yet stays "outside the matrix" (D-12)?** RESOLVED (recommendation).
   Add an `nvim-lsp` subcommand that acts on the already-bootstrapped container after `pass1`. `cmd_all` calls it only for `DISTRO=fedora`, between pass1 and pass2. The XDG redirect keeps the leftover check clean, and the container is removed by `cmd_all`'s existing trap in the same run. A separate fresh container would have to reinstall neovim through `--categories editor`, which drags in vscode, jetbrains-toolbox and sublime (registry lines 2438, 2504, 2554).
10. **Hints: one action or two?** RESOLVED (discretion).
    Use a separate static action that mirrors `_show_lean_tips` (`post_install.py:290-296`, `_LEAN_TIPS` at :142-145). The hints then survive a crashed starter: `run_post_install` turns one action's crash into a warning and continues (`post_install.py:349-354`).

### Known Threat Patterns
| Pattern | STRIDE | Standard Mitigation |
|---------|--------|---------------------|
| Tampered tarball | Tampering | API digest check before extraction (existing) |
| Moved or rewritten upstream branch | Tampering | Checkout by SHA, assert `HEAD == pin`, `apply --check` before apply |
| git credential prompt hangs the worker | DoS | `GIT_TERMINAL_PROMPT=0`, timeout, stdin not a TTY |
| Clobbering user config through a race or symlink | Tampering | lstat symlink refusal, re-check, rename fails on a non-empty target |
| Control characters from a user rc echoed to the terminal | Tampering | `sanitize_log_line` |
| argv injection | Elevation | argv lists only; no registry string reaches the git argv (pin, URL and patch path are code constants) |
