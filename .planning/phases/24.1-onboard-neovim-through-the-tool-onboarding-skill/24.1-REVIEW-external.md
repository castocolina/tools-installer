## Findings

### M-01 (was Lane A H-02, downgraded to MEDIUM): a reinstall that yields leaves the earlier neovim block in place

- **Location:** `installer/post_install.py:279-282` (`_tune_shell_init`)
- **Reported problem:** if the user's files export `EDITOR`/`VISUAL`, the yield returns `Kept your EDITOR=…` and stops. A `tweak:neovim` block written by an earlier install stays in `~/.myshellrc`.
- **Failure scenario:** the first install writes the block because no export exists. Later the user adds `export EDITOR=vim` to `~/.zshenv`, `~/.zprofile` or `~/.profile`, or higher up in `~/.myshellrc`, then reinstalls or updates neovim. The summary says the user's value was kept, but `~/.myshellrc` is sourced later (from `.zshrc`/`.bashrc`) and its block sets `nvim` again.
- **Verification:** holds. `_source_shell_init` passes `skip_recorded=False`, so the yield check runs, and it returns before any `strip_block`. `find_export` skips terminated installer blocks: a probe of `export EDITOR=vim` followed by a `tweak:neovim` block that sets `nvim` returns `('EDITOR', 'vim')`, so the block is ignored as a competitor and never removed. The case is narrower than reported. An export in `.zshrc`/`.bashrc` after the `~/.myshellrc` source line still wins. It needs a reinstall or update after the user added the export. Nothing is lost: the user gets the wrong editor and a false "Kept" line. **Downgraded to MEDIUM.**
- **Fix:** when yielding, strip the existing `tweak:neovim` block (the per-tool removal path already does this) and drop `neovim` from the shell-init record. Add a test: block present, then a `.zshenv` export, then reinstall leaves no block.

### M-02 (Lane B #2): a failed starter init can pass as a zero-LSP proof

- **Location:** `scripts/container-e2e-verify.sh:1699-1702`, `scripts/nvim-lsp-check.lua:59-60`
- **Problem:** the verdict needs both launches to exit 0 and the plugin directories to exist. Both launches send stderr to `first-launch.err`/`check.err`, and nothing reads those files (the parser comment at `:1596` says stderr is ignored). Headless `nvim` reports a Lua error in `init.lua` and still exits 0 through `+qa`/`qa!`.
- **Failure scenario:** a plugin API error stops `init.lua` before the LSP/Mason setup runs. The probe sees zero clients and no Mason packages and prints `TRACER_NVIM_LSP_OK`. That proves the setup failed, not that a working setup runs no servers.
- **Verification (orchestrator):** the stderr files are never read, confirmed with grep. The tests cover non-zero exits only.
- **Fix:** fail on `Error` lines in `check.err` apart from an explicit allowlist (the Treesitter noise), or have the check print a marker that the starter's LSP config loaded. Add a test where a Lua error comes with exit 0.

### M-03 (Lane B #1): the per-language check yields to the event loop only once, after the last buffer

- **Location:** `scripts/nvim-lsp-check.lua:50-55`
- **Problem:** all five files are opened in a row, then a single `vim.wait` runs with `A.java` current. A deferred FileType or BufEnter callback that looks at the current buffer would see Java, not the buffer it was scheduled for.
- **Verification (orchestrator):** the structure is as described. The real risk is low: `vim.lsp.enable` attaches on `FileType` for every matching buffer, and `server_processes()` also checks for server processes. `tests/test_container_e2e_receipts.py` checks only strings in the Lua source. Kept at MEDIUM as reported, with low plausibility.
- **Fix:** wait briefly after each `:edit`, and carry any client seen across files.

### M-04 (was Lane A H-01, downgraded to MEDIUM): a conditional empty assignment hides an earlier export

- **Location:** `installer/shellrc.py:1299-1305` (`find_export`)
- **Problem:** every parsed assignment counts as executed, the last one wins, and an empty value counts as unset.
- **Failure scenario:** the file has `export EDITOR=vim`, then `[ -n "$SSH_CONNECTION" ] && export EDITOR=`. Outside SSH the second line does not run, so the user's editor is `vim`. The scanner returns `None`, the bundle is written and sets `nvim`.
- **Verification:** holds. The probe returns `None` for that content. The trigger is rare: a conditional assignment that empties the variable after an unconditional export. Conditional non-empty assignments already fall on the safe side (they count as yields). No data loss. **Downgraded to MEDIUM.**
- **Fix:** treat a variable that ever had a non-empty live assignment as user-set, so an empty value never clears an earlier export. Add the reported case as a regression test.

### M-05 (Lane A #3): the manual recovery line does not quote the patch path

- **Location:** `installer/post_install.py:186-191` (`_by_hand`)
- **Problem:** `git -C ~/.config/nvim apply {_KICKSTART_PATCH}` puts the absolute patch path into the line unquoted.
- **Failure scenario:** with the installer checked out under a path that contains a space, the printed `git apply` line splits at the space and fails when pasted.
- **Fix:** `shlex.quote(str(_KICKSTART_PATCH))`. The `~/.config/nvim` target must stay unquoted so that `~` expands.
- *Severity note:* kept at MEDIUM as reported. It is only a printed instruction, so LOW would also be fair.

### L-01 (Lane A #4): the "no language server" hint shows even when the user's own config was kept

- **Location:** `installer/post_install.py:180-182` (`_NVIM_HINTS`)
- **Problem:** `show_nvim_hints` always says "Neovim runs no language server", including when `clone_nvim_starter` skipped because `~/.config/nvim` belongs to the user, who may have LSP set up.
- **Fix:** word it for the starter ("The kickstart starter runs no language server …"), or show it only when the starter was placed.
