# Phase 24.1: Onboard Neovim through the tool-onboarding skill — Specification

**Created:** 2026-10-13
**Ambiguity score:** 0.15 (gate: ≤ 0.20)
**Requirements:** 6 locked
**Amended:** 2026-11-07 (24.1 D-14..D-18: R4/R5 applied at install with no question, **needs confirmation**; edge table re-run)

## Goal

Neovim is in the catalog. It installs without sudo or a reboot on every supported OS and arch, including immutable Bazzite. Its removal is receipt-proven. The `EDITOR` choice and a no-LSP kickstart starter are offered only on "yes". *(amended 2026-11-07, 24.1 D-14/D-15, **needs confirmation**: under TUNE-04 both are applied at install with no question — `EDITOR`/`VISUAL` only when the user's own shell files set no editor, kickstart only into an absent or empty `~/.config/nvim`)*

## Background

Scouted and measured 2026-10-13:
- **Registry.** It has no `neovim`/`nvim` entry. Only `ToolCategory.EDITOR` exists (`installer/enums.py:49`).
- **Upstream.** Release `v0.12.6` publishes `nvim-linux-x86_64.tar.gz`, `nvim-linux-arm64.tar.gz`, `nvim-macos-x86_64.tar.gz` and `nvim-macos-arm64.tar.gz`, each with a GitHub `digest` sha256. It also ships AppImages and Windows assets.
- **Layout verified in a disposable Fedora container.**
  - The tarball holds `bin/`, `lib/` and `share/`.
  - It was extracted with `--strip-components=1` to `~/.local/opt/nvim` and symlinked from `~/.local/bin/nvim`.
  - Through the symlink, `nvim --version` prints `v0.12.6`, and `$VIMRUNTIME` resolves to `~/.local/opt/nvim/share/nvim/runtime`.
  - The extracted tree is 40 MB.
- **The existing installer already handles this tree.** `github_release` with `strip` extracts the whole archive into `opt_dir(<bin>)` and links the member (`installer/download.py:155-185`), so no new kind is needed.
- **kickstart.nvim.** Master is at `8e35dbedb7966e3a95e1f26f9fc1179ab6c68db4` (2026-10-03).
  - It uses `vim.pack`, and declares `local servers = { stylua, lua_ls }` (`init.lua:735-776`) plus Mason, mason-lspconfig and mason-tool-installer (:784-790).
  - Measured earlier: kickstart at 26 MB PSS, versus +358 MB resident for basedpyright on this repo.
- **Dependencies.** Phase 22 provides the receipt, the removal proof and `config_paths`. Phase 23 provides the shell-line and bundle pattern. Phase 24 provides the updated onboarding skill.

## Requirements

1. **Registry entry (ONB-08)**: `neovim` (cmd `nvim`, category editor, user tier) declares its methods in this order.
   - The `github_release` tarball method comes first on linux x86_64/arm64 and macOS x86_64/arm64, with `strip = 1` and `member = "bin/nvim"`.
   - `brew` is the fallback.
   - dnf, apt and pacman appear only as handoffs.
   - Current: Absent.
   - Target: The onboarding research is recorded (assets per OS/arch, brew, distro packages, removal paths), and the entry carries `verified = 2026-10-13` and `config_paths = ["~/.config/nvim"]`.
   - Acceptance: `make verify-registry` passes for the entry on all four OS/arch pairs. A load test finds the entry with its `config_paths`.

2. **No-reboot install with a receipt (ONB-08)**: On Bazzite, install puts the tree in `~/.local/opt/nvim` and the link at `~/.local/bin/nvim`, then writes a receipt.
   - Current: Not installable.
   - Target: The row shows `✓` on its tier.
   - Acceptance:
     - In a scratch HOME (fixture archive), the receipt lists the opt tree and the link.
     - In a container, `nvim --version` works through the link and `$VIMRUNTIME` points into the opt tree.

3. **Removal keeps config (ONB-08)**: Uninstall removes exactly the receipt paths. `~/.config/nvim` is kept unless "delete config too" is chosen (Phase 22).
   - Acceptance:
     - After removal, the opt tree and the link are gone, and `~/.config/nvim` is intact.
     - With the toggle on, it is gone too.
     - A file the user dropped into `~/.local/opt/nvim` that is not in the receipt is listed, not deleted.
   - *Amended 2026-11-13 (24.1 D-03 refinement, plan-phase finding, **needs confirmation**):* 22 D-07 lists foreign files only at declared paths. The opt tree is one receipt `dir` artifact, removed whole, and every update already replaces it whole. A per-file manifest would exceed the receipt's 64 KiB cap. So the removal preview names `~/.local/opt/nvim` as one removable tree, and a file dropped inside it goes with the tree. If the user keeps the original clause, a generic member manifest for every archive tool becomes a new plan (see 24.1-CONTEXT "Amended 2026-11-13").

4. **`EDITOR`/`VISUAL` (ONB-09)**: Install asks whether Neovim becomes the default editor, default no.
   - Current: Not offered.
   - Target:
     - "Yes" enables a managed bundle that exports `EDITOR=nvim` and `VISUAL=nvim`. The bundle is guarded by `command -v nvim` and placed so it takes effect after earlier user exports.
     - The summary names the value it overrides.
     - Removing the tool disables the bundle, so the earlier value takes effect again.
   - Acceptance:
     - In a scratch rc with `export EDITOR=vim`: "yes" → a new zsh prints `nvim`, and the summary says "overrides EDITOR=vim".
     - Removal → `vim` again.
     - "No" → no line written.
   - *Amended 2026-11-07 (24.1 D-14, **needs confirmation**: ONB-09 was user-locked as "asked"; the user's 2026-11-07 rule is "always, no question"):* there is no question. Install writes the bundle with no prompt, on every route including headless, only when the user's own shell files (outside managed blocks) export neither `EDITOR` nor `VISUAL`; OS defaults such as `/etc/profile.d` do not count as the user's. When the user set one, nothing is written and the summary says "kept your EDITOR=…" (verbatim). Removing the tool removes the bundle. A present `nvim` that never got the bundle shows `≈` "apply install tuning" (23.2 D-04/D-08 written-once record).
   - *Amended acceptance 2026-11-07 (24.1 D-14):* scratch rc with no editor export → a new zsh prints `nvim`; scratch rc with `export EDITOR=vim` → no line written, a new zsh prints `vim`, the summary says "kept your EDITOR=vim"; an OS-default-only `EDITOR` is overridden; removal → the bundle is gone.

5. **kickstart starter, no LSP (ONB-10)**: Install asks whether to add the kickstart.nvim starter, default no.
   - Current: Not offered.
   - Target:
     - "Yes" clones the pinned commit `8e35dbed…` into `~/.config/nvim`, only when that dir is absent or empty.
     - A recorded patch then empties `servers` and the Mason `ensure_installed` lists.
     - A non-empty `~/.config/nvim` is never touched, and the summary explains why.
   - Acceptance:
     - An empty or absent dir gets the pinned checkout plus the patch.
     - A dir with any file is byte-identical afterwards.
     - The patch applies cleanly at the pin.
   - *Amended 2026-11-07 (24.1 D-15/D-16/D-17, **needs confirmation**: ONB-10 was user-locked as "asked"):* there is no question. Install clones the pinned starter and applies the patch whenever `~/.config/nvim` is absent or empty, on every route including headless. There is no pending `≈` step for it: a starter the user deleted is placed again only by an explicit reinstall. A failed clone or patch leaves no dir, does not fail the `neovim` row, and the summary names the reason and the manual commands. Unit tests fake `git` through an injected runner (23.1 sandbox); the real clone and "the patch applies cleanly at the pin" are proven in the container.

6. **Zero LSP processes (ONB-10)**: With the patched kickstart, opening Python, Lua, TypeScript, Go or Java files starts zero LSP clients and zero server processes, and Mason installs nothing.
   - Target: The install summary names `:!pre-commit run --files %` and `:lsp enable <name>` for a one-off session.
   - Acceptance: In a container, a headless nvim opens one file of each language. Then `#vim.lsp.get_clients() == 0`, no server process exists, and Mason's package dir is empty.

## Boundaries

**In scope:**
- The `neovim` registry entry, its research note and its `verified` key
- Install, receipt and removal through the existing `github_release` archive path; `config_paths`
- The `EDITOR`/`VISUAL` bundle question; the pinned kickstart clone plus the no-LSP patch; the summary hints *(amended 2026-11-07, 24.1 D-14/D-15: no question — the bundle is install tuning that yields to a user export, the clone is install tuning into an absent or empty dir)*

**Out of scope:**
- An AppImage method — the tarball covers every target without FUSE
- Plugin updates inside kickstart (`vim.pack.update`) — the user owns the config after the clone
- Re-pinning kickstart automatically — a later re-pin is a data change with a fresh `verified` date
- LSP on demand beyond the summary hint — the user decided "sin LSP en nvim"
- Windows assets — not a supported OS

## Constraints

- Zero sudo, and no new method kind.
- The kickstart pin is a full commit SHA, and the patch is checked into the repo and applied by a test. *(amended 2026-11-07, 24.1 D-17: the test that applies it runs in the container; unit tests fake `git`, which the 23.1 sandbox does not allowlist)*
- Containers only for real downloads and runs. Unit tests use fixture archives and a scratch HOME.
- Writing `EDITOR` follows the Phase 23 bundle mechanics (asked, reversible, removed with the tool). *(amended 2026-11-07, 24.1 D-14, needs confirmation: not asked — 23.2 install tuning with its written-once record; reversible and removed with the tool)*
