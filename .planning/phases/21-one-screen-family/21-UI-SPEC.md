# Phase 21 — UI Design Contract

> Visual and interaction contract for the screen lifecycle, the Uninstall projection, the removal state, Policies and Doctor.
> Generated by gsd-ui-researcher in `--auto` mode (no user questions). To be verified by gsd-ui-checker.
> Amended during plan check it.1: one template, fixed holder noun. The mutation refusal is one template with a fixed noun per lock holder (Copywriting Contract); the two failed-read error lines for Policies and Doctor and the ` — found at {path}` suffix on the known-owner managed row were added in the same pass.

This is a **Textual terminal UI**, not a web frontend. Units are terminal **cells** and **rows**, not px. The design system is the house chrome (`installer/ui_common.py`: `AppScreen`, `StatusLine`, `VIEWS`), the Phase 19 health marks (`health_cell`) and the Phase 20 vocabulary (`WORDS`, `RowOutcome`). Phase 19 and 20 conventions are reused unchanged: glyph set `… ! ≈ ↑ ✓ ○ –`, Rich named ANSI styles, the 78-cell line budget, no motion, sentences with an em dash.

**Sources (locked, none re-asked):** `21-SPEC.md` R1–R9, `21-CONTEXT.md` D-01..D-16, `20-UI-SPEC.md`, `.claude/architecture.md`. Code facts read from `installer/wizard_app.py` and `installer/ui_common.py` on `main` (`UninstallScreen` :922, `PoliciesScreen` :1619, `DoctorScreen` :292, `VIEWS` table). Anything the upstream files left open is listed under **Auto-decided**.

**Scope.** No new screen, no new view, no new number key, no new widget. Phase 21 changes what the six existing views show and when. The visible changes are:

1. Uninstall regroups into three groups and gains a Health column and a "Removing…" state.
2. Policies gains a live state, a DRIFT state and live prerequisites.
3. Doctor loses the hidden `a` key and renders pnpm findings from tool reasons.
4. A single app-level "mutation in flight" refusal appears on every screen.
5. Quit waits for a running removal; a second `ctrl+c` stops waiting.
6. Every status obeys one lifecycle.

## Screen lifecycle contract (R1, R3; D-01..D-04)

This is the one interaction contract all six views share.

| Moment | What the user sees | Rule |
|--------|--------------------|------|
| App launch | The system tier, through the same `show_view` path as any other view. No flash of an empty root | The root screen is empty and non-navigable; it is never visible after `on_mount` completes |
| Press the current view's key | Nothing changes: same cursor, same selection, same status | `show_view` is a no-op for the visible view |
| Leave a view | The view's transient status is gone | `clear_transient()` runs first. The catalog tiers also clear the recommends line (existing override) |
| Enter a view | The view shows the **latest published** state, never the state it had when it was left | `enter_view` renders from `state_of`. It never starts a refresh pass |
| First entry | A status written during entry stays visible (for example a startup read error, or the first-run link-mode result) | Widgets are built in `on_mount`; content and status are written only in `enter_view` / `state_refreshed`; entry never clears its own status |
| Visible view and a pass publishes | The view re-renders in place; cursor stays on the same row id, selection is kept | `app` calls `screen.state_refreshed()` on publish; a view under a modal re-renders when the modal closes; views the user left wait for their next `enter_view` |
| Rows whose state is not yet published | `…` in the Health mark and `checking…` where a word is shown (Phase 19 and 20 rule, unchanged) | Never a stale `✓` |

- Cursor and scroll position survive a `state_refreshed` re-render (keyed by row id). A row that vanished moves the cursor to the nearest surviving row.
- A re-render never clears a status written after the mutation that caused it (the removal summary survives the publish that follows it).
- No view shows a spinner or any motion. In-flight is always a static word or glyph.

## Uninstall (R4, R5; D-07..D-11)

### Groups

Three tool groups in this order, then the existing environment group. Titles are lowercase, as the current section titles are.

| Order | Section title | Membership | Selectable |
|-------|---------------|------------|------------|
| 1 | `removable here` | `removable.level` is set. The proof (receipt, adoption or archive layout) is shown | yes |
| 2 | `managed elsewhere` | present, no proof | no (dim) |
| 3 | `nothing to do` | missing or unavailable | no (dim) |
| 4 | `shell config the installer manages` | ban / PATH block / tweaks pseudo-rows (existing) | yes, as today |

- The old `not installed` and `not available` titles merge into `nothing to do`. Within the group an unavailable tool keeps its unavailable reason text; a missing tool reads `not installed`.
- A group with no rows is not drawn (no empty header).
- **Nothing installed:** only `nothing to do` is drawn (plus the environment group when it has rows). Status `ok`: `Nothing to uninstall.` (existing copy, written by `enter_view`).

### Columns

`Sel`, `Tool`, `Health`, `Cat`, `Installed via`, `What gets removed`. Health is new, one cell wide, between Tool and Cat, filled by `health_cell(state_of(id))`. The header text is the one the catalog tiers already use for their health column (assumption A2). The full row must stay within the existing 78-cell table tests: the Health column costs 1 cell plus 1 separator, taken from `What gets removed`, which already truncates.

### Row text by group

| Group / situation | `Installed via` | `What gets removed` | Detail bar |
|-------------------|-----------------|---------------------|------------|
| Removable with a receipt | `installer`: the owner of the removable copy (amended 2026-11-03, review C-23; a manager is named only when it owns the copy this row removes, which the removal proof never yields) | the proven artifact paths, comma-joined, truncated | the proof sentence (`installed by this installer: receipt matches`) and the env levers |
| Removable, another manager's copy is active | `installer` | the proven paths | the proof sentence followed by ` — active copy: {manager label}` (C-23) |
| Removable by adoption | `installer` | the proven paths | `adopted: the file matches the release checksum` (Phase 19 text) |
| Removable by archive layout | `installer` | the proven directory | the layout proof sentence already produced by `removable` |
| Managed elsewhere, owner known | the owner label | `—` | `removable.hint` verbatim, followed by ` — found at {path}` when the resolver recorded the active path |
| Managed elsewhere, owner **unknown** | `unknown` | `—` | `owner unknown; nothing here can remove it safely`. **No manager name, no command, no argv** (prohibition) |
| Managed elsewhere, broken | the owner label, or `unknown` | `—` | `reinstall it from the catalog to repair; nothing to remove here` |
| Nothing to do, missing | `—` | `—` | `not installed` |
| Nothing to do, unavailable | `—` | `—` | the `UnavailableReason.detail` (for example `needs Homebrew, which is not on PATH`) |

- Detail text is data: build with `Text`, sanitize with `sanitize_log_line`, never markup (Phase 20 rule). The BROKEN repair sentence is a fixed string and is the same in the detail bar and in the row's `removes` cell when the cell is wide enough.
- The Health glyph carries the state independent of color (Phase 19 rule); under `NO_COLOR` nothing changes.

### Removal flow

| Step | Screen state | Copy |
|------|--------------|------|
| Select and press `enter` | `ConfirmUninstall` modal (unchanged) | unchanged |
| Confirmed | status `warn`: `Removing…`. The removed tools' rows show `…` on every tier and in Uninstall's Health column. The table stays interactive for navigation | `Removing…` (the ellipsis is the single character `…`, as in `checking…`) |
| User navigates to another view | Allowed. That view shows `…` for exactly the tools being removed and its normal state for the rest | none |
| User presses a mutating key anywhere (second removal, install `enter` / `a`, `u`, Doctor `enter` / `r`, Policies `space` / `t` / `m`) | Refused; nothing starts; status `warn` on the screen that received the key; the refusal still ends with one refresh pass | The lock template with the removal noun: `A removal is running; wait for it to finish. Navigation still works.` (68 cells) |
| Worker ends (success, partial, or crash) | Summary written to the status line; rows republish; each removed tool moves to `nothing to do` and shows `○` on every tier; a removed policy ban reads OFF in Policies on its next entry | the existing environment-lever summary text (`_applied_summary`) is kept; per-tool words come from `WORDS` (`removed`, `remove_failed`) |
| Quit (`q` / `ctrl+c`) during the removal | Status `warn`: `Waiting for the removal to finish…`, then the app exits | `Waiting for the removal to finish…` (34 cells) |
| A second `ctrl+c` while waiting (D-10 amended, C-26) | The app exits at once without waiting for the removal; the warning prints on the terminal after the app closes. A second `q` keeps waiting | `Quit before the removal finished; some files may remain.` |

- A tool whose removal failed keeps its row in `removable here`, stays selected (Phase 20 D-10 rule) and its word is `remove failed`, followed by ` — ` and the first line of the sanitized error.
- Outcome words added to the shared vocabulary: `removed` (green), `remove failed` (red, counts toward a failure summary). They render in the status summary exactly like Phase 20's `summary_counts` (non-zero counts, comma-joined): `3 removed, 1 remove failed`.
- The mutation lock template is the only refusal copy of a held lock. There is one template, `{Holder} is running; wait for it to finish. Navigation still works.`, one owner (`MutationLock`, inherited by `UnifiedApp`) and one fixed noun per holder (Copywriting Contract). The old `_TOGGLE_IN_FLIGHT_MESSAGE` and `_DAEMON_DEFAULT_IN_FLIGHT_MESSAGE` strings and their flags are deleted; the background-job toggle and the on-by-default daemon hold the same lock under their own nouns.

## Policies (R7; D-12)

### State cell

| State | Cell | Style | When |
|-------|------|-------|------|
| ON | `● [on]` | green | `policy.is_active()` is true |
| OFF | `○ [off]` | dim | not active and not owned |
| DRIFT | `! [drift]` | yellow | `policy.owned()` and not `policy.is_active()`, only for policies that declare `owned` |

- Glyph and word both carry the state; color is redundant (existing rule for this table). `!` is the Phase 19 "needs action" glyph.
- The State column width grows from 6 to 9 cells (`! [drift]`). Policy and Effect columns absorb it; the table must still fit 78 cells (existing test).
- `enter_view` re-reads `is_active()` for every policy and rewrites each State cell, the Requires cell and the detail panel for the highlighted row. The link-mode line is re-read in the same pass.
- A scheduled-job row (`state_cache`) is read on a worker. On `enter_view` its State cell is empty until that read answers; on a publish, or when a modal closes over Policies, it keeps its last answer while the worker re-reads (amended 2026-11-03, review C-21). A failed read still empties it.
- macOS: the prune policy is ON only when its plist exists. Without the plist it reads OFF.

### Requires cell

Computed from `state_of`, not from a snapshot. Copy is unchanged: `missing: {ids}` (bold yellow, hard requirement), `recommended: {ids}` (yellow), or the existing satisfied text. Installing `watch` makes the docker tweak's cell stop reading `missing: watch` on the next entry.

### Detail panel for DRIFT

First line of the detail text for a drifted policy: `Drift: this installer enabled it, but it is not active now. space applies it again.` (83 cells; the panel is 11 rows and wraps, no 78-cell cap applies to wrapped detail). The rest of the panel is unchanged.

### Toggles

Toggling stays immediate and reversible. A toggle ends with one full-catalog pass request. During a removal a toggle is refused with the mutation-lock message above.

## Doctor (R8; D-13, D-14)

- Doctor renders from `enter_view` / `state_refreshed`, like every view. It shows the latest published state on each entry without a restart.
- **Keys.** The hidden `a` binding is deleted. The visible keys are exactly `enter` apply and `r` reinstall pnpm globals (the registry row `actions="enter apply | r reinstall pnpm globals"` is unchanged). Pressing `a` does nothing, with no status.
- **pnpm findings.** Missing, unhealthy and incomplete global shims are shown from the tool's `ToolState.reasons`, the same sentences the catalog tier shows. A dangling pnpm shim therefore reads the same in Doctor and in the tier detail bar, and its tier row shows `!`. Doctor no longer builds its own text from the globals report.
- **First-run link-mode pick.** After a successful pick, Doctor re-renders and shows the chosen mode in its next frame, even if it was the visible-next view. A failed pick re-renders nothing and keeps the error status.
- Doctor `r` and `enter` (a fix) are mutations: they end with one pass request and are refused during a removal with the mutation-lock message.
- The browser smoke check still runs on a Doctor worker. While it runs, the pnpm findings that depend on it read the last evidence (or none); the result changes the reasons only after the pass that follows it. No new status copy: the existing audit status lines are kept.

## Catalog tiers and the status line

- The three tier screens keep their layout, legend and keys (Phase 19 and 20 contracts). The only change is that they now go through the shared lifecycle, so a mutation made on any other view is visible on the next entry, and immediately when the tier is the visible view.
- Rows being removed show `…` in the health mark on every tier, with the detail bar reading `checking…`-equivalent text already used for pending rows. No new copy.
- A tier that is visible when a pass publishes keeps its cursor row, its marked selection and its filter. Selected ids that are no longer selectable (removed, or made unavailable) are dropped silently on that re-render; the selection count in the footer shows the smaller number. No status message is written for a silent prune.

### Status line lifecycle (single rule)

| Event | Status |
|-------|--------|
| Written by an action | stays until the next write or until the view is left |
| Written during first entry | stays; entry never overwrites it |
| Leaving the view | cleared (`clear_transient`) |
| Re-entering | empty, except a standing status the view itself writes in `enter_view` (Uninstall: `Nothing to uninstall.` when nothing is listed) |
| A publish re-render | never clears it |
| A result lands (update, removal, toggle) while another view is visible | written to the visible view's status, the way app warnings are; the view it came from stays empty (amended 2026-11-03, review C-28). A result that names a key of the view it came from names that view too: `{N} remove failed. Fix the cause, then open Uninstall and press enter to try again.`, `Uninstall failed: {error}. Check permissions, then open Uninstall and press enter.` |

## Keyboard and accessibility

- **Keys do not change** except one deletion: Doctor `a`. The six number keys, `esc`, `q`, `ctrl+p` and per-view keys stay as in `VIEWS`.
- **Navigation is never blocked.** During a removal only mutating keys are refused; number keys, `esc` back, `ctrl+p` and cursor keys work.
- **Word and glyph first.** Every state added here is a word plus a glyph (`! [drift]`, `Removing…`, `remove failed`). Meaning never depends on color; under `NO_COLOR` nothing is lost.
- **No motion.** No spinner and no animated ellipsis, including for `Removing…`.
- **Width.** `…` `!` `●` `○` are one cell by `rich.cells.cell_len`. As in Phase 19, two-cell ambiguous-width terminals are not supported.
- **Escaping.** Detail, reasons and errors are `Text` pieces passed through `sanitize_log_line`; a `[` in a path or id never restyles anything.
- **Focus.** On every `enter_view` the main table keeps focus (Uninstall browser, Policies table, tier tables). Re-rendering on publish never steals focus from an open modal; a publish while a modal is on top is rendered on the view below when the modal closes (C-08), keeping its cursor, selection and status.
