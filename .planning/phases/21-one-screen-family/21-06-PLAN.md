<objective>
One refresh owner for the whole app. `UnifiedApp.request_refresh()` runs one full-catalog pass on one worker, coalesces requests, and on publish re-renders the visible view through `state_refreshed()`. The launch, a `u` update that ran, and an install close that ran something request it after they complete. The catalog's per-tier refresh workers, their messages and flags are deleted here, in the same commit as their replacement (D-16). The Uninstall half (its own worker, `OwnershipRefreshed`, `UninstallInputs.refresh`) and the refused-`u` pass follow in 21-07.

Purpose: UI-01 (after any mutation every view shows the new state on its next entry, and at once when visible) and the publish half of UI-08 (the re-render prunes stale picks).
Output: the owner in `installer/wizard_app.py`; `CatalogScreen.state_refreshed`; the per-tier deletions in `installer/catalog_tui.py`; `tests/screen_family.py` (new) with `settle`; `FrozenStateService.passes/queued`; tests.

Decisions recorded for this plan (Claude's discretion):
- Coalescing lives on the event loop (RESEARCH A2): `_refresh_running` and `_refresh_pending` are plain attributes; `request_refresh` returns early without a service; the finish handler restarts. `exclusive=True` is kept as D-05 says, but it is not what prevents overlap (P2).
- The worker posts `RefreshPublished(error, warning)` after `refresh` and again after `refresh_skills`, and `RefreshFinished()` from `finally:`. The messages are defined in `installer/wizard_app.py`, next to `UnifiedApp`, because only the app handles them.
- Publish target, per D-06 ("top screen only"): `_render_published()` calls `state_refreshed()` on `_visible_app_screen()` (unchanged: `self.screen` when it is an `AppScreen`, else None). Under a modal (`ConfirmUninstall`, `ExecuteScreen`, the nav palette) nothing re-renders; the covered view picks up the publication on its next `enter_view` (which renders from state and starts no pass). `_install_closed` calls `_render_published()` after the execute modal is gone, so the revealed view is current. This follows the UI-SPEC Focus line literally and deviates from RESEARCH P6's "topmost AppScreen in the stack" by orchestrator resolution (plan check it.1).
- A status line written while a modal covers every view goes through the existing `_pending_warnings` / `_flush_pending_warnings` path (reused, no new queue).
- Retry after a failed pass (O2): the error copy says the next change retries it; no new key, and entry still starts no pass.
- The app remembers the state line it last wrote (screen and text) and clears it on a clean publish only while that exact text is still the screen's status, which preserves today's self-clearing behavior without clearing anything a view wrote.
- `u` requests a pass for every `ToolUpdated` (an update that ran and failed may still have changed the machine). A refused `u` is handled in 21-07 (SPEC R2: a refused mutation still ends with one pass). The install close requests one only when `result is not None and ran_anything(result)` (A11).
- The catalog handler that posted `OwnershipRefreshed` is deleted with the per-tier path, so this plan renames `UninstallScreen.ownership_refreshed` to `state_refreshed` (body unchanged) and points `UnifiedApp.on_ownership_refreshed` at it: a visible Uninstall re-renders on the app publish from this commit on, and Uninstall's own worker keeps working until 21-07 deletes it.
- `tests/screen_family.py` (new) holds helpers several test files share: `settle(app, pilot)` waits until no worker is pending or running, then pauses once. 21-13 adds `HeldRemover`. The module-local `_family_app` builder in `tests/test_screen_family.py` (21-01) stays there.
- `FrozenStateService` gains class-level immutable defaults `passes: int = 0` and `queued: tuple[ToolState, ...] = ()` in Task 1, because Task 1's own tests count passes; `refresh` increments `passes`, re-publishes the current states plus `queued`, then empties `queued`. `HeldRefreshService` is unchanged.
- Task 1 touches seven files: the deleted per-tier path and its tests must leave the suite green in the same commit. The test edits are mechanical (waits on deleted flags become `settle`, flag assignments on bare screens are dropped, handler tests move to the app).
