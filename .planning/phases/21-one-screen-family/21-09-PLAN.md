Decisions recorded for this plan (Claude's discretion):
- Attribution: a previewed path belongs to the selected tool whose non-verifying `plan_removal([tool], bin_dir)` names it in `removable` or `yourself`. `yourself` is included on purpose: a path that drifted since the preview is no longer proven, so only the name match still ties it to its tool, and that tool must then read `remove failed` with the refusal line instead of disappearing from the report. Paths are tool-specific (one opt dir and one link per tool), so a path matches at most one tool.
- `UninstallDecision` is unchanged. A per-tool path map on the decision would duplicate what `plan_removal` already answers from the same tree.
- `remove_proven` stays the one remover (L-19-06) and is called once per tool; it already re-proves with `verify=True` and retires the receipt only when every proven path is gone. The CLI `run_uninstall` path is untouched.
- A tool's result: no attributed path -> `remove_failed` with `changed since the preview; not removed` (nothing it owns is still there to remove safely); a refusal -> `remove_failed` with its first refusal line; an `OSError` -> `remove_failed` with `first_line(exc)`; otherwise `removed`.
- `warnings` keeps every refusal line exactly as today. 21-14 renders per-row lines from `remove_failed` and leaves out of the status the refusal lines a failed row already shows.
- The environment levers (ban, PATH block, tweaks) run after the tool loop, as today, and now also after a tool's failed delete, which used to raise out before them.
</context>
