- `r` (cycle-2 HIGH, REVIEWS L414-422@59a2c4d): `_reinstall_globals_worker` (already `finally:`-posting and lock-holding after 21-16) calls `invalidate(reason="pnpm globals reinstalled")` on the service through `run_live` inside its `finally:`, before the post, success or failure, and also when the reinstall raised an exception `run_live` does not map (`run_live` maps only `OSError`, `CommandError` and `ShellrcRefusal`, `installer/ui_common.py:42-55`@59a2c4d): a failed or crashed `pnpm add -g` can write before it fails. The invalidate is guarded on a present service.
- The invalidate result travels with the completion (review L204-205, L242, L266 at 31c4e9c). `GlobalsReinstalled` gains `invalidate_error: str | None = None`. The worker's shape is `try:` the reinstall's `run_live` (21-16's default reinstall error stays until it returns) `finally:` a nested `try:` that, when a service is present, sets the default invalidate error `the cache invalidation did not complete` and then lets the invalidate call's `run_live` result overwrite it, `finally:` the post. So the post (and with it the lock release) happens even when `invalidate` raises an exception `run_live` does not map; that case carries the reinstall's real result and a non-empty invalidate error, and is never reported as `the reinstall did not complete`. No `except` clause is added: `run_live` and the two `finally:` blocks are the whole mechanism; an unmapped exception still ends the worker in Textual's error state (`exit_on_error=False`, 21-16), as today.
- Cache-write failure (cycle-2 MEDIUM; `installer/version_status.py` `VersionRefreshService.invalidate` L1121-1141@59a2c4d). `invalidate` bumps the epoch and marks the skills stale in memory first, then writes the cleared manager snapshot; the write's `OSError` propagates and `run_live` maps it into `invalidate_error`. The defined behavior: Doctor shows `version cache invalidation failed: {error}` under the reinstall line; the follow-up pass still runs under the new epoch, so every tool state, skills included, is re-derived live; the lock is released. The persisted manager snapshot was not cleared, so that pass may reuse it while it is inside its 6-hour window (`_load_or_query_snapshot`). Until the window ends, a later invalidate succeeds or the next start, pnpm's outdated and inventory facts can predate the reinstall. That limit is Phase 19's cache contract and is deferred in the ledger, not changed here. `test_a_real_cache_write_failure_after_a_reinstall_is_reported` pins the defined part on a real service.
- `on_globals_reinstalled` keeps `end_mutation()` first (21-16), stores the invalidate error on the screen, renders it as one extra line under the reinstall result in the globals section, using the copy the removal and install handlers already use, `version cache invalidation failed: {error}`, then starts its existing re-audit and posts `RefreshRequested()` (the 21-07 channel 21-16 already uses from Doctor, so the `_DoctorHost` test host needs no refresh owner). The pass is requested whether the invalidate succeeded or failed, as 21-07 does for a removal. The next `r` press clears the stored invalidate error with the other globals fields.
- `enter` relates to the guard chain as follows (review L204-205, L266 at 31c4e9c). The fix and the guard-file edits are one mutation, so `enter` requests its one pass when that mutation ends, success or failure (the fix can write before it fails). `action_apply` posts `RefreshRequested()` at its two returns after the fix (`_guard_file is None`, and no pending guards after the rescan), and `_finish_guard_chain()` posts it after its rescan and render. `_guard_next` calls that method once the last `ConfirmGuardFile` is answered, skipped or dismissed. Nothing posts while a `ConfirmGuardFile` is open, and the `if self.applied` early return stays pass-free (21-16 pins it at 0 passes).
- A refused `enter` or `r` (lock held) already ends with one pass through 21-16's `refuse_if_mutating`; this plan adds no second request on that path.
- First-run pick: the success branch of `UnifiedApp._first_link_mode_picked` calls `target.enter_view()` after writing its status when `target` is the `DoctorScreen`; the `enter_view` path writes no status, so the link-mode line survives.
