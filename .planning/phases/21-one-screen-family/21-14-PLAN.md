Decisions recorded for this plan (Claude's discretion unless a plan-check resolution is named):
- W2 (plan check it.1): `on_removal_finished` calls `self.app.request_refresh()` for every removal, whether or not the decision named a tool, unless the app is quitting. Only the invalidate stays conditional on a named tool (an environment-only removal changes no tool, so there is nothing to invalidate; the pass still re-reads every view, and Policies re-reads live state on its next entry). This replaces 21-13's conditional request.
- The failed-row lines live in `_failed_lines: dict[str, str]` (REVIEWS L150-151, adjudication L237-238@31c4e9c). `enter_view` and `state_refreshed` keep them, so a reason survives navigation and every publish until the retry. An entry is dropped in two cases: when a removal whose decision names that tool starts (the retry replaces it with its own outcome), and when a publish puts the tool in `nothing to do` AND its published `state.removable` has neither `removable` nor `yourself` paths (it is gone with nothing left behind, so there is nothing left to retry or explain). A partial delete (cycle-2 MEDIUM, REVIEWS L426-439@59a2c4d) removes the bin link, so the tool reads MISSING and lands in `nothing to do`, while the opt dir it failed to delete is listed in `yourself`; that row keeps `remove failed — {reason}` so the user learns why files remain. The failed row's cell is `outcome_word(...)` and its detail prefix uses `outcome_detail_text(...)` (21-02, sanitized). Refusal lines that a failed row already shows are left out of the status.
- Which failures stay selectable (adjudication L237@31c4e9c): selection follows the published proof, through the existing paths only. While the follow-up pass runs, the painted-row memory (21-12) keeps a failed row selectable. When the pass publishes, 21-03's reload prune keeps a row the state still proves removable (an OS error left the files and their proof in place) and drops one whose proof is gone (a `remove_proven` refusal: changed since the preview, or a drifted receipt), which then sits in its new group with its failure line. UI-SPEC L130 ("failed rows stay selected; enter retries") is honored for every failure that can be retried. A refused row is not offered again, because SPEC R6 and D-15 forbid offering a path its state does not prove. The locked status copy is unchanged: it is written when the removal finishes, before the pass has published.
- Retry: Enter on failed rows is a new removal (21-13 already dropped the `applied` guard); the lock alone prevents overlap.
- Quit: `action_abort` and `action_hard_abort` become `async`. During a removal they call the new `_exit_after_removal()`, which sets `_quitting`, writes the waiting copy on `_visible_app_screen()` (21-06; D-06 top screen only), or appends it to `_pending_warnings` when a modal is on top (21-06 reuse), then awaits the removal worker through `self.workers` and Textual's `Worker.wait()` with `WorkerFailed` and `WorkerCancelled` suppressed (`contextlib.suppress`), then `self.exit(None)`. No existing helper waits on a worker before exit, so `_exit_after_removal` is new and reuses those two. Outside a removal both actions behave as today.
- Quit under a modal during a removal (adjudication L238@31c4e9c): `action_abort` keeps its `_navigable()` guard first, so `q` under the nav palette or `ConfirmUninstall` does nothing, as it does today. A modal owns its keys, and the palette's filter types `q`. `action_hard_abort` stays unguarded and calls `_exit_after_removal()` during a removal. With a modal on top, `_visible_app_screen()` is None, so the waiting copy goes to `_pending_warnings`, and the app exits after the worker returns. The copy is visible only if the modal closes first; the guarantee is that the delete is never cut.
- The old `except Exception` block around the inputs invalidate seam, with its suppression comment, goes with the seam, so the suppression count drops by one.
