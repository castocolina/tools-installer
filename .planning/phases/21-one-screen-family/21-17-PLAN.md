Decisions recorded for this plan (Claude's discretion unless a plan-check resolution is named):
- `on_mount` adds the columns and one row per policy, keyed by policy id, with the static Policy label and Effect text and empty State and Requires cells; it still starts the one-shot competing-mechanism warm-up. Rendering lives in `state_refreshed()`; Policies does not override `enter_view` (the `AppScreen` default calls `state_refreshed`).
- `state_refreshed()` does, in order: for each policy without a `state_cache` that binds `is_active`, read it through `run_live` (one helper, `_read_live_state(policy)`, which 21-18 extends with `owned`); a success sets `active_state[id]`, a failure deletes `active_state[id]` and keeps the first error of this render; rewrite every State cell (`update_cell(..., update_width=True)`) and Requires cell; re-render the detail for the highlighted row and the link-mode line; then the status: a failure writes `Could not read the policy state: {error}.` as `error`, where `{error}` is the first line of the `run_live` message; a clean render clears the line only when it still holds that error copy (the 21-06 rule for its own retry line). Policies with a `state_cache` keep their state until 21-18 moves them to a worker. A policy without `is_active` keeps the state its last toggle left.
- The State cell takes the policy id: no entry in `active_state` renders an empty cell (no glyph, no word), so an unknown state is never drawn as `○ [off]`.
- `action_toggle_policy`: after the 21-15 lock check, a policy with no entry in `active_state` rewrites the error copy of the last failed read, applies nothing, and posts `RefreshRequested()` (21-07), which is the one pass a refused mutation ends with.
- W4 (plan check it.1): `VersionRefreshService.installed_or(launch: Mapping[str, bool]) -> Callable[[str], bool]` returns a closure over `state_of`. It mirrors `is_present`'s known/unknown split, but its fallback is the launch snapshot rather than a probe, because it runs at render time on the event loop and a probe there is blocking I/O. Tested in `tests/test_version_status.py`. `setup.py` keeps building the `installed` snapshot it already builds and passes `version_refresh.installed_or(installed)`; when there is no service (the non-interactive uninstall path) it keeps passing the mapping, which 21-04 already accepts.
- `refresh_daemon_state` stays: it applies the daemon default's own worker-resolved answer when Policies is visible at that moment.
- Requirements read (REVIEWS L177-178@31c4e9c; `installer/wizard_app.py:1732`, `:1746-1748`, `:1847-1861`, `:2055`). Today the Requires cell, `_policy_detail` and the toggle each call `missing_requirements()` live. `state_refreshed()` now reads it once per policy per render through `run_live`, into the remembered map `_missing: dict[str, tuple[str, ...]]`, in the same loop as the state read. A success stores the answer. A failure deletes the entry and contributes the render's first error, so the status rule above covers both reads with its one copy. `_requires_cell`, `_policy_detail` and the toggle read the map only: no entry means a blank Requires cell and a detail with no `Missing required tool(s)` / `Required tool(s)` / `Recommended tool(s)` line. The toggle treats a missing map entry like a missing `active_state` entry (refused, one pass). One read per render also keeps the render from calling the predicate three times per row.
