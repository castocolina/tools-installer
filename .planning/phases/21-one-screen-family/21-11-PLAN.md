Decisions recorded for this plan (Claude's discretion):
- `UninstallScreen(inputs, *, tools, version_refresh)`: `UnifiedApp` already holds the catalog and the service and passes both, so `setup.py` needs no new wiring. `required_by` comes from `reverse_dependencies(tools)` (uninstall.py), computed once in `__init__` (the catalog does not change in a session).
- `_UninstallEntry` gains `group: UninstallState`, so sections are built from the entries alone (the zip with a parallel row list goes).
- Unknown state: `self._painted: dict[str, _UninstallEntry]` keeps the last entry built from a known state. A row whose state is `None` or CHECKING reuses it with the Health cell set to `…`; with no memory it is an unselectable `nothing to do` row reading `checking…`. Keeping the painted selectability is what lets a failed removal's rows stay selected while the follow-up pass runs (21-14), and is safe because `remove_proven` re-proves every path at deletion time. The catalog's prune rule (21-03) behaves the same way: an unpublished state never prunes.
- `What gets removed`: for a removable row, the proven paths comma-joined and truncated with an ellipsis to the fixed `_REMOVES_CELL_MAX` budget, so the column is never sized by the longest path (CR-03); the full list is still shown by `ConfirmUninstall` before anything is deleted. Every other row reads `—`. The budget is the largest value for which the 80x20 layout backstop passes with the Health column present.
- Health header is `Health`, the tiers' header (UI-SPEC A2).
- Re-derivation splits in two: `enter_view` re-reads the three environment predicates through `run_live` (failure keeps the last values and writes `Could not read the uninstall state: {error}.` as warn; the one-time startup error keeps its existing copy), clears `applied`, renders, then writes the standing status into an empty line. `state_refreshed` only renders and writes the standing status into an empty line; it never clears or replaces a status (21-01 status lifecycle). The method that did both halves is deleted, not renamed.
- The removal flow (`_apply_removal`, `_applied_summary`, `ConfirmUninstall`) is untouched here; 21-13 moves it to a worker.
- Split seam (plan check it.1 B2): Task 2 deletes the rows seam and the setup closures, which are the only callers of `classify_tools` outside `installer/uninstall.py`. `classify_tools`, `ToolRow` and the owner hints then stay in `installer/uninstall.py`, still exercised by `tests/test_uninstall.py`, for exactly one wave until 21-12 deletes them with their tests. D-16's "same wave" is read as the logical Uninstall-projection step of CONTEXT's suggested order (21-11 plus 21-12), which the orchestrator split for the context budget; vulture does not flag the window (min confidence 80, an unused function scores 60).
- Task 1 touches five files and Task 2 eight: deleting a dataclass field must update every constructor and test in the same commit for the tree to stay green. Those edits are deletions of one keyword argument or of tests whose subject no longer exists.
