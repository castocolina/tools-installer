<objective>
Stale selections cannot survive a re-render: `ToolBrowser.reload` drops selected ids that are still listed but no longer selectable, and `selected_ids()` filters on `selectable`, so `Accepted` (and therefore execute) never receives an id the user could not select now.

Purpose: UI-08 (SPEC R6, D-15). The refresh owner (21-06) re-renders every visible view through `reload`, so pruning happens on every publish without any new call site.
Output: two small changes in `installer/tool_browser.py`; tests in `tests/test_tool_browser.py`.
</objective>

Decisions recorded for this plan (Claude's discretion):
- The prune runs in `reload` only, before `_rebuild`, as one in-place set operation next to the existing stale-row prune. It considers only items of the new adapter, so ids another browser owns in a shared set are untouched.
- No `SelectionChanged` is posted for a prune: the catalog's handler clears the status on that message, and a publish must never clear a status (UI-SPEC status lifecycle).
- The catalog is safe with this rule: `CatalogScreen._is_unavailable` falls back to the launch-time unavailable map, so a tool whose state is not yet published stays selectable and is not pruned while rows show `…`.
</context>
