<objective>
Stale selections cannot survive a re-render: `ToolBrowser.reload` drops selected ids that are still listed but no longer selectable, and `selected_ids()` filters on `selectable`, so `Accepted` (and therefore execute) never receives an id the user could not select now. When the highlighted row itself vanishes in that re-render, the cursor lands on the nearest surviving row, as the approved UI-SPEC requires, not on the first item row.

Purpose: UI-08 (SPEC R6, D-15). The refresh owner (21-06) re-renders every visible view through `reload`, so pruning and the cursor rule apply on every publish without any new call site.
Output: three small changes in `installer/tool_browser.py`; tests in `tests/test_tool_browser.py`.
</objective>

Decisions recorded for this plan (Claude's discretion):
- The prune runs in `reload` only, before `_rebuild`, as one in-place set operation next to the existing stale-row prune. It considers only items of the new adapter, so ids another browser owns in a shared set are untouched.
- No `SelectionChanged` is posted for a prune: the catalog's handler clears the status on that message, and a publish must never clear a status (UI-SPEC status lifecycle).
- The catalog is safe with this rule: `CatalogScreen._is_unavailable` falls back to the launch-time unavailable map, so a tool whose state is not yet published stays selectable and is not pruned while rows show `…`.
- Nearest surviving row (cycle-3 HIGH, REVIEWS L167@2b0f9ec; locked `21-UI-SPEC.md:76`). Today `_rebuild` falls back to the first item row when the highlighted key is gone (`installer/tool_browser.py:214-225`, through `_first_selectable_row` at `:291-296`), and `tests/test_tool_browser.py:159-176` pins that. `_rebuild` now also records `table.cursor_row` before `table.clear`, next to `previous_key`. When the key cannot be restored, the cursor moves to the item row nearest that index. Reuse instead of a second scan: `_first_selectable_row` becomes `_nearest_selectable_row(self, row: int = 0) -> int | None`, over the same `table.rows` walk and the same `row_key.value in self._by_id` item test. It returns the item-row index with the smallest distance to `row`, the upper one on a tie (`min` over the walk in table order), or None when there is no item row. The default `row=0` is exactly the old first-row answer, so the on-mount call (no key yet) and the empty-detail check keep their behavior. The rule is not destructive either way: Uninstall's Enter acts on `selected_ids()`, not on the cursor (`installer/tool_browser.py:356-365`). A tab switch whose new view lacks the key takes the same path, which is consistent with the UI-SPEC line. A column sort keeps every key.
