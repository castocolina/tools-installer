Decisions recorded for this plan (Claude's discretion unless a plan-check resolution is named):
- `MutationLock` is a plain class (no Textual base) holding `_mutation_holder`, `mutation_in_flight`, `begin_mutation`, `end_mutation` and `refuse_if_mutating`, moved verbatim from `UnifiedApp`. `refuse_if_mutating` posts `RefreshRequested()` from the screen (21-13), so the base needs no `request_refresh` and no app reference. `UnifiedApp(MutationLock, App[...])`; `_DoctorHost` in `tests/test_wizard_app.py` inherits it first. Reuse: the 21-13 methods, moved, not rewritten. 21-21's `matrix_app` builds on `UnifiedApp`, so it inherits the same lock.
- Holder nouns (plan check it.1 W3): `GLOBALS_REINSTALL = "A pnpm reinstall"` and `INSTALL_RUN = "An install run"`. Every rendered refusal is at most 78 cells (nouns shortened at plan check it.1 so none wraps), pinned by the layout backstop in Task 2.
- The pnpm reinstall: `action_reinstall_globals` checks the lock first; where it sets `globals_running` it also calls `begin_mutation(MutationHolder.GLOBALS_REINSTALL)`. `_reinstall_globals_worker` takes `exit_on_error=False` and posts `GlobalsReinstalled` from `finally:` with the default error `the reinstall did not complete` (the `PoliciesScreen._toggle_policy_worker` shape). `on_globals_reinstalled` starts with `self.app.end_mutation()`. `globals_running` stays; it drives the body's `Reinstalling…` line.
- The install run: `on_install_run_started` calls `begin_mutation(MutationHolder.INSTALL_RUN)` after setting `run_in_flight`; `on_install_run_finished` calls `end_mutation()` as its first statement. The lock cannot already be held there: tier `enter` refuses while it is held, the default-daemon apply holds it from construction (21-15), and the install flow is modal, so no other key is reachable between `enter` and the run's start. The tier `enter` refusal test pins the first link of that chain.
- Tier `enter`: `on_tool_browser_accepted` returns on `self.app.refuse_if_mutating(self)` before it posts `Decided`.
- Doctor `enter`: `action_apply` returns on `self.app.refuse_if_mutating(self)` before running the fix.
- Doctor early returns (REVIEWS L168-169@31c4e9c; `installer/wizard_app.py:651-653`, `:737-774`). A return is a refusal when it tells the user why nothing ran. A refusal ends with one pass, which is the same rule 21-07 applies to the five refusal branches of `u`.
  - Silent returns, which are not refusals and request no pass: `action_apply` when `applied` is already true, and `action_reinstall_globals` when `globals_done` is true.
  - `r` while a reinstall runs: the lock check comes first, so the `GLOBALS_REINSTALL` refusal fires. It writes the template and requests its pass through `refuse_if_mutating`. The old `globals_running` early return is only reachable now if the flag and the lock disagree; it stays silent.
  - The three note-writing returns (`_GLOBALS_UNKNOWN_YET` while the audit runs, `_GLOBALS_UNKNOWN` with its existing re-audit, `_NOTHING_TO_REINSTALL`) keep their notes and each post `RefreshRequested()`. 21-07's message is answered by the app with `request_refresh()`, so `_DoctorHost` needs no handler.
  - The `report is None` branch is unreachable once the audit has answered (it returns behind `globals_auditing`). It gets no test case, and the SUMMARY records why.
- The first-run link-mode pick is not a key on a view; it is answered once at launch, before any holder but the default-daemon apply can exist, and it does not check the lock (its setter does not race the daemon's unit files). Recorded in the SUMMARY.
