Decisions recorded for this plan (Claude's discretion):
- `_read_live_state(policy)` (21-17) also reads `owned()` through `run_live` when the policy binds it; either failure takes the 21-17 failure branch. The drift set is the policies whose `owned()` answered true and whose `is_active()` answered false in this render.
- The State cell reads `active_state` and the drift set: `● [on]` green, `○ [off]` dim, `! [drift]` yellow, empty when unknown (21-17).
- `state_refreshed` skips the synchronous read for `state_cache` policies, deletes their `active_state` entry (so the row is blank, not stale, until the worker answers), and starts `_read_job_states_worker` (`@work(thread=True, exclusive=True, group="policies-job-state", exit_on_error=False)`). The worker reads `is_active()` and `owned()` for those policies through `run_live` and posts `JobStatesRead(states, error)` from `finally:`, with `error` defaulting to `the job state read did not complete` so a crash still posts. `JobStatesRead` is a plain `Message` beside `CompetingProbed`. `on_job_states_read` applies the states it carries, rewrites those rows the same way, and on an error takes the 21-17 status rule with the same copy. Reuse: the `_probe_competing_worker` shape (worker, `finally:` post, `is_mounted` guard in the handler).
- Generation (REVIEWS L186-187, adjudication L240@31c4e9c). `exclusive=True` cancels an older Textual thread worker, but the thread keeps running and its `finally:` still posts, so a read started by an earlier render can arrive after a newer one. `PoliciesScreen` keeps `_job_state_generation: int`. Each `state_refreshed` that starts the worker increments it and passes the new value as the worker's argument. The worker posts `JobStatesRead(generation, states, error)`. `on_job_states_read` returns at once when `message.generation != self._job_state_generation`, before the `is_mounted` guard has anything to do. This is the guard Doctor already uses for its globals audit (`installer/wizard_app.py:481-494`, `:828-835`), reused as a pattern; no shared helper is extracted for two call sites.
- A toggle requests the pass on every completion, success or failure, because a failed apply can already have written part of its layers: `_finish_toggle` ends with `self.app.request_refresh()` on both branches; it is the single completion point of the sync path and of `on_policy_toggled`, so neither caller adds its own.
- Completions supersede in-flight reads (cycle-2 HIGH, REVIEWS L414-422@59a2c4d). A job-state read started before a mutation finished (the user re-entered Policies while a job toggle or the launch daemon-default apply was still running) can carry the pre-mutation answer and land after the completion wrote the new one, still carrying the current generation. Every completion that writes policy state therefore advances the generation. The worker start that `state_refreshed` does (bump plus `_read_job_states_worker(generation)`) is extracted as `_start_job_state_read()`, shared by both callers below; deleting the `state_cache` entries stays in `state_refreshed`.
  - `_finish_toggle` increments `_job_state_generation` as its first statement, on both branches. Its pass request then publishes, and the publish's `state_refreshed` starts the fresh read (a hidden Policies reads on its next entry).
  - `refresh_daemon_state` requests no pass (D-05 lists the mutations that do; the daemon default is not one of them), so it starts the fresh read itself. Its early return keys on an unknown policy id instead of a missing `active_state` entry, because after 21-17/21-18 an absent entry means "unread or in flight", and the worker-resolved `live` answer is the freshest one. It writes the resolved value as today (`live` wins, `applied` only for a policy with no `is_active`), even into an absent entry. Then, when the screen is mounted, it calls `_start_job_state_read()`, which supersedes any older read, also when the resolved value did not change. An unmounted screen has nothing in flight; its first entry reads.
