<objective>
Give the `kind="node"` method five new optional params — `co_install` (npm package names
that must land in the SAME pnpm global install group as this method's own `npm_pkg`),
`allow_build` (npm package names whose postinstall scripts are explicitly permitted),
`versions` (a package-name -> semver-range table pinning group members), `min_node`
(the minimum node runtime the resulting install needs), and `smoke` (a token naming one
code-owned post-install check from a closed set — the registry SELECTS a check, it never
supplies a command) — plus the runtime version preflight that refuses to use any of it on a
toolchain too old to support it, the post-install check that refuses to report success for a
browser that cannot start, and a container run proving the resulting install sequence really
produces a working `mmdc` before any registry data depends on it.

Purpose: REQ-puppeteer-catalog-entries says `mmdc.requires` gains `puppeteer` "so
`resolve_dependencies` drags it in automatically". 05-RESEARCH.md Pitfall 1 shows that
`requires` alone satisfies the catalog's install ORDER while leaving `mmdc` unable to
resolve `puppeteer` at runtime: pnpm's own documentation states that each `pnpm add -g`
invocation — and each space-separated package inside one invocation — gets its own
isolated `node_modules`/lockfile, and that only the comma-separated form bundles packages
into one group that "share a `node_modules` tree and lockfile, resolve peer dependencies
against each other, and are removed together". 05-RESEARCH.md Pitfall 2 shows the second
half: puppeteer's `postinstall` (`node install.mjs`, the Chrome + chrome-headless-shell
download) is blocked by pnpm's default-deny build-script gate and exits 0 with only a
warning. Both gaps live in the executor, not in registry data, so they are fixed here first
and consumed by plan 05-03.

Decisions implemented:
- D-03: one `puppeteer` catalog entry whose dependency really works on the platforms it
  claims. This plan supplies the mechanism that makes D-03's single entry functional
  rather than declarative; plan 05-03 supplies the entry itself and its platform gating.
- Claude's Discretion (CONTEXT.md): "exact registry kind/method shape" — resolved as
  additive optional params on the existing `kind="node"` method rather than a new method
  kind or a new registry-level dependency-group concept. Rationale: `installer/deps.py`
  keeps sole ownership of install ORDER (`.claude/architecture.md`'s tier rule), and the
  new params shape only the pnpm INVOCATION.
- 05-RESEARCH.md "Common Pitfalls" option 1 (the recommended one) over option 2:
  option 2 would teach `installer/session.py::run_installs` to detect adjacent
  same-manager tools and coordinate them, which is a second ordering mechanism living
  outside `requires` — forbidden by `.claude/architecture.md`.

Added in cross-AI review cycle 2: `smoke` and the post-install browser check exist because
`installer/engine.py:89-94` reports INSTALLED on any zero exit from `pnpm add -g`, and on
Linux amd64 that is a false success in a real, reachable case — puppeteer's downloaded Chrome
links against roughly thirty system shared libraries a minimal Linux install does not ship, so
the install command succeeds and the browser cannot start. Cycle 2's second HIGH concern is
that this phase documented that prerequisite and verified nothing. It is now verified: the
check runs the browser that was actually downloaded, and a failure becomes a FAILED install
outcome carrying the reason, through `engine.py`'s existing `ExecutorError` handling.

Recorded deviation from 05-CONTEXT.md (added 2026-09-05, cross-AI review cycle 1; extended
cycle 2): 05-CONTEXT.md's `<specifics>` states Phase 5 is "strictly a method correction ... no
new tools, no new mechanisms." This plan does add a mechanism: five method params, a load-time
validator for them, an injectable version-probe seam, a semver-comparison helper, and one
code-owned post-install check. The
deviation is deliberate and is recorded here rather than left implicit, exactly as ROADMAP
SC#3's wording was formally amended. The reason it is unavoidable: ROADMAP SC#3 requires
`mmdc.requires` to include `puppeteer` AND requires the resulting install to work, and
05-RESEARCH.md establishes that no arrangement of EXISTING registry fields produces a
shared pnpm install group. Declining the mechanism would mean shipping a `requires` edge
that satisfies the criterion's letter and leaves `mmdc` broken — the scope reduction this
project's planning rules forbid. The mechanism is additive: every method that declares none
of the new params produces byte-identical argv and runs zero extra subprocesses.

Task-count note: this plan carries 4 tasks rather than the usual 2-3. Task 1 modifies no
repository file (it is the Tier-3 evidence run); Tasks 3 and 4 both edit
`installer/executors.py::_node`, and Tasks 2 and 4 both edit `installer/versions.py`, so
splitting them across plans would put two plans on the same function and the same module in
the same wave. The argv builder and the two gates are separated into distinct tasks because
they fail for different reasons and are verified by different commands, not because they
could run in parallel. Task ownership is strict after cross-AI review cycle 2: the pure
version helpers belong to Task 2 (which is the only task that validates a declared version),
and the probe seam, the floors and the post-install browser check belong to Task 4 (the only
task that runs anything). No task's `<action>` instructs work outside its own `<files>`.

Output: five validated method params, one changed argv builder, one fail-closed version
preflight, one fail-closed post-install browser check, a container-verified end-to-end proof
including the brownfield case and the missing-shared-library case, and an architecture rule
stating that `co_install` never orders anything.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| registry -> pnpm argv | Registry-declared strings become argv elements of a global package install. |
| npm package -> local machine | An installed package's lifecycle scripts execute with the user's privileges, and pnpm's permission for them persists past this invocation. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-05-01 | Elevation of Privilege | `allow_build` on a `kind="node"` method | high | mitigate | **Scope correction (cross-AI review cycle 1), restated accurately (cycle 2):** `--allow-build=<pkg>` is NOT invocation-scoped. pnpm's own `add` documentation states the flag "will run its postinstall script and **also add it to the `allowBuilds` field**… So, it **will always be allowed to run its scripts in the future**", added in pnpm 10.4.0. The grant is PERSISTENT and PACKAGE-LEVEL, keyed by package NAME with no version qualifier: once this installer runs it for `puppeteer`, ANY future `puppeteer` install performed by that pnpm on that machine runs its postinstall unprompted — any version, from any command, including ones this project never issues. **What does NOT bound it: this project's `^25` pin.** An earlier revision of these plans described the pin as bounding the grant; cycle 2 correctly rejected that. `versions = { puppeteer = "^25" }` constrains only the argv THIS project generates (the install path and the Doctor replay), so it is a compatibility control that keeps `mmdc` and `puppeteer` inside a working peer range — it is not a security boundary and it authorises nothing. What actually bounds the residual risk: (1) the grant names ONE package, never a wildcard — `load_tools` rejects any `allow_build` name outside `{npm_pkg} ∪ co_install` (Task 2), so no registry edit can produce a blanket allowance and `dangerouslyAllowAllBuilds` is never used; (2) the grant is inert until someone installs that package again, so its blast radius is one named package's postinstall on one machine; (3) plan 05-03 Task 1's legitimacy gate binds that package's identity to its canonical upstream repository BEFORE the grant is created; (4) the grant is observable and revocable — Task 1 of this plan records the file and lines pnpm writes it into, and plan 05-03 Task 3 writes that location and the revocation step onto the registry entry, so a user can re-gate the package by removing that entry. **Residual risk, accepted explicitly:** a compromised future `puppeteer` release — of ANY version, not merely one inside `^25` — runs its postinstall silently on a machine that has this grant. Accepted because declining the grant produces an `mmdc` that installs successfully and cannot render, which is the failure this phase exists to remove, and because the only stronger control (pinning an exact `dist.integrity`) freezes the browser at one build with no security-update path. |
| T-05-02 | Tampering | comma injection through `npm_pkg`/`co_install`/`versions` | medium | mitigate | All three are rejected at load time when they contain a comma (Task 2), so a registry value cannot smuggle extra packages into an install group through the separator, on either side of the `@`. |
| T-05-03 | Spoofing | argv[0] resolution for pnpm, and the version probe's target | medium | mitigate | Unchanged from plan 04-03: `real_pnpm()` returns an absolute path that skips this installer's own shim dir, so the argv-conditional wrapper cannot rewrite a catalog install into `volta install` (which per `installer/registry.toml`'s volta comment runs npm lifecycle scripts unrestricted). Task 3 preserves it, and Task 4's pnpm probe uses that same resolved absolute path rather than a bare name, so the version the gate reads is the version that will run. |
| T-05-18 | Tampering | a mechanism running on a toolchain that silently mis-parses it | high | mitigate | Task 4's fail-closed preflight. On pnpm 10 a comma-joined group is not a group but one package name containing a comma, and `--allow-build` is an unknown option; on node below a declared `min_node`, puppeteer's postinstall cannot run. Each is refused with an `ExecutorError` naming observed and required versions, and an unreadable version is treated as too old rather than waved through. |
| T-05-26 | Repudiation | reporting INSTALLED for a puppeteer whose browser cannot start | high | mitigate | **Added in cross-AI review cycle 2.** `installer/engine.py:88-94` turns any zero exit from the executor into an INSTALLED outcome, and `pnpm add -g puppeteer@^25` exits 0 on a minimal Linux amd64 machine that lacks headless Chrome's ~30 shared libraries. Before this revision the phase's only answer was a registry comment naming the prerequisite. Task 4 now runs the browser puppeteer actually downloaded (`<browser> --version`, the cheapest execution that still goes through the dynamic loader) after the install returns, and raises `ExecutorError` — which `engine.py` already turns into FAILED with the message — when the browser is absent or cannot start. The message names the resolved path and both documented remedies (install the platform's shared libraries, or set `PUPPETEER_EXECUTABLE_PATH`). Task 1's Container D reproduces the broken machine and records whether the signal fires there. Residual, accepted: the check proves the browser STARTS, not that it renders every page, and a later OS update that breaks the browser is not re-checked until the next install. |
| T-05-04 | Denial of Service | Tier-3 containers executing real upstream installers | low | accept | Every run is inside a disposable `docker run --rm` container under colima per ONESHOT-RULES Rule 14, never against the host. Containers are torn down by `--rm` in the same invocation. |
