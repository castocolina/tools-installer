<objective>
Give the `kind="node"` method two new optional params — `co_install` (npm package names
that must land in the SAME pnpm global install group as this method's own `npm_pkg`) and
`allow_build` (npm package names whose postinstall scripts are explicitly permitted) — and
prove the resulting install sequence really produces a working `mmdc` before any registry
data depends on it.

Purpose: REQ-puppeteer-catalog-entries says `mmdc.requires` gains `puppeteer` "so
`resolve_dependencies` drags it in automatically". 05-RESEARCH.md Pitfall 1 shows that
`requires` alone satisfies the catalog's install ORDER while leaving `mmdc` unable to
resolve `puppeteer` at runtime: pnpm's own documentation states that each `pnpm add -g`
invocation — and each space-separated package inside one invocation — gets its own
isolated `node_modules`/lockfile, and that only the comma-separated form bundles packages
into one group that resolves peer dependencies against each other. 05-RESEARCH.md Pitfall
2 shows the second half: puppeteer's `postinstall` (`node install.mjs`, the Chrome +
chrome-headless-shell download) is blocked by pnpm's default-deny build-script gate and
exits 0 with only a warning. Both gaps live in the executor, not in registry data, so they
are fixed here first and consumed by plan 05-03.

Decisions implemented:
- D-03: one `puppeteer` catalog entry whose dependency really works on the platforms it
  claims. This plan supplies the mechanism that makes D-03's single entry functional
  rather than declarative; plan 05-03 supplies the entry itself.
- Claude's Discretion (CONTEXT.md): "exact registry kind/method shape" — resolved as two
  additive optional params on the existing `kind="node"` method rather than a new method
  kind or a new registry-level dependency-group concept. Rationale: `installer/deps.py`
  keeps sole ownership of install ORDER (`.claude/architecture.md`'s tier rule), and the
  new params shape only the pnpm INVOCATION.
- 05-RESEARCH.md "Common Pitfalls" option 1 (the recommended one) over option 2:
  option 2 would teach `installer/session.py::run_installs` to detect adjacent
  same-manager tools and coordinate them, which is a second ordering mechanism living
  outside `requires` — forbidden by `.claude/architecture.md`.

Output: two validated method params, one changed argv builder, a container-verified
end-to-end proof, and an architecture rule stating that `co_install` never orders anything.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| registry -> pnpm argv | Registry-declared strings become argv elements of a global package install. |
| npm package -> local machine | An installed package's lifecycle scripts execute with the user's privileges. |
| GitHub/npm registry -> container | The Tier-3 tracer fetches and executes real upstream code inside a disposable container. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-05-01 | Elevation of Privilege | `allow_build` on a `kind="node"` method | high | mitigate | `load_tools` rejects any `allow_build` name outside `{npm_pkg} ∪ co_install` (Task 2), so a registry entry can only ever un-gate a postinstall for a package that same invocation installs. No blanket allow-all and no `dangerouslyAllowAllBuilds` anywhere. |
| T-05-02 | Tampering | comma injection through `npm_pkg`/`co_install` | medium | mitigate | Both are rejected at load time when they contain a comma (Task 2), so a registry value cannot smuggle extra packages into an install group through the separator. |
| T-05-03 | Spoofing | argv[0] resolution for pnpm | medium | mitigate | Unchanged from plan 04-03: `real_pnpm()` returns an absolute path that skips this installer's own shim dir, so the argv-conditional wrapper cannot rewrite a catalog install into `volta install` (which per `installer/registry.toml`'s volta comment runs npm lifecycle scripts unrestricted). Task 3 explicitly preserves this. |
| T-05-04 | Denial of Service | Tier-3 container executing real upstream installers | low | accept | Runs inside a disposable `docker run --rm` container under colima per ONESHOT-RULES Rule 14, never against the host. Container is torn down by `--rm` in the same invocation. |
| T-05-SC | Tampering | npm/pip/cargo installs | high | mitigate | This plan adds no dependency to the project itself; it changes an argv builder and its validation. The npm packages it makes installable (`puppeteer`, `@mermaid-js/mermaid-cli`) carry their legitimacy gate in plan 05-03 Task 1, which runs before their registry entries land. 05-RESEARCH.md's Package Legitimacy Audit records both as `too-new`-heuristic flags on canonically-sourced, high-download packages. |
</threat_model>
