<objective>
Give the `kind="node"` method four new optional params — `co_install` (npm package names
that must land in the SAME pnpm global install group as this method's own `npm_pkg`),
`allow_build` (npm package names whose postinstall scripts are explicitly permitted),
`versions` (a package-name -> semver-range table pinning group members), and `min_node`
(the minimum node runtime the resulting install needs) — plus the runtime version preflight
that refuses to use any of it on a toolchain too old to support it, and prove the resulting
install sequence really produces a working `mmdc` before any registry data depends on it.

Purpose: REQ-puppeteer-catalog-entries says `mmdc.requires` gains `puppeteer` "so
`resolve_dependencies` drags it in automatically". 05-RESEARCH.md Pitfall 1 shows that
`requires` alone satisfies the catalog's install ORDER while leaving `mmdc` unable to
resolve `puppeteer` at runtime: pnpm's own documentation states that each `pnpm add -g`
invocation — and each space-separated package inside one invocation — gets its own
isolated `node_modules`/lockfile, and that only the comma-separated form bundles packages
into one group that "share a `node_modules` tree and lockfile, resolve peer dependencies
against each other, and are removed together". 05-RESEARCH.md Pitfall 2 shows the second
half: puppeteer's `postinstall` (`node install.mjs`, the Chrome + chrome-headless-shell
download) is blocked by pnpm's default-deny build-script gate and exits 0 with only a
warning. Both gaps live in the executor, not in registry data, so they are fixed here first
and consumed by plan 05-03.

Decisions implemented:
- D-03: one `puppeteer` catalog entry whose dependency really works on the platforms it
  claims. This plan supplies the mechanism that makes D-03's single entry functional
  rather than declarative; plan 05-03 supplies the entry itself and its platform gating.
- Claude's Discretion (CONTEXT.md): "exact registry kind/method shape" — resolved as
  additive optional params on the existing `kind="node"` method rather than a new method
  kind or a new registry-level dependency-group concept. Rationale: `installer/deps.py`
  keeps sole ownership of install ORDER (`.claude/architecture.md`'s tier rule), and the
  new params shape only the pnpm INVOCATION.
- 05-RESEARCH.md "Common Pitfalls" option 1 (the recommended one) over option 2:
  option 2 would teach `installer/session.py::run_installs` to detect adjacent
  same-manager tools and coordinate them, which is a second ordering mechanism living
  outside `requires` — forbidden by `.claude/architecture.md`.

Recorded deviation from 05-CONTEXT.md (added 2026-09-05, cross-AI review cycle 1):
05-CONTEXT.md's `<specifics>` states Phase 5 is "strictly a method correction ... no new
tools, no new mechanisms." This plan does add a mechanism: four method params, a load-time
validator for them, an injectable version-probe seam, and a semver-comparison helper. The
deviation is deliberate and is recorded here rather than left implicit, exactly as ROADMAP
SC#3's wording was formally amended. The reason it is unavoidable: ROADMAP SC#3 requires
`mmdc.requires` to include `puppeteer` AND requires the resulting install to work, and
05-RESEARCH.md establishes that no arrangement of EXISTING registry fields produces a
shared pnpm install group. Declining the mechanism would mean shipping a `requires` edge
that satisfies the criterion's letter and leaves `mmdc` broken — the scope reduction this
project's planning rules forbid. The mechanism is additive: every method that declares none
of the new params produces byte-identical argv and runs zero extra subprocesses.

Task-count note: this plan carries 4 tasks rather than the usual 2-3. Task 1 modifies no
repository file (it is the Tier-3 evidence run), and Tasks 3 and 4 both edit
`installer/executors.py::_node`, so splitting them across plans would put two plans on the
same function in the same wave. The argv builder and the version preflight are separated
into two tasks because they fail for different reasons and are verified by different
commands, not because they could run in parallel.

Output: four validated method params, one changed argv builder, one fail-closed version
preflight, a container-verified end-to-end proof including the brownfield case, and an
architecture rule stating that `co_install` never orders anything.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| registry -> pnpm argv | Registry-declared strings become argv elements of a global package install. |
| npm package -> local machine | An installed package's lifecycle scripts execute with the user's privileges, and pnpm's permission for them persists past this invocation. |
| local toolchain -> installer | `pnpm --version` / `node --version` output is read back and gates a mechanism. |
| GitHub/npm registry -> container | The Tier-3 tracer fetches and executes real upstream code inside a disposable container. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-05-01 | Elevation of Privilege | `allow_build` on a `kind="node"` method | high | mitigate | **Scope correction (cross-AI review cycle 1):** `--allow-build=<pkg>` is NOT invocation-scoped. pnpm's own `add` documentation states the flag "will run its postinstall script and **also add it to the `allowBuilds` field**… So, it **will always be allowed to run its scripts in the future**", added in pnpm 10.4.0. The grant is therefore PERSISTENT and PACKAGE-LEVEL: once this installer runs it for `puppeteer`, any later `puppeteer` version's postinstall runs unprompted on that machine, including one installed by a command this project never issued. Mitigations, in force together: (1) `load_tools` rejects any `allow_build` name outside `{npm_pkg} ∪ co_install` (Task 2), so the persistent grant can only ever be created for a package the same invocation installs — never a blanket allow-all and never `dangerouslyAllowAllBuilds`; (2) the same registry entry pins that package with `versions` (plan 05-03), bounding the pre-authorised code to one major line whose peer range is known; (3) plan 05-03 Task 1's legitimacy gate binds the package identity and records the exact approved version before the grant is ever created; (4) Task 1 of this plan records where pnpm persisted the grant, so the artifact is observable rather than assumed. **Residual risk, accepted explicitly:** a compromised patch release inside the pinned major line still runs its postinstall silently. This is accepted because the alternative — declining the grant — produces an `mmdc` that installs successfully and cannot render, which the phase exists to prevent, and because the only stronger control (npm provenance/integrity pinning of an exact version) would freeze the browser at one build with no update path. Recorded on the registry entry by plan 05-03 Task 3. |
| T-05-02 | Tampering | comma injection through `npm_pkg`/`co_install`/`versions` | medium | mitigate | All three are rejected at load time when they contain a comma (Task 2), so a registry value cannot smuggle extra packages into an install group through the separator, on either side of the `@`. |
| T-05-03 | Spoofing | argv[0] resolution for pnpm, and the version probe's target | medium | mitigate | Unchanged from plan 04-03: `real_pnpm()` returns an absolute path that skips this installer's own shim dir, so the argv-conditional wrapper cannot rewrite a catalog install into `volta install` (which per `installer/registry.toml`'s volta comment runs npm lifecycle scripts unrestricted). Task 3 preserves it, and Task 4's pnpm probe uses that same resolved absolute path rather than a bare name, so the version the gate reads is the version that will run. |
| T-05-18 | Tampering | a mechanism running on a toolchain that silently mis-parses it | high | mitigate | Task 4's fail-closed preflight. On pnpm 10 a comma-joined group is not a group but one package name containing a comma, and `--allow-build` is an unknown option; on node below a declared `min_node`, puppeteer's postinstall cannot run. Each is refused with an `ExecutorError` naming observed and required versions, and an unreadable version is treated as too old rather than waved through. |
| T-05-04 | Denial of Service | Tier-3 containers executing real upstream installers | low | accept | Every run is inside a disposable `docker run --rm` container under colima per ONESHOT-RULES Rule 14, never against the host. Containers are torn down by `--rm` in the same invocation. |
| T-05-SC | Tampering | npm/pip/cargo installs | high | mitigate | This plan adds no dependency to the project itself; it changes an argv builder, its validation, and a version gate. The npm packages it makes installable (`puppeteer`, `@mermaid-js/mermaid-cli`) carry their legitimacy gate in plan 05-03 Task 1, which runs before their registry entries land. 05-RESEARCH.md's Package Legitimacy Audit records both as `too-new`-heuristic flags on canonically-sourced, high-download packages. |
