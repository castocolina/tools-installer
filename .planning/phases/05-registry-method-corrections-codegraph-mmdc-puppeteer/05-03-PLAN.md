<objective>
Add `puppeteer` as its own platform-conditional catalog tool, wire `mmdc.requires` and
`mmdc`'s node method to it, and record `mmdc`'s install-method decision — stays on pnpm,
brew and Volta both rejected — as a durable, test-guarded artifact rather than an implicit
registry edit.

Purpose: REQ-puppeteer-catalog-entries and REQ-mmdc-install-decision, ROADMAP SC#2 and SC#3.
This is the plan that consumes plan 05-01's mechanism: without `co_install` the
`mmdc.requires = ["pnpm", "puppeteer"]` edge satisfies the catalog's ordering layer while
leaving `mmdc` unable to `require('puppeteer')` at runtime (05-RESEARCH.md Pitfall 1), and
without `allow_build` puppeteer's install exits 0 with no browser downloaded
(05-RESEARCH.md Pitfall 2).

Decisions implemented:
- D-01: `mmdc`'s install method was genuinely researched rather than assumed, and the soft
  lean toward Homebrew is overturned by a documented finding — upstream mermaid-cli's own
  README states the Homebrew path is "no longer supported", and GitHub issue #1122 (closed
  "not planned") records brew-installed `mmdc` failing at runtime with a
  chrome-headless-shell error because the formula's only declared dependency is `node`.
  Volta is rejected too, reusing Phase 4's already-committed volta-internals finding rather
  than re-deriving it. `mmdc` stays on pnpm.
- D-02: the decision is weighed against all four of the user's criteria, and the weighing is
  written into the registry beside the entry: STABILITY (brew is a currently-reproducing
  breakage, not a hypothetical), SECURITY (Volta's `npm install --global` runs every
  lifecycle script unrestricted, while pnpm's default-deny gate plus a scoped
  `--allow-build=puppeteer` is a reviewable, minimal allowlist), SIMPLICITY (mmdc is already
  a `kind="node"` entry; staying is a no-migration outcome), MAINTAINABILITY (one manager
  for mmdc and its peer, so the pair can share one install group).
- D-03: exactly one `puppeteer` catalog entry, with platform-conditional methods, exactly as
  the decision's own words asked for. The install MECHANISM is verified identical on macOS
  and on Linux amd64 (both `pnpm add -g puppeteer`), so the two methods differ only in their
  platform scoping and not in their params. The real asymmetry is twofold, and this revision
  splits it correctly: the Linux shared-library prerequisite (~30 system libraries headless
  Chrome links against) is a documented caveat, because the tool CAN work once they are
  present; but Linux arm64 is a hard unavailability, because puppeteer's own troubleshooting
  documentation states Chrome publishes no Linux arm64 binary at all, so no amount of
  prerequisite installation makes the downloaded browser run there. The entry therefore
  declares `arch = ["amd64"]` on its Linux method and resolves to nothing on Linux arm64.
- Claude's Discretion (CONTEXT.md): `chrome-headless-shell` gets NO separate entry —
  puppeteer's own `postinstall` (`node install.mjs`) downloads both Chrome for Testing and
  `chrome-headless-shell` into `~/.cache/puppeteer`, so there is no independent install path
  to model.

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-05-09 | Elevation of Privilege | puppeteer's `postinstall` (`node install.mjs`) | high | mitigate | **Scope correction (cross-AI review cycle 1):** `--allow-build=puppeteer` is NOT scoped to this invocation. pnpm's own `add` documentation states the flag also adds the package to pnpm's build-allowance configuration, so it "will always be allowed to run its scripts in the future" on that machine — including for versions installed by commands this project never issues. The grant is un-gated deliberately and narrowly, with four controls in force: (1) `allow_build` names exactly one package and plan 05-01's load-time rule forbids naming any package the same invocation does not install, so a blanket grant is impossible; (2) `versions = { puppeteer = "^25" }` bounds the pre-authorised code to one major line, chosen as the ceiling of mmdc's own peer range; (3) Task 1's legitimacy gate binds the package's canonical repository and records the approved version's integrity value before the grant is created; (4) Task 3 writes the persistence fact onto the entry so it is discoverable by whoever next reads the registry. pnpm's default-deny gate stays in force for everything else, and Volta — which per this registry's own `volta` comment runs every lifecycle script unrestricted — is explicitly rejected as mmdc's manager. |
| T-05-19 | Elevation of Privilege | a future puppeteer release inheriting the persistent grant | medium | accept | Residual after T-05-09's controls: a compromised release INSIDE the pinned `^25` line still runs its postinstall silently, and if plan 05-01's probe showed a version specifier cannot ride inside a comma group, the grouped install additionally resolves at `latest` rather than at the pin. Accepted rather than mitigated because the two stronger controls both cost more than the risk: pinning to an exact `dist.integrity` freezes the browser at one build with no security-update path, and declining the grant entirely produces an `mmdc` that installs successfully and cannot render — the failure this phase exists to remove. Recorded on the entry (Task 3) and in `05-03-SUMMARY.md` so the acceptance is explicit and revisitable, not implicit. |
| T-05-10 | Spoofing | `puppeteer` / `@mermaid-js/mermaid-cli` package identity | high | mitigate | Task 1 discharges 05-RESEARCH.md's two `SUS` flags against live `registry.npmjs.org` metadata using a NORMALIZED EXACT `owner/repo` match (the previous substring test accepted look-alike owners and hosts), plus real creation date and published-version count. The expected repository is bound per package to the fetched document's own `name`, so one package cannot be discharged by the other's repository, and the gate runs under `set -eu` with `|| exit 1` per iteration so the first mismatch aborts with a non-zero status rather than falling through to the success marker. Explicitly scoped: this authenticates registry metadata identity, not tarball bytes. |
| T-05-20 | Spoofing | the installed tarball itself | medium | accept | No integrity verification covers the npm artifact `pnpm add -g` downloads, in contrast to `codegraph`'s checksummed GitHub download in plan 05-02. Task 1 records the approved version's integrity value so the artifact this phase reasoned about remains identifiable, and the gap is stated rather than implied. |
| T-05-11 | Tampering | drag-in installing a tool the user did not select | medium | accept | Inherent to `requires`, which is the mechanism ROADMAP SC#3 asks for. Mitigated by disclosure, not prevention: `installer/deps.py::missing_requires` surfaces the drag-in in the tier-scoped view at mark time, and `render_dependency_notice` reports it before the install confirmation prompt. `puppeteer` is a real, visible catalog entry rather than an invisible peer dependency — which is the point of REQ-puppeteer-catalog-entries. |
| T-05-12 | Repudiation | reporting a successful install of a tool that cannot run | high | mitigate | **Corrected in cross-AI review cycle 1.** `installer/engine.py::install_tool` reports INSTALLED on any pnpm exit 0, so before this revision a Linux arm64 user was told puppeteer installed successfully although Chrome publishes no Linux arm64 binary. The Linux method now declares `arch = ["amd64"]`, so `installer/resolve.py::_applies` returns no method there, `installer/app.py`'s `available` callback reports unavailable, and `installer/deps.py::is_blocked` skips both puppeteer and `mmdc` with a warning. Residual, accepted and documented: a caller that bypasses `resolve_dependencies` and calls `install_tool(mmdc)` directly on Linux arm64 still installs a non-functional mmdc — the production wizard path does not do this, and closing it would mean a second availability rule outside the resolver. |
| T-05-21 | Denial of Service | a brownfield machine left with a split install group | medium | accept | A machine that already has standalone `mmdc` never reaches the grouped invocation, because `install_tool` returns `ALREADY_INSTALLED` and `deps.py` drops installed tools from the order. Recorded on the entry (Task 3) so the next uninstall or Doctor-UX phase inherits the fact instead of rediscovering it. |
| T-05-13 | Repudiation | pnpm reporting success while skipping a build script | medium | mitigate | Plan 05-01's Tier-3 tracer asserts `~/.cache/puppeteer` is non-empty after the install, which is the observable that distinguishes a real install from the silent no-op.
