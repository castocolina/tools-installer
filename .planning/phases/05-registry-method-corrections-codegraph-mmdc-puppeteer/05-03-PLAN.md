<objective>
Add `puppeteer` as its own catalog tool, wire `mmdc.requires` and `mmdc`'s node method to it,
and record `mmdc`'s install-method decision — stays on pnpm, brew and Volta both rejected —
as a durable, test-guarded artifact rather than an implicit registry edit.

Purpose: REQ-puppeteer-catalog-entries and REQ-mmdc-install-decision, ROADMAP SC#2 and SC#3.
This is the plan that consumes plan 05-01's mechanism: without `co_install` the
`mmdc.requires = ["pnpm", "puppeteer"]` edge satisfies the catalog's ordering layer while
leaving `mmdc` unable to `require('puppeteer')` at runtime (05-RESEARCH.md Pitfall 1), and
without `allow_build` puppeteer's install exits 0 with no browser downloaded
(05-RESEARCH.md Pitfall 2).

Decisions implemented:
- D-01: `mmdc`'s install method was genuinely researched rather than assumed, and the soft
  lean toward Homebrew is overturned by a documented finding — upstream mermaid-cli's own
  README states the Homebrew path is "no longer supported", and GitHub issue #1122 (closed
  "not planned") records brew-installed `mmdc` failing at runtime with a
  chrome-headless-shell error because the formula's only declared dependency is `node`.
  Volta is rejected too, reusing Phase 4's already-committed volta-internals finding rather
  than re-deriving it. `mmdc` stays on pnpm.
- D-02: the decision is weighed against all four of the user's criteria, and the weighing is
  written into the registry beside the entry: STABILITY (brew is a currently-reproducing
  breakage, not a hypothetical), SECURITY (Volta's `npm install --global` runs every
  lifecycle script unrestricted, while pnpm's default-deny gate plus a scoped
  `--allow-build=puppeteer` is a reviewable, minimal allowlist), SIMPLICITY (mmdc is already
  a `kind="node"` entry; staying is a no-migration outcome), MAINTAINABILITY (one manager
  for mmdc and its peer, so the pair can share one install group).
- D-03: exactly one `puppeteer` catalog entry, and whether the dependency applies identically
  across platforms is VERIFIED rather than assumed. The verified answer: the install
  MECHANISM is identical on macOS and Linux (both `pnpm add -g puppeteer`), and the real
  platform asymmetry is a Linux-only runtime prerequisite — ~30 system shared libraries
  headless Chrome links against, plus the fact that Chrome publishes no Linux arm64 build at
  all. That asymmetry is recorded on the entry and is deliberately NOT modeled as a `requires`
  edge; 05-RESEARCH.md's Anti-Patterns section shows a Linux-only system-deps tool would
  resolve `available() == False` on macOS and make `installer/deps.py::is_blocked` skip
  puppeteer and mmdc on the platform that needs no such prerequisite at all.
- Claude's Discretion (CONTEXT.md): `chrome-headless-shell` gets NO separate entry —
  puppeteer's own `postinstall` (`node install.mjs`) downloads both Chrome for Testing and
  `chrome-headless-shell` into `~/.cache/puppeteer`, so there is no independent install path
  to model.

Scope boundary: `graphify` (Phase 8) and codegraph's MCP postinstall (Phase 9) stay out, per
05-CONTEXT.md `<specifics>`.

Output: one new `[[tool]]` block, an amended `mmdc` block, two comment blocks recording the
decision and the platform asymmetry, one Key Decisions row, and the registry-integrity tests
that keep `co_install` honest.
</objective>
