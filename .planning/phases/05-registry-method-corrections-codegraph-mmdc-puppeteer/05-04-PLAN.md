<objective>
Teach the pnpm-globals snapshot/replay mechanism about install groups, version pins and
build allowances, so the Doctor's reinstall action cannot silently undo the `mmdc` +
`puppeteer` co-install that plan 05-03 ships — and so it becomes the working remedy for the
brownfield machine that never got the co-install in the first place.

Purpose: Phase 4 shipped `installer/pnpm_globals.py` to replay pnpm's live global set in one
invocation after a pnpm self-update loses it (plan 04-05). It builds
`[pnpm, "add", "-g", *packages]` — packages separated by SPACES. pnpm's own Global Packages
documentation states that space-separated packages in a single command each get their own
isolated `node_modules` tree and lockfile, and that only a comma-separated list bundles them
into one group that resolves peer dependencies against each other. Before this phase that
distinction was invisible, because the residual `kind="node"` set was `mmdc` alone. Plan
05-03 makes `mmdc` + `puppeteer` the first real install group in this catalog, and from that
moment the existing replay actively breaks it: `pnpm list -g --json` reports both packages,
the replay reinstalls them space-separated as two isolated groups, and `mmdc` stops being
able to load `puppeteer`. That is exactly the runtime failure 05-RESEARCH.md Pitfall 1
describes, reintroduced by a remediation action the user is invited to run.

This plan closes it rather than leaving it as a known-broken gap. It is additive: every
existing caller that passes no policy keeps today's exact argv and spawns no extra process.

Second purpose, added in cross-AI review cycle 1: this replay is also the documented remedy
for the phase's brownfield gap. A machine that already had a standalone `mmdc` never runs
the grouped invocation, because `installer/engine.py::install_tool` returns
`ALREADY_INSTALLED` before `resolve_methods` is consulted and `installer/deps.py` drops
already-installed tools out of the order. Plan 05-01's Tier-3 container measured that
failure and then measured this exact replay argv repairing it. Plan 05-03 writes the gap and
the remedy onto the registry entry. This plan makes the remedy real and pins it with a
regression test named for the failure rather than for the mechanism.

Decisions implemented:
- D-01: `mmdc` stays on pnpm, so it remains a pnpm-managed global and stays inside this
  module's scope — the Volta redirect never covers it. That is the whole reason this
  interaction exists and has to be handled here.
- D-03: `puppeteer` is a real catalog entry with its own build allowance and version pin, so
  the replay must carry both or a replay onto a cold browser cache reproduces Pitfall 2 and a
  repair silently moves the pinned peer.

Third purpose, added in cross-AI review cycle 2: make the brownfield condition VISIBLE. Cycle
2's first HIGH concern is that a remedy documented in `installer/registry.toml` is not a
remedy — `installer/engine.py:80-83` still short-circuits on an already-installed `mmdc`, so
an affected user is never routed anywhere, and the only written record lives in a file they
never read. Task 3 closes that by teaching the Doctor's existing pnpm-globals audit (Phase 4's
`audit_node_globals`) to compare the registry's declared install groups against pnpm's LIVE
group membership and report a split as its own named condition. It reuses the surfaces that
already exist: one new field on `NodeGlobalsReport`, one new item from
`installer/guidance.py::node_globals_guidance`, and no change to `installer/wizard_app.py` or
`installer/render.py`, both of which already render whatever that function returns.

Recorded deviation from 05-CONTEXT.md: the `NodeInstallPolicy` layer this plan adds is a new
mechanism, which `<specifics>` said this phase would not add. The deviation is recorded here,
in plan 05-01's objective, and as a Key Decisions row in `.planning/PROJECT.md` (plan 05-03
Task 3). The reason is the same in every case: without it, a remediation action this project
ships would actively re-break the thing ROADMAP SC#3 asks for.

Output: a registry-derived install policy carrying groups, allowances and pins; a
group-aware, pin-aware, allowance-aware argv builder with a truthful return contract and a
version floor; the two `setup.py` wiring lines that feed it; a corrected module docstring
that states what the replay cannot reconstruct; and a Doctor condition that tells an affected
user their install group is split and which key repairs it.
</objective>

      `versions: tuple[tuple[str, str], ...]` (package name paired with the semver range the

      value stays frozen, hashable and order-deterministic, which is what makes the
      preview-equals-effect assertion a stable equality rather than a dict-ordering accident.

      together, and it is intersected with pnpm's live set before it affects any argv.

    Extract the argv tail into a private helper

    `(flags, specs)`, and build it in three steps:

    1. De-duplicate `packages` with `dict.fromkeys`, as today.
    2. Walk that order once. When a package is the first member (in `packages` order) of a
      declared group, emit ONE spec element joining every group member that is actually
      present in `packages`, comma separated, each member rendered as its bare name or as

      Never add a package to the specs that is not in `packages` — the replay's contract is

      user never chose.
