## Gaps Summary

One gap, precisely scoped, cheap to close, and against the phase's own governing principle rather than against new scope.

The phase built a correct and well-guarded **mechanism** for Linux-cask ownership (`_OWNERSHIP_ONLY_KINDS` / `_method_targets_platform` / `_ownership_only_methods`, with a cross-module parity gate that keeps it from drifting from `resolve.py::_applies`, and with `resolve.py` itself deliberately untouched so install behaviour on Linux is unchanged). Result: the Owner column renders **blank** and the Uninstall cell renders **"package manager"** — which is exactly what the ROADMAP goal clause "an Owner column whose blank cell only ever means genuinely-don't-know" and D-02's verbatim user rationale ("everything in the catalog should be traceable") forbid.

I confirmed this is purely a data gap, not a mechanism gap, by injecting a Linux-gated cask method into the in-memory `Tool` and re-resolving: `unknown` -> `cask` / `visual-studio-code-linux` / label "Homebrew cask" / hint "managed by Homebrew — `brew uninstall --cask visual-studio-code-linux`", with no code change at all. The fix is one registry row in the shape commit `dda9814` already established, plus the matching `test_registry.py` pair (row exists; `resolve_methods` still returns no cask method on Linux so install behaviour stays unchanged), plus a short audit for any third instance — both casks `brew list --cask` reports on this host carry the `-linux` suffix, which suggests the suffix is the linuxbrew norm rather than a jetbrains-toolbox peculiarity.
