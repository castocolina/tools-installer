# Phase 15.4: Catalog ownership visibility and Uninstall screen real manager attribution - Context

**Gathered:** 2026-09-15
**Status:** Ready for planning

<domain>
## Phase Boundary

Two related visibility gaps, both about *who owns/manages a tool* not being surfaced
where the user actually looks: (1) the main catalog table has no visible package-manager
column — ownership only appears in the focused-row detail bar; (2) the Uninstall
screen's "Installed via" column shows a generic 4-value enum string
("userspace"/"managed elsewhere") instead of the real manager name/path `uninstall.py`
already computes but discards, and its own manager detection only knows brew/cask
(never dnf/apt/pacman/rpm-ostree/pnpm/volta/sdkman/uv). This phase also fixes a related,
more severe bug discovered during discussion: `UninstallScreen._rows` (the whole
tool-list-with-install-state) is computed exactly once at app startup and never
re-derived — an install/uninstall performed during the session can leave this screen's
tool list permanently stale or missing newly-installed tools.

</domain>

<decisions>
## Implementation Decisions

### Main catalog: Owner column
- **D-01:** Add a visible "Owner" column to the main catalog table (`_COLUMNS`/
  `_row_cells` in `catalog_tui.py`), reading the same ownership data
  `_version_detail` (`catalog_tui.py:385-429`) already computes via
  `service.ownership_of(tool.id)` — no new data plumbing, only a new rendered cell.
  — **Reversibility:** reversible.

  **Correction (2026-09-16, live UAT finding during Phase 15.1 closure — READ BEFORE
  PLANNING):** D-01's "no new data plumbing" premise is disproven on this real host.
  Live investigation (subagent, this session) confirmed `service.ownership_of()` /
  `resolve_ownership` genuinely returns `owner='unknown'` today for at least two real,
  legitimately-owned tools:
  - **git** — OS base-image RPM (`/usr/bin/git`, `rpm -qf` confirms `git-core-...`),
    not in the booted deployment's `requested-packages` (only explicitly-layered
    packages are tracked by `_rpm_ostree`, `installer/install_ownership.py:130-170`
    — a base-image package is invisible to it by design). **No "OS base image" owner
    concept exists in the current model at all.**
  - **jetbrains-toolbox** — installed via linuxbrew cask (`jetbrains-toolbox-linux`),
    but `installer/registry.toml`'s `cask` method for this tool is gated
    `os = ["macos"]` (dropped on Linux), AND the declared cask name
    (`jetbrains-toolbox`) doesn't match the actual installed cask name
    (`jetbrains-toolbox-linux`) — a registry data gap, not just a resolver gap.
  Implementing D-01 as originally locked (render whatever `ownership_of()` already
  returns) would ship an Owner column reading "unknown" for exactly the cases D-02's
  governing principle ("blank should only ever mean genuinely don't know") forbids
  treating as acceptable. **This phase's planning MUST include:** (a) a base-image/OS
  owner resolution path for immutable hosts (e.g. `rpm -qf <active_path>` against the
  live filesystem, independent of `_rpm_ostree`'s layered-only evidence — note
  `install_ownership.py:178`'s `_rpm_owns_path` already exists and may be reusable),
  and (b) a Linux-cask registry/path-attribution fix (the `jetbrains-toolbox-linux`
  naming mismatch, and casks not being categorically unmodeled on Linux). This is new
  resolver/registry work, not "just a rendered cell" — budget planning accordingly.

- **D-02:** Display rule: show an explicit label whenever the owner is knowable —
  including `dnf`/`apt`/`pacman`/`rpm-ostree`/`brew`/`cask`/`pnpm`/`uv` — regardless of
  whether the tool was originally installed through this app or found already present
  on the machine. Only genuinely `unknown`/not-yet-installed rows show blank/dash.
  — **Reversibility:** reversible.
  **Rationale (user, verbatim intent):** "todo lo que está en el catalog debería ser
  rastreable porque si está aquí es porque es importante para el usuario" — everything
  in the catalog should be traceable; a blank cell should only ever mean "genuinely
  don't know," never "didn't bother labeling this case."
  **Correction note:** per D-01's correction above, "knowable" must now be read as
  requiring the base-image-owner and Linux-cask fixes to actually exist — otherwise
  git/OS-package tools and Linux-cask tools stay incorrectly "unknown" and this
  decision's own principle is violated in practice, not just in wording.

- **D-02a (revision, same session):** When `owner == "installer"` — i.e. this app
  placed the artifact directly with no package manager mediating (e.g. a
  `github_release` binary drop or a `curl|sh` script) — do NOT render the bare word
  "installer" as if it were a manager peer to dnf/brew/pnpm. Instead render the actual
  placement mechanism (e.g. "github release" / "script") so the label is genuinely
  informative rather than a vague catch-all that implies a real package manager exists
  behind it. — **Reversibility:** reversible.
  **Rationale (user, verbatim):** "al final esta tools es un forwarder, no es que
  mantenga su propia BD o manage de tools, así que si es el mismo campo para decir
  this|others[dnf,pacman,pnpm] realmente no me sirve de nada" — a same-field
  this-app-vs-everyone-else label carries no actionable information given this app is
  not itself a package manager. Confirmed this does NOT require new persisted state:
  ownership resolution (`installer/ownership.py:1-37`) — including the `"installer"`
  case — is already computed live from the active binary path each refresh, so
  attaching the concrete method-kind label at render time introduces no new staleness
  surface beyond what D-05 already fixes for the owner value itself.

### Uninstall screen: real manager attribution
- **D-03:** `UninstallScreen`'s "Installed via" table cell (`wizard_app.py`'s
  `_tool_entry`, currently a static 4-value `UninstallState`-keyed dict) must derive
  from the real per-tool hint — the same rich string `uninstall.py`'s `_manager_hint`/
  `_managed_hint` already compute into `ToolRow.hint` (today only reaching the
  focused-row detail bar via `detail=row.hint`), not a generic enum-keyed string.
  — **Reversibility:** reversible.

- **D-04:** `uninstall.py`'s manager detection (`_manager_hint`, currently checks only
  `method.kind in {"cask", "brew"}`) must be wired to the fuller ownership resolution
  already proven for the catalog — reuse `installer/ownership.py`'s
  `resolve_ownership`/the `install_ownership.py`/`ownership.py` machinery, so
  pnpm/volta/sdkman/uv/dnf/apt/pacman/rpm-ostree-owned tools get a real, specific
  manager name instead of the generic "managed outside this installer" fallback.
  — **Reversibility:** reversible.

### Ownership data source and freshness
- **D-05:** Uninstall reuses the catalog's already-computed ownership map (not a
  fresh, duplicate probe on every Uninstall-screen open) — for speed. **But this must
  not repeat Phase 15.1's staleness bug**: the ownership data feeding both the Owner
  column (D-01) and the Uninstall attribution (D-03/D-04) must be refreshed on the
  same trigger Phase 15.1's D-01 established (the `ExecuteScreen`-close callback in
  `wizard_app.py`), so returning from any install/update/uninstall run leaves both
  screens showing current data, not a stale snapshot from before the run.
  — **Reversibility:** reversible — the reuse-vs-fresh-probe choice is a local
  wiring decision, not a data-model commitment.
  **Rationale (user):** explicitly required — "que no caigamos en el mismo problema
  del stale una vez que se instala/desinstala y volvamos al catalog o uninstall."

### Uninstall screen row-list staleness (scope addition, user-approved)
- **D-06:** `UninstallScreen._rows` (`wizard_app.py:600`, set once from
  `inputs.rows` at app construction, from `setup.py:408`'s one-time `classify_tools`
  call) must be re-derived — not just the environment rows (`_ban_names`,
  `_has_path_block`, `_tweak_ids`) that `enter_view()` (`wizard_app.py:773-791`)
  already re-checks on every entry — whenever the underlying install state could have
  changed. In scope for THIS phase (explicit user decision, not deferred): an install
  performed elsewhere in the session must make a newly-installed tool appear in
  Uninstall, and a tool's ownership label must reflect its current real state, the
  next time the Uninstall screen is entered. — **Reversibility:** reversible.
  **Rationale (user):** same domain (UninstallScreen), same refresh trigger being
  touched for D-05 — fixing it now avoids a second UAT round-trip on the same screen
  later.

### Claude's Discretion
- Exact column position/width for the new "Owner" column (D-01) within the existing
  `_COLUMNS` tuple order.
- Exact label wording for each owner value in the new column (can likely reuse or
  adapt the `labels` dict already built in `_version_detail`, `catalog_tui.py:392-405`) —
  except the `installer` case, which per D-02a must resolve to the tool's actual
  install method-kind (e.g. `github_release` → "github release") rather than any
  single fixed string; the exact source for that method-kind lookup (e.g. the
  `Method.kind` that `resolve_methods`/`ownership.py`'s active-path match already
  identified) is left to research/planning.
- Whether `UninstallScreen`'s row re-derivation (D-06) re-runs the full
  `classify_tools` call on every `enter_view()`, or only when a cheaper signal (e.g. an
  epoch/dirty flag set by the same install-close callback) indicates something changed
  — implementation shape, not a product decision, as long as the end result is
  "never stale after returning from an install/update/uninstall run."
- Whether `resolve_ownership`'s inventory/artifacts/managed_bin_dir construction is
  literally shared (same object instance) between the catalog's `VersionRefreshService`
  and Uninstall, or independently built with the same inputs — an implementation
  choice research should investigate given `version_status.py:521-527`'s existing
  call shape.

- `enter_view()`'s existing conditional-rebuild pattern (re-derive only when something
  actually changed, comparing tuples) in `UninstallScreen` (`wizard_app.py:773-791`) is
  the established shape D-06's fix should extend, not replace.
- Phase 15.1's `_install_closed`-as-refresh-trigger decision is the established pattern
  for D-05/D-06 — one callback, multiple screens made to re-derive their state from it.

### Integration Points

  single coordination point for D-05 and D-06 too — both screens' staleness share the
  same root cause and the same natural fix location.
