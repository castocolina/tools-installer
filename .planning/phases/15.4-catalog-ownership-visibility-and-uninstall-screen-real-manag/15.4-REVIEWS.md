## Codex Review

## 15.4-01

### Summary

Strong resolver-first plan with good evidence tracing from package-database probe through ownership resolution, update refusal, and catalog rendering. It correctly targets the current active-path early return in `installer/ownership.py:373-385` and the missing inverse query beside `installer/install_ownership.py:178-226`.

### Strengths

- Correctly identifies that existing probes only confirm a declared package, while `rpm -qf` must discover the actual package name (`installer/install_ownership.py:178-204`).
- Correctly places the new fallback before the active-path `unknown` branch (`installer/ownership.py:360-385`).
- Covers the current Owner-column integration points, which currently have only eight columns and no ownership cell (`installer/catalog_tui.py:157-166`, `435-460`).
- Includes update safety: the current refusal branch only handles `NATIVE_OWNERS` (`installer/update.py:225-269`).

### Concerns

- **MEDIUM** The plan introduces `os-package` as a direct-confidence owner, but its evidence is a generic package-database answer. It should explicitly define whether this value means “owned by the OS package database” or specifically “base image”; otherwise mutable Fedora packages and immutable base-image packages become indistinguishable.
- **LOW** The source-order and AST validation commands are brittle implementation tests. Behavioral tests already cover the important guarantee; these gates may reject harmless refactors without improving correctness.

### Suggestions

- Specify the displayed distinction between mutable OS-package ownership and immutable base-image ownership, or document why one label is intentional.
- Add tests for a package-database result on a mutable host and an immutable host, not only the git-shaped case.

### Risk Assessment

**MEDIUM.** The core design is sound, but the new owner category affects update refusal, labels, and downstream uninstall attribution.

## 15.4-02

### Summary

The plan correctly finds both Linux-cask blockers: the installer’s macOS-only cask gate and the registry-name mismatch. The ownership-only approach is appropriately narrower than changing installation behavior.

### Strengths

- The two-layer diagnosis is directly supported by `installer/resolve.py:61-69` and ownership’s dependence on `resolve_methods` (`installer/ownership.py:319-327`, `340-342`).
- The registry currently declares only the macOS cask name and gate (`installer/registry.toml:2162-2165`), so adding Linux ownership evidence is grounded.
- Preserving the install-time cask gate avoids broadening Linux installation behavior.

### Concerns

- **MEDIUM** The planned helper partially reimplements method applicability. `resolve.py::_applies` also handles minimum OS versions (`installer/resolve.py:40-46`), while the plan’s helper checks only OS and architecture. A future Linux cask with `min_os_version` could be attributed even when it should not apply.
- **LOW** The plan’s source gate asserting the implementation is “byte-identical” to the current cask branch is unnecessarily rigid and may make future refactoring harder.

### Suggestions

- Either reuse a shared applicability helper or explicitly document why ownership evidence intentionally ignores `min_os_version`.
- Test a Linux cask with an excluded architecture and, if supported by the schema, a minimum OS version.

### Risk Assessment

**LOW/MEDIUM.** The design is narrow and well-supported, with some future applicability-drift risk.

## 15.4-03

### Summary

The plan correctly addresses the current duplication between the catalog cell and detail bar. However, its requirements contain an internal contradiction: it demands a distinct cask label, byte-identical existing detail text, and no duplicate detail sentences.

### Strengths

- The current Owner cell is absent in both `_row_cells` branches (`installer/catalog_tui.py:435-460`), so exhaustive coverage is necessary.
- The current detail bar uses a local owner-label dictionary (`installer/catalog_tui.py:494-529`), making a shared vocabulary a reasonable refactor.
- The legend has an explicit three-line, 78-column constraint (`installer/catalog_tui.py:195-216`), and leaving it unchanged is sensible.

### Concerns

- **HIGH** The requirements cannot all be satisfied. Current code intentionally renders both brew and cask as `"managed by Homebrew"` (`installer/catalog_tui.py:500-503`). Plan 15.4-01 requires a distinct cask column label, while this plan requires the old cask detail sentence to remain byte-identical and also requires no two owner states to share a detail sentence.
- **MEDIUM** The plan says changing `OWNER_LABELS` must change both surfaces, but preserving the old cask detail wording requires a separate presentation mapping. Those two requirements conflict.
- **LOW** Exhaustiveness tests over `Owner` values do not guarantee distinct human-readable sentences; the collision test needs an explicit product rule.

### Suggestions

Choose one of these designs before execution:

- Allow the Owner column and detail prose to use different registers, preserving existing detail wording.
- Change cask detail wording and update the existing tests.
- Preserve duplicate brew/cask detail wording and remove the “no duplicate sentences” requirement.

### Risk Assessment

**HIGH.** The plan has mutually incompatible acceptance criteria and should be revised before implementation.

## 15.4-04

### Summary

The plan correctly targets the frozen uninstall snapshot and follows the existing entry-time refresh pattern. The main completeness problem is that changing `UninstallInputs.rows` from a list to a callable breaks several direct test constructors not covered by the plan.

### Strengths

- The stale snapshot is real: `UninstallScreen` stores `inputs.rows` directly (`installer/wizard_app.py:598-606`), while only the three environment predicates are re-evaluated (`installer/wizard_app.py:769-792`).
- The proposed navigation trigger matches the existing single path (`installer/wizard_app.py:1743-1765`).
- The current setup call is genuinely one-time (`setup.py:408-414`), so converting it to a closure addresses the root cause.
- Failure handling through `run_live` matches the project seam (`installer/ui_common.py:41-50`).

### Concerns

- **HIGH** The plan claims existing test call sites remain valid, but several tests construct `UninstallInputs` directly with list values. They would become non-callable and fail when `UninstallScreen` invokes `inputs.rows()`. Examples: `tests/test_catalog_tui.py:66-71`, `tests/test_uninstall_e2e.py:63-68`, `121-127`, `156-160`, and `tests/test_execute_screen.py:260-265`. The plan’s modified test files do not cover all of these call sites.
- **MEDIUM** The planned failure isolation applies to entry-time refresh, but initial evaluation in `UninstallScreen.__init__` will still call the new rows predicate directly. A filesystem `OSError` during app construction could therefore escape before `run_live` is involved.
- **LOW** Re-reading every catalog tool on every Uninstall entry may be expensive; the plan should at least record the expected cost, since the current setup performs classification only once (`setup.py:408-414`).

### Suggestions

- Either normalize `list | Callable[[], list]` inside `UninstallScreen`, or update every direct `UninstallInputs` construction and include those files in the plan.
- Decide whether initial row construction also needs `run_live` protection.
- Add a performance-oriented test or measurement for the full catalog entry path.

### Risk Assessment

**MEDIUM/HIGH.** The production approach is sound, but the unlisted constructor breakage is likely to fail the suite immediately.

## 15.4-05

### Summary

The plan correctly identifies that `_tool_entry` discards the richer hint and that `_manager_hint` currently only recognizes brew and cask. Its injected-seam design avoids duplicate probing, but its freshness guarantee is incomplete.

### Strengths

- The current table discards `row.hint` and uses a four-state enum map (`installer/wizard_app.py:625-648`), while the richer hint already reaches the detail bar (`installer/wizard_app.py:650-655`).
- The current manager detection is demonstrably brew/cask-only (`installer/uninstall.py:137-154`).
- Reusing the existing ownership map follows the service’s established resolution path (`installer/version_status.py:505-530`).
- Keeping the “What gets removed” cell unchanged is correctly scoped to the existing `removes` construction (`installer/wizard_app.py:634-648`).

### Concerns

- **HIGH** The claimed freshness chain does not actually guarantee fresh ownership data. `VersionRefreshService` updates `_ownership` only when its worker commits results (`installer/version_status.py:555-569`). During refresh, `ownership_of()` still returns the previous record, not `None`; therefore the planned fallback to a registry-derived hint will not occur for stale data.
- **HIGH** Uninstall itself does not invalidate or refresh the ownership service. `_apply_removal` performs the sweep and sets `applied`, but has no version-refresh invalidation (`installer/wizard_app.py:864-898`). The plan therefore does not fully satisfy D-05 after a same-session uninstall.
- **MEDIUM** A valid initial Uninstall view can be entered without ever refreshing a catalog. `UnifiedApp.on_mount` can open the requested view directly (`installer/wizard_app.py:1658-1670`), while ownership refresh is started by catalog entry (`installer/catalog_tui.py:317-322`). In that path, apt/dnf/pnpm/etc. still fall back to generic registry hints.
- **MEDIUM** This plan inherits the direct `UninstallInputs` constructor breakage identified in 15.4-04, but its file list also does not include all affected test files.

### Suggestions

- Add an ownership-refresh generation/readiness check and treat records from an older generation as unavailable while refresh is running.
- Invalidate or refresh ownership after uninstall, or explicitly narrow D-05 to install/update runs.
- Seed the shared ownership map before opening an initial Uninstall view, or document that manager attribution is best-effort there.
- Include every direct `UninstallInputs` construction in the migration plan.

### Risk Assessment

**HIGH.** The display wiring is straightforward, but the central “fresh shared ownership map” guarantee is not implemented by the proposed mechanism.
