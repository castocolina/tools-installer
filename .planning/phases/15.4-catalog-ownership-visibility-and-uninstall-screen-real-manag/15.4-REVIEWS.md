## Codex Review

## 15.4-01

### Summary

This is a strong resolver-first plan. It correctly places the new OS-package fallback between native-manager attribution and the active-path unknown return, and it preserves update safety. The main residual risk is cross-plan vocabulary coupling: later plans must consume the new owner consistently.

### Strengths

- Correct control-flow placement: the current native fallback must run before the active-path unknown return at `installer/ownership.py:360-385`.
- The inverse package query is appropriately separated from `_rpm_owns_path`, which currently requires a caller-supplied package name at `installer/install_ownership.py:178-180`.
- Fail-closed probe handling reuses `_run`, whose exception boundary is at `installer/install_ownership.py:66-70`.
- Update refusal is placed before the dispatch ladder, matching the current native-owner safety branch at `installer/update.py:225-253`.
- The plan explicitly protects the existing `NATIVE_OWNERS` contract while adding a broader refusal set.

### Concerns

- **MEDIUM:** The new `os-package` owner is added to ownership and update paths, but its detail-bar representation is intentionally deferred to 15.4-03. Between plan executions, `_version_detail` only has labels for the existing owners at `installer/catalog_tui.py:494-517`; the plan should make this dependency explicit as a hard intermediate-state requirement.

### Suggestions

- Add an explicit cross-plan contract stating that `OWNER_LABELS`, detail labels, update refusal, and removal hints must all include `os-package`.
- Include one mutable Fedora test as well as the immutable-host case, since the planned fallback deliberately runs without checking `platform.immutable`.

### Risk Assessment

**MEDIUM.** The resolver change is security-sensitive, but the evidence ordering, fail-closed query behavior, and update refusal are well specified.

## 15.4-02

### Summary

This plan accurately identifies and addresses both Linux-cask blockers: the registry-name mismatch and the macOS-only install resolver gate. The ownership-only design is appropriately narrow. The remaining risk is maintaining a duplicated applicability predicate despite the parity tests.

### Strengths

- Both independent blockers are grounded in source: the install gate is at `installer/resolve.py:67-69`, while the current registry only declares the macOS cask at `installer/registry.toml:2162-2166`.
- The candidate builder already handles cask inventory attribution at `installer/ownership.py:533-553`, so the plan extends an existing mechanism.
- Keeping `resolve.py` unchanged preserves Linux install behavior while adding ownership evidence.
- Feeding the same ownership-only methods into both candidate collection and unreadable-inventory detection directly addresses the existing guard at `installer/ownership.py:577-590`.
- The parity tests correctly cover the three dimensions used by `_applies`: OS, architecture, and minimum OS version at `installer/resolve.py:38-47`.

### Concerns

- **MEDIUM:** `_method_targets_platform` intentionally duplicates part of `_applies`. The parity test reduces drift risk, but future changes to `_applies` still require coordinated updates. This is an architectural maintenance cost, not merely a test concern.
- **LOW:** The real-registry test depends on a specific cask name and platform matrix, while the ownership-only path is intentionally broader than installability. Future registry entries could silently gain Linux ownership behavior without install behavior unless this convention remains documented.

### Suggestions

- Keep the parity test table-driven and require every future ownership-only method class to declare which install-gate dimensions it mirrors.
- Add a test showing that a Linux cask method with an unsupported `os` does not enter either candidates or `competing_owners`.

### Risk Assessment

**MEDIUM.** The blast radius is narrow and well tested, but the duplicated applicability logic remains a long-term drift point.

## 15.4-03

### Summary

The plan resolves the cycle-1 brew/cask contradiction coherently by separating column labels from detail prose. It also covers the new owner exhaustively and preserves the existing legend contract. The principal concern is that the two vocabularies introduce a new cross-plan consistency obligation.

### Strengths

- The current contradiction is real: brew and cask intentionally share `"managed by Homebrew"` in `installer/catalog_tui.py:494-517`, while the new column needs to distinguish them.
- Moving vocabulary out of the screen is consistent with the current `_version_detail` local dictionary and avoids another UI-owned registry.
- The Owner column integration point is clear at `installer/catalog_tui.py:435-460`.
- Section-row padding already derives from the live column count at `installer/tool_browser.py:149-156`, so the plan correctly avoids unnecessary changes there.
- The 80×20 legend constraint is concretely documented at `installer/catalog_tui.py:195-228`.

### Concerns

- **MEDIUM:** The two-register design creates a consistency constraint that 15.4-05 does not fully lock down. Its removal-hint requirement says generated text must contain `owner_label`, while 15.4-03 requires distinct cask and brew column labels and preserves the existing cask phrase. The existing cask phrase only contains `Homebrew` and `--cask` (`installer/uninstall.py:137-145`). Unless the cask column label is explicitly fixed to `cask`, a label such as `Homebrew cask` cannot satisfy both requirements.
- **LOW:** The minimum-size assertion that a known Owner value is visually reachable may be brittle because Textual’s table width and horizontal scrolling are determined at runtime; the existing table test currently checks height and legend fit, not visible ownership content at `tests/test_catalog_tui.py:1567-1608`.

### Suggestions

- Fix the exact cask column label in the plan, or explicitly exempt cask from the removal-hint label-agreement rule.
- Test the Owner cell through the table’s cell data as well as rendered output, separating semantic correctness from terminal-layout behavior.

### Risk Assessment

**MEDIUM.** The presentation design is sound, but label consistency across the column, detail bar, and uninstall hint needs one exact contract.

## 15.4-04

### Summary

This plan addresses the real stale-list and stale-ownership problems and correctly builds on the existing predicate pattern. However, it contains a concrete migration-count error and does not fully solve asynchronous ownership refresh visibility after an install.

### Strengths

- The current stale snapshot is directly confirmed by `setup.py:408-414`, where `classify_tools` is called once, and `wizard_app.py:598-611`, where the resulting list is stored.
- Extending `_live_state()` is structurally consistent with the existing three predicates at `installer/wizard_app.py:769-794`.
- The epoch fix targets a genuine flaw: current refresh commits ownership in both branches at `installer/version_status.py:555-569`, while `ownership_of()` simply returns the stored record at `installer/version_status.py:407-409`.
- Routing construction-time and entry-time reads through `run_live` is appropriate because its failure boundary is defined at `installer/ui_common.py:41-50`.
- The removal invalidation seam correctly mirrors the existing install/update invalidation pattern at `installer/wizard_app.py:1920-1947` and `installer/update.py:431-443`.

### Concerns

- **HIGH:** The construction-site count is wrong. The listed files currently contain 13 `UninstallInputs` calls: `setup.py:447`, `tests/test_wizard_app.py:113`, `tests/test_catalog_tui.py:66`, `tests/test_execute_screen.py:260`, six in `tests/test_policies_e2e.py:70,168,233,272,362,445`, and three in `tests/test_uninstall_e2e.py:63,121,156`. The planned AST gate asserts `len(calls) == 12`, so a correct migration will fail its own verification.
- **HIGH:** The install freshness chain is asynchronous. `_install_closed` calls `active.enter_view()` at `installer/wizard_app.py:1909-1911`; catalog entry starts a threaded refresh at `installer/catalog_tui.py:320-373`. If the user enters Uninstall before that worker commits, the epoch-gated map will correctly return `None`, but nothing later rebuilds the mounted Uninstall screen when the refresh completes.
- **MEDIUM:** The plan says a changed row state clears `applied`, but it does not specify how status warnings from a failed rows predicate interact with the unchanged-state early return. This needs an explicit precedence rule.

### Suggestions

- Change the AST expectation to 13, or explicitly exclude the helper and assert 12 direct production/test call sites.
- Add a refresh-completion callback or shared invalidation/refresh event that rebuilds Uninstall after ownership refresh completes; alternatively weaken the guarantee to “generic until refresh completion.”
- Add a deterministic test for entering Uninstall during an in-flight refresh and then asserting that the screen updates when the refresh commits.

### Risk Assessment

**HIGH.** The migration-count gate is objectively inconsistent, and the asynchronous refresh path can leave the visible Uninstall attribution stale or merely generic after a successful install.

## 15.4-05

### Summary

The injected-hint design is the right dependency direction and avoids duplicate manager probes. The main unresolved issue is that fallback attribution remains platform-insensitive, so the “best-effort” and epoch-stale paths can still produce confidently wrong Homebrew-cask labels.

### Strengths

- The current UI discards the richer hint at `installer/wizard_app.py:625-655`, exactly matching D-03’s target.
- The current weak manager detection is clearly isolated in `installer/uninstall.py:137-154`; injecting a callable avoids adding resolver imports or subprocesses.
- Reusing `VersionRefreshService.ownership_of()` follows the existing ownership refresh architecture at `installer/version_status.py:521-530`.
- The SDKMAN registry shape is real: tools such as Java declare `kind = "sdkman"` and `candidate` at `installer/registry.toml:1754-1761`.
- Keeping “What gets removed” separate from “Installed via” respects the current cell construction at `installer/wizard_app.py:628-648`.

### Concerns

- **HIGH:** The fallback path can misattribute tools because `_manager_hint` scans raw registry methods without checking platform applicability. For example, Codex declares a Linux script followed by a macOS-only cask at `installer/registry.toml:1343-1350`; on Linux, `resolve.py` excludes that cask at `installer/resolve.py:38-69`, but `_manager_hint` still returns the Homebrew-cask hint at `installer/uninstall.py:137-145`. This fallback is used precisely when ownership is absent or epoch-invalidated, so the plan’s claim that degradation is generic and never confidently wrong is not guaranteed.
- **HIGH:** The plan inherits 15.4-04’s asynchronous freshness gap. After `_install_closed`, ownership may be invalidated and then refreshed in a background catalog worker, while Uninstall has already rendered fallback hints. No completion signal causes it to rebuild.
- **MEDIUM:** Volta is treated as “not applicable,” but the phase goal explicitly names Volta-owned tools. The registry says Volta “owns globally installed Node CLIs” at `installer/registry.toml:1969-1976`, and the guard redirects global installs through `volta install` at `installer/app.py:342-348`. The current `Owner` type has no Volta value at `installer/ownership.py:71-73`, so the plan does not actually attribute such tools; it only observes that current catalog methods lack a Volta-owned method kind.

### Suggestions

- Make `_manager_hint` platform-aware by filtering through `resolve_methods`, or use the generic fallback whenever no shared ownership record exists.
- Add an explicit test for a Linux script+cask tool such as Codex in the direct-`--uninstall` and epoch-stale paths.
- Either implement a Volta ownership source or formally record Volta attribution as deferred/out of scope, with acceptance criteria explaining why the phase goal is not met.

### Risk Assessment

**HIGH.** The seam architecture is good, but the fallback can display a wrong manager and the main freshness guarantee depends on an unresolved asynchronous race.

## Cross-Plan Comparison

The resolver plans (15.4-01/02) are the most technically grounded. The rendering plan (15.4-03) is coherent after cycle 1, provided the cask label is fixed precisely.

The highest-risk area is the 15.4-04 → 15.4-05 freshness chain:

- `_install_closed` starts refresh asynchronously.
- Epoch invalidation correctly hides stale records.
- Uninstall can render fallback hints before the new refresh commits.
- No described completion event repaints Uninstall afterward.

The plan set should not be considered fully converged until the 13-site migration count and post-refresh Uninstall repaint behavior are corrected.

## Overall Risk Assessment

**HIGH.** The ownership resolver work is well designed, but two concrete integration defects remain: an impossible construction-count verification gate and an asynchronous freshness gap that can leave the Uninstall screen generic or incorrectly registry-attributed immediately after mutations.
