## Ownership data source for Uninstall

| Option | Description | Selected |
|--------|-------------|----------|
| Reutilizar el mapa de ownership del catalog | Reuse the catalog's already-computed ownership map (fast, no duplicate probe) | ✓ (with added constraint) |
| Probar en vivo cada vez que se abre Uninstall | Fresh probe every time Uninstall screen opens (slower, always current) | |

**User's choice:** Reuse the catalog's map — but with an explicit added constraint, not
a clean selection of the option as originally framed.

**User's own words (verbatim):** "Pero que no caigamos en el mismo problema del stale
una vez que se instala/desinstala y volvamos al catalog o unistall" (but let's not fall
into the same staleness problem once we install/uninstall and come back to catalog or
uninstall).

**Resolution:** Reuse is the data-source choice (D-05), but it must be paired with the
same refresh-on-`ExecuteScreen`-close trigger established in Phase 15.1's D-01, extended
to also invalidate/refresh the ownership data feeding Uninstall — not a static one-time
reuse. Captured as D-05 in CONTEXT.md, explicitly cross-referencing 15.1's precedent.

## Owner column display rule

| Option | Description | Selected |
|--------|-------------|----------|
| Blank/dash para tools manejadas por el installer o no instaladas | Blank for installer-managed or not-yet-installed tools, label only for native/brew/pnpm/etc | (rejected as framed) |
| Mostrar "installer" explícitamente también | Show an explicit "installer" label too, no blank case for anything installer-placed | ✓ (closest, but reframed) |

**User's choice:** Rejected the "blank for installer" framing entirely — not a clean
pick of option 2 either, but a broader principle that subsumes it.

**User's own words (verbatim):** "Si owner es dnf/brew/pnpm/pacman/ostree es lo que debe
mostrar indiferente si se instalo dese esta tools-installer o el user manualmente por
fuera. Todo lo que esta en el catalog deberia ser rastreable porque si esta aqui es
porque es importante para el usuario." (If owner is dnf/brew/pnpm/pacman/ostree, that's
what must show regardless of whether it was installed via this tools-installer or by the
user manually outside it. Everything in the catalog should be traceable because being in
the catalog means it matters to the user.)

**Resolution:** The display rule is not "installer gets a label too" as a special case —
it's a general traceability principle: show whatever owner is actually knowable,
regardless of installation origin (this app vs. manual). Blank/dash is reserved only for
genuinely unresolvable/unknown cases, never as a stand-in for "we didn't bother." Captured
as D-02 in CONTEXT.md.

## Uninstall row-list staleness (scope addition)

| Option | Description | Selected |
|--------|-------------|----------|
| Incluirlo en esta phase | Fold the newly-discovered `UninstallScreen._rows` staleness bug (never recomputed after app startup) into 15.4's scope | ✓ |
| Separarlo en su propia phase | Split it into its own new phase, keep 15.4 scoped to display-layer only | |

**Context:** Discovered mid-discussion while investigating the anti-staleness
constraint above — `UninstallScreen._rows` (`wizard_app.py:600`) is set once from
`setup.py:408`'s one-time `classify_tools()` call and never recomputed; `enter_view()`
only re-derives environment rows, not the tool list itself. A newly-installed tool
would not even appear in Uninstall.

**User's choice:** Incluirlo en esta phase (recommended option) — clean selection, no
further clarification needed.

**Resolution:** Captured as D-06 in CONTEXT.md, sharing the same refresh trigger as D-05.

## "installer" owner label revision

Raised by the user immediately after CONTEXT.md's first draft was written (D-02
originally included `installer` as just another label alongside dnf/brew/pnpm/etc.).

**User's objection (verbatim):** "Pues no sirve de nada eso, ya que al final esta
tools es un forwader, no es que mantenga su propia BD o manage de tools, asi que si
es el mismo campo para decir this|others[dnf,packman,pnpm] realmente no me sirve de
nada, ademas de que quizas tengamos que mantener una BD de ello que vaya a quedar
staled" (that's useless, since this tool is ultimately a forwarder — it doesn't
maintain its own DB/management of tools — so if it's the same field just saying
"this app vs. others [dnf, pacman, pnpm]" that's genuinely useless to me, plus we
might end up needing to maintain a DB for it that goes stale).

**Investigation:** Read `installer/ownership.py:1-37` (module docstring) to check
whether an `installer`-owner label would require new persisted state. Confirmed it
would not — ownership resolution (all values, `installer` included) is computed live
from the active binary path on every refresh, the same mechanism as every other
owner value; no separate DB. This answered the staleness half of the concern but not
the "not actionable" half.

| Option | Description | Selected |
|--------|-------------|----------|
| El mecanismo real | Render the concrete placement method (e.g. "github release", "script") instead of the generic "installer" label — communicates there's no real manager AND what actually placed it | ✓ |
| Etiqueta clara de "sin manager" | Generic "binario directo"/"sin package manager" label — clarifies it's not a real manager but doesn't say which mechanism | |

**User's choice:** El mecanismo real (recommended option).

**Resolution:** Captured as D-02a in CONTEXT.md — supersedes the original D-02
treatment of the `installer` case specifically (the general traceability principle
in D-02 for dnf/brew/pnpm/etc. stands unchanged).
