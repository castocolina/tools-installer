<objective>
Add the new `kind="uv-tool"` installer executor and wire it end-to-end through
`graphify`'s registry entry — the foundation ROADMAP Phase 8 needs before any of its
other three entries (`cursor-agent`, `antigravity`, `rtk`) can be usefully recommended
to an agent host. `uv tool install <pypi_pkg>` is `uv`'s own documented mechanism for
installing an isolated-venv Python CLI with a PATH shim, and this project already trusts
`uv` as its own toolchain owner (`CLAUDE.md`: "uv owns the environment... never
pip/poetry/conda"), so this executor is structurally the simplest one in
`installer/executors.py`: unlike `_node`, which resolves pnpm's real absolute path to
route around this project's own argv-conditional pnpm wrapper (Phase 4's
package-manager-redirect-policy), `uv` carries no entry in `installer/guards.py`'s
`BANNED`/`REDIRECTED`/`GLOBAL_REDIRECTED` dicts, so a bare `"uv"` argv element is correct
and no such indirection is needed.

While grounding this design against the actual `installer/resolve.py` source (not
assumed from 08-RESEARCH.md's Architecture Patterns diagram alone, which shows
`resolve.py` in the pipeline but does not call out a code change there), this plan found
a real gap 08-RESEARCH.md's Alternatives Considered section did not anticipate:
`_applies`'s kind dispatch is a CLOSED set — `script`/`node`/`sdkman`/`github_release`/
`tarball`/`app` return `True` unconditionally, `brew`/`cask` check `has_brew`,
`rpm_ostree` always returns `False`, and every OTHER kind falls through to
`_NATIVE_OS[kind] == platform.os`, where `_NATIVE_OS` is `{"dnf": ..., "apt": ...,
"pacman": ...}`. `"uv-tool"` is in none of these branches, so the very first
`resolve_methods(graphify, ...)` call after this phase's first entry lands would raise
`KeyError: 'uv-tool'` from that fallthrough — not a hypothetical, but the literal next
line of code any catalog render, `resolve_dependencies` call, or install attempt would
execute. This plan adds `"uv-tool"` to `_applies`'s unconditional-True set (mirroring
`node`/`sdkman`: the installer's own hard requirement is what gates it, not the
platform) and to `_RANK` at rung 20 (the "userspace install" tier, alongside
`node`/`sdkman`/`github_release`/`tarball`/`app` — before native package managers,
after an official script), so `resolve_methods` behaves correctly the moment `graphify`
loads.

This plan is the phase's tracer: the thinnest path that touches every layer the phase
modifies — model validation, resolver dispatch, executor dispatch, and registry data —
wired end-to-end with a real runnable verify, proven against the ACTUAL registry file
rather than a synthetic fixture alone. Because `graphify`'s package (`graphifyy`) is
flagged `[SUS]` by the automated package-legitimacy seam (a `too-new`/`unknown-downloads`
false positive — the seam's `publishedAt` signal reads only the LATEST release's
timestamp, not the package's real age, and `graphifyy` ships very frequently: 223
releases across five months), Task 1's action is ordered so the legitimacy gate runs
and is recorded BEFORE the registry entry itself is written — mirroring this project's
own established Phase 5 precedent (05-03-PLAN.md Task 1: an automated, fail-closed
identity check against live registry metadata, recorded in the SUMMARY, deliberately
NOT a `gate="blocking-human"` checkpoint, because ONESHOT-RULES Rule 9 reserves that gate
for what the Tier-3 container tier genuinely cannot cover, and Rule 14's
`human_verify_mode: end-of-phase` consolidates evidence into one end-of-run review
rather than a mid-run stop). Both concerns — proving the new executor kind end-to-end,
and discharging the one `[SUS]` package this phase installs — belong in the SAME leading
task precisely because the tracer's job is to wire every layer this phase touches, and
package trust is one of those layers for a package-installing capability.
