## Critical Issues

### CR-01: The test sandbox does not clear `BUN_INSTALL*`, so tests read the developer's real bun tree

**File:** `tests/sandbox.py:743-763` (`CLEARED_ENV_NAMES`, `CLEARED_ENV_PREFIXES`); consumed by `tests/conftest.py:237-258`
**Issue:** The autouse sandbox clears `PNPM_HOME`, `VOLTA_HOME`, `UV_*`, `XDG_*` and so on, but not `BUN_INSTALL`, `BUN_INSTALL_BIN` or `BUN_INSTALL_GLOBAL_DIR`. bun's own installer exports `BUN_INSTALL=$HOME/.bun` into the shell rc, so most developers have it set. `bun_dirs()` then ignores the per-test scratch `HOME` and points at the real `~/.bun`. Every test that does not set the bun variables itself reads the real manifest and real `node_modules`. This breaks the AGENTS.md rule that tests use a scratch HOME. Reproduced twice:
- A probe test run under the suite's own conftest, with `BUN_INSTALL=/home/bazzite/.bun` set in this shell, returned `bun_dirs() == (/home/bazzite/.bun/bin, /home/bazzite/.bun/install/global)` while `Path.home()` was the scratch dir.
- With `BUN_INSTALL` pointed at a scratch tree whose manifest lists `@mermaid-js/mermaid-cli`, `tests/test_version_status.py::test_node_floor_reads_the_probed_prerelease` fails. The service's default `bun_versions` reader (`listed_versions`) finds mmdc, the owner resolves to bun, and the test tries to reach `registry.npmjs.org`. With `BUN_INSTALL` unset or pointing at an empty path it passes.

Failure scenario: a developer who installed mmdc or pi through this feature (so a real bun-owned manifest exists) gets a red, host-dependent suite. A test that creates files under `bun_dirs()` would write into the real `~/.bun`. `resolve_bun()` also falls back to `bun_dirs()[0]/bun`, so "bun absent" tests can silently find the real binary.
**Fix:**
```python
# tests/sandbox.py
CLEARED_ENV_NAMES = frozenset({
    ...,
    "BUN_INSTALL",
    "BUN_INSTALL_BIN",
    "BUN_INSTALL_GLOBAL_DIR",
})
```
Add the same three names to `HOME_OVERRIDE_NAMES` so the home fingerprint guard also watches the real bun tree. Add a test that `bun_dirs()` stays under the scratch HOME inside the sandbox.

## Warnings

### WR-01: One foreign global with a non-lowercase name makes the whole bun inventory unreadable

**File:** `installer/bun_globals.py:129-137` (`read_bun_globals`)
**Issue:** The loop returns `None` for the entire manifest when any key fails `NPM_PACKAGE_RE` (lowercase only), for example the legacy `JSONStream`. Reproduced: a manifest holding `@mermaid-js/mermaid-cli` plus `JSONStream` gives `read_bun_globals() is None` and `listed_versions() is None`. Everything keyed on that inventory then fails closed:
- every bun-managed catalog tool (mmdc, puppeteer, pi) resolves to `unknown`;
- `bun update -g` is refused;
- `_package_already_there` reads "already there", so no receipt is recorded for a fresh install;
- the Doctor bun audit is skipped;
- the removal pre-check cannot tell that a package is gone.

The stated reason for `None` (a key that would steer the member path out of the tree) is fully handled by never reading that member, so it does not need to poison unrelated entries. Catalog packages are registry-validated, so an invalid foreign key can never be one of them.
**Fix:** skip the invalid key and keep going; return `None` only for an unreadable or non-object manifest or a non-object `dependencies`.
```python
for name, spec in dependencies.items():
    if not isinstance(name, str) or not isinstance(spec, str):
        return None          # a malformed manifest
    if NPM_PACKAGE_RE.fullmatch(name) is None:
        continue             # foreign name: never joined to a path, never a catalog package
    found[name] = BunGlobal(spec, _installed_version(name))
```

### WR-02: A bun-installed tool reads `unknown` on a host without pnpm when its command is not on this process's PATH

**File:** `installer/ownership.py:1239-1247` (`_unreadable`), `812-825` (by-elimination branch), `installer/ownership.py:413-414` (`pnpm_globals=None` when pnpm is absent)
**Issue:** mmdc, puppeteer and pi still declare a `node` fallback, so `competing_owners` always contains `pnpm`. When pnpm is not installed, `pnpm_global_packages()` returns `None`, so `pnpm` is in `unreadable` for every evaluation. This phase removed `pnpm` from those tools' `requires`, so a bun-only host is now the normal case, not an oddity. When the live binary resolves into bun's tree, ownership is `direct` and fine. When `which(cmd)` finds nothing, ownership falls to the by-elimination branch, which demands `not unreadable`. Reproduced with a probe: mmdc listed in bun's inventory, `pnpm_globals=None`, `which` returns None gives `owner=unknown`, reason "the pnpm inventory could not be read". That state is reachable: `status.present_bin_dir` reports mmdc present from `~/.bun/bin/mmdc` while that directory is not on this process's PATH. One case is a relaunch from a shell that has not re-sourced the managed block after the first install. A declared-`bin_dir` method would get a candidate from its declared location (`ownership.py:1101`); a bun method has none.
Failure scenario: the row shows "installed" but the owner is unknown, so `u` and the Uninstall view refuse it even though bun's manifest, tree and bin link prove it.
**Fix:** give a bun method the same declared-location evidence the `bin_dir` path has, using `method_bin_dir(method)/cmd` that resolves into `bun_dirs()[1]`, as an attributable proof when `which` finds nothing. Alternatively treat `pnpm_globals is None` as not-claiming when pnpm is not installed, which is distinct from a failed `pnpm list`.

### WR-03: A bun row can read "outdated" forever while `u` reports success and changes nothing

**File:** `installer/version_status.py:613-628` (bun branch of `resolve_status`), `installer/update.py:418-429`
**Issue:** `latest` is the npm registry's `latest` tag (`resolve_npm_latest`). The update is `bun update -g <pkg>`, which stays inside the manifest range (D-13: `^25` becomes `^25.17.0`, never `^26`). `pinned_spec` only decorates the row. Once upstream publishes a version outside the installed range (puppeteer 26 against the registry pin `^25`, or the next mmdc major), the row stays `outdated=True`. Each `u` runs `bun update -g`, passes the smoke check, refreshes the receipt and returns `status="updated"`, and the row is outdated again on the next pass. Nothing compares the version before and after.
**Fix:** compare against the newest version that satisfies the manifest range (or keep the bun branch's `outdated` as None with a "newer major available" note), or have `_perform` compare the installed version before and after and return a "kept by range" outcome instead of "updated". The first option needs the range, which `read_bun_globals()` already supplies.
