# Phase 24.5: JavaScript install priority brew then bun then volta — Specification

**Created:** 2026-11-14
**Ambiguity score:** 0.13 (gate: ≤ 0.20)
**Requirements:** 7 locked
**Amended:** 2026-11-14 (24.5 discuss D-02/D-05/D-10/D-21: PRIO-02 acceptance, PRIO-06 trust command, one edge row; edge table re-checked)

## Goal

The install ladder tries Homebrew (formula or cask) first, then bun, then pnpm on the volta-provided Node runtime, then today's order. The npm-package CLIs (mmdc, puppeteer, pi) install through bun. Every bun-installed tool gets ownership, receipts, version status, update and removal through the existing manager patterns. Copies already installed by another manager stay as they are.

## Background

Scouted and checked live on 2026-11-14. The container runs used a disposable `fedora:44` with the host's bun 1.3.14 mounted read-only and were removed afterwards. Host calls were read-only.

- **Owner input (2026-11-14):** "Algo en cuanto a la prioridad de installers, creo ahora prefiero el order sea brew -> bun -> volta y despues lo demas, entiendo que bun es mas rapido como runtime e instalador de node y de dependencias ademas de mas seguro." ("About installer priority: I now prefer the order brew, then bun, then volta, then the rest. I understand bun is faster as a runtime and as an installer of Node and dependencies, and also safer.")
- **The ladder today** (`installer/resolve.py` `_RANK`, lower first):
  - script 10, host_setup 15;
  - github_release / node / uv-tool / sdkman / tarball / app 20;
  - cargo_distrobox 25;
  - dnf / apt / pacman 30, rpm_ostree 35;
  - brew / cask 40.
  - README §"How installs are decided" and the v1.0 PRD ladder ("`.sh` oficial → tar.gz → nativo → brew") call Homebrew the last resort.
  - `brew` applies only when `platform.has_brew`; `cask` only on macOS with brew. So on a host without Homebrew no brew method applies at all.
  - 66 catalog tools declare a brew or cask method next to another method.
- **JavaScript methods today:**
  - `kind = "node"` runs `pnpm add -g` through `real_pnpm()` (`executors._node`). Owner `pnpm`, removal `pnpm remove --global`.
  - Only `mmdc` and `puppeteer` declare it. mmdc's registry comment rejects brew (upstream "no longer supported", mermaid-cli #1122) and rejects volta, which runs `npm install --global` with dependency scripts unrestricted.
  - `pi` is a `host_setup` handoff: `pnpm add -g --ignore-scripts @earendil-works/pi-coding-agent`, probe `pnpm list --global`, owner `pnpm`.
  - `bun` and `volta` are catalog tools (script plus brew), not method kinds.
  - Volta stays recognised for detection, its update hint and its removal command (`ownership._volta_owner`, `update.py` "managed by Volta").
  - The registry notes volta upstream is unmaintained (2026-10-13).
- **bun global installs (live, container):**
  - `bun add -g @mermaid-js/mermaid-cli 'puppeteer@^25'` wrote `~/.bun/install/global/package.json` (`"puppeteer": "^25"`) and a text `bun.lock`.
  - It linked `~/.bun/bin/mmdc` and `~/.bun/bin/puppeteer` as symlinks into `~/.bun/install/global/node_modules/.../cli.js`.
  - Puppeteer's postinstall ran with no `--trust`: Chrome and chrome-headless-shell landed in `~/.cache/puppeteer`. It ran even with no system node; bun ran the script.
  - Both bin targets start with `#!/usr/bin/env node`. Without node on PATH, `mmdc --version` fails with "env: 'node': No such file or directory". With node 22.23.1 it prints 12.2.0. **bun-installed CLIs run under node, not under bun.**
  - mmdc installed alone also installed puppeteer as an auto-installed peer in the shared global tree, and `require.resolve('puppeteer')` from mmdc found it. Unlike pnpm v11, bun has no per-invocation install groups.
  - `bun update -g puppeteer` rewrote the range `^25` to `^25.17.0`, so the major pin holds.
  - `bun remove -g puppeteer` while mmdc needed it as a peer dropped the manifest entry but kept the package and its `~/.bun/bin/puppeteer` link. `bun remove -g @mermaid-js/mermaid-cli` removed mmdc's link.
  - `bun outdated -g` printed only its banner, with no rows, for an outdated global, so it cannot feed version status.
  - `bun pm ls -g` prints a text tree; `bun list -g --json` prints the same tree, not JSON.
  - `bun info <pkg> version` works only from a directory with a `package.json`.
  - `bun pm bin -g` on the host prints `~/.bun/bin` (`BUN_INSTALL=~/.bun`).
- **bun lifecycle scripts (bun.com/docs/install/lifecycle, fetched 2026-11-14):**
  - "Bun does not execute arbitrary lifecycle scripts by default". Only packages on a curated default allowlist, or named in `trustedDependencies`, run them.
  - Setting `trustedDependencies` replaces the default list instead of extending it.
  - The default list (`src/install/default-trusted-dependencies.txt`, 367 names) includes `puppeteer` and `@anthropic-ai/claude-code`.
  - pnpm v10+ also blocks dependency scripts by default (the existing `--allow-build=puppeteer` grant). So bun is safer than volta/npm, and comparable to pnpm, not stricter.
- **The owner's host (read-only):**
  - `pi` is already bun-installed: `~/.bun/bin/pi` → the global tree, manifest pin `"1.5.2"`.
  - `mmdc` resolves to `~/.volta/bin/mmdc` (volta-owned), and Homebrew also has `mermaid-cli` installed.
  - `node` is volta's shim, and Linuxbrew is at `/home/linuxbrew/.linuxbrew/bin/brew`.
- **Homebrew formulae (host, `brew info`, read-only):** `bun` 1.4.4, `volta` 2.0.2, `pnpm` 12.18.0, `mermaid-cli` 12.2.0 (depends on node only), `opencode` 2.3.0. There is no `codex` formula.
- **npm latest (bun info, container):** puppeteer 25.17.0, `@earendil-works/pi-coding-agent` 1.5.2, `@openai/codex` 0.169.0, `@anthropic-ai/claude-code` 2.1.325, `@opencode/cli` 2.3.0, `@github/copilot` 1.0.112.
- **Coupling from 24.4 (CONTEXT D-01..D-03):** `real_pnpm` survives in `installer/legacy_guard.py` and skips sentinel-marked leftovers. `executors` exports no PATH. bun was never a guarded name, so resolving bun needs no sentinel skip. The pnpm fallback keeps `real_pnpm`.

## Requirements

1. **Ladder order (PRIO-01)**: Install-method resolution tries Homebrew first, then bun, then pnpm, then today's order.
   - Current: `_RANK` tries script first and brew/cask last; `node` ranks with downloads at 20.
   - Target:
     - `brew` and `cask` rank first;
     - the new `bun` kind ranks second;
     - `node` (pnpm on the volta-provided Node runtime) ranks third;
     - every other kind keeps its current relative order after them.
     - Applicability rules do not change: brew needs `has_brew`, cask needs macOS with brew, and native kinds stay skipped on immutable hosts. On a host without Homebrew, every tool's resolved order equals today's, apart from tools that gain a bun method.
   - Acceptance: a resolver test pins the first method of every catalog tool on four fixture platforms: macOS with brew; mutable Fedora with Linuxbrew; immutable Fedora with Linuxbrew; Debian without brew. On macOS with brew, `rg` resolves `brew` first. On Debian without brew, `rg` resolves `github_release` first. With `has_brew` false, the full method order of every tool without a bun method equals the order before this phase.

2. **bun install method (PRIO-02)**: A `bun` method kind installs an npm package globally with bun.
   - Current: no method kind runs bun.
   - Target:
     - The executor runs `bun add -g <pkg>[@<range>]` with the bun it resolves, on PATH or under bun's global bin dir, by absolute path.
     - It checks the method's declared `min_node` against the node on PATH before installing, because the installed bins run under node.
     - It runs the method's declared smoke check after the install.
     - bun's global bin dir (`~/.bun/bin`, or `$BUN_INSTALL/bin`) is wired into PATH by the same mechanism that wires a method's declared `bin_dir`, whether bun itself came from its script or from brew.
     - A missing bun or a node below the floor fails that method with one line naming the fix, and the ladder falls through to the next method.
   - Acceptance: in a disposable container with bun and node 22 or newer, a catalog install of mmdc leaves `~/.bun/install/global/package.json` naming `@mermaid-js/mermaid-cli` and `puppeteer` with range `^25`. `mmdc --version` exits 0 from a fresh login shell, and the puppeteer-browser smoke check passes. With bun absent, the same install falls through to the pnpm method. With node below 22.12.0, the bun method fails with the floor message.
   - *Amended 2026-11-14 (24.5 D-02, D-10):* a catalog run always installs bun first (`requires`), so the bun-absent fallback is checked with a single-tool `install_tool` call (a unit test and a direct call in a container). When the node version is known and below the floor, the bun method is gated at plan time like the `node` method: the row plans BLOCKED with "needs Node >= 22.12.0". The executor's floor message covers an unknown node version.

3. **Which tools move to bun (PRIO-03)**: The npm-package CLIs install through bun first; the vendor-installed agent CLIs do not change.
   - Current: mmdc and puppeteer install with pnpm, pi's handoff names pnpm, and `requires` names pnpm for all three.
   - Target:
     - mmdc, puppeteer and pi each declare a bun method that is their first JavaScript method.
     - mmdc and puppeteer keep their `node` methods as the fallback.
     - Their `requires` names bun in place of pnpm.
     - A fresh pi install through the installer leaves pi bun-owned.
     - mmdc still declares no brew method.
     - codex, claude, opencode, copilot, cursor-agent and antigravity keep their current methods.
   - Acceptance: registry tests assert the bun method on the three tools, the kept `node` fallback on mmdc and puppeteer, and no bun method on the six agent CLIs. A container install of pi reads owner `bun`.

4. **bun-owned lifecycle (PRIO-04)**: A bun-installed tool is recognised, recorded, versioned, updated and removed like the other manager kinds.
   - Current: no owner `bun` exists, so the host's bun-installed pi has no manager owner.
   - Target:
     - **Ownership:** owner `bun` is attributed from bun's global tree.
     - **Receipts:** a receipt records kind `bun` and the package.
     - **Version status:**
       - the current version comes from the installed package's own `package.json`;
       - the latest version comes from the npm registry lookup the installer already has, because `bun outdated -g` lists nothing;
       - an inventory that cannot be read gives `unknown`, never "up to date".
     - **Update:** an update keeps the declared range and runs the declared smoke check.
     - **Removal:** removal runs `bun remove --global <pkg>`. When bun keeps the package because another global needs it, the removal says so and does not report the tool removed.
     - **Doctor:** the browser audit that re-checks pnpm-owned puppeteer and mmdc also covers bun-owned ones.
   - Acceptance: scratch-HOME tests with a seeded `~/.bun/install/global` show owner `bun` and the installed version for a bun-installed pi (`1.5.2`). An outdated seeded puppeteer reads outdated against a stubbed registry answer. Uninstalling bun-owned mmdc runs `bun remove --global @mermaid-js/mermaid-cli`. Removing puppeteer while mmdc stays installed reports that bun kept it.

5. **Existing installs stay with their manager (PRIO-05)**: The new order never reinstalls or moves a tool that is already installed.
   - Current: an installed tool short-circuits to ALREADY_INSTALLED, and updates follow the owning manager.
   - Target: a tool owned by pnpm, volta, brew or a vendor installer keeps that owner after this phase. Install runs report it already installed, updates and removals use its owner, and no route removes or reinstalls it to reach the new order. The docs name the way to move a tool to bun: remove it in the Uninstall view, then install it again.
   - Acceptance: scratch-HOME fixtures for a pnpm-owned mmdc, a volta-owned mmdc and a brew-owned mmdc each read ALREADY_INSTALLED on install. The pnpm one updates through pnpm, the volta one reports "managed by Volta", and the brew one updates through brew. No `bun` command runs in any of the three.

6. **Script permissions stay narrow (PRIO-06)**: The bun method never widens which packages may run lifecycle scripts.
   - Current: pnpm installs grant `--allow-build=puppeteer`, scoped to one package.
   - Target:
     - The bun method passes no `--trust` and writes no `trustedDependencies` into bun's global manifest. Puppeteer's postinstall runs through bun's default allowlist.
     - When the user's own manifest sets `trustedDependencies` without puppeteer, the browser download does not happen. The smoke check then fails the install with one line naming the command that trusts puppeteer.
   - *Amended 2026-11-14 (24.5 D-21):* the trust command is `bun add -g --trust puppeteer@^25`. Live: it appends puppeteer to the user's explicit list. `bun pm trust puppeteer` reports "0 scripts ran" for a global, and `bun pm untrusted` in the global dir lists nothing.
   - Acceptance:
     - After a container install of mmdc, bun's global manifest has no `trustedDependencies` key and `~/.cache/puppeteer` holds a browser.
     - A test with a manifest that sets `trustedDependencies` to `["esbuild"]` shows the failed smoke check naming the trust command, and the manifest unchanged by the installer.

7. **Docs and records follow (PRIO-07)**: The live docs describe the new order and state only verified claims about bun.
   - Current: README §"How installs are decided" lists Homebrew as the last resort, `.claude/architecture.md` describes the `_RANK` order with brew at 40, and the mmdc and puppeteer registry comments explain the pnpm choice.
   - Target:
     - README and `.claude/architecture.md` describe the new order and the no-Homebrew case.
     - The registry comments on mmdc, puppeteer, pi, bun and volta record the bun facts above.
     - Any statement about bun's safety says that bun runs dependency lifecycle scripts only for its default allowlist or `trustedDependencies`, and that bun-installed CLIs run under node.
     - REQUIREMENTS.md lists PRIO-01..07.
     - Historical PRDs are not edited.
   - Acceptance: `grep -n "last resort" README.md` finds no Homebrew line. The architecture `_RANK` passage names brew first. `make validate && make test` pass.

## Boundaries

**In scope:**
- The new `_RANK` order and its fixture-platform test (PRIO-01)
- The `bun` method kind: executor, PATH wiring of bun's global bin dir, node floor, smoke checks (PRIO-02)
- bun methods for mmdc, puppeteer and pi; `requires` switched to bun; pnpm fallback kept (PRIO-03)
- Owner `bun`: ownership, receipts, version status, update, removal, Doctor browser audit (PRIO-04)
- Leaving existing installs with their manager, and documenting the manual move (PRIO-05)
- No `--trust` and no `trustedDependencies` write (PRIO-06)
- README, architecture rule doc, registry comments, REQUIREMENTS.md (PRIO-07)

**Out of scope:**
- A `volta install` method kind: volta upstream is unmaintained, `volta install` runs npm dependency scripts unrestricted, and bun-installed CLIs still need the node runtime volta already provides.
- bun methods for the vendor-installed agent CLIs (codex, claude, opencode, copilot, cursor-agent, antigravity): their vendor installers or casks own self-update, and moving them to bun changes their owner and update route for no user gain.
- Automatic migration of pnpm-, volta- or brew-owned copies to bun: a standing rule forbids silently reinstalling a user's tool.
- Running catalog CLIs under bun's runtime (`bun --bun`): the bins declare `#!/usr/bin/env node`, and rewriting vendor shebangs is not this installer's job.
- Adding brew methods to tools that do not declare one, or removing brew methods: the ladder change applies to declared methods only.
- The guard retirement: Phase 24.4.
- pi's own installer script (`pi.dev/install.sh`, which runs sudo): Backlog 999.13.

## Constraints

- Zero sudo. bun installs into the user's `~/.bun`. The installer never runs `brew` with privilege.
- No new Policies knob and no new setting: the order is install tuning applied with no question.
- Tests use a scratch HOME. Real installs run only in disposable containers, which are removed afterwards.
- Every child process goes through the existing runner and `run_query` helpers. bun runs by absolute path once resolved.
- The ladder's existing rules hold: a checksum mismatch still halts it, and a native manager's handoff still ends it.
