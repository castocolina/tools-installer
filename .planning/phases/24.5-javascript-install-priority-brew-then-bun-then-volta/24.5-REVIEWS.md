### Lane A (`laneA-my-referee-one`)

#### 24.5-01

##### Summary

This plan introduces the bun method, validates its package declarations, runs it through the existing install ladder, and wires bun’s bin directory into the installer’s presence, smoke, shell and version checks.

##### Strengths

- **The bun argv has a narrow trust boundary.** The plan calls for a list-valued runner invocation, validates package names, and excludes `--trust` and manifest writes (`.planning/phases/24.5-javascript-install-priority-brew-then-bun-then-volta/24.5-01-PLAN.md:143-151,185-195`). That builds on the existing model’s closed method-parameter validation (`installer/model.py:640-644`).
- **The resolver integration covers both applicability and its explanation.** The proposed `_applies` and `_rejection` changes address the existing Node-floor gate and its mirrored reason (`.planning/phases/24.5-javascript-install-priority-brew-then-bun-then-volta/24.5-01-PLAN.md:149,186-197`; `installer/resolve.py:39-45,73-76,109-127`).

##### Concerns

- **HIGH — Environment-derived paths reach shell code without escaping.** The plan passes `BUN_INSTALL_BIN` or `BUN_INSTALL` through `bun_dirs()` into `collect_bin_dirs` (`.planning/phases/24.5-javascript-install-priority-brew-then-bun-then-volta/24.5-01-PLAN.md:143,233-236`). `path_export_guard` interpolates directory strings into double-quoted shell code without escaping and explicitly warns against user-supplied paths (`installer/shellrc.py:100-102,122-137`). A legitimate directory containing `$`, backticks or quotes can be expanded or interpreted when the shell sources the generated file.
- **HIGH — PATH lookup does not guarantee an absolute bun path.** The plan returns `shutil.which("bun")` directly while requiring an absolute executable (`.planning/phases/24.5-javascript-install-priority-brew-then-bun-then-volta/24.5-01-PLAN.md:36,144`). If PATH contains a relative entry, `which` can return a relative path; the fallback is also relative if a BUN directory variable is relative. That violates D-06’s absolute-path contract (`.planning/phases/24.5-javascript-install-priority-brew-then-bun-then-volta/24.5-CONTEXT.md:64-68`).
- **MEDIUM — Shell wiring ignores `collect_bin_dirs`’ injected home.** The plan calls the zero-argument `bun_dirs()` from `collect_bin_dirs` (`.planning/phases/24.5-javascript-install-priority-brew-then-bun-then-volta/24.5-01-PLAN.md:235`). The existing function explicitly resolves paths against its `home` argument (`installer/shellrc.py:51-58,67-77`). A caller supplying a different home without also changing the process environment gets the wrong bun directory.
- **MEDIUM — The first commit lacks the promised load-time name guard.** Task 1 makes `bun` loadable and executable, but postpones regex validation until Task 2 (`.planning/phases/24.5-javascript-install-priority-brew-then-bun-then-volta/24.5-01-PLAN.md:147-155,192-201`). The shared node loader only excludes empty or comma-bearing names (`installer/model.py:680-694`; `installer/model.py:249-268`), so that intermediate commit accepts option-shaped bun package names.

##### Suggestions

- Escape both the case pattern and exported value as literal shell data, and test sourcing a generated block with spaces, quotes and command-substitution characters in the bun directory.
- Normalize the resolved executable to an absolute path and test relative PATH and BUN directory values.
- Preserve the injected-home contract and land bun name validation with the initial executable method.

##### Risk Assessment

**HIGH.** The proposed shell wiring crosses an explicitly documented escaping boundary and can generate executable shell syntax from a directory value.

#### 24.5-02

##### Summary

This plan makes the browser smoke check manager-aware, stops the ladder after a bun post-install smoke failure, gives guidance for an explicit bun trust list, and records a note when bun installs a peer also present through another manager.

##### Strengths

- **The seam change is scoped to one commit.** The plan identifies the production dispatch and the test replacements that must change together (`.planning/phases/24.5-javascript-install-priority-brew-then-bun-then-volta/24.5-02-PLAN.md:93-105,126-132`); the current zero-argument seam and dispatch are visible at `installer/executors.py:328-348,372-405`.
- **It identifies a real post-install fall-through hazard.** Today executor errors are collected and the next method is tried (`installer/engine.py:288-289,315-322`); the existing pnpm executor can then issue an `--allow-build` allowance (`installer/executors.py:495-514`).

##### Concerns

- **HIGH — The terminal-smoke decision conflicts with locked D-06.** The plan makes post-install bun smoke failures stop the ladder (`.planning/phases/24.5-javascript-install-priority-brew-then-bun-then-volta/24.5-02-PLAN.md:165-169,258-260`), while D-06 explicitly says every failure raises `ExecutorError` **so the ladder falls through to node** (`.planning/phases/24.5-javascript-install-priority-brew-then-bun-then-volta/24.5-CONTEXT.md:64-72`). The safety rationale is substantive, but an orchestrator decision recorded in the plan does not reconcile the locked decision.
- **HIGH — A failed bun command can still fall through after changing state.** The new terminal exception wraps only the declared smoke after the runner returns successfully (`.planning/phases/24.5-javascript-install-priority-brew-then-bun-then-volta/24.5-02-PLAN.md:165-169`). The runner raises `CommandError` for a non-zero command (`installer/run.py:18-19,82-89`), and the engine catches it and tries the next method (`installer/engine.py:321-322`). A bun process that partially changed its global tree before failing can therefore still trigger pnpm and its build allowance. The plan does not establish that a non-zero bun exit leaves no installed state.
- **MEDIUM — Root ordering does not ensure the owning tree supplies the smoke.** The plan tries other managers’ roots after the preferred root and omits the bun root when its puppeteer directory is absent (`.planning/phases/24.5-javascript-install-priority-brew-then-bun-then-volta/24.5-02-PLAN.md:119-128`). The existing Node probe tries each root until resolution succeeds, then falls back to ordinary resolution (`installer/executors.py:210-223`). Thus a missing bun-owned puppeteer can be masked by a working pnpm or PATH copy, despite the plan’s claim that the check verifies the tree just installed.
- **MEDIUM — A trust list alone does not establish the stated failure cause.** The proposed error asserts that bun skipped the postinstall whenever a list lacks puppeteer and the browser smoke fails (`.planning/phases/24.5-javascript-install-priority-brew-then-bun-then-volta/24.5-02-PLAN.md:158-168`). The existing smoke can fail for missing shared libraries or browser launch problems (`installer/executors.py:351-378`). The manifest is evidence that trust is restricted, not proof that restriction caused this particular failure.

##### Suggestions

- Resolve the D-06 conflict with the owner and amend the locked decision before execution.
- Define and test a conservative policy for a bun runner failure after possible partial mutation; do not assume a non-zero exit is pre-install.
- For an owner-specific check, fail when that manager’s package cannot be resolved rather than silently accepting another manager’s copy.
- Phrase the trust guidance conditionally unless there is evidence that the postinstall was blocked.

##### Risk Assessment

**HIGH.** The plan changes a locked ladder decision and leaves a post-mutation fall-through route that its safety design intends to prevent.

#### 24.5-03

##### Summary

This plan adds file-based bun inventory, bun ownership and removal vocabulary, receipt attribution, and a live inventory read during version refresh.

##### Strengths

- **The live refresh avoids stale persisted bun inventory.** The proposed per-pass read and no-backfill rule (`.planning/phases/24.5-javascript-install-priority-brew-then-bun-then-volta/24.5-03-PLAN.md:171-176`) address the current snapshot reuse and merge paths (`installer/version_status.py:148-162,1633-1649,1768-1780`).
- **The pnpm coexistence test follows the actual ownership decision path.** A directly attributable candidate wins before the unknown/by-elimination branches (`installer/ownership.py:669-710,774-803`), supporting the plan’s pnpm-proven/unreadable-bun case (`.planning/phases/24.5-javascript-install-priority-brew-then-bun-then-volta/24.5-03-PLAN.md:165-167`).

##### Concerns

- **HIGH — A listed package with an unreadable or missing member version is treated as absent for receipt attribution.** The reader retains a manifest entry with `version=None`, but `installed_versions()` drops it (`.planning/phases/24.5-javascript-install-priority-brew-then-bun-then-volta/24.5-03-PLAN.md:125-128,132-135`). `_package_already_there` treats a readable inventory *without* the package as proof of absence and permits a new receipt (`installer/engine.py:332-343,374-387`). A pre-existing listed package with missing, corrupt or unrecognized member metadata can therefore be claimed by a subsequent install, contrary to the plan’s “already listed … is not claimed” rule.
- **HIGH — Invalid UTF-8 is not covered by the fail-closed reader contract.** The plan says the manifest is read as UTF-8 and maps `OSError`, invalid JSON and invalid structure to `None` (`.planning/phases/24.5-javascript-install-priority-brew-then-bun-then-volta/24.5-03-PLAN.md:130-132`). Invalid UTF-8 raises `UnicodeDecodeError`, not an `OSError` or JSON parse error. Since `read_inventory` and refresh consume the reader (`.planning/phases/24.5-javascript-install-priority-brew-then-bun-then-volta/24.5-03-PLAN.md:133,175-176`; `installer/version_status.py:1651-1663,1776-1779`), such a manifest can abort those paths instead of yielding unknown.
- **MEDIUM — The live refresh bypasses the injected inventory seam.** Task 2 calls `installed_versions()` directly on every pass (`.planning/phases/24.5-javascript-install-priority-brew-then-bun-then-volta/24.5-03-PLAN.md:171-176`), whereas fresh mutation-time owner resolution uses `self._read_inventory` (`installer/version_status.py:1589-1607`). This makes refresh and fresh owner resolution depend on different sources when callers inject inventory, and tests must explicitly isolate both.

##### Suggestions

- Preserve separate evidence for manifest membership and readable installed version, or fail the relevant inventory closed when a listed member cannot be verified. Test receipt attribution with a listed package whose member metadata is missing.
- Treat decoding errors as unreadable data and test invalid UTF-8 in both manifest and member metadata.
- Keep live per-pass reads injectable, and test that refresh and mutation-time resolution use consistent bun evidence.

##### Risk Assessment

**HIGH.** The proposed inventory projection can turn incomplete evidence into proof of absence and write a receipt for a pre-existing package.

##### Risk Assessment

**HIGH** — The proposed unit-level budget test can pass while the production refresh pass exceeds its fetch limit.

#### 24.5-09

##### Summary

This plan extends the disposable-container harness with a bun lifecycle driver, host-side verdict tests, and one real container run covering installation, ownership, removal, fallback, the Node floor, and lifecycle-script trust.

##### Strengths

- The existing container guard requires an engine marker, the harness marker, and the tester HOME (`tests/e2e_landing_driver.py:810-825`); reusing it gives the new driver a meaningful barrier against running against a real home.
- The plan calls for separate assertions of browser availability, login-shell execution, manifest contents, ownership, and trust behavior (`.planning/phases/24.5-javascript-install-priority-brew-then-bun-then-volta/24.5-09-PLAN.md:102-107,138-150`), rather than treating `bun add` success alone as end-to-end proof.
- The proposed uniquely named container and pulled-image ownership check build on the existing scoped teardown (`scripts/container-e2e-verify.sh:2714-2733`).

##### Concerns

- **HIGH — The new command does not wire the unique name into the variable that actually controls container operations.** The proposed implementation assigns `LANDING_CONTAINER_NAME` but does not assign `CONTAINER_NAME`, `IMAGE`, and `DISTRO` as the existing command does (`.planning/phases/24.5-javascript-install-priority-brew-then-bun-then-volta/24.5-09-PLAN.md:113`; `scripts/container-e2e-verify.sh:2799-2817`). `start_container`, `exec_root`, and `exec_tester` use `CONTAINER_NAME`, not `LANDING_CONTAINER_NAME` (`scripts/container-e2e-verify.sh:158-165,180-196`). The default is the shared `tools-installer-e2e-fedora` name (`scripts/container-e2e-verify.sh:131-148`), and bootstrap invokes `start_container replace` (`scripts/container-e2e-verify.sh:2758-2767`). Thus the plan can replace an existing shared container, then teardown checks/removes a different name and leaves the actual container behind. A supplied `--distro` can also select a non-Fedora image.
- **HIGH — The required teardown verdict cannot appear in the transcript using the planned reuse.** `landing_step` appends driver output to `LANDING_TRANSCRIPT`, but `landing_teardown` prints directly to stdout and never appends to that file (`scripts/container-e2e-verify.sh:2722-2733,2783-2796`). Plan 09 nevertheless requires `TRACER_LANDING_TEARDOWN_OK` in `bun-transcript.log` (`.planning/phases/24.5-javascript-install-priority-brew-then-bun-then-volta/24.5-09-PLAN.md:175-189`). The proposed task does not change teardown’s logging, so a successful run still fails its phase gate.
- **HIGH — The fallback verdict can pass without pnpm running, and cannot observe the bun refusal on a successful fallback.** The plan accepts a final pnpm error as proof of fallback (`.planning/phases/24.5-javascript-install-priority-brew-then-bun-then-volta/24.5-09-PLAN.md:139,148`). That can mean pnpm was not installed at all; the plan-06 dependency change explicitly removes pnpm from mmdc’s requirements (`.planning/phases/24.5-javascript-install-priority-brew-then-bun-then-volta/24.5-06-PLAN.md:128-131`). Conversely, the existing successful `InstallOutcome` does not include accumulated earlier errors (`installer/engine.py:320-323,360-371`), so checking its “first error” cannot establish bun’s refusal when pnpm succeeds. The real-container acceptance requires an actual fallback, not merely reaching a pnpm-not-found error.
- **HIGH — The ordered verbs are not isolated from mutations made by earlier verbs.** The fallback step may successfully install mmdc through pnpm, after which the floor and trust steps call `install_tool` on the same tool (`.planning/phases/24.5-javascript-install-priority-brew-then-bun-then-volta/24.5-09-PLAN.md:140,148-150`). `install_tool` returns `ALREADY_INSTALLED` before resolving any method when the command is present (`installer/engine.py:218-228`), so neither later step necessarily reaches the bun floor or trust check. Reducing PATH for fallback also does not by itself remove a manager’s installed copy or its declared bin directory from presence detection (`installer/status.py:93-109,122-141`).
- **MEDIUM — The promised Homebrew-bun adjacency is not asserted.** The plan checks the resulting manifest, browser, and shell, but does not require the bun dependency’s `method_kind` or provenance to be `brew` (`.planning/phases/24.5-javascript-install-priority-brew-then-bun-then-volta/24.5-09-PLAN.md:24,105,112`). The registry also has a script fallback (`installer/registry.toml:2197-2221`), so a successful script install could satisfy the proposed verdicts while failing to prove the claimed Homebrew case.
- **MEDIUM — The host test plan must update a private-name lookup, not just direct callers.** Renaming `_in_container` is requested at `.planning/phases/24.5-javascript-install-priority-brew-then-bun-then-volta/24.5-09-PLAN.md:110-111`; an existing test accesses it dynamically through `vars(driver)["_in_container"]` at `tests/test_container_e2e_landing.py:553-565`. A conventional direct-reference search can miss this and leave the intermediate commit red.

##### Suggestions

- Set and verify `CONTAINER_NAME="$LANDING_CONTAINER_NAME"`, `IMAGE="$LANDING_IMAGE"`, and `DISTRO=fedora` before bootstrap; test that every `ct run`, `exec`, and `rm` targets the same unique name, including when `--distro` is supplied. Refuse an existing unique name rather than replacing it.
- Append teardown’s verdict to the transcript and test the actual EXIT-trap path, including teardown failure and early bootstrap failure.
- Provision pnpm inside the disposable container for the fallback test, record both the bun refusal and a real pnpm invocation, and require the resulting method to be `node`.
- Reset or isolate filesystem, PATH, cache, receipts, and package-manager state before each negative scenario; assert the intended preconditions immediately before invoking the engine.
- Record and assert that the catalog bun dependency was installed with method `brew`. Update dynamic private-name references when making helpers public.

##### Risk Assessment

**HIGH.** As written, the harness can replace a shared container and clean up the wrong one; several acceptance checks also cannot prove the behavior they claim.
