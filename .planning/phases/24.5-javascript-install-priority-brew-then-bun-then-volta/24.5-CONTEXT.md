# Phase 24.5: JavaScript install priority brew then bun then volta - Context

**Gathered:** 2026-11-14 (assumptions mode, after 24.5-SPEC.md)
**Status:** Ready for planning

<domain>
## Phase Boundary

The install ladder tries Homebrew (formula or cask) first, then bun, then pnpm on the volta-provided Node runtime, then today's order. mmdc, puppeteer and pi install through a new `bun` method kind. Bun-installed tools get an owner, receipts, version status, update and removal through the existing manager patterns. Copies another manager already installed stay with that manager. Volta stays the Node runtime: no `volta install` method is added.
</domain>

### The `bun` method kind
- **D-05: `bun` joins `METHOD_KINDS` and shares `node`'s params: `npm_pkg`, `co_install`, `versions`, `min_node`, `smoke`, `smoke_argv`.**
  - `allow_build` is a load error on bun (PRIO-06). `KIND_PACKAGE_PARAM["bun"] = "npm_pkg"`.
  - The bun branch reuses `node`'s load rules (`model.py:680-737`) and adds an `NPM_PACKAGE_RE` fullmatch on `npm_pkg` and every `co_install` entry.
  - Today only script `latest_npm` is regex-checked (`model.py:787-794`), so a value starting with `-` would otherwise reach bun's option parser. The SPEC edge row is amended.
  - The `co_install` load rule now reads "names a package in this same invocation". Analyzer, Confident.
- **D-06: `executors._bun` mirrors `_node` (`executors.py:473-524`):**
  - validate the shape;
  - resolve bun to an absolute path (PATH first, then D-07's bin dir);
  - check `min_node` with bare `node --version`;
  - `runner([bun, "add", "-g", *specs])`, one argv element per `name[@range]`;
  - run the declared smoke.
  - Every failure raises `ExecutorError`, so the ladder falls through to `node` (`engine.py:320-321`).
  - bun was never a guarded name, so it gets no sentinel skip (24.4 D-01/D-03 coupling); the pnpm fallback keeps `real_pnpm`.
  - Registered in `EXECUTORS`. Analyzer, Confident.
- **D-07: One helper computes bun's two directories:**
  - the bin dir: `BUN_INSTALL_BIN`, else `$BUN_INSTALL/bin`, else `~/.bun/bin`;
  - the global tree: `BUN_INSTALL_GLOBAL_DIR`, else `$BUN_INSTALL/install/global`, else `~/.bun/install/global`.
  - Every reader uses this helper: the executor's bun lookup, the engine's PATH prepend and smoke target (`engine.py:53-64,296-298`), `status.present_bin_dir` (`status.py:91-108`), `collect_bin_dirs` for bun methods, ownership dirs, the smoke's module roots and `version_argv`.
  - Live (container): `BUN_INSTALL_BIN=/tmp/xbin BUN_INSTALL_GLOBAL_DIR=/tmp/xglobal bun add -g semver` linked the bin into `/tmp/xbin` and put the tree in `/tmp/xglobal`, and `bun pm bin -g` reported `/tmp/xbin`.
  - `bun pm bin -g` errors on a fresh host before the first global install, so it is not the source.
  - bunfig's `install.globalDir`/`globalBinDir` are not read: `shortcut:` comment, upgrade when a user relocates through bunfig.
  - choice 0.96 (computed_from_env).
- **D-08: The puppeteer-browser smoke resolves puppeteer from the owning manager's tree first.**
  - `_puppeteer_module_roots` (`executors.py:297-325`) gains the bun global tree. When the check runs for a bun-owned entry, it puts that root first; for a pnpm-owned entry, pnpm's root goes first.
  - This is a small signature change; `SMOKE_CHECKS` callables take no arguments today (`:392-394`).
  - **Own reasoning** (jev owning_manager_first low 0.77; Laya low 0.67): a host can hold both copies, and PATH order would audit the wrong one. Ledger.
- **D-09: `engine._listing` (`engine.py:389-396`) gets an explicit bun branch.** Without it, a bun kind falls into the pnpm inventory default.
  - `_manager_method` already covers bun, so the generic `<cmd> --version` smoke runs.
  - `receipts.record` stores kind `bun` and its package through `method_package`. Analyzer, Confident.
- **D-10: The bun-absent fallback is verified with a single-tool `install_tool` call: a unit test plus a direct call in a container.** A catalog run installs bun first through `requires` (`deps.py:45-61`). SPEC PRIO-02 acceptance amended. **Own reasoning** (jev direct_single_tool_install low 0.71; Laya low 0.42). Ledger.

### Ownership and lifecycle
- **D-11: Owner `bun` follows the uv pattern.**
  - Add `"bun"` to the `Owner` Literal, `_KIND_TO_OWNER` and `_CANDIDATE_ORDER` (`ownership.py:80-94,149-157`).
  - Add `ManagerInventory.bun_globals: Mapping[str, str] | None` (name → installed version). It is read from files, not bun's CLI:
    - the keys come from the global tree's `package.json` `dependencies`;
    - each version comes from `node_modules/<name>/package.json`;
    - a missing tree gives `{}`; an unreadable or invalid manifest gives `None`, which `_unreadable` turns into `unknown`.
  - `owner_dirs` names the global tree, never `~/.bun`, so bun's own binary is never read as bun-owned.
  - `read_inventory`, `manager_listing`, `_collect_candidates` and the refresh retry gate get bun entries.
  - Live: the host's manifest is `{"dependencies":{"@earendil-works/pi-coding-agent":"1.5.2"}}`, and `~/.bun/bin/pi` resolves into the tree. `bun list -g --json` prints text. An auto-installed peer is not in the manifest, so scanning `node_modules` would over-claim.
  - **Own reasoning** (jev scan_node_modules_tree low 0.62; Laya parse_cli_text_tree low 0.51): both answers contradict the live facts. Ledger.
- **D-12: Version status gets a bun branch in `resolve_status` (`version_status.py:498-649`).**
  - `installed` comes from the package.json read.
  - `latest` comes from `resolve_npm_latest` (`versions.py:422`) through the cache, backoff and fetch budget `_latest_status` already uses (`:333-401`).
  - An unreadable inventory gives `outdated=None, stale=True`. `_pinned_spec` shows the range.
  - It never takes the brew/pnpm mapping branch, where "absent from the outdated map" means up to date (`:596-608`). `bun outdated -g` lists nothing, so that branch would read every bun tool as current forever. Analyzer, Confident.
- **D-13: An update of a bun-owned tool runs `bun update -g <pkg>` by absolute path, then the declared smoke check, then the existing receipt refresh.**
  - Live (container): re-running `bun add -g semver@^7` over an installed 7.5.0 kept 7.5.0, and so did `--force`. `bun update -g semver` moved it to 7.8.6 and rewrote the range to `^7.8.6`, keeping the major (puppeteer: `^25` → `^25.17.0`).
  - So the pnpm pattern of re-running the install executor does not work for bun. This departs from `update.py`'s reuse note (`:14-38`); its docstring records why.
  - An exact pin the user set in bun's manifest (the host's pi reads `"1.5.2"`) is left alone: no `--latest`. The row reports the pin.
  - choice 0.95 (bun_update_then_smoke).
- **D-14: Removal adds `"bun": ("bun", "remove", "--global")` to `MANAGER_UNINSTALL_ARGV` (`uninstall.py:111-116`).** That one entry also feeds the removal hint and label (`ownership.py:1540-1546,1700-1706`). `perform` resolves `bun` to an absolute path the way it does for pnpm (`app.py:895-902`).
  - After the command, if `node_modules/<pkg>` or the tool's bin link still exists, the result is not-removed with "bun kept <pkg> because another global package needs it", and the receipt stays.
  - The ALREADY_REMOVED shortcut (`app.py:888-894`) checks the tree as well as the manifest.
  - `removal_order` already removes mmdc before puppeteer. Group retirement and the pnpm group warnings stay pnpm-only (`app.py:559-599`).
  - Live: the kept-peer behaviour (SPEC Background), and after `bun remove -g @mermaid-js/mermaid-cli` an auto-installed puppeteer stayed in the tree.
  - choice 0.97 (check_files_too).
- **D-15: One Doctor audit covers pnpm and bun.** `node_globals`/`_node_method` (`pnpm_globals.py:193-221`) collect `node` and `bun` methods. `audit_node_globals` (`:624-664`) takes a bun listing and re-runs `_unhealthy` for both managers. The split and incomplete group checks stay pnpm-only.
  - `session.pnpm_group_install` (`session.py:399-410`) and `catalog_audit._method_pins` (`:614-621`) take bun beside node.
  - `_volta_owner` (`ownership.py:858`) takes its package from the first bun or node method, so a volta-owned pi still gets `volta install @earendil-works/pi-coding-agent`.
  - choice 0.88 (extend_one_audit).
