<objective>
Build the one reusable self-deduping PATH emitter this phase exists for, wire it through
`managed_block()` (and therefore through both `write_myshellrc` and `write_managed_path`), and
prove the RUNTIME property that was never proven before: sourcing the block N times in a real
shell adds each directory at most once.

Purpose: D-03 — replace the plain unconditional `export PATH="{dir}:$PATH"` emission with the
case-guarded self-deduping idiom pnpm's own installer uses and `installer/rcclean.py:61-70`
already documents as safe to leave alone. D-02 — one reusable mechanism, called from every
site, not a one-off patch. D-01 — the existing `apply_block` replacement mechanism then
migrates every already-broken installation for free the next time `apply`/`fix` runs.

Output: `path_export_guard()` in `installer/shellrc.py`, a rewired `managed_block()`, and a
test file that proves file-content idempotency (already true) AND runtime-effect idempotency
(the actual bug) against real shells.

**The emitted per-directory line is exactly:**
`case ":${PATH-}:" in *":{directory}:"*) ;; *) export PATH="{directory}${PATH:+:$PATH}";; esac`

Three properties of that one line are load-bearing, not cosmetic. Copy it verbatim.

1. **It starts with `case`, so this project's own cleanup path cannot strip it.**
   15.8-RESEARCH.md verified live, by calling the real production function, that
   `installer/rcclean.py::find_duplicate_path_lines` cannot flag it: `installer/rcclean.py:16`'s
   `_PATH_EXPORT` regex requires the line to START (after optional whitespace) with `PATH=` or
   `export PATH=`, and this line starts with `case`. **Re-verified this planning session against
   the exact shape above** (including the two parameter expansions added below): the scanner
   returns no findings for the line alone and for the same line indented, and still returns
   exactly one finding for a plain unguarded export of the same directory placed beneath it. A
   future variant that collapses the guard into a single leading assignment WOULD be flagged.
   Plan 15.8-02 pins this with a direct test.

2. **The value is `{directory}${PATH:+:$PATH}`, never a bare colon join.** A trailing empty PATH
   component is not cosmetic: every POSIX shell reads an empty component as "the current working
   directory". With an empty starting PATH, a bare colon join leaves `{directory}:` — and a shell
   started under it will execute a script out of whatever directory the user is standing in.
   **Reproduced live this planning session** in a scratch directory holding an executable
   `hello.sh`: under the bare-join shape, `hello.sh` ran from the cwd; under the shape above, the
   same invocation reported `command not found` (exit 127). The conditional expansion contributes
   the separator and the old value only when PATH is non-empty, so an empty PATH becomes exactly
   the managed directory and nothing else. This supersedes the earlier planning note that called
   the empty segment "pnpm's own documented quirk and not a defect this phase introduces" — the
   note was wrong, and the cross-AI reviewer (MEDIUM-02) was right.

3. **The guard reads `${PATH-}`, not `$PATH`.** Verified live: under `set -u` with PATH unset,
   `case ":$PATH:"` aborts the shell in bash, zsh and this host's `/bin/sh`
   (`PATH: unbound variable`), while `case ":${PATH-}:"` completes and leaves PATH equal to the
   managed directory in all three. The assignment side needs no such treatment — `${PATH:+...}`
   is a default-applying expansion and is already safe with PATH unset.

Live evidence for 2 and 3 was produced against bash 5.3.9, zsh 5.9.2 and this host's `/bin/sh`
during planning; Task 1 and Task 2 re-establish it as committed tests rather than relying on it.

**Honest scope note on shell coverage (research assumption A3).** The idiom was live-tested this
phase under bash 5.3.9, zsh 5.9.2 and this host's `/bin/sh` — which is bash invoked as `sh`, not
`dash`. `dash` could not be installed (no sudo). `case`/`esac` is core POSIX grammar and pnpm
ships this idiom in production across the same shell spread, so the residual risk is low — but
no plan in this phase may claim dash/pure-POSIX coverage was proven. Say "bash, zsh, and this
host's /bin/sh", never "all POSIX shells".
