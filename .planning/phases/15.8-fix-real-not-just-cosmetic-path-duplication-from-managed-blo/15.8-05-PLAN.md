<objective>
Decide, precisely and conservatively, what consolidation does about a line inside `~/.shellrc`
that sources `~/.myshellrc` — and prove in real shells that the result cannot loop.

Plan 15.8-04 built the preconditions, the backup and the happy path. This plan adds the content
inspection that sits between them, plus the two public helpers plan 15.8-06 consumes.

Purpose: D-04. A `~/.shellrc` that sources `~/.myshellrc` is the case that turns consolidation
into a self-sourcing file: after the stub is written, `~/.shellrc` sources `~/.myshellrc`, which
now contains the copied-forward line sourcing `~/.myshellrc`. Research marks it `[ASSUMED]` (A1)
— unverifiable on this host, since `~/.shellrc` does not exist here — which makes it a case to
BUILD and TEST against synthetic fixtures, never one to acknowledge and skip.

Output: the line classifier, `consolidation_refusal`, `consolidated_body`, the public
`sources_file` predicate and `remove_source_block`, in `installer/shellrc.py`; unit and
real-shell tests in `tests/test_shellrc.py`.

**The rule, stated before any code: rewrite only what is unambiguous, refuse the rest.**

The first revision of this plan tried to detect source lines with one regex (command position at
line start or after `;`/`&&`/`||`/`|`) and comment out whatever it found, whole line. Cross-AI
review round 1 (HIGH-04) showed that rule failing in both directions at once:

- It MISSED `if . "$HOME/.myshellrc"; then`, `! source ...`, backslash-continued commands, and
  indirection through a variable (`target="$HOME/.myshellrc"; . "$target"`). Every missed line
  becomes a self-source after migration — the exact failure this handling exists to prevent.
- It OVER-REACHED on a compound line: `export A=1; . "$HOME/.myshellrc"; export B=1` would have
  been replaced wholesale by a comment, silently killing two exports the user relies on.

So: exactly one shape is rewritten — a simple logical line that consists SOLELY of a `.` or
`source` command whose argument statically resolves to the target. Everything else that looks
like a live source of the target ends the operation with a reason. Refusing is cheap, visible,
and leaves the user exactly where they were; guessing is none of those things.

**Round 2 sharpened the same rule and explicitly rejected building a parser.** Review round 2
(HIGH-02) found the per-line classifier still missing and still over-reaching — `. "$HOME"/.myshellrc`
is valid in all three shells but fails a "strip one matching quote layer" rule and would be copied
forward into a self-source; the same text inside a HERE-DOCUMENT body looks like a standalone
source command and would be commented out, altering inert unmanaged content; and
`root=$HOME; . "$root/.myshellrc"` evades the file-level indirection heuristic. The reviewer's
remedy was a shell-aware lexer or parser.

**That remedy is rejected, deliberately and on this project's own precedent.** A half-built shell
parser is a liability: it would be the most complex code in this repository, it would be trusted
to decide whether to edit a user's shell configuration, and its failures would be silent. This
project has answered this question before, twice, the same way:

- `installer/omz.py:9-19,113,140,215` — the multi-line `plugins=(...)` array is OUT OF SCOPE by
  design. The matcher is written so a multi-line form FAILS to match rather than being
  half-parsed, and `enable_plugins` raises rather than editing a file it cannot read confidently.
- `installer/daemon.py:294-321` — `install_wrapper` refuses a same-named file carrying no
  sentinel rather than clobbering it.

So round 2's fix moves the effort to the DETECTION side and leaves the REWRITE side exactly as
narrow as round 1 made it. Detection is widened by normalization (strip every quote character
before expanding, compare through `realpath`) and by three blanket file-level refusals that
replace the parser outright:

- **any here-document opener** anywhere in the file — refuse; we do not attempt to know where a
  here-doc body ends, and the alternative is commenting out inert text;
- **any live `eval`** — refuse; `eval` can source anything and no string rule can say what;
- **any live `.`/`source` whose argument is not statically resolvable** — refuse; this one rule
  subsumes every indirection form, single- or multi-variable, without tracking assignments at all,
  and is strictly stronger than the heuristic round 1 wrote.

A refusal that tells the user exactly what to do by hand is correct, shippable and testable. The
cost — a `~/.shellrc` containing a here-doc or an `eval` is never auto-consolidated — is real and
is stated to the user in the reason. Accept it.

**What that costs, said plainly.** Three concrete losses, each accepted on purpose:
- The guarded `[ -f "…" ] && . "…"` shape — the one this project's own `ensure_source` writes — is
  a compound line and is therefore REFUSED, not rewritten. Teaching the rewriter to handle a
  specific safe compound form is a designed decision with its own fixtures, not something to slip
  in while implementing this one.
- A `~/.shellrc` containing ANY here-document is never auto-consolidated, even when the here-doc
  has nothing to do with sourcing. Knowing where a here-doc body ends is parsing, and the
  alternative to refusing is commenting out inert text inside someone's usage message.
- A `~/.shellrc` containing ANY live `eval`, or any source command whose argument does not
  statically resolve, is never auto-consolidated.
In all three cases the user gets a refusal naming the file, the line, and what to do by hand.
Every one of them leaves both files exactly as they were, which is a strictly better outcome than
a rewrite this tool cannot justify.

**The documented residual, kept honest and now tested.** Foreign content copied forward verbatim
may itself contain plain, non-self-deduping PATH exports. They keep their existing behavior:
sourced twice, they add two copies. Rewriting a user's own lines would break D-04's verbatim
copy-forward promise, and this project already has a separate, user-facing mechanism for other
tools' plain exports (`installer/rcclean.py::find_duplicate_path_lines`). Task 2 pins that
residual with its own test and its own directory, so it is a stated contract rather than a
surprise — and so a later phase that decides to change it has to change a test to do so.
