# Phase 15.8: Fix real (not just cosmetic) PATH duplication from managed-block sourcing - Context

**Gathered:** 2026-09-15
**Status:** Ready for planning

<domain>
## Phase Boundary

`installer/shellrc.py`'s `managed_block()` (lines 101-111) and its `pnpm_home` export
(around line 210) both emit a plain, unconditional `export PATH="{dir}:$PATH"` per
directory into `.bashrc`/`.zshrc`/`.myshellrc`. The rc-FILE content itself is
idempotent (`apply_block` never writes the marker block twice) — but the block's
RUNTIME EFFECT is not: every nested/child shell that sources it again (tmux/WezTerm
panes, IDE-integrated terminals, subshells — all extremely common) re-prepends the
same directory onto an already-inherited PATH that has it, accumulating duplicates
with every nesting level. Confirmed live this session: 5 copies of `~/.local/bin`, 4
of `fnm`'s dir, 3+ of several others, in a single real shell session on this host —
this is the actual reason Doctor's PATH audit keeps reporting the same "duplicated on
PATH" findings even after applying the fix and opening a genuinely new terminal (not a
UI-staleness issue — that is Phase 15.1's separate, already-scoped finding). Fix: make
every PATH-export site self-deduping, following the exact case-guarded idiom this
codebase already recognizes from pnpm's own installer output
(`installer/rcclean.py:61-70`).

</domain>

<decisions>
## Implementation Decisions

### Migration: fix existing installations automatically
- **D-01:** The next time `apply`/`fix` runs on Doctor (or `make fix`), the
  regenerated `managed_block()` output uses the new self-deduping form, and the
  existing `apply_block()` mechanism (already idempotent — replaces the last
  marker-delimited block rather than appending a new one) naturally migrates any
  existing installation's old plain-export block to the new form. No separate
  migration script or one-off cleanup step — the existing block-replacement mechanism
  already does this for free once `managed_block()`'s output changes.
  — **Reversibility:** reversible.
  **Rationale (user):** chose automatic migration explicitly — fixes the user's own
  already-broken installation (and everyone else's) without requiring a fresh
  install, reusing the block-replacement mechanism that already exists rather than
  building something new.
  **Note (not yet asked, flag for research/planning):** migration fixes the *file*
  the next time `apply` runs; it does NOT retroactively clean the *already-running*
  shell session's in-memory PATH (which keeps its accumulated duplicates until that
  session's shell exits) — this matches the existing "restart your shell to apply"
  messaging pattern already used elsewhere in Doctor and is not a gap this phase
  needs to close further, just something the fix-preview/action text should keep
  being honest about.

### Scope: fix every plain-export PATH site, not just the main one
- **D-02:** Build one reusable, self-deduping PATH-block-emission mechanism and apply
  it to BOTH `managed_block()` (the primary bin-dirs block) AND the `pnpm_home` export
  (`shellrc.py` around line 210) in this same phase — not just the primary site, with
  `pnpm_home` deferred. A single mechanism, one pass, no second known site left with
  the same defect for a future phase to rediscover.
  — **Reversibility:** reversible.
  **Rationale (user):** explicitly chose the "fix every site" option — consistent
  with the user's original ask for a genuinely reusable function, not a one-off patch
  to a single call site.

### Fix mechanism: self-deduping guarded form (carried from initial framing, not re-asked)
- **D-03:** Replace the plain `export PATH="{dir}:$PATH"` emission with the same
  case-guarded, self-deduping shell idiom already used by pnpm's own official
  installer output and already explicitly recognized by this codebase's own
  `installer/rcclean.py:61-70` (`find_duplicate_path_lines`'s comment: pnpm's
  `*) export PATH="$PNPM_HOME:$PATH" ;;` form is "self-deduping ... nothing safe or
  necessary to strip"). Both `managed_block()`'s bin-dir exports and the `pnpm_home`
  export should emit this same guarded form.
  — **Reversibility:** reversible.
  **Rationale:** this was the framing the phase was inserted with (per the user's own
  explicit ask for "una función reusable que se encargue de agregar bloques no sin
  antes verificar ya existe... o que no se esté agregando a PATH dos veces lo mismo")
  and was not contested during discussion — the two areas actually discussed (D-01,
  D-02) refine ITS scope and migration behavior, not whether this is the right
  mechanism.

### Generic ~/.shellrc consolidation (added post-discussion, user request)
- **D-04:** Some machines carry a generic `~/.shellrc` file (not this project's own
  `~/.myshellrc` — a different, plain/conventional name some other tool or base
  system setup may have created) alongside or instead of `~/.myshellrc`. When the
  installer detects a `~/.shellrc` exists, it must consolidate: migrate its content
  into `~/.myshellrc` (this project's own managed file) and leave exactly one
  canonical file going forward, rather than two shell-config files whose sourcing
  order/precedence is ambiguous and can itself cause the same class of duplication
  bug D-01/D-02/D-03 fix (e.g. both files independently exporting PATH entries).
  — **Reversibility:** reversible (a migration/merge of file content, not a deletion
  of anything without first copying it forward).
  **Rationale (user, verbatim intent):** "para .myshellrc, algunas instancias tienen
  .shellrc y necesitamos usar solo uno, nuestro script debe reemplazar .shellrc por
  nuestro .myshellrc si se encuentra" — raised while confirming the autonomous-run
  start point for this phase; not reproducible on this exact host (`~/.shellrc` does
  not exist here) but based on the user's knowledge of other real setups. No existing
  code has any awareness of a generic `.shellrc` today (confirmed via grep — only
  `.myshellrc` is referenced anywhere in `installer/`).
  **Claude's Discretion (added):** exact detection (`~/.shellrc` existence at
  install/doctor-apply time) and merge mechanism (append its content into
  `.myshellrc`'s own managed area vs. a preserved verbatim copy above the managed
  markers, to avoid losing any of the user's own non-managed customizations already
  in that file) — implementation shape for research/planning; the requirement is
  "end state has one canonical file," not a specific merge algorithm.

### Claude's Discretion
- Exact case-guard shell syntax for the reusable function's output (matching pnpm's
  own `case ":$PATH:" in *":$dir:"*) ;; *) export PATH="$dir:$PATH";; esac` idiom
  precisely, vs. a functionally-equivalent variant) — implementation detail, as long
  as `installer/rcclean.py`'s existing pnpm-recognition logic continues to treat it as
  self-deduping (i.e., don't invent a shape `rcclean.py` doesn't already know to skip,
  or update `rcclean.py`'s recognition alongside this change).
  Whether the reusable function lives in `installer/shellrc.py` itself (both call
  sites are already there) or a smaller shared helper — implementation shape.
- Whether `find_duplicate_path_lines` in `rcclean.py` needs updating once
  `managed_block()`'s own output changes shape (since that function's whole purpose
  is flagging *other* tools' plain-export duplicate lines for cleanup — it must not
  start flagging this project's own now-self-deduping blocks as duplicates to strip)
  — flag for research to verify no regression there.

## Existing Code Insights

### Reusable Assets
- `installer/rcclean.py:61-70`'s already-documented case-guard idiom is the exact
  reference implementation to replicate in `managed_block()`'s new output — this
  codebase already "speaks" this shape, just doesn't emit it yet for its own blocks.
- `apply_block`'s existing idempotent block-replacement mechanism (`shellrc.py`) is
  directly reusable for D-01's automatic migration — no new replacement logic needed,
  only a changed `managed_block()` output feeding the same existing call.

### Established Patterns
- The marker-delimited block convention (`_PATH_BEGIN`/`_PATH_END`) already
  guarantees the FILE never gets the block twice; this phase only needs to change
  what goes *inside* the block, not the block-management mechanism itself.

### Integration Points
- `installer/status.py` (the Doctor PATH-audit generator, referenced across Phase
  15.1's context too) is the consumer that currently reports "duplicated on PATH" —
  not modified by this phase directly, but its findings should naturally stop
  recurring (for freshly-sourced shells) once D-01/D-02/D-03 ship, giving the planner
  a natural verification signal ("open a new shell, confirm zero duplicate findings")
  distinct from Phase 15.1's own UI-refresh-timing fix.
