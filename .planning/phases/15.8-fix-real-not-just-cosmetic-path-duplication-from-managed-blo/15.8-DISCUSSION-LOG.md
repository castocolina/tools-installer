## Origin (live bug report, this session)

User reported (with two screenshots) that Doctor's "duplicated on PATH" findings
persisted even after applying the fix and opening a genuinely new WezTerm window
(a different terminal than the one used to apply the fix) and running `make run`
fresh. Investigation found the real cause: `installer/shellrc.py`'s `managed_block()`
(and its `pnpm_home` export) emit a plain, unconditional
`export PATH="{dir}:$PATH"` — idempotent as file content, but NOT idempotent at
runtime, since every nested/child shell that sources the block again re-prepends the
same directory onto an already-inherited PATH. Reproduced independently in a live
bash session: 5 copies of `~/.local/bin`, 4 of `fnm`'s dir, etc. This is distinct
from Phase 15.1's separate finding (Doctor's UI not refreshing its own snapshot) —
this is a real environment defect, not a display artifact.

---

## Migration of existing installations

Trade-off presented: automatically rewrite the existing (already-broken) block to the
new self-deduping form the next time Doctor's `apply`/`fix` runs (reusing the
already-idempotent `apply_block` replacement mechanism) vs. only applying the fix to
brand-new installations, leaving existing ones (including the user's own) broken
until a full reinstall.

**User's choice:** Migrar automáticamente al aplicar (recommended option).

**Resolution:** Captured as D-01 in CONTEXT.md, with a note that this fixes the file
going forward but does not retroactively clean an already-running shell's in-memory
PATH (matches existing "restart your shell" messaging elsewhere, not a new gap).

---

## Scope: which PATH sites to fix

Trade-off presented: fix every plain-export site in one pass (the main
`managed_block()` bin-dirs AND the separate `pnpm_home` export around
`shellrc.py:210`) vs. fixing only the primary `managed_block()` site and deferring
`pnpm_home` to a future phase.

**User's choice:** Arreglar todos los sitios en esta fase (recommended option) —
consistent with the user's original ask for a genuinely reusable mechanism, not a
one-off patch to a single call site.

**Resolution:** Captured as D-02 in CONTEXT.md.

## Generic ~/.shellrc consolidation (added post-discussion, user request)

Raised by the user while confirming the autonomous-run start point (a separate
session turn, not part of the original --analyze discussion areas), but scoped
squarely into this phase's domain (`shellrc.py`).

**User's request (verbatim):** "para .myshellrc, algunas instancias tienen .shellrc
y necesitamos usar solo uno, nuestro script debe reemplazar .shellrc por nuestro
.myshellrc si se encuentra."

**Investigation:** `~/.shellrc` does not exist on this host (not reproducible here);
`installer/` has zero existing references to a generic `.shellrc` anywhere — this is
a new requirement, not a partially-built feature.

**Resolution:** Captured as D-04 in CONTEXT.md — detect `~/.shellrc` and consolidate
its content into `~/.myshellrc`, leaving one canonical file. Exact detection point
and merge mechanism left to Claude's Discretion (research/planning).
