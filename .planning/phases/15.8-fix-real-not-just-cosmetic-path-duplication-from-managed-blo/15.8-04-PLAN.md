<objective>
Build D-04's `~/.shellrc` consolidation as a pure decision layer plus one thin IO function in
`installer/shellrc.py`, with the sourcing-loop case treated as a real case to handle and prove,
not an afterthought. Wiring into `configure_path`/`setup.py` is plan 15.8-05; this plan is the
mechanism and its proofs.

Purpose: D-04 — some machines carry a generic `~/.shellrc` (a different, conventional name some
other tool or base system created) alongside or instead of this project's `~/.myshellrc`. Two
shell-config files with ambiguous sourcing order can independently export the same PATH entries,
which is the same class of duplication D-01/D-02/D-03 fix. The requirement is "the end state has
one canonical file", not a specific merge algorithm.

Output: `consolidate_shellrc()` and its pure helpers in `installer/shellrc.py`, plus unit and
real-shell tests in `tests/test_shellrc.py`.

**The design, resolved (CONTEXT's Claude's-Discretion note leaves the shape to planning;
15.8-RESEARCH.md Pattern 3 and Open Question 3 leave two options open — this plan closes them).**

- Detection trigger: `~/.shellrc` merely EXISTS. No ownership check on it is needed or possible;
  this project has never written that filename (confirmed by grep over `installer/`).
- The content is copied forward VERBATIM into `~/.myshellrc`, inside its own new marker pair,
  applied through the existing `apply_block`. Its own markers — not the PATH block's — are what
  keeps foreign content out of the span `write_myshellrc` rewrites, and what makes a repeat run
  idempotent instead of appending a second copy.
- Research Open Question 3 is resolved as option (b) with its gate: `~/.shellrc` is replaced by a
  MARKED stub that sources `~/.myshellrc`. Option (a), leaving the file untouched, would leave two
  live files with ambiguous precedence — exactly the state D-04 exists to end. The marker is what
  makes the stub recognizable on the next run and reversible later.
- Ordering: copy forward FIRST, stub SECOND. This is the inversion of `omz.py`'s
  record-before-write, and it is deliberate: the exposed state after a crash between the two
  writes is content present in both files, which the next run resolves idempotently. There is no
  rollback branch because the failure state is already the safe one.
- The loop case ([ASSUMED] per research A1 — a `~/.shellrc` that sources `~/.myshellrc` or vice
  versa is unverifiable on this host, since `~/.shellrc` does not exist here): handled in both
  directions. A source line pointing AT `~/.myshellrc` inside the copied content is commented out
  with a stated reason and its original text preserved on the same line. A `~/.myshellrc` that
  already sources `~/.shellrc` is a REFUSAL — commenting out a line in the user's own
  `~/.myshellrc` is a mutation outside this project's managed span and this plan will not make it.

**Residual risk, stated rather than hidden:** foreign content copied forward verbatim may itself
contain plain, non-self-deduping PATH exports. They keep their existing behavior. Rewriting a
user's own lines would break D-04's verbatim copy-forward promise, and this project already has a
separate, user-facing mechanism for other tools' plain exports
(`installer/rcclean.py::find_duplicate_path_lines`). Record this in the SUMMARY; do not silently
"fix" the user's lines here.

**RTK note (this host).** `uv run pytest ...` output is condensed here and can render as a false
`No tests collected` line on a green run. Re-run as `rtk proxy uv run pytest <args>` or
`.venv/bin/pytest <args>` to read the real result.

**Host-safety rule.** This plan is the one most able to damage a real machine. No task may pass a
real `Path.home()`-derived path to any function it writes or tests. Every test uses `tmp_path`
paths passed explicitly, and every spawned shell gets `HOME` pointed at `tmp_path`. No task runs
`make setup`, `make fix` or `make uninstall`.
