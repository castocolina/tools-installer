## Design decisions this plan implements

- **D-01 verbatim, 11 tools.** `direnv`, `gnu-bash`, `gum`, `oh-my-zsh`, `starship`, `watch`, `zsh`
  (shell), `sublime`, `vscode` (editor), `broot`, `zoxide` (nav) move to `human`. CONTEXT.md records
  this as "confirmed as-is, no individual review needed" — the user pre-empted per-tool review for
  this set, so the plan applies it as written.
- **D-02 verbatim, 5 more tools and 7 explicit keeps.** `gitui`, `lazygit`, `bottom`, `dive`, `fzf`
  move to `human`; `duf`, `dust`, `procs`, `bat`, `eza`, `glow`, `hexyl` stay `both`. Both halves get
  a test, because "we decided not to change these" is exactly the kind of decision that evaporates
  unless something asserts it.
- **The discretion clause was exercised, and produced no deviation.** CONTEXT.md's "Claude's
  Discretion" asks the planner to re-apply D-02's criterion if a tool turns out to have a
  non-obvious non-interactive mode, and to call out any deviation explicitly. Two were checked live
  against the installed binaries during planning and both are real: `fzf -f, --filter=STR` is
  documented as "Print matches for the initial query and exit", and `dive --ci` is documented as
  "Skip the interactive TUI and validate against CI rules". Read mechanically, D-02's parenthetical
  ("prints and exits, scriptable") would move both back to `both`.
  **They stay `human` anyway, and that is a decision, not an oversight.** D-02's criterion exists to
  answer one question — would an agent invoke this tool on its own? — and a flag's existence is not
  an answer. `fzf --filter` is a fuzzy-match utility an agent has `rg` and `grep` for; `dive --ci` is
  a CI gate for a human's pipeline, not a way an agent inspects an image (`docker history` is). The
  tools D-02 kept as `both` are ones whose one-shot output IS the product (`duf`, `procs`, `bat`),
  which is not true of either of these. The user also placed both in the `-> human` column of the
  same decision, with the interactive nature of each plainly in view. **No deviation from the
  16-tool list.** If the developer disagrees, this is the paragraph to overrule — the change is one
  word per row.
  **This paragraph does not ship, so Task 2's comment carries its conclusion.** A reader who greps
  `_INTERACTIVE_ONLY_TOOLS`, sees `fzf` and `dive` in it, and knows about `--filter`/`--ci` would
  otherwise be looking at a rule its own set appears to break, with the resolution available only in
  a planning file they will never open. So Task 2 states the rule in terms of a tool's default mode
  and its product rather than its flag inventory, and names these two as deliberately judged — the
  contradiction is answered where it is encountered.
- **The criterion is recorded next to the data it governs, not in `.claude/architecture.md`.** This
  phase adds no mechanism, so it has no architecture section to write; what it adds is a
  classification rule. The established house pattern for that is Phase 15-02's "registry-wide audit
  recorded as a dated, test-protected comment", and `test_d09_borderline_tools_stay_user_tier`
  (`tests/test_registry.py:939`) is the same shape for `tier`. So the rule lives as a comment on the
  pinned sets in `tests/test_registry.py`, where it is load-bearing for a test rather than prose in
  a document nobody greps.
- **Reversibility: reversible, on both decisions.** CONTEXT.md says so explicitly ("a value in a TOML
  file, trivially reverted"). No decision checkpoint is inserted and none is warranted.
- **The full `human` id set is pinned, not just the 16.** A test that only checks the 16 cannot see a
  bulk find-and-replace that also swept `bat` and `eza`; a test that only checks counts reports
  "expected 33, got 34" with no idea which row moved. Set equality names the row.

## Known follow-ups, deliberately out of this plan

- **The other 47 `both` rows are pinned, not reviewed.** Task 3's set equality freezes them so they
  cannot drift silently, but freezing is not the same as having read each one. If the user later
  wants the full pass, it is a new phase with CONTEXT.md's deferred-idea text as its brief.
- **`audience` has no effect beyond the `For` column.** Nothing in this phase makes it filter, sort
  or default anything. If a future phase wants "hide human-only tools in an agent-driven run", that is
  a behaviour change with its own design, not a consequence of this data edit.
- **The dataclass default stays `Audience.BOTH`.** Being the default is what made `both` the value a
  new row copies without thinking — note that all 63 rows do write it explicitly, so the fix is not
  "make them explicit" (they are) but "make the next author choose", which is what the criterion comment
  is for. Changing the default itself is a schema decision CONTEXT.md puts out of scope ("No code or
  schema change"). Record in the SUMMARY that the comment in `tests/test_registry.py` is the mitigation
  chosen instead.
