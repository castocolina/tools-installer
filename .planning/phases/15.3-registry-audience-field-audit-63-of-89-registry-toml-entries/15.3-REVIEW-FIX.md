## Fixed Issues

### WR-01: tracer test contained an assertion that can never fail

**Files modified:** `tests/test_catalog_tui.py`
**Commit:** `cffd961`

`assert all(members_by_title[title] for title in members_by_title)` was
tautological: `group_tools` ends with `... for title, detail, members in groups
if members` (`installer/catalog_tui.py:94`), so empty groups are dropped before
they are returned and every key in `members_by_title` is non-empty by
construction. The line advertised an independent "all three groups are still
populated" guard while asserting nothing — exactly what `.claude/testing.md`
means by not writing assertion-free tests to touch lines.

Two changes, taking the review's suggested shape:

1. The real guard is the title-list equality on the line above — a group that
   emptied would *vanish* from the list rather than arrive empty, so the equality
   would fail. That is now stated in a comment above it, so the next reader does
   not re-add a redundant emptiness check.
2. The vacuous line is replaced by an assertion that can bite, pinning what the
   test is really about — that the re-tag moved the interactive rows across the
   split *without* dragging the scriptable one-shots with them:

```python
    assert "bat" in members_by_title["for both"]
    assert "bat" not in members_by_title["for human"]
```

**Falsification:** flipped `bat`'s registry `audience` from `both` to `human` and
re-ran the test. RED on `assert "bat" in members_by_title["for both"]`
(`AssertionError: assert 'bat' in {'ast-grep', 'brew', ...}`). The deleted line
stayed green under the same mutation, which is the finding.

### WR-02: the standing instruction corrupted the two sets it pointed at

**Files modified:** `tests/test_registry.py`
**Commit:** `5708406`

`test_audience_human_set_is_exactly_the_reviewed_tools` told the next maintainer
to add a new `human`-tagged id "to one of these two sets", but both are dated
historical records: `_INTERACTIVE_ONLY_TOOLS` is *"these 16 rows were re-tagged
from `both` to `human`"* in Phase 15.3, and `_PRE_15_3_HUMAN_TOOLS` is *"the 17
ids that already carried `audience = "human"` **before** Phase 15.3"*. A tool
added in Phase 16 belongs to neither. Following the instruction falsifies
whichever set it joins (and silently widens the `fzf`/`dive` judgement note,
which is scoped to "the 16"); refusing it leaves the test red with no sanctioned
destination.

Added an explicitly open-ended third set and aimed the instruction at it, so the
two historical sets stay frozen and true:

```python
# Ids tagged `human` AFTER Phase 15.3. This is the open-ended set and the
# only one that may grow: the two above are frozen historical records of
# what Phase 15.3 found and what it changed, and adding a new id to either
# would make that set's own comment false.
_POST_15_3_HUMAN_TOOLS: set[str] = set()
```

and the guard became
`human_ids == (_PRE_15_3_HUMAN_TOOLS | _INTERACTIVE_ONLY_TOOLS | _POST_15_3_HUMAN_TOOLS)`.
An empty set unions to a no-op, so the assertion pins exactly the same 33 ids it
pinned before — this adds a door, it does not loosen the lock.

**Falsification, both directions** (the escape hatch has to *work*, not just
exist):
- Tagged `bat` `human` in the registry, left the sets alone → RED, with the
  set-difference message the test was designed for: `Extra items in the left set:
  'bat'`.
- Same mutated registry, `_POST_15_3_HUMAN_TOOLS = {"bat"}` → GREEN. So the
  instruction the comment now gives is one a future maintainer can actually
  follow.

The narrower IN-03 point (the `test_registry_tier_distribution_is_pinned`
cross-reference carries a count discipline, not an id-set rule) is left as the
review wrote it — see below.

### WR-03: the criterion comment failed its own self-check for `gum` and `gnu-bash`

**Files modified:** `tests/test_registry.py`
**Commit:** `886dac5`

Task 2's acceptance criterion is that the rule above `_INTERACTIVE_ONLY_TOOLS`,
applied as written to all 16 ids beside it, returns `human` for all 16 "with no
member whose presence has to be explained from a file outside the repo". Two
members failed it, and the comment named only `fzf` and `dive` as deliberately
judged:

- **`gum`** — its own registry entry (`installer/registry.toml:769`) describes it
  as "A tool for glamorous shell scripts", and `gum style` / `format` / `log`
  print and exit. The rule's `both` clause ("invoking it non-interactively and
  reading what it printed IS the product") matches those subcommands verbatim.
- **`gnu-bash`** — `bash -c '…'` read non-interactively is the single most common
  non-interactive invocation shape there is, and it is how agents run everything.
  The rule as written yields `both`.

The facts that settle both existed only in `15.3-CONTEXT.md` (`:134-138`), which
the future reader will not open. Extended the judged-exception paragraph — the one
that already handles `fzf --filter` and `dive --ci` — to cover them, naming the
tool and why the naive reading does not apply:

```python
# `gum`, `gnu-bash` and `zsh` are judged the same way. `gum` bills itself
# as "a tool for glamorous shell scripts" and several subcommands (`style`,
# `format`, `log`) print and exit, but what the catalog installs is the
# interactive prompt toolkit a person's own scripts drive; an agent
# composing output has no use for styling it. `bash -c`/`zsh -c` are how
# agents run everything, but that runs on whatever shell the box already
# has -- these entries install the shell a person logs into, and no agent
# cares which one that is.
```

`zsh` is folded in because it fails the rule the same way `gnu-bash` does, and
because it is the phase's tracer subject — a reader who greps it should find the
reasoning at the set, not in a planning document.

**This records the existing decision; it re-tags nothing.** Comment-only: no
`audience` value moved, `_INTERACTIVE_ONLY_TOOLS` still holds the same 16 ids, and
`test_registry_audience_distribution_is_pinned` still reads `both` 47 / `ai` 9 /
`human` 33. The review was explicit that WR-03 is a completeness finding about the
written rule, not a request to re-litigate `gum`, and it was treated that way.
