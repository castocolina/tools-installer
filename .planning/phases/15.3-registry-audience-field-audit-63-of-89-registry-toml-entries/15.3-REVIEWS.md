### Strengths

- The 16 re-tags and seven deliberate keeps exactly match the decisions in `.planning/phases/15.3-registry-audience-field-audit-63-of-89-registry-toml-entries/15.3-CONTEXT.md:22-61`.
- Current registry state supports the expected `17 + 16 = 33` human, `47` both, and `9` AI distribution. Representative target rows currently carry `both`, including `zsh` at `installer/registry.toml:503-508`, `fzf` at `installer/registry.toml:357-362`, and `dive` at `installer/registry.toml:1051-1056`.
- The data path is accurately traced: loading applies the audience value at `installer/model.py:675-684`, validates it through `Audience` at `installer/model.py:306-312`, and groups it at `installer/catalog_tui.py:56-81`.
- The proposed exact-human-set and distribution guards complement each other: set equality identifies unintended human-row movement, while the `Counter` tripwire catches `both`↔`ai` movement. This follows the established tier-distribution pattern at `tests/test_registry.py:928-936`.
- The plan correctly preserves schema behavior already covered by the default and invalid-value tests at `tests/test_model.py:110-128` and `tests/test_model.py:334-349`.
- Final verification matches the repository's required gates: `make validate` and `make test` are defined at `Makefile:34-48`, and `.claude/testing.md:31-33` requires both.

### Concerns

- **MEDIUM — The claimed end-to-end `For`-column test does not exercise the renderer.** The proposed tracer only calls `group_tools` and directly indexes `AUDIENCE_LABEL` (`15.3-01-PLAN.md:191-203`). Actual column rendering occurs in both branches of `CatalogScreen._row_cells` at `installer/catalog_tui.py:435-460`, and detail rendering occurs at `installer/catalog_tui.py:467-472`. Existing row tests only assert cell count at `tests/test_catalog_tui.py:903-908`. Therefore, a regression that hard-codes or misplaces the rendered audience cell could pass the proposed test despite the plan claiming the `For` column is verified.
- **MEDIUM — Task 3's falsification runs cannot fail "independently" as written.** It runs the entire `tests/test_registry.py` after each mutation (`15.3-01-PLAN.md:397-406`). Changing a kept tool from `both` to `human` will fail the kept-tool test, exact-human-set test, and distribution test. Changing a pre-existing human tool to `both` will fail both the exact-set and distribution tests. Thus the stated behavior that each mutation exercises one guard independently (`15.3-01-PLAN.md:354-360`) is false; only the `both`→`ai` mutation isolates the distribution guard.
- **MEDIUM — Post-commit diff acceptance criteria are not executable as stated.** Task 1 says to commit at `15.3-01-PLAN.md:223-224`, then requires ordinary `git diff --numstat -- installer/registry.toml` to report `1/1` at `15.3-01-PLAN.md:230-235`. Task 2 has the same conflict between `15.3-01-PLAN.md:322-324` and `15.3-01-PLAN.md:330-335`. After committing, ordinary `git diff` reports no working-tree changes.
- **LOW — The planned durable comment should not say rows were changed "from the class default."** Each target row explicitly declares `audience = "both"`—for example `installer/registry.toml:508`—while the loader default at `installer/model.py:683` applies only when the key is absent. The classification matched the default, but it was not supplied by the default.

### Suggestions

- Extend the real-registry tracer to instantiate the existing screen fixture and assert `screen._row_cells(zsh)[4].plain == "human"` for at least the normal branch; optionally also assert `_detail_text(zsh)` contains `for human`. Keep the `group_tools` assertion for audience-view placement.
- Run each falsification against its named test, for example `pytest ...::test_scriptable_one_shot_tools_stay_audience_both`, then run the full registry suite after restoration. Alternatively, explicitly document the expected collateral failures instead of claiming isolation.
- Capture and record `git diff --numstat` before each task commit, or compare committed revisions with an explicit range such as `git diff --numstat <pre-task-sha>..HEAD -- installer/registry.toml`.
- Phrase the durable comment as "re-tagged from the explicit default-valued `both` classification" rather than "from the class default."

### Risk Assessment

**MEDIUM.** The production change itself is mechanical and low risk, with no meaningful security or performance impact. The remaining risk is plan executability and evidentiary accuracy: one success claim is not actually tested, the falsification expectations are contradictory, and two acceptance checks occur after the state they inspect has been committed away.
