## Warnings

### WR-01: Tracer test contains an assertion that can never fail

**File:** `tests/test_catalog_tui.py:923`
**Issue:** `assert all(members_by_title[title] for title in members_by_title)` is tautological.
`group_tools` ends with `return [(title, detail, members) for title, detail, members in groups if members]`
(`installer/catalog_tui.py:94`) — empty groups are dropped before they are ever returned, so every
key in `members_by_title` is built from a non-empty `members` list and the comprehension can only
produce truthy sets. The line is dead weight that reads like an independent "all three groups are
still populated" guard; the plan's `<behavior>` block explicitly claims that guard ("all three still
non-empty"). The real non-emptiness check is the line above it (`:922`): a group that emptied would
be dropped and the title-list equality would fail. Per `.claude/testing.md` ("don't write
assertion-free tests just to touch lines"), a never-failing assertion is worse than no assertion —
it advertises coverage that does not exist.
**Fix:** delete it, or replace it with an assertion that can actually bite — e.g. pin a row that must
have stayed on the other side of the split, which is what the test is really asserting about:
```python
assert [title for title, _, _ in groups] == ["for AI", "for both", "for human"]
assert "zsh" in members_by_title["for human"]
assert "zsh" not in members_by_title["for both"]
assert "bat" in members_by_title["for both"]  # a D-02 keep, still on the other side
```

### WR-02: The comment's standing instruction corrupts the two sets it points at

**File:** `tests/test_registry.py:174-181` (instruction), `:78-104` and `:149-151` (the set docs it contradicts)
**Issue:** `test_audience_human_set_is_exactly_the_reviewed_tools` tells the next maintainer:

> A phase adding a `human`-tagged catalog entry must add its id to one of these two sets in the same commit

But both sets are documented as *historical records with fixed membership*:
`_INTERACTIVE_ONLY_TOOLS` is "these 16 rows were re-tagged from `both` to `human`" in Phase 15.3
(`:78-79`), and `_PRE_15_3_HUMAN_TOOLS` is "the 17 ids that already carried `audience = "human"`
**before** Phase 15.3" (`:149-150`). A tool added in Phase 16 belongs to neither. Following the
instruction makes whichever set it joins a lie, and silently breaks the `fzf`/`dive` judgement note
(`:94-101`), which is scoped to "the 16". Refusing to follow it leaves the test red with no sanctioned
place to put the id. There is no third destination and no escape hatch — the instruction and the set
definitions cannot both be honoured.
**Fix:** add an explicitly open-ended third set and aim the instruction at it, so the two historical
sets stay frozen and true:
```python
# Ids tagged `human` after Phase 15.3. A phase adding a `human` catalog entry
# appends here in the same commit -- the two sets above are frozen historical
# records of what Phase 15.3 found and changed, and must not grow.
_POST_15_3_HUMAN_TOOLS: set[str] = set()


def test_audience_human_set_is_exactly_the_reviewed_tools() -> None:
    ...
    assert human_ids == (
        _PRE_15_3_HUMAN_TOOLS | _INTERACTIVE_ONLY_TOOLS | _POST_15_3_HUMAN_TOOLS
    )
```

### WR-03: The criterion comment fails its own self-check for `gum` and `gnu-bash`

**File:** `tests/test_registry.py:85-101` (the rule and its judged exceptions), `:110-115` (the members it fails on)
**Issue:** The comment's rule is: `human` when "its default mode is an interactive session … and a
one-shot print is not what it is for"; `both` when "invoking it non-interactively and reading what it
printed IS the product — the shape `df`, `ps`, `cat` and `ls` have". It then names exactly two members,
`fzf` and `dive`, as judged against that rule rather than waved through by it. Applying the rule as
written to the rest of the set does not return the set:

- **`gum`** — its own registry entry describes it as "A tool for glamorous shell scripts"
  (`installer/registry.toml:776`). `gum style`, `gum format`, `gum log` and `gum join` are
  print-and-exit subcommands whose printed output is precisely the product; only `gum choose`/`input`/
  `filter` are interactive. A reader applying the rule lands on `both`.
- **`gnu-bash`** (and, by the same reading, `zsh`) — `bash -c '…'` invoked non-interactively with its
  output read back is the single most common non-interactive invocation shape in existence, and it is
  how agents run everything. The rule as written yields `both`. The fact that actually settles it —
  that this catalog entry installs *a person's login shell*, and that no agent cares which shell the
  box has (the user's own framing, which is what anchors D-01) — appears nowhere in the shipped
  comment; it lives only in CONTEXT.md `:134-138`, a file the reader will not open.

This is the exact failure the comment exists to prevent, restated by Task 2's own acceptance criterion:
"apply the rule as written to all 16 ids in the set beside it and the answer is `human` for all 16,
with no member whose presence has to be explained from a file outside the repo." Two members currently
need that outside file. The consequence is concrete: a future maintainer greps the set, spots `gum`,
reads the rule above it, concludes the set is stale or wrong, and either re-litigates the phase or
"corrects" `gum` back to `both`.
**Fix:** extend the judged-exception paragraph to cover them (this records the existing decision; it
does not change any value):
```python
# `gum`, `gnu-bash` and `zsh` are judged the same way. `gum` bills itself as
# a tool for shell scripts and several subcommands (`style`, `format`, `log`)
# print and exit, but the thing the catalog installs is the interactive
# prompt toolkit a person's own scripts use -- an agent composing output has
# no use for styling. `bash -c`/`zsh -c` are how agents run everything, but
# that runs on whatever shell the box already has; this entry installs the
# shell a person logs into, and no agent cares which one that is.
```
