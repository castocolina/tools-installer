## 15.1-01

### Summary

The plan correctly identifies the catalog refresh path and existing legend infrastructure, with unusually strong rendered-UI coverage. However, its expanded promise that newly installed tools reflect fully current state conflicts with the manager-cache behavior it explicitly leaves unchanged. It also contains a materially false premise about cask version detection.

### Strengths

- D-01 uses the correct active-tier route: `_catalogs` includes every tier, while `_views` excludes the base tier (`installer/wizard_app.py:1575-1592`). Calling `enter_view()` preserves the existing generation and epoch protections (`installer/catalog_tui.py:264-297`).
- The plan correctly avoids copying `show_view()`'s base/non-base stack asymmetry (`installer/wizard_app.py:1732-1755`).
- D-04's corrected interpretation matches the implementation: dim branches return before stale-marker assembly, while both colored branches can receive ` ~` (`installer/catalog_tui.py:299-323`).
- Reusing `_LEGEND` is architecturally sound. It already flows through `BrowserAdapter.legend` into the always-present catalog browser widget (`installer/catalog_tui.py:242-255`, `installer/tool_browser.py:124-129`).
- The proposed rendered tests cover meaningful behavior rather than only private state: post-modal refresh, in-flight checking text, legend clipping, and cursor retention.
- Re-deriving installation presence from `ExecuteInputs.installed` correctly handles PATH, `detect_path`, and application-bundle presence (`installer/execute_screen.py:311-327`, `installer/status.py:18-42`).

### Concerns

- **CRITICAL: The plan's cask premise is false.** The plan states that app/cask installs have `VersionStatus.installed is None` "forever" (`15.1-01-PLAN.md:30-32`). For a cask recognized by manager inventory, ownership carries `current_version` (`installer/ownership.py:544-552`), and `resolve_status()` uses that value for both installed and outdated casks (`installer/version_status.py:275-318`). A command may also provide a readable `--version`. The presence-predicate design is still justified by `detect_path` tools, but the cask claim must be corrected so implementers and tests do not encode the wrong model.
- **HIGH: Newly installed manager-owned tools can still receive stale version/ownership status.** `VersionRefreshService` reuses a fresh manager snapshot without querying again (`installer/version_status.py:424-430`, `:505-520`). Updates invalidate that snapshot (`installer/update.py:436-443`), but the install path has no equivalent invalidation seam in `ExecuteInputs` (`installer/execute_screen.py:311-327`, `setup.py:634-676`). The plan explicitly defers this at `15.1-01-PLAN.md:324-329`, while simultaneously promising that every installation shape reflects real current state. A newly installed brew/cask/pnpm/uv tool can gain the correct Inst mark but still be resolved from pre-install inventory, leaving its Ver/ownership interpretation stale.
- **MEDIUM: The cursor fallback contract is untested.** The plan changes shared `_rebuild()` behavior and specifies fallback when the old row key disappears (`15.1-01-PLAN.md:608-624`), but only requests a test where the key survives both repaints (`:689-701`). Current `_rebuild()` always chooses the first selectable row (`installer/tool_browser.py:138-160`), so the missing-key path is entirely new behavior affecting catalog and uninstall browsers.
- **MEDIUM: Scope and test volume are disproportionate to the phase goal.** The roadmap asks for one post-close refresh, differentiated version text, and a legend (`.planning/ROADMAP.md:605-614`). The plan additionally changes all-tier installation-state synchronization and global `ToolBrowser` cursor semantics, then adds roughly fifteen tests and shell count gates. These additions have rationale, but the plan should separate requirements-critical behavior from incidental shared-widget improvements to reduce execution risk.

### Suggestions

- Replace all "cask versions stay `None` forever" claims with the accurate rule: installation presence cannot generally be inferred from version readability; `detect_path` and some app-bundle cases are the decisive examples.
- Resolve the manager-cache contradiction before execution:
  - Either invalidate the manager snapshot after successful install mutations before the post-close refresh.
  - Or narrow Task 1's promises and tests so they do not claim fresh manager-derived version/ownership state for newly installed manager tools.
- Add a focused `ToolBrowser` test that rebuilds after removing the highlighted key and verifies fallback to the first selectable row. Include a non-selectable or section-row case if that is part of the intended contract.
- Consider moving general cursor-preservation behavior into a separate task or phase unless the start-of-refresh repaint cannot be implemented without rebuilding the whole table.
- Keep the end-to-end update test distinct from the plain-install simulation. The reported defect was an update flow, while the proposed tracer deliberately forces the install path (`15.1-01-PLAN.md:438-458`).

### Risk Assessment

**HIGH.** The core refresh and legend changes are well designed, but the plan currently promises fresh post-install state while knowingly retaining a pre-install manager snapshot. Combined with the incorrect cask premise, this can produce an implementation that passes the specified tests yet remains wrong for manager-owned installations.
