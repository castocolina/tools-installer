## 15.1-01

### Summary

The plan is thoroughly grounded and correctly identifies the existing refresh path, screen ownership, generation guards, and shared legend mechanism. However, three proposed behaviors do not fully achieve the phase goal: installed-state promotion excludes valid non-command installations, `source="unknown"` is treated as permanently untracked despite also representing transient ownership failures, and the stale legend describes a latest version that green cells do not display.

### Strengths

- The post-close wiring is correct: `_catalogs` contains every tier while `_views` excludes the base tier (`installer/wizard_app.py:1575-1592`), so `self._catalogs[self.current_view].enter_view()` is the right uniform call.
- The plan preserves the established refresh lifecycle and race protection. `enter_view()` invokes `_start_version_refresh()`, while generation and epoch checks reject superseded results (`installer/catalog_tui.py:264-297`).
- The end-to-end tests exercise the actual modal close callback and rendered table rather than testing `_install_closed` or `_ver_cell` in isolation.
- Reusing `_LEGEND` is architecturally sound. It already reaches every catalog through `_adapter()` (`installer/catalog_tui.py:242-255`) and is rendered by the shared browser (`installer/tool_browser.py:124-129`).
- The plan correctly preserves real installed-version text when no comparison is available and keeps the existing green/yellow styles (`installer/catalog_tui.py:305-323`).
- D-04's corrected interpretation matches the code: dim branches return before stale-suffix assembly, while statuses with `latest=None` are consistently stale (`installer/version_status.py:262-337`).

### Concerns

- **CRITICAL: The prescribed stale legend is factually wrong for green cells.** The plan requires the gloss "the shown latest came from a cache entry" and says this applies to both green and yellow cells (`15.1-01-PLAN.md:571-580`). Yellow cells display `installed -> latest`, but green cells display only `status.installed`; `status.latest` is not shown (`installer/catalog_tui.py:311-316`). This would make the always-on explanation inaccurate in one of the two states where `~` appears.
- **HIGH: Installed-state promotion does not cover every supported installation shape.** Task 1 promotes a row only when `VersionStatus.installed` is non-`None` (`15.1-01-PLAN.md:303-317`), but that value comes solely from parsing `<cmd> --version` (`installer/version_status.py:166-167,217-219`). The authoritative presence predicate also supports `detect_path` markers and app/cask bundles without a PATH command (`installer/status.py:18-42`), and the registry contains real `detect_path` entries (`installer/registry.toml:555,1725`) and app/cask methods (`installer/registry.toml:2117-2197`). Such a tool can install successfully yet retain a missing Inst mark and blank Ver cell, contradicting the plan's "every tool" success criterion.
- **HIGH: `source="unknown"` does not reliably mean "not tracked for updates."** Task 2 maps every `latest=None, source="unknown"` status to `(not tracked)` (`15.1-01-PLAN.md:429-436`). The final `resolve_status` branch uses `source="unknown"` for any unknown owner (`installer/version_status.py:325-337`), including transient manager-read failures. The existing test demonstrates a brew tool becoming unknown because "the brew inventory could not be read" (`tests/test_version_status.py:839-873`). Labeling that stable "not tracked" conflates temporary uncertainty with the native-package case the user wanted identified.
- **MEDIUM: Showing the checking state introduces an unmitigated cursor reset.** Task 2 adds a full browser reload at refresh start (`15.1-01-PLAN.md:461-472`), and completion already reloads again (`installer/catalog_tui.py:296-297`). Each reload calls `_rebuild()`, which moves the cursor to the first selectable row (`installer/tool_browser.py:138-155`). A user returning from an execution can therefore lose their highlighted row immediately and again at completion. The plan acknowledges the reset but provides no preservation behavior or regression test.

### Suggestions

- Change the stale gloss to describe the comparison source, for example: "`~` latest comparison used cached data not re-confirmed this pass."
- Refresh catalog presence through the same semantics as `installer.status.is_installed`, ideally via an injected live presence callback or a freshly computed installed map after `ExecuteScreen` closes.
- Determine "not tracked" from authoritative ownership, such as `ownership_of(tool.id).owner in NATIVE_OWNERS`, rather than from `VersionStatus.source == "unknown"`. Render transient or unattributable unknown ownership as "no comparison."
- Preserve the highlighted row across `ToolBrowser.reload`, or repaint the affected Ver cells without rebuilding the table. Add a rendered test that starts away from the first row and verifies highlight retention through refresh start and completion.

### Risk Assessment

**HIGH.** The core D-01 refresh wiring is low risk and well tested, but the plan's added state interpretation can still display incorrect installed status and misleading version labels for supported tools. The stale legend also fails the phase's central requirement that every marker explain its actual meaning.
