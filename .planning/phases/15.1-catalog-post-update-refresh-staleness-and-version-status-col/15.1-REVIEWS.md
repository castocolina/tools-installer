## 15.1-01

### Summary

The core D-01 wiring and reuse of the existing legend are well grounded. However, the plan has one direct contradiction with D-04 and two rendering gaps that prevent it from fully proving the phase goal. Revision is required before execution.

### Strengths

- The proposed refresh target is correct. `_catalogs` contains every tier, while `_views` excludes the base tier (`installer/wizard_app.py:1575-1592`), so `self._catalogs[self.current_view].enter_view()` avoids incorrect base-tier branching.
- The refresh reuses the established concurrency controls. `enter_view()` starts a new generation (`installer/catalog_tui.py:264-273`), and completion rejects superseded generations and stale epochs (`installer/catalog_tui.py:289-297`).
- The modal preserves `current_view`: navigation is disabled while `ExecuteScreen` is active (`installer/execute_screen.py:330-341`, `installer/wizard_app.py:1757-1768`), supporting the callback mechanism proposed at `15.1-01-PLAN.md:207-225`.
- Extending `_LEGEND` is preferable to adding another widget. Every catalog adapter already supplies it (`installer/catalog_tui.py:242-255`), and `ToolBrowser` renders it whenever present (`installer/tool_browser.py:124-129`).
- The plan includes integration coverage for base, non-base, and never-started closure paths (`15.1-01-PLAN.md:228-259`) rather than testing `_install_closed` in isolation.
- The source-aware distinction between "not tracked" and "no comparison" reflects real service behavior: failed GitHub retrieval retains `source="github"` (`installer/version_status.py:173-200`), while the unsupported ownership fallback uses `source="unknown"` (`installer/version_status.py:325-335`).

### Concerns

- **CRITICAL: D-04 is contradicted rather than implemented.** The locked context says `stale` is orthogonal and its suffix applies whenever `VersionStatus.stale` is true (`15.1-CONTEXT.md:55-57`). The plan explicitly preserves early returns that omit the suffix from every dim branch (`15.1-01-PLAN.md:327-330`), matching the current behavior at `installer/catalog_tui.py:303-322`. The underlying model further complicates this because statuses with `latest=None` are assigned `stale=True` (`installer/version_status.py:262-270`, `283-291`, `325-333`), even though the legend's proposed gloss describes a cached latest value. The plan must reconcile this domain inconsistency instead of encoding conflicting requirements.
- **HIGH: the "checking…" state is not repainted when refresh starts.** `_start_version_refresh()` only sets `version_refreshing=True` and starts the worker (`installer/catalog_tui.py:268-273`); it does not reload the browser. Rows are reloaded only after completion (`installer/catalog_tui.py:289-297`). Consequently, a currently rendered "no version" cell will remain unchanged during a subsequent refresh, even though direct calls to `_ver_cell()` return the checking label. Task 2 proposes only direct unit coverage for this transition (`15.1-01-PLAN.md:356-372`), so its test can pass while the user never sees the state D-02 requires.
- **HIGH: newly installed tools still cannot show their refreshed version.** The context requires the catalog to reflect the current state after an install or update run (`15.1-CONTEXT.md:9-15`), but `CatalogScreen` copies the initial installed map (`installer/catalog_tui.py:223-237`) and `_ver_cell()` always returns an empty cell when that snapshot says the tool was absent (`installer/catalog_tui.py:299-301`). The plan acknowledges this exclusion (`15.1-01-PLAN.md:174-183`) while still claiming install/update correctness. Its tracer avoids the defect by making the catalog's installed map true while making `ExecuteInputs.installed` return false (`15.1-01-PLAN.md:235-244`), a state combination that exercises the install path but does not model a genuine newly installed row.
- **LOW: the plan is disproportionately prescriptive for a small UI fix.** The 490-line plan mandates test names, exact label strings, source-code introspection, and test-count shell gates. This increases implementation rigidity without addressing the two missing rendered-state behaviors above.

### Suggestions

- Resolve D-04 explicitly. Define which statuses may meaningfully carry `~`, update the context if `stale` only applies when `latest` exists, or render the suffix across dim branches with a legend description that remains truthful.
- Repaint the table when `version_refreshing` changes to true, or establish another mechanism that visibly renders the checking state. Add a headless rendered-table test that observes the cell while a blocked worker is in flight.
- Either refresh `_installed` after `ExecuteScreen` closes or narrow the phase language to updates of already-installed tools. Do not use contradictory installed-state providers as evidence of real post-install behavior.
- Replace the implementation-introspection and test-count gates with behavior-focused tests where possible. The integration and rendered-widget assertions provide stronger guarantees than inspecting source indentation.

### Risk Assessment

**HIGH.** The D-01 callback itself is low risk and correctly designed, but the plan currently contradicts the locked stale-marker decision and can pass all proposed tests while the checking state and newly installed versions remain invisible in the rendered catalog.
