<objective>
Two bugs the user hit running the built app, both inside the catalog's own rendering of state it
already has.

Bug 1 (D-01): after an install/update run, the catalog the run was launched from keeps showing the
versions it probed before the run. `ExecuteScreen` is a `ModalScreen` pushed on top of the active
`CatalogScreen`; popping it resumes that screen, and `CatalogScreen.on_screen_resume`
(`installer/catalog_tui.py:648-656`) deliberately re-stamps selection marks only. `UnifiedApp.show_view`
is the one navigation path that calls `enter_view()`, and it is never reached because nothing
navigated. So `UnifiedApp._install_closed` (`installer/wizard_app.py:1833-1834`) clears the staged set
and the Ver column stays one run behind until the user leaves the tab and comes back — exactly what
the user saw after updating deno.

Bug 2 (D-02/D-03/D-04): `_ver_cell` (`installer/catalog_tui.py:299-323`) renders three different
situations as dim text, two of them as the identical literal word, and one of them as a bare version
with no marker at all. A user cannot tell "a system package this installer will never manage" from
"still probing" from "the comparison failed", and nothing on screen explains what green, yellow or the
trailing `~` mean either.

Purpose: after this plan, a user who runs an update sees the result immediately, on the screen they
are already on, and can read what every color and marker in the Ver column means without pressing
anything.
Output: one added line in `_install_closed`, a rewritten set of dim branches in `_ver_cell` driven by
new shared label constants, a version segment appended to the existing `_LEGEND` from those same
constants, a one-property CSS change so the legend wraps instead of clipping, and the tests that fail
without each of them.
</objective>

## Design decisions this plan implements

- **D-01 — `_install_closed` calls `self._catalogs[self.current_view].enter_view()`.** `_catalogs`
  holds one screen per `Tier`, keyed by the same tier strings `current_view` carries, for all three
  tiers including the base one; `_views` is that same dict with the base tier removed plus the
  non-catalog screens, which is why indexing `_views` here would work on two tiers and raise or miss
  on the third. `enter_view()` already guards on `is_mounted`, so the call needs no guard at the call
  site. This is the full-refresh path CONTEXT.md's D-01 asks for; a per-tool patch of
  `_version_statuses` is explicitly rejected there because a dependency drag-in can change a row that
  was never named in the run.
- **The refresh is unconditional.** `_install_closed` is a screen-result callback with no result to
  branch on (`ExecuteScreen` is a `ModalScreen[None]`). `ExecuteScreen.action_close`
  (`installer/execute_screen.py:717-723`) dismisses only when the run has not started or has already
  finished, so there is no mid-run case to guard against, and an immediate escape refreshing a
  catalog that nothing changed costs one already-cheap re-probe.
- **D-02 — distinct text, never distinct color.** CONTEXT.md rejects new colors outright. The two
  colored branches keep `green` and `yellow` byte-for-byte; every disambiguation is a text label.
- **The `latest is None` branch splits on `status.source`.** That branch is reached by two very
  different situations: a native/unattributable tool this installer does not track (`resolve_status`'s
  final fallthrough, `installer/version_status.py:325-337`, always `source="unknown"`), and a tool this
  installer does own whose latest lookup failed, was budget-deferred, or has no source at all
  (`source="github"`, `"installer"`, `"brew"`, `"cask"`, `"pnpm"`, `"uv"`). Labelling the second one as
  untracked would be a lie the existing test at `tests/test_wizard_app.py:3320-3333` puts straight in
  the diff. `status.source` is already on the dataclass the cell receives, so this needs no ownership
  lookup and does not trespass on Phase 15.4's ownership-column scope.
- **The label constants are the anti-drift mechanism.** `_ver_cell` and `_LEGEND` both read the same
  module-level `_VER_*` constants, so the legend cannot describe a label the cell no longer renders.
  RESEARCH.md's alternative — hand-typing the labels twice — is the drift this design removes.
- **D-03/D-04 — extend `_LEGEND`, do not build a second legend.** `_LEGEND` is already passed as
  `BrowserAdapter.legend` into the `#browser-legend` `Static` that `ToolBrowser.compose` docks under
  the table, and `_adapter()` runs once per `CatalogScreen`, i.e. once per tier. Extending the one
  constant satisfies "visible, always-on, all three top-level views" with no new widget, no new region
  and nothing to keep in sync.
- **The legend widget stops being one row tall.** `#browser-legend` is pinned at `height: 1` today,
  which already clips the existing legend's tail on a 100-column terminal. A legend nobody can read is
  not a legend, so the widget sizes to its content. This is the only reason `installer/tool_browser.py`
  is in scope.

## Known follow-ups, deliberately out of this plan

- The `Inst` column is not re-derived by this refresh. `enter_view()` re-probes versions;
  `self._installed` is the snapshot the app was constructed with, and re-deriving it needs an
  `is_installed` closure `CatalogScreen` does not hold. D-01 names the version-refresh path and only
  that path. Record it in the SUMMARY if it comes up.
- A newly-installed tool's manager snapshot is not invalidated by the install path (only
  `installer/update.py:438` calls `invalidate`). That is a `version_status.py` concern CONTEXT.md puts
  out of scope for this phase; the installed version itself is probed live on every refresh, so D-01's
  user-visible symptom is fixed regardless.
