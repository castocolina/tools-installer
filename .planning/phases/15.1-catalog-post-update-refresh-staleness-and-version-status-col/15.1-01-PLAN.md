<objective>
Two bugs the user hit running the built app, both inside the catalog's own rendering of state it
already has.

Bug 1 (D-01): after an install/update run, the catalog the run was launched from keeps showing the
versions it probed before the run. `ExecuteScreen` is a `ModalScreen` pushed on top of the active
`CatalogScreen`; popping it resumes that screen, and `CatalogScreen.on_screen_resume`
(`installer/catalog_tui.py:648-656`) deliberately re-stamps selection marks only. `UnifiedApp.show_view`
is the one navigation path that calls `enter_view()`, and it is never reached because nothing
navigated. So `UnifiedApp._install_closed` (`installer/wizard_app.py:1833-1834`) clears the staged set
and the Ver column stays one run behind until the user leaves the tab and comes back — exactly what
the user saw after updating deno.

Bug 2 (D-02/D-03/D-04): `_ver_cell` (`installer/catalog_tui.py:299-323`) renders three different
situations as dim text, two of them as the identical literal word, and one of them as a bare version
with no marker at all. A user cannot tell "a system package this installer will never manage" from
"still probing" from "the comparison failed", and nothing on screen explains what green, yellow or the
trailing `~` mean either.

Purpose: after this plan, a user who runs an update sees the result immediately, on the screen they
are already on, and can read what every color and marker in the Ver column means without pressing
anything.
Output: two added lines in `_install_closed` — re-enter the tier the run ran from, and replace the
frozen installed map with a fresh reading from the run's own presence predicate so a tool the run
installed stops being suppressed whatever shape its install took — one added line in
`on_install_run_finished` so the run this app just performed invalidates the manager snapshot the way
every other mutation in this app already does, one repaint call in
`_start_version_refresh` so the checking state is something a user can see rather than only a value a
test can read, a cursor-preserving `_rebuild` so those repaints stop throwing the user back to the
first row, a rewritten set of dim branches in `_ver_cell` driven by new shared label constants, a
version segment appended to the existing `_LEGEND` from those same constants, a one-property CSS
change so the legend wraps instead of clipping, and the tests that fail without each of them.

## Design decisions this plan implements

- **D-01 — `_install_closed` calls `self._catalogs[self.current_view].enter_view()`.** `_catalogs`
  holds one screen per `Tier`, keyed by the same tier strings `current_view` carries, for all three
  tiers including the base one; `_views` is that same dict with the base tier removed plus the
  non-catalog screens, which is why indexing `_views` here would work on two tiers and raise or miss
  on the third. `enter_view()` already guards on `is_mounted`, so the call needs no guard at the call
  site. This is the full-refresh path CONTEXT.md's D-01 asks for; a per-tool patch of
  `_version_statuses` is explicitly rejected there because a dependency drag-in can change a row that
  was never named in the run.
- **The refresh is unconditional.** `_install_closed` is a screen-result callback with no result to
  branch on (`ExecuteScreen` is a `ModalScreen[None]`). `ExecuteScreen.action_close`
  (`installer/execute_screen.py:717-723`) dismisses only when the run has not started or has already
  finished, so there is no mid-run case to guard against, and an immediate escape refreshing a
  catalog that nothing changed costs one already-cheap re-probe.
- **The installed map is re-derived from the run's own presence predicate, not promoted from the
  version probe.** `CatalogScreen.__init__` copies the installed map once
  (`installer/catalog_tui.py:225`) and `_ver_cell` returns an empty cell whenever that copy says False
  (`:300-301`), so before this plan a tool installed *by the run* stays blank no matter how fresh the
  version data is — D-01's refresh would fix the deno case the user reported and silently fail the "I
  just installed it" case. CONTEXT.md's Phase Boundary says "after `ExecuteScreen` closes
  (install/update run finished), `CatalogScreen` must reflect the real, current state of every tool it
  shows", so narrowing the phase to updates-only would contradict the locked boundary rather than
  honour it.

  Round 1 of this plan promoted the map from `VersionStatus.installed`. Round 2's review showed that
  signal is too narrow; round 3's review showed that round 2's *reason* was partly wrong, and
  re-reading the source settles both. The accurate rule is: **presence cannot be inferred from version
  readability**, in either direction.
  - `is_installed` answers True on any one of three independent signals — a PATH command, a
    `detect_path` marker file, or an app/cask bundle directory (`installer/status.py:18-42`).
  - `VersionStatus.installed` is filled from two sources, not one: the `--version` probe
    (`installer/version_status.py:166-167`, `:217-219`) on the installer/github/fallthrough paths, and
    **the manager inventory** on the brew/cask/pnpm/uv paths, where `resolve_status` renders
    `ownership.current_version or probed` (`installer/version_status.py:275-318`) and
    `current_version` is what `brew list --versions` reported for that formula or cask
    (`installer/ownership.py:534-552`).
  - So the round-2 phrasing "`installed` comes only from `<cmd> --version`" and the derived claim that
    an app/cask install has `installed is None` **forever** are both false, and round 3's CRITICAL is
    correct: a cask the brew inventory lists carries a version even when nothing answers `--version`.
    Do not write a test or a comment that encodes the "casks never have a version" model.
  - What survives, and is what actually justifies the presence-predicate design, is narrower and
    exact: a `detect_path`-only tool with no owning manager has **no** path to a version at all.
    `oh-my-zsh` is the standing counter-example — `cmd = "omz"` is a zsh function, so `shutil.which`
    never finds it and the probe never answers, its methods are `script`-kind so no manager inventory
    will ever list it, yet `detect_path = "~/.oh-my-zsh/oh-my-zsh.sh"` makes it genuinely installed
    (`installer/registry.toml:539-555`). SDKMAN is the same shape. A promotion keyed on the probe
    could never fire for either of them, which is why the map is re-derived from the predicate.
  - A freshly installed cask is a *second*, transient case in the same direction: its version exists
    in principle but the inventory that carries it is a snapshot taken before the run. That is the
    round-3 HIGH, and it is fixed by the invalidate entry below rather than by the installed map.

  Round 1 also recorded "the only trustworthy demotion signal is a real `is_installed` closure
  `CatalogScreen` does not hold." That was true of `CatalogScreen` and false of `UnifiedApp`, which is
  the class the fix lives in: `ExecuteInputs.installed` is exactly that closure, defaulting to
  `installer.status.is_installed` (`installer/execute_screen.py:322`) and reaching the app as
  `self._execute` — the same object `on_catalog_screen_decided` requires to be non-None before an
  `ExecuteScreen` can ever be pushed. So `_install_closed` can ask the authoritative predicate
  directly, for every tool of every tier, and hand each screen a whole fresh map. That is one
  `shutil.which` plus a couple of `Path.exists` per tool on the main thread, against a run that just
  spent seconds spawning installers — and it is strictly more correct than any promotion, because it
  is right in both directions: presence is answered by the presence predicate and version-readability
  by the version probe, so a tool whose `--version` stopped parsing keeps its mark while a tool
  uninstalled during the run loses it. The one-directional promotion and its demotion follow-up are
  both retired by this.
- **The run invalidates the manager snapshot, because every other mutation in this app already
  does.** Addresses review concern (round 3): "newly installed manager-owned tools can still receive
  stale version/ownership status". `VersionRefreshService` reuses a persisted manager snapshot while
  it is inside `MANAGER_STALE_AFTER` (`_load_or_query_snapshot`, `installer/version_status.py:424-430`;
  the snapshot is read once per pass at `:505-520` and drives `resolve_ownership` for every tool). A
  freshly installed brew/cask/pnpm/uv tool is absent from that pre-run snapshot, so the post-close
  refresh resolves it through `resolve_status`'s final fallthrough (`:325-337`) and renders a real
  probed version with the no-update-source marker instead of the manager comparison it should have —
  for up to six hours. Verified against the tree: `invalidate` is wired into `UpdateService` only
  (`setup.py:604` -> `installer/update.py:436-443`), and `_execute_inputs` (`setup.py:634-676`) gives
  the install path no equivalent seam.

  This is not a scope decision left open by CONTEXT.md; it is a documented invariant the install path
  silently breaks. `installer/version_status.py:26-30` states it in the module's own words: "`invalidate`
  bumps the epoch AND drops the persisted manager snapshot so the next refresh re-queries. **Every
  mutation this app performs calls it**, so the cache can only ever be stale about changes made
  OUTSIDE this app." An install run is a mutation this app performs. CONTEXT.md's canonical refs put
  `VersionRefreshService`'s cache-invalidation *behavior* out of scope to change — and nothing here
  changes it; this adds a call site to an existing public method, exactly as D-01 adds a call site to
  `enter_view()`.

  The call goes in `UnifiedApp.on_install_run_finished`, not in `_install_closed` and not in
  `execute_screen.py`. Three reasons, in order of weight: (1) `InstallRunFinished` is posted from
  `_execute_worker`'s `finally` on every path (`installer/execute_screen.py:462-546`), so it fires
  when and only when a run actually ran — an escape before starting posts nothing, and an
  unconditional invalidate in `_install_closed` would force a full `brew list` / `brew outdated` /
  `pnpm` / `uv` re-query on every enter-then-escape, which is a very different cost from D-01's
  `--version` re-probe; (2) it keeps `installer/execute_screen.py` and `setup.py` untouched, so the
  phase still does not touch install/update *execution* logic as CONTEXT.md's Phase Boundary requires
  — this is app-level plumbing in the same file and the same message flow D-01 already extends;
  (3) it orders correctly with no new state — the epoch is bumped while the execute screen is still
  up, so the refresh `_install_closed` starts a moment later reads the already-bumped epoch and passes
  `on_version_status_refreshed`'s epoch gate, while any refresh that started *before* the bump is
  discarded by the same gate and cannot persist its pre-install snapshot (`:555-559`).

  Cost and safety, both checked: `invalidate` holds the service lock only across a small atomic JSON
  rewrite (`:410-417`), and `refresh` never holds that lock across its subprocess queries (`:555`), so
  calling it from the event loop cannot block the UI on manager commands — the re-query itself happens
  on the refresh worker thread. Over-invalidating is safe in one direction only: it costs one extra
  manager query and can never produce wrong data, which is why a run that failed outright still
  invalidates rather than the plan trying to infer "did anything actually change".
- **D-02 — distinct text, never distinct color.** CONTEXT.md rejects new colors outright. The two
  colored branches keep `green` and `yellow` byte-for-byte; every disambiguation is a text label.
- **The checking state has to be painted, not merely returnable.** `_start_version_refresh`
  (`installer/catalog_tui.py:268-273`) bumps the generation, sets `version_refreshing` and starts the
  worker; the browser is reloaded only on completion (`:297`). So a cell that says "no version" keeps
  saying it for the entire duration of the next refresh, and D-02's checking marker — which
  `_ver_cell` would happily return — is a label no user can reach. A unit test that calls `_ver_cell`
  with `version_refreshing` forced True passes against that broken UI, which is why this plan pins the
  state with a rendered-table assertion against a blocked worker instead. The fix is one call to the
  repaint path the completion handler already uses, `self._browser.reload(self._adapter())`, placed
  immediately after `version_refreshing = True`. `ToolBrowser.reload` guards on `is_mounted`
  (`installer/tool_browser.py:177`) so the `on_mount` call site stays safe, and its selection-pruning
  line is a no-op here because the item list is unchanged.
- **D-04 — the stale suffix is scoped to a rendered latest, and CONTEXT.md is corrected to say so.**
  CONTEXT.md's D-04 parenthetical ("appended today whenever `VersionStatus.stale` is true,
  orthogonally to the outdated/unmanaged/unknown states") and RESEARCH.md's echo of it
  (`15.1-RESEARCH.md:197-199`) are both **wrong about the code they describe**: the suffix is assembled
  at `installer/catalog_tui.py:319-323`, after the two colored branches have set `base`, and every dim
  branch returns before reaching it. D-04's *normative* clause — "gets its own legend entry too" — is
  what this plan implements, in Task 3. Rendering the suffix unconditionally instead would be actively
  worse, on three pieces of evidence: (1) `resolve_status` hardcodes `stale=True` on every path that
  yields `latest=None` (`installer/version_status.py:269`, `:290`, `:332`), so `~` would appear on
  substantially every dim cell at all times and would distinguish nothing; (2) the suffix's own
  meaning is a claim *about the latest a comparison rested on* — it "marks a cached `latest` at or
  past STALE_AFTER that this pass did not re-confirm" (the comment at
  `installer/catalog_tui.py:319-320`) — and a dim cell makes no comparison, so the claim has no
  referent and reads as a cached-latest gloss that does not apply; (3) the
  current behaviour is already pinned by an existing anti-regression assertion,
  `tests/test_catalog_tui.py:1073-1077`, where a `stale=True` status with `installed=None` is asserted
  to render no ` ~` — the unconditional reading would require deleting that assertion. No information
  is lost by the scoping, because the situation `~` would have flagged on those branches (a latest
  lookup that failed, was budget-deferred, or never had a source) is exactly what the
  `_VER_NO_COMPARISON` label and its legend gloss already say in words. CONTEXT.md D-04 gains a dated
  Interpretation note recording this, so the locked decision and the shipped behaviour agree instead
  of the plan quietly diverging from its own context. The scope stops being an accident of early
  returns and becomes a named property with its own test in Task 2.
- **The `latest is None` branch splits on `status.source`, and the split claims only what `source`
  proves.** That branch is reached by two very different situations: a tool whose update source this
  installer could not attribute at all (`resolve_status`'s final fallthrough,
  `installer/version_status.py:325-337`, always `source="unknown"`), and a tool this installer does own
  whose latest lookup failed, was budget-deferred, or has no source at all (`source="github"`,
  `"installer"`, `"brew"`, `"cask"`, `"pnpm"`, `"uv"`). Labelling the second one as unmanaged would be a
  lie the existing test at `tests/test_wizard_app.py:3320-3333` puts straight in the diff.
  `status.source` is already on the dataclass the cell receives, so this needs no ownership lookup and
  does not trespass on Phase 15.4's ownership-column scope.

  Round 2's review is right that `source="unknown"` is itself two populations, and re-reading the
  source confirms it is worse than the review said: the fallthrough is reached by every owner that is
  not `installer`/`brew`/`cask`/`pnpm`/`uv`, which means the genuine native-package owners
  (`NATIVE_OWNERS = ("dnf", "apt", "pacman", "rpm-ostree")`, `installer/ownership.py:84`) and a
  `owner="unknown"` produced by an inventory read that failed
  (`ManagerOwnership.unknown_reason`, `installer/ownership.py:145`; the worked case is
  `tests/test_version_status.py:839-873`, a brew tool whose "brew inventory could not be read") land
  on the identical `source="unknown"` string. **Telling them apart is not possible from the data the
  cell receives**: `VersionStatus` has seven fields (`installer/version_status.py:123-131`) and none of
  them is the owner or the reason — `resolve_status` drops `unknown_reason` on the floor. The two ways
  to recover it are a new `VersionStatus` field, which CONTEXT.md's canonical refs put out of scope
  ("`VersionStatus` ... not in scope to change"), and an ownership lookup from the cell, which
  CONTEXT.md's Deferred Ideas assign to Phase 15.4's ownership column. So this plan does the one thing
  that is both in scope and honest: it names the label after what `source="unknown"` actually means —
  no update source was attributed — instead of asserting the permanent property "this installer does
  not track it", which is true of only one of the two populations. The limitation is recorded as a
  follow-up with a pointer, not dropped.

  Round 3 surfaced what would have been a third population reaching this same label — a manager-owned
  tool resolved against an inventory snapshot taken before the run that installed it. The invalidate
  entry above closes that one at its source instead of absorbing it into this marker, which is why
  the marker and its legend gloss stay at two populations (a native package; a manager inventory that
  could not be read this pass) rather than growing a third clause a one-line legend has no room for.

- **The two repaints per refresh must not cost the user their place.** `ToolBrowser._rebuild` moves the
  cursor to the first selectable row on every call (`installer/tool_browser.py:153-155`), and this plan
  adds a second `reload` per refresh cycle, so without a change a user coming back from a run would be
  thrown to row 0 twice. Preserving is cheap and needs no new machinery: `installer/ui_common.py:52-58`
  already exposes `highlighted_key(table)`, and `DataTable.get_row_index` maps a key back to a row.
  Capture the key before `clear()`, restore it after the rows are re-added, fall back to
  `_first_selectable_row()` when the key is gone (a filtered-out row, the uninstall view's live
  re-derivation) or absent (the `on_mount` call site, where the table is empty). This lands in the
  shared widget rather than the catalog because all four `_rebuild` call sites want it — the two
  reloads, the tab switch, and the column sort, where keeping the highlighted item under the cursor is
  the behaviour a user expects anyway. The two existing cursor assertions
  (`tests/test_tool_browser.py:163`, `tests/test_catalog_tui.py:245`) are not affected: both follow
  `action_select_all`/`action_invert`, which repaint through `refresh_marks` and never call `_rebuild`.

  Because the change lands in the shared widget, its contract is pinned at the widget, not only
  through the catalog. Addresses review concern (round 3): "the widened `_rebuild()` cursor-fallback
  contract is untested". The catalog's `refresh_cursor` test covers the key-survives half; the
  key-is-gone half is entirely new behaviour on a path two browsers take (the catalog's reloads and
  the uninstall view's live re-derivation, `wizard_app.py`'s own `BrowserAdapter`), and a branch no
  test enters is a branch that can be written backwards and still ship. It gets two focused tests in
  `tests/test_tool_browser.py`, whose `_Host` app and `_adapter(items=...)` helper already make both
  cases three lines each — which is also why this coverage is cheap enough that leaving it out would
  be a false economy.
- **The label constants are the anti-drift mechanism.** `_ver_cell` and `_LEGEND` both read the same
  module-level `_VER_*` constants, so the legend cannot describe a label the cell no longer renders.
  RESEARCH.md's alternative — hand-typing the labels twice — is the drift this design removes.
- **D-03/D-04 — extend `_LEGEND`, do not build a second legend.** `_LEGEND` is already passed as
  `BrowserAdapter.legend` into the `#browser-legend` `Static` that `ToolBrowser.compose` docks under
  the table, and `_adapter()` runs once per `CatalogScreen`, i.e. once per tier. Extending the one
  constant satisfies "visible, always-on, all three top-level views" with no new widget, no new region
  and nothing to keep in sync.
- **The count gates call `--collect-only` without an extra `-q`, on purpose.** `pyproject.toml`'s
  `[tool.pytest.ini_options] addopts = "-q"` already supplies one quiet flag, so writing `-q` again on
  the command line makes it `-qq`, and at that verbosity `--collect-only` prints a per-file tally
  (`tests/test_catalog_tui.py: 3`) instead of node ids — `grep -c '::test_'` would then return 0 no
  matter how many tests exist, and every count gate below would fail against correct code. Verified
  against this repo: plain `--collect-only` prints the node ids these gates count. Do not "tidy" a
  `-q` back into them.
- **The legend widget stops being one row tall.** `#browser-legend` is pinned at `height: 1` today,
  which already clips the existing legend's tail on a 100-column terminal. A legend nobody can read is
  not a legend, so the widget sizes to its content. This is the only reason `installer/tool_browser.py`
  is in scope.
