<objective>
Two bugs the user hit running the built app, both inside the catalog's own rendering of state it
already has.

Bug 1 (D-01): after an install/update run, the catalog the run was launched from keeps showing the
versions it probed before the run. `ExecuteScreen` is a `ModalScreen` pushed on top of the active
`CatalogScreen`; popping it resumes that screen, and `CatalogScreen.on_screen_resume`
(`installer/catalog_tui.py:648-656`) deliberately re-stamps selection marks only. `UnifiedApp.show_view`
is the one navigation path that calls `enter_view()`, and it is never reached because nothing
navigated. So `UnifiedApp._install_closed` (`installer/wizard_app.py:1833-1834`) clears the staged set
and the Ver column stays one run behind until the user leaves the tab and comes back — exactly what
the user saw after updating deno.

Bug 2 (D-02/D-03/D-04): `_ver_cell` (`installer/catalog_tui.py:299-323`) renders three different
situations as dim text, two of them as the identical literal word, and one of them as a bare version
with no marker at all. A user cannot tell "a system package this installer will never manage" from
"still probing" from "the comparison failed", and nothing on screen explains what green, yellow or the
trailing `~` mean either.

Purpose: after this plan, a user who runs an update sees the result immediately, on the screen they
are already on, and can read what every color and marker in the Ver column means without pressing
anything.
Output: one added line in `_install_closed`, a one-directional promotion of the frozen installed map
inside `on_version_status_refreshed` so a tool the run installed stops being suppressed, one repaint
call in `_start_version_refresh` so the checking state is something a user can see rather than only a
value a test can read, a rewritten set of dim branches in `_ver_cell` driven by new shared label
constants, a version segment appended to the existing `_LEGEND` from those same constants, a
one-property CSS change so the legend wraps instead of clipping, and the tests that fail without each
of them.

## Design decisions this plan implements

- **D-01 — `_install_closed` calls `self._catalogs[self.current_view].enter_view()`.** `_catalogs`
  holds one screen per `Tier`, keyed by the same tier strings `current_view` carries, for all three
  tiers including the base one; `_views` is that same dict with the base tier removed plus the
  non-catalog screens, which is why indexing `_views` here would work on two tiers and raise or miss
  on the third. `enter_view()` already guards on `is_mounted`, so the call needs no guard at the call
  site. This is the full-refresh path CONTEXT.md's D-01 asks for; a per-tool patch of
  `_version_statuses` is explicitly rejected there because a dependency drag-in can change a row that
  was never named in the run.
- **The refresh is unconditional.** `_install_closed` is a screen-result callback with no result to
  branch on (`ExecuteScreen` is a `ModalScreen[None]`). `ExecuteScreen.action_close`
  (`installer/execute_screen.py:717-723`) dismisses only when the run has not started or has already
  finished, so there is no mid-run case to guard against, and an immediate escape refreshing a
  catalog that nothing changed costs one already-cheap re-probe.
- **The installed snapshot is promoted from the refresh's own probe, one-directionally.**
  `CatalogScreen.__init__` copies the installed map once (`installer/catalog_tui.py:226`) and
  `_ver_cell` returns an empty cell whenever that copy says False (`:300-301`), so before this plan a
  tool installed *by the run* stays blank no matter how fresh the version data is — D-01's refresh
  would fix the deno case the user reported and silently fail the "I just installed it" case.
  CONTEXT.md's Phase Boundary says "after `ExecuteScreen` closes (install/update run finished),
  `CatalogScreen` must reflect the real, current state of every tool it shows", so narrowing the
  phase to updates-only would contradict the locked boundary rather than honour it. The fix needs no
  new plumbing: `VersionRefreshService.refresh` iterates **every** tool handed to it
  (`installer/version_status.py:520`) and each path resolves `installed` from a live
  `probe_output([tool.cmd, "--version"])` (`:166-167`, `:217-219`), so a non-None `status.installed`
  is already a live "this command exists and answered" signal crossing into the screen. Promote on
  that signal in `on_version_status_refreshed`, and never demote: a None `installed` means the probe
  produced nothing parseable, which is the S3 "no readable version" case for a tool that is very much
  installed, and demoting would blank both its Inst mark and its Ver cell. Uninstall-during-run
  therefore still shows a stale ✓ until the app is restarted — recorded below as a known follow-up,
  because the only safe demotion signal is a real `is_installed` closure `CatalogScreen` does not hold.
- **D-02 — distinct text, never distinct color.** CONTEXT.md rejects new colors outright. The two
  colored branches keep `green` and `yellow` byte-for-byte; every disambiguation is a text label.
- **The checking state has to be painted, not merely returnable.** `_start_version_refresh`
  (`installer/catalog_tui.py:268-273`) bumps the generation, sets `version_refreshing` and starts the
  worker; the browser is reloaded only on completion (`:297`). So a cell that says "no version" keeps
  saying it for the entire duration of the next refresh, and D-02's checking marker — which
  `_ver_cell` would happily return — is a label no user can reach. A unit test that calls `_ver_cell`
  with `version_refreshing` forced True passes against that broken UI, which is why this plan pins the
  state with a rendered-table assertion against a blocked worker instead. The fix is one call to the
  repaint path the completion handler already uses, `self._browser.reload(self._adapter())`, placed
  immediately after `version_refreshing = True`. `ToolBrowser.reload` guards on `is_mounted`
  (`installer/tool_browser.py:177`) so the `on_mount` call site stays safe, and its selection-pruning
  line is a no-op here because the item list is unchanged.
- **D-04 — the stale suffix is scoped to a rendered latest, and CONTEXT.md is corrected to say so.**
  CONTEXT.md's D-04 parenthetical ("appended today whenever `VersionStatus.stale` is true,
  orthogonally to the outdated/unmanaged/unknown states") and RESEARCH.md's echo of it
  (`15.1-RESEARCH.md:197-199`) are both **wrong about the code they describe**: the suffix is assembled
  at `installer/catalog_tui.py:319-323`, after the two colored branches have set `base`, and every dim
  branch returns before reaching it. D-04's *normative* clause — "gets its own legend entry too" — is
  what this plan implements, in Task 3. Rendering the suffix unconditionally instead would be actively
  worse, on three pieces of evidence: (1) `resolve_status` hardcodes `stale=True` on every path that
  yields `latest=None` (`installer/version_status.py:269`, `:290`, `:332`), so `~` would appear on
  substantially every dim cell at all times and would distinguish nothing; (2) the suffix's own
  meaning is a claim *about a latest value* — "the latest shown here came from a cache entry this pass
  did not re-confirm" (the comment at `installer/catalog_tui.py:319-320`) — and a dim cell shows no
  latest, so the claim has no referent and reads as a cached-latest gloss that does not apply; (3) the
  current behaviour is already pinned by an existing anti-regression assertion,
  `tests/test_catalog_tui.py:1073-1077`, where a `stale=True` status with `installed=None` is asserted
  to render no ` ~` — the unconditional reading would require deleting that assertion. No information
  is lost by the scoping, because the situation `~` would have flagged on those branches (a latest
  lookup that failed, was budget-deferred, or never had a source) is exactly what the
  `_VER_NO_COMPARISON` label and its legend gloss already say in words. CONTEXT.md D-04 gains a dated
  Interpretation note recording this, so the locked decision and the shipped behaviour agree instead
  of the plan quietly diverging from its own context. The scope stops being an accident of early
  returns and becomes a named property with its own test in Task 2.
- **The `latest is None` branch splits on `status.source`.** That branch is reached by two very
  different situations: a native/unattributable tool this installer does not track (`resolve_status`'s
  final fallthrough, `installer/version_status.py:325-337`, always `source="unknown"`), and a tool this
  installer does own whose latest lookup failed, was budget-deferred, or has no source at all
  (`source="github"`, `"installer"`, `"brew"`, `"cask"`, `"pnpm"`, `"uv"`). Labelling the second one as
  untracked would be a lie the existing test at `tests/test_wizard_app.py:3320-3333` puts straight in
  the diff. `status.source` is already on the dataclass the cell receives, so this needs no ownership
  lookup and does not trespass on Phase 15.4's ownership-column scope.
- **The label constants are the anti-drift mechanism.** `_ver_cell` and `_LEGEND` both read the same
  module-level `_VER_*` constants, so the legend cannot describe a label the cell no longer renders.
  RESEARCH.md's alternative — hand-typing the labels twice — is the drift this design removes.
- **D-03/D-04 — extend `_LEGEND`, do not build a second legend.** `_LEGEND` is already passed as
  `BrowserAdapter.legend` into the `#browser-legend` `Static` that `ToolBrowser.compose` docks under
  the table, and `_adapter()` runs once per `CatalogScreen`, i.e. once per tier. Extending the one
  constant satisfies "visible, always-on, all three top-level views" with no new widget, no new region
  and nothing to keep in sync.
- **The count gates call `--collect-only` without an extra `-q`, on purpose.** `pyproject.toml`'s
  `[tool.pytest.ini_options] addopts = "-q"` already supplies one quiet flag, so writing `-q` again on
  the command line makes it `-qq`, and at that verbosity `--collect-only` prints a per-file tally
  (`tests/test_catalog_tui.py: 3`) instead of node ids — `grep -c '::test_'` would then return 0 no
  matter how many tests exist, and every count gate below would fail against correct code. Verified
  against this repo: plain `--collect-only` prints the node ids these gates count. Do not "tidy" a
  `-q` back into them.
- **The legend widget stops being one row tall.** `#browser-legend` is pinned at `height: 1` today,
  which already clips the existing legend's tail on a 100-column terminal. A legend nobody can read is
  not a legend, so the widget sizes to its content. This is the only reason `installer/tool_browser.py`
  is in scope.

## Known follow-ups, deliberately out of this plan

- **Superseded by Task 1 (review round 1, finding 3):** an earlier draft of this plan listed "the
  `Inst` column is not re-derived by this refresh" as an accepted limitation. It is no longer
  accepted — Task 1 promotes `self._installed` from the refresh's own live probe, so both the Inst
  mark and the Ver cell of a freshly installed row become correct after the run closes.
- What stays out is the **demotion** direction. A tool uninstalled outside this screen (or whose
  `--version` stops answering) keeps its ✓ until the app restarts, because the only trustworthy
  demotion signal is a real `is_installed` closure `CatalogScreen` does not hold, and the available
  signal (a None `installed` on a status) collides with the perfectly ordinary "installed but the
  version string will not parse" case this plan labels S3. Record it in the SUMMARY.
- A newly-installed tool's manager snapshot is not invalidated by the install path (only
  `installer/update.py:438` calls `invalidate`). That is a `version_status.py` concern CONTEXT.md puts
  out of scope for this phase; the installed version itself is probed live on every refresh
  (`installer/version_status.py:166-167`, `:217-219`), which is exactly why the promotion in Task 1
  works without touching the service.
