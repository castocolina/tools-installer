# Phase 15.1: Code Review Report

**Reviewed:** 2026-09-16T11:02:03Z
**Depth:** deep (cross-file: import graph, call chains through `deps.py` / `selection.py` /
`version_status.py` / `execute_screen.py`, and the shared `ToolBrowser` widget's two consumers)
**Files Reviewed:** 6
**Status:** issues_found

## Summary

Commits `351f4f4`, `abdbfca`, `d99cc24`, `64be010` implement D-01..D-04: a post-run catalog
refresh, a presence-predicate-derived installed map, a `VersionRefreshService.invalidate` call
on the install path, four distinct dim `Ver` labels, a cursor-preserving `_rebuild`, and an
always-on legend. The full suite passes (`tests/test_catalog_tui.py`,
`tests/test_tool_browser.py`, `tests/test_wizard_app.py`: 304 passed) and the D-01 mechanics
(tier indexing, unconditional refresh, epoch ordering vs. `InstallRunFinished`, worker
generation gating) hold up under tracing.

Two defects survive the plan's four review rounds and its test suite, both because the new code
was only exercised through **single-tool, single-tier catalogs at 100-120 columns**:

1. The installed-map re-derivation silently **narrows the map from the whole catalog to one
   tier**, which breaks the two cross-tier consumers that read the same map
   (`deps.missing_requires`, `selection.unstaged_recommends`). Reproduced below: after one
   execute-screen close, `mmdc` is told it "also needs pnpm" when pnpm is installed. This also
   contradicts `.claude/architecture.md`'s "Tier is a browsing label ... the tier filter narrows
   what is DISPLAYED and never what is resolved".
2. The legend CSS change (`height: 1` -> `height: auto`) combined with a 466-character legend
   **collapses the catalog `DataTable` from 8 rows to 3 rows at the project's own tested minimum
   terminal size (80x20)**. Measured, not estimated.

The remaining findings are robustness and comment-accuracy defects around the new
`on_install_run_finished` / `_install_closed` code path.

## Critical Issues

### CR-01: `_install_closed` narrows every catalog's installed map to one tier, breaking cross-tier requires/recommends

**File:** `installer/wizard_app.py:1854-1857` (consumers: `installer/catalog_tui.py:606`,
`installer/catalog_tui.py:621`, `installer/deps.py:154-183`, `installer/selection.py:88-118`)

**Issue:**
`CatalogScreen.__init__` is handed the **whole-catalog** installed map
(`setup.py:388` builds `{tool.id: is_installed(tool) for tool in tools}`, and
`wizard_app.py:1576-1589` passes that same map to all three tier screens while filtering only
`tools`). The new code replaces it with a **tier-filtered** map:

```python
for screen in self._catalogs.values():
    screen.set_installed({tool.id: installed(tool) for tool in screen.tools})
```

`set_installed` (`catalog_tui.py:313-332`) is a documented plain replacement, so every id
belonging to another tier is dropped. Two call sites read `self._installed` against
`self._catalog` (the **full** catalog), not against `self.tools`:

- `catalog_tui.py:604-607` -> `deps.missing_requires(... installed=self._installed)`, whose own
  docstring says it exists "so a tier-scoped view can show a cross-tier dependency at mark time".
- `catalog_tui.py:616-623` -> `selection.unstaged_recommends(... installed=self._installed)`.

Both use `installed.get(dep_id, False)`, so there is no crash — the missing key is silently read
as "not installed". Result, after any execute-screen close: marking a tool whose cross-tier
dependency is already installed raises the false notice *"mmdc also needs pnpm - added
automatically at install time"*, and already-installed cross-tier recommendations are offered
again.

The registry has ten such pairs today, verified against `installer/registry.toml`:
`oh-my-zsh(system)->git(user)`, `mmdc(user)->pnpm(system)`, `mmdc(user)->puppeteer(ai)`,
`puppeteer(ai)->pnpm(system)`, `pi(user)->pnpm(system)`, `graphify(ai)->uv(system)`,
`spec-kit(ai)->uv(system)`, `openspec(ai)->pnpm(system)`, `superpowers(ai)->pi(user)`, plus the
`claude|codex|opencode|cursor-agent (user) -> codegraph|graphify|rtk (ai)` recommends block.

Reproduced directly against the shipped code (two tools, cross-tier `requires`, one
`app._install_closed(None)` call):

```
BEFORE user._installed: {'pnpm': True, 'mmdc': True}
BEFORE missing_requires: ()
AFTER  user._installed: {'mmdc': True}
AFTER  missing_requires: ('pnpm',)
```

Why the suite misses it: all six `install_closed` tests
(`tests/test_wizard_app.py:3455-3738`) use a one-tool catalog, so the narrowed and the full map
are the same object shape.

Secondary consequence in the same block: because the key set always changes on the first call,
`set_installed`'s early return (`catalog_tui.py:328-329`) can never fire on the first close, so
its docstring claim *"No-ops when nothing changed, so the common 'nothing this run touched'
close costs no rebuild"* is false exactly when it matters.

This also violates the project rule in `.claude/architecture.md` ("Tier is a browsing label ...
The tier filter narrows what is DISPLAYED and never what is resolved").

**Fix:** derive the map once over the full catalog and hand the identical map to every screen —
same total cost (`is_installed` runs once per catalog tool), and the key set stays exactly what
the constructor established:

```python
if self._execute is not None:
    predicate = self._execute.installed
    # The catalog is tier-filtered for DISPLAY only; missing_requires /
    # unstaged_recommends resolve against the whole catalog, so the map must
    # keep every id it was constructed with.
    fresh = {tool.id: predicate(tool) for tool in self._catalog_tools}
    for screen in self._catalogs.values():
        screen.set_installed(fresh)
self._catalogs[self.current_view].enter_view()
```

(`self._catalog_tools` = the full `tools` list `__init__` already receives; any of
`self._catalogs.values()`'s `_catalog` attribute carries the same list.) Add a regression test
with two tiers and a cross-tier `requires` asserting `missing_requires` stays empty after the
close.

### CR-02: the always-on legend collapses the catalog table to 3 rows at the project's tested minimum terminal size

**File:** `installer/tool_browser.py:99`, `installer/catalog_tui.py:196-217`

**Issue:**
`#browser-legend` moved from `height: 1` to `height: auto` while `_LEGEND` grew from 155 to
**466 plain characters**. The widget is `dock: bottom`, so every wrapped line is taken out of the
`DataTable`'s `1fr`. Measured on the shipped tree with `app.run_test(size=...)`:

| size | legend height | DataTable height |
|------|---------------|------------------|
| 80x20 (project's tested minimum) | **7** | **3** |
| 100x30 | 5 | 15 |
| 120x30 | 4 | 16 |

Same measurement with the pre-phase CSS and legend at 80x20: legend 1, **table 8**. So the
catalog — the app's primary screen, listing 89 tools — loses 62% of its content area at 80x20
and shows roughly two tool rows under the column header.

Prior phases record `size=(80, 20)` as this project's tested minimum
(`.claude/.../11-03-PLAN.md:287`, `03-VERIFICATION.md:40`), and 25 existing tests run at that
size. The new legend test (`tests/test_catalog_tui.py`,
`test_legend_widget_paints_every_marker_at_full_width`) runs at `size=(100, 30)` and asserts only
that each marker is present — it cannot fail on the table being squeezed out, so nothing gates
this.

D-03 requires the legend to be visible and always-on; it does not authorize consuming a third of
an 80x20 screen. The cost is mostly the glosses, which are prose-length and partly redundant
(see WR-05).

**Fix:** cap the legend and shorten the glosses, e.g.

```css
ToolBrowser #browser-legend { dock: bottom; height: auto; max-height: 3; padding: 0 1; }
```

plus compressed entries (`checking… probing · no version unreadable · (source unknown) not
attributed · (no comparison) no latest · ~ cached latest`), and add a test at `size=(80, 20)`
asserting both that every marker paints **and** that the `DataTable` keeps a usable height
(e.g. `>= 6`).

## Warnings

### WR-01: `invalidate` failure is swallowed with no signal, unlike the precedent it cites

**File:** `installer/wizard_app.py:1871-1877`

**Issue:** `with contextlib.suppress(Exception): self._version_refresh.invalidate(...)` discards
every exception silently. The comment says it "Mirrors UpdateService's own call
(installer/update.py:436-443)", but that precedent does **not** swallow: it catches and then
*surfaces* the failure to the user (`warning = f"cache invalidation failed: {extra}"`, folded
into `outcome.detail`). Here, a failed cache rewrite means the post-close refresh silently
resolves every manager-owned tool against the pre-run inventory for up to `MANAGER_STALE_AFTER`
(6h) — the exact bug D-01 is meant to close — with nothing on screen and nothing in any log.
It also hides genuine programming errors (e.g. a future signature change to `invalidate`).

**Fix:** mirror the precedent — catch, and record the failure where the user can see it:

```python
if self._version_refresh is not None:
    try:
        self._version_refresh.invalidate(reason="install run finished")
    except Exception as exc:  # noqa: BLE001 -- post-mutation side effect
        self.screen.status.set(f"version cache invalidation failed: {exc}", "warn")
```

(or append to the run summary the way `UpdateService` appends to `outcome.detail`).

### WR-02: comments in `on_install_run_finished` describe code that is not there

**File:** `installer/wizard_app.py:1866-1875`

**Issue:** Two claims are false about the code they annotate:
- *"it is isolated in its own try/except here, structurally separate from the summary-merge
  below"* — there is no `try`/`except`; it is a `contextlib.suppress`.
- *"BLE001 (bare Exception): deliberate"* — there is no `except Exception` and no
  `# noqa: BLE001`; `contextlib.suppress` does not trigger BLE001 at all.

A reader grepping for the suppression rationale, or a future maintainer converting the block,
will be misled about which lint rule is in play and about the structure of the guard. The
SUMMARY's key-decision ("Used `contextlib.suppress(Exception)` (ruff SIM105) rather than a bare
try/except/pass") shows the comment was written for the pre-SIM105 shape and never updated.

**Fix:** delete the stale BLE001/try-except sentences (or restore the real `try/except` per
WR-01, in which case the `noqa: BLE001` becomes accurate again).

### WR-03: `self._catalogs[self.current_view]` is an unguarded `KeyError` in a screen-result callback

**File:** `installer/wizard_app.py:1858`

**Issue:** `_catalogs` is keyed by tier only (`system`/`user`/`ai`, `wizard_app.py:1576-1589`),
while `current_view` ranges over all six `VIEWS` (`doctor`, `uninstall`, `policies` included).
The in-code justification — "`ExecuteScreen` is modal: `_navigable()` returns False while it is
on top" — is about *bindings being ignored*, not about the invariant `current_view ∈ _catalogs`.
Nothing structurally prevents a future caller from pushing `ExecuteScreen` with this callback
from a non-catalog screen (the uninstall or doctor view is the obvious candidate), and a
`KeyError` raised inside a Textual screen-result callback takes down the message pump rather
than degrading.

**Fix:** fail soft, and keep the intent explicit:

```python
active = self._catalogs.get(self.current_view)
if active is not None:
    active.enter_view()
```

### WR-04: the live presence predicate is called unguarded from the callback

**File:** `installer/wizard_app.py:1855-1857`

**Issue:** `installed(tool)` is `ExecuteInputs.installed` — an injected, live-environment
predicate (default `installer.status.is_installed`, which touches PATH, `~` paths and
`/Applications`). It is invoked 89 times in a bare dict comprehension inside a screen-result
callback with no guard, while the `invalidate` call three lines below *is* guarded. Any
exception (an injected predicate raising `KeyError`, as the tests' own
`installed=lambda t: presence[t.id]` would for an unknown id; an `OSError` from a stat on a
network path) propagates out of the callback and crashes the app. Every other live core call
from a screen goes through `ui_common.run_live` per `.claude/architecture.md` rule 3 ("a failed
core action is surfaced, never a silent crash").

**Fix:** wrap the sweep so a failed presence read leaves the previous map and reports itself:

```python
fresh, error = run_live(lambda: {tool.id: predicate(tool) for tool in self._catalog_tools})
if fresh is not None:
    for screen in self._catalogs.values():
        screen.set_installed(fresh)
elif error is not None:
    self.screen.status.set(error, "warn")
```

### WR-05: the legend glosses stutter and do not match the styling of what they explain

**File:** `installer/catalog_tui.py:200-216`

**Issue:** Rendered plain text of the two label entries:

```
· checking… still checking · no version no version could be read ·
```

Interpolating the constant and then glossing it with a near-synonym produces "checking… still
checking" and "no version no version could be read", which read as duplication bugs to a user.
Separately, the two colored entries carry their real style tokens (`[green]`, `[yellow]`) but the
four dim markers are rendered in the default style while the cells render them `dim`, so the
legend does not visually match the cells it is explaining — which is also what inflates its
width (CR-02).

**Fix:** gloss without repeating the label and mark the dim entries dim, e.g.

```python
f" · [dim]{_VER_CHECKING}[/] probe in flight"
f" · [dim]{_VER_NO_VERSION}[/] nothing readable"
```

## Info

### IN-01: `_VER_*` constants are interpolated into a markup string without escaping

**File:** `installer/catalog_tui.py:196-217` (rendered at `installer/tool_browser.py:129` via
`Text.from_markup`)

**Issue:** The module comment promises "a label edit here reaches the legend automatically", but
the labels are spliced raw into a Rich markup string. A future label containing `[` (e.g.
`[deferred]`) would be parsed as a markup tag or raise `MarkupError` at compose time rather than
render literally — the same trap `ui_common._view_key` already documents and escapes for.

**Fix:** `from rich.markup import escape` and interpolate `escape(_VER_CHECKING)` etc., or build
the Ver segment as a `Text` and append it.

### IN-02: two full table rebuilds per close, with a visible wrong-label flicker in between

**File:** `installer/wizard_app.py:1854-1858`, `installer/catalog_tui.py:330-332`, `:337-348`

**Issue:** For the active tier, `set_installed` repaints (rebuild #1) and `enter_view()` ->
`_start_version_refresh()` repaints again (rebuild #2) one statement later. Between them, a row
the run just installed has a fresh `True` presence mark but no `VersionStatus` and
`version_refreshing` is still `False`, so rebuild #1 renders the affirmative `"no version"`
before rebuild #2 flips it to `"checking…"`.

**Fix:** set `version_refreshing = True` (or skip the `set_installed` repaint for the active
tier) before the presence sweep, so the first painted state of a freshly installed row is the
checking marker.

### IN-03: a pass discarded by the epoch gate leaves every row asserting "no version"

**File:** `installer/catalog_tui.py:364-372` with `:378-383`

**Issue:** `on_version_status_refreshed` sets `version_refreshing = False` *before* the epoch
check and then returns without touching `_version_statuses`. With the new `invalidate` caller
added by this phase, a refresh that started before the run finished now hits that gate, so every
installed row renders the affirmative `"no version"` (legend: "no version could be read") for the
window until the next refresh starts. Pre-phase this rendered the non-committal `"unknown"`. In
the D-01 flow `_install_closed` always starts a new refresh immediately afterwards, so the
window is transient — but the label is a claim the code has not established.

**Fix:** only clear `version_refreshing` once the pass is accepted, or re-arm a refresh when a
pass is dropped on the epoch gate.

### IN-04: "no version" is also what a catalog with no version service shows forever

**File:** `installer/catalog_tui.py:378-383`

**Issue:** When `version_refresh is None`, `_start_version_refresh` returns immediately,
`version_refreshing` stays `False`, and `_version_statuses` stays empty, so every installed row
renders `"no version"` permanently — an affirmative statement about a probe that never ran. The
comment on the branch only reasons about the crashed-worker case. Production always wires a
service (`setup.py:610`), so this is limited to the non-`setup.py` construction sites.

**Fix:** treat "no service configured" as its own (empty) cell, or reuse the neutral wording for
`status is None and self._version_refresh is None`.

### IN-05: new async tests poll with large `pilot.pause()` loops and assert on worker threads

**File:** `tests/test_catalog_tui.py` (`test_ver_cell_dim_checking_marker_reaches_the_rendered_table`,
`test_refresh_cursor_survives_both_repaints_of_one_cycle`)

**Issue:** Both use `for _ in range(400..500): await pilot.pause()` spin loops plus
`assert release.wait(timeout=5)` executed **inside** `resolve_tag`/`probe_output`, i.e. on the
`@work(thread=True, exit_on_error=False)` worker thread. An `AssertionError` there is swallowed
by the worker, so a real timeout on a loaded CI box surfaces as a confusing downstream assertion
(`cursor_row == started_row` / `"checking…"`) instead of the actual cause. The inline comments
correctly explain *why* blocking waits were replaced by polling, but not this failure mode.

**Fix:** have the worker-side helper record the timeout into a shared list and assert it from the
test coroutine after the polling loop, and give the loops a wall-clock deadline rather than a
fixed iteration count.
