# Phase 15.1: Catalog post-update refresh staleness and version-status color disambiguation - Context

**Gathered:** 2026-09-15
**Status:** Ready for planning

<domain>
## Phase Boundary

After `ExecuteScreen` closes (install/update run finished), `CatalogScreen` must reflect
the real, current state of every tool it shows — without requiring the user to navigate
away from and back into the tab. Separately, the version column's color/text states
(green/orange/gray, plus the stale-cache `~` suffix) must each be distinguishable, backed
by a visible, always-on legend explaining what every state means. This phase does not
touch update *execution* logic (already correct, per this session's investigation) — only
the catalog's own rendering/refresh of what it already knows.

</domain>

<decisions>
## Implementation Decisions

### Post-update refresh scope
- **D-01:** When `ExecuteScreen` closes, `wizard_app.py`'s `_install_closed` callback
  (currently `wizard_app.py:1833`, only clears `self._staged`) must also trigger a full
  refresh of the active catalog tab — call the equivalent of `enter_view()`/
  `_start_version_refresh()` on the tab that was active before the install/update ran, not
  a narrower per-tool refresh limited to the ids that were part of that run. — **Reversibility:**
  reversible — narrowing to a per-tool refresh later is a local change to one callback.
  **Rationale (user):** simpler and more robust against edge cases like a dependency
  drag-in that also changed state — worth the extra re-probe cost over the precision of a
  per-tool-only refresh.

### Gray-state disambiguation
- **D-02:** The four gray-producing `VersionStatus` situations (`_ver_cell`,
  `catalog_tui.py:299-323`) get distinct **text**, not new colors: "not tracked for
  updates" (today's `latest is None` branch, e.g. dnf-owned tools) gets a stable marker
  like `(unmanaged)`; "no data yet / still probing" and "unparseable version"
  (`status is None` / `outdated is None`) get an in-progress-style marker like `…` or
  `(unknown)` — exact wording is Claude's discretion at planning time, as long as each of
  the four cases is texually distinguishable from the others. — **Reversibility:**
  reversible.
  **Rationale (user):** avoids introducing new colors that would need to work across
  light/dark themes and constrained terminals; a legend explaining specific text labels is
  simpler to build and to keep accurate than a growing color palette.

### Color/state legend
- **D-03:** A visible, **always-on** legend line lives in the footer/status bar area,
  present across all three top-level views (System/User/AI) without requiring any toggle
  or keypress to reveal — not a help-screen or `?`-triggered overlay. It must cover: green
  (up to date), orange (update available), and each distinct gray-state label from D-02,
  plus the stale-cache `~` suffix (D-04). — **Reversibility:** reversible.
  **Rationale (user):** discoverability was the entire complaint — a toggle just relocates
  the same "how would I know to press this" problem the colors already have.

- **D-04:** The stale-cache `~` suffix (appended today whenever `VersionStatus.stale` is
  true, orthogonally to the outdated/unmanaged/unknown states) gets its own legend entry
  too — it is exactly the kind of "symbol that doesn't explain itself" the user flagged.
  — **Reversibility:** reversible.

  **Interpretation (added 2026-09-16, after cross-AI plan review round 1, `6c2dd1f`):**
  the parenthetical above is **wrong about the code it describes**, and the normative
  clause is the rest of the sentence. The suffix is assembled at
  `installer/catalog_tui.py:319-323`, *after* the `outdated is True` / `outdated is False`
  branches have set `base`; every dim branch returns before reaching it. So the suffix is
  not orthogonal to the other states today and must not be made so:
  - `resolve_status` hardcodes `stale=True` on **every** path that yields `latest=None`
    (`installer/version_status.py:269`, `:290`, `:332`), so an unconditional suffix would
    appear on substantially every dim cell at all times and would distinguish nothing.
  - The suffix's meaning is a claim about a latest value the cell rendered — "the latest
    shown here came from a cache entry this pass did not re-confirm"
    (`installer/catalog_tui.py:319-320`). A dim cell shows no latest, so on a dim cell the
    claim has no referent and reads as a cached-latest gloss that does not apply.
  - The current scope is already pinned by an anti-regression assertion:
    `tests/test_catalog_tui.py:1073-1077` asserts a `stale=True` status with
    `installed=None` renders **no** ` ~`. The unconditional reading would require deleting
    it.

  **What D-04 therefore requires, and what it does not.** Requires: the ` ~` character has
  its own always-on legend entry (D-03's legend), glossed as what it actually marks — a
  *shown* latest that was not re-confirmed — not as a property of the row or the tool.
  Does not require: appending it to the dim branches. No information is lost by that
  scope, because the situation it would have flagged there (a latest lookup that failed,
  was budget-deferred, or never had a source) is stated in words by the "no comparison"
  dim label and its own legend entry. `15.1-01-PLAN.md` turns this scope from an accident
  of early returns into a named, test-protected property. `15.1-RESEARCH.md:197-199`
  repeats the same mistaken description and is superseded by this note.

### Claude's Discretion
- Exact wording/labels for each gray-state marker (D-02) and the legend's phrasing —
  as long as every rendered state (green, orange, each gray case, and the `~` suffix) has
  a corresponding, findable legend entry.
- Whether the refresh triggered by D-01 shows any loading indicator on the catalog tab, or
  happens silently the same way `enter_view()` already does today for a normal tab switch.
- Exact placement/formatting of the legend line within the existing footer/status-bar
  layout (single line vs wrapped, ordering of entries).

### Folded Todos
None — the one todo matched by `todo.match-phase` (`2026-09-11-remove-orphaned-tool-post-install-plural-field.md`)
is now stale/obsolete (see Deferred Ideas) and was not folded.

- `CatalogScreen.enter_view()` / `_start_version_refresh()` (`catalog_tui.py:264-268`) —
  the exact refresh mechanism already exists and is proven (fires on mount and explicit
  tab entry); D-01 only needs to call it from one more call site.

  label differently — no new data/schema needed, only the rendering in `_ver_cell`.

  app (per Phase 13's screen-stack work) — the legend (D-03) should follow that existing

- `DoctorScreen`'s own post-fix refresh fix (Phase 15, D-01/D-02) is a directly analogous
  precedent: same bug class (a screen not re-reading fresh state after an action closes),
  same phase family — worth reading that plan/summary for the concrete refresh-call
  pattern used there.

### Integration Points
- `wizard_app.py`'s `_install_closed` is the single integration point for D-01 — it
  already has a reference to the app and its active catalog screens via the same
  mechanism `on_catalog_screen_decided` uses.
- `_ver_cell` in `catalog_tui.py` is the single integration point for D-02 — purely a
  rendering change, no upstream data plumbing needed.

<specifics>
## Specific Ideas

The user's own words (translated): they want a legend that explains "los grises
ambiguos, verdes y naranjas, o si hay algo más raro que no se explique solo" (the
ambiguous grays, greens and oranges, or anything else weird that doesn't explain itself)
— this directly motivated including the stale `~` marker (D-04) even though it wasn't
one of the four original gray cases, since it is exactly this kind of "something else
weird."

</specifics>
