  <name>Task 1: Bootstrap a long-lived, non-root, Homebrew- and uv-capable Fedora-family container</name>
  <precondition>scripts/detect-container-runtime.sh (12.3-01) exists and reports a working container tool on this host.</precondition>

  <action>
Create `scripts/container-e2e-verify.sh`. First line of real logic: source
the detection result via `eval "$(scripts/detect-container-runtime.sh)"` —
if that fails (non-zero exit), propagate the failure immediately and stop;
never fall back to running anything on the host.

Start ONE detached, named container from a Fedora-family base image (D-05:
Fedora-family only this phase — no debian/arch/ubuntu image):
`$CONTAINER_TOOL run -d --name tools-installer-e2e-12-3 -v "$PWD":/repo:ro,Z
fedora:latest sleep infinity`. The repo mount is READ-ONLY and `sleep
infinity` keeps this ONE container alive across every subsequent `exec` call
this plan and Plan 12.3-03 make into it — this is what makes Plan 12.3-03's
rerun pass a genuine test of previously-installed state instead of a second
clean container mislabeled as a rerun (12.3-CONTEXT.md's Claude's Discretion
note). Record the resolved Fedora version (`$CONTAINER_TOOL exec
tools-installer-e2e-12-3 cat /etc/fedora-release`) for reproducibility.

Then, via `$CONTAINER_TOOL exec tools-installer-e2e-12-3 ...` calls only
(never a bare host command):

1. As root: `dnf install -y` the documented Homebrew-on-Linux prerequisites
   — the `Development Tools` group plus `procps-ng curl file git tar which
   sudo ca-certificates`.
2. Create a non-root user (`useradd -m tester`) with passwordless sudo via a
   dedicated `/etc/sudoers.d/tester` file (`tester ALL=(ALL) NOPASSWD:ALL`)
   — required because Homebrew's official installer refuses to run as root.
3. Pre-create `/home/linuxbrew/.linuxbrew` and `chown -R tester` it, so
   Homebrew's own installer needs no interactive sudo prompt when it runs as
   `tester`.
4. As `tester` (`su - tester -c '...'`, NEVER with an allocated pseudo-TTY —
   no `-it`/`-t` on any of these exec calls, so `sys.stdin.isatty()` is
   False for every later `uv run setup.py` call and the CLI takes its
   non-interactive branches): copy `/repo` (the read-only mount) into
   `/home/tester/workspace` with `cp -r` — this is the ONLY copy anything
   in this container ever writes to, never the mounted path; bootstrap
   Homebrew non-interactively (`NONINTERACTIVE=1 /bin/bash -c "$(curl -fsSL
   https://raw.githubusercontent.com/Homebrew/install/HEAD/install.sh)"`);
   bootstrap `uv` via its official installer and add it to `tester`'s PATH
   (append the shellenv line to `~/.bashrc` for `tester`, then source it for
   this and every later exec); `cd /home/tester/workspace && uv sync`.
5. Confirm readiness: `uv run python -c "import installer"` succeeds as
   `tester` inside `/home/tester/workspace`. Print
   `TRACER_HARNESS_READY_OK` only once this succeeds.

Homebrew's own bootstrap (step 4) can take several minutes on a fresh
container with a cold formula cache. If a foreground call risks the
invoking agent's own tool-call timeout ceiling, run steps 4-5 via the same
background-execution discipline Task 2 below uses (redirect output to a
bootstrap log, launch via `run_in_background`-equivalent semantics, poll the
log for `TRACER_HARNESS_READY_OK` rather than blocking in the foreground).
  </action>

  </verify>

formulae potentially building from source, plus GitHub-release, npm/pnpm,

explicitly raised). Addresses review concern (12.3-REVIEWS.md HIGH,
12.3-02): do NOT run this pass as a single blocking foreground call. Launch
`$CONTAINER_TOOL exec tools-installer-e2e-12-3 su - tester -c "cd
/home/tester/workspace && uv run setup.py --all --yes"` as a background
process — redirect its full stdout/stderr verbatim into
`.planning/phases/12.3-container-e2e-verification-of-the-reconciled-branch-real-end/pass1-transcript.log`
and start it via the invoking agent's background-execution facility (the
Bash tool's `run_in_background: true`, or `nohup ... > pass1-transcript.log
2>&1 & disown` if driving a raw shell) so the launching call returns
immediately instead of blocking for the run's full duration. Poll
`pass1-transcript.log` for `TRACER_CLEAN_INSTALL_OK` or the process's exit
every few minutes rather than in a tight loop — treat 30-45 minutes of wall
time on a cold Homebrew/formula cache as plausible and NOT itself a failure
signal; state the actual wall time observed in the task's own commit
message/SUMMARY. If, after a generous stated budget, the log has produced no
new output for an extended period and the process is gone, treat it as
genuinely stalled/killed and investigate rather than assuming success. If a
single `--all --yes` call repeatedly proves impractical to complete this
way, fall back to chunking via the CLI's own, already-real `--categories
<name>[,<name>...] --yes` flag (`installer/cli.py`'s existing mechanism, not
a new one this plan invents) — run one category or a small batch per
background call, appending each call's output to the same transcript, so no
single call risks the timeout ceiling; the aggregate across all calls still
covers the FULL catalog per D-04, it is just partitioned across multiple
non-blocking calls instead of one.

This is the exact non-interactive entrypoint the Makefile's own
`ARGS="--all --yes"` convention documents — do NOT scope this to only the
reconciliation's own diff; D-04 requires the FULL catalog, whether run as
one call or chunked into several. `installer/render.py`'s `render_summary`
prints one deterministic line: `Installed: N  Already: N  Failed: N
Dependency failed: N  Checksum mismatch: N  No method: N  Manual setup
required: N` — parse those counts (summed across calls if chunked).

`No method` and `Manual setup required` are expected to be nonzero (e.g.
every macOS-only entry, and any `host_setup`/`skill_pack` handoff tool, on a
Linux container) and are acceptable as-is. `Failed`, `Dependency failed`,
and `Checksum mismatch` must each be 0, or every single one of them must be
individually investigated: if it traces to a real installer bug (not a
genuine, explainable platform/network limitation — e.g. a formula genuinely
absent on Linux, a network timeout worth retrying once), fix the bug on the
host in `installer/` with a regression test FIRST (red), then the fix
(green), following this project's existing TDD discipline. Addresses review
concern (12.3-REVIEWS.md HIGH, 12.3-02/12.3-03): before re-running, re-sync
the fix into the container's writable workspace copy — the container's
`/home/tester/workspace` was populated ONCE at bootstrap (Task 1) and is
never touched again by anything except an explicit re-sync, so a host-side
fix does not reach the container on its own. Run `$CONTAINER_TOOL exec
tools-installer-e2e-12-3 su - tester -c 'cp -r /repo/. /home/tester/workspace/'`
(the read-only `/repo` mount is always the source of truth for this re-sync;
never treat the container's own prior in-place copy as authoritative) before
re-running this task's Pass 1 sequence — then re-run it (via the same
background-execution discipline above) until the failure is gone or is
recorded as a genuine, explained platform limitation in this task's own
commit message/SUMMARY — never silently ignored. Confirm `make validate &&
make test` still passes on the host after any such fix.

Print `TRACER_CLEAN_INSTALL_OK installed=<n> failed=<n> no_method=<n>
manual_required=<n>` once the pass completes with `failed=0`,

individually explained in the commit message).

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Host filesystem <-> long-lived container | The container's only host contact is a read-only repo mount; everything it writes lands in its own filesystem. |
| Container root <-> container non-root `tester` | Root is used only for prerequisite installs, user creation, and directory ownership; every install/uninstall command in this and the following plan runs as the unprivileged `tester` user. |
| Internet <-> container | Homebrew's installer, uv's installer, and up to ~90 catalog tools' own upstream sources (GitHub releases, Homebrew formulae, sdkman, npm/pnpm registries) are fetched over the network from inside the container. |
