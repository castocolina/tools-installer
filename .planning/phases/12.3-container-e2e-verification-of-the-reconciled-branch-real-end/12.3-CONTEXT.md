# Phase 12.3: Container E2E Verification of the Reconciled Branch - Context

**Gathered:** 2026-09-10
**Status:** Ready for planning

<domain>
## Phase Boundary

Real, container-based end-to-end verification of the reconciled branch's
full catalog (~90+ tools) — a clean install pass across the whole
`registry.toml`, followed by a rerun exercising install/uninstall/reinstall,
inside a disposable Fedora-family container (closest match to this dev
host's Bazzite). This is real-machine-effect verification (Tier 3 in origin's
own terminology) — the kind Tier 1 (`make test`, isolated `HOME`) and Tier 2
(`tmux` structural TUI checks) cannot prove: a real filesystem, real package
managers, real shell-rc rewrites, inside a disposable, real container.
Depends on Phase 12.1 (merge verification) and ideally Phase 12.4 (the
rtk/graphify postinstall gap should be closed before this phase measures it)
being done first, though this CONTEXT.md's decisions stand regardless of
execution order.

</domain>

<decisions>
## Implementation Decisions

### Container tooling — platform-aware detection
- **D-01:** Detect the host platform and pick the container tool
  automatically, not hardcode one option — **Reversibility:** reversible.
  - **Linux (this dev host, Bazzite amd64):** `podman` — already installed
    natively (`podman 5.8.4` confirmed present), no VM layer needed.
  - **macOS (Intel or ARM):** follow origin's own documented convention from
    `.planning/ONESHOT-RULES.md` Rule 14 — `colima` + the `docker` CLI.
    Origin found live on an Intel Mac that `podman`'s Homebrew formula pulls
    in an Apple-Silicon-only dependency (`vfkit`) and fails to build; this
    decision does not re-litigate that finding, it reuses it. Whether that
    same podman-on-ARM-Mac limitation still holds is NOT assumed — if a
    future ARM Mac run finds podman works there, that's a research-time
    finding, not something decided here.
  - The detection logic must be OS/arch-aware in general (developers use
    Linux amd64 or macOS Intel/ARM as dev machines, and the target runtime
    matrix — Phase 12.3's Fedora-family container — is a separate axis from
    the host running the container).

### Container tooling — reusability and fallback
- **D-02:** The platform/tool detection is NOT single-use logic for this
  phase — it ships as a reusable script (e.g. `scripts/`) any future e2e
  phase can invoke. **Reversibility:** reversible.
- **D-03:** If neither the platform's expected tool (podman on Linux,
  docker+colima on macOS) nor a working alternative is found, the plan must
  surface an interactive choice (AskUserQuestion-equivalent for whatever
  agent runs this phase) offering: install the missing tool inline, print
  manual install instructions, or bypass the e2e check for this run — never
  silently skip or silently fall back to testing against the real host.
  **Reversibility:** reversible.

### Verification scope — full catalog, two passes
- **D-04:** Do NOT scope this down to only the reconciliation's own diff
  (host_setup/skill_lifecycle, remapped tiers, Phase 12.4's rtk/graphify
  work). Run the full `registry.toml` catalog (~90+ tools) inside the
  container, in two passes:
  1. **Clean install pass** — every tool, fresh container, install path only.
  2. **Rerun pass** — install/uninstall/reinstall cycles, to catch
     idempotency bugs (a tool that installs clean but breaks on a second
     run, or an uninstall that leaves stray state a reinstall then trips
     over) — the class of bug a single clean-install pass cannot surface.
  **Reversibility:** reversible — this is a verification run, not a
  production commitment; a future phase can narrow scope if the full-catalog
  run proves too slow to repeat regularly.

### Base image matrix
- **D-05:** Fedora-family only for this phase, not debian/arch/fedora — the
  closest match to this dev host's actual distro (Bazzite is Fedora-based).
  Debian/arch coverage is explicitly deferred, not decided to be
  unnecessary — narrowed for this phase's scope only. **Reversibility:**
  reversible — a future phase can add the other two images using the same
  reusable detection/harness this phase builds.

### Evidence format
- **D-06:** Follow origin's own Tier-3 evidence convention from
  `.planning/ONESHOT-RULES.md` Rule 14 — tracer markers (e.g.
  `TRACER_<NAME>_OK`) captured from real command output/file diffs, folded
  into a phase-end report — for consistency with the rest of the milestone's
  `.planning/RUN-REPORT.md`, in case the two lines of work are ever compared
  or merged. **Reversibility:** reversible.

### Claude's Discretion
- Exact script location/name for the platform-detection helper (D-02) —
  planner's call, following this project's existing `scripts/` conventions
  (e.g. `scripts/prune-user-tmpdir.sh`'s style).
- Whether the two-pass run (clean + rerun) needs one container per pass or
  can reuse the same container for both — implementation detail, as long as
  the rerun genuinely exercises a previously-installed state (not a second
  clean container mislabeled as a rerun).

</decisions>
