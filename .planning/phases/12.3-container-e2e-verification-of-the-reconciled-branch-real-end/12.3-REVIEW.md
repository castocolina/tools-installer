Reviewed the cumulative diff for Phase 12.3 (`f44e9fb~1..522c192`): the four real

`engine.py` PATH re-export, `registry.toml` pnpm `bin_dir`, `render.py`

(`.planning/phases/12.3-.../12.3-02-SUMMARY.md`, `host-attestation.log`) — no
regressions found in either.

Two BLOCKER-level issues were found that were *not* caught by the container run
or the new unit tests, both directly relevant to the areas this review was asked
to focus on:

1. **`render_failure_details` (installer/render.py) is not markup-safe.** Any
   captured exception whose message contains a lowercase-leading bracketed
   substring (extremely common in real package-manager/curl/npm output — e.g.
   `[self-signed certificate in certificate chain]`, `[not-supported]`,
   `[deprecated]`) is silently swallowed by Rich's markup parser instead of
   being printed. This was verified by direct execution, not just inspection —
   see CR-01. It defeats the exact goal this function was added for ("a bare
   'failed' is never the last word an operator sees").
2. **`scripts/container-e2e-verify.sh` has an unsanitized shell-injection path**
   through `pass1 --categories <value>`, which is embedded unescaped into a
   multi-line command string executed via `su -c` inside the container. See
   CR-02.

## Critical Issues

### CR-01: `render_failure_details` silently truncates/erases failure text containing lowercase-bracketed substrings (Rich markup injection)

**File:** `installer/render.py:72-84` (also exercised via `installer/app.py:159-160`)

**Issue:** `render_failure_details` interpolates the raw exception (`detail =
outcome.errors[-1]`, a `CommandError`/`ExecutorError`/`VersionError`/
`ChecksumMismatch`) directly into an f-string passed to `console.print()`, which
has Rich markup parsing enabled by default (`Console()` has `markup=True`
unless overridden — confirmed via `setup.py:564`, `console = Console()`).
`CommandError.__str__` includes raw subprocess `detail`/stderr text
(`installer/run.py:24-35`), which routinely contains bracketed diagnostic
substrings from real tools (curl SSL errors, npm/pip warnings, etc.).

Verified live against the installed Rich version (15.0.0) in this repo's own
venv:

```
>>> console.print(f'[red]tool failed: {"curl: (60) SSL: [self-signed certificate in certificate chain]"}[/]')
'tool failed: curl: (60) SSL: \n'          # message silently truncated
>>> console.print(f'[red]tool failed: {"npm ERR! [not-supported] Unsupported"}[/]')
'tool failed: npm ERR!  Unsupported\n'     # bracketed detail silently erased
```

Any lowercase-leading bracket run (`[a-z#/@]...`) is treated as a Rich style
tag; since it does not resolve to a real style, Rich drops the "tag" and
everything between it and the next closing tag disappears from the rendered
output — with no exception raised, so nothing signals that data was lost. This
directly undermines the function's own stated purpose ("so a bare 'failed' is
never the last word an operator sees") and could re-hide exactly the class of
diagnostic detail this phase's container run needed to find the puppeteer/pnpm
bug in the first place.

None of the three new tests in `tests/test_render.py`
(`test_render_failure_details_prints_the_error`,
`test_render_failure_details_is_silent_when_nothing_failed`,
`test_render_failure_details_falls_back_without_a_captured_error`) use a
message containing brackets, so this regression is untested.

**Fix:**
```python
from rich.markup import escape

def render_failure_details(outcomes: list[InstallOutcome], console: Console) -> None:
    for outcome in outcomes:
        if outcome.status is not InstallStatus.FAILED:
            continue
        detail = outcome.errors[-1] if outcome.errors else "no method succeeded"
        console.print(f"[red]✗ {outcome.tool_id} failed: {escape(str(detail))}[/]")
```
Add a regression test asserting a bracketed message (e.g.
`RuntimeError("curl: [self-signed certificate in certificate chain]")`) is
printed verbatim, not truncated.

### CR-02: Command injection via unsanitized `pass1 --categories <value>` in `scripts/container-e2e-verify.sh`

**File:** `scripts/container-e2e-verify.sh:229-241` (`run_setup_as_tester`) and
`scripts/container-e2e-verify.sh:287-329` (`cmd_pass1`'s categories parsing/loop)

**Issue:** `cmd_pass1` accepts a free-form `--categories NAME[,NAME...]` value
from the script's own CLI (line 289: `categories="${2:-}"`). Each trimmed token
`cat` is passed straight into:

```bash
run_setup_as_tester "--categories ${cat} --yes" > "$tmp" 2>&1
```

`run_setup_as_tester` builds a **double-quoted** (host-shell-interpolated)
multi-line string with `${args}` spliced in literally:

```bash
exec_tester "set -euo pipefail
...
uv run setup.py ${args}
"
```

and `exec_tester` forwards that whole string as the single `-c` argument to
`su - tester -c "$1"` inside the container, which the container's login shell
then *parses and executes as a script*. Because `${args}` (and thus `${cat}`)
is embedded unescaped, any shell metacharacter in a category value — `;`, `` ` ``,
`$(...)`, `&&`, `|` — is interpreted by the container's shell, not treated as a
literal argument to `setup.py`. Example:

```bash
scripts/container-e2e-verify.sh pass1 --categories 'devtools;touch /tmp/pwned'
```

produces the executed script line `uv run setup.py --categories
devtools;touch /tmp/pwned --yes`, which runs `uv run setup.py --categories
devtools` and then separately executes `touch /tmp/pwned` as `tester` — who has
passwordless `sudo ALL` inside the container (`create_tester`,
`scripts/container-e2e-verify.sh:129`). This is textbook shell/command
injection (classified Critical per this review's rubric) even though the
current blast radius is limited to the disposable container the harness itself
creates and tears down; it stops being "limited" the moment `--categories` is
ever driven by anything less trusted than a developer's own keyboard (CI
parameter, generated from a PR label, etc.), and it undermines a script whose
entire purpose is producing trustworthy pass/fail evidence.

**Fix:** validate every category token against an allowlist before use, and/or
avoid re-interpolating it into a shell string:
```bash
_valid_category() {
  [[ "$1" =~ ^[a-z0-9_-]+$ ]]
}
...
for cat in $categories; do
  cat="${cat#"${cat%%[![:space:]]*}"}"
  cat="${cat%"${cat##*[![:space:]]}"}"
  [[ -n "$cat" ]] || continue
  _valid_category "$cat" || die "invalid category: $cat"
  ...
done
```
(Registry categories are a small closed set — `category = "..."` values in
`installer/registry.toml` — so an allowlist regex is cheap and correct here.)

## Warnings

### WR-01: `prepend_path` runs after the tool's own `postinstall` hook, not before

**File:** `installer/engine.py:146-154`

**Issue:** On success, `run_postinstall(...)` (line 149) executes *before*
`prepend_path(bin_dir(raw_bin_dir))` (line 154). The one hook that exists today
(`_codegraph_mcp_register`, `installer/postinstall.py:40-110`) sidesteps this by
invoking the binary via its resolved absolute path rather than relying on
process `PATH`, so there is no active bug — but the ordering is a latent trap:
any future `postinstall` hook that expects to find its *own* tool's
freshly-installed binary via `PATH`/`shutil.which` (rather than an explicit
`bin_dir(...)` path) will silently fail, exactly the class of bug this phase
just spent effort diagnosing for puppeteer/pnpm across *different* tools.

**Fix:** Move the `prepend_path` call above the `postinstall` dispatch so a
hook for the *same* tool also benefits from the PATH visibility fix:
```python
raw_bin_dir = method.params.get("bin_dir")
if isinstance(raw_bin_dir, str) and raw_bin_dir:
    prepend_path(bin_dir(raw_bin_dir))
warning = None
if tool.postinstall:
    try:
        warning = run_postinstall(tool.postinstall, method, runner, tools or {})
    except Exception as exc:  # noqa: BLE001
        warning = f"postinstall hook {tool.postinstall!r} crashed: {exc}"
```

### WR-02: Same markup-injection class already exists in `render_verification`'s CHECKSUM_MISMATCH line

**File:** `installer/render.py:224`

**Issue:** `console.print(f"  {outcome.tool_id}: {outcome.errors[0]}")` inside
`render_verification` interpolates a raw `ChecksumMismatch` (or other captured
exception) the same unescaped way as CR-01, and is explicitly called out in
`render_failure_details`'s own docstring as the pattern it "mirrors." This line
predates this diff, so it's not newly introduced, but it shares the exact
vulnerability class as CR-01 and should be fixed in the same pass rather than
left as the one remaining unescaped exception-interpolation site.

**Fix:** Apply the same `rich.markup.escape()` wrap as CR-01's fix.

### WR-03: Fixed `COLUMNS=200` can still truncate very long dependency/manual-required lines

**File:** `scripts/container-e2e-verify.sh:231-241` (`run_setup_as_tester`),
`scripts/container-e2e-verify.sh:258-261` (`accumulate_summaries`'s
`grep -E '^⚠ .+ skipped — dependency failed: '` / `'^  manual setup required: '`
capture)

**Issue:** `COLUMNS=200` was added specifically to stop Rich's non-tty
`Console` (default width 80) from wrapping `render_summary`'s one-line output
across two physical lines, which this phase's own investigation found was
silently zeroing every parsed count. The same class of line-wrap can still
recur for `render_skipped`'s `"... skipped — dependency failed: A, B, C, ..."`
line or `render_handoff`'s tool-id line once the joined tool-id list exceeds
~200 columns (a real possibility as the registry grows — the catalog already
has ~90 tools). Because `accumulate_summaries` captures these lines with a
single-line `grep -E '^...'` pattern, a wrapped line would be silently
truncated, and `dependency_failures_explained` (line 268-283) would then
conservatively treat a legitimately-explained dependency chain as
"not explained," turning a clean pass into a false `TRACER_CLEAN_INSTALL_INCOMPLETE`.
Fails safe (stricter, not looser) today, but it is the same bug class the
phase already had to hunt down once.

**Fix:** Raise `COLUMNS` further (e.g. 1000) or, more robustly, have
`render_skipped`/`render_handoff` join tool-id lists in a way `grep` can match
regardless of Rich's wrap width (e.g. an env-var/flag that disables Rich
soft-wrap entirely for non-interactive output).

### WR-04: New `render_failure_details` tests don't exercise markup-special characters

**File:** `tests/test_render.py:108-129`

**Issue:** All three new tests use plain messages (`"network unreachable"`,
`"no method succeeded"`) with no `[`/`]` characters, so none of them would have
caught CR-01. Given how common bracketed diagnostic text is in real
package-manager output, this is a meaningful coverage gap for a function whose
entire job is to surface arbitrary third-party error text.

**Fix:** Add a test asserting a message like
`RuntimeError("curl: [self-signed certificate in certificate chain]")` is
printed in full (not truncated) by `render_failure_details`.

## Info

### IN-01: `rcclean.py`'s indentation skip is a deliberate, documented false-negative tradeoff

**File:** `installer/rcclean.py:82-96`

**Issue:** Any `PATH=`/`export PATH=` line that starts with a space or tab is
now *never* a strip candidate, even outside a control-flow block (e.g. a
manually-indented top-level PATH line that duplicates a managed dir). This is
intentional and well-reasoned (documented in the surrounding comment and
`12.3-02-SUMMARY.md`'s key-decisions: correctness of not corrupting rc files
outweighs completeness of duplicate removal), and the false-positive direction
(never wrongly *flags* something it shouldn't) was verified correct by tracing
`_PATH_EXPORT`/`line[:1]` against the pnpm case-guard test and the new
if-block regression test. Noting this only so the accepted completeness
trade-off is visible in review, not as something requiring a code change.

### IN-02: `render_failure_details` can surface local absolute paths / full command lines

**File:** `installer/render.py:72-84`, `installer/run.py:24-35`

**Issue:** `CommandError.__str__` includes the full `' '.join(cmd)` argv,
which can contain local absolute paths (e.g. `~/.local/bin/...`) or the
invoking username via `$HOME`-derived paths. No secrets/tokens were found
flowing through any subprocess argv in this codebase (`grep` for
`Authorization|Bearer|-u user:pass` in `installer/*.py` and
`registry.toml` was empty), so this is not an active leak today — but if any
future method adds an authenticated download (private registry, token-bearing
URL), this render path would echo it straight to the console/transcript with
no redaction. Worth keeping in mind rather than an active fix.
