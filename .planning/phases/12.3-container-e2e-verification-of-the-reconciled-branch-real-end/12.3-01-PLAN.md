Create `scripts/detect-container-runtime.sh`: bash, `set -euo pipefail`, following
`scripts/prune-user-tmpdir.sh`'s existing style (a `usage()` heredoc reachable via
`-h`/`--help`, explicit flag parsing, coreutils-only dependencies, no non-stdlib
tooling). Its job is exactly D-01/D-02: detect the host OS via `uname -s`
(Darwin -> macos, Linux -> linux) and arch via `uname -m` (mirroring
`installer/platform.py`'s amd64/arm64 mapping), then pick and verify a real,
working container tool — never just check that a binary exists on PATH.

On Linux: look for `podman` via `command -v`. If found, prove it actually
works by running one real disposable container (e.g.
`podman run --rm docker.io/library/alpine:latest true`) — a `--version` check
alone is not proof. If podman is missing or that live run fails, check for a
working `docker` as the alternative (same live-run proof) before declaring
failure — D-03 requires exhausting "a working alternative", not just the
platform's single expected tool.

On macOS: look for `colima` and `docker` via `command -v`. If both exist but
`colima status` reports not running, start it with `colima start` — this is
normal Tier-3 operation per ONESHOT-RULES Rule 14, not a D-03 failure case —
then prove it with a real `docker run --rm docker.io/library/alpine:latest
true`. If colima is entirely absent, check for a working `podman` as the
alternative before declaring failure (D-01 does not assume podman-on-Mac is
permanently broken — only that origin found it broken on one Intel Mac
specifically; a future host may resolve differently, so the script tests
live rather than hardcoding the old finding as a permanent rule).

When the platform's expected tool is entirely absent AND no working
alternative was found either: the script MUST NOT proceed, MUST NOT invoke
any `podman`/`docker`/`colima` mutating command, and MUST NOT fall back to
running anything on the host. It prints, verbatim, the three D-03 options —
"1) install the missing tool inline  2) print manual install instructions
3) bypass the e2e check for this run" — on stderr, and exits with code 3.
Any task that invokes this script and sees exit code 3 must stop immediately
and surface those three options to the user (via AskUserQuestion or the
calling agent's equivalent interactive-choice mechanism) rather than
proceeding — this is the behavior Task 2 below proves.

On success the script prints exactly one line to stdout —
`CONTAINER_TOOL=podman` or `CONTAINER_TOOL=docker` — and exits 0, so a caller
can do `eval "$(scripts/detect-container-runtime.sh)"` to capture
`$CONTAINER_TOOL`.

Then, using the detected `$CONTAINER_TOOL`, prove the whole pipeline
end-to-end on exactly one real, network-cheap, checksum-verified catalog
tool: `wezterm`. `installer/registry.toml`'s `wezterm` entry resolves on
Fedora/amd64 to a `github_release` method (a checksum-verified AppImage,
`raw=true`) — no Homebrew, no sudo, no non-root user needed, the thinnest
possible real install path (already proven live in a Tier-3 container during
Phase 7). Run ONE disposable container:
`$CONTAINER_TOOL run --rm -v "$PWD":/repo:ro,Z fedora:latest bash -c '...'`
— the repo is mounted READ-ONLY (`:ro,Z` for SELinux) so nothing that runs
inside can write back into the host's real source tree. Inside the
container: `dnf install -y curl tar git ca-certificates python3`, `cp -r
/repo /workspace && cd /workspace`, bootstrap `uv` via its official installer
(`curl -LsSf https://astral.sh/uv/install.sh | sh`, then add `uv` to PATH),
`uv sync`, then run a one-line `uv run python -c` snippet that: imports
`installer.model.load_tools`, `installer.platform.detect`,
`installer.engine.install_tool`, `installer.enums.InstallStatus`; loads
`installer/registry.toml` via `load_tools`; builds `tools_by_id = {t.id: t
for t in tools}`; finds the `wezterm` Tool; calls
`install_tool(tools_by_id["wezterm"], detect(), tools=tools_by_id)` for
real; asserts `outcome.status == InstallStatus.INSTALLED` and
`outcome.verified is True`; and only then prints
`TRACER_WEZTERM_INSTALL_OK`. Record the resolved `fedora:latest` image
version (e.g. `cat /etc/fedora-release` inside the container) in the task's
own commit/SUMMARY for reproducibility, since `latest` is not itself a
pinned reference.

Installing `python3` via `dnf` above is a deliberate offline-fallback net:
without a system interpreter present, `uv sync` depends on fetching a
managed CPython interpreter from `python-build-standalone` over the network
(uv's default behavior when no system interpreter is found) — an additional
outbound-network dependency beyond wezterm's release asset and uv's own
installer script. Name this dependency explicitly in the task's own
commit/SUMMARY, so a future host with restricted egress to that CDN has a
named failure mode to check against (and, with `python3` present, `uv sync`
can fall back to the system interpreter instead of hanging/failing on that
fetch).

Before and after the entire tracer run, on the REAL host (never inside the
container), record `stat`/checksum output for `~/.myshellrc`, the real
zsh rc file, `~/.bashrc`, and `~/.local/bin/wezterm` (expected: identical
stat/checksum for the first three if they exist, or absent both times; the
last must be absent both times, since `wezterm` was only ever installed
inside the disposable container's own `/workspace`, never on the host). This
is the phase's hard architectural proof that the container boundary actually
held — record it verbatim as evidence, not merely asserted.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Host filesystem <-> disposable container | The container gets a read-only mount of the repo and its own writable copy; nothing it does may reach back to the host. |
| Detection script <-> real container runtime | The script decides whether ANY container operation is even attempted; a wrong decision here either silently runs on the host (unsafe) or silently no-ops (masks a real gap). |
| Internet <-> container | The container downloads uv's installer and one checksum-verified GitHub release asset over the network. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-12.3-01 | Tampering | repo bind-mount inside the tracer container | high | mitigate | Repo mounted `:ro,Z`; container copies into its own writable `/workspace` before any write; no task ever mounts the repo read-write. |
| T-12.3-02 | Elevation of Privilege | detection script accidentally running install commands on the host | critical | mitigate | Every install command in this plan lives exclusively inside a `podman run`/`docker run` invocation; the D-03 gate refuses to proceed at all (exit 3, no mutating command) when no container tool is detected — proven directly by Task 2, not merely documented. |
| T-12.3-03 | Tampering (supply chain) | uv's install script and wezterm's GitHub-release AppImage, both fetched over the network inside the container | medium | accept | `wezterm`'s asset is checksum-verified by this project's existing `download.install_download` path (Phase 7 already vetted this exact method); uv's official installer is the same bootstrap this project's own contributors already run; execution is confined to a disposable container whose blast radius ends at teardown. |
| T-12.3-04 | Information Disclosure | container gaining access to host credentials | high | mitigate | No bind-mount of the host's real `$HOME`, `~/.ssh`, or any credential path — only the repo source, read-only. |
| T-12.3-05 | Repudiation | claiming the host was untouched without evidence | medium | mitigate | Task 1 records real before/after `stat`/checksum comparisons of the host's actual rc files and `~/.local/bin`, not a bare assertion. |
</threat_model>
