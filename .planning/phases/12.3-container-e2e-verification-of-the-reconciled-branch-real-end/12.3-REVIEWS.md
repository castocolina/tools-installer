## 12.3-01

### Summary

The tracer plan (detection script + one-tool end-to-end proof + D-03 refusal proof) is well-scoped
and correctly grounded in real, checksum-verified registry data (`wezterm`'s
`installer/registry.toml:2458-2467` `github_release` method for `os=["debian","fedora"]`,
`arch=["amd64"]`, confirmed live). Its container-safety architecture is genuinely enforced in the
`<action>` bodies — every install/mutating command is textually confined inside a
`$CONTAINER_TOOL run`/`exec` invocation, never a bare host command, and the D-03 refusal
requirement ("MUST NOT proceed... MUST NOT fall back to running anything on the host") is written
as hard script control flow, not a comment. One HIGH defect: Task 2's own codified `<verify>`
command does not actually exercise the no-tool-found branch on this exact host.

### Strengths

- `wezterm`'s Fedora/amd64 method is a real, checksum-verified `github_release` entry
  (`installer/registry.toml:2458-2467`, `checksum = "{asset}.sha256"`, `raw = true`) — an accurate,
  thin, already-proven (Phase 7) slice to tracer with, not a fabricated example.
- The mandated repo mount is `:ro,Z` (read-only, SELinux-relabeled) in both Task 1's action text
  and the threat model's T-12.3-01/T-12.3-02 mitigation — appropriate for this SELinux-enforcing
  Bazzite host, and structurally prevents any in-container write from reaching the real source
  tree.
- Task 1's before/after host `stat`/checksum comparison of `~/.myshellrc`, the real zsh rc, and
  `~/.local/bin/wezterm` gives the "host untouched" claim a concrete, falsifiable check rather than
  a bare assertion (Repudiation mitigation T-12.3-05).

### Concerns

- **HIGH: Task 2's automated `<verify>` command does not test the real D-03 no-tool-found path on
  this host — the exact host this phase will execute on.** The `<verify>` block is
  `env -i PATH=/usr/bin bash scripts/detect-container-runtime.sh; test "$?" -eq 3`
  (`12.3-01-PLAN.md:194`). Confirmed live on this machine: `podman` is installed at
  `/usr/bin/podman` (`which podman` → `/usr/bin/podman`, real file, 45MB, root-owned). With
  `PATH=/usr/bin`, `command -v podman` inside the script **succeeds** — the script takes its
  normal success branch (`CONTAINER_TOOL=podman`, exit 0), not the D-03 refusal branch (exit 3).
  The literal `<verify>` command as written would therefore fail its own `test "$?" -eq 3`
  assertion, or — worse, if an executing agent "fixes" this by silently swapping in the
  container-based alternative the action prose also describes without updating the committed
  `<verify>` block — the checked-in automated gate stays broken for any future re-run of this
  script's regression coverage. This is precisely the caller's concern: a "proof" that does not
  test the real code path. The action prose itself proposes a more reliable venue (running inside
  the tracer's own base `fedora:latest` container before podman/docker/colima are installed into
  it), but that is not what the codified, automatically-checked `<verify>` line says — and GSD's
  own execution discipline treats `<verify>` as the executable gate, not prose describing a better
  alternative.
- **MEDIUM: Task 1's container bootstrap installs `curl tar git ca-certificates` via `dnf` but
  never `python3`, relying implicitly on `uv sync`'s ability to fetch a managed Python at
  `uv sync` time.** This is very likely to work (uv's default behavior fetches a managed
  interpreter from `python-build-standalone` when none is found), but the action text does not
  name this dependency or note the outbound-network requirement it adds beyond wezterm's own
  release asset and uv's installer script — worth one explicit sentence in the SUMMARY if this
  phase is meant to be a template other e2e phases copy.

### Suggestions

- Change Task 2's `<verify>` to something that is actually falsified by this host's real
  `/usr/bin/podman`, e.g. running the check inside a scratch container/chroot that genuinely lacks
  all three binaries (the action text already describes this as "more reliable" — promote it to
  the codified `<verify>`), or use an empty/nonexistent `PATH` directory (`env -i PATH=/nonexistent
  bash scripts/detect-container-runtime.sh`) instead of `/usr/bin`.
- Note the implicit `uv`-managed-Python network dependency explicitly in Task 1's action text or
  SUMMARY, so a future host with restricted egress to `python-build-standalone`'s CDN has a named
  failure mode to check against rather than a silent `uv sync` hang/failure.

### Risk Assessment

**HIGH.** The plan's architecture is sound, but its own automated safety-gate proof for D-03 is
self-defeating on the exact host it will run on — this needs a fix before the "D-03 gate proven,
not assumed" success criterion can be trusted.

## 12.3-02

### Summary

Correctly builds a single long-lived, non-root, sudo-capable container and runs the full-catalog
clean-install pass through the real production `uv run setup.py --all --yes` entrypoint — no
scope-narrowing to only the reconciliation's diff, matching D-04. The container-safety boundary
holds (every mutating command lives inside `$CONTAINER_TOOL exec ... su - tester -c '...'`, no
pseudo-TTY, matching `sys.stdin.isatty()`'s non-interactive branch requirement verified live at
`setup.py:589-592`). Two real gaps: no execution-time budget for a ~90-tool run, and the
"fix on host, re-run" loop this task itself mandates has no step that re-syncs the fix into the
container's copy of the repo.

### Strengths

- The non-interactive entrypoint claim is verified accurate: `setup.py:448` (`if not
  sys.stdin.isatty()`) and `setup.py:589` (`can_proceed = options.all or ... or sys.stdin.isatty()`)
  confirm that omitting `-it`/`-t` on every `exec` (as the action text explicitly mandates) is what
  makes `--all --yes` take its scripted, non-interactive path — this is a real mechanism, not an
  assumed one.
- `render_summary`'s deterministic tally line the plan parses (`Installed: N Already: N Failed: N
  Dependency failed: N Checksum mismatch: N No method: N Manual setup required: N`) is a real,
  existing `installer/render.py` output, and the plan correctly identifies `No method`/`Manual
  setup required` as expected-nonzero on a Linux container (macOS-only entries, `host_setup`/
  `skill_pack` handoffs) rather than treating any nonzero count as a failure.
- The threat model correctly scopes `tester`'s passwordless sudo (T-12.3-06) as container-local and
  torn down at the end of Plan 12.3-03, not a host privilege grant.

### Concerns

- **HIGH: No execution-time budget, chunking, or background-execution strategy for a ~90-tool
  catalog run — realistic risk this task cannot complete in one execution.** The action text is a
  single `su - tester -c "... uv run setup.py --all --yes"` foreground call with no discussion of
  how long this is expected to take or what happens if the invoking agent's own tool-call timeout
  (a hard ceiling on this kind of harness — commonly capped in the 10-minute range unless
  explicitly raised) fires mid-install. A Homebrew bootstrap alone commonly takes several minutes
  on a fresh container with a cold formula cache, and ~90 tools' worth of GitHub releases, pnpm
  installs, and brew formulae (several of which build from source) plausibly pushes total wall time
  well past any default single-call timeout. The plan gives the executing agent no guidance to run
  this in the background, poll for completion, or split the catalog into resumable chunks — if the
  call is killed mid-run, the transcript capture and the `TRACER_CLEAN_INSTALL_OK` marker (gated on
  process completion) are simply absent, and nothing in the plan distinguishes "genuinely still
  running" from "silently killed" the way ADR-2782's reviewer-lane timeout discipline (used
  elsewhere in this same GSD tooling) explicitly does. This is exactly the caller's named concern
  and is not hypothetical — it is the single largest execution-feasibility risk across all four
  plans.
- **HIGH (shared with 12.3-03, described once here): the container's `/home/tester/workspace` copy
  of the repo is a one-time snapshot with no re-sync step, which breaks this task's own "fix on
  host, re-run" instruction.** Task 1's action text copies `/repo` (the read-only mount) into
  `/home/tester/workspace` exactly once, during bootstrap (`cp -r /repo /home/tester/workspace`).
  The container is long-lived (`sleep infinity`) and reused verbatim by Plan 12.3-03. Task 2's
  action text then requires: "if it traces to a real installer bug... fix the bug on the host in
  `installer/`... then re-run this task's Pass 1 sequence until the failure is gone" — and Plan
  12.3-03's Task 1 repeats the identical instruction for its own rerun/uninstall/reinstall
  sequence. But neither plan's action text, anywhere, includes a step that re-copies the
  now-fixed `/repo` into `/home/tester/workspace` before re-running. Every `exec` after bootstrap
  operates against the STATIC in-container copy made once at the start. As written, "fix on host,
  re-run" would re-run the *same, unfixed* code inside the container — the fix would be real on
  the host and verified by `make validate && make test` there, but the container-side re-run that
  is supposed to prove the fix actually holds under the real Tier-3 conditions would silently
  exercise the pre-fix code instead, producing a false "resolved" signal. This directly undermines
  both plans' success criteria ("any real bug the pass found was fixed... and re-verified").

### Suggestions

- Either run Pass 1 with `run_in_background`-equivalent semantics and poll a marker file/log for
  completion (with a generous, explicit timeout budget stated in the plan), or explicitly split the
  catalog into resumable batches (e.g. by `Category`) so a single call never risks exceeding a
  harness timeout ceiling — and say so in the plan text rather than leaving it to the executing
  agent to discover the problem live.
- Add an explicit `cp -r /repo/. /home/tester/workspace/` (or equivalent rsync) re-sync step,
  scoped narrowly to the fix commit's changed files or done wholesale, immediately before any
  "re-run until clean" loop iteration in both this plan's Task 2 and Plan 12.3-03's Task 1 — and
  say explicitly that the read-only host mount is always the source of truth for a re-sync, never
  the container's own prior in-place edits.

### Risk Assessment

**HIGH.** The container-safety boundary and non-interactive entrypoint mechanism are both
genuinely sound. But the plan is silent on a highly plausible execution-timeout failure mode for a
90-tool run, and its own "fix, then re-verify" loop is structurally broken by a missing repo
re-sync step — both need to be closed before this plan can be trusted to produce the evidence it
claims to produce.
