<domain>
## Phase Boundary

A `catalog-audit` skill audits every registry entry in a loop: pinned, installed and latest versions, the changelog in between, the install, update, removal and tuning steps, and the scripts behind them. It writes one report per entry and a summary of proposed changes into a dated, committed run directory, resumes mid-loop, and changes nothing without approval. Its first run lands three things: OpenCode 2 (install, update, removal, latest-version source, the `permissions` tuning key), Pi as a codegraph MCP host, and copilot as a codegraph MCP host (Backlog 999.12). It also refreshes the Pi entry's text. Drift on every other entry is proposed, not applied.

This phase assumes Phases 23.1, 23.2, 24 and 24.1 have landed: `present_harnesses` lives in `postinstall.py`, copilot is a catalog entry with install tuning, `HOST_CATALOG_IDS` has `pi` and `copilot` (24 D-21), and `tool-onboarding` carries TUNE-04's rule.

### OpenCode 2 (R6, R7)
- **D-07: The opencode script method:**
  - `url = "https://opencode.ai/v2/install"`, `args = ["--no-modify-path"]`, `paths = ["~/.opencode/bin/opencode", "~/.opencode/bin/opencode2"]`, `bin_dir` unchanged.
  - The `update` key is **dropped**, so an update re-runs the v2 installer through the existing branch (`installer/update.py:432-436`, "no declared update → `executors.execute`"). This moves v1 installs to 2.x and keeps v2 current with one path. codex, antigravity, volta, fnm and kitty already have no `update` key.
  - Evidence (analyzer, sources read as data):
    - v1.19.5's `opencode upgrade --major` pipes the v2 installer to a shell *without* `--no-modify-path` (`installation/index.ts` `majorUpgrade`), so it would edit the user's shell rc.
    - v1's plain `upgrade` refuses targets ≥ 2.
    - v2.2.6's own `upgrade` with the curl method re-runs the same v2 installer with `--version X --no-modify-path` (`packages/cli/src/services/updater.ts` ~476-495).
    - The v2 installer always replaces the binary and always writes `opencode2` (`install_legacy_shim`). The receipt is rewritten after an installer-owned update (`update.py:347,378-392`), so `opencode2` gets recorded.
  - Plan-time container check: a seeded 1.x updates to 2.x, the receipt lists both paths, and no shell rc changes.
  - **Own reasoning** (jev vendor_major_flag low 0.34, vendor_upgrade_cmd low 0.55): both jev picks either edit shell rc files or stay on v1. Ledger.
- **D-08: Removal stops the background service through the existing L3 recipe, `remove = ["opencode", "service", "stop"]`.** The app runs it with the receipt-proven leaf before deleting the proven paths (`installer/uninstall.py:246-275` `_recipe_argv`; `installer/app.py:789-826`).
  - Live: the `opencode serve --service` process is parented by `systemd --user`, and there is no unit file, so nothing else stops it.
  - v2's `uninstall` also deletes `~/.cache/opencode` and may rewrite shell rc files (v2.2.6 `commands/handlers/uninstall.ts:24-113`), the same reason v1's uninstall was rejected (`registry.toml` opencode `# Verified 2026-11-04`).
  - **Open for planning:** the exit code of `opencode service stop` when no service runs. If it is non-zero, a failing recipe aborts removal and keeps the receipt (`app.py:819-822`). The planner then picks the smallest correct form within the recipe mechanism, e.g. a vendor flag or status-then-stop. It must not add a new pre-removal mechanism. *(amended 2026-11-13, 24.3 research: v2.2.6 `service.ts` terminates only when a registration file exists and the CLI handler ignores the PTY shutdown result, so the plain recipe completes with no service running; the landing container check confirms the process exit code, and no other form is planned, needs confirmation)* *(amended 2026-11-13, 24.3 review cycle 1 R1-03: superseded in part: the recipe is `remove = ["opencode2", "service", "stop"]`. OpenCode v1.19.5 (`packages/opencode/src/index.ts`) has no `service` command, parses strictly and has a default `$0 [project]` command, so `opencode service stop` against a v1 binary exits 1 or treats `service` as a project and can start the TUI. `_recipe_argv` binds a head only to a receipt-proven leaf and returns `()` otherwise, and only the v2 installer writes `opencode2`, so a v1 receipt skips the recipe and its removal deletes the proven binary. This stays inside the L3 recipe mechanism as the open-for-planning clause allows; the shim execs the sibling `opencode`; the landing container proves both the v2 stop and the v1 removal, needs confirmation)*
  - choice 0.99 (service_stop_recipe).
- **D-09: The brew method moves from `anomalyco/tap/opencode` to homebrew/core `opencode`. pacman stays as it is (`extra/opencode` 2.2.5).**
  - Live (analyzer): the tap's `opencode.rb` is 1.19.5. The tap's `opencode-v2.rb` is 2.2.6 with `conflicts_with "opencode"`. homebrew/core `opencode` is 2.2.6. v2's updater handles core `opencode` (`updater.ts:157,277-283`).

The `# Verified` comment records the switch. *(amended 2026-11-13, 24.3 plan-phase: `ownership.listed_name` reads both `anomalyco/tap/opencode` and core `opencode` as `opencode`, so such a host stays brew-owned and `brew upgrade opencode` keeps the tap's 1.19.5; the `# Verified` comment and SUMMARY record that gap and nothing migrates a user's formula, needs confirmation)*
  - **Own reasoning** (jev tap_v2_formula low 0.39, core_formula low 0.61): a core formula has no tap trust or name churn and no conflict declaration. Ledger.
- **D-10: An installer-owned script method gets a latest-version source from a new declared npm package param.** The name is at Claude's discretion; it must not reuse the `node` kind's `npm_pkg` semantics by accident, e.g. `latest_npm = "@opencode/cli"`.   - *(amended 2026-11-13, 24.3 plan-phase: a `permission` value the ledger records as the installer's own is ours: no write, no `≈`, still reverted on removal, never "set by you"; only an unrecorded `permission` is the user's and blocks the rule.
