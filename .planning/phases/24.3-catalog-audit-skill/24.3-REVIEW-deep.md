## Critical Issues

### HR-01: `--state` guard accepts any existing JSON file, so verify-registry overwrites user config

**File:** `installer/catalog_audit.py:676-692`, `installer/catalog_audit.py:707-716`; sink `installer/verify_registry.py:1492-1494`
**Issue:** `_state_refusal` refuses only three cases:
1. the resolved path equals `default_state_path()`;
2. the path is inside `--repo`;
3. the path is an existing file that is not JSON.

Everything else passes. That includes every JSON file under the real HOME:
`~/.claude/settings.json`, `~/.claude.json`, `~/.codex/*.json`,
`~/.local/state/tools-installer/version-cache.json`, and so on. A dangling symlink whose
target sits in HOME passes too.

What happens next:
- `record_verify` copies the warm state over the target when it is absent
  (`ensure_dir(state.parent)` plus `atomic_write_bytes`, which follows symlinks,
  `atomic.py:45`).
- `verify_registry.main` loads the file with `_load_state`, which drops every non-string
  value.
- It then rewrites the file whole with `_save_state`, through `on_verified` and once more at
  the end.

**Failure scenario:**
- An agent passes `--state ~/.claude/settings.json`, or any JSON path under `~`. For example,
  it might reuse a path from `facts` output. The user's settings are replaced by
  `{"tool:url": "sha..."}`. That is data loss and a host mutation from a command documented as
  "writes only `.planning/audits/catalog`".
- `--state ~/scratch/vr.json` (absent) is also accepted and creates files in HOME, which
  breaks R5's rule that HOME is only read.
- `--repo /elsewhere` turns off the in-checkout check.

Reproduced: `_state_refusal(<tmp>/settings.json holding {"permissions": {...}}, repo)` returns
`None`. No test covers a JSON file that is not a state file, or any path under HOME.

**Fix:** refuse anything under the real HOME. Also refuse an existing file that is not
verify-registry's own shape (a flat `dict[str, str]`). Do the HOME check on the resolved path
and on the parent of a dangling link.
```python
def _state_refusal(state: Path, repo: Path, home: Path) -> str | None:
    resolved = state.resolve()
    for real_home in {home, home.resolve()}:
        if resolved.is_relative_to(real_home):
            return "--state lies under the home directory; name a scratch path outside it"
    if resolved.is_relative_to(CHECKOUT.resolve()) or resolved.is_relative_to(repo.resolve()):
        return "--state lies inside the repo checkout; name a scratch path"
    if resolved.exists():
        try:
            data = json.loads(resolved.read_text(encoding="utf-8"))
        except (OSError, ValueError):
            return "--state names an existing file that is not JSON"
        if not (isinstance(data, dict) and all(isinstance(v, str) for v in data.values())):
            return "--state names a JSON file that is not a verify-registry state"
    return None
```
Read the warm copy from `default_state_path()` before the HOME check rejects that path, as the
code does now. Add tests for a JSON config under a scratch HOME, an absent path under HOME, and
a dangling symlink into HOME.

## Warnings

### MR-01: Stale-citation state is wrong in both directions (44 of 50 committed rows say `stale`)

**File:** `installer/catalog_audit.py:1379-1399` (token choice), `installer/catalog_audit.py:1085-1095`, `installer/catalog_audit.py:1412-1419`
**Issue:** The token checked against `path:N` is the first backticked span of the pattern or
source. Two failures follow.

1. **Report rows always read `stale`.** The template's own style starts a drift source with the
   citation in backticks (`` `installer/agent_settings.py:12` writes ... ``,
   `references/report-template.md`). The token is then the citation itself, which never appears
   on line N.
2. **A comment on the cited line reads `current`.** `_line_has` matches the token anywhere on
   the line, comments included.

Evidence in the committed `.planning/audits/catalog/2026-11-13/SUMMARY.md`:
- 44 of 50 script-finding rows are `stale`, including unresolved `proposed` rows such as
  `.claude/skills/tool-onboarding/SKILL.md:106`.
- Backlogged rows show `stale (resolved by backlog:999.15)`, but the backlog resolved nothing.
- The one real fix shows `installer/agent_settings.py:679 | ... permission deprecated ... |
  current` (line 874). Line 679 is now the new comment
  ``# OpenCode 2's schema deprecates `permission`; ...``.

SPEC R3's concurrency backstop ("a mismatch marks the finding `stale` rather than citing a
wrong line") is therefore not met. A maintainer reading the column gets the opposite of the
truth. Reproduced: `_line_has(repo, "installer/a.py:1", "permission")` returns True on a
comment line, and the citation token is always False. `test_stale_citation` only uses
hand-written scan rows whose token is real code.

**Fix:**
- Skip spans that match `_CITATION_RE` or contain `/` when picking the token. Take the first
  span that is a code token instead, or record the token explicitly. The scan already knows it:
  store it in `ScanRow`, and require an explicit `--token` on `add-finding`.
- Strip a trailing `#`/`//` comment before matching Python and shell lines.
- Show `stale (backlog:999.x)` without the word "resolved" for backlog dispositions.

### MR-02: Re-running `scan` or `verify` silently drops sticky drift from SUMMARY and the gate

**File:** `installer/catalog_audit.py:1553-1562`, `installer/catalog_audit.py:664-670`
**Issue:** `write` refuses to rewrite a complete report. `scan` and `verify`, however,
overwrite `scripts.md` and `verify-registry.md` unconditionally through `_write_run_file`.
`_model` reads scan drift only from the current `scripts.md` (`:1343-1346`).
`_verify_lines` reads only the current verify record.

**Failure scenario:** a landing change fixes `agent_settings.py:679`. Someone then runs
`scan --date <same run>` "to refresh". The `permission` row disappears from `## Drift`.
`summarize --require-disposition opencode` exits 0 without any `dispositions.toml` row. The
amended R4 rule ("a `scripts.md` drift keeps its key drift and in the disposition gate until a
`dispositions.toml` row names it") is bypassed. The skill only says to run step 4 when
`scripts.md` is missing; nothing enforces it.

**Fix:** treat both files like reports. Refuse to overwrite an existing `scripts.md` or
`verify-registry.md` in a run with exit 73, and tell the user that a new date starts a new run.
Alternatively, merge the new scan with the old rows, so old drift keys survive. Add a test that
re-scans a fixed tree and checks that the gate still fails.

### MR-03: Merge rule: a report `n/a` swallows later `unknown` and `ok` findings

**File:** `installer/catalog_audit.py:1280-1292`
**Issue:** `effective()` starts from `current = self.report`.
- For `"n/a"`, an `unknown` finding keeps `current or "unknown"`, which is still `"n/a"`.
- An `ok` finding changes `current` only when it is `None`, or when it is `"unknown"` and the
  source is a container.

So `n/a` never moves. The cycle-2 rule (worst wins: drift > unknown > ok > n/a, "a late
finding can raise a row") still applies wherever cycle 3 did not narrow it. Cycle 3 narrowed
only unknown→ok and ok→unknown.

**Failure scenario:** a report says `postinstall hook | n/a | reason: no hook`. Later a
container finding says `unknown: reason: container check not run`, or a container proves
`ok`. SUMMARY's `## Entries` still shows `n/a`. Reproduced both cases. `_MERGE_CASES` has no
`n/a` case.

**Fix:**
```python
if finding.status == "unknown":
    current = "unknown" if current in (None, "n/a") else current
elif current in (None, "n/a") or (current == "unknown" and _CONTAINER_RE.fullmatch(finding.source)):
    current = "ok"
```
Add `n/a` rows to `_MERGE_CASES`.

### MR-04: Secret filter misses GitHub's own CLI token prefixes (`gho_`, `ghu_`, `ghs_`, `ghr_`) and npm tokens

**File:** `installer/catalog_audit.py:91-102`
**Issue:** `_SECRET_RES` covers `ghp_` and `github_pat_` only. `default_seams` takes its token
from `gh auth token` (`:131`, `verify_registry.github_token`), and gh's OAuth login yields
`gho_…` tokens. GitHub Actions and app tokens are `ghs_`/`ghu_`/`ghr_`. npm tokens (`npm_…`)
are also missed, yet the audit reads npm for `@opencode/cli` and Pi. A pasted
`Authorization: token gho_…` line passes `write` and `add-finding`, because the `Bearer`
pattern does not match `token`.

The constraint "Reports quote no secrets" is the third MUST NOT. Reproduced: `_hygiene("token
gho_" + 36 chars)` returns no problem.

**Fix:**
```python
r"gh[pousr]_[A-Za-z0-9]{36,}",
r"npm_[A-Za-z0-9]{36}",
r"glpat-[A-Za-z0-9_-]{20,}",
r"AIza[0-9A-Za-z_-]{35}",
r"(?i)(?:authorization|token)[:=]?\s+[A-Za-z0-9._~+/=-]{24,}",
```
Run the same hygiene over the `verify-registry.md` body before writing it.

### MR-05: Symlink refusal checks only `catalog/` and `<date>/`; a symlinked ancestor escapes the run directory

**File:** `installer/catalog_audit.py:159-165`, `installer/catalog_audit.py:313-316`, `installer/catalog_audit.py:664-670`
**Issue:** `run_dir` rejects a symlink at `root` or at `run` only. `.planning/audits` and
`.planning` are tracked paths. If either is a symlink (a checked-in symlink, or a dotfiles-style
`.planning` link), the following land wherever the link points:
- `ensure_dir(run)`;
- `atomic_write_text` of `<id>.md`, `SUMMARY.md`, `findings.toml` and `scripts.md`.

That breaks the module docstring's promise ("changes nothing outside its run directory") and
the review scope's "symlink refusal for every write". The `.planning` ancestor check uses
`is_dir()`, which follows symlinks.

**Fix:** resolve and confine:
```python
anchor = next(p for p in (root, *root.parents) if p.name == ".planning")
for part in (root, *root.parents):
    if part.is_symlink():
        raise UsageError(f"{part} is a symlink")
    if part == anchor:
        break
```
Also check that `run.resolve().is_relative_to(anchor.resolve())` before each write.

### MR-06: Copilot presence false positive: AWS Copilot CLI's `copilot` binary triggers a codegraph write to `~/.copilot/mcp-config.json`

**File:** `installer/postinstall.py:62`, `installer/postinstall.py:100-110`, `installer/postinstall.py:185`
**Issue:** Presence is `which("copilot") or (~/.copilot exists and holds more than ide/)`. The
footprint check applies only to the marker. Any `copilot` on PATH counts. AWS Copilot CLI
(`brew install aws/tap/copilot-cli`, ECS deploy tool) installs a binary named exactly
`copilot`.

**Failure scenario:** on a machine with AWS Copilot and no GitHub Copilot CLI:
1. Installing codegraph, or any resync, passes `copilot-cli` in the `--target` CSV.
2. codegraph creates `~/.copilot/mcp-config.json` for an absent host.
3. The catalog shows codegraph `≈ not registered for copilot` until that happens.

This is R3's "write for an absent host" unsafe pattern. The phase made it a real write by
adding `copilot` to `_CODEGRAPH_TARGETS`. A macOS `~/.copilot/.DS_Store` also passes the
footprint check.

**Fix:**
- Confirm the PATH hit is GitHub's CLI before counting it. Two options: a cheap
  `copilot --version` first-line check run through the telemetry-safe probe, or require the
  marker as well. `which` alone should not mean GitHub Copilot.
- Ignore dotfiles in `_copilot_cli_footprint`:
  `any(e.name not in {"ide"} and not e.name.startswith(".") for e in marker.iterdir())`.

### MR-07: OpenCode 2 removal is blocked wherever PID 1 does not reap (the gate fixed the harness, not the product)

**File:** `installer/registry.toml` opencode `remove = ["opencode2", "service", "stop"]`; `installer/app.py:822-829`
**Issue:** The first landing run failed `V2_REMOVE` because `opencode service stop` timed out:
the daemon it stops stays a zombie under a non-reaping PID 1 (24.3-11-SUMMARY:96). The fix
(394fa836) added `--init` to the test container. The product still treats a non-zero recipe
exit as fatal: `remove_tool` returns `ToolRemoval(False, …)` and deletes nothing, keeping the
receipt.

**Failure scenario:** a user runs the installer inside a devcontainer, a `docker run` without
`--init`, or any box whose PID 1 is `sleep infinity` or a shell. After `opencode service
start`, every removal attempt fails with the stop timeout, and there is no override path.
Neither the fakes nor the fixed harness exercise a non-reaping PID 1 any more.

**Fix:** keep the recipe, but make a `service stop` failure non-fatal when no live service
remains. One way is a per-method `remove_ok_codes`. Another is to treat a timeout as success
when no `opencode serve` runs from the proven binary afterwards. A third is to check
`opencode2 service status` before the stop (CONTEXT D-08 allowed status-then-stop). Add an
e2e step that runs the removal in a container started without `--init`, as a recorded edge, or
put it on the UAT list.

### MR-08: Landing driver's container check passes inside toolbox and distrobox, where HOME is the real home

**File:** `tests/e2e_landing_driver.py:812-814`
**Issue:** `_in_container()` accepts `/run/.containerenv`. Podman writes that file in every
container, including toolbox and distrobox containers, and those bind-mount the user's real
`$HOME`. On Bazzite, this project's host OS, development commonly happens inside them.
`python -m tests.e2e_landing_driver install opencode` (or `remove`, `seed-v1`, `codegraph …`)
run there would:
- install and remove OpenCode;
- start and stop its service;
- rewrite `~/.config/opencode` tuning and receipts;
- register codegraph into the real `~/.copilot` and `~/.pi`.

All of that is a host mutation AGENTS.md forbids.

**Fix:** require a positive marker that only the audit-landing harness sets. One option is an
env var such as `TOOLS_INSTALLER_E2E_LANDING=<container name>`, passed by `exec_tester`.
Another is a sentinel file the harness writes into the tester's HOME. Also refuse when
`/run/.toolboxenv` exists or `$HOME` is mounted from the host (`findmnt -T "$HOME"`).

### LR-02: Home-path redaction misses the `/home` alias when `$HOME` is `/var/home/<user>`

**File:** `installer/catalog_audit.py:235`, `installer/catalog_audit.py:620-624`
**Issue:** `{home, home.resolve()}` covers `/home/x` to `/var/home/x`, but not the reverse. On
an Atomic Fedora host where `$HOME=/var/home/x`, a report containing `/home/x/.claude` passes
`_hygiene` and `_tilde`.
**Fix:** also add `Path("/home") / home.name` and `Path("/var/home") / home.name` when
`/home` is a symlink, or compare resolved path tokens found in the text.

### LR-03: `LANDING_ENV_RE` turns product failures into "infeasible" (exit 2)

**File:** `scripts/container-e2e-verify.sh:2693`, `landing_step`
**Issue:** The bare alternatives `SSL|TLS|certificate|Connection refused` match anywhere in a
failing step's whole output. That includes the product's own lines, such as a refused
connection to the opencode service port or an `OpenSSL` version string. The step then exits 2
as environmental, and the remaining verdicts never run.
**Fix:** match only lines from the known environmental emitters (`curl: (`, `dnf`, `brew`,
`uv`, the pull). Never classify a run that already printed a `TRACER_*_FAILED` line as
infeasible.

### LR-04: `--init` was added to the shared `start_container`, so every e2e command changed

**File:** `scripts/container-e2e-verify.sh:194-196`
**Issue:** Podman's `--init` needs `catatonit` at `init_path`. Fedora pulls it in. Debian and
Ubuntu podman only recommend it (unverified on a minimal install). If it is missing, every
`container-e2e-verify.sh` command (`all`, `bootstrap`, …) fails at `ct run`, not just
`audit-landing`.
**Fix:** add `--init` only for the landing and distro jobs that need it. Or probe with
`ct info --format '{{.Host.OCIRuntime}}'` / `init_path`, and fall back with a clear message.

### LR-05: The skill states the telemetry opt-out as a fact, not a command; some "read-only" host probes write caches

**File:** `.claude/skills/catalog-audit/SKILL.md:157-167`
**Issue:**
- "Every probe runs with `CODEGRAPH_TELEMETRY=0` and `DO_NOT_TRACK=1`" is true for the tool's
  own probe only. An agent that types `codegraph install --print-config pi` in its shell gets
  no opt-out, and codegraph writes `~/.codegraph`.
- `brew info --json=v2` refreshes `~/Library/Caches/Homebrew/api/*.jws.json` (or the Linux
  cache) when stale.
- `opencode debug paths` may create opencode's log and data directories on first run
  (unverified).
**Fix:** write the exact prefix: `env CODEGRAPH_TELEMETRY=0 DO_NOT_TRACK=1
HOMEBREW_NO_AUTO_UPDATE=1 <probe>`. Prefer the formulae.brew.sh JSON, which `facts` already
reads, over `brew info`, and drop `opencode debug paths` unless shown to write nothing.

### LR-06: The Pi gate gives different answers in the fact path and the register path

**File:** `installer/version_status.py:844-845` with `installer/versions.py:348-350`; `installer/postinstall.py:190-200`
**Issue:** `_hook_fact` passes `probe_version_output`, which returns `None` for an exit 0 with
empty stdout. `_codegraph_register` uses `codegraph_query`, which returns `""`, a pass. A
codegraph whose `--print-config pi` prints to stderr, or prints nothing, would register Pi but
never show `≈`, or the reverse. The fact path also re-probes on every refresh while Pi is
present and unsupported. It costs about 50 ms, or the probe timeout if codegraph hangs.
**Fix:** use one probe adapter for both paths, with "exit 0" as the only criterion, for example
`codegraph_query(...) is not None`. Optionally memoise per binary path and mtime for the
lifetime of the refresh service.

### LR-07: Script `cite` cannot name the docs the skill tells agents to cite

**File:** `installer/catalog_audit.py:87`, `installer/catalog_audit.py:1147-1149`; `SKILL.md:107-109`
**Issue:** `_CITATION_RE` allows only `installer|scripts|tests|.claude`. Step 4.4 says to record
a doc's missing symbol with `--cite '<doc path:line>'`. Citations into `docs/`, `AGENTS.md` or
`README.md` are refused with exit 73. Also, `\S+:\d+` is greedy, so `x.py:12:3` splits as
file `x.py:12`.
**Fix:** allow any repo-relative path without `..` that exists under `--repo`. Anchor the line
number with `(?P<path>[^\s:]+):(?P<line>\d+)`.

### LR-08: Debian "latest" is the newest version across all suites, unlabelled

**File:** `installer/catalog_audit.py:415-419`
**Issue:** `versions[0]` from sources.debian.org is usually unstable or experimental. The `apt`
method installs from the user's release (stable or Ubuntu). The `- latest:` line therefore
invites false install-method drift. Fedora is labelled "rawhide"; Debian is not.
**Fix:** append the suite (`(Debian <suites>)`) from the row, or pick the newest version whose
suites include `stable`.

### LR-09: Pi registration location is not recorded, so removal can miss a custom `PI_CODING_AGENT_DIR`

**File:** `installer/postinstall.py:269-272`, `installer/uninstall.py` `_hook_undo`
**Issue:** The codegraph hook relies on the inherited `PI_CODING_AGENT_DIR` both at register
time and at unregister time. If the removal runs without that variable (another shell, a
schedule, the TUI launched from a desktop entry), codegraph's `pi` uninstall targets the
default `~/.pi/agent` and leaves the real entry behind. This stays dormant until codegraph
ships `pi`.
**Fix:** record the effective dir alongside the `pi` host in `receipt.hooks`, and export it
for the unregister argv. Or refuse to unregister `pi` when the recorded and current dirs
differ.
