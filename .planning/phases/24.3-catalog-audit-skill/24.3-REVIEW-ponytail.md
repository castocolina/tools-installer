# Phase 24.3 - ponytail review

Range: `6b3c25c..00631790`, code only (`.planning/` skipped). Read-only review. No installer,
make, container or vendor command was run.

Load assumed: one maintainer (or one agent session) runs the audit by hand, about once per
release, over the 86-entry registry. The installer changes (npm latest, OpenCode 2, codegraph)
run on every user's machine.

**What this change does:** It adds `installer/catalog_audit.py`, a CLI that collects facts about
each registry entry from upstream, validates the reports an agent writes, scans the script
surfaces, and builds a `SUMMARY.md` with a gate for drift that has no disposition. It moves
OpenCode to the v2 installer, with an npm latest-version source, an `opencode2 service stop`
removal step and the new `permissions` tuning (the old `permission` key becomes a retired key).
It also registers codegraph for copilot-cli, adds Pi behind a probe, and adds the
`audit-landing` container e2e that exercises all of this.

Counts: HIGH 0, MEDIUM 4, LOW 7.

No HIGH: every candidate failure I checked needs bad input or a manual run outside the
harness. Each one is listed below at MEDIUM, with the concrete case.

## Should fix

### 1. MEDIUM - `verify --state` can overwrite any existing JSON file (`installer/catalog_audit.py:676-692`)

- **What this is:** `verify` passes `--state` to verify-registry. `_state_refusal` is meant to
  allow only a scratch path.
- **Problem:** It refuses only three things: the default state, a path inside the checkout, and
  an existing file that is not JSON. Any other existing JSON file gets through, for example
  `--state ~/.claude/settings.json` or `~/.config/opencode/opencode.json`. verify-registry then
  reads it with `_load_state`, which keeps only string-to-string pairs
  (`installer/verify_registry.py:1476-1489`). At the end it always calls `_save_state`
  (`verify_registry.py:1629`), which rewrites the file whole. The agent's settings are lost. The
  path comes from the agent, so this check is the trust boundary.
- **Fix:** Accept a path that does not exist yet, or an existing file whose JSON is a flat object
  with only string values (verify-registry's own format). Refuse anything else. That is about 3
  lines in `_state_refusal`, plus one test with a nested-JSON file.
- **If we skip it:** A typo or a confused agent can wipe a real agent config, which breaks the
  repo's "never mutate the developer's host" rule.

### 2. MEDIUM - A late finding or disposition for a removed registry entry blocks `summarize` (`installer/catalog_audit.py:1144-1146`, `1204-1211`, `1214-1235`)

- **What this is:** `findings.toml` and `dispositions.toml` are checked against the *current*
  registry ids every time they are read, including by `summarize` and `add-finding`.
- **Problem:** A common approved change is to drop or rename an entry (Phase 23.1 dropped 8).
  The drift row for that entry is then mapped to the commit that dropped it
  (`disposition = "commit:..."`). On the next `summarize`, `_identity_problems` reports
  "entry 'x' is not a registry id" and `read_dispositions`/`read_findings` raise
  `ReportRefused`. The run exits 73 and `SUMMARY.md` is never rebuilt. `add-finding` fails the
  same way, because it reads the existing file first. Orphan *reports* are handled (listed, never
  deleted), but orphan findings and dispositions are not.
- **Fix:** Check entry membership only when a row is added (`add_finding`). At read time, accept
  any non-empty entry string and list the unknown ones as orphans, the same way `status` lists
  orphan reports. Add one test where the registry loses an entry after its disposition was
  written.
- **If we skip it:** The disposition gate breaks exactly when the run is applying its changes,
  and the maintainer has to hand-edit the toml to recover.

### 3. MEDIUM - GitHub rate limiting is recorded permanently as "unknown" (`installer/catalog_audit.py:490-499`, `319-336`, `1280-1292`)

- **What this is:** `facts` turns every failed upstream read into a `- latest: unknown: ...`
  line, and the agent then writes and stores the report.
- **Problem:** Without `GITHUB_TOKEN` or a `gh` login, GitHub allows 60 requests per hour. Step 2
  (`verify`) runs verify-registry first, which reads about 90 GitHub release endpoints, so the
  budget is gone before the first entry. Every GitHub latest then comes back as
  `unknown: HTTPError: HTTP Error 403: rate limit exceeded`. The validator rightly refuses `ok`
  install and update rows, so the agent writes `unknown`. That report is then complete and can
  never be rewritten (line 330). The merge rule lets only a `container:` transcript upgrade an
  `unknown`. One rate-limit window freezes most of the run as unknown, and the only way out is a
  new date. The skill's line "one fresh subagent per entry ... GitHub's anonymous rate limit
  stays unspent" is also wrong: subagents share one IP and one token.
- **Fix:** In `_latest_lines`, when the cause is an `urllib.error.HTTPError` with code 403 or 429
  from `api.github.com`, raise instead of printing a line. Have `facts` exit with a distinct
  code (for example 75, "try again later") that names the reset time. In SKILL.md, tell the agent
  to stop and wait on that code, and fix the subagent sentence. That is about 8 lines of code and
  1 test.
- **If we skip it:** An audit run without a token quietly produces a catalog full of unknown rows
  that looks finished.

### 4. MEDIUM - The landing driver's container check passes inside toolbox and distrobox (`tests/e2e_landing_driver.py:812-814`)

- **What this is:** The driver installs, updates and removes real OpenCode and codegraph, and
  edits agent configs, in `Path.home()`. It refuses to run outside a container.
- **Problem:** "In a container" is decided by `/run/.containerenv` or `/.dockerenv`. Podman
  creates `/run/.containerenv` in every container, including toolbox and distrobox, and both of
  those mount the real `$HOME`. This developer's host is Bazzite, where distrobox is the normal
  way to work. Running `python -m tests.e2e_landing_driver remove opencode` from a distrobox shell
  would delete the real `~/.opencode/bin` and rewrite the real opencode config.
- **Fix:** Also require `Path.home() == Path("/home/tester")`, the harness's `TESTER_HOME`
  (`scripts/container-e2e-verify.sh:31`). One line, plus a test case for a home that is not the
  tester's.
- **If we skip it:** One manual run in the wrong shell mutates the real host, which AGENTS.md
  forbids.

## Nice to have

### 5. LOW - `audit-landing` removes the shared `fedora:latest` base image on every run (`scripts/container-e2e-verify.sh:2714`)

- **What this is:** `landing_teardown` runs `ct rmi "$LANDING_IMAGE"` unless `--keep-image` is
  given. `LANDING_IMAGE` is `fedora:latest` (line 19), which every other target uses too.
- **Problem:** Unlike the schedules target, which removes an image it built, this deletes a base
  image that may have been on the host before the run. The next `bootstrap`, `all` or `nested`
  run has to pull it again.
- **Fix:** Note `ct image inspect "$LANDING_IMAGE"` before `start_container`, and remove the image
  only when this run pulled it.
- **If we skip it:** Extra pulls and slower e2e runs. Nothing breaks.

### 6. LOW - The Debian latest source asks for a source package by its binary name (`installer/catalog_audit.py:353`, `415-419`)

- **What this is:** For `apt`, `sources.debian.org/api/src/<name>/` is read with the apt
  *binary* package name.
- **Problem:** Many Debian source packages have another name (ripgrep is built from
  `rust-ripgrep`). The real 2026-11-13 run shows `unknown: the answer is an error body: 404` for
  ripgrep and alacritty, so most Rust tools always come back unknown.
- **Fix:** Query an endpoint that takes binary names (for example ftp-master's `madison` JSON),
  or map binary names to source names before the read.
- **If we skip it:** The apt rows stay unknown and the agent has to look them up by hand each run.

### 7. LOW - The Pi capability probe runs again on every refresh pass (`installer/version_status.py:844-845`, `installer/postinstall.py:206-219`)

- **What this is:** The drift fact calls `pair.supported(...)`. When `pi` is pending, that starts
  `codegraph install --print-config pi`.
- **Problem:** On a host with `~/.pi` and codegraph v1.6.2 (no `pi` target, so `pi` stays
  pending), every status refresh starts a Node process that always gives the same answer.
- **Fix:** Cache the answer per codegraph binary path for the life of the process
  (`functools.cache` on a small helper keyed by the path).
- **If we skip it:** A fraction of a second of extra work per view entry on those hosts.

### 8. LOW (lean, reuse) - The npm dist-tags URL is built in two places (`installer/catalog_audit.py:457-458` and `installer/versions.py:421`)

- **Problem:** The two copies have to change together, and nothing forces them to.
- **Fix:** Add a single `npm_dist_tags_url(package)` in `versions.py` and use it in both places.
  About -2 lines.

### 9. LOW (lean, merge) - The "is this source cited" check exists twice (`installer/catalog_audit.py:224-226` and `1155-1161`)

- **Problem:** `_check_rows` repeats the URL, backtick-span and `path:line` test inline, and
  `_cited` has the same test plus the container rule. A rule change in one place silently skips
  the other.
- **Fix:** Have `_check_rows` call a shared predicate (with the container branch excluded for
  report rows). About -3 lines.

### 10. LOW (lean, delete) - Small leftovers (`installer/catalog_audit.py:139-140`, `installer/version_status.py:416`)

- `_which` only wraps `shutil.which`. Pass `shutil.which` directly. -3 lines.
- `_version_argv` was renamed to the public `version_argv`, but no new caller uses it: only
  `version_status.py` (and a test docstring) refer to it. Revert the rename to keep the module's
  public surface where it was.

### 11. LOW (split by job) - `catalog_audit.py` holds four unrelated jobs in 1609 lines

- **What this is:** The module holds (a) the report grammar and writer (~330 lines), (b) the
  upstream readers and `facts` (~330), (c) the AST and shell scanner with the JSON-schema `$ref`
  walker (~330), and (d) the findings, dispositions, merge rule and summary (~420), plus the CLI
  (~140).
- **Verdict on size:** The size matches the SPEC's scope (seven subcommands, a validator, a
  merge rule, a gate). I found no dead code (vulture gates it) and no speculative options. The
  only real cuts are the small items 8-10. The scanner (c) shares nothing with the rest except
  `ScanRow` and the owner labels, and it is the hardest part to read. Moving it to
  `installer/catalog_scan.py` would split the module by job, not by line count. This saves no
  lines; do it only if the module keeps growing.

## Checked and fine

- The GitHub token goes only to `api.github.com` (`installer/versions.py:370`). npm, brew, Arch,
  Fedora, Debian and PyPI reads never see it. Every fetch has a 10 s timeout.
- `write` and `add-finding` take only registry ids (or the two owner labels) as file names.
  `run_dir` refuses symlinks and bad dates. `_line_has` stays inside the repo.
- Retired `permission` key: ledger entries for it are kept (`_kept_entries` touches only written
  or dropped paths), the revert table includes it, and `setting_facts` never shows it as pending.
  Tests cover ours, the user's, a changed value and user removal.
- `opencode2 service stop` binds only to a receipt-proven `opencode2` leaf. A v1 receipt skips
  it. A failed recipe deletes nothing and keeps the receipt (`installer/app.py:826-829`).
- The Pi gate drops only `pi` from the CSV, never claude or codex, and keeps the skip note when
  registration fails. The copilot `ide/`-only rule has tests.
- npm latest uses the existing fetch budget, backoff and stale rules (tests at
  `tests/test_version_status.py:512-668`).
- Scale: the summary is O(entries x rows) at worst, which is trivial for 86 entries.

Verdict: fix 1, 2, 3 and 4 first.
Lean: about -10 lines possible.
Not checked: whether OpenCode 2 still honours the retired `permission` key, and how
