# Phase 24.3 Plan 09: the audit-landing container target Summary

**A disposable-container harness that has the installer's own code install, tune, update and remove OpenCode 2 and codegraph, with 13 ordered steps and a named, host-tested verdict line for every pass, failure and unproven claim; written and host-tested here, never run.**

## What was built

- `audit-landing` in `scripts/container-e2e-verify.sh`: `LANDING_*` constants, `landing_infeasible`, `landing_environmental`, `landing_teardown` (EXIT trap), `landing_stage`/`landing_bootstrap` (start, prereqs, tester, workspace, Homebrew, uv, PATH, sync; any failure is infeasible with its stage name, exit 2), `landing_driver` (`uv run --isolated --no-dev python -m tests.e2e_landing_driver` as the tester, whose login PATH is Homebrew plus `~/.local/bin`), `landing_step` (transcript under `.e2e-artifacts/container-landing/`, environmental failure exits 2, a non-zero exit or a `_FAILED`/`_UNPROVEN` line fails the step) and `cmd_audit_landing`. No token is passed and no host directory is mounted.
- The 13 steps, in order: `install opencode`, `latest opencode`, `update opencode --with-service`, `remove opencode --with-service`, `install opencode`, `remove opencode`, `seed-v1 opencode`, `remove-v1 opencode`, `seed-v1 opencode`, `update opencode`, `codegraph copilot-and-pi`, `codegraph unregister`, `codegraph ide-only`.
- `tests/e2e_landing_driver.py`: the verbs and verdicts of the plan. Removal and unregistering use `app.perform_uninstall` with a one-tool `UninstallDecision` built from the fresh `uninstall.removal_plan(tool, bin_dir, verify=True)`. The tuning is read from the file `agent_settings.settings_file("opencode", ...)` chose. Service commands run through the receipt-proven absolute `opencode` path with every stream closed, and serve processes are found by scanning `/proc/*/cmdline`.
- `tests/test_shell_scripts_path.py`: the four `export PATH=` line pins moved (311, 432, 487, 754 became 329, 450, 505, 772), as the plan allows when the lines shift.

## Deviations from Plan

### Auto-fixed / auto-added

**1. [Rule 3 - Blocking] `bootstrap_homebrew` split out of `bootstrap_homebrew_and_uv`**
- **Issue:** the landing stages must name a Homebrew failure apart from uv and the PATH wiring. Calling the combined function masks a failed Homebrew install, because errexit is off inside a captured stage and only the last command's status survives.
- **Fix:** the Homebrew block moved verbatim into `bootstrap_homebrew`; `bootstrap_homebrew_and_uv` calls it, then `bootstrap_uv` and `write_tester_path`, in the same order. No test extracted that function.
- **Commit:** 04725ee8

**2. [Rule 2 - Missing critical] the driver refuses to run outside a container**
- **Issue:** its verbs install and remove real tools and `shutil.rmtree` the tester's `~/.copilot`. A mistaken host run would mutate the developer's host, which the project forbids.
- **Fix:** `main` exits 2 unless `/run/.containerenv` or `/.dockerenv` exists; tested with a patched `_in_container`.
- **Commit:** 04725ee8, e63ae145

**3. [Rule 2 - Missing critical] extra host tests beyond the plan's list**
- The shell helpers (`landing_stage`, `landing_step`, `landing_environmental`, `landing_infeasible`) have tests, as does the `/proc` serve-process matcher, and a test pins that every step the script runs is accepted by the driver's parser (`accepts`, new public function).

None otherwise: the plan's tasks, verdict line names and step order are as written.

## Concerns for the orchestrator (24.3-11 Task 2)

- **The verbs could not be exercised against the code they drive.** This worktree's base is wave 4: `registry.toml` still holds the v1 opencode entry, and 24.3-06 (v2 method and `remove` recipe), 24.3-07 (`permissions` rule) and 24.3-08 (copilot and Pi targets, `HookPair.supported`) land in parallel. The verdict functions are host-tested; the verbs are type-checked (pyright strict) but only a real run proves them against the merged wave.
- **Assumed interfaces:** `<opencode> service start|restart` and a serve process whose command line is `<opencode|opencode2> serve ...`; `version_status._hook_fact(tool, receipt, hosts, presence_error, binary, probe_output)` called through `vars(version_status)["_hook_fact"]` with the signature it has at this base (24.3-08 may change it; the driver then fails loudly with `ERROR`); `engine.install_tool`'s `postinstall_warning` as "the hook warning".
- **The v1 removal depends on the product's plan:** `remove-v1` removes with the shipped (v2) tool against a receipt that proves only `opencode`. If `removal_plan` refuses that receipt, `TRACER_OPENCODE_V1_REMOVE_FAILED detail=removal failed` is the finding, which is what review R1-03 wants proven.
- **`LANDING_IMAGE` is `fedora:latest`** (the distro entry's base image). Teardown's `rmi` leaves it when `tools-installer-e2e-fedora` still uses it; `TRACER_LANDING_TEARDOWN_LEFT` names a container that did not go.
- **Network:** codegraph's install and `latest opencode` (npm) go to the network and GitHub's anonymous API; no token is passed on purpose (T-24.3-33).
