## Goal

A `catalog-audit` skill keeps every registry entry honest. It loops over the catalog one entry at a time, compares the pinned, installed and latest upstream versions, reads the changelog in between, and checks the install, update, removal and tuning steps and the scripts behind them against upstream. It writes one report per entry plus a summary of proposed changes, can resume mid-loop, and changes nothing without approval. Its first run lands the OpenCode 2 and Pi MCP findings (and the copilot codegraph host from Backlog 999.12) in the registry and the postinstall code.

## Requirements

1. **Skill that builds on tool-onboarding and verify-registry (AUDIT-01)**: A project skill at `.claude/skills/catalog-audit/` audits the catalog by reusing the two existing tools.
   - Current: `tool-onboarding` reviews one entry on request; `make verify-registry` checks only downloadable methods; no skill loops over the registry.
   - Target: `catalog-audit/SKILL.md` names `tool-onboarding`'s steps (classify, platforms, method, removal, tier, dependencies, postinstall, customizations with TUNE-04's rule, classifiers, `# Verified`) as its per-entry criteria by reference, without restating them, and takes `make verify-registry`'s report as the result for downloadable methods instead of re-checking assets or checksums.
   - Acceptance: the skill file exists with valid frontmatter; it links `.claude/skills/tool-onboarding/SKILL.md` and `make verify-registry`; it contains no copy of tool-onboarding's step tables or of verify-registry's asset/checksum checks.

2. **Per-entry version, changelog and upstream-steps report (AUDIT-01)**: Every registry entry gets one report.
   - Current: an entry's only audit trail is its `verified` date and `# Verified` comment.
   - Target: for each `[[tool]]` entry, in registry order, the report records the pinned or declared version (or "unpinned" with the method kind), the `verified` date, the installed version from a read-only probe (or "not installed"), the latest upstream version with its source, the changelog notes between the installed or pinned version and the latest that touch install, update, removal, config or MCP, and one result per check (install method, update argv, removal recipe and `paths`, tuning keys, postinstall hook) as `ok`, `drift` or `unknown`, each with a cited source URL or command.
   - Acceptance: a run produces exactly one report per entry in the registry at run time; every check row has a status and a source; an entry whose upstream cannot be reached reads `unknown`, never `ok`.

3. **Install and customization script audit (AUDIT-02)**: The scripts behind install and tuning are audited for drift and unsafe patterns.
   - Current: no review covers the postinstall hooks, post-install actions, tuning keys, shims or shell scripts as a set.
   - Target: the audit covers `installer/postinstall.py` hooks and their target maps, `installer/post_install.py` actions, `installer/agent_settings.py` key tables, the shims the installer writes (the `npx` guard shim, the cursor-agent shim from 24.2) and `scripts/*.sh`. It flags drift against the target tool's current CLI or config schema and these unsafe patterns: privilege escalation (`sudo`, `pkexec`, `doas`), `--target auto`/`all` or any write for an absent host, a blind overwrite of user config, a write outside the declared `paths`, and argv that a shim rewrites into a different command. Each finding names the script, its file:line and the entry it belongs to.
   - Acceptance: the summary lists every script finding with file:line; the run over today's tree reports the `permission` key (`agent_settings.py:538`) as drift for OpenCode 2. *(amended 2026-11-13, 24.3 research: the key now sits at `agent_settings.py:679` (`_KEYS[("opencode", "auto-approve")]`); the first full run happens on the untouched tree before R6-R9 land, so "today's tree" still carries the key when the run reports it, needs confirmation)*

4. **Run directory, summary, resume and approval (AUDIT-02)**: A run writes a dated run directory, resumes mid-loop, and changes nothing else without approval.
   - Current: none.
   - Target: a run writes `.planning/audits/catalog/<YYYY-MM-DD>/<entry-id>.md` per entry and `SUMMARY.md` with the proposed registry and script changes, each naming its entry, evidence and risk. A run stopped mid-loop and started again for the same date continues at the first entry without a complete report and keeps the reports already written. Without the user's explicit approval the run writes nothing outside its run directory; an approved change goes through `make verify-registry`, `make validate` and `make test`. *(amended 2026-11-13, 24.3 research: `SUMMARY.md` is rebuilt from the reports plus a committed `dispositions.toml` in the run directory, so the R10 commit and backlog mapping survives every rebuild (D-04 amended), needs confirmation)*
   - Acceptance: stopping after entry k and rerunning produces the same report set with entries 1..k unchanged; `git status` after an unapproved run shows changes only under the run directory.

5. **Read-only live checks; container-only installs (AUDIT-01, 23.1)**: The audit never mutates the host.
