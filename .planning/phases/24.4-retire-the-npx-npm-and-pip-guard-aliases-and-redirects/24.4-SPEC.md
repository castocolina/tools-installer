# Phase 24.4: Retire the npx, npm and pip guard aliases and redirects — Specification

**Created:** 2026-11-14
**Ambiguity score:** 0.10 (gate: ≤ 0.20)
**Requirements:** 6 locked
**Amended:** 2026-11-14 (24.4 discuss D-07/D-16/D-17: R2 every well-formed block, R6 rule doc and surface test; edge table re-run); 2026-11-14 (24.4 review cycles 1-2: R3 swap wording reworded in place to the identity re-check, re-verified immediately before unlink)

## Goal

The installer stops writing its package-manager guard: no PATH shims for npm, npx, pnpm, pip or pip3 and no `tools-installer ban` alias block. Every launch removes the guard files and blocks an earlier version wrote on an existing host, and the user's own lines and files stay as they are.

## Requirements

1. **No guard writer (GUARD-01)**: No route of the installer creates or rewrites a guard shim or the guard alias block.
   - Current: the Policies row `ban`, `run_guard` (`--guard`, `make guard`) and the launch repair write or rewrite the five shims and the `tools-installer ban` block.
   - Target: no code path writes a file that carries `# tools-installer-ban-shim` or `# tools-installer-redirect-shim`, or a `# >>> tools-installer ban >>>` block. The shim and alias renderers, the installers of the three shim kinds, the npx translator and both `rewrite_outdated_*` repairs are deleted.
   - Acceptance: in a scratch HOME, a headless install, `--fix`, `--doctor`, applying every Policies row and an uninstall create no file with either sentinel in the managed bin dir and no ban block in any rc file. No function that renders or writes a shim body or the ban block remains under `installer/` or in `setup.py`.

2. **Launch removes old guard files (GUARD-02)**: Every route that runs the launch repair today removes the guard an earlier version wrote.
   - Current: `_launch_repairs` rewrites an outdated ban block and an outdated npx redirect, and never removes either.
   - Target: the same single launch step removes the last well-formed `# >>> tools-installer ban >>>` … `# <<< tools-installer ban <<<` block from `~/.myshellrc`, the zshrc and `~/.bashrc`. From the managed bin dir it removes each file named `npm`, `npx`, `pnpm`, `pip` or `pip3` that is a regular file by its own `lstat` (never a symlink), is at most 8 KiB and carries either sentinel, hand-edited or not. Each removal prints one line naming the path. A failure prints a warning naming the path and how to fix it, and never raises or stops the launch. A launch with nothing left to remove prints nothing about the guard.
   - *Amended 2026-11-14 (24.4 D-07):* every well-formed ban block in a file goes in one launch, not only the last one, so a hand-duplicated copy cannot make the second launch change bytes; an orphan begin marker with no end after it still stays.
   - Acceptance: a scratch HOME seeded like the owner's host (five shims and the ban block in `~/.myshellrc`) has no shim and no ban block after one `--doctor` launch, and the output names each removed path. A second launch changes no byte and prints no guard line. A read-only bin dir yields a warning line and exit status unchanged.

3. **The user's own lines and files stay (GUARD-03)**: The cleanup changes nothing it did not write.
   - Current: `rewrite_outdated_ban_aliases` already rewrites only the marker-owned block and keeps every other byte; `rewrite_outdated_npx` re-checks the file's identity before replacing it.
   - Target: every byte outside the removed block stays as read, CR line endings included. A user's own `alias npx=…`, `alias npm=…` or `alias pip=…` outside the markers stays. A file with an orphan begin marker and no end marker is left byte-identical, and so is a non-UTF-8 rc file or one over 1 MiB. In the bin dir, a symlink, an unmarked file, a file over 8 KiB, a FIFO or a non-UTF-8 file at one of the five names is left alone. A marked file replaced by another file before the identity re-check, which is re-verified immediately before unlink, is not deleted; a swap landing between that re-check and the unlink is the documented residual below. *(amended 2026-11-14, 24.4 review cycle 2, H-03)*
   - *Amended 2026-11-14 (24.4 review cycle 1, H3):* the shim's identity is re-verified immediately before unlink (an `O_NOFOLLOW` re-open whose device, inode and bytes must match the read snapshot); a file swapped before that re-check is not deleted. No userspace unlink is atomic against a swap, so a swap landing between the re-check and the unlink is a documented residual (a `shortcut:` comment in `installer/legacy_guard.py`), not a guarantee.
   - Acceptance: scratch-HOME tests for each case above show the file byte-identical, or only the block removed. A real `pnpm` binary and a volta `npx` symlink in the bin dir survive the launch.

4. **The guard's surfaces are gone (GUARD-04)**: Nothing offers, reports or toggles the guard.
   - Current:
     - Policies lists `ban` with its detail text;
     - `make guard`/`make unguard` and `--guard`/`--unguard` exist;
     - Doctor prints "Package manager guards active", the per-command labels and the PATH-order and redirect warnings;
     - the Uninstall view and the CLI uninstall preview offer to remove "the pip/npm ban".
   - Target: the `ban` row, its detail text, both make targets, both CLI flags, the Doctor guard section and warnings, and the uninstall ban row and preview line are removed. An old `--guard` or `--unguard` flag fails as an unknown option, and `make guard` fails as an unknown target.
   - Acceptance: the Policies list has no `ban` row. `setup.py --guard` exits 2 with argparse's "unrecognized arguments". `make help` lists neither target. A Doctor run in a scratch HOME prints no guard section. The Uninstall view has no ban row.

5. **No PATH workaround, and no leftover is run (GUARD-05)**: The installer handles PATH as on a host that never had the guard. It still never runs or counts a leftover shim it could not remove.
   - Current:
     - `executors.shell_path` moves `~/.local/bin` to the end of PATH in vendor install shells.
     - `real_binary`/`real_pnpm`, `look_through_shim`, `status._is_installer_shim` and the schedule runner's `_resolve` skip files that carry a sentinel.
   - Target: shells the installer spawns get PATH in its normal order. Resolving pnpm or npm for an install, update or scheduled job, and checking whether a tool is present, still skip a file that carries a guard sentinel. A leftover the launch could not remove is never executed as the real tool or counted as the tool being present.
   - Acceptance:
     - A vendor install shell's PATH equals the process PATH, in the same order.
     - With an unremovable pnpm wrapper planted in a read-only scratch bin dir and no real pnpm, pnpm reads absent and no install runs the wrapper.
     - With a real pnpm elsewhere on PATH, that pnpm is resolved.
     - The schedule runner skips a planted npm shim.

6. **Docs, requirements and tests follow (GUARD-06)**: Nothing in the live docs or tests describes the guard as a feature.
   - Current:
     - `README.md`, `docs/TROUBLESHOOTING.md`, `AGENTS.md` and the `Makefile` help describe `make guard`/`make unguard` and the ban.
     - `catalog_audit._PY_SURFACES` names `installer/guards.py`.
     - HOST-02 is listed as a live requirement.
     - About 30 test files test the guard.
   - Target:
     - The live docs describe the launch cleanup and do not offer the guard. AGENTS.md no longer names `make guard`/`make unguard`, and its `make doctor` line names the guard cleanup instead of the rewrite.
     - `_PY_SURFACES` names only files that exist.
     - REQUIREMENTS.md marks HOST-02 superseded by this phase.
     - Tests of deleted behaviour are deleted, and GUARD-02, GUARD-03 and GUARD-05 have tests.
     - Historical documents (`docs/prds/`, `docs/superpowers/`, earlier phase directories) are not edited.
   - Acceptance: `grep -rn "make guard\|unguard\|pip/npm ban" README.md docs/TROUBLESHOOTING.md AGENTS.md Makefile installer setup.py` finds nothing. `make validate && make test` pass. The catalog-audit scan runs without a missing-file error.
   - *Amended 2026-11-14 (24.4 D-16, D-17):* `catalog_audit._surfaces` already skips a missing file, so the last acceptance line cannot fail; it is replaced by a test that every `_PY_SURFACES` entry exists. `.claude/architecture.md` (a live rule document linked from AGENTS.md, which names `guard_status`, `guard_state`, `ban_policy` and the looked-through redirect shim) joins the edited docs and the grep.

## Boundaries

**In scope:**
- Deleting the guard writers, renderers, the npx translator and both launch rewrites (GUARD-01)
- The launch removal of old guard shims and ban blocks, with its notices (GUARD-02, GUARD-03)
- Removing the Policies row, make targets, CLI flags, Doctor section and uninstall ban row (GUARD-04)
- Restoring the normal PATH order in installer-spawned shells. Lookups keep skipping marked leftovers (GUARD-05)
- README, TROUBLESHOOTING, AGENTS.md, Makefile help, `catalog_audit._PY_SURFACES`, REQUIREMENTS.md HOST-02, and the tests (GUARD-06)

**Out of scope:**
- The install-method priority (brew, then bun, then volta) and how JavaScript CLIs install: Phase 24.5.
- The cache redirects (`env_redirect`, `cache-redirect:bun`) and the shell tweaks: they are not the guard.
- Any replacement nudge toward uv or pnpm (an alias, a hook, a doctor hint): the owner asked for removal, not a softer guard.
- Editing historical PRDs, superpowers plans or earlier phase artifacts: they record what was decided then.
- The headless schedule route: it runs no launch repair by design (one plain result line). Its lookups keep skipping marked files (GUARD-05).
- The test-suite subprocess guard (`tests/child_guard/`, HOST-03): it is unrelated to the user-facing guard.

## Constraints

- Zero sudo, and no write outside the user's own rc files and the managed bin dir.
- The launch removal never raises. A read or write failure is one warning line, like `strip_legacy_aliases` and the current rewrites.
- Writes go through `atomic_write_text`. A shim is deleted only after its identity is re-checked against the read snapshot (`read_snapshot`/`snapshot_matches`).
- Tests use a scratch HOME. Nothing runs `make setup`, `fix`, `doctor`, `uninstall`, `guard` or `unguard` on the developer's host.
- No new Policies knob and no new setting.
