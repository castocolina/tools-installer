<objective>
Make the Catalog view version-aware for `github_release`-kind tools: resolve each one's installed vs. latest version (reusing the existing `resolve_github_tag`), cache the result on disk with a `checked_at` timestamp so a 7-day-fresh entry is never re-fetched, and run the whole check on a Textual background `Worker` so it never blocks first paint or keypresses. This is the phase's tracer — it wires every layer this phase touches (parsing, persistence, background threading, rendering) end to end for one real, already-outdated proving case (`codegraph`, live-verified 1.2.0 → v1.6.0 on this machine) before Plan 12-02 generalizes it to every `github_release` tool and to brew/pnpm/uv-tool-managed ones.

Purpose: SC#1-3 of ROADMAP.md's Phase 12 (github-release version display, cached/staleness-tracked state, non-blocking background refresh) — the "what's out of date" half of the phase goal.
Output: `installer/version_cache.py` (new), `installer/version_status.py` (new), `extract_observed_version`/`is_outdated` added to `installer/versions.py`, a version-refresh worker + a new "Ver" column on the Catalog screen.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| GitHub API response -> installer | `resolve_github_tag`'s parsed `tag_name` (untrusted, third-party-repo-controlled JSON) crosses into this phase's version-comparison and display logic |
| Local cache file -> installer (next session) | `~/.local/state/tools-installer/versions.json`, writable by anything running as the same local user, is read back and trusted as "the last known latest version" on the next Catalog view |
| Background worker thread -> main render thread | The version-refresh `@work` worker's result crosses back into Textual's UI state via `post_message` |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-12-01 | Tampering | `~/.local/state/tools-installer/versions.json` | low | mitigate | `load_version_cache` type-checks every field before use (mirroring `installer/model.py`'s tomllib validation discipline) and never raises on malformed JSON — a tampered/corrupted entry degrades to "stale, re-fetch" rather than being trusted; cached values are used only for display/comparison, never interpolated into a shell string or subprocess argv (no executor in this phase reads the cache file). |
| T-12-02 | Spoofing | GitHub API `tag_name` / local `--version` output | medium | mitigate | Both sides of every comparison go through `extract_observed_version`/`parse_version`'s strict regex before being trusted as a version; an unparseable or adversarially-crafted string (e.g. a `tag_name` with shell metacharacters) fails to match and degrades to `unknown` rather than being displayed or compared as a real version. |
| T-12-03 | Denial of Service | GitHub fetch / local `--version` probe inside the background worker thread | medium | mitigate | `probe_version` already bounds the local `--version` call at `PROBE_VERSION_TIMEOUT` (`installer/versions.py:112`, 5s); `resolve_github_tag`'s `urlopen_fetch` already bounds its own network call at a 10s `urlopen` timeout (`installer/versions.py:165`) — both existing bounds are reused unchanged, so a wedged network call cannot leak an unbounded worker thread. |
| T-12-04 | Information Disclosure | `versions.json` readable by any local process running as this user | low | accept | Reveals only installed tool version strings — identical information to running `<tool> --version` directly. No new exposure; the file lives under the same `~/.local/...` userspace convention (default-umask, user-only-writable) this project already uses for every other managed artifact. |

</threat_model>
