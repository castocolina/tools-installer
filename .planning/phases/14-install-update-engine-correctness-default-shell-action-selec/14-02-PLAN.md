## Design decisions this plan implements

- **D-03 — refusals surface in the post-run summary, with the existing wording.**
  `CatalogScreen.action_update_tool` formats its refusal as `cannot update {tool_id}: {reason}` where
  the reason is the ownership record's own explanation or the fallback "no manager claimed this
  tool". The batch path reuses that exact sentence shape. What it prefixes or groups it under is
  Claude's discretion (CONTEXT.md says so explicitly); the substantive reason text is not.
- **Refusals are collected, not narrated.** CONTEXT.md is explicit that the reason surfaces in the
  post-run summary rather than inline during the run. Accumulate per tool, render once at the end.
- **A refused update is not a batch failure.** `installer/session.py::Summary` and the exit code
  `UnifiedApp` derives from it are about installs. An update that the gate refused is information,
  not a failed install, and must not be smuggled into the failed/mismatched buckets — doing so would
  change `setup.py`'s process exit code for a case that is not an install failure.
- **The post-run version re-probe mirrors the `u` keybind.** After a successful update,
  `_update_tool_worker` calls the refresh service for just that tool so the new version is known.
  The batch loop does the same, for the same reason, so the shared status cache is accurate and the
  report can name the version the user now has.

## Known follow-up, deliberately out of this plan

`CatalogScreen` keeps its own copy of version statuses, refreshed by its own worker on mount and on
view entry. Returning from the pushed `ExecuteScreen` does not re-enter the view, so the catalog's
Ver column can still show the pre-update value until the next refresh. That is a pre-existing
display-staleness property of the Phase 13 screen stack, not part of either bug this phase was
opened for, and fixing it means touching `installer/wizard_app.py`'s modal-dismissal path. Record it
in the SUMMARY as a follow-up rather than widening this plan.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| update service -> post-run report | outcome text, including `detail` that can carry child-process output, is rendered into a log the user reads |
| update outcomes -> install summary -> process exit code | mis-bucketing an update result would change what `setup.py` returns to the shell |
| worker thread -> widgets | anything the worker learns must cross back via a message, never a direct widget write |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-14-06 | Information Disclosure | an update outcome's `detail` carrying raw child-process bytes into the log | medium | mitigate | the update section renders through the existing captured-console helper, which already passes its output through `sanitize_log_line` (`installer/execute_screen.py:549-556`) |
| T-14-07 | Repudiation | an update silently refused, leaving the user believing it ran | high | mitigate | D-03's refusal line is mandatory and carries the ownership record's own reason; Task 2's `-k blocked_update` gate asserts it reaches the post-run log |
| T-14-08 | Tampering | an update result altering the install summary and therefore the process exit code | medium | mitigate | update results travel on their own `InstallRunFinished` fields and are never added to a `Summary` bucket or to the run-level error; Task 2 asserts the buckets are unchanged |
| T-14-09 | Denial of Service | a post-update version re-probe raising and tearing down the worker before the report is posted | medium | mitigate | the re-probe goes through `run_live`, and the worker's existing `try/finally` still posts `InstallRunFinished` on every path |
| T-14-10 | Spoofing | a refusal reason rewritten into softer wording that hides which manager refused | low | mitigate | the reason text is asserted to be the one `CatalogScreen.action_update_tool` produces, and a source-inspection gate fails if the two drift |
| T-14-SC | Tampering | npm/pip/cargo installs | high | accept | this phase introduces no external package; `14-RESEARCH.md`'s "Package Legitimacy Audit" section records the gate as not applicable |
