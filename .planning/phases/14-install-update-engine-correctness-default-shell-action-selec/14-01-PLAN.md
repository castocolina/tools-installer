<objective>
Bug 1, end to end, on the one path the real `make setup` actually takes.

Selecting a tool that the catalog itself is displaying as outdated and pressing enter currently does
nothing at all. The drop happens inside `installer/deps.py::resolve_dependencies`, which treats
"installed" as "satisfied" regardless of version and removes the tool from the returned order before
`install_tool` is ever called. The only working update mechanism today is the separate per-row `u`
keybind (`CatalogScreen.action_update_tool`). This plan gives that same mechanism a second call site
so the main select+enter flow triggers it too (D-01), behind the confirm gate that already exists
(D-02).

**Read this before anything else: `14-CONTEXT.md`'s canonical refs are stale.** They name
`installer/app.py::run_wizard` and its `prompter.confirm(...)` as the integration point. Phase 13
rewired the interactive flow: `run_wizard` is now reachable ONLY through the `--all`/`--categories`
CLI flags (`setup.py:891`), and the genuine `make setup` path goes
`CatalogScreen.Decided` -> `UnifiedApp.on_catalog_screen_decided` -> a pushed
`installer/execute_screen.py::ExecuteScreen`. `14-RESEARCH.md`'s "Current Implementation Analysis"
documents the correction with line numbers. Every decision (D-01 through D-07) still stands exactly
as written; only the file they land in moved. A task that edits `run_wizard` for D-01 has fixed a
code path this bug report never touches.

Purpose: make the reported bug stop happening, on the smallest possible slice, with the composition
root wired for real so this is production code and not a demo.
Output: `ExecuteInputs` carries the two shared services, `ExecuteScreen` splits selected tools into
install-vs-update and dispatches updates through the existing service, and `setup.py` hands it the
same service instances the three catalog screens already share.
</objective>

## Design decisions this plan implements

- **D-01 — one update mechanism, two call sites.** The batch path constructs an `UpdateTarget` and
  calls `UpdateService.run`, exactly as `CatalogScreen._update_tool_worker` already does. It does not
  re-derive the ownership gate: `UpdateService.run` re-resolves ownership freshly on every call
  (`installer/update.py:366-376`) and refuses on its own, so a caller that re-checks would only be
  able to drift away from it.
- **D-02 — the existing confirm is the consent.** All update dispatch happens inside
  `_execute_worker`, which only runs after `action_start` (bound to `enter`,
  `installer/execute_screen.py:282,348-356`). No new prompt, no new modal, no new keybinding.
- **The eligibility predicate is copied, not invented.** `CatalogScreen.action_update_tool` skips a
  tool only when its status is present AND its `outdated` flag is `False`. Both "no status yet"
  (the version probe is asynchronous and may not have finished) and "definitely outdated" attempt the
  update. `tests/test_catalog_tui.py:1440-1488` already locks that in for the `u` keybind; the batch
  path must behave identically or a slow probe silently reinstates the bug.
- **`installer/deps.py` is not touched.** Teaching a pure, platform-and-presence-only resolver about
  version state and manager ownership would couple core to screen-only data. The split is computed
  beside the resolver call, from the same selected list, in `ExecuteScreen.on_mount`.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| catalog selection -> batch execution | ids the user marked cross into a path that mutates installed software |
| screen -> update service | the screen decides WHICH tools to mutate; the service decides WHETHER each mutation is authorised |
| version-probe worker -> eligibility decision | an asynchronous, possibly-incomplete probe result feeds a mutate/skip decision |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-14-01 | Elevation of Privilege | a batch update bypassing the ownership/confidence gate | high | mitigate | every update goes through `UpdateService.run`, which re-resolves ownership freshly and refuses on its own (`installer/update.py:366-376`); Task 1's verify gate asserts no grade check and no direct lower-level mutation call exists in `installer/execute_screen.py` |
| T-14-02 | Tampering | mutating a tool the user never selected | high | mitigate | the update list is derived only from `select_tools(catalog, self._ids)`, the same ids the install path uses; nothing else can enter it |
| T-14-03 | Elevation of Privilege | mutation before consent | high | mitigate | dispatch lives in `_execute_worker`, reachable only from `action_start`; Task 2 asserts nothing runs before `enter` |
| T-14-04 | Denial of Service | two concurrent updates of the same tool corrupting a manager's state | medium | mitigate | the service's existing single in-flight latch is taken per tool and released in a `finally`, mirroring `action_update_tool`/`_update_tool_worker` |
| T-14-05 | Denial of Service | a long update tail that cannot be stopped | low | mitigate | `_should_continue()` is checked between tools, reusing the weak cancel Phase 13 built; an in-flight child still finishes, which is the deliberate existing trade |
| T-14-06 | Information Disclosure | child-process output from an update reaching the log unsanitised | low | accept | this plan writes nothing to the log; plan 14-02 owns rendering and routes everything through the existing `sanitize_log_line` |
| T-14-SC | Tampering | npm/pip/cargo installs | high | accept | this phase introduces no external package; `14-RESEARCH.md`'s "Package Legitimacy Audit" section records the gate as not applicable |
</threat_model>
