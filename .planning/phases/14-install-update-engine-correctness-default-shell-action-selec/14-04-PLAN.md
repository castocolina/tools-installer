<objective>
Plan 14-03 made `set_login_shell` real but left its output unread and its confirmation unbound: the
reviewed instructions ride on `InstallOutcome` with no renderer, and `install_tool`'s new
confirmation parameter has no production caller, so the only way it is ever non-`None` today is a
test passing it directly.

This plan closes both, and does the console entry point first because it is the simpler of the two
and it proves the seam without a Textual pilot. `installer/app.py::run_wizard` is reachable only via
the `--all`/`--categories` CLI flags since Phase 13 rewired the interactive path — but it still calls
the same `run_installs`/`install_tool`, so a tool installed through it would otherwise reach a
newly-implemented action that can never fire. Leaving one entry point structurally unable to reach a
just-implemented action is the same defect class this phase was opened to fix.

The binding is done with a narrow adapter rather than by widening `installer/session.py`'s `Install`
protocol. That protocol is implemented by 29 fake installs across four test files and by
`installer/execute_screen.py`'s attribution wrapper; adding a parameter to it would force a
mechanical edit into every one of them, including files other plans in this wave own.

Purpose: make the action's output visible and its consent bindable, on the console path.
Output: a renderer, a confirmation-binding adapter, and the `run_wizard` wiring that uses both.
</objective>

## Design decisions this plan implements

- **The shared `Install` protocol does not change.** A second, wider protocol describes "an install
  that also accepts a sensitive-action confirmation", and a small adapter binds the confirmation and
  hands back something satisfying the original, unchanged protocol. Only the two call sites that
  actually bind a confirmation ever mention the wider one.
- **`run_wizard` builds its own confirmation from the prompter it already holds.** No new parameter
  is threaded down from `setup.py`, and `setup.py` gains nothing — the decision of what to ask and
  when to ask it belongs in `installer/`, where pyright, coverage and tests apply (architecture
  rule 4).
- **`--yes` means no callback, which means skip.** This mirrors the rule the same function already
  applies one line away for the checksum-mismatch prompt (`installer/app.py:157`) and the rule
  `installer/session.py:85` documents for unattended runs. It is not a new policy, it is the existing
  one applied to a new sensitive action.
- **The sensitive question names the tool and what will change.** The batch question is
  "Install the selected tools?"; this one has to be distinguishable from it by a user reading a
  console, not only by a test reading a call count.
- **A new renderer, not a widened old one.** `render_handoff` prints reviewed steps for a tool that
  did NOT install (manual-required). These instructions belong to a tool that DID install, and a
  successful tool appearing under a "manual setup required" heading would be actively misleading.

## Artifacts this plan produces

New symbols, named exactly — the verify gates import them by these names:
- `installer/render.py`: `render_post_install_handoff`.
- `installer/session.py`: `SensitiveInstall`, `with_sensitive_confirm`.
- `installer/app.py`: no new public symbol; `run_wizard`'s `install` parameter type widens to
  `SensitiveInstall` and its body gains the confirmation closure, the binding call and the new
  renderer.

No new files, no new CLI flags, no `setup.py` change.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| prompter answer -> bound install seam -> the sensitive action's gate | one console answer authorises a system mutation |
| an unattended `--yes` run -> the sensitive action | nobody is present to refuse |
| instruction text -> the rendered console | the user is being shown a command and invited to run it |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-14-12 | Elevation of Privilege | a sensitive action firing on a scripted `--yes` run | high | mitigate | the confirmation closure is `None` when unattended, which the action treats as skip; Task 3's `ORDER-OK` gate additionally asserts the unattended check precedes the binding so the question is never even constructed for such a run (ASVS V4) |
| T-14-19 | Spoofing | the batch confirm being mistaken for consent to change the login shell | high | mitigate | the sensitive question is asserted to be distinct text naming the tool, and `FakePrompter` is extended specifically so a test can answer the two differently and read both (D-02's "the batch confirm is the consent" applies to updates, never to a sensitive system mutation) |
| T-14-20 | Tampering | instruction text mangled by markup interpretation, so the user copies a command that is not the one that was reviewed | medium | mitigate | Task 1 renders the lines without markup interpretation and asserts a bracketed fragment survives to the output |
| T-14-21 | Elevation of Privilege | widening the shared install protocol and silently changing the call contract of 29 existing fakes | medium | mitigate | the protocol is asserted parameter-for-parameter to be unchanged; binding happens at a composition point instead |
| T-14-22 | Repudiation | reviewed instructions produced but never shown, so the user cannot know an action was offered | medium | mitigate | the renderer joins the report sequence both entry points use; plan 14-05 adds the second call site |
| T-14-SC | Tampering | npm/pip/cargo installs | high | accept | this phase introduces no external package; `14-RESEARCH.md`'s "Package Legitimacy Audit" section records the gate as not applicable |
