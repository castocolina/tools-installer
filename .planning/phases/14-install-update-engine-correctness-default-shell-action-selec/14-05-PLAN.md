The last wiring, and the write-up.

`installer/execute_screen.py` is the only path the real `make setup` wizard takes, and it is the only
remaining place where `install_tool`'s sensitive-action confirmation is still `None` — so on the
production path, `set_login_shell` would be implemented, declared, rendered and reachable from the
CLI flags, and still never fire. This plan gives it the in-app prompt, prints what it produces, and
records both of this phase's mechanisms in `.claude/architecture.md` behind a test so the
explanation cannot rot away silently.

The prompt must use `ask_from_worker`, the one worker-to-modal mechanism this codebase has. Phase 13
chose it by spike rather than assumption and recorded the choice in `13-VALIDATION.md`; it is a
documented exception to `.claude/architecture.md` rule 2, scoped to thread workers that have no
callback to return into. A second, ad hoc mechanism for one more prompt would put that exception's
scope back in play.

Purpose: close bug 2 on the production path and leave both mechanisms documented.
Output: the in-app sensitive-action prompt, the instructions in the post-run report, and the
architecture record with its test.

## Design decisions this plan implements

- **One worker-to-modal mechanism.** The sensitive-action prompt goes through `ask_from_worker`,
  exactly as the checksum-mismatch prompt does. Do not add a second mechanism and do not add a second
  screen-registry entry — the prompt is a `ModalScreen`, like the mismatch prompt, for the same
  stack-invariant reasons Phase 13 recorded.
- **One prompt-open message for both prompts.** The screen already has a "the worker is blocked on a
  question" message and a `_waiting_prompt` guard that makes `c` explain itself instead of silently
  doing nothing. There are now two such questions. Rename the message and its handler to a
  mechanism-neutral name and use one for both, rather than keeping a parallel copy — the project's
  stated bias is one data structure over parallel copies. All five references live in this one file
  and none are in tests.
- **Unattended means no callback, on this path too.** The screen already computes
  `None if self._inputs.unattended else self._ask_mismatch` for the mismatch prompt. The sensitive
  confirmation is computed the same way, on the same line of reasoning, so `--yes` through the TUI
  behaves identically to `--yes` through the console.
- **A dismissed prompt is a no.** `.claude/architecture.md`'s established shape for a dismissed
  modal here is a conservative resolution that says so. For a confirmation the conservative answer is
  false; the screen says so in the log rather than silently resolving it.
- **The architecture record is behind a test.** `tests/test_docs.py` already asserts a tuple of
  load-bearing phrases for Phases 12 and 13. Phase 14 gets its own tuple and its own test. Do not
  assert how many tests that file contains — Phase 13's review cycle removed exactly that kind of
  count assertion, because it goes red the first time a later phase adds its own and the apparent
  fix is editing the number rather than adding the test.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| worker thread -> modal -> worker thread | a lost, defaulted or dismissed answer silently changes whether a system mutation is proposed |
| unattended TUI run -> the sensitive action | `--yes` through the app must behave exactly as `--yes` through the console |
| instruction text -> the in-app log | text the user is invited to run as a command, rendered into a live terminal widget |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-14-12 | Elevation of Privilege | the sensitive action firing on an unattended TUI run | high | mitigate | the confirmation is absent when the unattended flag is set, computed on the same line of reasoning as the existing mismatch suppression; Task 1's `WIRE-OK` gate asserts that check precedes the binding (ASVS V4) |
| T-14-23 | Spoofing | a dismissed confirmation read as consent | high | mitigate | the dismissal branch resolves to false and writes an explanatory attributed line naming the tool and the answer; a pilot test drives the escape path |
| T-14-24 | Denial of Service | the worker blocked forever on a prompt the user cannot reach | medium | mitigate | the prompt uses the single spiked-and-recorded worker-to-modal mechanism, which keeps the event loop running while the worker waits; a second mechanism is gated out by a source count |
| T-14-25 | Repudiation | a confirmation given but its instructions never shown | medium | mitigate | Task 2 puts the renderer in the report closure and asserts the in-app and console renderer orders match |
| T-14-26 | Information Disclosure | control characters in rendered instruction text reaching the live log widget | low | mitigate | the report closure already runs through the captured-console helper, which sanitises; no second path is introduced |
| T-14-27 | Tampering | the cancel key arming mid-prompt and tearing a decision in half | low | mitigate | the existing `_waiting_prompt` guard is generalised to cover both prompts rather than duplicated, and a pilot test asserts the cancel event stays unset while the prompt is open |
| T-14-SC | Tampering | npm/pip/cargo installs | high | accept | this phase introduces no external package; `14-RESEARCH.md`'s "Package Legitimacy Audit" section records the gate as not applicable |
</threat_model>
