# Phase 15.5: Relax set_login_shell's immutable-host block from total silence to honest explanation - Context

**Gathered:** 2026-09-15
**Status:** Ready for planning

<domain>
## Phase Boundary

`_set_login_shell` (`installer/post_install.py:40-49`) returns `()` unconditionally
whenever `platform.immutable` is true, giving zero user feedback when the "set zsh as
login shell" post-install action is silently skipped. This phase replaces that silence
with an honest, accurate explanation on hosts where `chsh` genuinely cannot do the job —
**not** with the originally-imagined "show the chsh instructions with a warning"
(investigated live during this session and found to be actively broken: `chsh` does not
exist as a binary on this Bazzite host at all — Bazzite's maintainers removed the
`util-linux-user` package on purpose). This phase is scoped to correctness of the
message shown (or not shown) for the *existing* chsh-based mechanism only. The actual
replacement capability the user wants — terminal-emulator-level shell configuration
(Konsole/kitty/WezTerm) that makes zsh the working shell without ever touching
`chsh`/`/etc/passwd` — is explicitly OUT of scope here and has been inserted as a new
phase (see `<deferred>`).

</domain>

<decisions>
## Implementation Decisions

### Root-cause finding (this session's live investigation)
Confirmed via `gh issue view 4159 --repo ublue-os/bazzite` (the exact issue Phase 14's
D-04 cited) that the root cause IS known and confirmed by Bazzite maintainers — Phase
14's `14-RESEARCH.md` Assumption A2 ("mechanism never confirmed") is now outdated:
- The specific failure: layering a shell via `rpm-ostree` (or layering `chsh` itself)
  and then running `chsh` to point the login shell at it, followed by a later
  rebase/unlayer, leaves `/etc/passwd` pointing at a binary path that no longer exists
  — breaking KDE/SDDM login. (Maintainer `KyleGospo`, comment on #4159.)
- Bazzite's fix was to remove `chsh`/`util-linux-user` from the base image entirely —
  confirmed live on this host: `which chsh` → not found, `rpm -q util-linux-user` →
  not installed.
- The maintainers' own recommended workaround: "set zsh as your shell in [your
  terminal emulator] and not touch bashrc... You can also install zsh with brew
  instead of layering it" (`KyleGospo`); a second maintainer (`m2Giles`) is more
  blunt: don't change the system login shell at all, use a terminal-emulator profile
  instead.
- This installer's own `zsh` registry entry already avoids the layering failure mode
  on immutable hosts today: `resolve.py:75-76` skips the `dnf` method (which would
  otherwise trigger `rpm-ostree` layering) whenever `platform.immutable` is true, so
  `zsh` here is always installed via `brew` on Bazzite — never layered. This does NOT
  make `chsh` safe to call, though, because `chsh` is simply absent as a binary
  regardless of how zsh got there.

### D-01: Key the block on chsh's actual presence, not just `platform.immutable`
`_set_login_shell` must check whether the `chsh` binary is actually resolvable
(`shutil.which("chsh")` or equivalent), not only `platform.immutable`. `immutable` and
"chsh unusable" are related but not the same fact — this phase must not conflate them
speculatively; it must probe reality.
— **Reversibility:** reversible.
**Rationale (user + investigation):** the user pushed back hard when the originally
planned fix (show chsh instructions with a warning) turned out to describe a command
that doesn't exist on this exact host — an inaccurate "fix" is worse than useful
silence. The check must be grounded in what's actually on the machine.

### D-02: When chsh is absent, explain honestly — no instructions to run, no silence
When the probe finds no `chsh` binary, `_set_login_shell` returns non-empty,
**informational-only** text: state plainly that this system (Bazzite/Fedora Atomic)
removed `chsh` by design to avoid breaking login after a rebase, and that configuring
zsh at the terminal-emulator level (rather than as the system login shell) is the
supported path — with a pointer to the follow-up capability once it exists (see
deferred phase). No shell command is offered to run, since none exists to offer.
— **Reversibility:** reversible.
**Rationale (user):** "mas que una advertencia quiero una solucion" — the user does not
want a warning wrapped around a broken command; if nothing can be run, say so plainly
and point toward the real remedy, don't manufacture fake actionability.

### D-03: No confirm() gate when chsh is absent
Phase 14's D-05 confirm-gate (`confirm_sensitive_action`) applies to the case where a
real, reviewed shell command is about to be shown/handed off — appropriate friction
before a mutating instruction. When chsh is absent there is no command to hand off,
only an explanation of why the feature can't act here — so no confirm() gate applies to
this branch; the explanation is shown unconditionally once install succeeds (same
"never silent" doctrine, just without a decision to gate).
— **Reversibility:** reversible.

### D-04: macOS / any host where chsh IS present is untouched
This phase's chsh-presence probe only changes behavior on hosts where `chsh` cannot be
found (Bazzite's confirmed case, and presumably other Fedora Atomic / ostree-based
distros that made the same call — verify during research whether the absence is
Bazzite-specific or shared across the ublue-os family). On macOS and any Linux host
where `chsh` genuinely exists and works, the existing Phase 14 flow (confirm-gated,
show `chsh -s $(which zsh)` instructions) is completely unchanged.
— **Reversibility:** reversible.
**Rationale (user):** explicit — "sabemos en macOS no hay esos problemas, son
problemas de bazite" — this is not a platform-wide (`immutable`) distinction, it's a
chsh-availability distinction, and macOS is never `immutable` anyway so D-01's probe
naturally never fires there, but the reasoning should be documented, not assumed.

### Rejected approach (investigated and explicitly ruled out)
Re-adding `chsh` via `rpm-ostree install util-linux-user` (layering it back onto the
immutable base) was raised and explicitly rejected: it requires the same
"layer + reboot, breaks atomicity" pattern this installer already avoids by design
(`resolve.py:70-73`'s `rpm_ostree` method is disabled for exactly this reason) and
this installer's own established doctrine of never requiring privilege escalation
(`installer/ownership.py`'s docstring). It also does not match Bazzite's own stated
position, which is to avoid changing the system login shell at all regardless of the
binary's provenance — not merely a technical workaround away.

### Claude's Discretion
- Exact wording of the honest-explanation text (D-02) — should name Bazzite/ostree
  specifically if `platform.immutable` implies it, or stay generic if the researcher
  finds the chsh-removal is shared more broadly across ublue-os/Fedora Atomic images.
- Exact probe mechanism for chsh presence (`shutil.which`, or a small platform.py
  helper alongside `detect_immutable`) — implementation detail.
- Whether the explanation text visually differs from ordinary "after install" cyan
  lines (`render.py`'s `render_post_install_handoff`) to signal "this is a limitation,
  not a next step" — e.g., reusing the yellow `⚠` styling `render_postinstall_warnings`
  already uses elsewhere in the same file.

### Folded Todos
None — see Deferred Ideas for the todo reviewed but not folded.

## Specific Ideas

The user's own words anchor this phase's real target: "mas que una advertencia quiero
una solucion, no quiero estar abriendo wezterm u otro terminal emulator y estar
seleccionando manualmente el shell" — they want zsh (with oh-my-zsh's plugins, if
installed) to just work as the default shell in every terminal emulator they use,
without manual per-session selection, and without ever touching the system login
shell. This phase does NOT deliver that outcome — it only stops the app from lying
about how to get there via a nonexistent `chsh`. The real solution is the deferred
phase below.

<deferred>
## Deferred Ideas

### New capability — deferred to its own phase (INSERT after 15.5)
**Terminal-emulator-level default-shell configuration**, so zsh (+ oh-my-zsh plugins,
when installed) becomes the working shell in Konsole/kitty/WezTerm (Linux) without
ever touching `chsh`/`/etc/passwd` — matching Bazzite maintainers' own recommended
workaround. User confirmed macOS does not need this (chsh works normally there via the
existing Phase 14 flow) — scope this to Linux/immutable hosts specifically, or wherever
research shows the chsh-removal is shared.

Investigated this session (feasibility only, not designed): both `kitty` and `WezTerm`
support CLI-level config overrides that avoid editing the app's own config file —
`kitty -o shell=/path/to/zsh` and `wezterm start --config 'default_prog={"zsh"}'`
respectively — which could be applied at the `.desktop`-launcher level (Linux) rather
than mutating `kitty.conf`/`wezterm.lua` directly. `Konsole` has no equivalent
single-flag shell override but supports the more universal `-e <command>` launch
pattern (works across most X11/Wayland terminals as a fallback). This is a real,
multi-app, cross-platform capability (desktop-launcher editing, possibly per-DE
`.desktop` file handling, config-file mutation as a fallback for terminals without a
CLI override) — genuinely out of scope for "relax a silent block," confirmed via
explicit user choice to split rather than fold into 15.5.

**Done:** inserted as **Phase 15.6**
(`.planning/phases/15.6-terminal-emulator-default-shell-configuration-konsole-kitty`)
via `/gsd-phase --insert 15 "..."` immediately after this phase's context was
committed. Needs its own `/gsd-discuss-phase 15.6` session before planning.
