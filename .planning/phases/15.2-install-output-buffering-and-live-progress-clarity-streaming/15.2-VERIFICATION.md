# Phase 15.2: Install output buffering and live-progress clarity Verification Report

**Phase Goal:** StreamingRunner (installer/run.py) already forwards child stdout line-by-line via
Popen+readline, but many installers (pnpm, sdkman, curl|sh scripts) block-buffer their own stdout when
not attached to a TTY, so output visibly arrives all at once at the end despite the installer streaming
faithfully -- force line-buffered/unbuffered child output where feasible (stdbuf -oL, PYTHONUNBUFFERED,
per-manager unbuffered flags) for known-buffering tools, and add a "waiting for output..." indicator per
in-flight tool so buffering-silence is not indistinguishable from a hang.

### Human Verification Required

The plan itself defers one verification item to a live, human-observed `make setup` session
(`15.2-02-PLAN.md` lines 649-662, `<human-check>`), and `15.2-02-SUMMARY.md` records it explicitly as
`human_judgment: true` (D7) — "Requires eyeballing a real slow installer ... in a live `make setup` TUI
session ... cannot be proven by an automated test alone." This is a deliberate, plan-authored deferral
(not a gap): the automated suite proves `stdbuf`/`PYTHONUNBUFFERED` reach the child and proves the
indicator's timing/attribution/staleness logic deterministically, but it cannot prove that a specific
vendor installer's own userspace buffering (pnpm, SDKMAN) actually honors either mechanism — that claim
can only be observed by watching a real slow tool install in the real TUI.

1. **Progressive output + indicator timing on a real slow installer**
   **Test:** Run `make setup`, stage a tool whose installer is slow to print (pnpm-backed or a
   `curl | sh` script), press enter, and watch the live log.
   **Expected:** Output arrives progressively rather than as one burst at the end; during any pause
   longer than ~2 seconds the tool's own region shows `-- still running; waiting for output --` at
   roughly two seconds (not noticeably later); that line is followed by real output.
   **Why human:** Vendor-installer buffering behavior is a property of that vendor's own binary, not
   something a unit test can observe.

2. **Silent update marker**
   **Test:** Stage an update for an already-installed tool.
   **Expected:** The live log shows `-- updating --` immediately rather than going blank for the whole
   update.
   **Why human:** Requires a real update binary running through `run_captured`.

3. **No repeated indicator in the failure report**
   **Test:** Force a failure (a tool whose install command exits non-zero).
   **Expected:** The end-of-run report shows the child's own error lines and does not repeat the
   waiting line.
   **Why human:** The plan explicitly reserves this as part of the same closing `<human-check>` even
   though an automated equivalent test exists.
