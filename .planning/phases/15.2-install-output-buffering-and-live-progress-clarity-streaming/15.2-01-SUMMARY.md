# Phase 15.2 Plan 01: StreamingRunner Output-Buffering Ladder Summary

**StreamingRunner gains a two-rung unbuffer ladder — PYTHONUNBUFFERED unconditionally, stdbuf -oL opt-in and best-effort — so a block-buffering child (pnpm, SDKMAN, curl\|sh scripts) streams live instead of bursting at process exit.**

## Performance

- **Tasks:** 2
- **Files modified:** 4

## Accomplishments
- `unbuffered_env()` merges `PYTHONUNBUFFERED=1` over `os.environ` unconditionally — a harmless no-op for non-Python children, a real fix for Python ones, PATH/HOME preserved
- `unbuffered_argv()` wraps a non-Python child's argv with `stdbuf -oL` only when the binary is present on PATH and the instance opted in via `unbuffer=True`, and never double-wraps a Python child
- `StreamingRunner` resolves `which` exactly once at construction time (never per call), and degrades silently — never failing an otherwise-successful install — if the cached `stdbuf` path vanishes before launch
- `ExecuteScreen._execute_worker`, the project's one live streaming call site, opts in via `unbuffer=True`
- Real `stdbuf` binary proof (skipped when absent, e.g. stock macOS) confirms the wrapper is genuinely applied to the child's environment, not just argv-inspected

## Decisions Made
- `PYTHONUNBUFFERED` stays unconditional (no knob) while `stdbuf` stays opt-in per instance — the two rungs have different risk profiles (env var is always safe; wrapping argv changes what actually executes) and CONTEXT.md's D-02/D-04 treat them differently
- No manager-name branching anywhere in `run.py` — the opt-in `unbuffer` knob lives on the call site (`ExecuteScreen`), keeping `StreamingRunner` itself generic, per Phase 6's registry-authoring guideline
