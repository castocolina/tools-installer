# Phase 15.2: Install output buffering and live-progress clarity - Context

**Gathered:** 2026-09-15
**Status:** Ready for planning

<domain>
## Phase Boundary

`StreamingRunner` (`installer/run.py`) already forwards a child process's stdout
line-by-line, faithfully — this is not a code defect. The user-visible symptom
("no progress during install, everything at once at the end") is caused by the
*child* process (some vendor installer scripts and package managers) block-buffering
its own stdout when it detects a non-TTY. This phase forces line-buffered/unbuffered
output for the specific managers confirmed to route through a shell wrapper where this
is fixable, and adds a "waiting for output…" indicator so genuine buffering-silence
is distinguishable from a hang.

</domain>

<decisions>
## Implementation Decisions

### Manager scope
- **D-01:** Apply the unbuffered-output fix to the three method kinds that actually
  route through a shell wrapper where injecting an env var / prefix is possible:
  `_script` (`installer/executors.py` — `curl | sh`, e.g. `oh-my-zsh`), `_node`
  (`pnpm add -g`), and `_sdkman` (`bash -c` wrapped `sdk install`). `_dnf`/`_apt`/
  `_pacman`/`_brew`/`_cask` invoke the manager binary directly (no shell wrapping) and
  are out of scope — they already stream line-by-line through `StreamingRunner`
  unchanged. — **Reversibility:** reversible.
  **Rationale (user):** these three are the ones actually confirmed to buffer; going
  further isn't warranted without evidence.

### Waiting indicator
- **D-02:** The "waiting for output…" indicator appears only after a prolonged silence
  (target: 3-5 seconds with no new line from the current tool), not immediately when a
  tool starts. — **Reversibility:** reversible.
  **Rationale (user):** avoids flicker/noise on tools that stream cleanly and finish
  fast — the indicator should only show up when silence could plausibly be confused
  with a hang.

### Claude's Discretion
- Exact mechanism for forcing unbuffered child output (e.g. `stdbuf -oL` prefix,
  `PYTHONUNBUFFERED=1`/equivalent env var, or a pseudo-terminal via Python's `pty`
  module) — this is an implementation detail, not a product decision. Note for
  research: `stdbuf` is GNU-coreutils-only and is not guaranteed present on macOS by
  default, which this project also targets (`CLAUDE.md`: "cross-platform (macOS /
  Linux)") — a `pty`-based approach (making the child believe it has a real TTY, which
  most tools' own buffering-detection logic already keys off) may be the more portable
  choice and is worth investigating during research rather than assuming `stdbuf`.
- Exact silence threshold within the 3-5s target window, and exact wording of the
  waiting indicator.
- Whether the indicator is a per-line addition to the `RichLog` or a separate small
  status widget near it — implementation shape, not scoped here.

### Folded Todos
None — see Deferred Ideas for the two todos reviewed but not folded.

</decisions>

<code_context>
## Existing Code Insights

### Reusable Assets
- `_env_prefix(method)` (`executors.py:335`) already builds `KEY=value` shell
  assignments from a method's registry-declared `env` dict — D-01's fix can likely
  reuse this same mechanism rather than inventing a new one, for `_script` at least.
- `_path_prefix()` (`executors.py:31`) is the existing pattern for prepending
  shell-level setup before a manager's own invocation — same shape as what a
  `stdbuf`/`pty` prefix would need.

### Established Patterns
- `StreamingRunner`'s own docstring already states the exact caveat this phase exists
  to mitigate — the team was already aware of this limitation; this phase makes it
  actionable rather than discovering something new.
- The registry's `env = { ... }` pattern (used today for e.g. `oh-my-zsh`'s
  `RUNZSH=no, CHSH=no, KEEP_ZSHRC=yes`) is a precedent for per-tool env overrides if a
  registry-level (rather than blanket executor-level) approach turns out to be needed.

### Integration Points
- `installer/executors.py`'s three named functions (`_script`, `_node`, `_sdkman`) are
  the three integration points for D-01.
- `execute_screen.py`'s `on_install_log_line`/`RichLog` handling is the integration
  point for D-02's indicator.

</code_context>
