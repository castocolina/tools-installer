# Phase 15.2: Install output buffering and live-progress clarity - Context

**Gathered:** 2026-09-16
**Status:** Ready for planning
**Mode:** Autonomous (smart discuss, self-accepted — user requested continuous run, no per-area pauses)

<domain>
## Phase Boundary

`StreamingRunner` (`installer/run.py:106`) already forwards a child's stdout
line-by-line via `Popen(bufsize=1)` + iterating `proc.stdout`, but its own
docstring already names the real limitation: `bufsize=1` line-buffers the
PARENT's *reads*, never the CHILD's *writes* — a vendor installer that
detects a non-TTY stdout (pnpm, SDKMAN, most progress-bar-drawing curl|sh
scripts) block-buffers on its own side and bursts everything at process
exit, regardless of how the parent reads it. This phase (1) forces
line-buffered/unbuffered child output where a real, safe mechanism exists,
for the specific known-buffering tools/managers this project already
shells out to, and (2) adds a "waiting for output..." indicator per
in-flight tool in `ExecuteScreen`'s live log widget, so a legitimately
silent-but-buffering child is never visually indistinguishable from a
hung one. Scope is the one live streaming path this project has
(`StreamingRunner` -> `ExecuteScreen`, built in Phase 13) — the separate
blocking console runner (`run_output`/`run_command`) is out of scope, it
was never meant to stream.

</domain>

<decisions>
## Implementation Decisions

### Forcing unbuffered child output
- Never assume every installer child honors any single flag — apply a
  best-effort, per-mechanism ladder, in order of reliability: (1) for a
  child that is itself a Python process, set `PYTHONUNBUFFERED=1` in its
  env — always safe, Python-specific, zero risk of altering unrelated
  behavior. (2) for a non-Python child (curl|sh installer scripts, pnpm,
  SDKMAN's bash-based `sdk` launcher), wrap the argv with `stdbuf -oL`
  when the `stdbuf` binary is present on PATH (coreutils; present by
  default on virtually every Linux distro including Bazzite, commonly
  absent on stock macOS unless coreutils is brew-installed) — detect
  once, not per-invocation, and silently skip the wrapper (never fail
  the install) when `stdbuf` is absent, exactly matching the existing
  "as live as the child allows, never a hard guarantee" framing already
  in `StreamingRunner`'s own docstring.
- Do NOT special-case pnpm/SDKMAN by name inside `StreamingRunner` —
  keep it a generic, reusable capability (an optional `unbuffer: bool`
  or similar knob `StreamingRunner`/its caller can opt into per Method),
  since this project's own registry-authoring guidelines (Phase 6)
  already establish "no manager-specific logic buried in a generic
  runner" as the convention to follow.
- `PYTHONUNBUFFERED` is set unconditionally on every streamed child's
  env (harmless no-op for non-Python children); the `stdbuf -oL` wrapper
  is applied only when the child is NOT already a case where Python's
  own env var covers it, to avoid a redundant/confusing double-wrap.

### The "waiting for output..." indicator
- Threshold: show the indicator only after 2 seconds with no new line
  from the in-flight tool's stream — short enough to reassure the user
  quickly, long enough that normal brief pauses between lines never
  flicker it on.
- Presentation: append it as a transient, clearly-marked last line in
  the tool's own log region of `ExecuteScreen`'s existing live widget
  (reuse the `InstallLogLine` message path already wired in
  `execute_screen.py`) — never a separate modal, spinner overlay, or
  second widget. It is replaced the instant a real line arrives; it
  never itself becomes part of the persisted log tail.
- Applies per in-flight tool, not globally — a batch with several tools
  running/queued must not show one indicator for the whole run when
  only one child is currently silent.

### Testing approach
- Unit-test the unbuffer-ladder logic (PYTHONUNBUFFERED env injection,
  stdbuf-present/absent branching) directly against `subprocess.Popen`
  call construction — no real slow/buffering child process needed.
- Test the indicator's timing via Textual's existing test-clock/worker
  test patterns already used elsewhere in `tests/test_execute_screen.py`
  (this project has an established convention for testing worker-driven
  UI state; follow it rather than real wall-clock sleeps).

### Claude's Discretion
- Exact wording of the indicator text (e.g. "waiting for output…" vs.
  "still running…") — pick something consistent with this project's
  existing terse, lowercase-first UI copy conventions.
- Whether the stdbuf-presence check is cached at process start or
  re-checked per install run — either is fine as long as it costs at
  most one extra subprocess check per app session, not per tool.

</decisions>

## Existing Code Insights

### Reusable Assets
- `installer/run.py:106` `StreamingRunner` — the class to extend; already
  has `_emit`, `set_tool`, `method_started` and the main `__call__` loop.
- `installer/execute_screen.py:462` `_execute_worker` — constructs the
  `StreamingRunner(emit)` instance and posts `InstallLogLine`/
  `InstallToolFinished` messages; the natural place to add per-tool
  last-line-seen timestamps driving the indicator.
- `tests/test_execute_screen.py` — existing worker/message-driven test
  patterns to follow for the indicator's timing behavior.

### Established Patterns
- This project's `run.py` docstrings are unusually explicit about the
  exact guarantee being made ("as live as the child allows") — new code
  here should keep that same honesty rather than overclaiming.
- Registry-authoring guidelines (Phase 6) establish keeping
  manager-specific behavior out of generic runners/executors.

### Integration Points
- `ExecuteScreen`'s live log widget (already exists, built Phase 13) is
  where the indicator renders — no new screen or widget class needed,
  only new state/messages feeding the existing one.
