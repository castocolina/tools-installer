# Phase 15.2 Plan 02: Silence Indicator for Buffering-vs-Hung Ambiguity Summary

**A self-re-arming Textual Timer writes "-- still running; waiting for output --" into the in-flight tool's own log region at exactly 2 seconds of silence, generation-guarded against staleness, and extended to cover otherwise-silent update runs.**

- **Completed:** 2026-09-16T19:28:58-03:00

## Accomplishments
- `ExecuteScreen` now shows a clearly-marked, tool-attributed line the instant 2 seconds pass with no new output from the in-flight tool's child — removing the ambiguity between legitimate buffering and a hung process
- The indicator fires AT the 2-second threshold (not up to a poll-interval late) via a self-re-arming one-shot `Timer`, proven against the real production wiring with a `set_timer` recorder, not just a "timer object exists" assertion
- Every transient carries a `silence generation` token; the handler drops any transient whose world moved on (a real line, a terminal message, a prompt open/close, or the run ending) before it was handled — proven with three deterministic race tests
- Updates, which previously streamed nothing at all between `begin` and `UpdateToolFinished`, now post a `-- updating --` marker that both ends the blank live log for updates and gives them an in-flight tool the silence indicator can attribute to
- The indicator can never leak into the end-of-run failure report, proven against a REAL `StreamingRunner` failure (not a hand-built `CommandError`) driven through the exact runner the install closure was handed
- Both of phase 15.2's mechanisms (the unbuffer ladder from plan 01, and this indicator) are now recorded in `.claude/architecture.md`, guarded by a `tests/test_docs.py` phrase-anchor test

## Decisions Made
- Wording is strictly "-- still running; waiting for output --": the screen cannot tell legitimate buffering from a hung child apart, so the copy asserts only liveness and waiting, never a diagnosis (D-11, review round 1 finding)
- "Replaced" (D-07/CONTEXT wording) is realised as SUPERSEDED, not deleted: `RichLog` is append-only with no public delete API, and retro-deleting the indicator would leave an unexplained gap in the scrollback of a long install
- The never-persisted test drives the `StreamingRunner` the install closure was actually handed (already attributed via `attributed_install`), documented as the ONLY correct approach after review round 2 flagged that a separately constructed runner raises `RuntimeError` from `_current()` before the child's failure is ever reached
- One commit per task rather than a strict RED/GREEN-per-task split, per this execution's explicit human instruction to "run the verify commands and confirm they pass, then commit atomically per task" — tests were written and confirmed failing for the right reason before implementation internally, but the git history reflects one commit per task rather than separate test/feat commits

### Auto-fixed Issues

**1. [Rule 1 - Bug] Test's own CommandError message text collided with its own assertions**
- **Found during:** Task 2's real-runner FAILED-install test
- **Issue:** The initial test script used literal `print('boom one')` in the subprocess `-c` argument; `CommandError.__str__` embeds the full argv verbatim in its message, so the substring "boom one" appeared 3 times (argv echo, live log, report tail) instead of the expected 2 (live log, report tail), failing the occurrence-count assertion.
- **Fix:** Built the printed strings from concatenated fragments (`'bo'+'om one'`) so the argv itself never contains the target substring contiguously, decoupling the argv-echo occurrence from the child's actual stdout occurrences the test cares about.
- **Files modified:** tests/test_execute_screen.py
- **Verification:** `test_failed_install_with_real_runner_shows_child_tail_and_indicator_once` passes with the corrected assertion (`== 2` for each of "boom one"/"boom two").
- **Committed in:** 1c9f3fe (Task 2 commit)
