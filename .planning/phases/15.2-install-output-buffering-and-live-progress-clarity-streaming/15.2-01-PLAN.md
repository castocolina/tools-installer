<objective>
`StreamingRunner` streams faithfully and still looks frozen. Its own docstring already names why:
`bufsize=1` line-buffers the PARENT's reads and cannot make a child line-buffer its own writes. A
vendor installer that detects a non-TTY stdout — pnpm, SDKMAN's bash launcher, most progress-bar
`curl | sh` scripts — block-buffers on its side and bursts everything at process exit, so the user
watches an empty log for two minutes and then gets 400 lines at once.

This plan makes the parent force the child's hand where a real, safe mechanism exists, as a
best-effort ladder that never fails an install when a rung is unavailable (D-01):

- Rung 1, unconditional: `PYTHONUNBUFFERED=1` in every streamed child's environment (D-02). Safe,
  Python-specific, a no-op for a non-Python child.
- Rung 2, opt-in and availability-gated: wrap argv in `stdbuf -oL` when the caller asked for it and
  the binary is on PATH, skipping a child rung 1 already covers (D-03, D-05).

Both rungs live in `installer/run.py` as a generic capability behind one `unbuffer` knob — no
manager-name branching anywhere in the runner (D-04) — and `ExecuteScreen._execute_worker`, the
project's one live streaming call site, opts in.

Purpose: a user running an install in the TUI sees output as the installer produces it, not as a
burst at the end.
Output: three module-level helpers and one constructor knob in `installer/run.py`, a rewritten
`StreamingRunner` class docstring that states the new guarantee without overclaiming, one changed
constructor call in `installer/execute_screen.py`, and the tests that fail without each of them.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| child process stdout/stderr -> ExecuteScreen log | Untrusted vendor-installer output crosses into a rendered TUI widget. Pre-existing; already mitigated by `sanitize_log_line` on both the runner's `tail` and the screen's write path. |
| PATH -> launched argv | `shutil.which("stdbuf")` resolves a binary from the user's PATH and this phase prepends it to install argv. New in this phase. |
| parent environment -> child environment | `os.environ` is copied and one variable overridden, then handed to `Popen`. New in this phase (the child previously inherited implicitly). |

|-----------|----------|-----------|----------|-------------|-----------------|
| T-15.2-01 | Elevation of Privilege | `StreamingRunner.__init__` resolving `stdbuf` via `shutil.which` | low | accept | A PATH-planted `stdbuf` would execute attacker code, but every install method this runner already drives resolves its own binary from the same PATH (`brew`, `pnpm`, `sudo dnf` — `installer/executors.py:360-375`), so the wrapper adds no trust assumption that is not already load-bearing. An absolute path is resolved once at construction, not re-resolved per command, which narrows the TOCTOU window rather than widening it. |
| T-15.2-02 | Tampering | `unbuffered_env()` handing a constructed mapping to `Popen` | low | accept | The mapping is `os.environ` plus one code-owned literal key set to a code-owned literal value. No caller-supplied or registry-supplied data reaches it, so there is no injection surface; the child's environment is materially identical to the one it inherited implicitly before this change. |
| T-15.2-03 | Information Disclosure | `CommandError.detail` and the failure report | low | mitigate | Unchanged from today: `sanitize_log_line` is still applied to every line entering the bounded `tail`, and `render_failure_details` sanitizes again. This plan adds no new producer into that path. |
| T-15.2-04 | Denial of Service | `stdbuf` absent or non-functional at exec time | low | mitigate | A missing binary is detected at construction and the rung is skipped silently (D-03). If `stdbuf` exists but cannot exec the wrapped command, the child exits 127 and the existing `CommandError` path reports it with the caller's own argv — the run reports a failure, it does not hang. The `finally` drain-then-reap block is untouched, so the never-signal-the-child invariant holds. |

No package-manager install tasks exist in this plan (no npm/pip/cargo install is added, removed or
changed), so the package-legitimacy gate does not apply and no `T-15.2-SC` row is required.
