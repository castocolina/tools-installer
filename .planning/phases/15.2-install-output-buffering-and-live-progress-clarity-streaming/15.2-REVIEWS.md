## OpenCode Review (opencode-plan-review)

## 15.2-01

### Summary

The plan is well grounded in the existing `StreamingRunner` seam and preserves attribution, bounded failure details, and caller-facing argv. However, Task 1 cannot pass its own verification as written, and the claim that existing tests remain unmodified is false. The plan also applies `stdbuf` more broadly than the context's per-method intent and lacks a safe fallback if the resolved wrapper disappears before launch.

### Strengths

- The extension point is correct: `StreamingRunner` already owns incremental `Popen` reads, attribution, sanitization, bounded error tails, and child reaping (`installer/run.py:106-180`).
- Preserving the original argv in `CommandError` is sound. Both current error paths use the caller's `cmd` (`installer/run.py:152-153`, `installer/run.py:179-180`), so separating `launch_argv` from reported argv is the right contract.
- The plan correctly identifies the single live-streaming production construction site at `installer/execute_screen.py:485-505`.
- Method attribution is structural: `install_tool` calls `method_started` before executing each method (`installer/engine.py:134-140`), and `attributed_install` sets the current tool before installation (`installer/execute_screen.py:194-228`).
- Merging the environment over `os.environ` follows an existing documented convention (`installer/run.py:186-208`).
- Availability injection through a `which` callable follows the established `VersionRefreshService` pattern (`installer/version_status.py:343-370`).
- The branch-matrix tests and preservation of caller argv cover useful failure behavior without depending on `stdbuf` being installed on the test host.

### Concerns

- **HIGH — Task 1 cannot pass pyright as specified.** The plan requires `unbuffered_argv(...) -> list[str]` but gives it only the `stdbuf is None` and Python-child returns, postponing the final wrapping return to Task 2 (`15.2-01-PLAN.md:136-139`, `15.2-01-PLAN.md:230-231`). A non-Python child with a resolved `stdbuf` falls off the function and returns `None`; Task 1 nevertheless requires `uv run pyright` to pass (`15.2-01-PLAN.md:211-213`).
- **HIGH — "Every pre-existing test passes unmodified" is factually wrong.** The plan adds `env=unbuffered_env()` to `Popen` (`15.2-01-PLAN.md:158-161`) while asserting existing tests remain unchanged (`15.2-01-PLAN.md:111`, `15.2-01-PLAN.md:216`). The existing `wrapping_popen` double accepts only `args`, `stdin`, `stdout`, `stderr`, `text`, and `bufsize`; it has no `env` parameter (`tests/test_run.py:254-269`). That test will fail with an unexpected keyword argument.
- **HIGH — Wrapper unavailability can still fail an install.** The phase goal says an unavailable forcing mechanism must never fail installation, but the plan only handles absence during constructor-time `which`. If the cached path disappears before `Popen`, the current `OSError` path becomes a 127 install failure (`installer/run.py:143-153`). The threat model explicitly accepts this failure instead of providing fallback (`15.2-01-PLAN.md:312`).
- **MEDIUM — `stdbuf` is enabled for every non-Python command in the live runner, not for specific methods.** One global `StreamingRunner(emit, unbuffer=True)` opt-in (`15.2-01-PLAN.md:188-191`) affects scripts, native package managers, brew, pnpm, SDKMAN, curl, chmod, unzip, cp, and symlink operations (`installer/executors.py:354-377`, `installer/executors.py:380-490`; `installer/download.py:164-190`). This is broader than the context's "opt into per Method" direction (`15.2-CONTEXT.md:46-50`) and increases regression surface.
- **MEDIUM — The automated proof validates only the Python rung's observable effect.** The real timing test exercises `PYTHONUNBUFFERED` with CPython; the `stdbuf` rung is tested only by inspecting constructed argv. That does not prove progressive output for the motivating pnpm/SDKMAN/shell cases. `stdbuf` changes libc stdio buffering but does not create a TTY or force every runtime's output implementation.
- **LOW — The timing test has avoidable scheduler sensitivity.** A 0.4-second child delay with a 0.3-second assertion (`15.2-01-PLAN.md:193-201`) can fail if the parent is not scheduled until both lines are already readable. The phase context preferred deterministic construction-level tests (`15.2-CONTEXT.md:72-79`).

### Suggestions

- Implement the complete `unbuffered_argv` function in Task 1, then reserve Task 2 for the branch-matrix tests. Every task should leave the tree type-correct and executable.
- Update the existing `wrapping_popen` test double to accept and forward `env`, and remove the inaccurate "pre-existing tests unmodified" acceptance criterion.
- If launching the cached `stdbuf` path raises `ENOENT`, retry the original argv without the wrapper; this is safe because `Popen` failed before the target command started. Add a test for that fallback.
- Either expose opt-in at command/method scope or explicitly document and test the intentional decision to wrap every non-Python command in the streaming path.
- Keep the construction-level `stdbuf` tests, but add a representative manual or platform-gated verification using a dynamically linked C stdio child. Do not claim this proves pnpm or SDKMAN unless those actual tools are observed.
- Increase the timing test margin or synchronize on receipt of the first line before beginning the measured child delay.

### Risk Assessment

**HIGH.** The architecture is reasonable, but Task 1 is not independently executable, one existing test is guaranteed to break, and the unavailable-wrapper behavior contradicts the phase's non-failure guarantee.

## 15.2-02

### Summary

The UI-side design appropriately reuses `InstallLogLine` and the existing `RichLog`, and the injected monotonic clock makes most state-machine tests deterministic. The plan nevertheless misses important production behavior: its polling interval can exceed the two-second goal, queued transient messages can render stale indicators after output or completion, and updates run in the same screen without ever establishing an in-flight tool. The proposed copy also asserts "not hung" without evidence.

### Strengths

- Reusing `InstallLogLine` and `on_install_log_line` preserves the worker-to-event-loop boundary already documented in the message (`installer/execute_screen.py:233-243`) and keeps all live lines going through sanitization (`installer/execute_screen.py:629-640`).
- No new widget is needed; `#execute-log` is already the sole streaming region (`installer/execute_screen.py:387-397`).
- Prompt suppression is grounded in real lifecycle messages. Both worker-side prompts post `PromptOpen(True)` and guarantee `PromptOpen(False)` in `finally` (`installer/execute_screen.py:604-627`), while the handler already owns `_waiting_prompt` (`installer/execute_screen.py:650-660`).
- Clearing state on terminal tool messages fits the existing progress handlers (`installer/execute_screen.py:642-648`).
- Keeping the indicator outside `StreamingRunner`'s tail is structurally correct: only child stdout enters the tail (`installer/run.py:155-180`), and only failed outcomes are later rendered (`installer/render.py:74-86`).
- A monotonic `now` seam is appropriate for elapsed time and follows the project's injected-clock practice (`installer/version_status.py:343-365`).
- The plan covers re-arming, one-per-gap behavior, prompt suppression, finished-state cleanup, install/update terminal messages, and documentation regression guards.

### Concerns

- **HIGH — Production display may miss the "within two seconds" phase goal.** The plan polls every 0.5 seconds and explicitly permits appearance between 2.0 and 2.5 seconds (`15.2-02-PLAN.md:121-125`). Its tests call `_check_output_silence` directly at exactly 2.0 seconds (`15.2-02-PLAN.md:185-197`), so they cannot detect the production delay. The roadmap goal requires the tool to say so within two seconds.
- **HIGH — Already-queued transient messages can become stale.** `_check_output_silence` posts a second asynchronous `InstallLogLine` (`15.2-02-PLAN.md:166-176`). If real output or `InstallRunFinished` is already queued but processed before that transient message, the real handler resets/clears state and then the stale transient can still be rendered last. Stopping the timer in `on_install_run_finished` does not remove messages already posted. The existing handler writes every `InstallLogLine` unconditionally (`installer/execute_screen.py:629-640`), and the plan adds no stale-message guard.
- **HIGH — Updates never establish an in-flight tool.** The plan clears state in `on_update_tool_finished` but has no corresponding update-start signal (`15.2-02-PLAN.md:239-241`). `_run_updates` calls `updates.run` and posts only the terminal message afterward (`installer/execute_screen.py:551-599`). Production updates use `run_captured`, not `StreamingRunner` (`setup.py:596-604`), so a long silent update in the same execution screen can never show the indicator.
- **HIGH — "buffering, not hung" makes an unsupported claim.** The same silence can be caused by legitimate buffering, slow work, deadlock, or a hung subprocess. The plan's own objective says these situations are visually indistinguishable (`15.2-02-PLAN.md:51-55`), but the proposed copy asserts the process is not hung (`15.2-02-PLAN.md:121-131`). The parent only knows that no line has arrived.
- **MEDIUM — The "never persisted" test is largely tautological.** It manually builds a `CommandError` whose detail contains only chosen child-tail lines (`15.2-02-PLAN.md:266-273`). Naturally, a UI-generated indicator absent from that manually supplied detail is not rendered again. This does not exercise a real failing `StreamingRunner` or prove its actual tail remained indicator-free.
- **MEDIUM — The initial-silence mechanism depends implicitly on `method_started`.** `_in_flight` is established only after handling a non-transient log line (`15.2-02-PLAN.md:155-173`). Production installs happen to emit `-- trying {method} --` before execution (`installer/engine.py:134-140`; `installer/run.py:133-134`), but injected installs and updates do not necessarily do so. This dependency should be explicit in the contract and tests.
- **LOW — The indicator is not actually removed.** It remains permanently in `RichLog`; subsequent output merely becomes the new last line. That may satisfy "superseded," but it is weaker than the context wording that it is "replaced" (`15.2-CONTEXT.md:62-67`).

### Suggestions

- Replace interval polling with a resettable one-shot timer scheduled for exactly `SILENCE_SECONDS` after each real line, or revise the phase goal explicitly if a 2.5-second upper bound is acceptable.
- Give transient messages a silence-generation or timestamp token. Before rendering one, verify that the same tool and generation are still in flight, `_silence_noted` is still active, and the run is unfinished. Drop stale messages after real output, tool completion, prompt changes, or run completion.
- Add race tests where a real line or `InstallRunFinished` is handled before an already-posted transient message; assert the stale transient is not rendered.
- Before `updates.run`, post an attributed installer marker through the existing `InstallLogLine` path so update silence has an in-flight tool and starting timestamp. Alternatively, explicitly exclude updates and remove update-specific claims.
- Use truthful copy such as `-- still running; waiting for output --`. It communicates liveness of the worker/process without claiming the child is healthy.
- For persistence coverage, run a real failing `StreamingRunner` through the screen seam or directly assert that its resulting `CommandError.detail` excludes the UI indicator.
- Add a production-timer test, not merely a "timer is non-None" assertion, so callback wiring and effective latency are verified.

### Risk Assessment

**HIGH.** The basic state model is sensible, but stale-message races, delayed production timing, unsupported "not hung" wording, and missing update-start attribution prevent the plan from reliably meeting its user-visible guarantees.
