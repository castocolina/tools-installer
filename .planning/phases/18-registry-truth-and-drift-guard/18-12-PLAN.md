<objective>
REG-03 (D-07, Ledger L-18-04), check core: there is no way to learn that an upstream asset was renamed, a member moved or a checksum changed until a user's install fails. This plan builds `installer/verify_registry.py`: a read-only check over every downloadable method and declared platform that reuses the real install resolver and verifies digests and members only when an asset changed since the last verified run.

Purpose: drift is caught by a check before a user hits it.
Output: the module (`Probe`, `Finding`, `Report`, `check_registry`, `format_report`, `main`) and offline tests. Plan 18-17 adds newer-stable detection for pins, the not-checkable listing, the run verdict that a single failing host cannot flip, the `Unverified at install` section and the gh-login token fallback. The registry writer (`--write`, `--candidate`) is plan 18-13. The GitHub issue upsert (`--issue`), the Makefile target and the weekly workflow are plan 18-14.

Scope split (checker scope_sanity, 2026-10-15): the original plan was estimated at 130k tokens with three tasks, and the revision added three findings to the same module. Its third task moved to plan 18-17 together with them.

Decisions recorded (RESEARCH Open Question 3, Ledger L-18-04, L-18-11): state is a JSON map `{key: fingerprint}` in `~/.local/state/tools-installer/verify-registry.json` by default (`--state PATH` overrides; the weekly job restores/saves it with `actions/cache`, never commits it); the key is `state_key(target)` = `<tool_id>|<url>#<member>|archive=<archive>|strip=<strip>|raw=<raw>` (member empty for a raw asset without one; `archive` is the method's value or `gz`, `strip` its value or 0, `raw` true/false; an app target is `archive=zip|strip=0|raw=false`), so a member that was never verified on a known url still forces one download (review H6) and so does a changed tool id or extraction setting (review N3, CONTEXT cycle-2 note); fingerprint = `sha256:<hex>` when a checksum-file or GitHub-digest hash is known, `sha256:<pin>|<HEAD validators>` when the only expected hash is the registry's own pinned `sha256` (a pin never changes by itself, so the validators are what reveal changed vendor bytes; plan-checker WARNING), else the HEAD validators. A state file written with the old `<url>#<member>` keys simply misses: every target is downloaded once (the documented cache-miss path).
</objective>
