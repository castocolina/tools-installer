- T-18-56, reproduced against the real `install_app` with a fake runner in a scratch HOME:
  - `draw.io.app` as a symlink to an outside dir, with a CLI: installed. The outside script ran, and `~/Applications/draw.io.app` became the symlink.
  - The same symlink, without a CLI: installed, and the bundle is the symlink.
  - `draw.io.app` as a regular file, without a CLI: installed as a file.
  - A real bundle whose CLI symlinks to `../../../other/draw.io` (a zip sibling): already refused by `staged_member(staged_bundle, cli)`.
- Deviation from the brief, on purpose. The brief suggested `staged_member(extract_root, f"{app}/{cli}")`. That root accepts the zip-sibling CLI above, which would then be smoked. After the swap, its relative link resolves to `~/Applications/other/draw.io`, outside the bundle. Once `extract_root / app` is proven a real directory (not a symlink), that directory is itself installer-anchored: `app` is a validated basename and `extract_root` is installer-created. So the plan keeps `staged_member(staged_bundle, cli)`, which is the tighter root. The new real-directory check closes the actual bypass, a bundle entry that is a symlink. The guard case pins this choice.
- T-18-69, from `tarfile.open(..., "r:xz"/"r:gz").getnames()` on crafted payloads:
  - Python 3.12.12 (the venv): a corrupt xz block raises `_lzma.LZMAError: Corrupt input data`. A gz stream with a bad deflate block after the first member raises `zlib.error: ... invalid block type`. Neither class is in the listing `except` (`tarfile.TarError`, `EOFError`, `zipfile.BadZipFile`) or in `_TRANSPORT_ERRORS`, so both escape `check_registry` and `main` exits 70.
  - Python 3.14 (host): tarfile wraps both as `tarfile.ReadError`, which is already drift.
  - The gz case is the same root cause as the xz case (an unwrapped decompressor error while tarfile skips member data), so it is fixed in the same tuple. The brief named only xz.
- Not taken: `gzip.BadGzipFile`. In probes, `getnames()` never reached the gzip CRC trailer: a flipped trailer lists cleanly on 3.12 and 3.14. A mid-stream `BadGzipFile` is an `OSError`, so the transport handler already reports it as inconclusive, not a crash. With no reproducible RED, nothing changes.
