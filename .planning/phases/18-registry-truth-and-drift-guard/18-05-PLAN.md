<objective>
REG-06 (D-11, amended by Ledger L-18-01): `make setup` runs `uv run setup.py`, which puts the project `.venv/bin` (synced with dev dependencies by `make install`) first on PATH, so a dev-only ruff shadows the user's real ruff and reads as installed with an unknown owner (audit D C1). Research proved `uv run --no-dev` alone still resolves `.venv/bin/ruff` in an already-synced venv; `uv run --isolated --no-dev` hides it, leaves the venv untouched and costs about 0.1 s warm. Every setup.py launcher, `install.sh`, and the container e2e harness move to that form; `validate` and `test` keep dev dependencies.

Purpose: the installer sees the host's tools, not its own dev tools.
Output: Makefile launchers, `install.sh`, container harness, a new Makefile test, the install.sh harness test literal, the living docs that quote the launch command (each doc lands with the launcher it describes), and an entry-point PATH filter for a shell with the project venv activated.

Review H2 (2026-10-15): `uv run --isolated --no-dev` stops uv from adding the project venv, but it does not remove a `.venv/bin` the launching shell already has on PATH (an activated venv, direnv, an IDE terminal). REG-06 says the installer launches without the dev venv on PATH, so Task 3 removes it at the one entry point every launcher reaches (setup.py), instead of narrowing the guarantee. This is a new reading of REG-06/D-11 for the run ledger (flagged to the orchestrator): the launch form plus an entry-point PATH filter.
</objective>
