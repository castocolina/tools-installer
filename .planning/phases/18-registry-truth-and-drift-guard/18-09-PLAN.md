<objective>
REG-05 (D-06): nothing runs a freshly installed binary, so a glibc-floor or wrong-architecture binary links "successfully" and fails at first use (audit D C6). Per D-06 one shared `smoke_binary` built on the `run_output`/`CommandError` path runs the binary once; download kinds smoke the staged binary before the atomic swap so a broken binary is never linked and an existing good install is untouched; any failure falls through to the next method.

Purpose: a binary that cannot run on this host never becomes "installed".
Output: `run_output_with_stderr` (and `run_output(env=...)` on top of it), `smoke_binary`, `method_smoke_argv`, `staged_member`, and the install path on the staged swap (`_replace_archive`/`_replace_raw` with a smoke hook).

Scope split (checker scope_sanity, 2026-10-15; plan-checker W4, round 2): the manager-kind smoke in the engine is plan 18-19 (wave 5); the `smoke_argv` loader key, its authoring docs and the registry comment corrections are plan 18-20 (wave 4, no shared file with this plan). This plan reads `smoke_argv` from `Method.params` only, so it does not need the loader key to pass its tests.

The install path moves from in-place extraction to the update path's staged swap here (RESEARCH Pattern 3): extracting in place would overwrite an existing good tree before the smoke run, which contradicts D-06 ("an existing good link is untouched"). App bundles get the same treatment in plan 18-11.

Loader errors on exit 0 (review N1, CONTEXT cycle-2 note): `run_output` returns stdout and drops stderr on success (`installer/run.py`, the `return completed.stdout` line), so a smoke built on it alone could not see a loader message from a wrapper that exits 0. `run_output_with_stderr` returns both streams from the same `subprocess.run` call; `run_output` becomes its first element, so there is still one subprocess path and one error mapping.
</objective>
