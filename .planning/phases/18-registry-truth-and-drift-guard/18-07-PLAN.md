<objective>
REG-04 (D-05), first half: 50 of 89 `github_release` methods install with no verification because they declare no checksum file. GitHub's `/releases/latest` response already carries a `digest` (`sha256:<hex>`) per asset (153 of 171 rendered assets, RESEARCH "Live findings"). Per D-05 the tag and the digests come from one read, a digest-backed install is fetched into a staging dir and hashed, and verification follows pinned checksum -> API digest -> "unverified" with a reason. A mismatch reuses `ChecksumMismatch`, so the engine's fail-fast branch covers it with no new engine logic.

Purpose: every release download GitHub can vouch for is verified, and the rest say why they are not.
Output: `Release`/`resolve_github_release`/`release_resolver`; the context seam; `_fetch_verified` (the update path's plain-argv fetch, generalized) used by install's verified path; the reason carried to the outcome and printed.

Scope split (checker scope_sanity, 2026-10-15): the original plan was estimated at 140k tokens with a 6-file tracer task. This plan keeps the release snapshot, the verified install path and the engine/render wiring. Plan 18-16 (wave 3) deletes the remaining no-hash `curl | tar` shell pipeline, adds the pinned tarball url and digest-checks updates. Ledger L-18-02: gron (x2) and jless (x2) publish no digest, so they stay "unverified" with a reason; that is the expected end state, not a gap. Smoke-before-link and the staged swap are plan 18-09; app downloads are plan 18-11; storing digests in the version cache is plan 18-10.
</objective>
