<objective>
REG-04 (D-05): 50 of 89 `github_release` methods install with no verification because they declare no checksum file, and the current unverified path is a `curl | tar` shell pipeline with no file on disk to hash. GitHub's `/releases/latest` response already carries a `digest` (`sha256:<hex>`) per asset (153 of 171 rendered assets, RESEARCH "Live findings"). Per D-05 the tag and the digests come from one read, the install fetches to a staging dir, and verification follows pinned checksum -> API digest -> "unverified" with a reason. A mismatch reuses `ChecksumMismatch`, so the engine's fail-fast branch covers it with no new engine logic.

Purpose: every release download GitHub can vouch for is verified; the rest say why they are not.
Output: `Release`/`resolve_github_release`/`release_resolver`; the context seam; one staged fetch-and-verify path for install and update; the pinned tarball url; the reason carried to the outcome and printed.

Ledger L-18-02: gron (x2) and jless (x2) publish no digest, so they stay "unverified" with a reason; that is the expected end state, not a gap. Smoke-before-link and the staged swap are plan 18-09; app downloads are plan 18-11; storing digests in the version cache is plan 18-10.
</objective>
