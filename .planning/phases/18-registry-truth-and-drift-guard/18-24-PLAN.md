<objective>
Close REVIEW WR-02: verify-registry and install disagree on archive member layout. D-07 promises that "a passing check means the real install works", and three divergences broke that promise:
- zip + `strip`: install ignores `strip` for zip, while the checker applied it;
- `./`-prefixed tars: tar counts `.` as a component, while the checker dropped it first;
- `strip = true`: install reads it as 0, the checker as 1.

Plan 18-15 hid the zip divergence with a data edit (gh macOS `strip = 1` -> `0`).

Purpose: the loader rejects every `strip` value or placement that install cannot honor, and the checker mirrors install's extraction exactly.
Output: one loader rule, one registry line deleted, and one checker function rewritten, each with a test that was RED before the fix.

Planner verification (2026-10-15, HEAD 6794a65):
- `verify_registry._member_present` (473-485) applies `strip` to every archive mode. It also drops a leading `.` (and `PurePosixPath` already normalizes `./`).
- `_strip_default` (182-186) returns `True` as 1. `download._opt_int` (62-67) rejects bool and returns 0. `download._extract_into` (368-388) passes zip members verbatim to `unzip` and ignores `strip`.
- Checked locally with GNU tar 1.35: `./top/bin/tool` with `--strip-components=1` extracts to `top/bin/tool`. bsdtar's `strip_components` is character-based and counts `.` the same way. Python's `tarfile.getnames()` keeps the `./` prefix (`['./top', './top/bin', './top/bin/tool']`).
- `model.load_tools` validates no `strip` value. The only shipped `strip` on a zip or raw method is gh macOS (`strip = 0`). 8 zip fixtures in tests/test_verify_registry.py carry `strip = 0`.
- None of the 74 container installs (18-18) failed on a strip mismatch, so no shipped Linux entry depends on the old checker behavior. macOS entries with `strip >= 1` are re-judged by the next weekly run.
</objective>
