<objective>
Bug 2: a tool whose `--version` output is not a bare semver reads as `unknown` forever.

`_OBSERVED_VERSION` (`installer/versions.py:29`) is `fullmatch`-anchored and requires the token to
START with an optional `v` and then a digit. `jq --version` prints `jq-1.8.1` — one token, name glued
to version — so it never matches, `parse_version` returns `None`, `extract_observed_version` finds no
parseable token at all, and the catalog shows `unknown` for a tool that is plainly installed and
plainly reporting its version.

D-03's mechanism is deliberately narrow: when the direct match fails, split at the last `-` or
whitespace immediately preceding a segment that starts with a digit or `v`/`V`, and re-run the SAME
regex on that trailing segment. No per-tool prefix table, no registry schema change, and no free
substring search — the discussion log rejected the free search specifically for its false-positive
risk.

The trap this plan is shaped around: `installer/versions.py` has TWO independent
`_OBSERVED_VERSION.fullmatch` call sites, in `parse_version` (`:70`) and `parse_status_version`
(`:141`), and they exist separately on purpose (different strictness contracts, documented in their
own docstrings). Fixing one gives jq a version in the Ver column while `is_outdated` keeps failing to
rank it, so the outdated signal stays silently dead. One shared helper, both call sites, same commit.

Purpose: a tool that tells you its version in its own format is read, not written off.
Output: one shared fallback helper in `installer/versions.py`, both parsers on it, the D-04 audit
findings recorded in the code, and tests covering the parse, the comparison, and the two shapes that
are intentionally still out of scope.
</objective>

## Design decisions this plan implements

- **D-03 — a name-prefix split, implemented once and shared.** `_NAME_PREFIX_BOUNDARY` finds the
  rightmost `-`-or-whitespace that is immediately followed by `[vV]?\d`; `_strip_name_prefix` returns
  the tail after it, or the token unchanged when there is no such boundary; `_match_observed_version`
  tries `_OBSERVED_VERSION.fullmatch` first and only then the stripped retry. Both existing call
  sites switch to the helper. Nothing else in either function changes.
- **The retry reuses `_OBSERVED_VERSION`, not a second parallel pattern.** Every caller reads
  `match.group(1)` (numeric core) and `match.group(2)` (prerelease) by index. A second pattern with
  its own group numbering would be two contracts pretending to be one.
- **A prerelease hyphen is not a split point, and that falls out of the mechanism rather than being
  special-cased.** In `tool-2.3.4-rc.1` the `-` before `rc` is followed by a letter, so it is not a
  boundary at all; greedy backtracking lands on the `-` before `2.3.4`, and the prerelease stays part
  of the match. The already-green prerelease tests (`25.10.0-rc.1`, `11.0.0-rc.1`, `0.28.1-nightly`)
  are the proof and must keep passing untouched.
- **D-04 — the audit is recorded in code, with a test, because a note nobody can grep rots.** This
  project's own convention for a load-bearing finding is a prose comment plus a substring test that
  fails if the comment is deleted (`.claude/architecture.md`, "Registry-authoring guidelines"). The
  finding here is about parsing rather than about one registry row, so the comment lives beside the
  mechanism in `installer/versions.py` and the test lives in `tests/test_versions.py`.
- **`procs` and `bash` stay unparsed, deliberately.** Their shapes are different problems — a leading
  double quote, and noise AFTER the numeric core — and widening D-03's mechanism to swallow them is
  exactly the free-search false-positive risk the discussion log rejected. They are recorded as known
  residual gaps, not silently swept in and not silently ignored.

## Known follow-up, deliberately out of this plan

`wezterm` and `cursor-agent` print date- or hash-shaped strings (`20240203-110809-5046fc22`) that the
CURRENT, unmodified regex already "parses" into a meaningless major version. That is a pre-existing
false positive, not something this plan introduces or removes; do not try to fix it here, and do not
write a test that pins it either way. Record it in the SUMMARY as a fast-follow candidate alongside
`procs` and `bash`.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| a third-party tool's `--version` stdout -> this installer's parsers | fully untrusted text from a child process crosses here |
| parsed version -> `meets_minimum` -> an install decision | a mis-parse silently lowers or raises a feature floor |
| parsed version -> `is_outdated` -> the update action's eligibility | a mis-parse makes a tool look permanently current, or permanently stale |

| T-15-04 | Tampering | `_match_observed_version`'s fallback path producing a partial or guessed version | high | mitigate | the retry runs the unchanged `_OBSERVED_VERSION` with `fullmatch`, so it either produces a complete, validated match or `None` — no zero-filled or best-effort parse is ever introduced, preserving the fail-closed contract `parse_version`'s docstring describes |
