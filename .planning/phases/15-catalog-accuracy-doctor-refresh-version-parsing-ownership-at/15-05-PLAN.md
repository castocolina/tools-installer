<objective>
Bug 3, second half: the probes work, the registry now says which to ask, and nothing in the running
application asks them.

`install_ownership.detect_owner` has zero production callers — before plan 15-04 and still after it.
`installer/ownership.py::resolve_ownership` is the live resolution path, and for a tool installed
through dnf/apt/pacman it walks to an `unknown` result with a hand-written reason string that says, in
effect, "this was probably installed by the OS package manager, which this installer does not track."
This plan makes it track.

Three things have to move together, and the plan is shaped around the fact that doing only the first
is worse than doing none:

1. `resolve_ownership` consults the adapter — at the right place. 15-RESEARCH.md's Pattern 3 suggests
   inserting it before the FINAL `return _unknown(...)`. Read the function: a dnf-installed `jq` has a
   live `/usr/bin/jq`, which `attribute_path` maps to no owner, so `resolve_ownership` returns from the
   `if active_path is not None:` branch several lines earlier and the final fallthrough is never
   reached. A fallback placed only at the end would pass every test written against a no-PATH fixture
   and do nothing at all on a real machine. It goes before that branch.
2. `Owner` is widened. It is a closed `Literal` and `pyright --strict` is enforced; the adapter cannot
   construct a native-owned result without it, and a `cast` or a `# type: ignore` to dodge that is a
   silenced gate, which CLAUDE.md forbids outright.
3. `installer/update.py::_perform` gains a refusal branch. This is the consequence of D-05's own locked
   mapping: `direct` is in `MUTATION_GRADE`, so a native-owned tool now PASSES the gate that used to
   stop it, reaches an owner-dispatch ladder with no branch for its owner, and hits
   `else: raise UpdateError(f"unsupported owner {owner!r}")` — surfacing as a confusing
   `status="failed"` outcome that is strictly worse than today's clean pre-flight refusal. The fix is
   an explicit, non-mutating refusal that names the owner, mirroring the SDKMAN branch that already
   sits there for exactly this reason.

Purpose: the catalog tells the truth about who owns a tool, and the update action refuses the ones it
cannot own with a sentence the user can act on.
Output: one adapter call and one widened type in `ownership.py`, one refusal branch in `update.py`,
real probe wiring at the composition root, and an owner label in the catalog detail line.
</objective>

## Design decisions this plan implements

- **D-05 — adapt, never duplicate.** `resolve_ownership` calls `install_ownership.detect_owner` and
  maps its `confidence="verified"` to this module's `confidence="direct"`. No probe, no subprocess and
  no parsing is written inside `installer/ownership.py`; `.claude/architecture.md` rule 5 and that
  module's own docstring (which already anticipates this work as "a matter of adding an inventory
  reader") are the reasons.
- **Only the four native managers are adapted.** `detect_owner` can also return `Homebrew`, `pnpm`,
  `SDKMAN`, `managed download` or a host-setup owner. Those already have evidence paths in this module
  through inventories and directory attribution, and routing them through a second, weaker path would
  make two mechanisms answer one question. The adapter maps the four native manager names and ignores
  anything else.
- **The adapter is a LAST-resort evidence source, gated on complete negative evidence.** It runs only
  when the tracked managers produced no candidate at all AND none of their inventories was unreadable.
  A readable brew inventory that lists the tool creates a candidate and the native claim never happens;
  an unreadable one means the negative evidence is incomplete, and this module fails closed to
  `unknown`. That is the same evidence rule the by-elimination branch already follows, applied to a new
  source of positive evidence.
- **Placement is before the `active_path is not None` unknown branch, after the positive-attribution
  branch.** Positive live-PATH attribution to a tracked candidate still wins outright. Everything after
  that point was already heading for `unknown` or for a by-elimination guess, and package-database
  membership is stronger evidence than "a vendor script method exists and nothing else claimed it."
- **`Owner` is widened, not bypassed.** `Literal["installer", "brew", "cask", "pnpm", "uv", "unknown"]`
  gains the four native names. No exhaustive `match`/`assert_never` over `Owner` exists anywhere in the
  codebase (every consumer uses `==`/`in`), so the widening is self-contained — but every `if owner ==`
  ladder that now has a new reachable value must be checked, which is what Tasks 2 and 3 do for the
  two that matter.
- **A2 — the refusal is deliberate, and the alternative is a different phase.** Really updating a
  dnf/apt/pacman package needs privilege escalation this installer has never required: every existing
  owner (brew, cask, pnpm, uv, installer) is user-space. This phase's scope is ATTRIBUTION correctness.
  The refusal branch is what keeps a correct attribution from silently becoming an incorrect capability.
- **`install_ownership.run_probe`, never `installer.run.run_query`.** The signatures are close enough to
  make the substitution tempting. `run_probe` sets `stdin=subprocess.DEVNULL`; `run_query` does not, and
  these probes run on a Textual worker thread while the main thread holds the terminal in raw/alt-screen
  mode. Reusing the already-isolated runner costs nothing.

## Known follow-up, deliberately out of this plan

`version_status.resolve_status` has no branch for the new owners, so a native-owned tool falls to its
final branch: installed version from the local `--version` probe, `latest=None`, `stale=True`,
`source="unknown"`. That is correct, not a gap — `source` names where the LATEST version came from, and
for these owners there is genuinely no source, because this installer does not read dnf/apt/pacman
outdated reports. Do not widen `VersionStatus.source` to carry the owner name; record the reasoning in
the SUMMARY so a later reader does not "fix" a field that is already honest.

An `unsupported` outcome reaching the batch execute screen is rendered by the update-report section
plan 14-02 built, using the same vocabulary as the per-row `u` keybind. Nothing here changes that
rendering, and no second refusal gate is added to `installer/catalog_tui.py`: all update mutation goes
through `UpdateService.run`, which re-resolves ownership and refuses on its own, and Phase 14's record
is explicit that two wordings for one refusal is how users learn to distrust one of them.
