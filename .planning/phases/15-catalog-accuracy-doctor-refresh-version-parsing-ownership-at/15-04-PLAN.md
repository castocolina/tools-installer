<objective>
Bug 3, first half: the machinery that could answer "which OS package manager owns this tool" is
complete for dnf/apt/pacman, has never been reachable, and has no answer at all for the
rpm-ostree/just-layering host this project is being developed on.

`installer/install_ownership.py` already has working `_apt`, `_dnf` and `_pacman` probes and a
`detect_owner` that dispatches them — but `detect_owner` iterates `tool.owner_probes`, and exactly
three registry rows declare that field today (`pi`, `drawio-desktop`, `drawio-cli`, none of them
native-manager rows). So every dnf/apt/pacman-installed tool in the catalog resolves to nothing,
because nobody ever asked.

This plan closes the two data-and-probe gaps, and stops there. It does not change any resolution
result yet: `detect_owner` still has no production caller after this plan, which plan 15-05 fixes.
Splitting it that way is deliberate — the probe and the closed-set schema are testable on their own,
and 15-05's work (widening a `Literal` used by a strict type checker, and adding a refusal branch to
the mutating update path) is the part that needs a clean context and the full attention of its own
review.

D-06's probe cannot key off a method kind the way its siblings do: no registry row declares
`kind = "rpm_ostree"`, and `installer/resolve.py::_applies` returns `False` for that kind
unconditionally — it is skipped as an INSTALL method by design, because it needs a reboot and breaks
atomicity. It is not skipped as an OWNERSHIP probe, which is a different question. The probe therefore
reads the tool's declared `dnf` package name, because rpm-ostree layers RPMs from the same
Fedora/Bazzite repositories dnf installs from.

Purpose: this installer can find out, on every platform family it supports, whether the OS itself owns
a tool.
Output: one new probe, one closed-set member, ten registry rows that opt in, and tests for all three.

## Design decisions this plan implements

- **D-06 — a new `_rpm_ostree` probe in `install_ownership.py`, same shape as its three siblings.**
  Not a new module, not a new abstraction: `_method_values` → `_run` → parse → `Ownership(...)` or
  `None`, registered in the existing `_PROBES` dict. The exact command and parsing are Claude's
  discretion per CONTEXT.md; `rpm-ostree status --json` is what this phase's research ran live on the
  real host, and the JSON shape below is that run's output.
- **Booted deployment only.** `rpm-ostree status --json` returns every deployment, including the
  rollback target and older ones. Ownership is a statement about the system the user is running right
  now, so only the deployment carrying `"booted": true` is consulted. Reading all deployments would
  claim ownership from a system the user is not running.
- **`requested-packages`, not `packages`.** `requested-packages` is what the user explicitly layered.
  It is the set that corresponds to "someone deliberately installed this here."
- **The package name comes from the tool's declared `dnf` method.** rpm-ostree layers RPMs from the
  same repositories, and inventing a second registry field for the same string would be a schema
  change D-03/D-06 never asked for. `_method_values` reads `tool.methods` directly and is not gated by
  `resolve_methods`, so the declaration is readable even on a platform where the dnf METHOD does not
  apply — which is exactly the immutable-Fedora case.
- **`rpm-ostree` is listed FIRST in `owner_probes`.** On an ostree host the rpm database still answers
  `rpm -q`, so `_dnf` would claim a package the user actually layered with rpm-ostree. Probing
  rpm-ostree first attributes a layered package to the mechanism that layered it; everything else falls
  through to `_dnf` unchanged, and on a non-ostree host the `rpm-ostree` binary is absent so `_run`
  returns `None` and the probe is free.
- **A base-image package still reports `dnf`, and that is accepted.** On an image-based OS a package
  that shipped in the base image is in the rpm database but not in `requested-packages`, so it falls
  through to `_dnf`. "The rpm database says so" is a true statement and the user-facing consequence is
  identical either way (15-05 refuses to update both). Record it; do not build a third probe for it.
- **Ten rows opt in, and only those ten.** The set is mechanical: every row declaring a `dnf`, `apt` or
  `pacman` method (`rg`, `jq`, `git`, `zsh`, `watch`, `docker`, `podman`, `kitty`, plus `opencode` and
  `wezterm`, which declare `pacman` only). A test pins the set so a future row cannot drift in or out
  silently.

## Known follow-up, deliberately out of this plan

`detect_owner` still has no production caller when this plan lands — it is reachable only from
`tests/test_install_ownership.py`, exactly as before. That is a knowing, one-plan-long violation of
`.claude/architecture.md` rule 5 ("no orphan helpers"), closed by plan 15-05 in the next wave, which
is the plan that calls it from `installer/ownership.py::resolve_ownership`. Neither plan reaches a
released build on its own: they are the same phase and the phase is not verifiable until both have
landed. Say so in this plan's SUMMARY rather than letting a reviewer discover it.

Per-tool probe cost is unchanged in shape and deliberately uncached: `_dnf`/`_apt`/`_pacman` already
run one subprocess per tool per package, and `_rpm_ostree` adds one more of the same kind. The ten-row
set is small and the live command returned in well under a second on the real host. Do not add a
caching layer here; if it ever matters, it belongs beside `VersionRefreshService`'s existing
manager-snapshot cache, not inside a probe.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| `rpm-ostree status --json` stdout -> `_rpm_ostree`'s parser | untrusted-shaped text from a child process, parsed as structured data |
| registry-declared package names -> a probe's argv | catalog data reaching a subprocess argument list |
| probe subprocess -> the caller's terminal | probes run from a Textual worker thread while the main thread holds the terminal |
