<objective>
Bug 1: the Doctor screen applies a fix successfully and then renders guidance it computed before the
fix ran.

`DoctorScreen.action_apply` (`installer/wizard_app.py:389-394`) calls `self._refresh_body()` and
never `self._refresh_guidance()`. Every other guidance-affecting event in the same class calls both,
in that order. So the success line lands next to an Audit block assembled from state that is one
event old — and any part of that state which the fix itself changed (the guard readings, and
anything else the injected `guard_state` closure reports) is silently stale.

Read this before writing a test: the PATH half of that Audit block genuinely cannot change. The
`DoctorReport` behind `doctor_guidance` is built once in `setup.py::_build_app` from the process's
own `os.environ["PATH"]` and is never re-audited, so calling `_refresh_guidance()` produces
byte-identical PATH findings. That is not a reason to skip D-01 — an invariant kept in three places
out of four is a latent bug waiting on the first guidance source that CAN move — but it does mean a
naive before/after diff of the rendered audit passes with or without the fix. The test therefore
drives a guidance source that really does change while the fix runs (Task 1), and the visible half
of the user-facing bug is D-02's note (Task 2).

Purpose: a user who presses enter on Doctor sees an Audit block that describes the machine as it is
after the fix, plus an explicit statement that the one part which cannot yet reflect the fix — the
live PATH — is expected to lag until they open a new shell.
Output: one added call in `action_apply`, one conditional line in `_refresh_body`, and two tests that
fail without them.
</objective>

## Design decisions this plan implements

- **D-01 — `action_apply` calls `self._refresh_guidance()` after a successful fix, before rendering.**
  The ordering is not discretionary: the three sibling call sites all call `_refresh_guidance()`
  immediately before `_refresh_body()`, and the guidance list is what `_refresh_body` reads through
  `_tui_guidance()`. Refreshing after rendering would be the same bug one frame later.
- **D-02 — the frozen-PATH note is conditional on `self.applied`, not permanent.** It is appended
  inside `_refresh_body`'s existing `if self.applied:` branch and nowhere else. Before the fix there
  is no discrepancy between "applied" and "the live PATH", so there is nothing to explain.
- **Wording is Claude's discretion; the framing is not.** CONTEXT.md leaves the exact sentence open
  and locks the meaning: the stale-looking audit is EXPECTED, not broken, and the way out is a new
  shell or `source ~/.myshellrc`. Do not phrase it as a warning or an error.
- **The note lives on the screen, not in `installer/guidance.py`.** `doctor_guidance` /
  `guard_guidance` / `node_globals_guidance` are pure, IO-free functions that know nothing about
  `self.applied`, and the console `make doctor` path has no apply action at all, so there is no
  second consumer for this sentence today. Pushing an apply-state concept into the pure layer to
  serve one screen would invert that split for no caller.

## Known follow-up, deliberately out of this plan

Re-auditing the live `PATH` after a fix (so the audit itself could change) would mean re-running
`installer/doctor.py`'s audit against a `PATH` the current process cannot have inherited — the new
entry only exists in shell rc files the running process never re-reads. That is not a refresh bug, it
is the operating system, and D-02 exists precisely because it cannot be fixed by refreshing. Do not
attempt it here; record it in the SUMMARY if it comes up.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| injected `guard_state` / `fix` closures -> DoctorScreen | the screen renders state it did not compute and cannot validate |
| DoctorScreen -> the user's mental model of their own PATH | what the screen says about the machine is what the user will act on |
| worker-thread globals audit -> this screen's guidance list | an in-flight audit can land while an apply is being rendered |
