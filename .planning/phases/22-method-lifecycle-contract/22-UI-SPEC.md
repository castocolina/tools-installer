# Phase 22 — UI Design Contract

> **Amendment 2026-11-04 (cross-AI review R2-05, orchestrator sign-off):** `opencode` declares no vendor `remove`. Upstream `opencode uninstall` (v1.19.5) rewrites the user's shell rc file regardless of `--keep-config`, deletes `~/.cache/opencode` and `~/.local/state/opencode`, and never deletes the binary, so it breaks "nothing removed or edited without proof". Its removal is the receipt-proven `~/.opencode/bin/opencode`; the vendor-`remove` mechanism (D-05/D-06) stays, tested on a test-local recipe, and recipe commands run from their receipt-proven absolute executable. Anchors naming `opencode uninstall --keep-config --keep-data` below are superseded. See 22-REVIEWS.md "Decision needing orchestrator sign-off".

Anything upstream left open is under **Auto-decided**; the open questions answered by the orchestrator are recorded there too (A13–A17).

**Scope.** No new screen, no new view, no new number key, no new widget class. Phase 22 adds one key to Uninstall (`c`), extends the `ConfirmUninstall` body, adds one disposition (`MANUAL`) to the shared vocabulary, and changes the copy of some Uninstall rows, removal results and `u` results. The visible changes are:

1. Uninstall: a per-row "delete config too" toggle on `c`, shown only for removable tools that declare `config_paths`.
2. `ConfirmUninstall` lists what runs, exactly which config paths are deleted, what is kept, and the pnpm group warnings, before anything runs.
3. Uninstall rows by removal level: L1 (receipt-proven manager uninstall) names its manager and command; native and SDKMAN owners get hints only.
4. The install review and run summary gain the `manual` disposition: "you run: `<exact command>`" for native dnf/apt/pacman installs and for a brew bootstrap whose prefix is not writable.
5. `u` refuses a pinned `app` tool with the reason copy, and runs the vendor updater for Oh-My-Zsh and SDKMAN.
6. The CLI uninstall (`--uninstall`, with or without `--yes`) states that config is kept.

## Uninstall: the "delete config too" toggle (UI-04, R6; D-11)

### When it is offered

| Row | `c` offered | Why |
|-----|-------------|-----|
| `removable here`, the tool declares `config_paths` | yes | the only case where config may be deleted |
| `removable here`, no `config_paths` | no | the toggle is absent (SPEC AC 8) |
| `managed elsewhere`, `nothing to do` | no | the tool cannot be removed here, so its config is never deleted here |
| environment rows (`pip/npm ban`, `PATH wiring`, `shell tweaks`) | no | they have no separate config |

### Key and states

The key is `c`. The toggle is **off by default**, per row, and never persisted (each Uninstall visit and each relaunch starts with every flag off).

| Action | Effect |
|--------|--------|
| `c` on an unmarked removable row with `config_paths` | marks the row **and** turns its config flag on (deleting config always comes with removing the tool) |
| `c` on a marked row with the flag off | turns the flag on |
| `c` on a row with the flag on | turns the flag off; the row stays marked |
| `space` unmarks a row, or `i` inverts it to unmarked | the flag of that row is cleared |
| `a` all | marks rows; config flags are unchanged (`a` never turns a flag on) |
| `c` on a removable row with no `config_paths` | nothing changes; status `warn`: `{id} declares no config to delete.` (longest id: 54 cells) |
| `c` on a `managed elsewhere` / `nothing to do` row | nothing changes; status `warn`: `{id} cannot be removed here, so its config stays.` (longest id: 69 cells) |
| `c` on an environment row or a section row | nothing changes; status `warn`: `This row has no config to delete.` |
| `c` while a removal runs | allowed, like marking (Phase 21 D-05: a mark is for the next removal). It does not clear the `Removing…` status and is never refused by the mutation lock |
| The row's removal succeeds | its flag is cleared together with its mark (Phase 21 selection rule) |
| The row's removal fails | the row stays marked (Phase 21) and its flag stays as it was, so `enter` retries the same choice; the review shows it again before anything runs |

### How a row shows it

| Element | Flag off | Flag on |
|---------|----------|---------|
| Sel cell (3 cells) | `[ ]` / `[x]` (unchanged) | `[c]` in `bold red` |
| `What gets removed` cell (40-cell budget, truncates with `…`) | unchanged | prefix `config + ` before the existing content |
| Detail bar suffix (removable row with `config_paths` only) | ` · config kept: {paths} (c deletes it too)` | ` · config deleted too: {paths} (c keeps it)` |

- `{paths}` are the tool's declared `config_paths` in their declared `~` form, comma-joined, **only the ones that exist now**. When none exists, the toggle is still offered and the suffix reads ` · config kept: none on disk (c deletes it too)` / ` · config deleted too: none on disk (c keeps it)`.
- Detail bar order for a removable row: the proof sentence (with ` — active copy: …` per C-23), then the config suffix, then ` · remove it yourself: …`, then ` · required by …`. The bar is 3 rows of 78 cells; anything beyond is clipped, and the review always lists everything in full.
- NO_COLOR: `[c]` is a letter, and `config + ` and `config deleted too` are words; color is redundant.
- Footer actions for the Uninstall view: `space mark | enter remove | a all | i invert | c config` (55 cells, shorter than the tiers' 58-cell line). The header hint is unchanged.

## Uninstall: row text by removal level (R1, R2, R4, R10; D-06..D-10)

This table **amends** the Phase 21 "Row text by group" table. Rows not listed here keep their Phase 21 text byte for byte.

| Group / level | `Installed via` | `What gets removed` | Detail bar |
|---------------|-----------------|---------------------|------------|
| Removable, **L1** (brew / uv / pnpm, receipt proves this installer put the package there) | the manager label (`Homebrew`, `uv`, `pnpm`). This is C-23's own rule: the manager owns the copy this row removes | the command, e.g. `brew uninstall gh` | `installed by this installer through {label}: receipt matches — runs `{command}`` |
| Removable, **L2** (download / app artifacts) | `installer` | the proven paths (unchanged) | unchanged (`installed by this installer: receipt matches`, or the adoption or layout sentence) |
| Removable, **L3** (script with `remove`) | `installer` | `{command}, {proven paths}` comma-joined, truncated | `installed by this installer: receipt matches — runs `{command}`, then deletes the proven paths` |
| Removable, **L3** (script, no `remove`) | `installer` | the proven paths | `installed by this installer: receipt matches` |
| Managed elsewhere, brew / cask / uv / pnpm, **no receipt** | the owner label | `—` | the existing `removal_hint`, e.g. `managed by Homebrew — `brew uninstall gh``. Shown as a hint only; nothing runs (D-06) |
| Managed elsewhere, **native** owner (dnf / apt / pacman / rpm-ostree), package known | the owner label | `—` | `managed by {label} — this installer will not remove the package {package}`. **No command, no backtick, no argv** (R4 prohibition) |
| Managed elsewhere, native owner, package unknown | the owner label | `—` | the existing package-less sentence, e.g. `managed by dnf — remove {name} with dnf (no verified package name)` |
| Managed elsewhere, **SDKMAN** candidate, version read | `SDKMAN` | `—` | `managed by SDKMAN — `sdk uninstall {candidate} {version}`` (version from the `VersionStatus` the pass already holds; D-09) |
| Managed elsewhere, SDKMAN candidate, version not read | `SDKMAN` | `—` | `managed by SDKMAN — `sdk uninstall {candidate} <version>`; the installed version was not read` |
| Managed elsewhere, Volta | `Volta` | `—` | the existing `managed by Volta — `volta uninstall {package}`` (unchanged) |
| Nothing to do, missing, with leftover unproven paths | `—` | `—` | `not installed · remove it yourself: {paths}` (today the `remove it yourself` clause is dropped for a missing tool; it is now kept) |

- `{command}` is the plan's argv joined for display with shell quoting (`shlex.join`). It is a display string, never re-parsed or executed from the text.
- **A foreign file at a declared script path** (one the receipt did not record, or one whose type or link target no longer matches) is never in `What gets removed`. It is listed by the existing ` · remove it yourself: {paths}` clause before the removal, and is still listed after it (row above).
- The `opencode` anchor reads: `What gets removed` = `opencode uninstall --keep-config --keep-data, {paths}` (truncated), detail = `installed by this installer: receipt matches — runs `opencode uninstall --keep-config --keep-data`, then deletes the proven paths`. Its config is not touched by the vendor command (it is told to keep it); `c` is the only way to delete it, and only for the paths the registry declares.

## ConfirmUninstall: the review (R6, R10; D-07, D-10, D-11)

The modal is the review: everything below is shown **before anything runs**. Layout at 80×20: `width: 60` (unchanged), `max-height: 18`, round red border, `padding: 1 2`, so the text column is 54 cells. The body scrolls inside the modal when it is taller than the space; the keys line is always the last visible row.

Order of lines (a block appears only when it has content):

| # | Block | Copy | Style |
|---|-------|------|-------|
| 1 | Title | `Remove {summary}?` (unchanged; `{summary}` from `_accept_summary`) | bold red |
| 2 | Warning | `This deletes installed artifacts and is not undoable.` (unchanged) | regular |
| 3 | What runs | one line per L1/L3 tool: `{id}: runs {command}` | regular |
| 4 | Config deleted | heading `Config deleted too:` then one line per path: `  {path} ({id})` | heading bold red; paths regular |
| 5 | Config kept, shared | `  {path} kept, also used by {other ids}` (under block 4's heading) | dim |
| 6 | Config kept | `Config kept: {ids}.` for marked tools that declare `config_paths` with the flag off | regular |
| 7 | pnpm group | one line per affected group, see below | `Warning:` yellow, rest regular |
| 8 | Keys | `enter remove · esc cancel` (unchanged) | dim |

- **Exactly the listed paths are deleted** (SPEC AC 8). A path is listed in block 4 only when it exists now and every tool that declares it is in this removal with its flag on. A path also declared by a tool that is not being removed, or whose flag is off, goes to block 5 and is kept.
- Paths are shown in their declared `~` form. **No review line is ever truncated** inside the 54-cell text column: a path (block 4/5), a command line (block 3, e.g. `opencode: runs opencode uninstall --keep-config --keep-data`, 59 cells) and a pnpm warning (block 7, e.g. `Warning: pnpm group mmdc: removing @mermaid-js/mermaid-cli leaves puppeteer installed.`, 86 cells) all wrap onto the next row with the same 2-cell hanging indent.
- **pnpm group warning** (D-10). Group = the declaring tool's id; members = the package names pnpm knows.
  - Some members stay: `Warning: pnpm group {group}: removing {removed} leaves {others} installed.` Example: `Warning: pnpm group mmdc: removing @mermaid-js/mermaid-cli leaves puppeteer installed.`
  - Every member is removed in this run: one line, `Warning: pnpm group {group}: all its members are removed together.`
  - A package outside any group: no line.
- Every line is built from `Text` pieces. Ids, paths, commands, package and group names are data: they go through `sanitize_log_line` and are appended as plain text, never interpolated into markup (today's `Text.from_markup(f"…{self.summary}…")` is replaced).

## Removal results (R1, R6; D-07)

Written by `on_removal_finished` through `show_result` (Phase 21 C-28). Order of status lines: the counts (`summary_counts`, unchanged), the failure line (unchanged), **the config lines below**, then `_applied_summary` (unchanged), then the cache and terminal warnings (unchanged).

| Situation | Status line | Severity |
|-----------|-------------|----------|
| Config deleted for one or more tools | `Config deleted for {ids}.` | ok (unless something else raised it) |
| A removed tool that declares `config_paths`, flag off, config still on disk | `Config kept for {ids}.` | ok |
| Flag on, but the tool's removal failed (vendor `remove` non-zero, or a delete failed) | `Config not deleted for {ids}: the removal failed.` | error (the run already has a `remove failed`) |
| Flag on, the removal succeeded, one config path could not be deleted | `warning: could not delete config {path} — {first line of the error}.` (the existing `warning: {…}.` form) | warn |
| A config path already gone | no line (skipped without error) | — |
| Unproven paths left in place by a successful removal | no status line; the row lists them (`not installed · remove it yourself: {paths}`) | — |

- `{ids}` are comma-joined in selection order. A line longer than 78 cells wraps onto the next status row; `StatusLine` is `height: auto`.
- **Vendor `remove` failed** (R1). The row word is the Phase 21 `remove failed — {first line of the sanitized vendor error}`. Nothing else of that tool was deleted, its config is untouched, its row stays in `removable here`, stays marked, and keeps its config flag.
- Shown on another view (C-28): these lines name no key, so `elsewhere=` is not needed for them; the existing `remove failed` rewrite still applies.

### CLI uninstall (`--uninstall`, with or without `--yes`)

The CLI never deletes config (SPEC R6), and it has no toggle. `run_uninstall` prints, after the existing preview (`The following will be removed:` and `Not removed (tools-installer cannot prove it installed these); …`) and before the confirm:

| Line | Copy |
|------|------|
| What runs | `{id}: runs {command}` per L1/L3 tool (the same string as review block 3) |
| pnpm group | the same `Warning: pnpm group …` lines as review block 7 |
| Config | `Config kept; only the Uninstall view deletes config (press c on a row):` (71 cells), then `  {path}` per existing declared config path of the tools being removed |

The config block is printed only when such a path exists. Paths and commands are printed with `markup=False` and `soft_wrap=True`, as `render_uninstall` does.

## MANUAL handoffs (R3, R9; D-12, D-13)

### Vocabulary

| Disposition | Review word | Done word | Color | Counts toward exit 1 | Stays selected |
|-------------|-------------|-----------|-------|----------------------|----------------|
| `MANUAL` (new) | `manual` | `manual` (the existing `RESULT_WORDS["manual"]`) | yellow | no | yes |

- `manual` takes its place in the review counts and summary counts right after `blocked`, as `summary_counts` already orders it: `Install plan — 2 will install, 1 manual`, then `Summary — 2 installed, 1 manual`.
- BLOCKED keeps its Phase 20 meaning ("nothing the installer can do", e.g. `blocked — dnf owns it; repair needs sudo (never run here)`). MANUAL means "here is your command".

### Review row (plan time, before anything runs)

`{health glyph} {id}  manual — {reason}`. The reason is written once in `build_plan`:

| Situation | Reason |
|-----------|--------|
| Native dnf install method | `needs sudo (never run here); you run: `sudo dnf install {package}`` |
| Native apt install method | `needs sudo (never run here); you run: `sudo apt-get install {package}`` |
| Native pacman install method | `needs sudo (never run here); you run: `sudo pacman -S --needed {package}`` |
| rpm-ostree host, the resolved method's own command | `needs admin rights and a reboot (never run here); you run: `rpm-ostree install {package}`` (no `sudo`: rpm-ostree elevates through polkit) |
| Script with a `writable_prefix` that is not user-writable (brew bootstrap) | `{prefix} is not writable by you; you run: `{shell} -c "$(curl -fsSL {url})"`` |

- The command is the **exact** command for the user to type: the package name from the method, no `-y` / `--noconfirm` (the user confirms it themselves). For the brew bootstrap the `NONINTERACTIVE` env of the method is dropped, because the user runs it interactively.
- The command is a **display string**. No code path builds an argv list whose first element is `sudo`, `pkexec` or `doas` (the R3 grep test).
- Widths with the longest native package (`docker-cli`): pacman reason 74 cells, rpm-ostree reason 90 cells. Both fold the same way after the `{glyph} {id}  manual — ` prefix, so rpm-ostree uses the same budget as dnf/apt/pacman and keeps the full wording.
- The reason folds with the existing hanging indent (`fold_reason`). The brew reason is 141 cells and folds over 3 rows at 80 columns; that is the review's normal wrap, not an error.
- If the engine's re-check at run time (D-12) finds a row that was planned to run now `needs_manual`, the row ends `manual` with the same reason text.

### Finished row and the run report

| Place | Copy |
|-------|------|
| Finished row | `manual — you run: `{command}`` (replaces the fixed `see the setup steps in the log` for MANUAL rows only; other `manual` results keep their Phase 20 text) |
| Run report (`render_handoff`, in the `#execute-log` and on the headless console) | `{id} — manual setup required:` (existing heading), then the command alone on the next line, indented 2 cells |
| Finished status (TUI) | the existing `{Done.|Failed.|Nothing ran.} {Still selected: N. }enter or esc returns to the catalog.` A manual-only run reads `Nothing ran. Still selected: 1. enter or esc returns to the catalog.` |
| Headless exit code | unchanged by MANUAL (0 when nothing failed) |

**Copying the command.** In the run report the command line holds the command and nothing else: no backticks, no trailing period, no prefix besides the 2-cell indent, printed with markup off (`render_handoff` gains `markup=False`, as `render_post_install_handoff` already has) and never wrapped by the app (`RichLog` keeps `wrap=False`; the headless console prints with `soft_wrap=True`). So one terminal selection of that line copies exactly the command. The review and finished rows show the same command between backticks; those rows may fold and are for reading, not for copying.

## `u` outcomes (R7, R8, R12; D-14..D-16)

| Situation | What runs | Status |
|-----------|-----------|--------|
| `u` on a pinned `app` tool with no version source (e.g. `drawio-desktop`) | nothing; no lock taken, no worker started, one refresh request (as every `u` refusal does) | `warn`: `cannot update {id}: pinned; update outside or re-pin` (the existing `cannot update {id}: {reason}` refusal template; 62 cells for `drawio-desktop`, 72 for the longest id) |
| Same refusal reached by a headless UPDATE row (race only; `build_plan` never plans it) | nothing | `blocked — pinned; update outside or re-pin` |
| `u` on `oh-my-zsh` | `{omz_root}/tools/upgrade.sh` | `ok`: `updating oh-my-zsh…`, then `updated oh-my-zsh` on exit 0; a non-zero exit uses the existing failed copy (`error`, the first line of the sanitized error) |
| `u` on `sdkman` (the bootstrap) | `sdk selfupdate` | `updating sdkman…`, then `updated sdkman`, or the existing failed copy |
| `u` on an SDKMAN **candidate** | nothing | unchanged: `SDKMAN owns this tool; this installer does not run SDKMAN's interactive upgrade — update it with `sdk upgrade {candidate}` in your own terminal` |
| macOS, a cask with `auto_updates` that `brew outdated --greedy` reports | `brew upgrade --cask --greedy {cask}` | its tier row shows `↑` (`update available`); `updating {id}…` then `updated {id}`. No new copy |
| Any other cask, and all of Linux | unchanged | unchanged |

- The `UpdateOutcome.detail` of the pinned refusal is exactly `pinned; update outside or re-pin`. The TUI adds `cannot update {id}: `, the headless row adds `blocked — `, so neither repeats the other.
- The pinned check runs in `action_update_tool` through the shared `update_refusal` predicate, **before** `begin_mutation`, so the user never sees `updating drawio-desktop…` for a refused update.
- Oh-My-Zsh reports `updated oh-my-zsh` whenever the vendor updater exits 0, including when it had nothing to do (SPEC edge R8: the exit code decides).

All new status strings are at most 78 cells for the longest tool id (`softaworks-agent-toolkit`, 24 cells), except where a list of ids or a path makes a line longer, in which case `StatusLine` wraps it onto the next row. All new sentences follow the house register: lowercase cell fragments with no period, status sentences capitalized and ending with a period (the `cannot update …` and `updated …` lines keep their existing lowercase, no-period form).

**Data, never markup.** These values are data. They are sanitized with `sanitize_log_line`, appended as `Text` (or printed with `markup=False`), and never interpolated into a markup string: tool ids, package and candidate names, versions, pnpm group names and members, every path (config, artifact, `remove it yourself`, `writable_prefix`), every displayed command (L1/L3 argv, MANUAL command, SDKMAN hint), and the first line of every error (vendor `remove`, config delete, update). A `[` or an ANSI escape in any of them renders literally.

## Keyboard and accessibility

- **One new key:** `c` on Uninstall. No other key changes. `c` is not a mutation (nothing runs until `enter` and the confirm), so the mutation lock never refuses it and navigation is never blocked.
- **Word and letter first.** `[c]`, `config + `, `Config deleted too:`, `Warning:`, `manual` and `cannot update …` all carry their meaning without color; under `NO_COLOR` nothing is lost.
- **No motion.** `updating {id}…` and `Removing…` stay static text.
- **Width.** `[c]` is 3 cells; every new glyph is one cell by `rich.cells.cell_len`.
- **Focus.** The modal takes focus while open (unchanged); its scroll body scrolls with the arrow keys and `pgup` / `pgdn`, while `enter` / `y` / `esc` / `n` keep their bindings.
