<objective>
The registry learns the lifecycle keys this phase needs, and the dangerous ones are validated at load. Tools may declare `config_paths` (tool level); script methods may declare `paths`, `remove`, `update` and `writable_prefix` (method level). The `config_paths` denylist comes from one constant shared with the skill harness detection, so a config entry can never point into `~/.claude`, `~/.cursor`, `~/.gemini`, `~/.codex` or any other harness dir. Script tokens get `~` plus a closed set of named roots (`{omz_root}`), never a shell. Dead fields (`Tool.source/owner/uninstall`) and the four dead post-install action names are deleted.

Purpose: LIFE-04 in full; the schema half of LIFE-01 (script recipes) and LIFE-07 (`writable_prefix`). Later plans read these keys: 22-03 (`paths`), 22-04 (`writable_prefix`), 22-05 (`update`), 22-06 (`remove`, `config_paths`), 22-08 (registry data).
Output: the validated keys in `installer/model.py`, `HARNESS_PRESENCE` derived in `installer/skill_lifecycle.py`, three registry rows cleaned, load fixtures.
</objective>

- `paths` entry shape (Claude's discretion, consumed by 22-03): `~/...` or `{root}/...`; a trailing `/` declares a directory (a type-only `tree` artifact); anything else is a file or link (a `leaf`). No absolute system path: a removal never deletes outside HOME.

- Error text names tool and key, the house style: `tool '{id}': config_paths entry '{entry}' {why}` and `tool '{id}': method 'script' key '{key}' {why}`.
