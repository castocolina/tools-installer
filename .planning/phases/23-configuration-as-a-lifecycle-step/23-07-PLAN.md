Decisions recorded for this plan:
- `ConfigStepKind` gains `hook_register` and `zshenv_shell`; `ConfigStep` gains an appended `report: str = ""` (step-specific report text: for `terminal_sync` the done note `{label} now starts zsh` plus a newline, two spaces and the `~` config path; for `zshenv_shell` the zsh path). `_STEP_KINDS` picks the kinds up automatically; `_step_runs_command` treats both as running a command.
- Hook facts (D-02): a `_hook_facts(tools, present)` helper in version_status: for each tool whose `postinstall` names a pair with targets and whose receipt (`receipts.read`, fail-closed) exists, `missing = [h for h in pair.targets if h in present and h not in receipt.hooks.get(name, ())]`; non-empty → `_ConfigFacts((f"{tool.id} is not registered for {labels}",), (ConfigStep(f"register {tool.id} for {labels}", "hook_register"),))` with `labels = host_labels(missing)`. `present` is one `present_harnesses(self._skill_home, self._looked_through)` call per pass, wrapped like `_scan_packs` (a failure gives an `unchecked` note `agent hosts not checked: {error}` on the hook tools, never a failed pass). Merged into `config` in `_pass`.
- zshenv facts (O6): `_terminal_facts` handles the name `zshenv` before the `_TERMINAL_ROWS` lookup: the zsh row gets `_ConfigFacts(("~/.zshenv does not export SHELL as zsh",), (ConfigStep(f"export SHELL={result.zsh} in ~/.zshenv", "zshenv_shell", report=result.zsh or ""),))`. Terminal steps get `report=f"{label} now starts zsh\n  {tilde(path)}"` from `dict(result.paths)`, where `tilde` writes a path under `Path.home()` as `~/…`; a terminal with no path keeps `report=f"{label} now starts zsh"`.
- `_run_step`: `terminal_sync` and `zshenv_shell` share the existing synchronizer branch; on success the warning (detail) is the synchronizer's own warning when it returned one, else `step.report` for `terminal_sync` and the fixed `~/.zshenv exports SHELL` for `zshenv_shell`. `hook_register`: receipt → `hook_method` → `register_hooks(tool, method, ctx.runner, hosts)` with `hosts = (ctx.harnesses or present_hosts)()`; no receipt or no method → `failed="no install receipt to record the hook in"`; nothing registered with a warning → `failed=warning`; registered → `warning=f"registered for {host_labels(registered)}"` (plus `; {warning}` when a host failed).
- `_run_reconfigure` keeps every step's warning in order, joined with newlines, as `detail`. `render_done_notes` prints, for a RECONFIGURE row, each detail line that starts with two spaces as is and every other line as `{id} reconfigured — {line}` (sanitized, markup off, soft wrap, as today).
- D-03 sweep: `RunContext.harnesses: Callable[[], frozenset[str]] | None = None` and `RowOutcome.resynced: tuple[tuple[str, tuple[str, ...]], ...] = ()` and `RowOutcome.resync_warnings: tuple[tuple[str, str], ...] = ()` (appended). After the row loop, when the last outcome whose row disposition is INSTALL, REPAIR or REINSTALL, whose result is `done` and whose tool id is a value of `HOST_CATALOG_IDS` exists, `_resync_hooks(ctx)` recomputes the hosts once (research D14, Pitfall 8) and, for each catalog tool whose pair has targets and whose receipt and `hook_method` exist, calls `register_hooks` inside an `except Exception` isolation (first line as the warning); the results replace that outcome via `dataclasses.replace` before `execute_plan` returns. Add a `shortcut:` comment: the sweep's command output is attributed to the last row in the TUI log; upgrade when the log gains a run-level attribution.
- Report: `render_hook_lines(outcomes, console)` prints the bold heading `Agent-host hooks` then, per outcome, `{tool}: registered for {labels}` from `install.hooks` and `{tool}: registered for {labels} (new host)` from `resynced`; it runs right after `render_postinstall_warnings`, and `resync_warnings` print in the warning form `⚠ {tool} postinstall warning: {warning}` inside `render_postinstall_warnings`' position. `render_shell_section(outcomes, console)` prints the bold heading `Shell`, `~/.zshenv now exports SHELL; new terminals start with it.` and `  SHELL={report}` for a done RECONFIGURE row with a `zshenv_shell` step; it runs last in `render_run_report`. Decision: the Shell section sits at the end of the one report renderer instead of after the PATH wiring lines (which the callers print later), so no caller gains a second render call; the order difference is cosmetic.
