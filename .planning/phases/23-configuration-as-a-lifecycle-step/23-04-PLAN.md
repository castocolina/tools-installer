Decisions recorded for this plan:
- D-15 (locked): the `.zshenv` line is an owned block, markers `# >>> tools-installer shell >>>` / `# <<< tools-installer shell <<<`, body `export SHELL=<shlex.quote(zsh_path)>`, through `apply_block`/`strip_block`, written with `atomic_write_text` only when the content changes.
- Placement (Claude's discretion): inside `sync_terminal_shells`, right after `zsh_path` is resolved, so the existing post-run trigger (20 D-11, D-17 already landed) and the existing dry run carry it. Linux only, like the terminal regions (the function returns early on macOS; macOS terminals already start zsh with a zsh `SHELL`, UI-SPEC U12). The block is reported as the name `zshenv` in `drifted` (dry run) and, on a write run, `zshenv` is added to `configured` and to `drifted` when it changed.
- Failure containment (review R1-21): `_sync_zshenv` catches `OSError` (which covers `TerminalShellError` from `_read_text`: non-UTF-8, FIFO, oversize) and returns the warning `zshenv: {first line}` instead of raising; `sync_terminal_shells` appends it to `warnings` and goes on to kitty, WezTerm and Konsole. Nothing is written to that `.zshenv`. (23-07 maps the `zshenv` warning prefix to the zsh row, so the terminal rows stay checked.)
- `locations.zshenv_path(home, environ)` (23-REUSE.md 04-2, amended by review R1-20): one resolver, built on `zshrc_path`. zsh reads `$ZDOTDIR/.zshenv` only when `ZDOTDIR` is already in the environment when zsh starts; when `~/.zshenv` itself assigns `ZDOTDIR` (a common setup, and the installer then inherits that `ZDOTDIR`), zsh reads `~/.zshenv` and never `$ZDOTDIR/.zshenv`. So: `home/.zshenv` when that file exists and has an uncommented line matching `^\s*(export\s+)?ZDOTDIR=`; otherwise `zshrc_path(home, environ).with_name(".zshenv")`. Read the file with the capped reader; an unreadable `~/.zshenv` falls through to the `zshrc_path` rule (the sync then reports its own `zshenv:` warning).
- No zsh on a write run: `_revert_terminal_shells` also strips the block (a file left with only whitespace keeps its bytes as they are after the strip; it is not deleted, because the user may own an empty `.zshenv`).
- `TerminalShellResult` gains appended fields `zsh: str | None = None` (the resolved zsh path) and `paths: tuple[tuple[str, Path], ...] = ()` (name → the file written or checked: `kitty`, `wezterm`, `konsole` (its profile path), `zshenv`).
- D-14 (shrunk by research D5): `write=False` already exists. The kitty body becomes two lines: the existing `shell …` line and `env SHELL=<zsh_path>`. The WezTerm body becomes three lines: the existing `config.default_prog = { "<zsh>", "-l" }`, then `config.set_environment_variables = config.set_environment_variables or {}`, then `config.set_environment_variables.SHELL = <_lua_string(zsh_path)>`. Every existing configured terminal therefore drifts once after the upgrade (research Pitfall 11, intended).
- D-16 (locked): `CacheRedirect` gains an appended field `absolute: str | None = None`; `target_path` returns `Path(absolute)` when it is set, still validating the variable name, absoluteness and the rejected characters. `write_linux_redirect` ends with `target_path(redirect, home).mkdir(parents=True, exist_ok=True)` (env_redirect.py near line 158), which creates the cache directory; with `absolute` set that path is the zsh BINARY: an existing binary raises `FileExistsError`, a missing one would get a directory created at that path outside the scratch HOME. Skip the mkdir when `redirect.absolute` is set, with a one-line why comment (23-REUSE.md 04-1, Important; review R1-03).
- Ownership without a zsh (review R1-48; reverses 23-REUSE.md 11-2's "drop `owned`"): `DESKTOP_SHELL_CONF = "52-tools-installer-desktop-shell.conf"`; `conf_owned(conf_dir, basename) -> bool` is the sentinel check `remove_linux_redirect` already does (an owned file exists), and `remove_owned_conf(conf_dir, basename) -> bool` is `remove_linux_redirect`'s body taking a basename; `remove_linux_redirect(redirect, conf_dir)` delegates to it and `linux_applied` reuses `conf_owned`'s read. 23-11's desktop row uses them so a file pointing at a removed or moved zsh still reads as ours and is removed by the uninstall sweep. `shell_redirect(zsh_path: str) -> CacheRedirect` builds `id="desktop-shell"`, `label="SHELL for desktop apps"`, `variable="SHELL"`, `target_parts=()`, `reason="Start apps launched from the desktop menu with zsh as their SHELL."`, `coverage_caveat="Takes effect at your next login; terminals already get SHELL from ~/.zshenv."`, `conf_basename=DESKTOP_SHELL_CONF`, `absolute=zsh_path`.
