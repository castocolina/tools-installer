# Phase 20 — UI Design Contract

> Visual and interaction contract for the install-plan review, the run progress panel, the summary and the headless plan printout.
> Generated by gsd-ui-researcher in `--auto` mode (no user questions). To be verified by gsd-ui-checker.

This is a **Textual terminal UI**, not a web frontend. Units are terminal **cells** (columns) and **rows**, not px. The "design system" is the existing house chrome (`installer/ui_common.py`), the `ExecuteScreen` modal (`installer/execute_screen.py`), the Phase 19 health marks (`health_cell` in `installer/catalog_tui.py`) and `installer/render.py`. Line references are from `main` at `db776d2`.

**Sources (all locked, none re-asked):** `20-SPEC.md` R1–R9, `20-CONTEXT.md` D-01..D-17 and ledger L-19-28, L-20-01..L-20-09, `20-RESEARCH.md` (Pitfalls 13, 15, 17), `19-UI-SPEC.md` (glyph set, colors, 78-cell budget, copy register), `.planning/research/2026-10-13-target-architecture.md` §3.1–§3.2. Anything not answered upstream was decided here and is listed under **Auto-decided**.

**Scope.** Phase 20 changes one screen (`ExecuteScreen`: review, wait, run, finish) and one text renderer (`render_plan` / `render_run_summary` in `render.py`, shared with headless). It adds **no new screen, no new view and no new navigation**. The catalog tiers keep Phase 19's contract; the only catalog-side copy changes are the two PLAN-08 strings and `UNPROVEN_NOTE` (see Copywriting Contract).

## Layout contract

### Regions and the 80×20 row budget

The screen has five regions. **Status and keys are pinned to the last two rows at every plan size.** That is the property the current screen fails (baseline above).

| Region | Widget (id) | Review / wait | Running / finished |
|--------|-------------|---------------|--------------------|
| Head | `Static` `#execute-head` | `height: auto; max-height: 3`, `padding: 0 1` | same |
| Plan | `OptionList` `#plan-rows` | `height: 1fr` (17 rows at 80×20 when the head is 1 row) | `height: auto; max-height: 8` (it shrinks to fit, never more than 8 rows, scrolls) |
| Log | `RichLog` `#execute-log` | `display: none` | `height: 1fr`, `padding: 0 1` (at least 8 rows at 80×20) |
| Status | `StatusLine` | `height: auto` (1 row; its copy is written to fit 78 cells) | same |
| Keys | `Static` `#execute-keys` | `height: 1`, `padding: 0 1` | same |

- Switch between the two columns with a screen class: `ExecuteScreen.-running` and `ExecuteScreen.-finished` show the log and cap the plan region. The idle and waiting states have neither class.
- Delete `#execute-progress` and its `Static`; `#plan-rows` is the one progress panel (the rows themselves change as the run goes). Keep `#execute-head`, `#execute-log` and `#execute-keys` as ids so the 97 existing `ExecuteScreen(` tests keep working.
- The old head padding `1 2` becomes `0 1`. The old `height: auto` head that held a Rich table is gone: the head is counts text only.
- **Row budget at 80×20, review, head = 1 row:** row 0 head · rows 1–17 plan (17) · row 18 status · row 19 keys. **Running, head = 1 row:** row 0 head · rows 1–8 plan (≤ 8) · rows 9–17 log (≥ 9) · row 18 status · row 19 keys.
- **Required pilot checks (planner), all at `size=(80, 20)`:**
  1. With 25 plan rows (some folded to 2–3 lines): `screen.get_widget_at(2, 18)` is the `StatusLine` and `get_widget_at(2, 19)` is `#execute-keys`.
  2. The same check with the worst-case head (every count category non-zero, two-digit counts: it folds to 3 rows).
  3. In the running state, the log region is at least 6 rows and the plan region at most 8.
  4. No rendered line of `#plan-rows` is wider than 78 cells (`rich.cells.cell_len`, measured on `render_line` text).
- At 120×30 the plan region simply gets more rows; the fold width grows with the widget (see Row anatomy), clamped to 100.

### Row anatomy (one `PlanRow` = one `Option`)

```
{mark}{sp}{indent}{id, padded}{sp}{sp}{word}{ — reason}
```

| Part | Rule |
|------|------|
| `mark` | exactly one cell. See "Marks" below |
| `sp` | one cell |
| `indent` | 2 cells for a dragged dependency, 0 for a directly selected tool. **The indent is applied after the mark, so the mark column stays at x=0 on every row** and a user can scan the health marks down one column |
| `id` | the tool id, **bold**. Padded with spaces to the id column width `idw` = the longest `indent + id` among all rows, capped at 26 (2 + the longest registry id, 24) |
| `word` | the review word from `WORDS` (see Words), styled by the color map below |
| ` — reason` | em dash with one space each side (3 cells), then the reason in regular weight. Absent for rows whose word is self-sufficient (done outcomes, `checking…`) |

- **Folding.** `render_plan(rows, width)` lays a row out on one line when `2 + idw + 2 + len(word + " — " + reason) <= width`. Otherwise it breaks the reason at spaces onto continuation lines whose first character is at the **word column** (x = `2 + idw + 2`), so the reason hangs under the word. Every produced line is `<= width` cells. `width` = the plan region's content width (80-column terminal → 78) in the TUI, `min(console.width, 100)` headless (80 when the width cannot be detected). A row has no line cap: the region scrolls. The folds are explicit newlines inside one `Text` per `Option`, so the widget never re-wraps them (the widget content width is the fold width; re-fold on `Resize`).
- **Worst case that must still fit unfolded:** `idw` 26 + word column start 30 leaves 48 cells; the longest fixed phrase `skipped — already current (r: reinstall)` is 41. `will install — needed by softaworks-agent-toolkit` is 49 and folds by one word. The 78-cell test uses a 24-character id and a 2-cell indent.
- **Steps.** A `will reconfigure` row adds one continuation block starting at the word column: `to configure: {step 1}; {step 2}` (the Phase 19 phrase, steps in execution order, which is `state.unconfigured` tuple order). The steps text is folded like a reason.
- **Reasons are data, not markup.** Build every row as `rich.text.Text` appended piece by piece (never f-string interpolated into markup) and pass reason, step and detail text through `sanitize_log_line`. A `[` in a plugin id or repo path must not restyle or hide anything. Test: a reason containing `[red]x[/]` and `\x1b[31m` renders literally and without the escape.
- **Dragged rows are grouped at render time (L-20-05, D-02).** `PlanRow` order is execution order (dependencies first). `render_plan` emits each directly selected row, then, immediately after it, the dragged rows whose `requested_by` is that tool, each indented 2 cells, in their execution order. A dragged row appears exactly once, under its first requester, at one indent level only (a chain C → B → A still indents both B and C once, under the selected root). A dragged dependency whose requester row is itself dragged does not nest further. Because a dragged row runs before the row it sits under, the plan head says so (copy below).
- **Selected-and-needed.** A tool that is both selected and required by another selected tool is a direct row (no indent). Indentation means "you did not pick this".

### Marks (column 0)

The mark states a fact about the tool, never about the disposition word, so it never needs a legend: the word is always on the same line.

| Phase of the screen | Mark | Style |
|---------------------|------|-------|
| Idle review, waiting, pending rows during a run | `health_cell(state)` glyph captured at plan time: `…` checking · `!` broken · `≈` misconfigured · `↑` outdated · `✓` ok · `○` missing · `–` unavailable | the Phase 19 style for that glyph |
| A row's tool is running | `>` | bold, default foreground |
| A row finished `done` | `✓` | `green` |
| A row finished `failed`, `mismatch` or `crashed` | `✖` | `red` |
| A row finished `skipped`, `blocked`, `manual`, `dependency_failed` or `not_attempted` | unchanged (the health glyph from plan time) | `dim` (amended by gap plan 20-27, WR-08: a row the run did not change never ends green like a `done` row) |

- The mark changes only when the tool's state changed (`✓`), was attempted and failed (`✖`) or is in flight (`>`). A skipped row never turns green. That keeps the screen truthful without a re-read of state (an update invalidates the epoch, so the screen must not read `state_of` after the run starts; the glyph is stored on the `PlanRow` as `health`).
- `PlanRow` therefore carries (UI contract addition to D-01 and research A6): `health` (the `Health` or `None`), `can_reinstall: bool`, `steps: tuple[str, ...]` (the `ConfigStep.text` values), and `owner_label`. The renderer reads only the row, never published state.
- All eight marks are distinct glyphs except that the OK health glyph and the `done` mark share `✓` by design (both say the tool is now fine; the finished style tells them apart: `done` green, unchanged `dim`); none relies on color. `>` and `✖` are new; `✖` already ships in `_PROGRESS_GLYPH` (`execute_screen.py:85`).

## Words (the one vocabulary, `WORDS` in `installer/session.py`)

One table feeds the review, the progress panel, the summary and headless output. No other module spells a disposition or outcome word.

| Disposition | Review word | Done word (summary and finished row) | Review color | Done color |
|-------------|-------------|--------------------------------------|--------------|-----------|
| INSTALL | `will install` | `installed` | green | green |
| UPDATE | `will update` | `updated` | yellow | green |
| REPAIR | `will repair` | `repaired` | yellow | green |
| RECONFIGURE | `will reconfigure` | `reconfigured` | yellow | green |
| REINSTALL | `will be reinstalled` | `reinstalled` | yellow | green |
| SKIP | `skipped` | `skipped` | dim | dim |
| BLOCKED | `blocked` | `blocked` | red | red |
| pending state (no published `ToolState`) | `checking…` | none (a plan with a `checking…` row is never executed) | dim | n/a |

Non-done result words (one per remaining `RowOutcome.result`; none has a review counterpart because nothing is planned as these):

| `result` | Word | Color | Counts toward exit 1 |
|----------|------|-------|----------------------|
| `failed` | `failed` | red | yes |
| `mismatch` | `checksum mismatch` | red | yes |
| `dependency_failed` | `dependency failed` | red | yes |
| `not_attempted` | `not attempted` | red | yes |
| `crashed` | `crashed` | red | yes |
| `manual` | `manual` | yellow | no |

- **Color rule (one sentence):** green = it worked or will be added; yellow = a present tool will be changed, or the user must act; red = nothing happened because something is wrong; dim = deliberately left alone. This is Phase 19's rule (yellow = "present and needs action") extended to words.
- **Parity (R4).** A `Disposition` member without a review word and a done word fails a test; a `result` without a word fails a test. `skipped` and `blocked` are the same word in review and summary on purpose. The tests iterate `WORDS`; they do not list words.
- **Reserved:** `WORDS` is structured so Phase 22's `Disposition.MANUAL` ("you run: `<exact command>`") only needs a new row (L-20-02). Phase 20 renders no plan-time MANUAL row.

### Summary counts

`summary_counts(outcomes)` renders non-zero counts only, comma-joined, in this fixed order: installed, updated, repaired, reconfigured, reinstalled, skipped, blocked, manual, failed, checksum mismatch, dependency failed, not attempted, crashed.

| Outcomes | Text |
|----------|------|
| 2 done installs, 1 done update, 3 skipped, 1 failed | `2 installed, 1 updated, 3 skipped, 1 failed` |
| An all-current tier after `a` | `3 skipped` |
| Empty outcome list (nothing selected) | `nothing selected` |

The plan head uses the same function over **review** words: `Install plan — 2 will install, 1 will update, 3 skipped, 1 blocked`. The finished head: `Summary — 2 installed, 1 updated, 3 skipped, 1 failed`. Both fold at a comma boundary; a fold is a normal wrapped line, not an error. Worst case (all 13 categories non-zero, two-digit counts) is 3 head rows, which is why the head has `max-height: 3`.

## Disposition copy (the reason after ` — `)

One reason per row (R1), written once in `build_plan`, rendered verbatim. `{x}` values come from state and are escaped as data.

| Situation | Word | Reason |
|-----------|------|--------|
| Direct, missing | `will install` | `not installed` |
| Dragged, missing | `will install` | `needed by {requester}` |
| Direct, broken, installer or user-level owner | `will repair` | the first clause of `state.reasons[0]` (the text before any ` — `), e.g. `shim present, package missing` |
| Direct, broken by receipt drift (L-20-01) | `will repair` | `changed since install; the file is replaced` |
| Dragged, broken | `will repair` | `{broken reason as above}; needed by {requester}` |
| Broken, owner would need sudo (R3, zero-sudo) | `blocked` | `{owner label} owns it; repair needs sudo (never run here)` |
| Direct, misconfigured with executable steps | `will reconfigure` | the first clause of `state.reasons[0]`, e.g. `partial: missing on Codex`; plus the `to configure:` continuation |
| Direct, misconfigured, no executable step (L-20-04) | `blocked` | the first clause of the health reason, e.g. `project pack: no repo detected` |
| Direct, outdated, update allowed | `will update` | `{installed} -> {latest}` (the ASCII arrow used by the Ver cell); `update available` when a version is unreadable |
| Direct, outdated, update refused | `skipped` | `managed by {owner label}`; `no update source` when the refusal is not an owner |
| Current, installer-owned | `skipped` | `already current` + the suffix ` (r: reinstall)` while reviewing (see below) |
| Current, `r` pressed | `will be reinstalled` | `reinstall requested; r again to undo` |
| Current, owned by another manager | `skipped` | `managed by {owner label}` |
| Current or outdated, off-policy (R8, case F) | `skipped` | `managed by {real}; the catalog installs it via {declared}`; only `managed by {real}` when the declared manager is unknown |
| Current, owner unknown | `skipped` | `already current; owner unknown` |
| Dragged, present and OK | `skipped` | `already present` |
| Dragged, present but outdated or misconfigured (D-03) | `skipped` | `already present; {first clause of the health reason}` |
| Unavailable (dragged, or direct in headless `--all`) | `blocked` | the `UnavailableReason.detail`, e.g. `needs Homebrew, which is not on PATH` |
| Dependent of a blocked dependency (D-04) | `blocked` | `needs {dependency}` |
| Dragged dependency whose every requester is blocked (gap plan 20-22, WR-04) | `skipped` | `not needed while {requester} is blocked` |
| State not yet published | `checking…` | none |

- The suffix ` (r: reinstall)` is appended by `render_plan` from `PlanRow.can_reinstall`, in the idle and waiting states only. It is not part of the stored reason and does not appear once the run has started or finished (the key is inert then). `r` eligibility is `Health.OK` and installer-owned, **receipt optional** (L-20-06).
- Rows that "need sudo" are the only reason text that names a refusal; the exact command to run is Phase 22's MANUAL work and is not promised here.

## Outcome copy (rows after the run)

The word and color follow the Words tables. The text after the word:

| `result` | Row text |
|----------|----------|
| `done` | `{done word}` alone, e.g. `installed` (no reason) |
| `failed` | `failed — {first line of the last error, sanitized}`; `failed — no method succeeded` when none |
| `mismatch` | `checksum mismatch` |
| `dependency_failed` | `dependency failed — {blocked_by ids, comma-joined}`; `dependency failed — an earlier failure` when empty |
| `not_attempted` | `not attempted` |
| `crashed` | `crashed — {exception type}: {message first line, sanitized}`; an exception with no message reads `crashed — {exception type} failed` (gap plan 20-31) |
| `manual` | `manual — see the setup steps in the log` ; a reinstall/repair of a present tool whose installer refuses to run over an existing install (gap plan 20-26, L-20-11) also ends `manual`, and the log carries `{id}: its installer refuses to run over an existing install, so it was not re-run.` before its post-install handoff |
| `skipped` | `skipped — {plan reason}` (without the `(r: reinstall)` suffix); an engine race (`ALREADY_INSTALLED`) reads `skipped — became present before it ran` |
| `blocked` | `blocked — {plan reason}`; engine `NO_METHOD` reads `blocked — no install method for this platform`; an update refused at run time reads `blocked — {outcome detail}` |

The end-of-run reports run after the summary rows, from the one `render_run_report` both routes call, in this order: `render_failure_details`, `render_handoff`, `render_post_install_handoff`, `render_postinstall_warnings`, `render_done_notes`, `render_verification`; the PATH wiring and audit blocks follow. `render_summary` was replaced by `render_run_summary`, whose first line is the finished-head text (`Summary — …`) so a plain-text capture, the headless output and the e2e parser all see one stable line (see the e2e note in Auto-decided A11). (Amended for gap plan 20-31: `render_skipped` was deleted by 20-27, `render_done_notes` is 20-25's update-notes renderer widened to reconfigurations.)

**Done notes** (gap plans 20-25, 20-31). A `done` row's own text stays `{done word}` alone. What a successful update or reconfiguration reported prints once, on its own line after the rows: `{id} {done word} — {notes joined by "; "}`. An update's notes are its replayed globals (`replayed {ids}`), cleanup warnings, postinstall warning and detail, in that order; a reconfiguration's note is its step warning (today only the terminal synchronizer's), e.g. `kitty reconfigured — Terminal shell synchronization warning: …`. A done row with no notes prints no line; a failed, blocked or skipped row prints none here (its row already carries the reason). Lines are sanitized and printed literally. The post-run terminal synchronizer (D-01, D-11) still reports its own warning separately after a run that ran something (headless after the PATH blocks, TUI on the catalog status line), exactly as it already does after an update.

## Interaction contract

### States of the screen

| State | Entered when | Head | Plan region | Keys line (one line, ≤ 78 cells) | Status line |
|-------|--------------|------|-------------|----------------------------------|-------------|
| **Idle review** | mount, with every planned row published | `Install plan — {counts by review word}` | rows, cursor on row 1 | `enter start · r reinstall · up/down move · esc cancel` (omit `· r reinstall` when no row has `can_reinstall`; with no runnable row the first word reads `enter continue`) | empty |
| **Waiting** | Enter pressed while any row is `checking…` | unchanged | rows stay `checking…`, cursor active | `waiting for the state check · esc cancels the wait` | `warn`: `Waiting for the state check; nothing starts until it finishes. esc cancels.` |
| **Running** | the plan has no `checking…` row and a start was requested | unchanged | pending rows keep their health mark, the in-flight row shows `>`, finished rows show their outcome; cursor follows the in-flight row | `c stop after this tool · ctrl+c aborts and can leave a tool half-installed` | `ok`: `Press c to stop after the current tool; nothing further will start.` (existing); prompt/cancel copy unchanged |
| **Finished** | `execute_plan` returned | `Summary — {counts by done word}` (green when exit 0, red when exit 1) | final outcomes, cursor free to scroll | `enter / esc return to catalog` (existing) | see below |
| **Empty** | mounted with no selected id | `Nothing selected.` | empty | `esc close` | empty |

- **Finished status line** (one template, severity `ok`, or `error` when the exit code is 1 or a run-level error exists, L-20-08):
  `{Done.|Failed.|Nothing ran.} {Still selected: N. }enter or esc returns to the catalog.`
  `Failed.` when the exit code is 1 (or a PATH-wiring or verify error exists), else `Nothing ran.` when no row ran, else `Done.`. `Still selected: N.` is omitted when N = 0, where N = the size of `_staged ∩ retained` (L-20-07). Worst case `Nothing ran. Still selected: 12. enter or esc returns to the catalog.` is 69 cells.
- **Idle review** with only skipped and blocked rows is a valid state: the screen still opens, Enter finishes immediately with `Summary — 3 skipped`, no engine call, no PATH wiring and no terminal sync (L-20-08, D-11), and the skipped rows leave the selection (D-10).
- **Mid-run prompts** (`ChecksumMismatchScreen`, `SensitiveActionScreen`), the silence indicator (`-- still running; waiting for output --`), `-- updating --`, the cancel copy and `esc` during a run (`Installation is still running. Press c to stop after the current tool. ctrl+c aborts the whole app and can leave the current tool half-installed.`) are **unchanged**.

### Keys

| Key | Idle review | Waiting | Running | Finished |
|-----|-------------|---------|---------|----------|
| `enter` | start. With any `checking…` row: enter the Waiting state (starts nothing) | no-op (the wait is already registered) | no-op | close (dismiss with the outcomes) |
| `esc` | close; **dismiss with `None`, the selection is untouched** (PLAN-05) | **cancel the wait and stay on the review** with the selection intact; bump the wait token. A second `esc` closes | refused with the existing warning | close |
| `r` | toggle reinstall on the highlighted row, if eligible (below) | inert | inert | inert |
| `up` `down` `pageup` `pagedown` `home` `end` | move the row cursor | move | inert while the run is in flight (the cursor follows the in-flight row); the list is not focusable | scroll and move |
| `c` | `No install is running.` (existing, warn) | same | cancel after the current tool | same |

- `r` is dispatched by the modal screen only. It does not collide with the catalog's `accept_recommends` (D-14).
- **`r` on an eligible row** (`can_reinstall` or already in the reinstall set): flip membership of the tool id in the screen's `reinstall` set, call `build_plan` again with it, repaint, and **keep the cursor on the same tool id**. No status message; the row text is the feedback (`skipped — already current (r: reinstall)` ⇄ `will be reinstalled — reinstall requested; r again to undo`). The head counts update in the same repaint.
- **`r` on any other row** (a will-run row, a foreign-owned row, a dragged row, a blocked row): nothing changes and the row's reason stays; the status line shows `warn`: `{id}: r needs a current tool this installer owns.` (69 cells at the 24-character id).
- **Dragged rows are never reinstall-eligible** (a dragged row is "already present", not a current tool the user picked). `a` and `--yes` never add to the reinstall set.
- The unattended auto-start (`inputs.unattended`) calls the same `action_start` as Enter, so it waits like Enter does (research Pitfall 17).

### Waiting for state (R7, O9, L-20-03)

- The review paints immediately from whatever `state_of` has. A row with no published state renders `… {id}  checking…`; nothing is ever rendered `✓` while pending.
- Enter with any `checking…` row registers a start request and joins the service's single refresh (`_await_state`, one helper that Phase 21 replaces). The screen shows the Waiting row of the table above. **There is no timeout and no spinner**: the `…` mark and the status line are static text (consistent with Phase 19's "no motion").
- On publication, the plan is rebuilt from published state with the screen's current reinstall set, the rows **repaint first** (so the user sees the real dispositions for one frame), and then, if a start was requested and no `checking…` row remains, the run starts.
- A publication whose captured wait token is stale (the user pressed `esc`) repaints nothing and starts nothing. After a cancelled wait the status line reads `warn`: `Wait cancelled; nothing started. enter waits again · esc closes.`
- If the refresh raises, the rows stay `checking…`, nothing starts, and the status line reads `error`: `State check failed: {error}. enter retries · esc closes.` (`{error}` truncated with `…` so the line is ≤ 78 cells).
- Hazard (locked by D-13, recorded in Auto-decided): a start requested while rows say `checking…` runs whatever the rebuilt plan says, including a `will repair` or `will update` the user never saw. The contract's mitigation is the one-frame repaint and the visible `r`/`esc` hints; it adds no second confirmation.

### Selection after the run (PLAN-05, D-10, L-20-07)

- `esc` before the run: the dismiss value is `None`; the app does not touch `_staged`.
- After a run: `_staged` is reduced in place (`intersection_update`) to the ids whose row ended failed, mismatch, dependency_failed, not_attempted, crashed, blocked or manual. Done and skipped ids leave it. A dragged-in dependency is never added.
- The catalog marks the retained rows `[x]` when the user returns to it. The finished status line tells the user how many (`Still selected: N.`).

## Headless output (R6, D-12)

Headless prints through the same `render_plan` and `render_run_summary` onto a Rich `Console`. No ANSI is written when output is not a TTY or `NO_COLOR` is set (Rich's default behavior), so the plan is plain text in CI logs.

```
Install plan — 1 will install, 1 will update, 3 skipped, 1 blocked
○ mermaid-cli    will install — not installed
○   node         will install — needed by mermaid-cli
↑ jq             will update — 1.7.1 -> 1.8.0
✓ ripgrep        skipped — already current
– podman         blocked — needs Homebrew, which is not on PATH
Run this plan?
```

- Mark column and word column are exactly as in the TUI; the `(r: reinstall)` suffix is **not** printed headless (there is no `r`).
- Order is `build_plan` execution order grouped by requester, identical to the TUI for the same selection and state.
- Without `--yes`: print the plan, then ask `Run this plan?` through the existing prompter (default No). On No, print `Cancelled; nothing was changed.` and keep today's declined-run behavior. With `--yes`: print the plan and run without asking.
- After consent (or with `--yes`) the held bookkeeping writes commit before the first row runs (L-20-10). An adoption the commit cannot record prints one line there, before the run, and changes no row and no exit code: `{id} was not adopted: its file or receipt changed after the plan was printed`, or `{id} was not adopted: {error}` when the receipt write fails (gap plan 20-30).
- When no row is runnable, do not ask: print the plan, then `Summary — 3 skipped` (or the counts), and exit 0 (R6 all-current host).
- After the run: `Summary — {counts by done word}` as its first line, then the existing report renderers. The exit code is `exit_code(outcomes)`; skipped and blocked rows never change it. A plan that still contains a `checking…` row after the synchronous pass is a failure to report (`State check failed: …`), not a plan to run.
- Width: fold at `min(console.width, 100)`, 80 when undetected. The 78-cell test reuses the existing `Console(width=80)` capture and the `len(plain) <= 78` assertion style (D-16).

## Keyboard and accessibility

- **Glyph and word first.** Every state is carried by a word that is always on the row, and every mark glyph is distinct, so meaning never depends on color. Under `NO_COLOR`, Textual applies its `Monochrome` filter (as in Phase 19); this contract holds unchanged. The only color-only cue left is the highlighted row, which Textual draws with reverse/intensity from the theme and which survives Monochrome (human UAT check below).
- **No motion.** No spinner, no animated `…`, no blink. The in-flight cue is the static `>` mark plus the existing live log and silence indicator.
- **Focus.** `#plan-rows` is focused on mount in the idle, waiting and finished states. During a run it is not focusable, so no key can move the cursor away from the in-flight row. `enter` and `esc` remain screen-level bindings (`priority=True` on `enter`, as today).
- **Width.** Every mark is one cell by `rich.cells.cell_len`. `… ≈ ↑ ○ – ✖ ✓` are East-Asian-ambiguous; `○ ✖` already ship. As in Phase 19, terminals that draw ambiguous-width characters as two cells (CJK locales) are not supported; there the 78-cell lines can wrap and the mark column can misalign. Not reshuffled.
- **Escaping.** See Row anatomy: reasons, steps, details and errors are `Text` pieces, sanitized, never markup.
- **Resize.** On `Resize`, rebuild the options at the new fold width and keep the cursor on the same tool id.
