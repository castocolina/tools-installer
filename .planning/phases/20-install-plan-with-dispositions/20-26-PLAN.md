L-20-11 (orchestrator, 2026-10-18): reinstall_only. No new health fact, no `≈`, no persistent RECONFIGURE, no `login shell is not zsh` copy, no `--yes` exception, no architecture exception. The handoff must show on a fresh install and on `r` (REINSTALL), on each route where that action exists (headless has no `r`).

Why an engine branch and not a plan change (Claude's discretion, smallest correct change): the REINSTALL row and its copy are right; what breaks is that the method cannot run over an existing install, so the post-install dispatch after a successful method is never reached. Removing `~/.oh-my-zsh` first would make the script run but destroys the user's `custom/` plugins and themes, so it is never done. Skipping the method only when the method itself declares it refuses existing installs keeps every other reinstall unchanged (`uv`, `rustup` and similar scripts reinstall in place and must keep doing so).

Decisions recorded for this plan:
- `installer/registry.toml`, oh-my-zsh's `script` method: add `refuses_existing = true`, with a comment quoting the upstream check and its verification date.
- `installer/model.py`: add `refuses_existing` to the `script` keys in `METHOD_PARAMS` (Task 1); the loader rejects a non-bool value with `tool '{id}': method 'script' key 'refuses_existing' must be true or false` (Task 2).
- `installer/engine.py` `install_tool`: in the ladder, before `_perform`, when `repair` is set, the tool is present (the already-computed `installed`), and `method.params.get("refuses_existing") is True`, return at once `InstallOutcome(tool.id, InstallStatus.MANUAL_REQUIRED, method_kind=method.kind, handoff=(f"{tool.id}: its installer refuses to run over an existing install, so it was not re-run.",), post_install_handoff=<lines>, postinstall_warning=<crash or None>)`, where lines and crash come from the existing `_dispatch_post_install(tool, platform, confirm_sensitive_action)`. No receipt write, no smoke, no `postinstall` hook (nothing was installed). The `install_tool` docstring's repair paragraph gains one sentence for this case.
- Row result: `_INSTALL_RESULT` already maps MANUAL_REQUIRED to `manual` (`manual — see the setup steps in the log`); `render_handoff` prints the not-re-run line and `render_post_install_handoff` prints the chsh block exactly as on a fresh install. `retained` keeps the row selected; `ran_anything` does not count it once plan 20-24 Task 2 has dropped `manual` from the ran set, which is why this plan depends on 20-24 (its Task 1 asserts `ran_anything` is False). No change in `installer/session.py`, `installer/render.py` or `installer/execute_screen.py`.
- `installer/post_install.py`: the module docstring paragraph that says a successful reinstall dispatches actions once more adds: a tool whose installer refuses to run over an existing install is not re-run, and the reinstall dispatches its actions directly.
- Existing fresh-install pins (keep green, name them in the SUMMARY): `tests/test_app.py::test_run_wizard_prints_login_shell_instructions_when_sensitive_confirmed` (headless, real engine) and `tests/test_session.py::test_with_sensitive_confirm_reaches_post_install_gate` (execute_plan, real engine; plan 20-28 renames it `test_execute_plan_confirmation_reaches_the_post_install_gate`).
