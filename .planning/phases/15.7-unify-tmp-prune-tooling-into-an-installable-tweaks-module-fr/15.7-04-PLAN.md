<objective>
Build D-04's reusable cache-redirect mechanism and its Policy factory, grounded in and validated
against Bun's `BUN_RUNTIME_TRANSPILER_CACHE_PATH` as the one real, already-confirmed case.

Purpose: D-04 — prevent orphaned runtime-cache files from landing in the OS temp dir in the
first place, rather than only cleaning up after. The mechanism is generalized (a declaration
any future tool can add an entry to) but is built and proved against exactly one real target,
not a speculative multi-tool abstraction.

Output: `installer/env_redirect.py` plus a `cache_redirect_policy` factory in
`installer/policy.py`. Composition into `setup.py`, the Policies view and the teardown sweep is
plan 15.7-05.

15.7-RESEARCH.md Pitfall 2 — `environment.d` files are read by the systemd user manager's
environment generator, which only runs when that manager (re)starts, i.e. at login. A
freshly written file is NOT live in the current session, and
`systemctl --user show-environment` does not show it either. The "applied" signal must therefore
be the file's own presence and content, mirroring how `installer/daemon.py` treats plist
presence as authority rather than a parsed runtime probe.
The live reference file on this host is `~/.config/environment.d/51-bun-cache-redirect.conf`,
one comment block plus one KEY=VALUE line pointing Bun at a disk-backed cache dir.
  </read_first>
  <behavior>
Write tests FIRST in tests/test_env_redirect.py; every one must fail before the module exists.

Declaration and registry:
- `REDIRECTS` contains exactly one entry today, whose environment variable is
  `BUN_RUNTIME_TRANSPILER_CACHE_PATH` and whose target resolves, under an injected home, to a
  cache directory beneath that home and NOT beneath any temp directory.
- Every entry's id is unique and every entry's conf basename sorts after the plain
  `51-bun-cache-redirect.conf` name an earlier hand-installed tool may already have left, so
  `environment.d`'s documented lexicographic last-file-wins rule makes this project's file
  authoritative without deleting anyone else's.

Linux writer:
- `render_conf` returns text whose final non-empty line is exactly the variable name, an equals
  sign, and the absolute target, preceded by a comment block explaining why the redirect exists
  and that it takes effect at the next login.
- `write_linux_redirect` creates the conf directory and the TARGET cache directory, writes the
  conf atomically at mode 0o644, and returns the written path.
- Writing twice produces a byte-identical file (idempotent) and does not raise.
- `remove_linux_redirect` deletes the conf file and returns True; it returns False and deletes
  nothing when the file is absent, and it refuses to delete a same-named file that does not
  carry this project's own ownership sentinel comment.
- `remove_linux_redirect` never touches the target cache directory, even when that directory
  exists and is non-empty.

macOS writer:
- `write_rc_redirect` writes a marker-delimited block into the given rc file through
  `apply_block`, committing with a mode-PRESERVING atomic write because the target is the
  user's own `~/.myshellrc`; applying twice leaves the file unchanged and never duplicates the
  block; surrounding user content is preserved verbatim.
- `remove_rc_redirect` strips only that block and leaves the rest of the file byte-identical.

Applied predicate:
- `linux_applied` is True only when the conf file exists AND assigns the expected variable;
  a conf file present but assigning a different variable reads False.
- `rc_applied` is True only when a CLOSED begin..end block is present; an orphan begin marker
  reads False.
- Neither predicate reads `os.environ` — asserted by setting the variable in the process
  environment and confirming the predicate still reports False with no file on disk.

Competing declarations:
- `competing_conf_paths` lists other `.conf` files in the same directory that assign the same
  variable, excluding this project's own file, and returns an empty tuple when there are none.

Validation:
- Rendering rejects, with a clear exception, a target that is not absolute, and any target or
  variable name containing a newline, carriage return, double quote, backslash, backtick or
  dollar sign — systemd's environment.d parser performs variable expansion and the rc form is
  shell source, so both are injection surfaces.
  </behavior>
  <action>
Create `installer/env_redirect.py`: the generalized cache-redirect mechanism (D-04), a small
dedicated module with one entry per known tool. CONTEXT.md leaves the API shape to discretion;
this is the lower-blast-radius option, because the alternative — a new field on `Tool` — would
touch every row of `installer/registry.toml` and its schema tests for a feature with exactly one
real case today.

Declare a frozen `CacheRedirect` dataclass carrying: a stable id, a human label, the environment
variable name, the home-relative target path parts, a short prose reason, and the
environment.d conf basename. Declare the Bun entry as a module constant with its target under
the user's own cache directory (mirroring the live reference file on this host) and collect the
entries in a `REDIRECTS` tuple. Give the conf basename a `tools-installer` component so it is
self-identifying and so it sorts after a plain hand-installed file with the same numeric
prefix — record that lexicographic-precedence reasoning in a comment, because it is the whole
reason this project can take authority without deleting another tool's file.

Declare an ownership sentinel comment string that every file and block this module writes
carries, and a marker begin/end pair for the rc-file form distinct from every other pair in
`installer/shellrc.py`.

Implement `environment_d_dir(home, environ)` returning the XDG_CONFIG_HOME value when set, else
home/.config, then `environment.d` — the same per-subsystem XDG read `systemd_daemon.user_unit_dir`
performs for its own directory.

Implement `target_path(redirect, home)`, a private validator that raises on the rejected
character set and on a non-absolute target, `render_conf`, `write_linux_redirect`,
`remove_linux_redirect`, `linux_applied`, `render_block`, `write_rc_redirect`,
`remove_rc_redirect`, `rc_applied` and `competing_conf_paths`, matching the behaviors above.
Compose `installer/shellrc.py`'s `apply_block`/`strip_block` for the rc form and
`installer/atomic.py`'s `atomic_write_bytes` for every write — explicit mode 0o644 for the conf
file this project owns outright, mode-preserving for `~/.myshellrc`, matching
`installer/daemon.py`'s documented split.

Make `write_linux_redirect` create the target cache directory with parents, so the redirect
points somewhere that exists the moment it becomes live. Make both remove functions leave that
directory alone unconditionally: deleting a user's cache is destructive, is not what disabling a
redirect means, and is not asked for anywhere in this phase's sources.
  </action>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| this process -> systemd environment generator | text written here is parsed at the user's next login and becomes that session's environment |
| this process -> shell rc file | text written here is sourced by every new shell on macOS |
| other tools' config files -> this process | a pre-existing environment.d file from another installer shares the same directory and variable name |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-15.7-15 | Tampering | `render_conf` / `render_block` | high | mitigate | Both reject a non-absolute target and any newline, carriage return, double quote, backslash, backtick or dollar sign before writing; environment.d performs variable expansion and the rc form is shell source, so both are injection surfaces |
| T-15.7-16 | Tampering | both writers | medium | mitigate | Every write goes through `atomic_write_bytes` — explicit 0o644 for the owned conf file, mode-preserving for `~/.myshellrc` — so a crash mid-write cannot leave a truncated file for the next login's environment generator or the next shell to read |
| T-15.7-17 | Tampering | `remove_linux_redirect` | medium | mitigate | Refuses to delete a same-named file lacking this project's ownership sentinel, mirroring `daemon._is_our_wrapper` |
| T-15.7-18 | Denial of Service | `remove_*_redirect` | high | mitigate | Neither remover touches the target cache directory, so disabling a redirect can never delete a user's cache |
| T-15.7-19 | Spoofing | competing conf file | medium | mitigate | Another tool's file is reported, never silently deleted, and precedence is made deterministic by filename ordering rather than by removal |
| T-15.7-20 | Repudiation | overstated "applied" status | medium | mitigate | The applied predicate reads the owned file, never the live process environment, and the reload hint states the next-login requirement explicitly |
| T-15.7-SC | Tampering | npm/pip/cargo installs | high | mitigate | Not applicable to this plan: no package-manager install task and no new external dependency |
</threat_model>
