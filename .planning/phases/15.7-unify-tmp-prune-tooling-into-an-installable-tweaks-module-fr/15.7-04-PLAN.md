Declaration and registry:
- `REDIRECTS` contains exactly one entry today, whose environment variable is
  `BUN_RUNTIME_TRANSPILER_CACHE_PATH` and whose target resolves, under an injected home, to a

- Every entry's id is unique and every entry's conf basename sorts after the plain

Linux writer:
- `render_conf` returns text whose final non-empty line is exactly the variable name, an equals
  sign, and the absolute target, preceded by a comment block explaining why the redirect exists
  and that it takes effect at the next login.
- `write_linux_redirect` creates the conf directory and the TARGET cache directory, writes the
  conf atomically at mode 0o644, and returns the written path.
- Writing twice produces a byte-identical file (idempotent) and does not raise.
- `remove_linux_redirect` deletes the conf file and returns True; it returns False and deletes
  nothing when the file is absent, and it refuses to delete a same-named file that does not
  carry this project's own ownership sentinel comment.
- `remove_linux_redirect` never touches the target cache directory, even when that directory
  exists and is non-empty.

macOS writer:
- `render_block` emits an `export` assignment — the rendered line begins with the export keyword,
  then the variable name, then an `=`, then the double-quoted absolute target. Asserted on the
  exact line, because a bare `KEY=VALUE` in `~/.myshellrc` is a shell-local variable that Bun's
  child process never sees, which would make the whole redirect a silent no-op (review HIGH
  15.7-04). `installer/shellrc.py:108-110` writes `export PATH="…"` for the same reason.
- The rendered rc line and the rendered conf line are asserted to DIFFER in exactly this way in
  one test: the conf form carries no export keyword (systemd's environment.d grammar has none),
  the rc form requires it. The test's name says the asymmetry is intentional, so a later
  "consistency" cleanup has to delete a test that explains why it must not.
- `write_rc_redirect` writes a marker-delimited block into the given rc file through
  `apply_block`, committing with a mode-PRESERVING atomic write because the target is the
  user's own `~/.myshellrc`; applying twice leaves the file unchanged and never duplicates the
  block; surrounding user content is preserved verbatim.
- `remove_rc_redirect` strips only that block and leaves the rest of the file byte-identical.

Applied predicate (ownership-coupled):
- `linux_applied` is True only when the conf file exists AND carries this module's ownership
  sentinel comment AND assigns the expected variable. A conf file present but assigning a
  different variable reads False; a same-named conf file WITHOUT the sentinel — the exact file
  `remove_linux_redirect` refuses to delete — also reads False. This is the review's HIGH finding:
  presence-plus-variable would let a policy report itself active while its own remover declines to
  act, which `installer/daemon.py:336-344` already documents as the state to design out.
- The pairing is asserted as an invariant, not as two independent facts: for a same-named
  non-owned file, `linux_applied` is False AND `remove_linux_redirect` returns False, in one
  test, so the two can never drift apart.
- A non-owned file that assigns the same variable is surfaced through `competing_conf_paths`
  instead, so "not ours" never means "invisible".
- `rc_applied` is True only when a CLOSED begin..end block is present; an orphan begin marker
  reads False.
- Neither predicate reads `os.environ` — asserted by setting the variable in the process
  environment and confirming the predicate still reports False with no file on disk.

Competing declarations:
- `competing_conf_paths` lists other `.conf` files in the same directory that assign the same
  variable, excluding this project's own file, and returns an empty tuple when there are none.
- Precedence is proved, not assumed (review MEDIUM 15.7-04). A pure test asserts this project's
  conf basename sorts after a plain hand-installed `51-bun-cache-redirect.conf` under the same
  ordering `environment.d` documents. A second, integration test resolves the real
  `systemd-environment-d-generator` and, when present, runs it against a fixture directory holding
  both files and asserts the generated environment carries THIS project's target; the test skips
  cleanly when the generator is not resolvable, so a macOS or container run is unaffected. A
  filename-ordering argument that has never met the real parser is a belief, not a behavior.

Validation:
- The variable name must match a strict shell/systemd identifier pattern — a leading letter or
  underscore followed by letters, digits or underscores — and anything else is rejected before any
  write. Pinned with the cases a character blocklist would have let through: a name containing a
  space, an `=`, a `#`, a leading digit, an empty string, and a trailing newline (review MEDIUM
  15.7-04: rejecting only quotes/backslashes/backticks/`$` leaves valid-looking but unassignable
  names).
- Rendering rejects, with a clear exception, a target that is not absolute, and any target
  containing a newline, carriage return, double quote, backslash, backtick or dollar sign —
  systemd's environment.d parser performs variable expansion and the rc form is shell source, so

- `environment_d_dir` ignores a RELATIVE XDG_CONFIG_HOME and falls back to home/.config, matching
  `systemd_daemon.user_unit_dir`'s own rule from plan 15.7-01 and the XDG spec's "if not absolute,
  must be ignored" (review LOW 15.7-04).

Implement `environment_d_dir(home, environ)` returning the XDG_CONFIG_HOME value when set AND

XDG_CONFIG_HOME is ignored rather than honoured (review LOW 15.7-04).

Implement `target_path(redirect, home)`, a private validator that raises on the rejected
character set and on a non-absolute target, `render_conf`, `write_linux_redirect`,
`remove_linux_redirect`, `linux_applied`, `render_block`, `write_rc_redirect`,
`remove_rc_redirect`, `rc_applied` and `competing_conf_paths`, matching the behaviors above.
Compose `installer/shellrc.py`'s `apply_block`/`strip_block` for the rc form and
`installer/atomic.py`'s `atomic_write_bytes` for every write — explicit mode 0o644 for the conf
file this project owns outright, mode-preserving for `~/.myshellrc`, matching
`installer/daemon.py`'s documented split.

`render_block` MUST emit `export <NAME>="<target>"`, not a bare assignment. This is load-bearing,
not stylistic: `~/.myshellrc` is sourced by the user's interactive shell, and a variable that is
assigned without being exported is not in the environment Bun's child process inherits — the
redirect would write a correct-looking line and change nothing, with `rc_applied` cheerfully
reporting True (review HIGH 15.7-04). `installer/shellrc.py:108-110` already writes
`export PATH="…"` for exactly this reason; follow it. `render_conf` stays a bare `KEY=VALUE`,
because systemd's `environment.d` grammar is assignments only and has no export keyword. Put a
comment on BOTH renderers stating that the asymmetry is required by two different grammars and
must not be unified.

Implement a private `_valid_name` using a strict identifier regex (leading letter or underscore,
then letters, digits or underscores) and apply it to every redirect's variable name before any
render or write. A character blocklist is the wrong tool here: it answers "does this contain
something dangerous" when the question is "is this a legal variable name at all", and a name with
a space, an `=`, a `#` or a leading digit passes a blocklist and produces a file that systemd or
the shell silently ignores (review MEDIUM 15.7-04). Keep the value-side character rejections as
well — the name gets an allowlist, the target gets the injection-character blocklist, and they are
different checks for different reasons.

Couple `linux_applied` to ownership: it is True only when the conf file exists, carries this
module's ownership sentinel, and assigns the expected variable. Do not settle for
presence-plus-variable. `installer/daemon.py:336-344`'s `wrapper_present` docstring states the
rule this follows — a predicate must never "promise to remove a same-named file the remover would
correctly refuse to delete" — and the failure it prevents is precise: an active-reading policy
whose remove is a no-op, so the Policies row shows ON, the user toggles it OFF, and the row snaps
back to ON with no error anyone can see. Implement `linux_applied` and `remove_linux_redirect`
against ONE shared private ownership predicate so the two cannot drift.

Make `write_linux_redirect` create the target cache directory with parents, so the redirect
points somewhere that exists the moment it becomes live. Make both remove functions leave that
directory alone unconditionally: deleting a user's cache is destructive, is not what disabling a
redirect means, and is not asked for anywhere in this phase's sources.
