## Critical Issues

### CR-01: Uninstall sweep skips an installed-but-inactive Linux timer, then clears the marker and reports success

**File:** `installer/policy.py:1109-1110,1119,1123`, `installer/uninstall.py:388-395,436-437`, `installer/app.py:461,517`, `installer/app.py:596-603`
**Issue:** `linux_daemon_policy` binds `active`/`is_active` to `cache.read() is DaemonState.ACTIVE`,
which is runtime state. `active_policies` uses that same predicate to decide what a full
uninstall sweeps. The architecture standard says every arm of the sweep answers "is this ours",
meaning footprint (an owned block or artifact is present), not "is it running". The macOS policy
does exactly that (`is_active=lambda: plist_path.exists()`). Here, any state other than ACTIVE
means the policy is never swept:
- the timer is INACTIVE (for example `systemctl --user stop` without `disable`, so it is still
  enabled and restarts at the next login), or
- the query is UNAVAILABLE (`make uninstall` run over ssh or `sudo -u` without a user bus, or the
  5 s query timeout fired).

After the skipped sweep, `run_uninstall` still clears the Linux marker. Both marker-clear sites
guard only on `id not in swept.failed`. `perform_uninstall`'s else branch clears it precisely
*because* `is_active()` is False.

Reproduced with fakes: after an apply, a policy whose `read_output` returns `inactive` gives
`units_present=True`, `active=False` and `active_policies(...) == []`.

Failure scenario:
1. The user runs `make uninstall` from a TTY-less session.
2. `tools-installer-prune-tmp.{service,timer}`, the `timers.target.wants` symlink and
   `~/.local/bin/<wrapper>` all survive.
3. The CLI prints success, and the "decided" marker is gone.
4. At the next graphical login the timer starts again and keeps deleting files from `/tmp`
   after an uninstall.
5. If the checkout has been deleted, the timer instead fails every 10 minutes.

No test covers present-but-inactive uninstall.
**Fix:** Separate "owned footprint" from "running". Keep the cache-backed answer for the row
display, but give the sweep a presence-based predicate. Also make `bootout`'s tolerant path cover
"not running":
```python
def _is_active() -> bool:          # sweep / uninstall / ownership
    return systemd_daemon.units_present(unit_dir) or systemd_daemon.wrapper_present(wrapper_bin_dir)

def _is_running() -> bool:         # Policies row display only
    return cache.read() is DaemonState.ACTIVE
```
Then add a regression test: apply, set `read_output` to `inactive`/raising, run `run_uninstall`,
and assert that no unit files or wrapper remain and that the marker is cleared only after they
are removed.

### CR-02: The on-by-default apply silently disables another tool's user-scope timer (D-02/D-05a disclosure is not met)

**File:** `installer/policy.py:968-990`, `installer/policy.py:1200-1201`, `setup.py:959-979`
**Issue:** `_detect_and_take_over_competitors` reports a *successful* user-scope takeover only as
a `PolicyLayer("Competing mechanism", "disabled: …")`. `warning_parts` holds only
`system_scope_warning(...)` and `user_scope_failure_warning(failed)`. `ensure_daemon_default`
forwards only `result.warning` to `on_warning`, and the layers are thrown away.
`on_daemon_default_applied` → `refresh_daemon_state` shows nothing either. So the one apply path
with no human present (15.7-05 must_have: "a first-run takeover of another tool's user-scope
timer … would happen with nothing said to anyone") still says nothing when the takeover
*succeeds*. That success is the case D-02 exists for.

Reproduced with fakes: user-scope listing `cleanup-bun-tmp-cache.timer enabled`, then
`ensure_daemon_default(p, on_warning=warn.append)` returns `True` with `warn == []`, while
`['systemctl','--user','disable','--now','cleanup-bun-tmp-cache.timer']` was issued.

Failure scenario: on a fresh interactive run, another tool's user timer is stopped and disabled
in the background. The user never sees a line about it, so they cannot tell why that tool's
cleanup stopped.
**Fix:** Treat a successful takeover as a disclosure. Either add a sentence to the warning:
```python
if disabled:
    warning_parts.insert(0, f"Stopped and disabled {', '.join(disabled)} (another cleanup job); "
                            f"re-enable with `systemctl --user enable --now {disabled[0]}`.")
```
or have `ensure_daemon_default` forward the competing layer detail too. Add a test to
`tests/test_setup.py` / `test_policy_linux_daemon.py` asserting that `on_warning` receives the
disabled unit name on a successful takeover.

## Warnings

### WR-01: First-ever apply rollback leaves a dangling enablement symlink; the remove rollback re-enables a half-deleted unit pair

**File:** `installer/policy.py:1021-1041`, `installer/policy.py:1075-1080`, `installer/systemd_daemon.py:356-358`
**Issue:**
- **Apply rollback.** `bootstrap` runs `daemon-reload`, then `enable`, then `restart`. If
  `restart` fails on a first-ever apply, the rollback deletes the unit files and reloads, but
  never runs `systemctl --user disable`. The
  `~/.config/systemd/user/timers.target.wants/tools-installer-prune-tmp.timer` symlink that
  `enable` created is left pointing at a deleted file. Every later `bootout` then takes the
  "units absent → probe → INACTIVE → return" path, so nothing ever removes the symlink, and the
  user manager logs a missing-unit error at each login. The only first-apply bootstrap-failure
  test (`test_first_ever_apply_enable_failure_leaves_no_artifacts_and_reraises`) fails at
  `enable`, so it never exercises this.
- **Remove rollback.** `remove_units` unlinks the service first. If unlinking the timer then
  fails, the rollback calls `bootstrap`, which re-enables and restarts a timer whose service unit
  no longer exists.

**Fix:** In the first-apply branch, run a best-effort `disable` before deleting the files:
```python
with contextlib.suppress(CommandError):
    run(["systemctl", "--user", "disable", systemd_daemon.TIMER_NAME])
with contextlib.suppress(OSError):
    systemd_daemon.remove_units(unit_dir)
```
In `_remove`, snapshot the unit bytes before `remove_units`, and restore them before
re-bootstrapping. Add a test with `fail_on={("restart", 1)}` on a first apply that asserts a
`disable` call was issued.

### WR-02: Blocking systemctl queries still run on the Textual event loop

**File:** `installer/wizard_app.py:362-392` (`_refresh_guidance` → `self.disk_pressure()` with default `blocking=True`, also re-run from the globals-audit handler at `:615`), `installer/wizard_app.py:1704-1721` (`refresh_daemon_state` → `policy.is_active()`), `setup.py:842-849` (Uninstall `tweak_ids` → `_reads_active` → `cache.read()`), `installer/wizard_app.py:1757` (`run_live(policy.apply)`)
**Issue:** The row-highlight path is fixed (`blocking=False` → `peek()`). But several other
main-thread paths still call `TimerStateCache.read()`, which runs a `systemctl --user is-active`
query bounded at 5 s:
- **Doctor entry and pnpm-audit landing.** `test_doctor_rereads_disk_pressure_on_enter_view`
  actually pins `all(calls)`, i.e. blocking, here. The pnpm audit usually takes longer than the
  5 s TTL, so every audit landing re-probes.
- **`on_daemon_default_applied`.** The worker's `_apply` just called `invalidate()` in its
  `finally`, so this `read()` is *guaranteed* to spawn a subprocess on the event loop.
- **Uninstall view entry.**
- **A manual toggle.** `_apply` now also runs `detect_competing`: up to 2 listings plus 4
  `is-active` probes, each 5 s, followed by unbounded `run_captured` disables.

With a wedged user manager or D-Bus, each of these freezes the UI: 5 s per probe, and up to about
30 s or more for a toggle. The `_temp_usage_line` docstring itself calls such a read "a frozen
UI". This contradicts the focus-area invariant that no path may block the UI on a systemctl
query.
**Fix:** Move all cache `read()` calls off the loop:
- The Doctor uses `blocking=False` for rendering and schedules a thread worker that calls
  `read()`, then posts a message to re-render.
- `refresh_daemon_state` does the same, or runs `read()` inside `_apply_daemon_default_worker`
  before posting, and passes the resolved state in the message.
- The Linux policy's toggle runs through a worker, as the auto-default already does.

### WR-03: TimerStateCache is shared across threads with no lock, so an invalidate can be lost and a stale answer stored as fresh

**File:** `installer/systemd_daemon.py:444-464`, `setup.py:1046-1077` (the execute-screen doctor closure reads the same probe from a worker), `setup.py:959-979`
**Issue:** `read()` takes `now` before probing and stores `(_value, _at=now)` after. Suppose the
main thread (Doctor entry) starts a `read()` while the daemon-default worker's `_apply` is still
running bootstrap:
1. The main thread's probe sees INACTIVE.
2. The worker finishes and calls `invalidate()` (`_at=None`).
3. The main thread then stores INACTIVE with the *old* timestamp. The invalidate is lost.

`refresh_daemon_state`'s `read()` within the next 5 s then returns the stale INACTIVE, so the
Policies row shows OFF while the timer is active. The ExecuteScreen's `run_doctor(...,
disk_pressure=probe)` also calls `read()` from a worker thread concurrently with main-thread
reads.
**Fix:** Guard the state with a `threading.Lock`, and add a generation counter that
`invalidate()` bumps. `read()` stores its result only if the generation is unchanged since it
started:
```python
with self._lock: gen = self._gen
value = self._probe()
with self._lock:
    if gen == self._gen:
        self._value, self._at = value, now
```

### WR-04: The environment.d directory ignores XDG_CONFIG_HOME at the composition root, and env_redirect.environment_d_dir is an orphan helper

**File:** `setup.py:124`, `installer/env_redirect.py:78-86`
**Issue:** `_LINUX_DAEMON_UNIT_DIR` honours `$XDG_CONFIG_HOME` through `user_unit_dir`, but
`_ENVIRONMENT_D_DIR = Path.home() / ".config" / "environment.d"` does not. systemd's user
environment generator reads `$XDG_CONFIG_HOME/environment.d`. With an absolute
`XDG_CONFIG_HOME=/x`, the Bun redirect is written to `~/.config/environment.d`, which is never
read. The row still reads ON, because `linux_applied` checks the same wrong file. The redirect
never takes effect, even after the login the UI tells the user to perform.
`env_redirect.environment_d_dir` was written for exactly this, but only its own test calls it.
That violates architecture rule 5 (no orphan helpers).
**Fix:** `_ENVIRONMENT_D_DIR = env_redirect.environment_d_dir(Path.home(), os.environ)`.

### WR-05: The competing environment.d warning claims precedence it does not have

**File:** `installer/policy.py:497-504`, `installer/env_redirect.py:243-255`
**Issue:** The apply warning always says "`{written.name}` takes precedence because it sorts
later". That is only true for a competing file whose name sorts *before*
`51-tools-installer-bun-cache-redirect.conf`. A user file such as `60-bun.conf` or
`99-local.conf` sorts later and wins, yet the UI tells the user the opposite.
`competing_conf_paths` also scans only the user directory. systemd merges
`/etc/environment.d`, `/usr/lib/environment.d` and `/usr/local/lib/environment.d` by basename, so
a system file that sorts later is never reported. The line matcher also misses an indented
assignment.
**Fix:** Compute precedence instead of asserting it. Split `found` into `name < ours` and
`name > ours`, and for the later-sorting ones warn that the redirect "is overridden by {names},
which sorts later". Include the system environment.d directories in the scan, read-only.

### WR-06: An unreadable or undecodable same-named conf bypasses the ownership check and is overwritten

**File:** `installer/env_redirect.py:149-152`
**Issue:** `existing = _read(path) if path.exists() else None`. `_read` returns `None` on
`OSError` or `UnicodeDecodeError`, which the code then treats exactly like "file absent". A
foreign `51-tools-installer-bun-cache-redirect.conf` that is mode 000, or that contains non-UTF-8
bytes, is replaced by `atomic_write_bytes`. The rename needs only directory write permission. The
docstring promises that "a same-named file lacking the ownership sentinel is left untouched".
**Fix:** Distinguish "absent" from "unreadable":
```python
if path.exists():
    existing = _read(path)
    if existing is None or not _owned(existing):
        raise OSError(f"{path} exists and is not managed by tools-installer")
```

### WR-07: On macOS the cache redirect is a silent no-op in split link mode

**File:** `setup.py:564-575` (`ensure_sourced_from=()`), compared with `setup.py:809-813,874`
**Issue:** In split mode `~/.myshellrc` is not sourced by the rc files (`ban_rc_paths` writes
into each rc directly). Tweak policies are wired with `_tweak_ensure_sourced_from` for exactly
this reason. `_cache_redirect_policies` hard-codes `ensure_sourced_from=()`, so the exported
`BUN_RUNTIME_TRANSPILER_CACHE_PATH` block lands in a file no shell reads. The row reads ON
(`rc_applied` checks only the block), and the redirect never reaches Bun. The factory's own
docstring warns about exactly this: "A redirect sourced only into a file split mode never reads
is a silent no-op."
**Fix:** Build the redirect policies inside `_build_app`, where `_current_link_mode` is in
scope, and pass `ensure_sourced_from=_tweak_ensure_sourced_from`. `_run_uninstall` can keep
`()`, because removal does not need sourcing.

### WR-08: On Linux, the disk-pressure next step recommends a command that fails or targets the wrong files

**File:** `installer/guidance.py:282-284,354-357`, `installer/wizard_app.py:169-173`
**Issue:** Both the INACTIVE and UNAVAILABLE next steps, and the TUI rewrite, tell the user to
run `./scripts/prune-user-tmpdir.sh --apply`. That is the macOS script:
- It defaults to `$TMPDIR`, with no `/tmp` fallback. On a stock Linux host with `TMPDIR` unset
  (this host included) it exits 1 with `error: TMPDIR empty; pass --tmpdir PATH`.
- Even with `TMPDIR=/tmp`, it prunes `*.dylib`, `*.node` and the gitid/codex directories older
  than **3 days**, not the fresh Bun `.so`/`.node` orphans that are filling the tmpfs.

So the one "immediate relief" command in the emphasised red finding does not work on the
platform where the `/tmp` rule applies. `make doctor` and the Doctor screen both show it.
**Fix:** Make the next step depend on the platform. `DiskPressure` already carries
`tmp_threshold`, which is Linux-only:
```python
script = "./scripts/prune-tmp-linux.sh --apply" if pressure.tmp_threshold else "./scripts/prune-user-tmpdir.sh --apply"
```
Also update `_DISK_PRESSURE_TUI_STEP` and add a test for each platform.

### WR-09: The broad-path refusal guard is a literal string compare, so non-canonical paths bypass it (verified rm -rf inside HOME)

**File:** `scripts/lib/prune-tmp-common.sh:72-82`, `scripts/prune-user-tmpdir.sh:83-85`, `scripts/prune-tmp-linux.sh:78-82`
**Issue:** `_prune_common_refuse_broad_path` compares the raw string after stripping exactly one
trailing slash. `$HOME/.`, `$HOME//`, `/tmp/..`, `///`, `/.`, or a symlink to `$HOME` all pass.
I verified this in the scratch dir: `HOME=$S prune-user-tmpdir.sh --tmpdir "$S/." --apply`
printed `deleted: 2`. It ran `rm -rf` on a 10-day-old `$S/gitid-stage-important/` (with its
contents) and deleted `$S/addon.node`, while `--tmpdir "$S"` was correctly refused.

The pinned `--tmpdir /` quirk is not itself a hole: `""` fails `-d`, exit 1, nothing deleted.
The Linux wrapper's narrow Bun regex limits its own impact. The macOS families (`*.node`, and any
`gitid-*` or `.com.openai.codex.*` directory, deleted with `rm -rf`) do not have that limit. The
guard is the only defence against a misconfigured `TMPDIR` or `--tmpdir`, and this phase made it
the shared implementation (D-01d).
**Fix:** Canonicalise before comparing, for both the root and every refusal entry:
```bash
_prune_common_canon() { (cd -P -- "$1" 2>/dev/null && pwd -P); }
root_c="$(_prune_common_canon "$root")" || { printf 'error: not a directory: %s\n' "$root" >&2; exit 1; }
for entry in "$@"; do entry_c="$(_prune_common_canon "$entry" || printf '%s' "$entry")"
  [[ "$root_c" == "$entry_c" ]] && { printf 'error: refusing broad path %s\n' "$root" >&2; exit 1; }; done
```
Add tests for `$HOME/.`, `$HOME//` and `/tmp/..`.

### IN-01: `$` is not rejected in rendered ExecStart tokens

**File:** `installer/systemd_daemon.py:155,243`
**Issue:** systemd substitutes `$VAR` and `${VAR}` inside `ExecStart=` arguments, even quoted
ones. `%` is correctly rejected, but a repo or home path containing `$` would be silently
rewritten.
**Fix:** Add `"$"` to `_REJECTED_CHARS`, or escape it as `$$`.

### IN-06: A transient query failure yields "no such policy on this host" advice

### IN-07: Takeover exception handling discards disclosures of work already done

**File:** `installer/policy.py:991-992`, `installer/systemd_daemon.py:675-681`
**Issue:** `disable_competing` catches only `CommandError`. An `OSError` from `run_captured`
partway through the loop, or a `ValueError`, reaches the outer
`except (CommandError, OSError, ValueError): return None, None`. That throws away both the
system-scope warning and the names of units already disabled.
**Fix:** Catch `OSError` per unit inside `disable_competing` (count it as failed), and compute
the system-scope warning outside the `try`.
