<objective>
Port the macOS launchd background-cleanup mechanism to Linux as a systemd user timer +
oneshot service, wired end-to-end through the existing Policy/Policies-screen machinery.

Purpose: D-01 — one cross-platform background cleanup capability, same Policy shape, same
ownership-marker convention, same wrapper-executable pattern; only the backend verbs differ.
This plan is the phase's tracer: it proves the whole stack (unit generation -> systemctl
through the injected Runner -> Policy factory -> composition root -> Policies screen) on one
path before any expansion task widens it.

Output: `installer/systemd_daemon.py`, `scripts/prune-tmp-linux.sh`, a `linux_daemon_policy`
factory in `installer/policy.py`, and a Linux branch inside `setup.py::_build_daemon_policy`.

**Decision D-01a — the Linux daemon is ON BY DEFAULT, exactly like macOS (resolved during
replanning; review HIGH 15.7-01).** `setup.py:744` gates the auto-apply on
`daemon is not None and apply_daemon_default`, and `setup.py:877` passes
`apply_daemon_default=True` from the genuine interactive wizard. The moment this plan returns a
non-None Linux policy, that existing path fires on Linux too. That must be a decision, not a side
effect, so it is decided here:

- **Chosen: Linux matches macOS.** The Linux row is on by default on first interactive setup,
  gated by the SAME `apply_daemon_default` allowlist (only `_run_interactive_wizard` passes it —
  never `--doctor`, `--fix`, `--guard`, `--unguard` or `--uninstall`), and applied at most once
  ever per machine via its OWN Linux `decided` sentinel. A user who turns it off stays off.
- **Rationale.** D-01's locked intent is one cross-platform capability with the same Policy shape,
  the same ownership-marker convention and the same Policies-screen wiring; a Linux row that is
  opt-in-only while the macOS row is on-by-default would be a *different product behavior per
  platform*, which is the exact thing D-01 rejected. The source todo's own complaint is that the
  user believed this was already working on Linux — shipping it dark would reproduce that failure.
  ROADMAP SC#2's "invisible/inert on Linux" is deliberately SUPERSEDED by this phase (that is the
  phase's whole purpose); the two tests asserting it are updated to assert the new, intended
  behavior rather than deleted, so the change is recorded rather than erased.
- **Rejected: opt-in-only on Linux.** It would leave the capability invisible on the platform this
  phase exists to serve, and would fork the on-by-default semantics across two platforms.
- **Coupled consent requirement.** `ensure_daemon_default` discards the `PolicyResult`, so an
  auto-default apply would silently swallow plan 15.7-03's competing-mechanism warning — the one
  thing in this apply path that touches state the user did not install through this project. Plan
  15.7-05 Task 1 therefore adds a warning sink to `ensure_daemon_default` and prints it after the
  wizard exits. D-01a is only safe WITH that sink; the two are one decision.

**Decision D-01c — the daemon's ACTIVE answer is systemd's runtime state, bounded and memoized
(resolved during replanning; review HIGH 15.7-01).** The previous plan defined both `active` and
`is_active` as `units_present(unit_dir)`. `installer/daemon.py:541` legitimately does the
equivalent for launchd, because `launchctl bootstrap` fails if the plist is absent and
`bootout` removes the registration with the plist — presence and registration move together
there. Systemd does not work that way: `systemctl --user disable`, `stop`, a failed timer, or a
`systemctl --user daemon-reload` after a hand-edit all leave the unit FILES exactly where they
were while the timer is no longer running. Presence-as-activity therefore reports a dead timer as
healthy, and plan 15.7-06's red Doctor finding is gated on that same value — so the false positive
lands precisely on the machine the warning exists for. Resolved as three coupled pieces:

- **`probe_timer_state(*, read_output)`** runs `systemctl --user is-active <timer>` and maps its
  answer onto `DaemonState`: `active`/`activating`/`reloading` -> ACTIVE, `inactive`/`failed`/
  `deactivating` -> INACTIVE, an unreadable or unrunnable query -> UNAVAILABLE. This is the only
  place in this phase that decides what "running" means.
- **`timer_state(unit_dir, *, read_output)`** is what the Policy binds. It answers INACTIVE
  WITHOUT spawning anything when `units_present(unit_dir)` is False, and otherwise returns
  `probe_timer_state`'s answer. Presence is a NECESSARY condition here, never a sufficient one —
  that ordering is the whole fix, and it is worth stating because it looks superficially like the
  predicate being replaced: files present + timer disabled now reads INACTIVE, which is exactly
  the case the old predicate got wrong, while files absent short-circuits to INACTIVE for free.
- **`TimerStateCache`** memoizes one answer for `STATE_CACHE_TTL` seconds against an injected
  monotonic clock, and exposes `invalidate()` which `linux_daemon_policy`'s `_apply` and `_remove`
  call so a toggle is reflected immediately rather than after the TTL. The cache exists because
  this predicate is now a subprocess and plan 15.7-06 reads it from
  `on_data_table_row_highlighted`, i.e. on every arrow-key move through the Policies table
  (review MEDIUM 15.7-06). Without it, correcting this predicate would trade a false report for a
  process spawn per keypress.
- **`query_systemctl`** is the bounded read adapter every systemd QUERY in this phase goes
  through: `installer.run.run_query` with an explicit `SYSTEMCTL_QUERY_TIMEOUT` and an
  `accept_codes` set covering the read-only verbs' documented non-zero "this is the answer" exits
  (`is-active` 3, `is-enabled` 1 and 4, `list-unit-files` 1). `OutputRunner` is
  `Callable[[list[str]], str]` and cannot carry a timeout keyword, so the bound is baked into the
  adapter that becomes `read_output`'s real default rather than left to each call site
  (review MEDIUM 15.7-03). A side-effecting `Runner` call is deliberately NOT bounded: `run_query`'s
  own docstring records why a bounded query and an unbounded mutation are different contracts.

**Decision D-01b — a systemd availability gate (resolved during replanning; review HIGH
15.7-03).** `installer/platform.py::detect_os` maps only to `macos`/`fedora`/`debian`/`arch`;
nothing in this codebase probes whether `systemctl` actually exists. A container, a WSL image
without systemd, or a musl/openrc host would get a daemon row whose every apply fails. So
`_build_daemon_policy` returns `None` on a non-macOS platform when `systemctl` is not resolvable
on PATH — degrading to exactly the behavior Linux has today (no row, no argv, no artifacts),
which is also what makes plan 15.7-03's "a machine with no systemd applies exactly as before"
claim true rather than aspirational.
</objective>

Create `installer/systemd_daemon.py` as the Linux mechanism tier, mirroring `installer/daemon.py`
name-for-name where the semantics line up (per D-01). Do NOT import `subprocess`: every external
call goes through the injected `Runner` seam from `installer/run.py`, exactly as
`daemon.bootstrap`/`daemon.bootout` already do.

Declare: `UNIT_BASENAME` of tools-installer-prune-tmp; `SERVICE_NAME` and `TIMER_NAME` derived
from it; `DEFAULT_BOOT_DELAY` of 2min, `DEFAULT_INTERVAL` of 10min and `DEFAULT_AGE_MINUTES` of
10 — these three are the confirmed-working ai-kit baseline cadence the source todo names
explicitly ("a systemd user oneshot service run every 10 minutes"), which is why the Linux
policy uses an interval rather than the macOS daily calendar time; and a Linux-specific
decided-marker sentinel pair whose text names daemon-linux so it can never collide with
`installer.daemon`'s own pair (RESEARCH Pattern 3).

Reuse, by importing from `installer.daemon` rather than re-declaring (the single-source-of-truth
discipline `installer/policy.py` line 52 already documents): `WRAPPER_COMMAND`, `install_wrapper`,
`remove_wrapper`, `wrapper_present`, `ensure_log_path`, `last_run_summary`, `DEFAULT_CAP_BYTES`
and `DaemonScheduleError`. The wrapper asset is backend-agnostic — it execs the script named by
--script with the forwarded tail — so one wrapper executable serves both daemons; the two are
never constructed on the same OS. Reuse `DaemonScheduleError` itself rather than declaring a
parallel exception, so `ensure_daemon_default`'s and `ui_common.run_live`'s existing OSError
catches keep working with no new except clause anywhere.

Implement `user_unit_dir(home, environ)` returning the systemd user unit directory: the
XDG_CONFIG_HOME value when set AND absolute, else home/.config, then systemd/user — systemd
documents `$XDG_CONFIG_HOME/systemd/user` as the per-user unit search path, so this read belongs
to this module rather than a shared helper. Ignore a relative XDG_CONFIG_HOME rather than
honouring it: the XDG base-directory spec says a non-absolute value must be ignored, and honouring
one here would resolve every unit path against whatever cwd the process happens to have (review
LOW 15.7-01).

Implement `systemd_available(*, which=shutil.which)` returning whether `systemctl` resolves on
PATH — the D-01b gate, injected rather than probed directly so the composition root's tests are
deterministic on any host. It resolves a name; it never spawns a process.

Implement a private `_quote` that validates one rendered value and returns it wrapped in double
quotes, raising DaemonScheduleError for the rejected character set above. Implement
`render_service` and `render_timer` as pure string builders that validate EVERYTHING before
returning anything (mirroring `daemon.render_plist`'s documented fail-closed ordering), and
`write_units(unit_dir, ...)` which renders both first, then creates the directory and writes
each file through `installer.atomic.atomic_write_bytes` at an explicit mode of 0o644.

For `render_timer`, declare `OnBootSec`, `OnUnitActiveSec`, the `Unit=` line and the `[Install]`
section — and deliberately NO persistence key. Record the reason in a comment at that render
point: persistence only gives calendar-style catch-up semantics for an `OnCalendar=` timer, and
declaring it on a monotonic `OnBootSec`/`OnUnitActiveSec` timer buys nothing while implying a
catch-up guarantee to the next maintainer that systemd does not provide here (review LOW 15.7-01).

Implement `bootstrap(unit_dir, *, run)` as daemon-reload, then enable the timer, then restart
the timer — restart rather than start because a re-apply that rewrote the unit content must
actually pick it up, and restart covers both the not-running and the running-with-stale-config
cases. Implement `daemon_reload(*, run)`.

Add `DaemonState` to `installer/enums.py` as a closed three-member `StrEnum` — ACTIVE, INACTIVE,
UNAVAILABLE — beside the existing `Severity` and `UninstallState`. It goes in that shared module,
not in `installer/systemd_daemon.py`, because plan 15.7-02's `installer/diskusage.py` consumes the
same vocabulary and must not import a Linux-only backend module to get it; `installer/enums.py`
already exists precisely as the place closed vocabularies live. Document on the enum that
UNAVAILABLE means "this machine has no managed background cleanup we can confirm" — a host with no
systemd, or one whose state query could not be answered — and is deliberately NOT the same fact as
INACTIVE, because the two want different user advice (plan 15.7-02 D-03c).

Implement `SYSTEMCTL_QUERY_TIMEOUT` and `query_systemctl(cmd)` per D-01c: a thin adapter calling
`installer.run.run_query` with that timeout and an `accept_codes` set covering 0, 1, 3 and 4. Put
the reason in its docstring: these are the documented exits where a read-only systemctl verb's
NON-ZERO status still carries the answer on stdout (`is-active` exits 3 for an inactive unit,
`is-enabled` exits 1 for disabled and 4 for a missing unit file), so treating them as failures
would turn every ordinary "no" into an exception; and the timeout is here rather than at each call
site because `OutputRunner` is `Callable[[list[str]], str]` and has nowhere to put one
(review MEDIUM 15.7-03). This adapter becomes `read_output`'s real default everywhere in this
phase.

Implement `probe_timer_state`, `timer_state` and `TimerStateCache` exactly as D-01c specifies,
with `STATE_CACHE_TTL` as a named constant and the clock injected. Record at `timer_state` why the
file check comes first and what it is NOT: presence is a necessary condition, never a sufficient
one, and the predicate this replaces failed precisely because it stopped there.

Implement `bootout(unit_dir, *, run, read_output)`. It ATTEMPTS the user-scope disable-now call
unconditionally, whether or not the timer unit file is on disk — `installer/daemon.py:262-279`
issues `launchctl bootout` unconditionally for the same reason: a deleted or hand-corrupted unit
file can coexist with a still-loaded unit, and a presence gate would skip the one call that fixes
it. What it does NOT do any more is decide the failure's meaning from file presence alone. On
CommandError it classifies: unit files present -> re-raise (this project wrote those units; a
failure to unregister them is real); unit files absent -> re-probe systemd through
`probe_timer_state` and re-raise when the timer is still ACTIVE, returning normally only when the
timer is INACTIVE or UNAVAILABLE. That is the narrow "the unit is already gone" case the macOS
precedent swallows via exit code 3 and nothing else — its docstring states the invariant this must
preserve: "a caller can never proceed past a real bootout failure and treat the daemon as removed
while it may still be loaded" (review HIGH 15.7-01). Systemd has no single ESRCH-equivalent exit
code for `disable` (a missing unit exits 1, the same code a permission or manager failure uses), so
the classification is made on systemd's own post-failure answer rather than on a code table or on
stderr text, which would be locale-dependent.

Implement `remove_units(unit_dir)`, `units_present(unit_dir)`, `unit_paths(unit_dir)`, and
`decided`/`record_decided`/`clear_decided` against the Linux sentinels using
`installer.shellrc.apply_block`/`strip_block` plus `atomic_write_bytes` with mode None
