# Phase 15.7: Unify tmp-prune tooling into an installable Tweaks module — Verification Report

**Phase Goal:** A developer on Linux gets the same installable, uninstallable background cleanup for orphaned agent-runtime temp files that macOS already has — a systemd user timer + oneshot service toggled from the Policies view, never a manual script — plus a reusable cache-redirect that keeps Bun's runtime-transpiler cache out of the temp dir in the first place, a scope-aware takeover of any pre-existing competing cleanup mechanism, and a red Doctor warning when the cleanup job is inactive while disk or /tmp space is running out.

`systemctl --user` verb were withheld. All daemon/redirect lifecycle evidence comes from
read-only host queries, the test suite, code reading, and a sandboxed run under a throwaway

### Gaps Summary

The phase delivers almost everything the goal asks for. The installable/uninstallable
systemd user timer + oneshot exists, is toggled from the Policies view, is transactional
with compensating `daemon-reload`s on every rollback branch, is on by default like macOS,
is gated on `systemctl`, and answers "active" from systemd's own runtime state through one
shared, bounded, memoized cache that the render path may only `peek()`. The scope-aware
takeover is real and was confirmed live and read-only against this host's actual
system-scope `cleanup-bun-tmp-cache.timer`: it is detected, classified system-scope,
disclosed with the exact root command, and structurally refused entry to any mutation path.
The reusable cache-redirect writes correct systemd and shell grammar from one declaration,
creates the target directory, never deletes the user's cache, and comes off cleanly on
uninstall. The shared prune core removes the duplicated logic and converges the fd/find age
semantics. Both prune wrappers are shellchecked by `make validate`.

One thing is wrong, and it is in the fourth deliverable the goal names — the Doctor warning.

`setup.py:478` measures free space on `Path("/")`. On an ostree/composefs host — Bazzite
and Silverblue, which this phase's own ROADMAP entry, CONTEXT.md and RESEARCH.md name as
the target and which is the machine this verification ran on — `/` is a ~45 MB read-only
composefs overlay that is by construction 100% used with 0 bytes free. It is not the
filesystem whose exhaustion the warning exists to predict; `/var` is, and it reports 402 GB
free. The consequence is that `DiskPressure.low_disk` is permanently True, so
`make doctor` and the Doctor screen render a **red, emphasised, `Severity.ERROR`** finding
("Background cleanup is off and free disk space is low / Free space is at 0.0%") on every
single run, on a machine with 402 GB free. Enabling the daemon does not silence it; it only
downgrades it to a permanent ordinary warning.

That directly falsifies two must-have truths — 15.7-02's "an inactive daemon on a machine
with plenty of space produces nothing at all" and 15.7-06's "a machine with healthy free
space sees no new Doctor output at all, on either surface" — and it inverts D-03's own
stated rationale, which chose 15%/70% over 30%/50% *specifically* to reduce false-positive
noise. It also falsifies Plan 06's `<human-check>` claim 6 verbatim.

The pure layer is not at fault: `installer/diskusage.py` faithfully reports what it is
handed. The failure is a wiring decision at the composition root, and it survived a clean
`make validate`, 2901 passing tests and 95.69% coverage because the "healthy machine is
silent" truth is only ever exercised at the pure layer with synthetic percentages injected
through the `usage` callable — no test asks the composition root which mount it chose.

The fix is small and the project already has the ingredient: `installer/platform.py:23,52`
exposes `Platform.immutable` / `detect_immutable()` off the `/run/ostree-booted` marker,
and `_DiskProbe` already receives the `Platform`. Resolve the root probe path from it —
the writable data mount on an immutable host, `/` elsewhere — and add a composition-root
test that pins the choice, so the next edit cannot silently re-hardcode it.

Neither review lane caught this, and 15.7-REVIEW-FIX.md does not list it as deferred, so it
is genuinely new scope rather than a knowingly-accepted trade-off.
