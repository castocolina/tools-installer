## Pre-discussion investigation

User said they thought this todo was already implemented. Investigation found it is
**half-implemented**: a real, production-grade daemon exists
(`installer/daemon.py`/`installer/policy.py`'s `daemon_policy`, wired into Policies)
but is explicitly macOS-only (`setup.py:349`, citing "ROADMAP SC#2: invisible/inert on
Linux"). No systemd equivalent, no env-var cache-redirect on either platform, no
`make doctor` integration exists. This narrowed the phase from "build from scratch" to
"extend the proven macOS mechanism to Linux + add the missing preventive/observability
pieces."

---

## Reuse vs. rewrite the daemon

Trade-off presented: mirror `daemon.py`/`policy.py`'s Policy pattern with a new
systemd backend (same ownership-marker, Policies wiring, wrapper-script pattern; only
plist/launchctl swapped for unit-files/systemctl) vs. a fully separate module given
how different systemd and launchd are.

**User's choice:** Option 1 (shared pattern, new backend) — with an added requirement:
**"también debe detectar si existe mecanismo ya activo para lo mismo y
desactivar/eliminar y dejar el de este repo. con los scripts proporcionados se
debería establecer un patrón."** The Linux daemon must detect the pre-existing
`ai-kit` systemd units (confirmed active and working on this host) and take over from
them — never running two competing cleanup daemons — using the already-provided
`ai-kit` scripts as the tested baseline pattern.

**Resolution:** Captured as D-01 (shared Policy pattern) and D-02 (detect-and-replace
requirement) in CONTEXT.md.

---

## Doctor warning thresholds

Trade-off presented: the todo's original numbers (disk <30% free, or Linux `/tmp`
>50%) vs. more conservative numbers to reduce false positives.

**User's choice:** More conservative — user specified `<15% / >70%` explicitly rather
than picking a labeled option as-is.

**Resolution:** Captured as D-03 in CONTEXT.md with the exact numbers the user gave.

---

## Env-var redirect: scope

Trade-off presented: Bun-only fix (the known, confirmed problem) vs. a generalized
mechanism for any catalog tool with the same orphaned-cache problem.

**User's choice:** Generalized mechanism ("2"), qualified: **"Pero con BUN como
target ya conocido"** — build the reusable mechanism, but grounded in and validated
against the one real, already-confirmed case (Bun), not a speculative multi-tool
design built ahead of a second real need.

**Resolution:** Captured as D-04 in CONTEXT.md.
