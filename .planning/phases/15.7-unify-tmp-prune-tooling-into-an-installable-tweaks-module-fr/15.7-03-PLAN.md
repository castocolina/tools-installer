<objective>
Detect a pre-existing competing Bun-temp cleanup mechanism before this project's own daemon
takes over, and act on it within this project's privilege model.

Purpose: D-02 — never run two competing cleanup mechanisms simultaneously.

**Scoped interpretation of D-02 (recorded as D-02a, resolved during planning).** CONTEXT.md's
Claude's-Discretion text assumed the competing `ai-kit` units were user-scope and detectable via
`systemctl --user list-unit-files`. 15.7-RESEARCH.md live-verified on this exact host that they
are SYSTEM-scope (`/etc/systemd/system/cleanup-bun-tmp-cache.{service,timer}`, root-owned);
`systemctl --user list-unit-files` returns nothing for them. Reading them needs no privilege;
disabling or deleting them needs root. This project has no `sudo`, `pkexec` or `doas` call
anywhere in its codebase and its entire install model is userspace-only. So D-02's
"detect and disable/remove" resolves as:

- **User-scope competitor found** -> genuinely detect and take over (disable it), which is
  D-02's original intent and is inside this project's existing privilege model.
- **System-scope competitor found** -> detect and WARN, never mutate. Surface it plainly, with
  the exact root command the user can run themselves. Silently doing nothing would leave two
  cleanup jobs running and tell the user nothing; silently escalating privileges would be this
  codebase's first-ever privilege escalation and a real architectural change nobody signed off.

This is the same kind of source-grounded correction Phase 15.4 applied to its own D-01: the
decision's intent is honoured, its factual premise is corrected against a live measurement.

**The honest consequence, stated plainly (review HIGH 15.7-03).** On a host whose competitor is
system-scope — which is the real, live-verified case on the target host — this phase does NOT
achieve exclusivity. Two cleanup jobs will run. This plan's earlier `must_haves` claimed "two
cleanup jobs never run side by side"; that claim was false for the system-scope branch and has
been corrected. What this plan actually guarantees is narrower and true: **no two USER-SCOPE jobs
run side by side, and any job this project cannot stop is named to the user rather than left
undisclosed.** Both mechanisms are idempotent `rm` passes over the same file pattern, so the
overlap is wasteful rather than dangerous — but the cost of the overlap is not the point; being
accurate about what shipped is.

**Decision D-02b — disable, never delete, a competing user-scope unit (resolved during
replanning; review MEDIUM/LOW 15.7-03).** For a user-scope competitor this plan issues
`systemctl --user disable --now`. It does NOT unlink the competitor's unit files. Deleting a file
this project did not write is outside its ownership model — `installer/daemon.py`'s
`install_wrapper`/`remove_wrapper`/`wrapper_present` all refuse to touch a same-named file without
this project's own sentinel, for exactly this reason — and a disabled unit is a recoverable state
the user can undo, while a deleted one is not. The consequence is real and must be stated in the
wording: the competitor's unit files remain on disk and could be re-enabled by hand. Every user-
facing string this plan produces therefore says "stops and disables", never "removes" or
"deletes" (review LOW 15.7-03: the earlier wording overstated what the command does).

**Decision D-02c — a failed user-scope disable keeps this project's daemon and discloses the
overlap (resolved during replanning; review HIGH 15.7-03).** The three candidate invariants were:
roll back this project's own registration, proceed with both active and warn, or retry with user
confirmation. Chosen: **proceed, and disclose.**

- *Not rollback.* The disable that failed belongs to a FOREIGN mechanism. Undoing this project's
  own working registration because someone else's unit would not stop leaves the machine running
  exactly one cleanup job — the unmanaged, untracked one the user just asked to replace. Going
  from two jobs to one worse job is not an improvement, and it makes an unrelated failure look
  like this policy's own failure.
- *Not retry-with-confirmation.* The `Policy` protocol has no confirmation seam; `apply` is a
  zero-argument closure called from a Textual worker and, under D-01a, from the on-by-default
  path where there is no user present to answer. Inventing a prompt channel for this one case
  would be a new UI concern in the middle of a policy apply.
- *Proceed and disclose.* The registration stands, and the result's `warning` names each
  competitor that could not be disabled, the failure reason, and the exact user-scope command the
  user can run themselves. Under D-01a that warning is surfaced after the wizard exits via the
  sink plan 15.7-05 Task 1 adds to `ensure_daemon_default`; from an explicit Policies-screen
  toggle it is rendered by the existing result path. Either way it reaches a human.

Output: competing-mechanism detection and scope-aware takeover inside
`installer/systemd_daemon.py` and `linux_daemon_policy`.
</objective>

Pure parsing:
- The unit-file listing parser returns the unit names from the first column of each non-empty
  line, ignoring a trailing summary line such as "2 unit files listed." and ignoring any line
  whose first column is not one of the names asked for.
- Given empty output it returns an empty tuple.
- Given output where the wanted name appears only as a substring of a longer unit name, it does
  NOT match — the comparison is on the whole first column.

Detection:
- With an injected output runner that answers the user-scope probe with a matching timer and the
  system-scope probe with nothing, detection reports exactly one competing entry, scope "user".
- With the inverse (nothing user-scope, a matching timer and service system-scope), detection
  reports those entries with scope "system".
- With both scopes answering, entries from both are reported and each carries its own scope.
- With an output runner that raises CommandError for one scope, the OTHER scope's result is
  still reported — one unreadable scope never suppresses the other and never propagates.
- With an output runner that raises OSError (no systemctl on this machine at all), detection
  returns an empty tuple.
- Every argv detection issues is a read-only `systemctl ... list-unit-files ...` invocation, and
  the user-scope probe carries the user flag while the system-scope probe does not.

Refusal and wording:
- Handing a system-scope entry to the takeover function raises ValueError before issuing any
  argv at all — a structural refusal, so a future caller cannot accidentally route a
  system-scope unit into a mutation path.
- The takeover function, given user-scope entries, issues one disable-now argv per entry, every
  one of which begins with `systemctl` and contains the user flag; it returns the names it
  actually disabled and collects, rather than raises, a per-entry CommandError.
- D-02b: the takeover function NEVER issues an argv containing a unit-file-removing verb and
  never unlinks a path — asserted positively on the recorded argv list and on the fixture unit
  files, which still exist afterwards.
- The system-scope warning builder returns None when there are no system-scope entries, and
  otherwise a single sentence naming the found unit, stating that it keeps running alongside this
  app's own daemon, and quoting the exact root command that stops and disables it.
- D-02c: the user-scope failure warning builder, given the names that failed to disable, returns
  a sentence naming each one, stating that it is still running alongside this app's own daemon,
  and quoting the user-scope command the user can run themselves. It returns None when nothing

- Every user-facing string this module produces describes the effect as stopping and disabling,

Implement `detect_competing(*, read_output)` taking an injected `OutputRunner`. It probes the
user scope and the system scope separately, each inside its own guard that swallows
`CommandError` and `OSError` and contributes an empty result for that scope — a machine without
systemd, or one where one scope is unreadable, must degrade to "found nothing there" rather than

system-scope, before issuing a single argv — the refusal is structural, not a comment. For
user-scope entries it issues one user-scope systemctl disable-now call per entry through the
injected `Runner`, collecting a per-entry `CommandError` into a failure list instead of
aborting, and returns the disabled names and the failed names.

file-removing systemctl verb. Record the reason at that call site: the competitor's unit files
