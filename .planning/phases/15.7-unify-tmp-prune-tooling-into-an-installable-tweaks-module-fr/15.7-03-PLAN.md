<objective>
Detect a pre-existing competing Bun-temp cleanup mechanism before this project's own daemon
takes over, and act on it within this project's privilege model.

Purpose: D-02 — never run two competing cleanup mechanisms simultaneously.

**Scoped interpretation of D-02 (recorded as D-02a, resolved during planning).** CONTEXT.md's
Claude's-Discretion text assumed the competing `ai-kit` units were user-scope and detectable via
`systemctl --user list-unit-files`. 15.7-RESEARCH.md live-verified on this exact host that they
are SYSTEM-scope (`/etc/systemd/system/cleanup-bun-tmp-cache.{service,timer}`, root-owned);
`systemctl --user list-unit-files` returns nothing for them. Reading them needs no privilege;
disabling or deleting them needs root. This project has no `sudo`, `pkexec` or `doas` call
anywhere in its codebase and its entire install model is userspace-only. So D-02's
"detect and disable/remove" resolves as:

- **User-scope competitor found** -> genuinely detect and take over (disable it), which is
  D-02's original intent and is inside this project's existing privilege model.
- **System-scope competitor found** -> detect and WARN, never mutate. Surface it plainly, with
  the exact root command the user can run themselves. Silently doing nothing would leave two
  cleanup jobs running and tell the user nothing; silently escalating privileges would be this
  codebase's first-ever privilege escalation and a real architectural change nobody signed off.

This is the same kind of source-grounded correction Phase 15.4 applied to its own D-01: the
decision's intent is honoured, its factual premise is corrected against a live measurement.

Output: competing-mechanism detection and scope-aware takeover inside
`installer/systemd_daemon.py` and `linux_daemon_policy`.
</objective>

15.7-RESEARCH.md Pitfall 1 — the live-captured output shape of `systemctl list-unit-files` on

15.7-RESEARCH.md Open Question 3 — exact-name matching is the recommended heuristic: there is
exactly one real, confirmed competing implementation today, and a pattern-based heuristic would

  </read_first>
  <behavior>
Write tests FIRST, extending tests/test_systemd_daemon.py.

Pure parsing:
- The unit-file listing parser returns the unit names from the first column of each non-empty
  line, ignoring a trailing summary line such as "2 unit files listed." and ignoring any line
  whose first column is not one of the names asked for.
- Given empty output it returns an empty tuple.
- Given output where the wanted name appears only as a substring of a longer unit name, it does
  NOT match — the comparison is on the whole first column.

Detection:
- With an injected output runner that answers the user-scope probe with a matching timer and the
  system-scope probe with nothing, detection reports exactly one competing entry, scope "user".
- With the inverse (nothing user-scope, a matching timer and service system-scope), detection
  reports those entries with scope "system".
- With both scopes answering, entries from both are reported and each carries its own scope.
- With an output runner that raises CommandError for one scope, the OTHER scope's result is
  still reported — one unreadable scope never suppresses the other and never propagates.
- With an output runner that raises OSError (no systemctl on this machine at all), detection
  returns an empty tuple.
- Every argv detection issues is a read-only `systemctl ... list-unit-files ...` invocation, and
  the user-scope probe carries the user flag while the system-scope probe does not.

Refusal and wording:
- Handing a system-scope entry to the takeover function raises ValueError before issuing any
  argv at all — a structural refusal, so a future caller cannot accidentally route a
  system-scope unit into a mutation path.
- The takeover function, given user-scope entries, issues one disable-now argv per entry, every
  one of which begins with `systemctl` and contains the user flag; it returns the names it
  actually disabled and collects, rather than raises, a per-entry CommandError.
- The system-scope warning builder returns None when there are no system-scope entries, and
  otherwise a single sentence naming the found unit, stating that it may run alongside this
  app's own daemon, and quoting the exact root command that removes it.
- `installer/systemd_daemon.py`'s source imports no subprocess module.
  </behavior>
  <action>
Extend `installer/systemd_daemon.py`.

Declare `COMPETING_UNITS` as the exact names `cleanup-bun-tmp-cache.timer` and
`cleanup-bun-tmp-cache.service`, with a comment recording that these are the one real, live-
confirmed competing implementation (15.7-RESEARCH.md) and that exact-name matching is a
deliberate choice over a broader heuristic.

Declare a frozen `CompetingUnit` dataclass holding the unit name and its scope, where scope is
one of the two literal strings for user and system, and declare those two scope values as named
constants so no call site spells them by hand.

Implement a pure `parse_unit_files(output, names)` that splits the listing into lines, takes the
first whitespace-delimited column of each non-empty line, and keeps only whole-column matches
against the wanted names. Keep it total over any input: a summary line, a legend line, or
ragged whitespace must never raise.

Implement `detect_competing(*, read_output)` taking an injected `OutputRunner`. It probes the
user scope and the system scope separately, each inside its own guard that swallows
`CommandError` and `OSError` and contributes an empty result for that scope — a machine without
systemd, or one where one scope is unreadable, must degrade to "found nothing there" rather than
break an apply. Both probes pass the no-legend and no-pager flags plus the wanted unit names as
pattern arguments, and both are read-only: reading a system-scope unit listing needs no
privilege, which is exactly why detection can span both scopes while mutation cannot.

Implement `disable_competing(units, *, run)`. It raises ValueError immediately if ANY entry is
system-scope, before issuing a single argv — the refusal is structural, not a comment. For
user-scope entries it issues one user-scope systemctl disable-now call per entry through the
injected `Runner`, collecting a per-entry `CommandError` into a failure list instead of
aborting, and returns the disabled names and the failed names.

Implement `system_scope_warning(units)` returning None when no entry is system-scope, otherwise
one sentence naming the unit(s), saying a system-level cleanup service was found and may run
alongside this app's own daemon, and quoting verbatim the root command that removes it:
`sudo systemctl disable --now cleanup-bun-tmp-cache.timer`. This string is user-facing prose
this project never executes; nothing in `installer/` may build it into an argv.

Write tests FIRST, extending tests/test_policy_linux_daemon.py.

- Applying on a machine with a user-scope competing timer issues this project's own
  daemon-reload/enable/restart sequence FIRST and the competitor's disable-now call AFTER, so
  the machine is never left with neither mechanism registered.
- That same apply returns a PolicyResult containing a layer naming the competing mechanism and
  the fact that it was disabled.
- Applying on a machine with a SYSTEM-scope competitor issues no disable call at all — asserted
  on the recorded argv list, which must contain no argv naming the competing unit — and returns
  a PolicyResult whose warning names it and carries the root command.
- Applying with both a user-scope and a system-scope competitor disables only the user-scope one
  and still warns about the system-scope one.
- A competing-disable call that fails does NOT roll back this project's own registration: the
  unit files remain, `is_active()` stays True, and the failure is reported in the result's
  warning alongside anything else collected there.
- A detection probe that raises leaves apply's behavior identical to a machine with no
  competitor: no extra argv, no warning, no layer.
- Applying on a machine with no competitor produces a result byte-identical to the pre-plan
  behavior (same layers, no warning) — pinned so this feature cannot add noise to the normal case.
  </behavior>
  <action>
Give `linux_daemon_policy` an injected `read_output` parameter typed `OutputRunner` and
defaulting to `installer.run.run_output`, so the composition root needs no change and tests can
drive detection with a double.

Inside `_apply`, after bootstrap has succeeded and inside the same warning-collection region
that already handles the marker write, run detection, then act by scope: disable the user-scope
entries, and build the system-scope warning without touching anything. Do the takeover AFTER
this project's own registration rather than before it, deliberately: D-02's requirement is that
two mechanisms never run side by side, and a takeover-first ordering that then failed to
register would leave the machine with NO cleanup at all, which is strictly worse than a few
milliseconds of overlap. Record the reason as a comment at that call site.

Add a `PolicyLayer` naming the competing mechanism and what happened to it, appended only when
detection found something — the no-competitor case must keep producing exactly the layers it
produced before. Fold the system-scope sentence and any per-entry disable failure into the same
joined warning string the marker-write failure already uses, so there is one warning channel,
not two.

Guard the whole detection-and-takeover region so that neither a raising probe nor a raising
disable can escape `_apply` after a successful registration — a bookkeeping-tier failure must
never undo a working daemon. Catch only `CommandError`, `OSError` and `ValueError` there
(ValueError is the structural refusal from task 1, which can only fire on a programming error
and must be reported rather than crash a live policy apply).
