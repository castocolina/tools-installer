<objective>
Collapse the duplicated halves of the two prune scripts onto one shared, shellcheck-clean core,
behind characterization tests that prove the macOS script's behavior did not move.

Purpose: the source todo's explicit engineering requirement — "don't just copy-paste ai-kit's
Linux scripts and `prune-user-tmpdir.sh`'s macOS logic side by side — build a single
cross-platform module ... rather than one script per OS with duplicated logic". Plan 15.7-01
delivers a working Linux script; this plan is what stops the phase from shipping the very
side-by-side duplication its own source rejects (review MEDIUM 15.7-01).

Output: `scripts/lib/prune-tmp-common.sh`, both platform scripts reduced to wrappers over it, a
new characterization suite for the macOS script, and a widened `make validate` shellcheck gate.

**Why this is its own plan rather than a fourth task in 15.7-01 (resolved during replanning round
2).** `scripts/prune-user-tmpdir.sh` is 266 lines, has no test of its own today, and is the
executable the SHIPPED macOS daemon already invokes on a schedule. Refactoring it is the riskiest
single change in this phase. Plan 15.7-01 is the phase's tracer: putting this on the tracer's
critical path would mean the end-to-end Linux path could not land until the macOS script had been
rewritten. Splitting it out keeps the risk isolated, lets the characterization tests come first,
and costs only a wave.

**Decision D-01d — share the engine, parameterise the patterns (resolved during replanning).**
The reviewer's suggestion was to extract "shared filename matching, safety checks, and summary
output into one reusable implementation". Two of those three are unconditionally shareable and are
shared here. Filename MATCHING is shared as a mechanism but not as data: the Linux target is one
regex family (`.{16 hex}-{8 digit}.{so,node}`), while the macOS target set is four unrelated
families including two directory shapes. Forcing both into one pattern expression would produce a
parameter that is really just "the whole matching rule", which is duplication wearing an
abstraction. So the core owns the traversal, the depth limit, the age filter, the refusal guard,
the age validation, the human-readable byte formatting and the summary emission; each wrapper owns
its own pattern set, its own default age and its own help text. That is one implementation of every
piece of LOGIC, with the per-platform DATA where it belongs.

**Decision D-01f — one age semantics (`-mmin`), and the "byte-for-byte" claim narrowed to the
contract it actually holds (resolved during replanning round 3; review HIGH 15.7-07 cycle 3).**
The previous revision asserted that `--days 1` deletes a 25-hour-old file and spares a 23-hour-old
one, while simultaneously promising byte-for-byte behavioral equivalence with a script that
filters by `find -mtime +"$DAYS"`. The reviewer called that an internal contradiction. It is — but
the real situation is worse than the review states, and the resolution follows from it rather than
from picking a side.

**Measured, not assumed** (GNU findutils 4.10.0, `bfs` 4.1.1 and `fd` 10.5.0, fixtures aged with
`touch -d`, this host, during round-3 replanning):

| file age | `find -mtime +1` | `fd --changed-before 1d` |
|----------|------------------|--------------------------|
| 23h      | no               | no                       |
| 25h      | **no**           | **yes**                  |
| 47h      | no               | yes                      |
| 49h      | yes              | yes                      |

`-mtime +N` truncates the age to whole 24-hour periods and then requires strictly more than N of
them, so it means "older than (N+1)*24h". `--changed-before Nd` is plain duration arithmetic:
"older than N*24h". The same divergence appears at the shipped default: with `--days 3`,
`find -mtime +3` SPARES a 73-hour-old file that `fd --changed-before 3d` deletes.

**The key finding: the current script already has BOTH semantics, and which one runs depends on
whether `fd` is installed.** `scripts/prune-user-tmpdir.sh:102-117` and `:143-155` branch on
`HAVE_FD`, using `fd --changed-before "${DAYS}d"` when `fd` resolves and
`find -mtime +"$DAYS"` when it does not. So "the existing behavior" is not one behavior to
preserve; it is two, and they disagree. That is why the previous revision's single assertion could
not be made true against both branches, and it is also why Task 1's characterization suite — which
correctly insists on running in both `PATH` configurations — would have surfaced this as a test
failure rather than a plan contradiction.

- **Chosen: converge on the duration semantics (`-mmin +N`), and narrow the compatibility claim.**
  The shared core filters with `-mmin +minutes`, which reproduces the `fd` branch exactly on both
  branches. The `<objective>`'s and `must_haves`' compatibility promise is narrowed from
  "byte-for-byte observable behavior" to the flag grammar, the refusal set, the age VALIDATION,
  the dry-run default, the target families, the depth limit and the `deleted: N` summary — with
  the `find`-fallback's age-cutoff arithmetic named as the one deliberate exception.
- **Why the `fd` semantics win.** They are what the shipped script does on any machine this
  project has done its job on: the header says "Prefers fd + rg from the tools-installer catalog",
  `fd` is in this project's own catalog, and the macOS daemon runs on a developer machine where
  the installer has run. The `find` path is the degraded fallback, not the reference. They are
  also what a minutes-based core produces naturally — D-01d already chose MINUTES as the core's
  internal unit, and `-mmin` is that unit's own filter; reaching back for `-mtime` would mean
  converting minutes to days and re-introducing the truncation on purpose. And they are what
  `--days 1` plainly means to a reader.
- **What this changes for a real user.** On a macOS machine WITHOUT `fd`, files between N*24h and
  (N+1)*24h old are now pruned where previously they survived one extra day. That is strictly more
  of the cleanup the user asked for, on the platform whose disk-pressure problem this whole phase
  exists to fix, and it makes that machine agree with every machine that has `fd`. It is recorded
  here as a deliberate behavior change rather than discovered later as a regression.
- **Rejected: reproduce `-mtime`'s day-boundary arithmetic in the core.** It would mean emulating
  a truncation rule bug-for-bug in new Python-adjacent shell code, keeping a documented
  inconsistency alive, and making `--days 1` mean "older than two days" on exactly the machines
  least likely to notice. The reviewer offered this as option (a); it loses on every axis except
  literal-fidelity-to-the-weaker-branch.
- **Rejected: keep both branches' current semantics.** That is the status quo the extraction
  exists to eliminate — "one implementation of the age filter" (D-01d) is incompatible with an
  age filter that answers differently depending on which binary is on PATH.
</objective>
