<objective>
Compose the Linux daemon and the cache redirect into the real application: the Policies list, the
on-by-default path, both uninstall entry points, and the Policies detail panel — including the
two disclosures this phase owes the user.

Purpose: D-01's "same Policies-screen wiring" and D-04's Tweaks-view toggle, plus the honest
disclosure of two real limitations 15.7-RESEARCH.md measured live on this host.

**Disclosure resolution (Open Question 2, resolved during planning).** A `systemctl --user`
timer stops firing once the user's last session ends unless `loginctl enable-linger` has been
run. This dev host already has lingering enabled, which would mask the gap in local testing.
This phase does NOT auto-run that command: it is a per-user, systemd-wide setting affecting every
user unit for the account, it may require an administrator authentication prompt, and running it
silently would be a system-level mutation outside this project's zero-escalation model. Instead
the Policies detail panel discloses it and names the command, exactly the way the existing macOS
LaunchAgent's own login-session-scoped behavior is disclosed. That is honest parity, not a
regression — provided it is stated rather than assumed.

**Composition-root argument policy (resolved during replanning; review HIGH 15.7-05).**
`installer/app.py:401-407` and `:529-533` already document, in prose, why `bundles`, `zshrc_path`
and `daemon_policy` are REQUIRED keywords on `run_uninstall` and `perform_uninstall` while the
primitives beneath them keep defaults: "a dropped kwarg would type-check, pass the suite, and
silently sweep nothing while reporting success — a user-visible data-integrity regression that
nothing else can catch." `extra_policies` has exactly that property: drop it at either entry point
and the cache redirect is left on disk while the uninstall prints success. So it is required at
both entry points and defaulted only on `active_policies`, `active_tweak_ids` and `sweep_tweaks`,
where a default is a test affordance rather than a wiring hazard. The existing rationale paragraph
is extended to name `extra_policies` rather than a new paragraph being added beside it.

**Consent sink for the D-01a on-by-default apply (resolved during replanning).** Plan 15.7-01's
D-01a makes the Linux daemon on-by-default, and `ensure_daemon_default` discards `policy.apply()`'s
`PolicyResult`. Plan 15.7-03's competing-mechanism warning — the only place this phase reports on
state the user did not install through this project — would therefore be silently dropped on the
one path where the user never chose anything. Task 1 adds a warning sink so it is not.

**Decision D-05a — the warning delivery is synchronised and abort-proof, not "printed after
`app.run()`" (resolved during replanning; review HIGH + MEDIUM 15.7-05).** A sink alone does not
deliver anything. `installer/wizard_app.py:2065-2066` dispatches the daemon default inside
`@work(thread=True, exclusive=True, group="daemon-default", exit_on_error=False)`, and Textual's
`app.run()` does not join thread workers — `setup.py::_run_interactive_wizard` branches on
`app.install_summary` the instant `run()` returns. So "print the collected warnings after
`app.run()` returns" delivers the disclosure only when the worker happened to finish first. On a
host where the competing-timer takeover is the slow part, that is exactly the run where it does
not. And the existing `if summary is None: console.print("Aborted."); return 0` branch returns
before any later print at all. Since this disclosure is the entire safety justification for the
narrowed D-02a takeover, "usually visible" is not an acceptable contract. Resolved as:

- The sink is not a bare `list[str]` but a small `DaemonDefaultWarnings` collector declared in
  `installer/policy.py` beside `ensure_daemon_default`, holding the collected strings, an `armed`
  flag, and a `threading.Event`. It exposes `append`, `arm`, `finish` and
  `wait(timeout) -> tuple[tuple[str, ...], bool]` returning the messages and whether the apply
  actually completed.
- `_build_app` calls `arm()` at the SAME site where it decides to wire `daemon_default` at all —
  so a run with no daemon policy, or without `apply_daemon_default`, leaves the collector unarmed
  and `wait` returns instantly with nothing. No wait is paid on the common path.
- The `daemon_default` closure calls `finish()` in its own `finally`, so completion is signalled
  whether `ensure_daemon_default` returns, returns False, or raises anything at all — including an
  exception outside its own `except (OSError, CommandError)` tuple. This reuses the guarantee the
  worker's own try/finally already documents (11-REVIEWS.md cycle 3 finding #15) rather than
  inventing a second one, and it keeps the signal inside the callable instead of adding a
  `UnifiedApp` parameter every existing construction site would have to grow.
- `_run_interactive_wizard` calls `wait(DAEMON_DEFAULT_WAIT_SECONDS)` immediately after
  `app.run()` and prints the collected warnings BEFORE the `summary is None` branch, so the abort
  path discloses too. The timeout is bounded and named: a wedged or never-dispatched worker costs
  a bounded delay, never a hang. On a timeout the collected messages are printed anyway, followed
  by one line saying the background cleanup apply had not finished — an honest partial report
  beats both silence and an unbounded block.
- Rejected: routing this through a Textual message and a new screen state. The string is already
  printable after exit; a message type, a handler and a screen field would be strictly more
  machinery for strictly less reliability, and would still not cover the abort branch.
- Rejected: `app.workers.wait_for_complete()`. It is async, would have to run inside the app's own
  event loop before exit, and would couple the disclosure to Textual's worker lifecycle instead of
  to the one callable that actually produces the warning.

Output: seams in `installer/policy.py`, `installer/app.py` and `installer/uninstall.py`; wiring
in `setup.py`; detail text and uninstall row copy in `installer/wizard_app.py`.
