<objective>
Compose the Linux daemon and the cache redirect into the real application: the Policies list, the
on-by-default path, both uninstall entry points, and the Policies detail panel — including the
two disclosures this phase owes the user.

Purpose: D-01's "same Policies-screen wiring" and D-04's Tweaks-view toggle, plus the honest
disclosure of two real limitations 15.7-RESEARCH.md measured live on this host.

**Disclosure resolution (Open Question 2, resolved during planning).** A `systemctl --user`
timer stops firing once the user's last session ends unless `loginctl enable-linger` has been
run. This dev host already has lingering enabled, which would mask the gap in local testing.
This phase does NOT auto-run that command: it is a per-user, systemd-wide setting affecting every
user unit for the account, it may require an administrator authentication prompt, and running it
silently would be a system-level mutation outside this project's zero-escalation model. Instead
the Policies detail panel discloses it and names the command, exactly the way the existing macOS
LaunchAgent's own login-session-scoped behavior is disclosed. That is honest parity, not a
regression — provided it is stated rather than assumed.

Output: seams in `installer/policy.py`, `installer/app.py` and `installer/uninstall.py`; wiring
in `setup.py`; detail text in `installer/wizard_app.py`.
</objective>

  <behavior>
Write tests FIRST.

- A Policy carrying a `decided` closure that answers True makes `ensure_daemon_default` return
  False without calling apply; one answering False makes it call apply and return True.
- `ensure_daemon_default` returns False, without calling apply, for a Policy whose `decided` is
  None — a policy with no ownership record has no once-per-machine default to apply.
- A failing apply still returns False and the marker is NOT recorded (the existing behavior).
- Both daemon factories return a Policy whose `decided` and `clear_decided` closures answer for
  their OWN module's sentinels: recording through the Linux factory leaves the macOS predicate
  False on the same state file, and vice versa.
- A full `run_uninstall` given the LINUX daemon policy clears the Linux marker and leaves any
  macOS marker in the same file untouched, in all three existing branches: nothing-to-sweep,
  post-sweep success, and the already-inactive skipped-selection branch of `perform_uninstall`.
- A `run_uninstall` given a daemon policy whose removal FAILED still preserves the marker
  (the existing cycle-3 finding #13 behavior), now resolved through the policy's own closure.
- A daemon policy whose `clear_decided` is None is a no-op at every one of those call sites
  rather than an exception.
  </behavior>
  <action>
Add two optional fields to `Policy`, declared beside the existing optional callables: a
`decided` closure answering whether any on/off decision has ever been recorded for this policy
on this machine, and a `clear_decided` closure that resets that record. Both default to None,
so every existing policy kind is unaffected.

Bind both on `daemon_policy` (to `installer.daemon`'s predicate and clearer, closed over the
factory's own `state_path`) and on `linux_daemon_policy` (to `installer.systemd_daemon`'s).
This is what makes the two daemons independently recordable, which is the whole reason plan
15.7-01 gave the Linux daemon its own sentinel pair.

Change `ensure_daemon_default` to read `policy.decided` and drop its `state_path` parameter
entirely — do not leave the old parameter as a fallback, because once both factories bind the
closure that fallback becomes an unreachable branch, which architecture rule 5 forbids keeping.
Update its docstring to describe the closure rather than the state file, and update the four
call sites: `setup.py`'s `daemon_default` closure and the three/four uses in
tests/test_wizard_app.py, preserving each test's intent exactly.

In `installer/app.py`, replace each of the four direct `daemon.clear_decided(myshellrc_path)`
calls with an invocation of the passed daemon policy's own `clear_decided` closure, guarded on
the closure being present, and keep every surrounding condition and ordering comment exactly as
it is — the "only after the sweep", "only when not left failed" and "already-inactive skipped
selection" branches are hard-won and must not be restructured by this change. After the
replacement, `installer/app.py` no longer references the `daemon` module at all; remove the now
unused import so ruff and vulture stay clean.
  </action>

| T-15.7-21 | Tampering | ownership-marker clearing | high | mitigate | The marker is resolved through the owning policy's own closure, so a Linux teardown can no longer clear the macOS record (or leave the Linux one set and silently re-enable a daemon the user just disabled) |
