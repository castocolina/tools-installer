# Phase 15.7: Unify tmp-prune tooling into an installable Tweaks module - Context

**Gathered:** 2026-09-15
**Status:** Ready for planning

<domain>
## Phase Boundary

From pending todo `2026-09-10-unify-tmp-prune-tooling-into-an-installable-tweaks-module.md`
(user thought this was already implemented — it is only half-built). A real,
production-grade background daemon for pruning orphaned Bun runtime-transpiler-cache
files (`.dylib`/`.node`) already exists (`installer/daemon.py` + `installer/policy.py`'s
`daemon_policy`, wired into the Policies screen) — but it is **macOS-only by explicit
design** (`setup.py:349`: `if platform.os != "macos": return None`, citing
"ROADMAP SC#2: invisible/inert on Linux"). This phase: (1) extends the same daemon
mechanism to Linux via systemd, (2) adds an env-var cache-redirect mechanism (Bun's
`BUN_RUNTIME_TRANSPILER_CACHE_PATH`, generalized for future reuse) that prevents
orphaning in the first place rather than only cleaning up after, and (3) adds a
`make doctor` warning for the daemon-inactive + low-disk/high-tmp-usage combination.

<decisions>
## Implementation Decisions

### Daemon architecture: reuse the Policy pattern, new systemd backend
- **D-01:** The Linux daemon follows the exact same `Policy` shape
  `installer/policy.py`'s `daemon_policy` already established for macOS — same
  ownership-marker convention ("has any decision ever been recorded for this policy"),
  same Policies-screen wiring, same wrapper-executable pattern
  (`uv run --script` with a `requires-python` PEP 723 constraint, mirroring
  `helper_assets/prune_daemon_runner.py`'s own documented reason for that constraint).
  Only the backend differs: a systemd user timer + oneshot service (unit files, INI
  format, `systemctl --user`) instead of a launchd plist (`launchctl bootstrap/bootout`).
  — **Reversibility:** reversible.
  **Rationale (user):** chose the shared-pattern option explicitly — consistency
  across platforms, one place where the decision/state logic lives, matching the
  precedent this project already established with the omz-plugins policy and the
  macOS daemon policy.

### Daemon architecture: detect and replace pre-existing mechanisms
- **D-02:** On Linux, before installing this project's own systemd units, detect
  whether an equivalent mechanism is already active on the machine (specifically: the
  `ai-kit` bundle's `cleanup-bun-tmp-cache.service`/`.timer`, confirmed present and
  working on this exact host per the source todo) and disable/remove it, replacing it
  with this repo's own managed daemon — never running two competing cleanup
  mechanisms simultaneously. The already-provided `ai-kit` scripts
  (`cleanup-bun-tmp-cache.sh` regex/logic, confirmed working — keeps `/tmp` under 1%
  usage on this host) are the tested baseline pattern to follow for the new
  systemd-backed daemon's own cleanup logic.
  — **Reversibility:** reversible (the detection+takeover is itself an install-time
  step, not a one-way migration — removing this project's daemon should not need to
  restore the old ai-kit units).
  **Rationale (user, verbatim intent):** "también debe detectar si existe mecanismo
  ya activo para lo mismo y desactivar/eliminar y dejar el de este repo. con los
  scripts proporcionados se debería establecer un patrón" — the ai-kit scripts are
  the reference pattern, and installing this project's daemon must not leave two
  overlapping cleanup jobs running.

### Doctor warning thresholds
- **D-03:** More conservative than the original todo's numbers — red warning when the
  cleanup daemon/service is inactive AND: general disk space is below **15%** free
  (not 30%), OR (Linux-specific, tmpfs-quota case) `/tmp` usage exceeds **70%** (not
  50%). Extra visual weight (bold/red) when both the daemon-inactive and low-space
  conditions are true at once — that combination is the actual failure scenario this
  whole todo exists to prevent.
  — **Reversibility:** reversible (a threshold constant).
  **Rationale (user):** chose the more conservative thresholds explicitly to reduce
  false-positive noise on machines with plenty of free space where the daemon simply
  isn't running yet (e.g., before this phase ships, or on a machine that doesn't need
  it as urgently).

### Env-var cache-redirect: generalized mechanism, Bun as the first target
- **D-04:** Build a reusable, generalized mechanism for redirecting a tool's cache
  directory off the OS temp dir (Linux: `~/.config/environment.d/`, systemd-user
  convention, matching `ai-kit`'s `51-bun-cache-redirect.conf`; macOS: find/confirm
  the equivalent, since `launchd` doesn't support `environment.d`-style env vars the
  same way — likely needs to go through shell rc files directly there) — not a
  Bun-only, one-off patch. `Bun`'s `BUN_RUNTIME_TRANSPILER_CACHE_PATH` is the first,
  concrete, already-confirmed-necessary target that drives and validates the
  mechanism's design, not a hypothetical abstraction built ahead of any real need.
  — **Reversibility:** reversible.
  **Rationale (user):** explicitly chose the generalized-mechanism option ("2") but
  qualified it — "pero con BUN como target ya conocido" — build the reusable
  mechanism, grounded in and validated against the one real, already-confirmed case,
  not a speculative multi-tool design built before a second real case exists.

### Claude's Discretion
- Exact systemd unit file naming/labeling convention (parallel to `daemon.py`'s
  `LABEL = "com.tools-installer.prune-tmpdir"` for launchd).
- Exact detection mechanism for the pre-existing `ai-kit` units (service/timer name
  match via `systemctl --user list-unit-files`, or a more general "any enabled
  service matching this cleanup's file-pattern signature" heuristic) — implementation
  shape for research to resolve.
- Exact shape of the generalized env-var-redirect mechanism's API (a registry-level
  declaration a tool can opt into, vs. a small dedicated module with one entry per
  known tool) — implementation detail, not a product decision, as long as Bun is the
  first wired-up case.
- Tweaks-view UI details (toggle label wording, status line format for "daemon
  active: yes/no, current tmp usage: X%") — follows the same established Policies-row
  pattern already used for `daemon:prune-tmpdir` and `omz-plugins` on macOS.

## Existing Code Insights

### Reusable Assets
- `installer/daemon.py` and `installer/policy.py`'s `daemon_policy` factory are
  directly reusable as the SHAPE to mirror (not literally shared code, since
  plist/launchctl and unit-files/systemctl are genuinely different backends) per D-01.
- `installer/helper_assets/prune_daemon_runner.py`'s wrapper pattern (log rotation,
  always-exit-0, `--script`/`--log`/`--cap-bytes` argv contract) is directly reusable
  for the Linux wrapper, backend-agnostic as written.
- `ai-kit`'s already-tested Linux scripts (`cleanup-bun-tmp-cache.sh` and its
  `environment.d` conf) are the proven logic baseline for D-01's cleanup pattern and
  D-04's Linux redirect mechanism respectively — port logic, don't rewrite from
  scratch.

### Established Patterns
- The Policies-screen `"daemon:" `-prefixed id convention (`_has_daemon_id`,
  `wizard_app.py:573-581`) is the established pattern for surfacing a daemon policy
  in the UI; a Linux daemon policy should use the same id-namespacing convention.
- `installer/policy.py`'s transactional apply/rollback pattern (snapshot before
  mutate, roll back on backend failure, degrade only the marker-write failure case
  to a warning) is the established correctness pattern for any Policy that touches
  an OS-level background-job mechanism.

### Integration Points
- `setup.py:331-370` and `:428,807` (`_build_daemon_policy` call sites in `_build_app`
  and the CLI uninstall sweep) are the two integration points a Linux daemon
  construction path must also reach.
- `installer/wizard_app.py`'s Doctor screen (`DoctorScreen`, referenced across Phase
  15.1's context too) is the integration point for D-03's new warning — this phase's
  planner should coordinate with Phase 15.1's Doctor-refresh work if both land close
  together, since both touch the same screen's guidance-rendering path.
