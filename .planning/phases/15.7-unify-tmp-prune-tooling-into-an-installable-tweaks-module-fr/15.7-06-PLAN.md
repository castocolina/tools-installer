**Construction point, named (resolved during replanning round 2; review HIGH 15.7-06).** The
previous revision named the SEAM the closure travels through but never the PLACE it is built.
That gap is not cosmetic: in `setup.py::_run_interactive_wizard`, `_execute_inputs(...)` is
evaluated as an ARGUMENT of the `_build_app(...)` call, so there is no point in the current code
where one object could be handed to both — and this plan's identity assertions were therefore
unsatisfiable as written. Resolved by decoupling the closure from the constructed Policy and
hoisting it:

- **`setup.py::_disk_pressure_probe(platform) -> Callable[[], DiskPressure]`** is THE construction
  point. One named module-level helper, one call per route.
- It deliberately does NOT take the daemon `Policy`. "Is a background cleanup running on this
  machine" is a property of the machine, resolvable from the platform plus the module-level
  artifact path constants — the launchd plist path on macOS, the systemd unit dir plus plan
  15.7-01's `TimerStateCache` on Linux, and `DaemonState.UNAVAILABLE` when `systemctl` does not
  resolve. Because it needs no `Policy`, it does not need `_build_app`'s internal `installed` map
  either, so it can be built BEFORE `_build_app` is called. That decoupling is what makes the
  identity requirement satisfiable at all; hoisting `_build_daemon_policy` out of `_build_app`
  instead would have duplicated an `is_installed` pass over the whole catalog at every route.
- `_run_interactive_wizard` calls it once into a named local and passes that SAME object into
  `_execute_inputs(..., disk_pressure=probe)` and into `_build_app(..., disk_pressure=probe)`.
  Two references, one object, asserted by identity.
- `_build_app` takes `disk_pressure` as an optional parameter and, when it is None, calls
  `_disk_pressure_probe(platform)` itself — so `_run_doctor`'s TTY branch, `_run_fix` and
  `_run_uninstall` still get a working Doctor screen without each growing wiring. The parameter is
  the explicit path; the internal call is the default, exactly the real-defaulted-seam convention
  `_build_daemon_policy`'s own `which`/`run`/`read_output` already use.
- `_run_doctor`'s non-TTY branch and `_verify_and_clean` each call `_disk_pressure_probe(platform)`
  once and pass the result to `run_doctor`. Three CLI routes, one helper, no route building its
  own probe inline.

**Wiring seam, specified (resolved during replanning round 1; review HIGH 15.7-06).** `UnifiedApp`
constructs `DoctorScreen` directly at
`installer/wizard_app.py:2019-2027` with no `PolicyInputs` reference in scope at that point. The
seam is now named, once, and every task uses it:

- `PolicyInputs` gains a `disk_pressure: Callable[[], DiskPressure] | None = None` field, appended
  after `set_link_mode`. It defaults to None, so all fifteen-plus existing
  `PolicyInputs(policies=[...])` construction sites across `tests/` keep working untouched.
- `UnifiedApp.__init__` reads `policies.disk_pressure` and passes it into the existing
  `DoctorScreen(...)` construction. **`UnifiedApp` gains NO new parameter** — adding one would
  touch every `UnifiedApp(...)` site in `tests/test_catalog_tui.py`,
  `tests/test_execute_screen.py`, `tests/test_policies_e2e.py` and `tests/test_uninstall_e2e.py`
  for a value the composition root already has a home for.
- `PoliciesScreen` reads the same field from the same `PolicyInputs` it is already handed.
- `setup.py` builds the closure exactly ONCE per route, at `_disk_pressure_probe`, and binds it to
  `PolicyInputs.disk_pressure` and to that route's `run_doctor` call site. One probe closure,
  three CLI routes and two TUI consumers, no second construction.

**Render path, specified (review MEDIUM 15.7-06).** `run_doctor` does not inline a second print
block. `installer/render.py` gains `render_disk_pressure(pressure, console)`, a sibling of the
existing `render_doctor` / `render_guard_status` / `render_node_globals`, which composes
`disk_pressure_guidance` with `guidance_text` and prints nothing for an empty item list.
`run_doctor` calls it in that same sequence. One named render function per report section is the
convention this file already holds; a bare `console.print(guidance_text(...))` inside `run_doctor`
would be the first exception to it.
