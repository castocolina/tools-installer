### HIGH-02 — deterministic takeover order, and a partial takeover that names both halves
**Commit:** `86a2e48`
**Files:** `installer/systemd_daemon.py`, `installer/policy.py`, `tests/test_systemd_daemon.py`,
`tests/test_policy_linux_daemon.py`

`systemctl list-unit-files` output order is not guaranteed stable across systemd versions, and
`detect_competing` preserves whatever order it read, so `disable_competing` attempted the
disables in that order. On a partial failure, WHICH competitor survived — and therefore the
"Competing mechanism" layer detail and every disclosure sentence built from the
`(disabled, failed)` split — could differ between two runs on the same machine.
`disable_competing` now sorts by unit name before the loop (after, and independently of, the
structural system-scope `ValueError`, which still fires before any argv), mirroring what
`system_scope_warning` already did with the names it discloses.

**No rollback was added** — D-02c stands: a partial takeover PROCEEDS and is disclosed, never
papered over by re-enabling what was already disabled.

**Transparency half — the gap was already closed, and is now pinned.** Auditing what
`policy._detect_and_take_over_competitors` surfaces: it emits all three sentences together
(`takeover_disclosure(disabled)`, `system_scope_warning(...)`, `user_scope_failure_warning(failed)`)
and builds the layer detail from all three name lists, so a partial takeover already named both
halves — with the `systemctl --user enable --now <unit>` that puts a disabled one back and the
`systemctl --user disable --now <unit>` that stops a survivor. What was missing was a test
asserting it: the existing partial-failure test only asserted the FAILED unit in the warning, so
dropping the disabled half would not have failed the suite. It now asserts both halves and both
commands, plus the name-sorted attempt order. A comment at the disclosure site records the
invariant.

- Tests that failed pre-fix: `test_disable_competing_order_does_not_depend_on_the_listing_order`
  (same two units in both input orders must yield identical argv),
  `test_disable_competing_issues_one_disable_now_call_per_user_scope_entry` (updated to the
  sorted order — `.service` sorts before `.timer`), and
  `test_apply_two_user_scope_competitors_partial_failure_is_never_reported_as_complete`.
  `test_disable_competing_splits_deterministically_when_one_entry_fails` is a pin, not a
  discriminator (a one-element tuple has no order to get wrong).

### LOW-02 — a relative `--tmpdir` is refused before anything canonicalizes it
**Commit:** `afaa17a`
**Files:** `scripts/lib/prune-tmp-common.sh`, `scripts/prune-tmp-linux.sh`,
`scripts/prune-user-tmpdir.sh`, `tests/test_prune_tmp_linux_sh.py`,
`tests/test_prune_user_tmpdir_sh.py`

WR-09 made `_prune_common_refuse_broad_path` canonicalize both sides before comparing, but a
RELATIVE root canonicalizes against whatever cwd the process happens to have. `.` was therefore
refused only when that cwd was itself on the refusal list (typically `$HOME`); `./tmp` or a bare
`tmp` resolved somewhere the list does not name, so BOTH wrappers accepted it, exited 0, and ran
a real prune pass over the current directory's depth-1 matches. Reproduced by the new tests
before the fix.

New `_prune_common_require_absolute` in the shared library, called from both wrappers
immediately after the non-empty check — **before** the trailing-slash strip and before the
canonicalizing guard, which is what makes the refusal independent of the refusal list rather
than another entry on it. Message and non-zero exit match the file's existing `error: ` style.

Placing it before the strip keeps each wrapper's pinned `--tmpdir /` behaviour byte-identical:
`/` is absolute, so it still reaches the Linux wrapper's broad-path refusal and the macOS
wrapper's strip-to-empty / "not a directory" quirk
(`test_refuses_root_via_not_a_directory_quirk`), and still deletes nothing.

- Tests: `test_refuses_a_relative_tmpdir[. | ./tmp | tmp]` in BOTH wrapper suites, run with the
  subprocess cwd set to the scratch HOME so a relative root genuinely resolves inside it. All
  six failed pre-fix — the `./tmp` and `tmp` cases by exiting 0 with a real prune pass. Both
  `_run` helpers gained an optional `cwd` keyword.

### LOW-01 — `peek()` docstring
**Commit:** `5d1dadb` · **File:** `installer/systemd_daemon.py`

`_ProbeCache.peek`'s docstring now states that `invalidate()` marks the stored answer stale
WITHOUT discarding it, so `peek()` still returns the last known value after an invalidate, and
that `None` means "this cache has never been probed", not "the system state is unknown". That
distinction is what keeps a Textual render path (peek-only, D-01e) drawing something across an
invalidate instead of flickering to "unknown"; D-01e recorded it, the code a caller reads did
not. Docstring only, no behaviour change — the existing
`invalidate()`/`peek()` tests already pin the behaviour being described.

## Deferred (second lane)

### MEDIUM-02 — `"decision not recorded:"` vs the shell scripts' `error: ` prefix
`installer/policy.py` formats a failed durable-decision write as
`warning="decision not recorded: {exc}"`, while `scripts/lib/prune-tmp-common.sh` uses
`error: %s` for its own validation failures. The finding is that a user reading both in sequence
could confuse a policy-layer failure with a script-layer one.

Deferred as cosmetic, and the reviewer itself rated it "Low priority — the distinction is
already clear from the policy result's structure". Concretely: the two never share a channel.
A `PolicyResult.warning` is rendered by the TUI/CLI inside that policy's own row or summary and
carries no `error: ` prefix at all; the shell `error: ` lines go to the wrapper script's stderr.
The proposed rewording (`"failed to record policy decision:"`) would churn every pinned
warning-string assertion across `test_policy_linux_daemon.py` for no behavioural gain, which is
more than an ambiguity that the surrounding structure already resolves justifies inside a fix
pass. Recorded here so a future wording sweep can pick it up deliberately.
