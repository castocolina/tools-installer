# Phase 15.7 Plan 06: Disk-pressure finding in both Doctors and live temp usage on the cleanup row Summary

D-03's disk-pressure finding now appears in `make doctor` and on the Doctor screen. Both read one probe per route, and that probe shares the route's single `TimerStateCache`. The background-cleanup Policies row now shows live temp-directory usage. It uses a non-blocking `peek()` read, so moving through the rows never starts a systemd query.

### Task 1 (750d68b)
- Added `render.render_disk_pressure`, which prints nothing when the guidance list is empty.
- `run_doctor` gained `disk_pressure=None`, guarded with `(OSError, ValueError)`. With no probe it prints the same bytes as before.
- `setup.py::_disk_pressure_probe(platform, *, timer_cache)` is the only construction point, and `timer_cache` is a required keyword. The probe reads the launchd plist on macOS, returns UNAVAILABLE for a None cache on Linux, and otherwise reads the injected cache. Its `blocking` keyword chooses between `read()` and `peek()`.
- `_build_app` resolves the cache once. The three `run_doctor` call sites and `_run_interactive_wizard` each build one cache and one probe. The interactive route passes the same objects to `_execute_inputs` and `_build_app`.
- Added `PolicyInputs.disk_pressure` in this task rather than Task 2, because `_build_app` already writes it.

### Task 2 (d718282)
- Tightened `PolicyInputs.disk_pressure` from `Callable[..., Any]` to the named `DiskPressureProbe` alias.
- `DoctorScreen` takes `disk_pressure` and stores it as a public attribute, so identity can be tested. It is read only in `_refresh_guidance`, on mount and on every entry, and the result goes after the guard items and before the pnpm-globals items.
- `_tui_guidance` rewrites the inactive-daemon next step to "Open the Policies view and turn on the Background tmpdir cleanup row; …". That branch comes before the generic `Run `make setup`` branch, with a comment saying the order matters.
- `UnifiedApp` passes `policies.disk_pressure` into `DoctorScreen`. `UnifiedApp` has no new parameter, and a test pins its signature with `inspect.signature`.
- New tests cover:
  - the default None
  - no change without a probe
  - at-risk and healthy readings
  - the item order
  - the rewrite, including that it never gives pnpm advice
  - no rewrite for UNAVAILABLE
  - a fresh read on re-entry, always blocking
  - OSError and ValueError survival
  - the identity hand-off
  - the pinned signature
  - `_build_app` binding the caller's exact probe without building another

### Task 3 (9ca583a)
- `PoliciesScreen._temp_usage_line` runs for `daemon:` rows, found through the existing `_has_daemon_id` rather than hard-coded ids. It calls the probe with `blocking=False` inside the same `(OSError, ValueError)` guard as the other detail reads.
- The line shows temp-directory usage to one decimal place. Only when the temp mount is unreadable does it fall back to root free space, labelled as the root filesystem. If neither mount was measured, there is no line.
- The docstring explains the choices: mount reads stay synchronous, the daemon half uses `peek()`, caching alone was not enough, and a worker would not help.
- New tests cover:
  - Linux and macOS rows
  - no line on non-daemon rows
  - no line without a probe
  - survival when the probe fails
  - the macOS temp figure against a different root figure
  - the labelled root fallback and the no-line case
  - every row-highlight call being `blocking=False`
  - zero `is-active` queries across a warm, far-expired and just-invalidated memo
  - a truly cold cache still showing the temp figure
- A setup-level test checks that the production `_DiskProbe(blocking=False)` makes zero queries in all four cache states, and that the default blocking call re-probes a stale memo once.
- Moved the source todo from pending to completed with `git mv`.
