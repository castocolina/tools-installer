### CRITICAL-01: Partial daemon unit-file deletion leaves conflicting systemd state
- **File**: installer/policy.py:1071-1080
- **Failure scenario**: During `_remove()`, if `systemd_daemon.remove_units()` fails to unlink the service file (permission denied, I/O error, etc.) before reaching the timer file, the exception stops the loop. The timer file is never deleted. The rollback then calls `systemd_daemon.bootstrap(unit_dir)`, which re-registers the BROKEN, partially-deleted state (timer exists, service missing). Subsequent `systemctl --user is-active` queries then fail or return incorrect state because the timer unit file references a service file that no longer exists on disk.

- **Evidence**: 
  - `installer/systemd_daemon.py:333-336`: `remove_units()` uses a `for` loop with `path.unlink(missing_ok=True)`. When an unlink raises an OSError (not `FileNotFoundError`), the loop stops immediately without attempting to delete remaining files.
  - `installer/policy.py:1076-1080`: The catch block catches the OSError from partial deletion and calls `systemd_daemon.bootstrap()` to re-register, leaving the systemd manager holding a now-inconsistent unit definition.
  - `tests/test_policy_linux_daemon.py::test_remove_unit_file_unlink_failure_rebootstraps_and_reraises`: The test verifies this exact scenario (service unlink fails, timer still exists), but the assertion `assert timer_path.exists()  # the loop never reached the timer unlink` accepts the broken state rather than flagging it as an invariant violation.

- **Suggested fix**: Change `remove_units()` to collect OSErrors from both unlink attempts and raise only AFTER both have been attempted. The callable signature changes from `-> None` to `-> tuple[OSError | None, OSError | None]` or similar. Alternatively, make `remove_units()` always delete in a consistent two-phase approach: first unlink both with `missing_ok=False`, catching individual errors, then re-raise a combined exception only after both complete. The rollback in `_remove()` must never call `bootstrap()` when the unit files are in an unknown partial state.

### HIGH-01: Doctor path cache read may block Textual UI thread
- **File**: installer/diskusage.py (via policy.py and setup.py), installer/systemd_daemon.py:417-465 (TimerStateCache)
- **Failure scenario**: The `_DiskProbe` in setup.py calls `cache.read()` by default when `blocking=True`. On a system with a wedged or slow `systemctl`, this can block for up to `SYSTEMCTL_QUERY_TIMEOUT` (5 seconds) during a Doctor screen render pass (via `_disk_pressure_probe(blocking=False)` call from render). Although render calls `peek()`, not `read()`, an upstream caller (e.g., `policy.is_active()`) might call `read()` during policy construction or evaluation without the `blocking=False` guard, freezing the Textual loop.

- **Evidence**: 
  - `installer/systemd_daemon.py:121`: `SYSTEMCTL_QUERY_TIMEOUT = 5.0` is generous headroom "without ever approaching the point a synchronous caller would consider the app looks frozen", but this is calibrated for a ONE-OFF call on the `make doctor` CLI path, not on the event loop.
  - `setup.py:353-371 (_DiskProbe)`: The probe supports `blocking=True/False`, but only the render path uses `blocking=False`. The policy construction at `setup.py:977` calls `cache.read()` unconditionally during construction, outside any explicit blocking guard.
  - D-01c in `15.7-CONTEXT.md` explicitly states "peek vs read" is load-bearing; D-01e states TimerStateCache sharing requires the construction-time `read()` to warm the cache "before the first TUI frame", but this phrasing assumes a one-off warmup, not repeated reads on the UI loop.

- **Suggested fix**: Verify that `cache.read()` is called ONLY once at composition time (setup.py's `_build_app` → `_timer_state_cache` path), never during policy `apply()`, `remove()`, or `is_active()` evaluation on the render loop. The `is_active()` closure on line 1110 (`return cache.read() is DaemonState.ACTIVE`) MUST be changed to `cache.peek()` with a fallback to `UNAVAILABLE`. Alternatively, wrap all `cache.read()` calls in a bounded timeout that halts rather than hangs, or move all blocking reads to an async worker thread before the TUI frame renders.

### HIGH-02: `disable_competing()` accepts iterable but `parse_unit_files()` returns tuple in different order
- **File**: installer/systemd_daemon.py:648-682 (disable_competing), 555-581 (parse_unit_files)
- **Failure scenario**: When `_detect_in_scope()` finds multiple competing units in one scope, `parse_unit_files()` returns them in the order they appear in the `systemctl list-unit-files` output (which is not guaranteed to be stable across systemd versions or configurations). `disable_competing()` then disables them in whatever order the iterable yields. If a disable call partway through fails (e.g., permission denied on a subsequent unit), the failed units remain running while preceding ones are already disabled. A later policy apply that re-detects competitors never knows which were disabled before because `disable_competing()` collects failures but the exception context is lost.

- **Evidence**: 
  - `installer/systemd_daemon.py:593-623`: `_detect_in_scope()` appends results to a list in parse order, which depends on `systemctl list-unit-files` output iteration.
  - `installer/systemd_daemon.py:676-681`: The loop disables each unit independently, collecting failures into a separate list, but if unit 1 succeeds and unit 2 fails, there is no rollback or re-enable of unit 1.
  - No test currently validates partial disable-failure idempotency (T-15.7-14 mentions this but no test asserts recovery behavior across multiple disable attempts).

- **Suggested fix**: Sort the units deterministically before disabling (e.g., alphabetically by name) so every run attempts disables in the same order. This reduces variability but does NOT fix the asymmetry—if disable fails partway, document this clearly as a known limitation: the policy apply will proceed with a partial takeover disclosed to the user. Optionally, add a pre-disable probe to validate which units are actually running before attempting disable, and skip already-disabled ones.

### MEDIUM-01: XDG_CONFIG_HOME relative path handling differs between systemd_daemon and env_redirect
- **File**: installer/systemd_daemon.py:130-143 (user_unit_dir), installer/env_redirect.py:78-86 (environment_d_dir)
- **Failure scenario**: Both functions ignore a relative `XDG_CONFIG_HOME` per the XDG spec, but the resulting paths diverge slightly. `systemd_daemon.user_unit_dir()` constructs `$XDG_CONFIG_HOME/systemd/user`, while `env_redirect.environment_d_dir()` constructs `$XDG_CONFIG_HOME/environment.d`. If a future refactor extracts these path computations to a shared helper, the two would collide if both are called with the same (relative) env var in the same session.

- **Evidence**: 
  - Lines 141-143 vs 84-86: Both use identical logic (`Path(raw) if raw and Path(raw).is_absolute() else home / ".config"`), but construct different sub-paths afterward.
  - No test currently exercises a relative `XDG_CONFIG_HOME` in both functions in one session to expose the divergence.

- **Suggested fix**: Extract the XDG base-directory resolution into a single shared function `_xdg_config_base(home, environ)` and call it from both `user_unit_dir()` and `environment_d_dir()`. This ensures future changes to the relative-path handling apply consistently. Low priority—current code is correct in isolation; this prevents a latent refactor bug.

### MEDIUM-02: `decision_not_recorded` error message uses generic "error: " prefix conflicting with other scripts
- **File**: installer/policy.py:1046, 1099
- **Failure scenario**: When `_record_decided_durably()` fails with `OSError`, the policy result includes `warning="decision not recorded: {exc}"`. The `_prune_common` shell library and wrapper scripts use the same `error: ` prefix for exit-code failures. If a user reads a PolicyResult warning and a wrapped script error in sequence, the wording is ambiguous—"decision not recorded: permission denied" could be confused with a script-level filesystem error.

- **Evidence**: 
  - `installer/policy.py:1046-1047` and `1099-1100`: Both catch OSError and format as `f"decision not recorded: {exc}"`.
  - `scripts/lib/prune-tmp-common.sh:38, 62, 78`: All use `printf 'error: %s; ...` for validation failures.
  - No deduplication or alignment in error wording between the two layers.

- **Suggested fix**: Change the warning text to clarify context, e.g., `"failed to record policy decision: {exc}"` or `"policy state-file write failed: {exc}"`, to distinguish policy-layer failures from script-layer ones. Low priority—the distinction is already clear from the policy result's structure; this is a wording hygiene issue.

### LOW-01: TimerStateCache.peek() documentation under-specifies failure recovery
- **File**: installer/systemd_daemon.py:455-458
- **Failure scenario**: The docstring for `peek()` says "The last stored answer whatever its age, or None if never read." But if `read()` was called once and then `invalidate()` is called, `peek()` still returns the old answer, not None. A caller unfamiliar with the distinction might assume `peek()` returning None means "system state is truly unknown" when it actually means "this cache instance has literally never been probed."

- **Evidence**: 
  - `installer/systemd_daemon.py:460-464`: `invalidate()` sets `self._at = None` but leaves `self._value` unchanged, so `peek()` still returns the stale value.
  - The docstring does not mention `invalidate()`'s effect on `peek()`.
  - D-01e mentions "peek() can still report the last known answer instead of falling back to None" but this is in the decision doc, not in the code docstring.

- **Suggested fix**: Expand the `peek()` docstring: `"The last stored answer whatever its age, or None if this cache has never been probed. Note: invalidate() marks the answer stale without discarding it; peek() still returns the last known value even after invalidation."` This clarifies that a None from peek means "never probed", while a non-None from peek after invalidation means "cached but possibly stale".

### LOW-02: Shell script cleanup flags allow dangerous broad paths with `--tmpdir "`
- **File**: scripts/prune-tmp-linux.sh:34, scripts/prune-user-tmpdir.sh
- **Failure scenario**: The `--tmpdir` flag accepts any path, including relative paths like `""` (which would read as current directory under `_prune_common_strip_trailing_slash`) or edge cases like `"."`. The refusal guard in `scripts/lib/prune-tmp-common.sh:81` explicitly checks against `"/"`, `/var`, `/private/var`, and `"$HOME"`, but does not prevent `""` (empty string, caught earlier) or reject `.` or other relative paths. A wrapper invocation with `--tmpdir "."` would prune the current directory's depth-1 contents matching the pattern.

- **Evidence**: 
  - `scripts/lib/prune-tmp-common.sh:35-41`: The `_prune_common_require_nonempty` check happens first, rejecting empty but not relative paths like `.` or `./tmp`.
  - `scripts/lib/prune-tmp-common.sh:72-82`: The refusal guard only checks the absolute, stripped path against a fixed allowlist; it does not validate `Path.is_absolute()`.
  - `scripts/prune-tmp-linux.sh:75-83`: The Linux script special-cases `/` explicitly before the refusal guard, but does not special-case or reject `.`.

- **Suggested fix**: Add a check in `_prune_common_require_directory` or before the refusal guard to ensure the path is absolute: `if [[ "$root" != /* ]]; then printf 'error: tmpdir must be absolute: %s\n' "$root" >&2; exit 1; fi`. This prevents any relative-path injection regardless of the refusal list.
