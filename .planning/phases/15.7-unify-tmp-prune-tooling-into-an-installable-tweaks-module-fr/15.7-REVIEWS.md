# Plan Review

## 15.7-01

### Summary

This is a strong tracer plan: it identifies the existing composition root and mirrors the tested macOS policy structure. However, its Linux activity model and rollback semantics are not yet sufficient to guarantee that the reported daemon state matches systemd's actual state.

### Strengths

- Reuses the existing construction point and policy wiring: `setup.py:340`, `setup.py:569`, and `setup.py:989`.
- Correctly mirrors the existing validate-before-write and transactional apply pattern in `installer/daemon.py:126` and `installer/policy.py:600`.
- The injected `Runner`/`OutputRunner` seams match `installer/run.py:17` and `installer/run.py:20`.
- Runtime-tests the new shell script instead of trusting only a fake systemd runner (`15.7-01-PLAN.md:361`).

### Concerns

- **HIGH** — `is_active()` is planned as `units_present(unit_dir)`, not actual systemd state (`15.7-01-PLAN.md:290`). Plan 15.7-06 then uses that value for Doctor (`15.7-06-PLAN.md:186`). A disabled, stopped, failed, or manually-unloaded timer whose files remain present will be reported as active, suppressing the required warning. The existing macOS presence check at `installer/daemon.py:541` is not sufficient evidence for Linux systemd.

- **HIGH** — `bootout()` swallows every `CommandError` when the timer file is absent (`15.7-01-PLAN.md:249`), whereas the existing macOS implementation only swallows the specific "already absent" return code (`installer/daemon.py:262`). A real systemd failure could therefore be reported as successful removal.

- **MEDIUM** — The rollback description removes unit files after an early failure but does not explicitly issue a compensating `daemon-reload` (`15.7-01-PLAN.md:378`). Since the apply path already reloads systemd before enabling (`15.7-01-PLAN.md:246`), the user manager can retain stale unit definitions after rollback.

- **MEDIUM** — The plan adds a separate Linux cleanup script despite the source todo explicitly asking for one reusable cross-platform module and warning against side-by-side copied logic (`.planning/todos/pending/...:57`, `:96`). The proposed `scripts/prune-tmp-linux.sh` plus unchanged macOS script (`15.7-01-PLAN.md:263`) leaves the core matching/deletion logic duplicated.

### Suggestions

- Define Linux activity as a bounded systemd probe, preferably cached outside the render loop.
- Distinguish "already absent" from real `systemctl` failures.
- Reload systemd after every rollback that changes unit files.
- Extract shared filename matching, safety checks, and summary output into one reusable implementation.

### Risk Assessment

**HIGH.** The happy path is well covered, but the planned active-state predicate and removal rollback can produce false "healthy/off" reports while systemd still has stale or active state.

## 15.7-02

### Summary

This is a well-scoped pure-layer plan with good threshold-boundary coverage and an appropriate extension of the existing `Guidance` model. Its main weakness is an internally contradictory "total probe" contract.

### Strengths

- Correctly preserves the hand-written `Guidance.__init__` contract at `installer/guidance.py:16` and the `dataclasses.replace` path at `installer/wizard_app.py:405`.
- Keeps severity closed and implements emphasis at the render layer, matching `installer/render.py:180`.
- Tests exact threshold boundaries, malformed probe data, and independent root/tmp failures (`15.7-02-PLAN.md:104`).
- Defers end-to-end wiring to the composition plan instead of duplicating setup concerns (`15.7-02-PLAN.md:35`).

### Concerns

- **MEDIUM** — The plan says `probe_disk_pressure` "never raises" (`15.7-02-PLAN.md:29`, `:60`), but explicitly requires `RuntimeError` to propagate (`15.7-02-PLAN.md:117`). The implementation contract and the stated must-have cannot both be true.

- **LOW** — The plan adds extra behavior—ordinary warnings when the daemon is already running—which is reasonable, but it changes Doctor output beyond the original conjunction requirement (`15.7-02-PLAN.md:51`). This should remain clearly documented as intentional compatibility behavior.

### Suggestions

- Replace "never raises" with "total over filesystem/probe-conversion failures; programming errors propagate."
- Name the exact caught exception set in the public contract and reuse that wording in plans 05 and 06.

### Risk Assessment

**LOW.** The implementation is isolated and testable; the main issue is contract clarity rather than architecture.

## 15.7-03

### Summary

The plan responsibly recognizes the privilege-boundary problem and prevents accidental system-scope mutation. It nevertheless leaves the actual host's confirmed system-scope competitor running, and its detection model treats unit-file presence as active state.

### Strengths

- Correctly separates read-only detection from mutation and uses the existing runner seam (`installer/run.py:17`, `installer/run.py:20`).
- Structurally refuses system-scope units before issuing mutation commands (`15.7-03-PLAN.md:214`).
- Preserves foreign unit files rather than deleting artifacts it does not own (`15.7-03-PLAN.md:73`).
- Registers this daemon before attempting takeover, avoiding a failure state with no cleanup mechanism (`15.7-03-PLAN.md:32`).

### Concerns

- **HIGH** — The real system-scope competitor remains enabled and can run alongside the new daemon (`15.7-03-PLAN.md:63`). This conflicts with the original locked decision to "disable/remove" the competitor and "never" run two mechanisms (`15.7-CONTEXT.md:41`). The roadmap records the narrowed D-02a interpretation, but this is still a material reduction of the phase's core outcome.

- **MEDIUM** — `list-unit-files` output is parsed only for unit names (`15.7-03-PLAN.md:201`); enablement and active state are ignored. A disabled stale unit file will be treated as a live competitor, producing unnecessary takeover or warning behavior.

- **MEDIUM** — Detection uses `OutputRunner` without specifying a timeout (`15.7-03-PLAN.md:206`). `installer/run.py:70` supports timeout-bounded queries, but the planned callable type does not expose it. A systemd query that hangs runs inside the policy-apply path.

- **LOW** — The system-scope warning names both service and timer but recommends only `sudo systemctl disable --now cleanup-bun-tmp-cache.timer` (`15.7-03-PLAN.md:227`). That disables the timer, but does not explicitly stop an already-running service unit.

### Suggestions

- Make the narrowed system-scope behavior an explicit user-approved requirements change, not only a plan-level reinterpretation.
- Query `is-enabled`/`is-active`, or parse the state columns and test enabled/active combinations.
- Add a timeout-bound output adapter.
- Make the warning command accurately cover both the timer and service lifecycle.

### Risk Assessment

**HIGH.** The plan is honest about the limitation, but the limitation affects the central "replace competing cleanup" goal on the actual target host.

## 15.7-04

### Summary

This plan has strong ownership, atomic-write, and platform-grammar discipline. The main completeness gap is that it does not lock the concrete Bun cache target from the source todo, allowing a superficially valid but ineffective redirect.

### Strengths

- Correctly composes existing atomic writes and marker editing: `installer/atomic.py:34` and `installer/shellrc.py:114`.
- Couples "applied" state to ownership, matching the existing wrapper ownership rule at `installer/daemon.py:336`.
- Explicitly preserves the required `export`/bare-assignment asymmetry (`15.7-04-PLAN.md:119`).
- Tests foreign configuration files without deleting them and verifies precedence (`15.7-04-PLAN.md:152`).

### Concerns

- **MEDIUM** — The registry test only requires the target to be somewhere beneath the user's home (`15.7-04-PLAN.md:97`). The source todo specifies the concrete working target `~/.cache/bun/transpiler-cache` (`.planning/todos/pending/...:35`). A different home-local directory could pass all planned tests while not matching the known Bun configuration.

- **MEDIUM** — The redirect only helps processes that inherit the environment variable; the source problem explicitly says some Bun invocations do not inherit it (`.planning/todos/pending/...:17`). The plan does not require the UI or Doctor wording to explain that the daemon remains the fallback for those invocations.

### Suggestions

- Assert the exact target path `~/.cache/bun/transpiler-cache`, not merely "under HOME."
- Add copy explaining that the redirect is preventive but not universal, and that the cleanup daemon remains necessary.

### Risk Assessment

**MEDIUM.** The mechanism is sound, but the first real Bun case is not pinned tightly enough to the known working configuration.

## 15.7-05

### Summary

This plan addresses the most important composition and teardown seams, especially ownership-specific markers and required uninstall arguments. Its largest risk is that the warning sink can race with the background worker or be skipped on an aborted wizard.

### Strengths

- Correctly identifies the existing hard-coded macOS marker calls in `installer/app.py:443` and `installer/app.py:495`.
- Makes `extra_policies` required at composition-root entry points while keeping lower-level defaults, matching the existing rationale at `installer/app.py:401`.
- Preserves the shared preview/sweep object invariant already documented in `installer/uninstall.py:398`.
- Correctly routes the cache redirect through the same Policy removal closure rather than duplicating teardown logic (`installer/uninstall.py:483`).

### Concerns

- **HIGH** — The warning sink is appended after the Textual app exits, but the daemon default runs in a background worker (`installer/wizard_app.py:2065`, `:2085`). `app.run()` can return before that worker has appended its warning. The current setup path immediately branches after `app.run()` (`setup.py:884`), and the plan does not specify synchronization or a shutdown handoff. The claimed guarantee that warnings "reach the user" (`15.7-05-PLAN.md:76`) is therefore not established.

- **MEDIUM** — The warning can also be skipped if the wizard exits through the existing `summary is None` branch at `setup.py:885`. The plan says warnings print after `app.run()` (`15.7-05-PLAN.md:186`), but does not require printing before the abort return.

- **MEDIUM** — The dependency manifest omits plan `15.7-03` even though this plan directly consumes its competing-mechanism warning behavior (`15.7-05-PLAN.md:6`, `:76`). Wave ordering may hide this, but the dependency declaration is incomplete.

- **MEDIUM** — The must-have claiming macOS behavior is unchanged except uninstall copy (`15.7-05-PLAN.md:36`) conflicts with the same plan adding a new cache-redirect Policy row on macOS (`15.7-05-PLAN.md:29`). The acceptance criterion is internally inconsistent.

### Suggestions

- Deliver warnings through the existing Textual completion message or explicitly await/join the worker before returning.
- Print queued warnings before the `summary is None` early return.
- Add `15.7-03` to `depends_on`.
- Rewrite the macOS criterion to say existing daemon behavior remains unchanged while the new redirect row is added.

### Risk Assessment

**HIGH.** The teardown design is strong, but losing a warning about an unmanaged competing daemon undermines the safety disclosure that justifies the narrowed takeover behavior.

## 15.7-06

### Summary

This plan has a good named seam for sharing disk-pressure data through `PolicyInputs` and explicitly accounts for the existing Doctor call sites. However, its "one closure built once" requirement is not reconciled with the current call order, and its macOS usage display does not actually measure TMPDIR usage.

### Strengths

- Uses the existing `PolicyInputs` handoff point (`installer/wizard_app.py:113`) and the existing `UnifiedApp` construction block (`installer/wizard_app.py:2017`).
- Preserves the current shared render path: the TUI already calls `guidance_text` at `installer/wizard_app.py:341`.
- Explicitly names all three current CLI `run_doctor` call sites: `setup.py:842`, `setup.py:919`, and `setup.py:1019`.
- Correctly recognizes that row highlighting calls `_policy_detail` synchronously on every move (`installer/wizard_app.py:1547`).

### Concerns

- **HIGH** — The requirement that all Doctor routes and `PolicyInputs` receive the same closure is under-specified and conflicts with current construction order. `_execute_inputs()` is created before `_build_app()` in `setup.py:873`, while its `verify()` closure is defined internally at `setup.py:816`. The plan requires one closure and identity assertions (`15.7-06-PLAN.md:182`, `:245`) but does not specify where that closure is constructed and passed to both call paths.

- **MEDIUM** — The macOS fallback reports root free percentage rather than TMPDIR usage (`15.7-06-PLAN.md:318`, `:341`). The source todo explicitly asks for "current tmp/TMPDIR usage %" (`.planning/todos/pending/...:79`). This is an honest measurement, but it does not satisfy the stated UI requirement.

- **MEDIUM** — When no systemd policy exists, the plan forces `daemon_active=False` and still reports an inactive-daemon red finding (`15.7-06-PLAN.md:155`). On a host where `systemctl` is unavailable, the proposed "enable through setup" next step cannot work. The UI should distinguish "unsupported/unavailable daemon" from "daemon disabled."

- **MEDIUM** — The synchronous row-highlight probe is safe only while `is_active()` is a filesystem check. If plan 15.7-01 is corrected to query systemd runtime state, the same closure will perform subprocess work on the Textual event loop (`15.7-06-PLAN.md:329`, `installer/wizard_app.py:1547`).

### Suggestions

- Construct the probe closure in `_run_interactive_wizard`, pass it explicitly into both `_execute_inputs` and `_build_app`, and use the same pattern for noninteractive routes.
- Probe `TMPDIR` on macOS for display while keeping the Linux-only threshold logic.
- Add an "unavailable" state or suppress the red warning when systemd is not supported.
- Cache or asynchronously refresh runtime systemd state before using it on row highlighting.

### Risk Assessment

**HIGH.** The Doctor integration is conceptually clear, but the closure plumbing and macOS metric currently do not prove the requested behavior.

## Cross-plan comparison

- The biggest shared correctness issue is the mismatch between artifact presence and real daemon state: `15.7-01-PLAN.md:290` feeds `15.7-06-PLAN.md:186`, while the requirement is about an inactive service/timer.
- The plan set is unusually strong on ownership and rollback intent, grounded in `installer/policy.py:525` and `installer/uninstall.py:147`, but several rollback paths do not explicitly account for systemd manager reload state.
- Plan 15.7-03's narrowed system-scope behavior is reflected in the roadmap (`.planning/ROADMAP.md:541`) but still conflicts with the original locked context (`15.7-CONTEXT.md:42`). That decision should be formally reconciled before implementation.
- Plan 15.7-05 should directly depend on 15.7-03, and plan 15.7-06 should make its shared-closure construction concrete before execution.

## Overall Risk Assessment

**HIGH.** The plans are detailed and test-conscious, but the remaining issues affect the phase's core guarantees: truthful daemon status, reliable teardown, competing-daemon handling, warning delivery, and the exact live-usage metric. The plans should be revised before execution, especially around runtime systemd state, worker synchronization, and the shared Doctor closure.
