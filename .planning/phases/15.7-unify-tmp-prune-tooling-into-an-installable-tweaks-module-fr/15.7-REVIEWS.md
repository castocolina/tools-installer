# Cross-AI Plan Review — Phase 15.7

## Codex Review

## 15.7-01

### Summary

The tracer has a strong reuse strategy and correctly mirrors the existing daemon transaction pattern, but it introduces a major Linux behavior change without fully updating composition-root tests or deciding whether Linux should be auto-enabled.

### Strengths

- Correctly reuses the existing rollback structure in `installer/policy.py:581-621`, including cleanup of partially-created wrappers and logs.
- Reuses ownership-checked wrapper installation from `installer/daemon.py:301-344`.
- Preserves the existing log contract: `last_run_summary()` requires `===` blocks and `deleted: N` lines (`installer/daemon.py:417-454`).
- Extending `_build_daemon_policy` preserves the existing shared construction point at `setup.py:340-383`.

### Concerns

- **HIGH:** The plan changes Linux from "no daemon" to a real policy, but existing tests explicitly assert the opposite at `tests/test_setup.py:659-677`. `tests/test_setup.py` is absent from the plan's modified-file list.
- **HIGH:** Returning a Linux policy causes the existing auto-default path to apply it during normal interactive setup: `setup.py:744-752` and `setup.py:871-883`. The plan does not explicitly decide whether Linux cleanup is opt-in or automatically enabled.
- **MEDIUM:** The new shell cleanup script is not runtime-tested. The fake Runner only records `systemctl`; it never validates the regex, age filter, broad-path refusal, or deletion behavior described in `scripts/prune-user-tmpdir.sh:48-80`.
- **MEDIUM:** `bootout()` skips `systemctl disable --now` when the timer file is absent. A deleted or partially-corrupted unit file could leave an already-loaded timer active. The existing macOS backend attempts bootout independently of plist presence (`installer/daemon.py:262-279`).
- **LOW:** `Persistent=true` is specified for a monotonic timer (`OnBootSec`/`OnUnitActiveSec`); it does not provide calendar-style catch-up semantics and may mislead future maintainers.

### Suggestions

- Add `tests/test_setup.py` to the plan and update the Linux-inert assertions.
- Explicitly choose and test Linux auto-default behavior.
- Add shell-level fixture tests for dry-run/apply, age boundaries, exact filename matching, and broad-path refusal.
- Make teardown robust to partial state, or document and test the chosen file-presence invariant.

### Risk Assessment

**HIGH.** The implementation shape is sound, but the default behavior and existing composition tests are not fully reconciled.

## 15.7-02

### Summary

This is a well-isolated pure-layer plan. The custom `Guidance` constructor and shared renderer are correctly identified as the sensitive points, though the plan depends on later integration work that is not sufficiently specified here.

### Strengths

- Correctly accounts for the hand-written `Guidance.__init__`; `dataclasses.replace()` would otherwise fail when adding a field (`installer/guidance.py:16-27`).
- Avoids expanding the closed `Severity` enum and uses the existing shared style path (`installer/ui_common.py:27`, `installer/render.py:180-190`).
- Keeps disk probing injectable and separate from guidance generation, matching the project's pure-layer pattern.
- Covers exact threshold boundaries and unreadable mounts.

### Concerns

- **MEDIUM:** The plan's direct tests do not prove that `make doctor` or `DoctorScreen` actually receives and renders the new guidance. Current CLI rendering only renders `doctor_guidance(report)` through `render_doctor()` (`installer/render.py:193-196`); later plan 06 must explicitly append disk guidance.
- **MEDIUM:** The "ordinary warning while the daemon is active" is an additional behavior beyond the core red inactive-daemon requirement. It should be explicitly confirmed as intended product behavior.
- **LOW:** The probe handles `OSError` and zero totals, but the composition plan later catches `ValueError` too. The error contract should be made consistent and tested at the layer where the probe is called.

### Suggestions

- Add an integration assertion for the final `run_doctor()` output once plan 06 is written.
- Document whether low space with an active daemon is intentionally reported or should remain silent.
- Define one total probe contract, preferably returning an unknown report rather than requiring every caller to add different exception guards.

### Risk Assessment

**MEDIUM.** The pure design is good; the main risk is incomplete integration with the existing Doctor rendering paths.

## 15.7-03

### Summary

The read-only parser and injected command seams are appropriate, but this plan materially narrows the locked D-02 behavior. It also leaves failure cases where two cleanup mechanisms can continue running, contradicting the plan's own "never side by side" claim.

### Strengths

- Uses the existing `OutputRunner` and `Runner` seams (`installer/run.py:17-20`) instead of embedding subprocess calls.
- Whole-column matching is appropriate for untrusted `systemctl list-unit-files` output.
- Structurally refusing system-scope mutation is safer than accidentally introducing privilege escalation.
- Performing takeover after successful registration avoids leaving the machine with no cleanup mechanism.

### Concerns

- **HIGH:** System-scope units are warned about but not disabled or removed. That is a deviation from the locked D-02 intent to detect and replace the existing mechanism; the plan should not call this "never two cleanup jobs" because the system-scope job remains active.
- **HIGH:** A user-scope disable failure also leaves both mechanisms active. The plan reports a warning but does not restore the invariant claimed by its `must_haves`.
- **HIGH:** The plan claims a machine without systemd "applies exactly as before," but plan 01 constructs a Linux policy for every supported distro. Existing construction is explicitly macOS-only at `setup.py:340-359`, and there is no systemd availability gate in `installer/platform.py:35-49`.
- **MEDIUM:** After this plan adds `read_output` with a real default, plan 01's setup-level tests will invoke the host's real `systemctl` unless they are updated. The plan only injects `read_output` directly into policy tests, not through `_build_daemon_policy`.
- **MEDIUM:** "Disable/remove" is implemented as disable-only for user units. The unit files remain available for manual restart.
- **LOW:** The warning command disables the timer but does not remove the service/unit files, so wording that it "removes" the mechanism is imprecise.

### Suggestions

- Treat D-02a as an explicit requirements change and update `15.7-CONTEXT.md`/roadmap artifacts, or obtain approval before implementation.
- Define the invariant for takeover failure: warn-and-accept overlap, rollback this daemon, or require a user-confirmed retry.
- Add a `systemctl` availability gate or an explicit unavailable/inert policy state.
- Thread an injected `read_output` through `_build_daemon_policy` so all tests remain offline and deterministic.
- Decide whether disabling is sufficient or whether user-scope unit files must also be removed.

### Risk Assessment

**HIGH.** The plan is safest from a privilege perspective, but it does not fully satisfy the locked takeover requirement and leaves contradictory runtime states on failure.

## 15.7-04

### Summary

The generalized redirect design is appropriately small and uses existing atomic/marker primitives, but two correctness gaps are significant: the macOS shell form must export the variable, and the applied predicate must agree with ownership checks during removal.

### Strengths

- Uses `apply_block`/`strip_block`, whose idempotent and orphan-safe behavior is established at `installer/shellrc.py:114-147`.
- Uses atomic writes with explicit versus mode-preserving permissions, matching `installer/atomic.py:34-53`.
- Correctly preserves user cache data during removal.
- Avoids expanding the `Tool` schema for a single real redirect target.

### Concerns

- **HIGH:** The plan says `linux_applied` is true when the file assigns the expected variable, but removal refuses a same-named non-owned file. This can produce an "active" policy that cannot remove its artifact. Existing ownership logic consistently couples presence with sentinel ownership (`installer/daemon.py:336-344`).
- **HIGH:** The macOS rc-file form must use `export BUN_RUNTIME_TRANSPILER_CACHE_PATH=...`; a bare assignment in `~/.myshellrc` is not inherited by Bun child processes. Existing shell writers explicitly use `export` (`installer/shellrc.py:108-110`), but the plan does not require it.
- **MEDIUM:** Variable-name validation is incomplete. Rejecting newline, quotes, backslashes, backticks, and `$` does not reject spaces, `=`, `#`, or other invalid assignment syntax. A generalized writer should validate a shell/systemd environment variable name with an identifier pattern.
- **MEDIUM:** The plan relies on filename precedence for competing `environment.d` declarations but does not test the actual generated environment with `systemd-environment-d-generator` or equivalent parser behavior.
- **LOW:** The same XDG path validation question from plan 01 applies: a relative `XDG_CONFIG_HOME` could produce a relative write target.

### Suggestions

- Require the ownership sentinel in `linux_applied`, or make removal return a warning/failure when ownership is lost.
- Specify and test `export` in the macOS block.
- Validate variable names with a strict identifier regex.
- Add a parser-level test for spaces and competing environment files.

### Risk Assessment

**HIGH.** The abstraction is reasonable, but the current specified behavior can silently fail to export Bun's variable or report a non-removable file as active.

## 15.7-05

### Summary

The policy-owned marker closures and shared teardown composition are strong architectural improvements. However, the plan risks silently omitting extra policies from production teardown and leaves existing uninstall copy text macOS-specific after Linux support is added.

### Strengths

- Moving ownership operations into `Policy` closures fits the existing optional callable structure (`installer/policy.py:100-117`).
- It preserves the single-list preview/sweep invariant described in `installer/uninstall.py:398-415` and `installer/uninstall.py:483-514`.
- It correctly addresses the four direct marker-clearing call sites in `installer/app.py:443`, `495`, `553`, and `567`.
- Sharing the same extra policy objects between Policies, interactive uninstall, and CLI uninstall is the right approach.

### Concerns

- **HIGH:** If `extra_policies` is defaulted at the `app.py` composition-root entry points, a missed wiring argument silently skips cache-redirect teardown. The existing code deliberately makes `daemon_policy` required for exactly this reason (`installer/app.py:401-407`, `529-533`).
- **MEDIUM:** The Uninstall screen's environment-row copy remains macOS-specific. `_tweak_entry()` says it unregisters the "background maintenance LaunchAgent" (`installer/wizard_app.py:801-815`), and the removal summary also uses LaunchAgent-specific wording (`installer/wizard_app.py:1276-1293`). The plan only adds Policies detail text, not these user-facing uninstall paths.
- **MEDIUM:** The cache redirect will be represented inside the aggregate "shell tweaks" uninstall row, but the row's detail text does not explain that an environment redirect is also removed. This weakens consent clarity.
- **LOW:** New `Policy` fields should be appended after existing fields to preserve any external positional construction, even though current in-repo calls are mostly keyword-based.

### Suggestions

- Require `extra_policies` at `run_uninstall()` and `perform_uninstall()`; keep defaults only on low-level helpers.
- Update `_tweak_entry()` and `_applied_summary()` for Linux timers and cache redirects.
- Add tests for missed-extra-policy wiring at both CLI and interactive composition roots.
- Add a policy-owned teardown detail layer so the uninstall UI can describe exactly what each extra policy removes.

### Risk Assessment

**MEDIUM-HIGH.** The composition direction is correct, but teardown omissions would leave user-owned configuration behind while reporting a successful uninstall.

## 15.7-06

### Summary

The threshold and UI integration strategy is mostly sound, especially the predicate-based Doctor refresh and shared guidance rewrite. The plan needs a more explicit data-flow design through `UnifiedApp` and all existing `run_doctor()` call sites.

### Strengths

- Reuses the existing Doctor predicate pattern: `DoctorScreen._refresh_guidance()` already re-reads live state at `installer/wizard_app.py:322-334`.
- Correctly places the TUI rewrite before the generic `Run \`make setup\`` branch (`installer/wizard_app.py:405-428`).
- Keeps the disk probe optional, preserving existing callers.
- Uses the existing `PolicyInputs` composition object, which is a natural place to share the probe with Policies detail rendering.

### Concerns

- **HIGH:** The plan does not explicitly specify how the new closure reaches `DoctorScreen`. `UnifiedApp` currently constructs it directly at `installer/wizard_app.py:2019-2027`, while setup constructs `PolicyInputs` separately at `setup.py:651-680`. The plan must state whether `UnifiedApp` gains an optional argument or reads `policies.disk_pressure`.
- **MEDIUM:** All existing CLI call sites need explicit handling: `_execute_inputs.verify()` (`setup.py:840-849`), `_run_doctor()` (`setup.py:919-927`), and `_verify_and_clean()` (`setup.py:1019-1026`). The plan does not list `tests/test_setup.py`, even though those call paths are already tested.
- **MEDIUM:** `run_doctor()` currently renders only `doctor_guidance(report)` through `render_doctor()` (`installer/app.py:277-288`, `installer/render.py:193-196`). The plan should specify whether disk guidance is appended through `guidance_text()` directly or whether `render_doctor()` is extended.
- **MEDIUM:** The Policies detail path runs on row highlight (`installer/wizard_app.py:1547-1553`). A fresh `shutil.disk_usage()` call there is acceptable, but the plan should state whether repeated probing is intentionally synchronous and how failures are handled consistently.
- **LOW:** The `git mv` destination under `.planning/todos/completed/` is not listed in `files_modified`.

### Suggestions

- Add an explicit shared `disk_pressure` field to `PolicyInputs`, then have `UnifiedApp` pass it to both `DoctorScreen` and `PoliciesScreen`.
- Add a setup-level test asserting the closure is present in `run_doctor`, `DoctorScreen`, and `PolicyInputs`.
- Extend `run_doctor()` with a clearly named additional-guidance render path rather than silently printing a second block.
- Include the completed-todo destination in the plan manifest.

### Risk Assessment

**MEDIUM-HIGH.** The pure guidance work is straightforward, but an omitted composition seam would make D-03 appear implemented while only working in isolated unit tests.

## Cross-plan comparison

- The largest cross-plan issue is the interaction between 01 and 03: once detection is added, plan 01's setup-level apply test must inject `read_output`; otherwise tests execute the host's real `systemctl`.
- Plans 01 and 05 implicitly enable Linux cleanup by reusing the existing auto-default path. This should be resolved before implementation.
- Plans 04 and 05 need a shared ownership contract so a foreign replacement cannot be reported as active and then treated as successfully removed.
- Plans 02 and 06 have the right layering, but the final Doctor data flow is under-specified.
- The plans consistently reuse existing seams and atomic writes, but several "must never" guarantees are stronger than the proposed failure behavior.

## Overall risk assessment

**HIGH.**

The phase has a good architectural foundation, but three decisions must be resolved before execution: Linux auto-default behavior, the approved interpretation of system-scope competitor takeover, and complete composition-root wiring for detection, redirects, and teardown.
