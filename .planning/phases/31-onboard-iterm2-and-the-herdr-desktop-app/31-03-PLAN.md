Reason: the research (pitfall 2, iTerm2 v3.7.8 `ProfileModel.m`) shows a running iTerm2 whose in-memory default profile file disappears sets its first profile as the default and writes that to the preferences, so a delete before the quit would overwrite the restore in the common case where iTerm2 is open; restoring first keeps the previous default even when the uninstall runs inside iTerm2 (the quit ends the installer), at the cost that the profile file may then remain inert. Flagged for owner confirmation; the real-Mac result is a UAT line.
- Choice (Claude's discretion; review H8): the pre-removal call is placed in `remove_tool` because both the CLI route (`run_uninstall`) and the TUI route call it and `_after_removal` runs only after a successful removal; the function is split into a thin public `remove_tool` and `_remove_tool_steps` so the restore lines reach the `detail` of every later outcome (the body has returns after the hook that never carried a note). A failed removal after a confirmed restore leaves the default restored and the profile present but unused; the status pass then reads `≈ apply install tuning` only while the default still names the profile, which it no longer does. A refused removal (unconfirmed restore) leaves everything installed, so the retry is the ordinary uninstall.
