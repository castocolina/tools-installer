## Contexto previo: cómo funciona codegraph hoy, y si opengsd tiene postinstall

Antes de las áreas formales, el usuario pidió confirmar el mecanismo real de
codegraph y si opengsd también tiene uno. Investigación confirmó:
- **codegraph:** `installer/postinstall.py`'s `POSTINSTALL_HOOKS` dispatch
  table tiene una única entrada real, `"codegraph-mcp-register"` →
  `_codegraph_mcp_register()` — detecta hosts presentes y registra el MCP
  server + hooks automáticamente.
- **opengsd:** NO tiene postinstall hook — usa `[tool.skill_lifecycle]`
  `mode = "manual-required"`, mostrando instrucciones paso a paso en vez de
  ejecutar nada automático. Confirmado como diseño correcto (no un gap),
  porque la elección de runtime+scope es interactiva por diseño de
  open-gsd — aunque research posterior mostró que SÍ existen flags
  no-interactivos (`--claude --global`, etc.), la razón para no automatizarlo
  sigue siendo que la elección del runtime/scope es específica del usuario,
  no la ausencia de sintaxis no-interactiva.
- **rtk/graphify:** confirmado el gap real — Phase 8's `08-RESEARCH.md` ya
  documentó los comandos per-host pero nunca se conectaron a
  `installer/postinstall.py`.

## Formato del skill/checklist

**User's requirements before deciding:** leer el README de graphify
(`github.com/Graphify-Labs/graphify`) y la doc de open-gsd
(`install-on-your-runtime.md`, sección "Per-runtime instructions") para
confirmar: (a) no reemplazar la statusline custom de `../ai-kit`, (b)
detectar y configurar el runtime actual sin prompts interactivos, (c)
investigar cómo reconciliar los dos modos de graphify (standalone
`graphify-out/` vs. vía `gsd-graphify` skill).

**Findings reportados:**
- graphify: `graphify install --platform <x>` (o `agents`) registra por
  host; default output `graphify-out/`; tiene su propio `graphify hook
  install` para reindex automático en cada commit.
- open-gsd: SÍ existen flags no-interactivos por runtime
  (`--claude/--opencode/--codex/--cursor` × `--global/--local`); pero NO hay
  flag para saltar la instalación de `gsd-statusline.js` en Claude Code —
  es automático, sin opción de skip (Codex es la única excepción documentada,
  issue #2586).

**Research gate question:** ¿cerrar CONTEXT.md dejando estos 3 puntos como
investigación obligatoria del research step, o seguir investigando ahora?

**User's answer:** De acuerdo en cerrar, con una corrección importante: el
riesgo de la statusline solo aplica si se usa el flag `--force` (el que
pisa configuración existente) — evitar ese flag resuelve el riesgo. Lo que
sí es importante investigar/resolver es que, sin importar el disparador
(standalone, git hook, vía codegraph u otro agente), graphify debería usar
una sola carpeta de salida en vez de `graphify-out/` y la ubicación de
`gsd-graphify` como dos targets separados.

**Result:** Folded into D-01/D-01a (doc + skill, never `--force`-equivalent
flags) and left the output-unification question as an explicit "Research
NOT yet done" item in canonical_refs — not decided here, resolved by the
research step per the user's own instruction to research more before
planning.

## Mecanismo concreto para rtk/graphify

| Option | Description | Selected |
|--------|-------------|----------|
| Hook por-host en postinstall.py, igual que codegraph | Añadir `_rtk_register()`/`_graphify_register()` al dispatch table, detectando host y ejecutando el comando correcto por host, sin `--force` | ✓ (refined) |
| Un solo comando 'auto' por tool | Confiar en una bandera `--auto` propia de cada CLI en vez de iterar hosts | |
| skill_lifecycle manual-required, como opengsd | No automatizar, solo instrucciones | |

**User's choice:** Opción 1 (recommended), con una adición importante: la
lógica de "qué host CLI está presente" se repite entre varios postinstall
hooks (codegraph hoy, rtk/graphify después de esta fase, futuras tools) y
debería ser una utilidad compartida y cacheada, no reimplementada por tool.

**Result:** Captured as D-02 (per-host dispatch entries following
codegraph's pattern) + D-03 (shared, cached host-detection utility — same
"reusable, not one-off" principle Phase 12.3 already established for its
container-tool detection script).
