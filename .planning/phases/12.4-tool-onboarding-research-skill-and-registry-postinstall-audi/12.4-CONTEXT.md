# Phase 12.4: Tool Onboarding Research Skill and Registry Postinstall Audit - Context

**Gathered:** 2026-09-10
**Status:** Ready for planning

<domain>
## Phase Boundary

Build a reusable "tool onboarding" process (skill + checklist) that any future
`registry.toml` addition must go through — tier classification, dependency
tree, and postinstall/host-setup needs — and use it retroactively to (1) close
the confirmed rtk/graphify postinstall gap (researched in Phase 8's
`08-RESEARCH.md`, never wired into `installer/postinstall.py`) and (2) audit
the full existing catalog (~90+ tools) for whether each entry actually went
through an equivalent process. Discovered mid-discussion in Phase 12.2 when
the user questioned whether rtk/codegraph/graphify need a CLI setup step
beyond binary install. codegraph is confirmed already correct (real
`_codegraph_mcp_register()` hook in `installer/postinstall.py`); opengsd is
confirmed correct-by-design (`skill_lifecycle` `manual-required`, since the
interactive choice is runtime+scope selection, not absence of non-interactive
syntax — open-gsd's own docs do expose `--claude/--opencode/--codex/--cursor
--global/--local` flags, this was a real gap in this session's prior
understanding, corrected during discussion).

</domain>

<decisions>
## Implementation Decisions

### Skill/checklist format
- **D-01:** Ship both a doc checklist and an invocable skill, not either
  alone — **Reversibility:** reversible.
  - **Checklist:** extends the existing "Registry-authoring guidelines" /
    "Per-tool, per-OS verification checklist" section in
    `.claude/architecture.md` (origin's Phase 6 convention, D-01/D-02 style)
    with new items: tier classification rationale, dependency-tree
    declaration, and postinstall-per-harness classification (does this tool
    need host-detection + per-host setup, and if so which mechanism).
  - **Skill:** a new invocable skill (this project's own, not GSD's) that
    walks through the checklist interactively for any new tool being added to
    `registry.toml` — research the tool, decide tier, decide postinstall
    mechanism, write the entry. Reusable for future additions, not a one-off
    for this phase's rtk/graphify work.
- **D-01a:** Any postinstall hook this phase adds or the skill guides future
  hooks to add must never pass a `--force`-equivalent flag (or any flag that
  overwrites existing host configuration such as a statusline file) —
  confirmed real risk: GSD's own installer (`npx @opengsd/gsd-core@latest`)
  writes `gsd-statusline.js` automatically on Claude Code with no flag to
  skip it, and this user's environment uses a separate custom statusline from
  `../ai-kit`. Since GSD is invoked manually (`skill_lifecycle`
  `manual-required`), the immediate risk is contained, but this principle
  generalizes to any future postinstall hook this project writes itself:
  **detect and configure, never blind-overwrite.**

### rtk/graphify postinstall mechanism
- **D-02:** Add per-host dispatch entries to `installer/postinstall.py`'s
  existing closed dispatch table, following the `_codegraph_mcp_register()`
  pattern — `_rtk_register()` and `_graphify_register()` — each detecting
  which agent host(s) are present and running the correct non-interactive
  command per host (e.g. `rtk init -g --claude`, `rtk init -g --opencode`,
  `graphify install --platform claude`, etc.), never a blind `--force` /
  overwrite-everything call. **Reversibility:** reversible.
- **D-03:** The "which agent host CLI(s) are present" detection logic must be
  a single shared, reusable utility — not reimplemented per-tool inside each
  `_*_register()` function. Multiple postinstall hooks (codegraph today;
  rtk/graphify after this phase; any future tool) need the same answer
  ("is claude/opencode/codex/cursor present on this machine"), so detection
  should run once and be cached for the duration of a postinstall run rather
  than re-probed per tool. **Reversibility:** reversible — refactor, not a
  new external dependency.
  - Applies the same "reusable, not one-off" principle Phase 12.3 already
    established for its platform/container-tool detection script (D-02
    there) — this project's convention going forward: detection logic used
    by more than one phase/tool lives as a shared helper, not duplicated.

### Registry audit depth
- **D-04:** Audit the full existing catalog (~90+ tools in `registry.toml`),
  not just the `ai`/agent-harness subset and not deferred to a future phase —
  every `[[tool]]` entry gets checked against the new checklist (tier
  correctness, dependency declaration, postinstall classification), producing
  a list of any additional gaps analogous to rtk/graphify, not just closing
  those two. **Reversibility:** reversible — an audit produces findings, not
  irreversible changes; any fixes the audit surfaces become their own
  follow-up work, in or out of this phase per planner/execution judgment.

### Claude's Discretion
- Exact name/location of the new onboarding skill and where the extended
  checklist section lives inside `.claude/architecture.md` (append to
  existing section vs. new subsection).
- Exact shape of the shared host-detection utility (module path, cache
  lifetime/scope) — implementation detail, as long as it's called once and
  reused, not reimplemented per tool.
- Whether audit-discovered gaps beyond rtk/graphify get fixed within this
  phase or logged as new phases/backlog items — planner's call based on
  volume of findings.

</decisions>
