## Summary

Scope: `0243b0e^..96c270d` restricted to `installer/`, `tests/`, `setup.py` (the true Phase 15.6
diff — the commit immediately before Plan 01's first commit through the merge of Plan 06). This
covers all 6 plans: the oh-my-zsh template repair (Plans 01–02), the new
`installer/terminal_shell.py` writer for kitty/WezTerm/Konsole (Plan 03), and the shared
terminal-synchronization closure wired into 6 lifecycle routes (Plans 04–06).

Every claim below was checked against the actual committed source (not the plan/summary
narrative), several were reproduced live in a sandboxed `tmp_path`-style HOME using the real
production functions, and one was cross-checked against this host's own `~/.config/konsolerc`
and `/usr/share/konsole/Vapor.profile`. Answers to the six questions this review was scoped to:

1. **Shared closure — yes for the synchronizer itself, no for the failure contract.** All six
   call sites resolve to `setup.py::_sync_terminals` (`setup.py:385`) — four of them through the
   identical `_sync_omz_terminals` object bound once in `_build_app` (`setup.py:572-580,612,638,
   745,776`), the other two (`main`'s unattended route, `_run_uninstall`) calling `_sync_terminals`
   directly since neither builds a `UnifiedApp`. But the *error handling* around that one closure
   is five independently hand-written `try/except` blocks that have already drifted in catch set
   and message casing — see **WR-03**.
2. **Always non-fatal and always visible — no, on both halves.** Non-fatal: every one of the six
   call sites narrows its catch to `OSError` (or `OSError`/`CommandError` via `run_live`), but the
   synchronizer's own file readers decode with `.decode("utf-8")` and raise `UnicodeDecodeError`
   — a `ValueError`, not an `OSError` — on any non-UTF-8 byte in `.zshrc`/`kitty.conf`/`konsolerc`.
   Verified live: `isinstance(UnicodeDecodeError(...), OSError)` is `False`. This escapes all six
   handlers (**CR-02**). Visible: the Uninstall screen renders a caught synchronization failure
   with the *success* status color (**WR-04**), and a fully-reverted or fully-skipped run is
   reported identically to a fully-successful one, because only `TerminalShellResult.warnings` is
   ever read (**IN-01**).
3. **Hostile-path escaping — kitty and WezTerm are correct; Konsole is not.** Konsole's
   `Command=` value is shell-escaped (`shlex.join`) but never KConfig-escaped on top of that, so a
   zsh path containing a backslash round-trips wrong once Konsole's own `\n`/`\t`/`\\` unescaping
   runs — and the shipped test (`tests/test_terminal_shell.py:262`) asserts the raw, un-escaped
   bytes, certifying the bug rather than catching it (**WR-01**). Separately and more seriously,
   the profile this phase writes has no `Name=` key at all (**CR-05**) — confirmed against this
   host's real `/usr/share/konsole/Vapor.profile`, which always carries one — so Konsole is
   expected to reject the profile outright, making the entire Konsole deliverable a no-op on a
   real KDE session regardless of the escaping bug.
4. **The oh-my-zsh repair can corrupt (semantically) a working `.zshrc`, and reproduces on every
   sync, not just once.** Reproduced live against the real `ensure_zshrc_template`: (a) it
   hardcodes `export ZSH="$HOME/.oh-my-zsh"` even when `omz_present()` — the exact predicate that
   gates the call — was satisfied via a *different* `$ZSH` (**CR-01**); (b) the common
   `[ -f "$ZSH/oh-my-zsh.sh" ] && source ...` guarded idiom is not recognized as "already sourced",
   so a fully correct `.zshrc` gets a second, unconditional `export ZSH=`/`source` pair appended
   (**WR-06**); (c) a `plugins=(...)` line indented inside an `if`/`case`/function body is hoisted
   out of that block by `_repair_sourced_template`, silently turning a conditional plugin set into
   an unconditional one and leaving the original conditional empty (**WR-05** — confirmed via
   `zsh -n` that this is a semantic change, not a shell syntax error, so the stronger
   "breaks the shell" framing is not supported). The core ordering fix itself (plugins array
   evaluated before `source $ZSH/oh-my-zsh.sh`) is correct against real oh-my-zsh semantics and is
   idempotent after its own first pass — that part holds up under direct testing.
5. **chsh / system login shell boundary — held.** `git diff 0243b0e^..96c270d -- installer tests
   setup.py | grep -i 'chsh\|/etc/passwd\|usermod\|login_shell'` returns nothing except one test
   name containing the substring `login_shell` (which refers to the terminal's own `-l` login-shell
   *argument*, not the system shell). `installer/post_install.py::_set_login_shell` is untouched by
   this diff. Confirmed clean.
6. **Planning-time findings that did not actually land.** Cycle 2's MEDIUM #2 ("test hostile path
   serialization for Konsole KConfig `General/Command`") is recorded in `15.6-REVIEWS.md` as
   addressed by Plan 03, but the shipped test pins the incorrect serialization (WR-01), so Cycle
   1's HIGH #5 ("format-specific escaping is not planned") is effectively still open for Konsole.

Additionally, on the exact host class this phase exists for — Bazzite/immutable, where
`registry.toml`'s zsh entry has no rpm-ostree method and installs via `brew` — the synchronizer's
bare `shutil.which("zsh")` lookup cannot see a zsh that was *just* installed in the same process,

Manual mutation-style verification (no mutation tool is configured in this project) was applied

## Critical Issues

### CR-01: `ensure_zshrc_template` hardcodes `$HOME/.oh-my-zsh`, contradicting the predicate that gates it

**File:** `installer/omz.py:355-362`, reached unconditionally from `installer/terminal_shell.py:266-267`
**Issue:** `omz_present(home, environ)` (`installer/omz.py:466-471`) deliberately treats oh-my-zsh
as present either at `~/.oh-my-zsh` **or** at whatever directory `$ZSH` names. `sync_terminal_shells`
gates the repair call on exactly that predicate, but `ensure_zshrc_template` takes no `environ`
parameter at all and always emits a literal `export ZSH="$HOME/.oh-my-zsh"`. For any user whose
oh-my-zsh lives somewhere else (a dotfiles-managed install, an XDG-relocated one), this both
overwrites their working `$ZSH` value and sources a path that does not exist. Reproduced live:

```python
# home = /tmp/xxx, no ~/.oh-my-zsh, a real oh-my-zsh checkout at /tmp/xxx/custom-omz
ensure_zshrc_template(Path("/tmp/xxx/.zshrc"))
# .zshrc becomes:
# ...
# export ZSH="$HOME/.oh-my-zsh"      <- wrong; the real install is at custom-omz
# plugins=(git)
# source $ZSH/oh-my-zsh.sh           <- points at a directory that does not exist
```

Every new zsh session on that machine then fails to source oh-my-zsh at all, and this repair runs
on every install-close, update, and uninstall event that finds oh-my-zsh present — it is not a
one-time mistake.
**Fix:** resolve the real root once (mirroring `omz_present`'s own logic) and pass it down instead
of assuming the default:

```python
def omz_root(home: Path, environ: Mapping[str, str]) -> Path | None:
    default = home / ".oh-my-zsh"
    if default.is_dir():
        return default
    configured = environ.get("ZSH")
    return Path(configured) if configured and Path(configured).is_dir() else None

# ensure_zshrc_template(zshrc_path: Path, root: Path) -> bool:
updated += f"export ZSH={shlex.quote(str(root))}\n"
```

Thread `environ` through `sync_terminal_shells` (which already has it) into `ensure_zshrc_template`,
and reimplement `omz_present` as `omz_root(...) is not None` so the two can never disagree again.
Add a regression test with `$ZSH` pointed at a non-default directory.

### CR-02: A non-`OSError` from the synchronizer escapes every one of the six call sites

**File:** decode sites `installer/omz.py:139-141`, `installer/terminal_shell.py:168-169`;
handler sites `installer/policy.py:449-453`, `installer/update.py:471-480`,
`installer/wizard_app.py:1226-1230`, `installer/wizard_app.py:2293-2298`, `setup.py:414-417`
**Issue:** Both `_read_rc` (omz.py) and `_read_text` (terminal_shell.py) decode file bytes with
`.decode("utf-8")` and let a failure propagate as-is. `TerminalShellError`/`OmzPluginsError` both
subclass `OSError` specifically so every call site's narrow `except OSError` can catch them — but
the decode happens *before* either of those types can be raised, so a `.zshrc`, `kitty.conf`,
`wezterm.lua`, or `konsolerc` containing one non-UTF-8 byte (a Latin-1 accented character in a
comment is entirely realistic) raises a bare `UnicodeDecodeError`, which `isinstance(exc, OSError)`
is `False` for — confirmed directly in this environment. Every one of the five handlers in the
table below, and the `run_live` seam wizard_app.py's two call sites route through, only catches
`OSError` (`installer/ui_common.py:41-50` catches `(OSError, CommandError)`). Consequences differ
by route: in `_install_closed` and the Policies toggle, the exception escapes a Textual
screen-result callback (the exact failure mode `wizard_app.py`'s own comments describe guarding
against elsewhere); in `main()`'s unattended route, it propagates through `_sync_terminals_and_report`
and `main()` into the bare `except KeyboardInterrupt` at the bottom of `setup.py`
(`setup.py:1084-1088`), turning a *successful* install into an uncaught traceback and a non-zero
exit.
**Fix:** make the readers total at the point they read bytes, rather than widening five separate
`except` clauses:

```python
def _read_text(path: Path) -> str:
    if not path.exists():
        return ""
    try:
        return path.read_bytes().decode("utf-8")
    except UnicodeDecodeError as exc:
        raise TerminalShellError(f"{path} is not UTF-8; refusing to rewrite it") from exc
```

Apply the equivalent wrapping in `installer/omz.py::_read_rc` (raising `OmzPluginsError`, already
an `OSError`). Add one regression test per reader asserting the file is left byte-identical and the
raised exception is an `OSError` subclass.

### CR-03: WezTerm has no presence check, so every synchronizer run creates a config for an app that may not be installed

**File:** `installer/terminal_shell.py:282-291`
**Issue:** kitty is gated on `_safe_executable(lookup("kitty")) is None` (line 272) and Konsole on
the same pattern inside `_sync_konsole` (line 185), matching D-03's "detect its presence live."
WezTerm has no `lookup("wezterm")` call anywhere in this module — lines 282-291 unconditionally
read, synthesize a default Lua skeleton if none exists, and write
`~/.config/wezterm/wezterm.lua`, creating the parent directory as needed. Reproduced live: calling
`sync_terminal_shells` with a `lookup` function that has no `"wezterm"` key at all still returns
`result.configured == ("kitty", "wezterm", "konsole")` and actually creates `wezterm.lua` on disk.
Combined with `_install_closed` running the synchronizer on *every* ExecuteScreen close regardless
of outcome (**WR-07**), a user who opens the wizard, installs nothing, and quits ends up with a new
WezTerm config directory and file they never asked for.
**Fix:** gate it exactly like the other two terminals, and record the skip:

```python
if _safe_executable(lookup("wezterm")) is None:
    skipped.append("wezterm unavailable")
else:
    wezterm_path = _wezterm_config_path(home, environ)
    ...
```

Update the tests that currently assert `configured == (..., "wezterm", ...)` without passing a
`wezterm` executable in `lookup`, and add a test mirroring
`test_absent_konsole_does_not_create_profile_or_kconfig` for the no-wezterm case.

### CR-04: bare `shutil.which` zsh discovery silently reverts on the phase's own target host class

**File:** `setup.py:400` (`lookup=shutil.which`), consumed at `installer/terminal_shell.py:262-264`
**Issue:** `sync_terminal_shells` treats `lookup("zsh") is None` as "zsh was removed" and calls
`_revert_terminal_shells`. On an immutable host — the only host class this phase targets —
`registry.toml`'s zsh entry has no rpm-ostree method, so it installs via the brew method
(`formula = "zsh"`, `installer/registry.toml:521-523`). `engine.py` only calls `prepend_path` for a
method whose params include `bin_dir` (`installer/engine.py:157-159`), and the brew method declares
no such param, so `/home/linuxbrew/.linuxbrew/bin` is never added to the *installer process's* own
`PATH`. Immediately after the install this phase exists to react to, `shutil.which("zsh")` still
returns `None` in that same process, and the synchronizer reverts rather than configures — the
motivating scenario silently does nothing on the exact host it was built for. This project already
has the fix pattern for this exact chicken-and-egg problem: `installer/postinstall.py:169-196`
(`_BREW_BIN_DIRS`, used for resolving `rtk`'s own binary right after a brew install). `terminal_shell.py`
does not reuse it. Compounding this, `_sync_terminals` (`setup.py:402-404`) only ever reads
`result.warnings`, and a revert produces none — so nothing is reported at all (see **IN-01**).
**Fix:** inject a resolver that falls back to known brew prefixes, reusing the existing constant:

```python
def _which_with_brew(name: str) -> str | None:
    found = shutil.which(name)
    if found:
        return found
    for brew_dir in _BREW_BIN_DIRS:
        candidate = brew_dir / name
        if candidate.exists():
            return str(candidate)
    return None
# setup.py::_sync_terminals -> lookup=_which_with_brew
```

Separately, surface the revert branch itself: `_sync_terminals` should return a message whenever
`result.reverted` is non-empty, not only when `result.warnings` is.

### CR-05: the Konsole profile this phase writes has no `Name=`, so Konsole is expected to reject it

**File:** `installer/terminal_shell.py:197-201`
**Issue:** The owned profile body written is exactly `[General]\nCommand={argv}` — no `Name=` key
at all. Reproduced live: calling `sync_terminal_shells` against a sandboxed home produces
`Path("…/konsole/tools-installer-zsh.profile")` containing only a `Command=` line under
`[General]`. Every real Konsole profile on this host carries a `Name=` — confirmed against
`/usr/share/konsole/Vapor.profile`:

```
[Appearance]
ColorScheme=Vapor

[General]
Name=Vapor
Parent=FALLBACK/
```

Konsole's profile manager is documented to reject a profile with no valid `Name` property. With
the profile rejected, `konsolerc`'s `DefaultProfile=tools-installer-zsh.profile` resolves to
nothing and Konsole falls back to its built-in default shell — meaning the Konsole half of this
phase's headline deliverable (D-02/D-03) is a no-op on a real KDE session, while the shipped tests
(`tests/test_terminal_shell.py:223-242`) only assert the bytes written, never that Konsole could
actually load the result.
**Fix:**

```python
updated_profile = _replace_owned_region(
    profile_content,
    "konsole-profile",
    "[General]\n"
    "Name=tools-installer zsh\n"
    "Parent=FALLBACK/\n"
    f"Command={_kconfig_command(zsh_path)}",
)
```

Add an assertion for `Name=` (and `Parent=FALLBACK/`) in the Konsole tests, and confirm manually on
a real KDE/Konsole session that the profile is selectable before closing this finding.

### CR-06: Konsole's own selection is not actually reversible

**File:** `installer/terminal_shell.py:188-190`, `207-212`, `215-230`
**Issue:** Two compounding problems, in direct conflict with D-02/D-03's stated "reversible"
requirement.

(a) The prior default profile name is recorded to
`$XDG_DATA_HOME/tools-installer/terminal-shell-konsole-default` (line 207-209) and later `unlink`ed
(line 228-229) — it is never *read* anywhere in this module or the rest of the codebase. It is
write-only state that implies a restore capability the code does not have.

(b) Reversion of the `konsolerc` selection is entirely marker-comment-driven
(`_remove_if_owned(konsolerc, "konsole")`). `konsolerc` is a KConfig file that Konsole itself
rewrites on ordinary use, and KConfig's own backend does not preserve comment lines — this host's
real `~/.config/konsolerc` has zero `#` lines across 11 entries, confirming the format does not
round-trip comments. Once Konsole rewrites the file, the `# >>> tools-installer … >>>` markers are
gone while `DefaultProfile=tools-installer-zsh.profile` survives as a plain, now-unmarked entry.
From that point on, `_remove_if_owned` finds no complete region and returns `False` — but
`_revert_konsole` still unconditionally deletes the profile file whenever its own marker comment is
present in the profile (lines 224-226), leaving `konsolerc` pointing at a now-deleted profile with
the user's original default unrecoverable, and the one record that could have restored it deleted
in the same pass.
**Fix:** stop inferring `konsolerc` ownership from comments that a KConfig rewrite cannot preserve;
make the state file load-bearing instead of decorative — read `prior` from it, and rewrite the
`DefaultProfile` key directly (restoring `prior`, or dropping the key when `prior == ""`) whenever
the current value still equals `tools-installer-zsh.profile`, independent of whether the marker
comments survived. Add a regression test that strips the marker lines from `konsolerc` (simulating
a real Konsole rewrite) before reverting, and asserts the prior default is restored rather than lost.

## Warnings

### WR-01: Konsole's `Command=` is shell-escaped but never KConfig-escaped — and the test pins the bug

**File:** `installer/terminal_shell.py:140-142`; test `tests/test_terminal_shell.py:245-262`
**Issue:** `_kconfig_command` returns `shlex.join((zsh_path, "-l"))`, and that value is written
verbatim into a KConfig `.profile` file. KConfig's own value-decoding layer unescapes `\\`, `\n`,
`\t`, `\r`, `\s`, `\;`, `\,` and `\x??` sequences when it *reads* the file — a separate layer from
the shell-argv quoting `shlex.join` performs. A zsh path containing a backslash therefore
round-trips wrong: `shlex.quote` on `/opt/a\test/zsh` produces the literal text
`'/opt/a\test/zsh'`, and KConfig reads that back as `/opt/a<TAB>est/zsh` (because `\t` is its escape
for a tab), silently corrupting the launch command. The shipped test asserts
`"Command='/opt/Zsh Tools/z\"sh\\bin' -l" in profile.read_text()` — i.e. it certifies the
un-escaped bytes as correct, closing Cycle 2's planning-time finding on exactly this point against
the defect rather than a fix.
**Fix:** apply a KConfig encoder *after* the shell-argv quoting:

```python
_KCONFIG_ESCAPES = {"\\": "\\\\", "\n": "\\n", "\t": "\\t", "\r": "\\r"}

def _kconfig_value(value: str) -> str:
    return "".join(_KCONFIG_ESCAPES.get(ch, ch) for ch in value)

f"Command={_kconfig_value(_kconfig_command(zsh_path))}"
```

Rewrite the test to read the value back through KConfig's own unescaping rules (or assert the exact
double-backslash bytes) for a path containing a space, a double quote, and a backslash.

### WR-02: `_revert_konsole` deletes the owned profile unconditionally but strips `konsolerc` only conditionally

**File:** `installer/terminal_shell.py:222-229`
**Issue:** The `konsolerc` cleanup is guarded by `_desktop_default(current) ==
"tools-installer-zsh.profile"`, while the profile file's own deletion is guarded only by the
profile's own marker comment being present. Whenever the effective default has already moved on —
a later `[Desktop Entry]` group, a Konsole rewrite (see CR-06), or the user picking a different
profile by hand — the profile file is deleted while the installer-owned
`DefaultProfile=tools-installer-zsh.profile` entry is left in `konsolerc` permanently, since the
guard that would remove it can never become true again. This is installer-owned content that
outlives the module's own revert path.
**Fix:** derive both actions from the same predicate — strip the owned region whenever it exists
(it is unconditionally ours by construction) and only *restore* the prior default when our profile
is still the effective one. Add a test where the effective default has changed away from ours
before reverting.

### WR-03: the shared synchronizer's failure contract is five independent, already-drifted `try/except` blocks

**File:** `installer/policy.py:449-453`, `installer/update.py:471-480`,
`installer/wizard_app.py:1226-1230`, `installer/wizard_app.py:2293-2298`, `setup.py:414-417`
**Issue:** The synchronizer function itself is genuinely shared (see the Summary), but its failure
handling is copy-pasted five times and has already diverged on every axis a shared contract exists
to pin:

| Site | Catches | Message |
| --- | --- | --- |
| `policy.py:452` | `OSError` | `Terminal shell synchronization failed: {exc}` |
| `update.py:474` | `OSError` | `Terminal shell synchronization failed: {extra}` |
| `wizard_app.py:1229` | `OSError` | `Terminal shell synchronization failed: {exc}` |
| `wizard_app.py:2296` (via `run_live`) | `OSError` **+ `CommandError`** | `terminal shell synchronization failed: …` (**lower-case t**) |
| `setup.py:416` | `OSError` | `Terminal shell synchronization failed: {exc}` |

This is what turns **CR-02** into a five-site fix instead of a one-site fix: because the catch and
message live at each call site, a defect in what should be caught has to be independently fixed
five times, and one of the five has already drifted in wording.
**Fix:** move the `try/except` and the message formatting into the closure itself — have
`setup.py::_sync_terminals` return `str | None` and never raise (catching
`OSError`/`TerminalShellError` internally and emitting the one canonical message). Every call site
then reduces to `warning = terminal_sync()`, and the duplicated literal and catch set disappear.

### WR-04: a terminal-sync failure on the interactive Uninstall screen is rendered with "ok" (success) styling

**File:** `installer/wizard_app.py:1226-1233`
**Issue:** `_apply_removal` appends the caught failure text to `summary_parts` and then calls
`self.status.set(multiline_summary(summary_parts), "ok")` unconditionally — the failure text is
present, but styled identically to a clean success. Contrast the Policies screen, whose analogous
outcome in this same phase was deliberately changed to `"warn" if result.warning else "ok"`
(`installer/wizard_app.py:1625` per grep), and `_install_closed`, which uses `"warn"` for the same
class of failure (`installer/wizard_app.py:2331`). Of this review's second question — is a failure
always visible — this fails the *severity* half here: the text is there, but nothing distinguishes
it from success at a glance.
**Fix:** track whether the terminal sync warned and pass that through to the status color:

```python
terminal_failed = False
...
    if terminal_warning:
        summary_parts.append(terminal_warning)
        terminal_failed = True
self.status.set(multiline_summary(summary_parts), "warn" if terminal_failed else "ok")
```

Extend the existing OSError-without-losing-`applied` test to also assert the severity, not only
the text.

### WR-05: `_repair_sourced_template` hoists a `plugins=(...)` line out of any enclosing block

**File:** `installer/omz.py:313-332`
**Issue:** `_PLUGINS_LINE`'s regex deliberately allows leading indentation, so a `plugins=(...)`
assignment nested inside an `if`/`case`/function body still matches `_locate`, and
`_repair_sourced_template` unconditionally `pop`s and re-`insert`s it before the source line with
no awareness of the surrounding block structure. Reproduced logically against the module's own
matching rules: a file shaped like

```zsh
source $ZSH/oh-my-zsh.sh
if [[ -n "$X" ]]; then
  plugins=(git)
fi
```

becomes

```zsh
  plugins=(git)
source $ZSH/oh-my-zsh.sh
if [[ -n "$X" ]]; then
fi
```

turning a conditional plugin set into an unconditional one and leaving the user's `if` an empty
no-op. Verified with `zsh -n` against exactly this emptied-body shape that it is not a shell syntax
error (exit 0) — so this is a silent semantic change, not file corruption in the stronger sense.
**Fix:** only relocate a top-level (unindented) assignment, and refuse the nested case the way this
module already refuses other shapes it cannot reason about:

```python
if match.group("indent"):
    return None  # nested assignment: not ours to relocate
```

Add a test for the indented case asserting the file is left byte-identical.

### WR-06: the common guarded-source idiom is not recognized, so a working `.zshrc` gets oh-my-zsh sourced twice

**File:** `installer/omz.py:85` (`_OH_MY_ZSH_SOURCE`), consumed at `installer/omz.py:349`
**Issue:** The regex anchors `source`/`.` to the start of the (whitespace-trimmed) line, so the
very common guarded form `[ -f "$ZSH/oh-my-zsh.sh" ] && source "$ZSH/oh-my-zsh.sh"` is classified
as "not sourced." Reproduced live: calling `ensure_zshrc_template` against exactly that guarded
file (plus an already-correct `plugins=(git)` line) produces

```
export ZSH="$HOME/.oh-my-zsh"
[ -f "$ZSH/oh-my-zsh.sh" ] && source "$ZSH/oh-my-zsh.sh"
plugins=(git)
export ZSH="$HOME/.oh-my-zsh"     <- appended, duplicate
source $ZSH/oh-my-zsh.sh          <- appended, duplicate
```

`ensure_zshrc_template` is called unconditionally by `sync_terminal_shells` whenever `omz_present()`
is true (`installer/terminal_shell.py:266-267`) — bypassing `write_plugins`'s own smarter
already-has-an-array gate entirely — so this fires on every install-close, update, and uninstall
event on a machine using this idiom. oh-my-zsh then loads twice per shell start (duplicated
`fpath`, a second `compinit`). It stabilizes after the first pass (the second `source` line is
now unguarded and gets recognized as active on the next run) — this is one-time degradation, not
unbounded growth — but the module's own stated contract ("source-correct files … are left
unchanged") is violated for this file.
**Fix:** detect an executable `source`/`.` anywhere the shell would actually execute it, not only
at line start, e.g.:

```python
_OH_MY_ZSH_SOURCE = re.compile(r"^[^#\n]*(?:^|[;&|]\s*|\s)(?:source|\.)\s+[^\n#]*oh-my-zsh\.sh")
```

while keeping "a comment never counts" as an explicit test case. Add tests for the `&&`-guarded and
`;`-separated forms.

### WR-07: `_install_closed` unconditionally re-syncs terminals on every close, including no-op runs

**File:** `installer/wizard_app.py:2286-2298`
**Issue:** This is a deliberate design choice per this plan's own comments ("never only a selected
tool id, never only a successful outcome"), but its consequence is real: merely opening and
dismissing the Execute screen on a Linux host that already has zsh present rewrites
`kitty.conf`, creates a brand-new `wezterm.lua` (see **CR-03**), and writes `konsolerc` — for a
session where the user selected and changed nothing. D-01 asks for reapplication "on relevant state
change"; opening and closing a screen with no selection is not obviously one. Every other post-run
side effect this same callback performs (`invalidate`, `enter_view`) is conditioned on something
having actually happened during the run.
**Fix:** gate the call on the run having produced a state change (the same signal
`on_install_run_finished` already has access to), or at minimum skip it when the close carried no
selected ids and no outcomes. The zsh-removal revert case is already independently covered by
`UninstallScreen._apply_removal` and `_run_uninstall`, so gating this call site does not lose
coverage for that scenario.

### WR-08: the pending-warning queue's documented flush path is not what actually flushes it

**File:** `installer/wizard_app.py:1948-1952`, `installer/wizard_app.py:2318-2331`
**Issue:** The `__init__` comment for `_pending_warnings` states queued warnings are "flushed to
the next screen that becomes visible (`show_view`) or the next `_install_closed` render." The
second half does not hold: `_install_closed` returns early at
`if not warnings: return` (line 2318-2319) *before* it ever reaches the code that would drain
`_pending_warnings` — so a close event that produces no *new* warning of its own never flushes a
previously-queued one; only a subsequent `show_view` navigation does (`_flush_pending_warnings`,
lines 2144-2155). The `visible is None` branch that populates the queue is also acknowledged in the
plan's own summary as structurally unreachable today, so this is currently a dead, untested code
path whose documented contract it does not fulfil — low real-world impact today, but a latent trap
for the next caller who does make that branch reachable.
**Fix:** either move the flush above the early return so both documented paths actually flush, or
remove the queue and the unreachable branch outright and let `show_view`/`self.screen` be the one
documented answer (dead-code tooling will then flag it correctly if it ever becomes unreachable
again).

### IN-01: `configured`/`skipped`/`reverted` are computed and then thrown away by every caller

**File:** `setup.py:402-404`, `installer/terminal_shell.py:29-32`
**Issue:** `TerminalShellResult` carries four fields; every call site (via `_sync_terminals`) reads
only `.warnings`. A full revert of all three terminals, a `skipped=("macos",)` no-op, and a fully
successful configuration are therefore indistinguishable to the user — all three produce no message
at all. This is what makes **CR-04**'s failure mode silent rather than merely wrong.
**Fix:** surface `reverted` as an informational message at minimum (e.g. "zsh is no longer present;
reverted kitty, konsole"), and consider folding `skipped` into the returned message so a
Bazzite/brew user is told the synchronizer ran and did nothing, instead of nothing being said.

### IN-02: Konsole's own "unavailable" case is silently dropped, unlike kitty's

**File:** `installer/terminal_shell.py:185-186`, `272-273`
**Issue:** When kitty is absent, `"kitty unavailable"` is appended to `skipped` (line 273). When
Konsole is absent, `_sync_konsole` returns `(False, None)` and contributes nothing to any result
field, and WezTerm has no absence handling at all (**CR-03**). Three terminals, three different
reporting conventions inside one function.
**Fix:** have `_sync_konsole` return a skip reason and append it the same way kitty does, for a
uniform result shape once CR-03 also gives WezTerm one.

### IN-03: owned regions are always written with `\n`, mixing line endings in a CRLF-edited config

**File:** `installer/terminal_shell.py:50`, `70`
**Issue:** `_replace_owned_region` strips a trailing `\r\n` when *matching* marker lines (line 50,
`line.rstrip("\r\n")`), but the region it emits is always `f"{begin}\n{body}\n{end}\n"` — pure LF.
A `kitty.conf` or `wezterm.lua` edited on Windows/WSL (the exact case `installer/omz.py`'s own CRLF
handling goes out of its way to preserve for `.zshrc`) ends up with mixed line endings after this
module touches it, and the LF markers still match on a subsequent pass, so the file never converges
to one convention.
**Fix:** detect the dominant line ending already present in the file and emit the owned region using
it, mirroring `installer/omz.py::_crlf_line`'s existing pattern.

### IN-04: the Konsole state file is written before the writes it is meant to describe

**File:** `installer/terminal_shell.py:207-212`
**Issue:** The prior-default record is written first (lines 207-209), then the profile and
`konsolerc` writes follow (lines 210-212). If either of those two later writes raises (e.g. a
permission error), a record claiming a prior default now exists for a configuration change that
never actually landed. This is currently harmless only because the record is never read at all
(**CR-06a**) — it becomes a live ordering bug the moment CR-06 makes the record load-bearing.
**Fix:** write the state record only after both configuration writes succeed, or wrap it in the same
kind of rollback `installer/omz.py::write_plugins` already uses for its own record/edit pair.
