## When the configuration is (re-)applied

Trade-off presented:
- **Solo al momento de instalar (evento único):** applied the first time zsh+terminal
  coincide as installed after an install run. Simple, but doesn't reapply if oh-my-zsh
  is activated later via Policies, or a terminal is installed much later.
- **Idempotente, reaplicado en cada punto de refresco relevante (recommended):**
  recomputed whenever something relevant changes (zsh install/update, a new terminal
  installed, oh-my-zsh activated later via Policies) — same "never stale" pattern
  already established in Phase 15.1 (catalog refresh) and 15.4 (Uninstall ownership
  refresh).

**User's choice:** Idempotente / siempre sincronizado (recommended option).

**Resolution:** Captured as D-01 in CONTEXT.md.

## Configuration method: launcher vs. config file

Trade-off presented:
- **Editar el archivo de config de cada terminal (recommended):** write directly into
  `kitty.conf`'s `shell`, `wezterm.lua`'s `default_prog`, Konsole's profile file.
  Persists regardless of how the terminal is launched (dock, app menu, taskbar,
  keyboard shortcut, IDE-integrated terminal) — a `.desktop` Exec= edit only applies
  to that one specific launcher and can be reset by a package update.
- **Wrapper/.desktop override:** add the flag at the launcher level without touching
  the app's own config. Easier to revert (just restore the original `.desktop`) but
  doesn't cover every way the terminal can be opened, and a package update can reset
  the `.desktop` file too.

**User's choice:** Editar el config propio del terminal (recommended option).

**Resolution:** Captured as D-02 in CONTEXT.md — supersedes the CLI-override research
leads noted in Phase 15.5 (kitty `-o shell=...`, WezTerm `--config default_prog=...`)
as the *mechanism* choice; those flags remain useful reference for understanding each
tool's config semantics, but the actual write target is the persistent config file.

## oh-my-zsh sourcing gap (confirmed live, added after initial close-out)

While reviewing the Policies screen live, the user hit and reported (with a
screenshot) a real error: the "Oh-My-Zsh plugins" toggle fails with `Policy change
failed: No single-line plugins=(...) array to edit; only the single-line form is
supported`.

**Investigation:** confirmed `~/.oh-my-zsh/` exists (real install) but nothing in
`~/.zshrc` or `~/.myshellrc` sources it — no `ZSH_THEME`, no `plugins=(...)`, no
`source $ZSH/oh-my-zsh.sh`. Root cause: the registry's `KEEP_ZSHRC=yes` setting
(`installer/registry.toml`, `oh-my-zsh` entry) correctly avoids clobbering an
existing `.zshrc`, but the installer never separately ensures the minimal sourcing
line exists when the pre-existing file didn't already have it — so oh-my-zsh
installs successfully and is completely inert, and `installer/omz.py`'s
single-line-array editor has nothing to find.

| Actualizar CONTEXT.md de 15.6 con el hallazgo confirmado | Already an open research question in this phase's scope ("is oh-my-zsh plugin-loading correct?") — convert it to a locked, confirmed decision and continue with Phase 15.7 | ✓ |
| Pausar y discutir esto a fondo aparte | Open a dedicated discussion session for this specific fix before continuing to 15.7 | |

**User's choice:** Actualizar CONTEXT.md (recommended option) — fold the confirmed
finding into 15.6 rather than opening a separate discussion, since it was already
within this phase's stated domain.

**Resolution:** Captured as D-04 in CONTEXT.md, replacing the earlier
"flagged for research, not yet confirmed" discretion note with a locked decision:
the installer must guarantee `.zshrc` sources oh-my-zsh after install (idempotent
append, never overwriting a correct existing sourcing line), including a default
single-line `plugins=(git)` array so the Policies toggle has something to edit.
