# Phase 15.6 Plan 05: Update-path terminal synchronization Summary

**`UpdateService.run` gained an injected terminal-follow-up seam, wired in `setup.py` to the same `_sync_omz_terminals` closure Plan 04 uses for Policies, so pressing `u` on an outdated tool re-syncs Konsole/kitty/wezterm's zsh config exactly like a committed OMZ plugin edit does — with a synchronization failure surfaced as a warning beside the updated status, never as a failure.**

## Performance

- **Duration:** ~35 min
- **Completed:** 2026-09-21T23:50:17Z
- **Tasks:** 2
- **Files modified:** 5

## Accomplishments
- `UpdateService.run` invokes an optional, narrowly-typed `terminal_follow_up: Callable[[], str | None] | None` closure exactly once, only after an `updated` outcome, after the pnpm globals replay, and before the cache-invalidation warning is assembled.
- A raised `OSError` from that closure is caught and appended to `UpdateOutcome.detail` as `"Terminal shell synchronization failed: {exc}"`, matching `installer/policy.py::omz_plugins_policy`'s own wording — the update stays `status="updated"`.
- Refused (`unknown-owner`), `unsupported`, and `failed` outcomes never invoke the closure — proven directly via reverted-and-restored mutation checks, not just asserted.
- `setup.py`'s `_build_app` passes its existing `_sync_omz_terminals` composition-root closure into the production `UpdateService` alongside its existing `omz_plugins_policy` wiring — one synchronizer, two mutation call sites, matching D-01's "same terminal synchronizer Plan 04 wired for Policies" requirement.
- `CatalogScreen.action_update_tool` / `on_tool_updated` needed zero changes: the new warning rides the existing `UpdateOutcome.detail` rendering path (`if outcome.detail: line += f" — {outcome.detail}"`), so there is no second, duplicated status-formatting branch.

## Decisions Made
- Reused the existing `_sync_omz_terminals` closure verbatim (only widening its docstring) rather than extracting a differently-named shared helper — the plan explicitly calls for "the same terminal synchronizer Plan 04 wired for Policies," and the closure's signature (`() -> str | None`) already matched `UpdateService`'s new seam with no adapter needed.
- Placed the terminal follow-up step between pnpm replay and cache invalidation, per the plan's explicit ordering requirement; this also keeps a terminal-sync failure from ever suppressing the (unrelated) cache-invalidation attempt, since each step's own `try`/`except` is independent.
- Skipped catalog_tui.py changes entirely — Task 2's own instruction to test "the existing `UpdateOutcome.detail` rendering rather than duplicating status formatting" held: no production code in `catalog_tui.py` needed to change.
