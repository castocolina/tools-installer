## 15.6-01

### Summary

D-04 is already partly implemented in `installer/omz.py`: `ensure_zshrc_template`
is called only from `write_plugins`. The plan is a 35-line stub with no executable
tasks, threat model, or install-time trigger. Its template appends `plugins=(git)`

### Strengths

- The must-haves match the `KEEP_ZSHRC` inert-`.zshrc` problem and the existing
  policy error handling in `installer/omz.py:58-64,90-91`.
- Writes use `atomic_write_text` (`installer/omz.py:212`, `installer/atomic.py:35-58`),
  which preserves symlink topology (`installer/atomic.py:42`).
- `write_plugins` keeps its ownership-record transaction around the `.zshrc` edit
  (`installer/omz.py:342-356`).
- Existing tests cover missing and already-sourced files (`tests/test_omz.py:91-120`).

### Concerns

- **HIGH: plugin configuration is written after Oh-My-Zsh is sourced.**
  `ensure_zshrc_template` appends `export ZSH`, then `source $ZSH/oh-my-zsh.sh`,
  then `plugins=(git)` (`installer/omz.py:302-305`). Oh-My-Zsh reads `plugins`
  when its script is sourced, so later policy edits can report success while no
  plugins load. The module's own explanation requires the final assignment before
  source (`installer/omz.py:99-106`).
- **HIGH: D-04 is not triggered by a successful Oh-My-Zsh install.** The only
  production path into `ensure_zshrc_template` is `write_plugins`
  (`installer/omz.py:328-335`) through `omz_plugins_policy._apply`
  (`installer/policy.py:424-425`). The registry retains `KEEP_ZSHRC=yes` and only
  declares `set_login_shell` (`installer/registry.toml:548-554`), so an install
  without a later Policies action leaves the exact inert file D-04 requires fixing.
- **HIGH: the plan is not executable.** It has no tasks, test command, threat model,
  or wiring instructions, despite its summary marking D-04 complete.
- **MEDIUM: a sourced file with no plugins array remains unusable.** The substring
  guard returns when `oh-my-zsh.sh` appears (`installer/omz.py:297-298,332`), then
  `enable_plugins` raises because no editable array exists (`installer/omz.py:164-166`).
- **MEDIUM: sourcing detection is too broad.** A comment or unrelated string
  containing `oh-my-zsh.sh` suppresses the template (`installer/omz.py:297`).

### Suggestions

- Write `export ZSH`, `plugins=(git)`, then `source $ZSH/oh-my-zsh.sh`, with a
  test that the live plugin assignment occurs before sourcing.
- Put template repair in the shared synchronization or successful install lifecycle,
  not only in the plugin policy.
- Define a safe repair rule for a sourced `.zshrc` that lacks a single-line plugins array.

### Risk Assessment

**HIGH.** The current plan does not reliably make Oh-My-Zsh or its configured plugins active.

## 15.6-02

### Summary

The module-and-composition-root approach matches D-02/D-03, but the stated Linux
gate cannot run on the actual platform model. Ownership parsing and data serialization
for each terminal format also need concrete mechanisms.

### Strengths

- Direct terminal config and no `chsh` match D-02 and the existing user guidance
  (`installer/post_install.py:40-46`).
- Injected home, platform, and executable discovery make a sandboxed test design
  possible; `atomic_write_text` preserves symlinks (`installer/atomic.py:10-14,42`).
- `_install_closed` is an existing post-run hook and preserves completed installs
  when follow-up failures become warnings (`installer/wizard_app.py:2174-2250`).
- Live Konsole discovery rather than a catalog entry matches D-03.

### Concerns

- **HIGH: `Platform.os == "linux"` is a dead production gate.** The platform type
  uses `debian`, `arch`, `fedora`, and `macos` (`installer/platform.py:21-22,41-49`);
  Bazzite is `fedora`. A literal `linux` check makes the capability a no-op on its
  target hosts. Existing Linux gates use `platform.os != "macos"` (`setup.py:356-357`).
- **HIGH: owned-region behavior is unspecified and cannot reuse `apply_block`.**
  The plan requires malformed markers to fail without modifying the file, while
  `apply_block` appends another block after an unpaired begin marker
  (`installer/shellrc.py:114-131`). A terminal writer needs a fail-closed parser,
  not the existing append-oriented helper.
- **HIGH: paths are not serialized for kitty, Lua, or KConfig.** The discovered
  `which` path is inserted into three configuration languages, but the plan has no
  escaping/quoting contract or test for spaces, quotes, or backslashes. Passing the
  path without a shell is insufficient when writing executable configuration text.
- **MEDIUM: warning delivery can be lost when no catalog is active.**
  `_install_closed` returns at `installer/wizard_app.py:2240-2241` before rendering
  accumulated warnings. A sync result must use a pending-warning mechanism when no
  catalog status line exists.
- **MEDIUM: per-tool update bypasses `_install_closed`.** The catalog's `u` update
  is in-place (`installer/catalog_tui.py:733-769`), yet D-01 includes zsh updates.
- **MEDIUM: Konsole paths need an XDG resolution contract.** The plan names generic
  user directories while discovery identifies `~/.local/share/konsole` and
  `~/.config/konsolerc`; `$XDG_DATA_HOME` and `$XDG_CONFIG_HOME` need explicit support.
- **LOW: kitty and Konsole login-shell arguments need exact, tested formats.**
  WezTerm specifies `"-l"`, but the other two formats are only implied.

### Suggestions

- Gate with `platform.os != "macos"` or the explicit Linux OS set, and test with
  `fedora`, `debian`, or `arch`.
- Specify a fail-closed marker parser and test an unpaired marker leaves bytes unchanged.
- Define and test each target format's escaping behavior using hostile-but-valid paths.
- Persist failures when no active catalog can display them.

### Risk Assessment

**HIGH.** As written, the capability can be entirely disabled on Bazzite and can corrupt user-owned config.

## 15.6-03

### Summary

One shared sync closure and avoidance of one-shot `post_install` are appropriate for
D-01. The lifecycle remains incomplete for unattended installs, direct update actions,

### Strengths

- The plan correctly rejects `POST_INSTALL_HOOKS` for reapplication because it skips
  already-present tools (`installer/post_install.py:19-21`).
- One composition-root closure follows the setup wiring boundary and the current
  optional-dependency construction pattern (`installer/wizard_app.py:1936-1940`).
- `_install_closed` covers catalog ExecuteScreen runs from every catalog tier
  (`installer/wizard_app.py:2176-2183,2197-2206`).
- Keeping terminal ownership independent from plugin provenance is correct:
  disabling plugins should not undo zsh terminal configuration.

### Concerns

- **HIGH: noninteractive installation never synchronizes.** `main()` uses
  `UnifiedApp` only for interactive runs (`setup.py:972-980`); the `--all` or
  category path runs `run_wizard`, then path configuration and verification
  (`setup.py:981-1002`) without `_install_closed` or any terminal synchronization.
  This contradicts D-01's every-relevant-state-change contract.
- **HIGH: a sync failure after a committed plugin write leaves the Policies UI false.**
  `omz_plugins_policy._apply` writes plugins before its proposed callback
  (`installer/policy.py:424-434`). If the callback raises, `run_live` makes
  `PoliciesScreen.action_toggle_policy` return without flipping `active_state`
  (`installer/wizard_app.py:1580-1592`), even though the ownership record and plugin
  edit remain committed. The plan's requested error behavior, retained mutation, and
  truthful state cannot all hold with that contract.
- **MEDIUM: direct `u` updates bypass this lifecycle.** `CatalogScreen.action_update_tool`
  updates without an ExecuteScreen close (`installer/catalog_tui.py:733-769`).
- **MEDIUM: uninstalling zsh does not invoke sync.** The uninstall path uses
  `perform_uninstall` and policy sweeping (`setup.py:511-523`), not `_install_closed`,
  leaving owned terminal settings stale until a later sync.
- **MEDIUM: the callback's exception contract is underspecified.** `run_live` catches
  only `OSError` and `CommandError` (`installer/ui_common.py:41-50`); parser/validation
  errors outside those types would escape the Textual workflow.
- **LOW: Oh-My-Zsh presence is a construction-time snapshot.** `missing_requires` is
  built once in `setup.py:581-585`, so a same-session install can still leave Policies
  unable to activate the plugin policy.

### Suggestions

- Invoke the same closure after unattended `run_wizard` completion and after the
  relevant update and zsh-uninstall paths.
- Convert post-plugin synchronization failures to a distinct follow-up warning while
  retaining truthful active state, or explicitly split the two user-visible outcomes.
- Restrict the terminal-sync error surface to exceptions `run_live` handles.

### Risk Assessment

**HIGH.** Interactive install completion alone cannot satisfy D-01's never-stale lifecycle.

- The plans use direct per-user terminal configuration, atomic symlink-preserving writes,
  and a shared composition-root closure rather than changing the login shell.
- The existing ExecuteScreen completion path and policy workflow provide useful seams.

### Agreed Concerns

1. **HIGH: The declared Linux gate cannot match Bazzite or another production Linux
   platform.** `Platform.os` is distro-specific, not `"linux"`.
2. **HIGH: D-04 remains incomplete.** Template ordering prevents plugin loading and
   the repair is not run by a normal Oh-My-Zsh install.
3. **HIGH: D-01 misses unattended installs.** `run_wizard` does not reach the TUI-only
   `_install_closed` synchronization path.
4. **HIGH: The policy callback error contract would make the UI report an uncommitted
   state after the plugin write has committed.**
5. **HIGH: Terminal ownership parsing and path serialization are incomplete.** The
   required malformed-marker safety contradicts `apply_block`, and format-specific
   escaping is not planned.

None. One reviewer was configured for this cycle.
