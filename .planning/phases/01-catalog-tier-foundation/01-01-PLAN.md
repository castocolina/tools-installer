<objective>
Add a hard-required `tier` (`system`/`user`/`ai`) field to every catalog tool, and prove the
existing `requires` resolver (`installer/deps.py::resolve_dependencies`) needs zero new logic to
carry that labeling across a tier boundary. `tier` is added alongside `audience`, not in place
of it -- per D-01 the two fields stay orthogonal (`audience="both"` tools like ripgrep/fd have
no lossless 3-value `tier` equivalent), so `Audience`/`AUDIENCE_LABEL` and the existing Audience
grouping view are untouched by this phase.

Purpose: Phase 2 needs `tier` to exist on every tool before it can split the flat Catalog view
into System/User/AI top-level views. This phase only adds the label and proves the resolver
already handles it correctly -- no view changes, no new ordering mechanism (per ROADMAP's
explicit Out-of-Scope: "a second ordering mechanism would drift out of sync").
Output: `Tier` enum, `Tool.tier` field with hard-required validation, all 65 registry.toml
entries tagged, a resolver-proof test using a real cross-tier edge, and an architecture.md
statement locking in "tier is a label, requires is the order."
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|--------------|
| `installer/registry.toml` -> `load_tools` | Repo-tracked config file (trusted, human/AI-authored, git-reviewed) parsed into typed `Tool` objects; malformed data must fail closed with a clear, named error, never crash unpredictably or silently corrupt state. |
| `Tool.tier` -> downstream consumers | Once loaded, every reader (this phase's tests; Phase 2's future catalog_tui.py views; deps.py, which never reads it) assumes `tool.tier` is always a valid `Tier` member -- the only enforcement point is `load_tools`. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|------------------|
| T-01-01 | Denial of Service | `installer/model.py::load_tools` | low | accept | A fail-fast `ValueError` at startup on a missing/unknown `tier` is the intended D-03 behavior, not attacker-reachable input (`registry.toml` is a trusted, git-tracked file, not user/network-supplied); an identical, already-accepted risk exists today for `priority`/`audience`/`category`. |
| T-01-02 | Tampering | `installer/registry.toml` (65-entry backfill) | low | mitigate | A typo'd tier value (e.g. `"sytem"`) is caught by `_parse_enum`'s exact `StrEnum` match, raising a hard, named error instead of silently misclassifying a tool's bootstrap-order view -- reuses existing, already-implemented validation; no new code path needed. |
| T-01-03 | Tampering (injection) | `Tool.tier` values -> any downstream consumer | info | accept | `tier` values are validated `StrEnum` members consumed as plain attribute reads (`tool.tier`); they are never interpolated into a shell command, subprocess argv, or format string reaching `Runner`. Unlike `Method.params` (which already carries that responsibility for install commands, unchanged and out of scope here), `tier` introduces zero injection surface. |
| T-01-04 | Elevation of Privilege | `installer/deps.py::resolve_dependencies` (unmodified) | info | accept | `tier` never reaches any subprocess/Runner seam and this phase adds zero new branches to the resolver, per REQ-dependency-chain-requires's "zero new resolver logic" -- there is no code path by which `tier` could change what commands execute. |

No package-manager install tasks exist in this phase (no npm/pip/cargo installs, no new
dependencies) -- the package-legitimacy gate does not apply.
</threat_model>
