# Phase 24.2 Plan 06: `--run-schedule`, the in-group runner, Pi and the runner contract Summary

A timer can now call `setup.py --run-schedule update-<tool>`: the tool is updated once through the shared ownership-first `UpdateService`, one result line is printed, and the exit code matches. Pi updates through its reviewed host-setup command, copilot through its cask, OS-package and unknown owners are skipped, and a cursor-agent update keeps the model shim in place.

## What was built

- **Task 1 (tracer), `55383f1`:** `cli.Options` gained `run_schedule` and `parent_holds_run_lock` on its tail; `setup.main` routes `--run-schedule` first (no TTY needed, no repairs, builtin `print`); `schedule_run.run_schedule` re-resolves ownership, probes the version before and after with `version_status.probed_version` (renamed from `_probed_version`), and maps the outcome through `schedules.update_result_line`. `run.run_captured_in_group` (R2-04) keeps the vendor child in the process group the runner kills on a timeout, and `_build_services` takes a `runner` keyword for it.
- **Task 2, `966a7e1`:** `update.host_setup_update_argv` takes the reviewed `pnpm add ...` argv from the code-owned `HOST_SETUPS`; `_perform` runs it through `guards.real_pnpm` (a ban shim first on PATH is skipped); `update_refusal` refuses a pnpm-owned host-setup tool only when no reviewed command exists. The review (`build_plan`) and the catalog's `u` share that predicate, so both now offer Pi's update.
- **Task 3, `4627832`:** a run without `--parent-holds-run-lock` takes the run lock through `runlock.try_acquire` (`skipped: busy` when held, released in `finally`); a `cursor-agent` run checks `agent` before updating (`failed: ~/.local/bin/agent is missing or dangling`), then reads the model list outside any lock and refreshes the shim in the same state-lock critical section that reads the row's decision, saving the status only when it changed. The contract test proves the runner's child argv parses with `cli.parse_args`, its log lines read back through `read_last_runs`, a held lock logs `skipped: busy`, and its lock content reads back through `runlock.holder`.
