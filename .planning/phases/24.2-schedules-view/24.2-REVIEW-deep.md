# Phase 24.2: Deep Code Review (Schedules view)

**Reviewed:** 2026-11-13
**Depth:** deep (call chains traced across schedules → systemd_daemon/daemon → runner → setup.py `--run-schedule` → UpdateService)
**Status:** issues_found

## Summary

The engine is careful about atomic writes, symlink refusal, fingerprint-proved deletion and the
order of locks. I found no path that runs sudo, no way to inject into argv or unit text (`_quote`
rejects `" \ % $ CR LF`, plists go through plistlib, model ids use a closed character set and are
single-quoted in the shim), and no `platform_os` comparison against anything but `"macos"`.
The lock order holds: no flock is taken while the state lock is held.

The main defect is in the run contract, not the engine. With the default timing, all six
calendar schedules fire at the same instant and contend for a lock that is taken without
waiting. One job wins and five log `skipped: busy`, at every slot and at every catch-up. The
container e2e started units one at a time, so it could not see this.

The medium findings are gaps between the fakes and a real host:
- On macOS, launchd's bootout leaves the runner's child processes running.
- `uv cache prune` refuses to run while any `uv run` or `uvx` process is alive.
- The reconcile never refreshes or restores the copied runner.
- A damaged state file makes the full uninstall leave live timers behind.
- A failed read inside `update_state` erases the user's offs.

Four scratch tests reproduce MR-03, MR-04 and MR-05 against the real engine (scratch HOME,
fake systemctl), and one shell probe reproduces HR-01 with the real runner:
`/tmp/claude-1000/-var-home-bazzite-git-personal-tools-installer/954c3fb8-ff60-4af7-85b4-b39cda9abded/scratchpad/test_review_probe.py`
(4 passed).

Necessity was not assessed, because the caller asked for an HR/MR/LR schema.

## High

### HR-01: Default schedules fire together, and five of six log `skipped: busy` at every slot

**Files:**
- `installer/schedules.py:53-54,79-91` (every non-tmp schedule defaults to 6 h from 00:00)
- `installer/schedules.py:155-157` (identical `OnCalendar=`)
- `installer/systemd_daemon.py:236-248` (no `RandomizedDelaySec`, no ordering)
- `installer/helper_assets/schedule_runner.py:173-183,350-353` (`LOCK_EX | LOCK_NB`, then `skipped: busy`)

**Failure scenario:**
1. At 00:00, 06:00, 12:00 and 18:00, systemd elapses six timers with the same calendar in one
   coalesced wake (default `AccuracySec=1min`). launchd does the same for the same
   `StartCalendarInterval`.
2. Six `uv run … runner.py` processes start together. The first to reach `flock` wins and the
   other five log `skipped: busy` and exit 0.
3. Which job wins is a race, so a given update such as `claude` may not run for days.
4. A `Persistent=true` catch-up at login fires all of them at once too, so the "one catch-up
   run" (SPEC R4) is lost for five of the six.
5. The Linux tmp cleanup runs every 10 min and also takes the lock, which adds random
   collisions.

Reproduced: three runners started at once against one lock gave `start`, `skipped: busy`,
`skipped: busy`, `ok`.

The e2e (`schedules_run_one`) starts each unit alone, and `schedules_run_verdict` also accepts
`skipped`, so the gap stayed hidden. SPEC R8's "skipped: busy" rule, combined with R4's
identical defaults, is what defeats the phase goal of updating every tool every 6 h.

**Fix:** Serialize schedule-against-schedule contention instead of skipping it, and keep
`skipped: busy` for installer contention only. In the runner:

```python
# _run_lock: wait for a peer schedule run, skip only when the installer holds the lock
deadline = time.monotonic() + _PEER_WAIT  # e.g. 3600 s, longer than the sum of job timeouts
while True:
    try:
        fcntl.flock(fd, fcntl.LOCK_EX | fcntl.LOCK_NB); break
    except BlockingIOError:
        holder = _read_holder(fd)            # "<job> <pid> <iso>"
        if holder.startswith("installer ") or time.monotonic() > deadline:
            yield False; return
        time.sleep(5)
```

Also, or instead, stagger the default start minutes per schedule (00:00, 00:05, 00:10, …) and
add `RandomizedDelaySec=` to the calendar timer. Either way it needs a SPEC R8 amendment and an
e2e step that starts two units at once and expects two results.

## Medium

### MR-01: macOS bootout kills only the runner; its children keep running without the lock, and the mount reconcile triggers this on its own

**Files:**
- `installer/helper_assets/schedule_runner.py:143-150` (`start_new_session=True`)
- `installer/daemon.py:211-213` (`bootstrap` = bootout + bootstrap)
- `installer/schedules.py:1441-1451` (`_refresh_in_place` → `turn_on`)
- `installer/wizard_app.py:3664-3671` (`SCHEDULE_DEFAULTS` is not a cross-process holder)

**Failure scenario:**
1. By default, launchd kills the process group of the job it stops. The runner puts every child
   (`uv run setup.py`, then `claude update` and the rest) into a new session, so those
   processes escape the kill.
2. A bootout during a run kills `uv` and the runner. The runner's flock goes with it (the
   descriptor is close-on-exec), but the update keeps running.
3. The next timer, or the TUI's install run, then takes the lock while `claude update` is still
   writing. SPEC R8 says runs never overlap. The D-12 amendment assumes the bootout "stops that
   run"; in fact it stops only the runner.
4. A bootout happens on off and retime, which the amendment covers, and also on every TUI mount
   reconcile that finds a plist stale, which it does not. The TUI reconcile holds no run lock
   (`_CROSS_PROCESS` lacks `SCHEDULE_DEFAULTS`).
5. A plist turns stale for incidental reasons:
   - a new `~/.bun/bin` or `~/.opencode/bin` directory changes `clean_unit_path`;
   - `uv` resolves to a different path;
   - the launch shell has a different TMPDIR.

   When that happens, opening the installer during a scheduled update interrupts it mid-write.

Linux is not affected: systemd's `KillMode=control-group` kills the whole cgroup, and the
reconcile only restarts the timer.

**Fix:**
- In the runner, install a SIGTERM handler that forwards the signal to the current child's
  group (`os.killpg(proc.pid, SIGTERM)`), waits for the grace period, and then logs
  `failed: interrupted`.
- Have the TUI mount reconcile skip macOS refreshes while `runlock.holder(run_lock_path())`
  names a live schedule job, or take the run lock for the reconcile as the headless route does.

### MR-02: `uv cache prune` refuses to run while any uv process is alive, so cache cleanup fails routinely

**Files:**
- `installer/helper_assets/schedule_runner.py:50-55,263-289`
- `installer/schedules.py:816-821`

**Failure scenario:**
1. Commit a326c71 found that `uv run` holds the cache lock while it runs, and `uv cache prune`
   (uv 0.11.28: "--force  Force removal of the cache, ignoring in-use checks") waits on it until
   `UV_LOCK_TIMEOUT`, then fails.
2. The fix covered only the runner's own `uv run`. The same lock is held by:
   - `make setup` itself (`uv run --isolated … setup.py`) while the TUI is open;
   - every long-lived `uvx` or `uv run` MCP server an agent session keeps alive;
   - a user's dev server.
3. On this AI-dev host, at most slots the cache job waits about 5 min. It then logs
   `failed: uv cache prune exited 2 (pnpm, npm ok)` and the row shows a red `!`, every 6 h.

The fakes stand in for `uv` with a shell script, so this cannot show in the unit tests.

**Fix:**
- Do not add `--force`, because it deletes environments that are in use.
- Run `uv cache prune` with `UV_LOCK_TIMEOUT=<short>` in its environment.
- Classify the lock-timeout failure as a soft skip in the result line, for example
  `ok: pruned pnpm, npm; uv skipped: cache in use`, so it does not count as a failure.

### MR-03: The reconcile never refreshes or restores the copied runner and scripts; a deleted runner fails silently while the row reads `on`

**File:** `installer/schedules.py:1411-1438` (`_is_stale` compares the unit or plist text only)

**Failure scenario:**
- **A runner-only fix never reaches existing hosts.** A fix to `schedule_runner.py` or to a
  prune script that leaves `runner_argv` unchanged keeps the unit text identical, so
  `_is_stale` returns False and the copy in `~/.local/share/tools-installer/schedules/` stays
  the old version indefinitely. Only a manual toggle refreshes it. Probe
  `test_changed_runner_is_not_refreshed` passes.
- **A deleted runner is never restored or reported.** If `runner.py` is deleted (a cleaned
  `~/.local/share`, or `_remove_timer` deleting the shared assets while another schedule's
  unit was kept), every timer's `uv run --script` fails before the runner can write a log
  line. The log keeps its old last result and `row_state` reads `on`, because it checks only
  unit files. Probe `test_deleted_runner_is_not_restored` passes.

**Fix:** Count a shared asset as stale in `_is_stale`, and report a missing one in `row_state`
as drift:

```python
for source, target in _shared_pairs(ctx):
    if not target.is_file() or target.read_bytes() != source.read_bytes():
        return True
```

### MR-04: A damaged state file makes the full uninstall leave live timers, the runner and the update jobs behind

**Files:**
- `installer/schedules.py:1608-1618` (`_footprint`: non-tmp schedules are found only through
  `record.files`)
- `installer/schedules.py:1710-1723` (`sweep_adapters`)
- `installer/schedules.py:1591-1599,1639-1640` (the `.damaged` copy is deleted)

**Failure scenario:**
1. `schedules.json` fails to decode. Causes include:
   - a newer checkout's `version` or key, after a branch switch back to an older checkout;
   - a manual edit;
   - disk damage.
2. `load_state` returns defaults, so every update schedule has no recorded files.
3. `sweep_adapters` then finds no footprint for the `tools-installer-schedule-*` units, and
   `state.shared` is empty.
4. The full uninstall leaves behind the service and timer files, the wants links, `runner.py`
   and the scripts. It deletes `schedules.json.damaged`, which was the only record of them.
5. The timers keep firing and keep running `claude update` and the other updates through the
   checkout after the user uninstalled. Probe `test_damaged_state_uninstall_leaves_units`
   passes.

**Fix:** In `_footprint` and `_sweep_schedule`, fall back to the installer-namespaced names
when the record is empty: `unit_paths(unit_dir, basename_for(id))` and the wants link on Linux,
`_plist_path` on macOS. Remove those files with bootout plus unlink, the same way tmp cleanup
is "ours by name". In `_cleanup_if_last`, also remove `_shared_pairs` targets whose bytes equal
the checkout source. Keep `.damaged` until the sweep has succeeded.

### MR-05: A failed read inside `update_state` saves defaults with no `.damaged` copy, so the next reconcile turns the user's offs back on

**Files:**
- `installer/schedules.py:345-360` (OSError / non-regular / oversized → defaults and a warning,
  with no copy kept)
- `installer/schedules.py:392-397` (`update_state` ignores the warning and saves)

**Failure scenario:**
1. The user turned `update-opencode` off.
2. Any later state write, such as `after_target_removed` or the reconcile's gone-target drop,
   meets a failed read: EACCES, EIO, a symlinked state file, or a file over 1 MiB.
3. `load_state` returns `ScheduleState()` and a warning, but writes no `.damaged` copy, because
   it never had the bytes.
4. `update_state` saves those defaults over the real file, and the decision `false` is gone.
5. The next `ensure_schedule_defaults` loads a valid file with no damage flag and turns
   `update-opencode` back on. Probe `test_unreadable_state_is_overwritten_with_defaults`
   passes.

This is the exact guarantee "the reconcile never re-enables a user's off", lost through a
side door.

**Fix:** `update_state` must refuse to save when the load returned a warning:

```python
loaded = load_state(path)
if loaded.warning is not None:
    raise OSError(loaded.warning)
```

Alternatively, `load_state` can create the `.damaged` marker for every warning, not only for
decode errors, so the sticky flag covers this case too.

## Low

### LR-01: A retime of macOS tmp cleanup before the first reconcile saves the time but leaves the plist; the next reconcile then overwrites the user's time

**Files:**
- `installer/schedules.py:1257-1263` (`is_on = record.decided is True`)
- `installer/schedules.py:1394-1408` (`_seed_legacy_start`)

**Failure scenario:**
1. An adopted tmp cleanup has `decided` None, but the row reads `on` by name.
2. The Schedules view is open from a route with no reconcile (`make doctor`'s TUI, `--guard`,
   or uninstall).
3. `e` saves 05:30 in the state, and the view's Next cell says 05:30. The plist still runs at
   03:00.
4. The next `make setup` reconcile runs `_seed_legacy_start`, which reads the plist (03:00) and
   overwrites the saved 05:30.

**Fix:** For tmp cleanup, compute `is_on` as `row_state(...).word == "on"`, or
`record.decided is True or _tmp_unit_present(ctx)`.

### LR-02: A retime of a Linux drift row adopts a modified `.service` file, or leaves the timer and the state out of step

**File:** `installer/schedules.py:1259-1263`

**Failure scenario:**
- `_refuse_change` allows drift rows. `timer_only=True` rewrites only the timer, and
  `_fingerprint_unit` then re-fingerprints the drifted service, so the modified file is now
  recorded as ours.
- If the service file was deleted instead, `_fingerprint` raises after `bootstrap` has
  registered the new grid. The state keeps the old interval while the timer on disk has the
  new one.

**Fix:** Refuse retime on drift rows ("press space to rewrite first"), or rewrite the full pair
when the record does not match.

### LR-03: `clean_stamp` during a retime likely does nothing, because the timer is still active

**Files:**
- `installer/schedules.py:924-926`
- `installer/systemd_daemon.py:370-379`

**Failure scenario:**
1. `systemctl clean` refuses a unit that is not inactive or failed (systemd's `unit_clean`
   returns EBUSY). The timer is active at this point, and the error is suppressed.
2. The old grid's stamp survives, so a new slot that falls between the last trigger and now
   fires immediately at `restart`.
3. The result is an unexpected run right after a retime.

This was not verified against a live systemd. `schedules_stamp_observation` could confirm it.

**Fix:** Run `stop` on the timer, then `clean`, then `bootstrap`; or drop the clean and record
the catch-up behaviour as intended.

### LR-04: A failed first registration after a runner change leaves rewritten shared assets with stale fingerprints

**File:** `installer/schedules.py:1086-1095`

**Failure scenario:**
1. `_ensure_shared_assets` overwrites `runner.py` with new checkout bytes.
2. `_register` fails. Only files the call newly created are removed; overwritten files keep the
   new bytes, while `state.shared` keeps the old sha256.
3. If no later `turn_on` succeeds, the last off or the full uninstall refuses `runner.py` as
   "kept, changed since it was copied" and leaves it on disk.

**Fix:** On a registration failure, restore the overwritten assets to their previous bytes too
(`_ensure_shared_assets` already has `previous`), or save the new `shared` fingerprints before
`_register`.

### LR-05: The launching process's TMPDIR is baked into every unit and drives refresh churn

**Files:**
- `installer/schedules.py:606` (`tmpdir`)
- `installer/schedules.py:836-838` (`_unit_environment`)

**Failure scenario:**
1. Update and cache jobs do not need the launcher's TMPDIR, but they get it. A launch from a
   shell with a session-scoped TMPDIR (an agent sandbox, a toolbox, a private tmp) writes that
   directory into all seven units.
2. When the session ends the directory is gone, and `uv run` and the installer child fail.
3. Every launch from a shell with a different TMPDIR makes `_is_stale` true for all units,
   which rewrites them; on macOS that is a bootout (MR-01).

**Fix:** Bake TMPDIR only into the tmp-cleanup unit, or resolve it once (the per-user default)
instead of reading it from the launching environment.

### LR-06: The runner's child environment drops proxy and CA variables

**File:** `installer/helper_assets/schedule_runner.py:127-130`

**Failure scenario:**
1. Only PATH, HOME, TMPDIR and LANG reach the children, and the unit environment is closed to
   PATH, HOME and TMPDIR.
2. On a host behind a proxy (`HTTPS_PROXY`, `NO_PROXY`, `SSL_CERT_FILE`, `REQUESTS_CA_BUNDLE`),
   every scheduled update and `brew cleanup` fails. The interactive `u` works on the same host.

**Fix:** Forward a closed allowlist of network variables when the systemd user manager or the
launchd job provides them.

### LR-07: A stale holder line plus a reused PID reads as a live scheduled run

**File:** `installer/runlock.py:80-98`

**Failure scenario:**
1. A runner killed by SIGKILL (macOS bootout escalation, OOM) leaves its holder line.
2. If the PID is later reused by any process, `holder()` reads alive.
3. The view shows `running` for that job when its newest log line is a start, and
   `refuse_if_mutating(cross_process=True)` refuses installs with "A scheduled run is running".
   This lasts until that unrelated process exits.

**Fix:** Have the holder line carry the process start time (`/proc/<pid>/stat` field 22, or
`ps -o lstart` on macOS) and compare it. Alternatively, trust the holder line only when a
non-blocking `flock` probe fails, from code paths where a probe is safe (not from the render
path).

### LR-08: Test gaps on risky code

**Files:** `tests/test_schedule_runner.py`, `tests/test_schedules_lifecycle.py`,
`scripts/container-e2e-verify.sh:200-231`

**Gaps:**
- No test fires two schedule runs together (HR-01). The e2e runs units one at a time and
  accepts `skipped`.
- No reconcile test changes the runner or prune script bytes, or deletes them (MR-03).
- No sweep test runs with a damaged or unreadable state (MR-04, MR-05).
- No macOS test covers what survives a stop signal to the runner (MR-01).
- No test uses a real `uv` cache lock (MR-02); the e2e cache job ran with no other uv process
  alive.

**Fix:** Add the four probes in the scratch file above as regression tests once the fixes land,
plus an e2e step that runs `systemctl --user start` on two calendar services in parallel and
expects two non-busy results.
