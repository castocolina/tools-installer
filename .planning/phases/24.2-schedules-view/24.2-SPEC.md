## Goal

A seventh view, Schedules, turns the upkeep the user does by hand into user-level timers he can switch on and off and re-time: cache cleanup, the existing tmp cleanup, and updates of claude, opencode, Pi, cursor-agent and copilot every 6 h from 00:00. The cursor-agent update keeps a model-defaulting shim in place of the `cursor-agent` symlink.

## Requirements

1. **Schedules view (SCHED-01)**: A seventh `VIEWS` row, Schedules (number key 7, mode LIVE), lists the built-in schedules in a fixed order with name, script, target, state, interval and start, next run, and last run with its result.
   - Current: There is no Schedules view. The only recurring job is a Policies row.
   - Target: Schedules is reached like every other view, through `UnifiedApp.show_view`. Each row reads `on`, `off`, or `unavailable: <reason>` (target not installed, or no user timer manager). Space toggles a row and applies at once through `run_live`. A key edits the interval and start time of the focused row.
   - Acceptance: Pressing `7` shows the view with one row per built-in (R2). A row whose target is missing reads `unavailable: <tool> not installed` and cannot be toggled on. Toggling an available row changes its state cell and the timer on disk in the same action.

2. **Built-in schedules and what they run (SCHED-02)**: The built-ins are tmp cleanup, cache cleanup, and the claude, opencode, pi, cursor-agent and copilot updates.
   - Current: Only the tmp cleanup exists, as a Policies row.
   - Target:
     - tmp cleanup is the existing daemon, unchanged in what it deletes.
     - cache cleanup runs each package manager's own documented prune command, each only when that manager is installed: `uv cache prune`, `pnpm store prune`, `brew cleanup`, and npm's own cache verification. npm runs as the real npm binary, never through the guard shim.
     - Each update runs that one tool's update (R6).
   - Acceptance: A cache-cleanup run on a host with only uv and pnpm runs exactly those two prune commands and logs one line for each. A host with none of the managers logs `ok: nothing to clean`. No other path is deleted.

3. **Default on, the user's choice kept (SCHED-01)**: A schedule is on by default when its target is installed. Once a decision is recorded, the installer never changes it on its own.
   - Current: Only the daemon has this rule, through a decided marker in `~/.myshellrc`.
   - Target:
     - The first installer run (TUI or headless) that finds a schedule's target installed, with no decision recorded, turns the schedule on and records the decision.
     - A schedule the user turned off stays off on every later run.
     - A target that later disappears takes its timer with it. The row reads unavailable, and the recorded decision is kept for a reinstall.
     - A host that already has the tmp-cleanup timer and decided marker shows tmp cleanup as `on`, with no second unit.
   - Acceptance:
     - On a scratch HOME with claude present and no decision, one run leaves the claude-update timer on disk and a decision recorded.
     - After the user turns it off, a second run leaves it off.
     - Removing claude removes its timer, and the row reads unavailable.
     - The existing `tools-installer-prune-tmp` units are adopted unchanged.
   - *Amended 2026-11-07 (24.2 D-08):* "adopted unchanged" means adopted by name: the `tools-installer-prune-tmp` units (and the macOS `com.tools-installer.prune-tmpdir` agent) keep their names and are rewritten in place with one restart, so they use the copied scripts, the shared log and the lock (R5, R8), with no second unit and no off/on gap.

4. **Interval and start time (SCHED-02)**: Cache cleanup and every update default to every 6 h starting at 00:00. The user can set the interval to a whole number of hours that divides 24 (1, 2, 3, 4, 6, 8, 12, 24) and a start time HH:MM.
   - Current: Only the macOS daemon has an editable hour and minute. The Linux daemon is fixed at 10 min.
   - Target:
     - Runs fall on the same clock times every day: start, start + interval, and so on, wrapping at 24 h.
     - A run missed while the machine slept or was off runs once at the next wake or login, never once per missed slot.
     - tmp cleanup keeps its own cadence: Linux every 10 min; macOS daily at its editable hour and minute.
   - Acceptance:
     - Default: next runs at 00:00, 06:00, 12:00 and 18:00 local time.
     - Interval 8 with start 01:30 gives 01:30, 09:30 and 17:30.
     - An interval of 5, 0 or 25, or a start of 24:00, is rejected with a message, and the timer on disk is unchanged.
     - After a missed slot, exactly one catch-up run is logged.
   - *Amended 2026-11-07 (24.2 D-05):* on macOS, launchd catches up a slot missed during sleep only; a slot missed while the Mac was powered off is not run, and the next slot runs on time. The view's note says so. Linux catches up after both sleep and power-off (at the next login).

5. **User-level timers, receipts, removal (SCHED-03)**: Each on schedule is one user-level timer: a systemd user `.service` + `.timer` pair on Linux, a launchd agent in `~/Library/LaunchAgents` on macOS.
   - Current: Only the daemon's units exist, and they have no receipt.
   - Target:
     - Unit and plist files and the installed schedule scripts are written atomically and recorded in a receipt.
     - Turning a schedule off stops it and removes exactly its recorded files.
     - The full uninstall removes every schedule's files and receipt.
     - Self-contained schedule scripts are copied into the user's data dir with an ownership sentinel, so a moved or deleted checkout does not break them.
     - A host without a user timer manager shows every row as `unavailable: <reason>` and writes nothing.
     - No code path runs `sudo`, `pkexec` or `doas`.
   - Acceptance:
     - Turning a row on in a scratch HOME (fake `systemctl`/`launchctl`) writes the unit pair or plist and a receipt naming them. Off deletes exactly those files.
     - `make uninstall`-path tests leave no schedule file, script or receipt.
     - A grep of the new code finds no privilege-escalation command.

6. **Update runs follow the catalog's update rules (SCHED-02, SCHED-03)**: An update run updates its one tool through the same ownership-first path as the catalog's `u`, run headless.
   - Current: Updates run only from the TUI (`UpdateService`).
   - Target:
     - The run re-resolves ownership.
     - A tool owned by an OS package manager or SDKMAN is not updated. The run logs that refusal as `skipped: <owner> owns <tool>`.
     - An up-to-date tool logs `ok: up to date`.
     - Post-install steps and install tuning run exactly as after a manual update.
     - If the installer the run calls is missing (moved checkout), the run logs `failed: installer not found at <path>`.
   - Acceptance:
     - With fakes, a script-owned claude run calls `claude update` once.
     - A pacman-owned opencode run calls no package manager and logs the skip.
     - A run with the checkout path removed logs the failure line and exits non-zero.
   - *Amended 2026-11-07 (24.2 D-16):* a tool installed through a reviewed host-setup handoff (Pi) is updated by re-running that reviewed host-setup command through the shared update path, so the catalog's `u` and the schedule both update it instead of refusing.

7. **cursor-agent model shim (SCHED-04)**: When the cursor-agent schedule is turned on, and after every cursor-agent update run, a `~/.local/bin/cursor-agent` that is a symlink is replaced atomically by the installer's shim.
   - Current: Both links point to the same release launcher. No shim exists.
   - Target:
     - Without `--model`/`--model=`, the shim runs cursor-agent with the configured default model. With one, it passes the arguments through unchanged.
     - The shim always execs the launcher that `~/.local/bin/agent` resolves to at that moment, by absolute path, so an update that relinks only `agent` is picked up.
     - `~/.local/bin/agent` is never modified.
     - A `cursor-agent` that is a regular file without the installer's sentinel (the user's own shim) is left alone and logged.
     - Turning the schedule off restores `cursor-agent` as a symlink to `agent`'s target.
     - Removing cursor-agent removes the shim.
     - The default model is `gpt-5.6-sol-xhigh` and can be changed from the view. **Needs confirmation:** the user asked for `gpt-6.1-sol`, which is not in the model list.
     - When the account's model list (`cursor-agent --list-models`, no tokens) does not contain the configured model, the shim is written as a plain pass-through and the run logs a warning that the view shows.
     - When the list cannot be read (offline, logged out), the shim keeps the configured model and logs `model unverified`.
   - Acceptance:
     - In a scratch HOME with a fake release dir, `cursor-agent -p hi` execs the launcher with `--model gpt-5.6-sol-xhigh -p hi`. `cursor-agent --model sonnet -p hi` and `--model=sonnet` exec it with the arguments unchanged.
     - After `agent` is relinked to a newer release, the shim runs the newer launcher.
     - A foreign regular file survives a run byte-for-byte.
     - Turning the schedule off leaves a symlink equal to `readlink agent`.
   - *Amended 2026-11-07 (24.2 D-19):* each shim write and each symlink restore re-records the `~/.local/bin/cursor-agent` entry in cursor-agent's install receipt, so cursor-agent's own update and removal keep working with the shim in place.

8. **Run log and last result (SCHED-05)**: Every run appends a timestamped start line and one result line (`ok …`, `skipped: <reason>` or `failed: <reason>`) to a size-capped log. The view's last-run cell shows the latest result per schedule. Runs never overlap.
   - Current: Only the daemon logs (`prune-daemon.log`, capped). Policies shows its "deleted: N" summary.
   - Target:
     - One lock serializes all schedule runs and the installer's own apply and update work.
     - A run that finds the lock held logs `skipped: busy` and exits 0.
     - The log never grows past its cap.
   - Acceptance:
     - After a run, the log's last two lines for that schedule carry an ISO-8601 local timestamp and the result, and the view shows that result and time.
     - A run started while the lock is held logs `skipped: busy`.
     - A log at the cap is trimmed, never grown.
     - A container e2e runs each available built-in once through its installed script and checks its log lines and the view's last-run cell.
   - *Amended 2026-11-07 (24.2 D-26):* the container e2e runs in a container target that boots systemd with a user manager for the test user, so units are written, started and logged for real; if plan-time research shows rootless podman cannot run that target, the fallback runs each copied runner job directly and that gap is recorded.

9. **Policies hands the tmp cleanup over**: The tmp-cleanup daemon row leaves Policies. `cache-redirect:bun` stays in Policies.
   - Current: Policies has 7 rows on Linux and 5 on macOS (23.2 R7), including the daemon row.
   - Target:
     - Policies lists the 23.2 kept ids minus the daemon row: 6 on Linux, 4 on macOS.
     - Schedules owns the daemon's on/off, its decided marker and its units.
     - The headless competing-mechanism notice and the daemon-default worker move with it.
   - Acceptance:
     - The composed Policies list has no `daemon:` id.
     - The Schedules tmp-cleanup row toggles the same units the Policies row toggled.
     - An existing on daemon stays on across the upgrade.

## Boundaries

**In scope:**
- The Schedules `VIEWS` row and screen, toggle and re-time through `run_live`
- Seven built-ins: tmp cleanup (adopted from Policies), cache cleanup, and claude, opencode, pi, cursor-agent and copilot updates
- systemd user units and launchd agents per schedule, receipts, removal on off and on full uninstall
- A headless single-tool update entry the timers call, using the existing ownership-first update path
- The cursor-agent shim, its default model setting and its removal paths
- Run log with cap, last-run cell, one run lock shared with installer apply and update
- Moving the daemon row out of Policies and amending 23.2's Policies counts
- Unit tests in a scratch HOME with fake `systemctl`/`launchctl`; a container e2e of the run contract

**Out of scope:**
- User-defined schedules or custom scripts — the user asked for built-ins with a default script each
- Deleting agent version dirs, browser caches (Playwright, puppeteer) or data dirs (`~/.local/share/opencode`, `~/.claude`) — no proof they are unused; a running session can still load them
- Enabling systemd linger — it can need privilege; the view says user timers run while the user is logged in
- Moving `cache-redirect:bun` — a static environment setting, not a recurring job
- Updating codex, pnpm or other catalog tools on a schedule — not requested; the catalog's `u` covers them
- Copilot's catalog entry — Phase 23.2 (TUNE-06); this phase depends on it
- A desktop notification for failed runs — not requested; the log and the view show it

## Constraints

- Zero sudo. Every timer is per-user. A host without a user timer manager degrades to `unavailable`.
- Unit tests never touch the real HOME, real `systemctl --user` or real `launchctl` (23.1 sandbox). A real timer is exercised only in a disposable container.
- `UnifiedApp.show_view` is the only navigation path, `run_live` the only apply path, and `VIEWS` the only view list (`.claude/architecture.md`). `setup.py` stays wiring only.
- Writes go through the existing atomic writers. Ownership of the shim and the copied scripts is sentinel-checked, like the daemon wrapper (`daemon.py:294-344`).
- The shim must keep the launcher's own behaviour: `realpath`-based lookup and `CURSOR_INVOKED_AS`.
- Depends on Phase 23.2 (copilot entry, kept Policies list) and Phase 24.1.
