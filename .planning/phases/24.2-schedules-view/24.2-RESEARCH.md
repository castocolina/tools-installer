### Locked Decisions

- **D-01: The seven built-ins are a closed Python table in a new `installer/schedules.py`, not `registry.toml`.** Each row holds id, label, target tool id (or none), job kind, default interval and start, and platforms. A registry test checks every target id against the catalog.
- **D-02: `installer/systemd_daemon.py` and `installer/daemon.py` take a unit basename / launchd label instead of the hard-coded names, and the Linux renderer gains an `OnCalendar=` + `Persistent=true` timer form next to today's monotonic form.**
- **D-03: Unit names.** New units are `tools-installer-schedule-<id>.{service,timer}`, and new launchd labels are `com.tools-installer.schedule.<id>`. The adopted tmp cleanup keeps `tools-installer-prune-tmp` and `com.tools-installer.prune-tmpdir`.
- **D-04: One pure slot function turns (interval, start) into the sorted daily (hour, minute) list.** It renders `OnCalendar=*-*-* H1,H2,…:MM:00` with `Persistent=true` on Linux, and an array of `{Hour, Minute}` dicts in `StartCalendarInterval` on macOS. The `start/step` hour form is never used.
- **D-05: macOS power-off catch-up is a launchd limitation, and the SPEC says so** (SPEC R4 amended).
- **D-06: One validated JSON state file, `~/.local/state/tools-installer/schedules.json`**, holds each new schedule's `decided`, interval, start, recorded files (D-07), the cursor default model (D-20) and the checkout and `uv` paths baked at apply time. The tmp-cleanup decision keeps living in the two existing `~/.myshellrc` marker blocks, read and written in place with no migration.
- **D-07: A schedule's files (unit pair or plist, wants link, copied runner and scripts) are recorded inside `schedules.json` as absolute paths with sha256, through `receipts.fingerprint`/`matches`. Off and the sweep delete them through `uninstall.remove_paths`.**
- **D-08: The existing tmp units are adopted by name and rewritten in place with one `restart`, never disabled and re-enabled.**
- **D-09: `ensure_daemon_default` / `DaemonDefaultWarnings` become one reconcile pass, `ensure_schedule_defaults`, in `schedules.py`.** It runs in the wizard's on-mount worker, after each install run, and after `run_wizard` on the headless `--all/--categories` route. `MutationHolder.DAEMON_DEFAULT` becomes a schedules holder.
- **D-10: Every timer runs `uv run --no-project --script <data>/tools-installer/schedules/runner.py <job> …`.** The runner generalizes `installer/helper_assets/prune_daemon_runner.py`: stdlib only, PEP 723 `requires-python>=3.11`, sentinel header. The runner owns the lock, the start and result lines, and the cap. The old `~/.local/bin/tools-installer-prune-daemon` wrapper is removed after adoption.
- **D-11: One shared line log, never past the cap.** `~/.local/state/tools-installer/schedules.log` on Linux, `~/Library/Logs/tools-installer/schedules.log` on macOS. The file is trimmed *before* the append.
- **D-12: The lock is `fcntl.flock(LOCK_EX | LOCK_NB)` on `~/.local/state/tools-installer/run.lock`.** The runner logs `skipped: busy` and exits 0 when it is held. The TUI takes it in `MutationLock.begin_mutation` for `INSTALL_RUN`, `UPDATE`, `REMOVAL` and `GLOBALS_REINSTALL`. Schedule and Policies toggles take only the in-app lock.
- **D-13: Last run comes from parsing the shared log.** No `systemctl show` or `launchctl print`: render must not spawn.
- **D-14: `cli.Options` gains `--run-schedule <id>`, routed by `setup.py` to `schedules.py`.** An update job calls `UpdateService.run` and prints exactly one result line.
- **D-15: Cache cleanup runs inside the stdlib runner.** `uv cache prune`, `pnpm store prune`, `brew cleanup`, `npm cache verify`, each only when it resolves on the unit's PATH, failures isolated. npm is found by walking PATH and skipping files carrying `# tools-installer-ban-shim`.
- **D-16: Pi updates by re-running its reviewed host-setup command through the shared update path** (SPEC R6 amended).

- **D-18: Model ids are checked against a closed character set `[A-Za-z0-9._-]` plus `[ ] = ,`, single-quoted in the script.**
- **D-19: Every shim write and every restore re-fingerprints the `~/.local/bin/cursor-agent` leaf in cursor-agent's install receipt, through a small receipts helper under `_WRITE_LOCK`.**
- **D-20: `cursor_default_model` lives in `schedules.json` (default `gpt-5.6-sol-xhigh`, needs confirmation).** The view edits it with a picker filled by `cursor-agent --list-models` on a thread worker.
- **D-21: A new `SchedulesScreen(AppScreen)` fed by a `ScheduleInputs` dataclass, plus one `VIEWS` row (`name="schedules"`, label Schedules, mode `LIVE`, key 7).** `Policy` is not extended.

- **D-23: Policies drops the daemon row.** The uninstall sweep receives one `schedule:<id>` `Policy` adapter per owned schedule through `extra_policies`. The now-unused Policies job-state machinery is deleted. `TimerStateCache` keeps feeding Doctor's disk-pressure probe.

## Summary

The phase is mostly composition of mechanisms the repo already has (atomic writers, sentinel-owned copies, bounded systemctl queries, `run_live`, `UpdateService`, receipts fingerprints). Three things are new to the repo: a calendar-form timer, a cross-process `flock`, and `Select`/`Input` widgets (first use; verified working at the locked Textual 8.2.7). The expensive part is not the new code. It is moving the tmp-cleanup daemon out of Policies: `tests/` mentions the daemon in 30 files (about 4,500 lines of dedicated daemon tests plus 151 mentions in `test_setup.py` and 212 in `test_wizard_app.py`), and `PoliciesScreen`, `setup.py`, `policy.py` and the uninstall sweep all carry daemon-specific branches.

Research found one **critical defect in a locked decision** (F1): D-17's "write the shim with `atomic_write_bytes(..., mode=0o755)`" overwrites cursor-agent's real release launcher when `cursor-agent` is a symlink, because `atomic_write_bytes` resolves a symlink before replacing. Verified live in a scratch dir. After that write `agent` would run the shim and the shim would exec itself. The shim must be installed with a sibling temp and `os.replace` onto the link path, never through `atomic_write_bytes`. Smaller findings (F2-F10) below also change plan content.

**Primary recommendation:** build bottom-up in pure, fake-seamed layers (slots/validators/state, then runner, then shim, then parameterized unit writers, then apply/reconcile engine, then lock, then view), and do the Policies handover last as its own two-plan wave so the existing daemon tests keep guarding the writers until Schedules row 1 provably replaces them.

### Pattern 1: slot grid (D-04)
**What:** `slots(interval, start) -> tuple[tuple[int,int], ...]`: hours `(start_h + k*interval) % 24` for `k in range(24 // interval)`, sorted, same minute. Linux renders `*-*-* HH,HH,...:MM:00`; macOS renders a list of `{"Hour","Minute"}` dicts. Validation is `interval in {1,2,3,4,6,8,12,24}` and `re.fullmatch(r"([01]\d|2[0-3]):[0-5]\d", s)`.
**Verified outputs (`systemd-analyze calendar`, systemd 262, 2026-11-13):**
- `*-*-* 00,06,12,18:00:00` -> Normalized `*-*-* 00,06,12,18:00:00`; iterations 12:00, 18:00, 00:00, 06:00.
- interval 8 start 01:30 -> `*-*-* 01,09,17:30:00` -> 17:30, 01:30, 09:30, 17:30. Matches SPEC AC.
- interval 6 start 23:30 -> `*-*-* 05,11,17,23:30:00` -> 11:30, 17:30, 23:30, 05:30 (wraps at midnight).
- interval 24 start 03:30 -> `*-*-* 03:30:00`. interval 1 -> a 24-hour list parses.
- `*-*-* 23/6:30:00` -> `Failed to parse calendar specification ... Invalid argument`. `*-*-* 00/6:00:00` parses, so the start/step form only works from a grid-aligned start: confirms D-04's "never use it".
- `*-*-* 24:00:00` -> `Invalid argument` (the HH:MM validator must reject `24:00` itself too).
[VERIFIED: `systemd-analyze calendar`, probe script `calendar_probe.sh`]

### Pattern 3: macOS plist
`StartCalendarInterval` accepts "dictionary of integers or array of dictionary of integers" with keys Minute, Hour, Day, Weekday, Month; missing keys are wildcards. [CITED: launchd.plist(5) at https://www.manpagez.com/man/5/launchd.plist/]. An array of N `{Hour, Minute}` dicts is therefore the right shape for a multi-slot grid. `read_schedule` (`daemon.py:221-243`) currently accepts only the single-dict form and must learn the array form.

### Anti-Patterns to Avoid
- **Using `atomic_write_bytes` for the shim** (F1).
- **Computing home-derived paths as module constants inside `installer/`.** The conftest re-roots only `setup.py` attributes of type `Path` (`tests/conftest.py:296-316`). A module constant such as `Path.home() / ".local" / ...` in `installer/schedules.py` is evaluated at import, before `sandboxed_home`, and would point tests at the real HOME. Follow `settings.default_settings_path()` (computed at call time), or take paths as parameters from `setup.py`.
- **Rendering the Next/Last cells with a spawn** (`systemctl list-timers`, `launchctl print`): D-13.

## Common Pitfalls

### Pitfall 1: the shim write replaces the launcher (F1)
**What goes wrong:** `agent` and `cursor-agent` run the shim, which execs `agent`'s target (itself): an exec loop, and the release dir is corrupted.
**How to avoid:** entry-replacing atomic write; test asserts launcher bytes and `agent` link unchanged and `cursor-agent` is a regular 0755 file.
**Warning signs:** `agent` stops working right after the schedule is turned on.

### Pitfall 2: host mutation from tests (the hard rule)
**What goes wrong:** a test calls real `systemctl --user`, `launchctl`, `uv`, `cursor-agent`, or writes real units.
**Why it cannot happen by accident:** the Popen guard refuses these names unless the program resolves under pytest's base temp (`tests/sandbox.py` `FORBIDDEN_PROGRAM_NAMES` includes `uv`, `claude`, `opencode`, `cursor-agent`, `copilot`, `brew`, `npm`, `pnpm`, `systemctl`, `launchctl`; `CHECKOUT_SCRIPTS` allows only `install.sh` and the three prune scripts). A refusal fails the test even when production code catches it (`refusals_fail_the_test`).
**How to avoid:** schedule/unit tests use recording `Runner`/`OutputRunner` closures (zero processes), like `tests/test_policy_linux_daemon.py:30-60`. Runner tests plant fake `uv/pnpm/brew/npm/claude` executables under `tmp_path` and import the runner in-process. Shim tests run `bash <tmp>/cursor-agent` with a fake launcher under `tmp_path` (the guard allows a script under the base temp; the shell's own children are not guarded, so the sandboxed PATH is the net). Never add the new runner or shim to `CHECKOUT_SCRIPTS`: tests run copies under `tmp_path`.
**Real timers:** exercised only in a disposable container (orchestrator).

### Pitfall 3: the real-HOME fingerprint
`tests/home_fingerprint.py` already watches `.config/systemd/user`, `.local/bin`, `.local/state/tools-installer/receipts`, `.local/state/tools-installer/config`, `.local/opt`. D-25 wants to add `schedules.json`, `schedules.log`, `run.lock`. **Do not watch `schedules.log` or `run.lock`**: once the phase ships and the developer's real timers run, the runner touches them every few minutes (the live prune log was modified at 11:05 and is at its cap), which would fail unrelated test runs ("If an entry was written by another program running at the same time ... re-run"). Watch the data dir listing (`.local/share/tools-installer/schedules`), `schedules.json` (installer-written only), and `~/Library/LaunchAgents` (macOS). Also keep trims by temp+replace rare (dir mtime churn).

### Pitfall 4: module-level HOME constants (see Anti-Patterns)
Only `setup.py` attributes are auto re-rooted. New `installer/` code must compute paths at call time or accept them as parameters.

### Pitfall 5: flock semantics
- `flock` is per open file description, so a second `open()` in the same process contends with the first. This makes "busy" testable in-process: hold the lock through one fd in the test, run the runner, expect `skipped: busy` and exit 0 [ASSUMED standard flock behaviour; confirm in the first test].
- Python fds are non-inheritable by default (PEP 446) and `subprocess` defaults to `close_fds=True`, so a child (the update installer) does not inherit and keep the lock [CITED: Python docs].
- The TUI holds the lock only for the mutation duration, never for the whole session, otherwise timers would skip all day while the wizard is open. Always release in `finally`; a crashed TUI is released by the kernel.
- For the view's `running` cell do **not** take a flock probe every 30 s from the UI (it can make a runner see `busy` in a microsecond window). Have the runner write `<job> <pid> <iso>` into `run.lock` after acquiring; the view reads that content and checks pid liveness (`os.kill(pid, 0)`). Use the flock probe only at the TUI mutation seam, where it needs authority.
- Hold the log lock (F5) around trim+append.
- `begin_mutation` raises on a second take and "every caller refuses first": extend `refuse_if_mutating(screen, *, cross_process=False)` and pass `True` at the four sites above; have `begin_mutation` acquire the flock for the four holders and raise a typed error only if it loses a race.

### Pitfall 6: `Persistent=true` and re-timing
The stamp (`~/.local/share/systemd/timers/stamp-<timer>.timer`, mtime = last trigger) is created on the first trigger, so a brand-new timer has no catch-up; a timer left behind by an off schedule keeps its stamp. Per the man page the service fires immediately on activation when a slot elapsed since the stamp. Consequences: (a) turning a schedule off should run `systemctl --user clean --what=state <timer>` while the unit is still loaded, before its files are deleted (the man page says to do this before uninstalling a timer); (b) re-timing (interval or start edit) rewrites the unit and restarts the timer, which can trigger an immediate catch-up run if the stamp predates the new grid's last slot. Recommend `clean --what=state` before the restart on a re-time so "next run at HH:MM" in the status line is true, and a test in the systemd container (D-26). The adopted tmp timer is monotonic (`OnBootSec`/`OnUnitActiveSec`) and unaffected. Whether an in-place rewrite plus `restart` keeps the stamp is [ASSUMED from the man page: the stamp is a separate file keyed by timer name, and only `clean`/disable-with-state removes it]; the container e2e settles it.

### Pitfall 7: unit hygiene
- Use a clean PATH (F4). Also set `TMPDIR`/`HOME` like today.
- systemd's default `AccuracySec=` is 1 min, so a run can start up to a minute after the slot; the Next cell is to the minute, so no change needed. [ASSUMED from systemd.timer defaults]

### Pitfall 9: the cursor shim
- Sentinel check: read only the first few KiB and match a header line, never `sentinel in path.read_text()` of an arbitrary regular file (the daemon's `_is_our_wrapper`, `daemon.py:294-298`, does the latter; a binary raises `UnicodeDecodeError` and reads False, which is safe, but a foreign script that merely mentions the sentinel would count). `is_symlink()` first: `read_text` follows links into the launcher.
- Exec the absolute target (no `exec -a "$0"`): the launcher computes `SCRIPT_DIR` from `realpath "$0"` and sets `CURSOR_INVOKED_AS` from `basename "$0"` before it runs.
- Use `[[ ... ]]`-free POSIX tests where possible so the shim runs under the sandbox's bash and macOS bash 3.2 (`set -u` with empty arrays on bash 3.2 errors on `"${arr[@]}"`; avoid arrays or guard them).
- `cursor-agent update` (the registry's declared `update` argv) resolves, through `_declared_leaf` (`update.py:466`), to the declared leaf `~/.local/bin/cursor-agent` and so runs **through the shim** as `--model <m> update`. SPEC records that a root `--model` before a subcommand is accepted (`--model X update --help` ran). Whether the vendor `update` relinks `cursor-agent`, `agent` or both was **not** exercised (it mutates); D-17's design is correct either way, and a relink that replaces the shim with a symlink is repaired by the next scheduled run. [ASSUMED]
- Receipt (D-19): `_leaf_matches` (`receipts.py:926-941`) returns False for a non-symlink path when the recorded artifact has a `target`, so an unrefreshed receipt makes `broken_drift` non-empty and `UpdateService.run` refuses (`update.py:587-599`). Confirmed by reading. `fingerprint(path, "leaf")` records `target=None` for a regular file and the symlink target for a link (`receipts.py:779-830`), so the helper simply re-fingerprints after each write/restore under `_WRITE_LOCK`. A regular-file leaf is proven by type alone (comment `receipts.py:936-940`), which is exactly why the sentinel check must guard the write.
- `~/.local/bin/agent` must never be opened for write; compare a snapshot before/after in the test.

- Order within the adoption: write the copied runner and scripts first, then the rewritten units, then `daemon-reload` + `restart`; only after a successful restart remove `~/.local/bin/tools-installer-prune-daemon` (sentinel-checked, `daemon.remove_wrapper`). A failure in between must leave the old units pointing at the old wrapper (still valid).

### Pitfall 13: DST
Times are local wall clock in both systemd (`OnCalendar` is evaluated in the local zone) and launchd; do next-run arithmetic on naive local datetimes and convert only for display. Tests set `TZ` and call `time.tzset()` (xdist-safe through `monkeypatch.setenv`) for a zone with a gap and a fold (for example `Europe/Berlin`, 2026-03-29 and 2026-10-25) [ASSUMED test technique].

### Pitfall 14: log hygiene
A child's stderr can contain ANSI and non-UTF-8 bytes. The reason text is decoded with `errors="replace"`, ANSI/CSI and other control characters stripped, newlines collapsed, and the line length bounded (for example 300) before it is written. The view sanitizes again with `sanitize_log_line` and renders as `Text`.

### Known Threat Patterns
| Pattern | STRIDE | Standard Mitigation |
|---------|--------|---------------------|
| Unit-file injection through a path or id | Tampering | `_quote` rejection set; ids from a closed table, never user text |
| Shell injection in the shim through the model id | Tampering / Elevation | charset + alphanumeric first char + single quotes; never interpolate any other value |
| Tampered `schedules.json` redirecting what runs every 6 h (checkout path, runner path) | Tampering / Elevation | bake paths into the unit at apply time from fresh resolution (`__file__`, `shutil.which`), validate absolute + exists; do not read the JSON for execution paths; same-privilege user, so impact is bounded but real |
| PATH hijack of the runner's child commands | Tampering | explicit clean PATH in the unit; no relative or cwd entries; skip the ban shim for npm |
| Log injection (ANSI/newlines in child output) | Tampering / Repudiation | sanitize before write and again before render |
| Privilege escalation to update OS-package tools | Elevation | refuse owners in `UNMANAGEABLE_OWNERS`; no escalation command exists |
| Lock starvation (a hung child holds `run.lock`) | Denial of service | per-child timeouts in the runner |
| Concurrent writers corrupt state/log | Tampering | atomic state writes, log lock, flock for runs |
| Deleting user data in cache cleanup | Tampering | only the managers' own prune commands; MUST-NOT test that other scratch cache dirs are byte-identical |
| Symlink swap of `~/.local/bin/cursor-agent` between check and write | Tampering | `lstat`/`is_symlink` check then `os.replace` of a temp; accept the residual TOCTOU (same user) |
