# 24.2 Review (ponytail)

Range: `1d09c02..415cb2d`, code only (`.planning/` skipped). Read-only review: no installer
code, make target, container, `systemctl` or `launchctl` was run.

Load assumed: one person on one machine, with a TUI open for long stretches while 1 to 7 user
timers fire every 1 to 24 hours, plus the occasional headless install or uninstall. So the real
concurrency is a timer firing while the TUI or a CLI route works, not many users.

## What this change does

It replaces the Policies tmp-cleanup daemon with a Schedules view (key 7). Seven fixed jobs (tmp
cleanup, cache cleanup and five tool updates) each become a systemd user timer or a launchd agent.
Each one runs a copied stdlib runner. The runner takes a shared run lock, writes one capped log,
and for updates calls back into `setup.py --run-schedule`. A reconcile turns undecided rows on at
launch, the uninstall sweep removes them, and the cursor-agent row keeps a model-defaulting shim.

Counts: HIGH 1, MEDIUM 4, LOW 4.

## Must fix

1. **HIGH: the copied runner and prune scripts are never refreshed after a checkout update**
   (`installer/schedules.py:1411-1438` `_is_stale`, `:1441-1451` `_refresh_in_place`; the only
   writer of the assets is `_ensure_shared_assets`, called only from `turn_on` at `:1086`)
   - **What this is:** At every interactive launch the reconcile checks each "on" row and calls
     `turn_on` again only when `_is_stale` says the unit files differ from what this checkout
     would write. Only `turn_on` copies `schedule_runner.py` and the prune scripts into
     `~/.local/share/tools-installer/schedules/`.
   - **Problem:** `_is_stale` compares only the unit or plist bytes. The runner and the scripts
     are not checked. Case: the user does `git pull` to get a fix inside `schedule_runner.py` (or
     `prune-tmp-linux.sh`) and runs `make setup`. The `ExecStart` argv is unchanged, so no row is
     stale, `turn_on` never runs, and every timer keeps running the old runner for good. Nothing
     shows it: `row_state` checks only the unit files, so the row still reads `on`. No test
     covers this; `test_schedules_engine.py` tests asset copy, ownership and refcount only.
     Verified against the source.
   - **Fix:** In `_is_stale`, also return True when a shared asset differs from its source:
     `any(not t.exists() or t.read_bytes() != s.read_bytes() for s, t in _shared_pairs(ctx))`.
     `turn_on` then rewrites the assets through the existing ownership check. Add one lifecycle
     test: change the source runner's bytes, reconcile, and assert the data-dir copy matches.
   - **If we skip it:** Every later runner or script fix (including finding 2's fix) silently
     never reaches existing installs.

2. **MEDIUM: on macOS, stopping a running job leaves its work running with no run lock**
   (`installer/helper_assets/schedule_runner.py:140-150` `start_new_session=True`, no SIGTERM
   handler in `main` at `:337-365`; triggered by `daemon.bootout` from `turn_off`, `retime` and
   the reconcile refresh via `daemon.bootstrap`)
   - **What this is:** The R1-11 amendment says an off or a re-time on macOS "stops that run".
     launchd's bootout sends SIGTERM to the runner and kills the runner's process group.
   - **Problem:** The runner starts every child (`uv run setup.py --run-schedule`, `brew
     cleanup`, the prune script) in a new session, so the child is outside the group launchd
     kills. Only the runner dies. Its `flock` goes with it, but the child keeps updating claude
     or running `brew cleanup` as an orphan. Case: the user turns off "claude update" during a
     run, then starts an install in the TUI. `begin_mutation` gets the run lock, because nothing
     holds it, and two package-manager mutations run at once. The reconcile refresh does the same
     to every running job when the units go stale (for example, the first launch after
     `~/.bun/bin` appears changes the baked PATH). Linux is not affected: systemd kills the whole
     cgroup.
   - **Fix:** In the runner, keep the live child's pid in a module global, and in `main` install
     `signal.signal(SIGTERM, ...)`. The handler calls `_kill_group(pid, SIGTERM)` and then
     `_kill_group(pid, SIGKILL)` after the grace period, and exits non-zero. That is about 8
     lines plus one test that sends SIGTERM to a runner whose child sleeps. It needs finding 1 to
     reach installed timers.
   - **If we skip it:** A rare but real double mutation on macOS, which is exactly what D-12's
     lock is meant to prevent.

3. **MEDIUM: cache cleanup's `uv cache prune` waits and then fails whenever any `uv run` is
   alive, including the TUI itself** (`installer/helper_assets/schedule_runner.py:50-55`,
   `:273`)
   - **What this is:** The cache job runs `uv cache prune` with a 1200 s bound.
   - **Problem:** Commit a326c71 found that a live `uv run` holds the uv cache lock and blocks
     `uv cache prune`. It fixed this only for the runner's own `uv run`. `make setup` itself is
     `uv run --isolated --no-dev setup.py`, so while the TUI is open (and while any other
     long-lived `uv run` or `uvx` process is alive) every cache-cleanup slot waits for uv's lock
     timeout. It then logs `failed: uv cache prune exited 2 (...)`, and the Last cell turns red.
     `uv cache prune --help` (uv 0.11.28) lists `--force  ... ignoring in-use checks`, which
     confirms the in-use lock.
   - **Fix:** Do not use `--force`, because it can pull files from under a running process. Run
     uv with a short lock timeout (`UV_LOCK_TIMEOUT=30` for that child only) and map a lock
     timeout to `skipped: uv cache in use` instead of `failed:`. Or drop `uv` from `_MANAGERS`
     and let uv's own GC handle it. Check it in the container target with a sleeping `uv run`
     alongside.
   - **If we skip it:** Users who keep the TUI open see a red cache row at every slot.

4. **MEDIUM: a damaged or newer-version `schedules.json` hides live update timers from off and
   from uninstall** (`installer/schedules.py:1186-1191` `_remove_timer`, `:1323-1328`
   `row_state`, `:1608-1618` `_footprint`)
   - **What this is:** For every schedule except tmp cleanup, "is this on, and what do I delete"
     comes only from the files recorded in `schedules.json`. tmp cleanup alone also counts its
     units by name.
   - **Problem:** `_decode_state` rejects any unknown key (`_TOP_KEYS`, `_RECORD_KEYS`). A file
     written by a newer checkout (another worktree, or a downgrade) or a hand edit therefore loads
     as defaults with no recorded files, while `tools-installer-schedule-update-*.timer` keeps
     firing. Then: the row reads `off`; space turns it "on" again; `turn_off` deletes nothing yet
     prints "its timer files are removed"; and `sweep_adapters` skips it, so a full uninstall
     leaves timers running `uv run ... setup.py` from the checkout. This does not reopen the
     R1-09 damage decision, which is about never turning rows on.
   - **Fix:** Generalise the tmp special case. `_tmp_unit_present` becomes
     `_unit_present(ctx, schedule_id)`, using `basename_for` and `label_for`, which are this
     project's own names. `row_state`, `_footprint` and `_remove_timer`'s no-records branch call
     it for every schedule (`systemd_daemon.remove_units(ctx.unit_dir, basename=...)` and the
     plist unlink). This mostly deletes the `kind is TMP_CLEANUP` conditions. Add one test: state
     damaged, a schedule unit on disk, the sweep removes it.
   - **If we skip it:** Rare, but when it happens the uninstall reports success and leaves
     background update jobs behind.

## Nice to have

6. **LOW: `retime`'s Persistent-stamp clean does nothing on an "on" timer**
   (`installer/schedules.py:924-926`, called with `clean_stamp=True` from `:1262`)
   - **What this is:** Before re-registering a re-timed Linux timer, `systemctl --user clean
     --what=state` is run so the old stamp does not cause a catch-up.
   - **Problem:** The timer is still active at that point. As far as I know (not run here),
     systemd refuses `clean` on a unit that is not inactive or failed. The `CommandError` is
     suppressed, so the stamp survives and the restart can fire at once. Case: last run 12:00,
     at 14:00 the user re-times to start 13:00, and the job runs immediately. Fake-runner tests
     cannot catch this. `_remove_timer` is fine, because it cleans after `disable --now`.
   - **Fix:** For `clean_stamp`, run `systemctl --user stop <timer>` before the clean (bootstrap
     restarts it), or drop the clean and accept the catch-up.
   - **If we skip it:** One possible extra run right after a re-time.

7. **LOW: two copies of the cache-manager list** (`installer/wizard_app.py:2688-2693`
   `_CACHE_PRUNES` and `installer/helper_assets/schedule_runner.py:50-55` `_MANAGERS`)
   - **Problem:** These must change together. The runner cannot import `installer`, but the view
     can import the runner module, as the tests already do.
   - **Fix:** Build `_CACHE_PRUNES` from `schedule_runner._MANAGERS` (rename it to a public
     `MANAGERS`).

8. **LOW: `systemd_daemon` re-exports `WRAPPER_COMMAND`, and nothing imports it from there**
   (`installer/systemd_daemon.py:26,58`)
   - **Fix:** Drop the import and the `__all__` entry. Also, the `owned` field comment at
     `installer/policy.py:127-132` still describes "the Linux timer's is-active state", which is
     gone.

9. **LOW: misleading error text in the Pi host-setup update** (`installer/update.py:385-386`)
   - **Problem:** It says "pnpm was not found" when `argv is None` too. `update_refusal` makes
     that case unreachable today.
   - **Fix:** Split the two conditions, or drop the `argv is None` half and let the type narrow
     through an assert.
