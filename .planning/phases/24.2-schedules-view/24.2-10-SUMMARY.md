# Phase 24.2 Plan 10: Schedules e2e harness Summary

A host-tested `schedules` target for the container harness: Fedora 44 with systemd as PID 1 and the tester's user manager, where the installer's real engine writes the units through an in-container driver, each built-in runs once, a held lock is skipped, a calendar slot fires and a missed one catches up once, plus a `--direct` fallback. Nothing here was run against a container (executor rule); the orchestrator runs it in 24.2-13.

## What the orchestrator runs in 24.2-13

`scripts/container-e2e-verify.sh schedules` (add `--keep-image` to keep the built image, `--direct` for the fallback). Verdict lines to read, in order:

- start: `TRACER_SCHEDULES_INFEASIBLE step=<build|run|boot|useradd|uid|linger|bus> detail=...` (exit 2, environmental) or the run continues
- per built-in: `TRACER_SCHEDULE_RUN_OK id=<id> result=<ok|skipped>` and `TRACER_SCHEDULE_CELL_OK id=<id> cell=<cell>` (ids `tmp-cleanup`, `cache-cleanup`, `update-claude`); failures print `TRACER_SCHEDULE_RUN_MISSING|RUN_FAILED|CELL_NEVER` and `SCHEDULE_JOURNAL <unit> <line>`
- `TRACER_SCHEDULE_BUSY_OK`, `TRACER_SCHEDULE_CALENDAR_OK` (up to 200 s), `TRACER_SCHEDULE_CATCHUP_OK runs=1` (75 s), then informational `SCHEDULE_STAMP_MTIME ...` and `SCHEDULE_STAMP_KEPT=yes|no`
- `TRACER_SCHEDULE_OFF_OK` (or `TRACER_SCHEDULE_OFF_LEFT path=|timer=`), then `TRACER_SCHEDULES_TEARDOWN_OK` on every outcome
- `--direct`: `TRACER_SCHEDULES_DIRECT_OK` plus `SCHEDULES_GAP=no-systemd units,calendar,catch-up not exercised`

The run takes roughly 6 minutes of waiting (calendar up to 200 s, catch-up 75 s) on top of the image build and `uv sync`.
