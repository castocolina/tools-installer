# Phase 24.2 Plan 09: The Schedules view Summary

**Key 7 opens a seven-row Schedules table (state, timing, next run, last result, detail panel) that toggles, re-times and sets the cursor-agent model live through `run_live`, inside the 80x20 and 78-cell budgets with the seven-tab header whole.**

## What was built

- `installer/ui_common.py`: the `schedules` `View` row after Policies (UI-SPEC section 1 values) and `WayfindingTab { margin-right: 1; }` with `:last-of-type { margin-right: 0; }`, so `[1] System ... [7] Schedules` is 78 cells (P1). `GLOBAL_NAV` and the key bindings follow from the row.
- `installer/wizard_app.py`:
  - `ScheduleInputs` (frozen: context, present, disk_pressure, competing, now), `ScheduleChange`, `ScheduleChanged`, `ScheduleManagerProbed`, `CursorModelsRead`.
  - `SchedulesScreen`: seven columns of fixed width (13/12/9/9/5/7/9, 78 cells), the note line, the detail panel (state, last, times, row-specific, runs), a manager probe on a thread worker, a toggle/retime/model worker under `MutationHolder.SCHEDULE_CHANGE` only, and a `set_interval(30)` tick guarded to "this screen is on top and nothing is mutating". Rows repaint from a fresh disk read after every change; every successful change calls `schedules.clear_damage`.
  - `ScheduleTimeScreen` (Select over the eight intervals with `allow_blank=False`, an `HH:MM` Input, live preview, inline rejection, macOS tmp cleanup shows the time only) and `CursorModelScreen` (thread-worker list read, substring filter, free text checked by `validate_model_id`, late answers dropped).
  - `_competing_line`, `_temp_usage_line` and `_LINGER_SENTENCE` moved to module level; `PoliciesScreen` calls them (the detail text is byte for byte the same).
- `setup.py` `_build_app`: builds `ScheduleInputs` from `schedules.context_for(platform.os, checkout=..., present=version_refresh.installed_or(installed), read_models=cursor_shim.read_models)` and passes it to `UnifiedApp`.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Bug] `self._closed` on a modal froze the app**
- **Found during:** Task 3 (the "a list that arrives after esc is dropped" test hung)
- **Issue:** `CursorModelScreen` kept its "dismissed" flag in `self._closed`, which is Textual's own message-pump flag; setting it stopped the screen from processing messages, so `pilot.press("escape")` (and a real escape) never returned.
- **Fix:** the flag is `_dismissed`. The late-list test now pins the drop (`modal.listed == ()`).
- **Files modified:** installer/wizard_app.py
- **Commit:** 62ba57e

**2. [Rule 3 - Blocking] `UnifiedApp.__init__` signature pin**
- **Found during:** Task 1 (`test_unified_app_signature_carries_no_disk_pressure_parameter` lists every parameter)
- **Fix:** added `"schedules"` after `"policies"` in `tests/test_wizard_app.py`; the plan's sweep list missed it.
- **Commit:** bc8ff10

### Choices the plan left open

- Copy the UI-SPEC does not state, written minimally: `Turned on tmp cleanup: runs every 10 min.` (Linux tmp has no next slot), a `(unverified)` suffix with warn severity on a turned-on cursor row whose list was unreadable, the `last: could not be read` detail line when the log read fails, a fallback damage line (`schedules.json was damaged earlier; the damaged copy is kept beside it.`) when the `.damaged` copy exists but the current file reads cleanly, and `cursor-agent --list-models gave no list` as the reason when `read_models` returns None.
- `read_models` returns only a list or None, so the "Could not read the model list: {reason}" text uses that fixed reason unless the read raised.
- The macOS tmp default start is `03:00` in the code (`daemon.DEFAULT_HOUR/MINUTE`); the UI-SPEC's `24h 03:30` is only an example, so the test pins the schedule's own default.
- The default cursor model `gpt-5.6-sol-xhigh` still **needs confirmation** (UI-SPEC P7, D-20); nothing in this plan changes it.
