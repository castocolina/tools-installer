## HIGH

### H-01: A macOS bootout of a running update orphans the installer child, which keeps mutating without the run lock (Lane B, confirmed)

- **Where:** `installer/helper_assets/schedule_runner.py:140-156` (`_run_child`, `start_new_session=True`), `:172-192` (`_run_lock`, fd `O_CLOEXEC`), `:206-224` (`_update`), and `main` at `:337-365`. The runner installs no signal handler.
- **Failure:** CONTEXT D-12 (amended for R1-11) says an off or a re-time on macOS stops the run in flight through `launchctl bootout`. launchd terminates the job's main process and its process group. The `uv run --isolated --no-dev setup.py --run-schedule … --parent-holds-run-lock` child runs in its own session, so it is outside that group and survives. The runner's lock fd closes when the runner dies, and the child never held the lock itself because it was told its parent holds it. The update keeps running (brew, pnpm, the cursor shim refresh) while another install or a scheduled run can take `run.lock`.
- **Fix:** In the runner, handle SIGTERM and SIGHUP: `killpg` the active child group with SIGTERM, wait out the grace period, send SIGKILL, write the result line, and release the lock only after that. Alternatively, keep the child in the runner's process group for the update job, so launchd's group kill reaches it. Add a test that sends SIGTERM to the runner during a fake long child and checks that the child group is gone before the lock frees.
- **Verification:** I confirmed there is no `signal.signal` in the runner, that the child uses `start_new_session=True`, and that the lock fd is `O_CLOEXEC`. Linux is not affected: an off does not stop the service there, and a `systemctl stop` kills the whole cgroup. I did not check here whether `uv run` forwards SIGTERM to the runner. Either way the child's separate session escapes the group kill.

### H-02: A reconcile in another process can turn a row back on after the user turned it off (Lanes C and A, confirmed)

- **Where:** `installer/schedules.py:1359-1374` (`_turn_on_default`: `_decision_moved` checks, then releases the state lock), `:1441-1450` (`_refresh_in_place`, which never re-checks the decision before `turn_on`), and `:1108-1128` (`turn_on.change` writes `decided=True` unconditionally). Toggles in `installer/wizard_app.py:3114-3132` take only the in-app mutation lock, not the reconcile lock.
- **Failure:** Process A (a headless install's reconcile, the reconcile of a second TUI at launch or after an install, or the after-removal pass) reads a row as undecided, or as on and stale. Process B, a TUI, turns that row off: it removes the files and saves `decided=False`. A then runs `turn_on`: `_register` rewrites and enables the units, and `change` saves `decided=True`. The window includes `systemctl`/`launchctl` calls and up to 40 s of `cursor-agent --list-models`. The user's off is undone, which breaks D-09 ("never undo a user's off").
- **Fix:** Pass the decision the pass expects into `turn_on` (for example `expect_decided: bool | None`) and re-check it inside `change` under the state lock. On a mismatch, roll back the registration this call made and report "skipped". Or make Schedules-view toggles take the reconcile lock (run lock, then reconcile, then state), so a pass and a toggle are serialized. Add a test that interleaves the off after `_decision_moved` returns. `tests/test_schedules_lifecycle.py:128` changes the decision earlier in the pass.
- **Verification:** I read every line cited. Within one process this is safe, because the reconcile holds `SCHEDULE_DEFAULTS` and toggles are refused. The race needs two installer processes, which D-12 allows (a headless route next to a TUI).

### H-03: Turning off the last schedule deletes the shared runner that another process's `turn_on` just adopted (Lane A, confirmed, one detail corrected)

- **Where:** `installer/schedules.py:1086` (`_ensure_shared_assets` runs outside the state lock), `:1118-1128` (records `shared=assets` later), `:1211-1215` (the off's `change` deletes `shared` when `_on_schedules` finds no other record with files), and `:770-774`.
- **Failure:** Cache cleanup is the only schedule on, and the user turns it off in one process. In another process, `turn_on(update-claude)` adopts the identical runner and prune scripts and registers its units. The off's `change` runs first under the state lock, sees no other record with files, and unlinks `runner.py` and the prune scripts. The on then records fingerprints of the deleted files. The claude timer is enabled, and every run fails because `runner.py` is gone. The same unlocked snapshot feeds the cleanup when `turn_on` fails to register (`:1090`).
- **Correction to the lane:** a later explicit `turn_on` does rewrite the missing file (`current is None` takes the write path, `:729-741`). It does not "adopt the absence". The reconcile does not repair it, though: `_is_stale` compares only the schedule's own units, not `shared`, so the timer stays broken until the user toggles it again.
- **Fix:** Record intent under the state lock before copying: write `shared` plus an in-flight marker for the schedule in one `update_state`, then copy, then finish the record. Have the off's delete honour that marker. Also have `_is_stale` or the reconcile treat a missing shared asset as stale, so it repairs itself.
- **Verification:** I confirmed that `update_state` loads fresh under the lock, so the race is between `turn_on`'s copy and its own record, as the lane says. It needs two processes, as H-02 does.

## MEDIUM

### M-01: The cache cleanup resolves the npm global-redirect shim, so `npm cache verify` hits the ban and fails on every run (Lane B, HIGH downgraded to MEDIUM)

- **Where:** `installer/helper_assets/schedule_runner.py:47-48, 247-260` skips only `# tools-installer-ban-shim`. `installer/guards.py:119, 299-301` writes the npm wrapper with `# tools-installer-redirect-shim`, and its non-global fallback is `ban_body("npm")`, which exits 127.
- **Failure:** On a guarded host, the clean unit PATH puts `~/.local/bin` first, so the cache cleanup logs `failed: npm cache verify exited 127 (uv, pnpm, brew ok)` every day.
- **Fix:** Skip both sentinels (mirror `guards.is_our_shim`) and test with the real redirect-shim text ahead of a fake npm.
- **Why downgraded:** I verified it. The failure is loud, repeats, and loses no data. It is a broken sub-step, not a safety issue.

### M-02: A scheduled update drops a custom `PNPM_HOME`, so pnpm ownership falls back to the default dir (Lane B)

- **Where:** `schedule_runner.py:127-130` (child env is PATH/HOME/TMPDIR/LANG only), and the unit env, which is closed to the same keys. `installer/ownership.py:504-509` reads `PNPM_HOME`.
- **Failure:** A Pi installed under a non-default pnpm home is found on the unit PATH but not attributed. The scheduled update logs `skipped:` or attributes Pi to the wrong owner, while the interactive installer updates it.
- **Fix:** Bake the validated pnpm home into the unit environment and pass it to the child, or derive it from the recorded inventory. Test with a non-default home.

### M-03: A receipt-write failure after a successful scheduled update is hidden (Lane B)

- **Where:** `installer/update.py:412-414` appends `install receipt not written: …` to `detail`. `installer/schedules.py:445-465` (`update_result_line`) ignores `detail` for `updated`.
- **Failure:** The log says `ok: updated a → b` while the receipt is stale, and later removal or update proof checks fail with no trail.
- **Fix:** Append a `; warning: <first line of detail>` suffix for `updated` with a non-empty detail, and keep exit 0.

### M-04: Turning off the last schedule on Linux deletes the prune script before an in-flight run executes it (Lane C)

- **Where:** `installer/schedules.py:1211-1215` deletes `shared` when the last schedule goes off. The runner `exec`s `--script` later (`schedule_runner.py:195-197`).
- **Failure:** Linux lets a running job finish on an off (D-12). If the off lands between the runner's `start` line and its `exec` of the prune script, the run logs `failed: prune-tmp-linux.sh could not start`.
- **Fix:** Leave the shared assets in place while `runlock.holder()` names a live scheduled run, and let the next reconcile or off sweep them (they stay recorded in `shared`). Or accept the case and document it next to the R1-11 amendment.

### M-05: `uv cache prune` waits on any other live `uv` process, so the cache cleanup fails while the user has a `uv run` open (orchestrator, real-environment gap)

- **Where:** `schedule_runner.py:50-51` (`("uv", ("cache", "prune"))`) and `_MANAGER_TIMEOUT = 1200` at `:44`. The fix in a326c71 (`--no-cache` on the runner, `schedules.py:816-821`) removes only the runner's own hold.
- **Failure:** The container e2e showed that `uv run` holds the uv cache lock for its lifetime. Any other long-lived `uv run` holds the same lock: the user's dev servers, a notebook, or this installer's own TUI (`make setup` runs `uv run --isolated`). The prune then waits until `UV_LOCK_TIMEOUT` and logs `failed: uv cache prune exited …`. Fakes cannot show this, and the e2e host had no competing uv process.
- **Fix:** Treat uv's lock-timeout exit as `skipped: uv cache in use`, not `failed`, and set a short `UV_LOCK_TIMEOUT` in the child env. `uv cache prune --force` (uv 0.11.28: "ignoring in-use checks") is the other option, but it can break the concurrent process and is not recommended.
- **Verification:** `uv cache prune --help` on this host lists `--force` ("Force removal of the cache, ignoring in-use checks"), and no `UV_LOCK_TIMEOUT` is set anywhere in `installer/`. I did not reproduce this in a container.

## LOW

### L-01: A drift repair writes through a symlink that replaced a recorded unit file (Lane C, HIGH downgraded to LOW)

- **Where:** `installer/schedules.py:854-859` (`_refuse_symlinks` accepts any symlink whose path is recorded), then `atomic_write_bytes` follows it.
- **Failure:** If someone replaces a recorded unit or plist with a symlink, for example a dotfile manager that stows `~/.config/systemd/user`, pressing Space on the drift row writes the unit text into the link's target.
- **Why downgraded:** only the same user can plant the link, so there is no privilege boundary, and what gets written is our own unit text into the file the user linked as that unit. It is still worth closing, because the codebase rule is never to write through a link we did not record as a link. Accept a symlink only when the recorded artifact's kind is `symlink`.

### L-02: The TUI's schedule-defaults reconcile takes the reconcile lock without the run lock (Lane A MEDIUM and Lane C HIGH merged, downgraded to LOW)

- **Where:** `installer/wizard_app.py:3662-3669` (`SCHEDULE_DEFAULTS` is not in `_CROSS_PROCESS`), `:4364-4371` (the post-install pass starts after `end_mutation` released the run lock), and `installer/schedules.py:1508`.
- **What the lanes claimed:** Lane C said a reconcile in one TUI can register a timer for a tool that another process removes under the run lock, leaving a timer for a missing tool. Lane A said the lock order is inverted and could deadlock in the future.
- **Why downgraded:** (1) Every run-lock take is non-blocking (`try_acquire` with `LOCK_NB`, `wizard_app.py:3689`, `setup.py:1303/1502`), so no path waits on the run lock while holding the reconcile lock, and the order cannot deadlock. (2) The removal's `after_target_removed` (`schedules.py:1519`) blocks on the reconcile lock until the TUI's pass ends, then removes the timer that pass wrote, so the end state converges. (3) D-12 lists the four TUI holders that take the run lock, and the reconcile is not one of them. The remaining point is that the TUI pass does not follow the documented order. Either take the run lock non-blocking in the defaults worker and skip the pass when it is busy, or fix the docstring at `schedules.py:1347`.
