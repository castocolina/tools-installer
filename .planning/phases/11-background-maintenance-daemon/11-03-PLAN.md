<design_decisions>
**The time picker is a `ListView` of 48 fixed 30-minute slots, never a free-text `Input`.**
Grepping this codebase for `Input(` returns zero matches anywhere in `wizard_app.py`/
`catalog_tui.py` — introducing free-text entry would be the first of its kind in this TUI,
requiring new validation/error-display code with no existing pattern to extend. `NavScreen`'s
`ModalScreen[str | None]` + `ListView`/`ListItem` + `on_list_view_selected`/`action_cancel` shape
is a proven, already-tested precedent this task reuses verbatim, parameterized over 48 slot
strings instead of `VIEWS`.

**`t` is gated on `set_schedule is not None AND active`, never merely `set_schedule is not
None`.** Allowing the picker to open (and, worse, to actually write a plist) for a policy the
user has not yet enabled would make `active=plist_path.exists()` lie: a plist would exist purely
because the user was curious about the time picker, before ever pressing `space` to enable the
policy. The status-line message this plan adds for the not-yet-active case mirrors the existing
"Install required tool(s) first..." pattern's tone and placement exactly.

**The log-view toggle state (`self._log_view: bool`) lives on `PoliciesScreen`, resets on row
navigation.** Moving the highlighted row away from the daemon's policy and back should show the
normal detail panel again, not a stale log view left on from a previous row — this matches
`on_data_table_row_highlighted`'s existing behavior of fully recomputing `detail_text` on every
row change; this plan's log-view flag is cleared inside that same handler.

**The log tail shown is the raw last N lines of the file (a plain, bounded `read_text()` slice),
not a re-parse into structured blocks.** `last_run_summary` already does the one piece of
structured parsing this phase needs (the single "last run" line in the normal detail view); the
`l` toggle's job is to let a user SEE the log, not to re-render it — reading the tail directly
avoids a second parsing implementation for a view whose whole point is "show me the raw file."
</design_decisions>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|--------------|
| The `TimePickerScreen`'s `ListView` selection (one of 48 fixed, code-authored strings) → `StartCalendarInterval` | A closed enumeration, not free text — an out-of-range hour/minute is structurally impossible, which 11-RESEARCH.md's Security Domain V5 notes is a stronger control than validating a parsed string. |
| The log-view toggle's file read → the Policies detail panel | Reads only the path `daemon_policy` itself wrote (`policy.log_path`), never an arbitrary user-supplied path; a missing file renders a placeholder, never an exception surfaced to the user. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-11-09 | Tampering (state confusion) | Opening the time picker or writing a plist as a side effect of an inactive policy, making `active=plist_path.exists()` lie about whether the policy is actually enabled | medium | mitigate | `t` is gated on the policy being active FIRST; `TimePickerScreen` itself performs no IO — only a confirmed selection calls `set_schedule`, and that path is unreachable while inactive. Pinned by Task 2's "inactive policy shows a message, never opens the modal" test. |
| T-11-10 | Information Disclosure | The log-view toggle displaying arbitrary file content if `log_path` were ever attacker- or user-controlled | low | accept | `log_path` is a `Path` object set exactly once, by `daemon_policy`'s own construction in `setup.py` (11-04) — never derived from any UI input in this plan — so there is no reachable path for it to point anywhere but the daemon's own managed log file. |

Package Legitimacy Gate: not applicable — no new package dependency in this plan.
