<objective>
Add the two Policies detail-panel controls REQ-daemon-log-diagnostics and ROADMAP SC#5 require:
a "last run" summary line plus a log-view toggle for any policy carrying a `log_path` (11-02's
`daemon_policy` is the only one today), and a quantized time-of-day picker for any policy
carrying a `set_schedule` closure (again, only `daemon_policy` today). Both additions extend
`PoliciesScreen` — the SAME screen every other policy already renders into — adding zero new
top-level views, exactly as REQ-daemon-log-diagnostics requires.

This revision (post cross-AI review cycle 1) closes five findings scoped to this plan: every
time-slot widget id must be a VALID Textual identifier, never the raw "HH:MM" string (#11); the
schedule change must route through `run_live`, this project's one apply-workflow seam, not a
direct unguarded call (#12); the detail panel needs a PERSISTENT schedule value to read, not just
a one-time message (#13, resolved by 11-02's `Policy.read_schedule`, consumed here); the generic
"shell config"/"reversible shell policy" copy must become daemon-accurate (#14); and reading the
log for the `l` toggle must handle `OSError`/`UnicodeDecodeError`, not just file-absence (#15).

Task 1 is this plan's tracer: the smallest end-to-end UI-visible slice — the "last run" line, the
persistent schedule line, the daemon-accurate copy, and the `l` log-view toggle — wired against a
real (not yet daemon-shaped) fake `Policy` carrying a `log_path`/`read_schedule`, proving the
detail-panel extension mechanism works before Task 2 builds the heavier `TimePickerScreen` modal
on top of the same screen.

Purpose: REQ-daemon-log-diagnostics (log surfacing, no new Diagnostics view), REQ-launchd-
prune-policy / ROADMAP SC#5 (the time-of-day picker for `StartCalendarInterval`).
Output: `TimePickerScreen`; `PoliciesScreen`'s "last run" line, persistent schedule line,
daemon-accurate copy, `l` log-view toggle, and `t` time-picker binding (routed through
`run_live`).

<design_decisions>
**The time picker is a `ListView` of 48 fixed 30-minute slots, never a free-text `Input`.**
Grepping this codebase for `Input(` returns zero matches anywhere in `wizard_app.py`/
`catalog_tui.py` — introducing free-text entry would be the first of its kind in this TUI,
requiring new validation/error-display code with no existing pattern to extend. `NavScreen`'s
`ModalScreen[str | None]` + `ListView`/`ListItem` + `on_list_view_selected`/`action_cancel` shape
is a proven, already-tested precedent this task reuses, parameterized over 48 slot strings
instead of `VIEWS` — with one structural correction `NavScreen` did not need: `NavScreen`'s own
ids are view NAMES (`"system"`, `"doctor"`, ...), which are already valid identifiers, so its
`ListItem(..., id=view.name)` shape works unmodified. A time slot's natural display string
(`"03:30"`) is NOT a valid identifier (leading digit, embedded `:`), live-verified against this
project's installed Textual version (`ListItem(Label("x"), id="00:00")` raises `textual.css.
identity.BadIdentifier: '00:00' is an invalid id; identifiers must contain only letters, numbers,
underscores, or hyphens, and must not begin with a number` — and a hyphen-only rewrite like
`"03-30"` STILL fails the same check, since it still begins with a digit). The fix keeps the
`ListView`/`ListItem` shape identical to `NavScreen` but separates the WIDGET ID (`f"time-
{h:02d}-{minute:02d}"`, always letter-first) from the DISPLAY VALUE (the `Label`'s own text,
`f"{h:02d}:{minute:02d}"`) — `on_list_view_selected` derives the "HH:MM" dismissal value from the
id by reversing the transform, so `TimePickerScreen`'s own `ModalScreen[str | None]` OUTER
contract (dismiss with an "HH:MM" string or `None`) is unchanged, and `action_pick_time`'s
`"HH:MM"`-parsing logic needs no changes at all (11-REVIEWS.md cycle 1 finding #11).

**`policy.set_schedule(hour, minute)` is called through `run_live`, exactly like `action_
toggle_policy` already calls `policy.apply`/`policy.remove` through it.** 11-02's `daemon_policy.
set_schedule` can now raise `CommandError` (a `bootstrap` failure) or `DaemonScheduleError` (an
`OSError` subclass, from 11-01's validation) — both are real, expected failure modes a screen must
surface without crashing the app, and `run_live` is this project's ONE apply-workflow seam for
exactly that (architecture rule 3). Calling `set_schedule` directly from the modal's dismissal
callback, as an earlier draft of this plan did, would leave those exceptions uncaught, violating
the same rule `action_toggle_policy` already follows and reopening the exact "a screen writes its
own try/except OSError" anti-pattern the architecture doc calls out by name (11-REVIEWS.md cycle
1 finding #12).

**`t` is gated on `set_schedule is not None AND active`, never merely `set_schedule is not
None`.** Allowing the picker to open (and, worse, to actually write a plist) for a policy the
user has not yet enabled would make `active=plist_path.exists()` lie: a plist would exist purely
because the user was curious about the time picker, before ever pressing `space` to enable the
policy. The status-line message this plan adds for the not-yet-active case mirrors the existing
"Install required tool(s) first..." pattern's tone and placement exactly.

**The log-view toggle state (`self._log_view: bool`) lives on `PoliciesScreen`, resets on row
navigation.** Moving the highlighted row away from the daemon's policy and back should show the
normal detail panel again, not a stale log view left on from a previous row — this matches
`on_data_table_row_highlighted`'s existing behavior of fully recomputing `detail_text` on every
row change; this plan's log-view flag is cleared inside that same handler.

**The log tail shown is the raw last N lines of the file (a plain, bounded, DEFENSIVELY-READ
`read_text()` slice), not a re-parse into structured blocks.** `last_run_summary` already does
the one piece of structured parsing this phase needs (the single "last run" line in the normal
detail view); the `l` toggle's job is to let a user SEE the log, not to re-render it. The read is
wrapped in `try/except (OSError, UnicodeDecodeError)` rather than only checking file existence,
because 11-01's own truncation is decode-safe for content THIS module writes, but a hand-edited
or externally-corrupted log file is still a real possible input to a passive display read —
crashing the whole TUI over a malformed log file would be a strictly worse outcome than a
placeholder line naming the read failure (11-REVIEWS.md cycle 1 finding #15). This read is a
passive display concern, not a "live core mutation" per architecture rule 3, so a local `try/
except` here (rather than `run_live`) is the correct, narrowly-scoped guard — mirroring how
`_policy_detail`'s own reads are already local, un-wrapped display logic today.

**The Effect-column/detail-panel copy fix keys off `policy.log_path is not None`, not a hardcoded
`policy.id` string comparison.** `log_path` is already the generic, reused-elsewhere signal that
"this policy is daemon-shaped" (11-02 sets it only for `daemon_policy`); branching on it here
avoids a second, id-string-based special case and stays correct automatically if a future policy
ever reuses the same `log_path`/`set_schedule` shape.
</design_decisions>

## Trust Boundaries

| Boundary | Description |
|----------|--------------|
| The `TimePickerScreen`'s `ListView` selection (one of 48 fixed, code-authored id/display pairs) → `StartCalendarInterval` | A closed enumeration, not free text — an out-of-range hour/minute is structurally impossible, which 11-RESEARCH.md's Security Domain V5 notes is a stronger control than validating a parsed string. The id→display-value transform is a pure, deterministic string operation over a fixed, code-authored set, never user-typed text. |
| The log-view toggle's file read → the Policies detail panel | Reads only the path `daemon_policy` itself wrote (`policy.log_path`), never an arbitrary user-supplied path; a missing, unreadable, or invalid-UTF-8 file renders a placeholder, never an exception surfaced to the user. |
| `run_live`-wrapped `set_schedule` → the Policies status line | The one path a schedule-change failure (a rejected input, or a real `launchctl` failure) can reach the user, mirroring every other live mutation in this codebase — no screen-local `except` clause is introduced. |
