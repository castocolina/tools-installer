<design_decisions>
**`ProgramArguments` names the installed WRAPPER first, with the (unmodified)
`scripts/prune-user-tmpdir.sh` passed to it as the value of a `--script` flag, resolved once
at apply time by the composition root (11-04) via `Path(__file__).parent / "scripts" /
"prune-user-tmpdir.sh"` — mirroring `setup.py`'s existing `_REGISTRY = Path(__file__).parent /
"installer" / "registry.toml"` pattern.** This project is run via `uv run setup.py` from a git
checkout, not installed as a package, so the wrapper (copied once into `~/.local/bin`, decoupled
from the checkout) cannot re-derive the checkout's location at run time; the checkout's absolute
path must be baked into the plist's `ProgramArguments` at apply time instead.

**TMPDIR is resolved into `EnvironmentVariables.TMPDIR`, not baked into `ProgramArguments` as a
`--tmpdir` flag.** This mirrors the SAME fix RESEARCH already recommends for `fd`/`rg` discovery
(`EnvironmentVariables.PATH`) rather than inventing a second mechanism, and it means the wrapper
needs no special-case handling: `subprocess.run` inherits the wrapper's OWN process environment
by default (no explicit `env=` kwarg), so setting `TMPDIR` once in the plist reaches
`scripts/prune-user-tmpdir.sh`'s own `${TMPDIR:-}` read with zero wrapper-side plumbing. This is
the plan's own finding (RESEARCH's Pitfall 3 enumerates the PATH gap but not this one) — grounded
directly in reading `scripts/prune-user-tmpdir.sh` line 24 (`TMP_ROOT="${TMPDIR:-}"`, hard error
if empty) against RESEARCH's own live-verified finding that a freshly bootstrapped LaunchAgent's
default environment is `{PATH => /usr/bin:/bin:/usr/sbin:/sbin}` and nothing else. Without this
fix, every single scheduled run would fail at the script's own first validation line.

**The wrapper's own process always exits 0 and never raises, regardless of the wrapped script's
outcome.** `launchd` has no one watching a scheduled job's exit code interactively; a wrapper that
propagates the script's failure as its own crash would leave nothing in the log at all for that
run (the log-write step never runs), which is strictly worse than a logged failure. The script's
real exit code is recorded as a `(exit N)` line inside the logged block instead, so a failure is
visible without crashing anything downstream.

**`StandardOutPath`/`StandardErrorPath` both point at the SAME log file the wrapper's own code
writes to, and the wrapper never itself prints to stdout/stderr.** This keeps `launchd`'s own
redirection from duplicating the wrapper's structured, timestamped append — `StandardOutPath`/
`StandardErrorPath` exist purely as a crash safety net for an uncaught Python-level exception in
the wrapper itself (before it reaches its own file-write code), never as the primary logging path.

**`bootstrap`/`bootout` take an injectable `run: Callable[[list[str]], None] = run_captured`
parameter rather than hardcoding `installer.run.run_captured`.** This is the single seam that
lets every later plan (11-02, 11-03, 11-04) unit-test `daemon_policy`'s `apply`/`remove`/
`set_schedule` closures with a fake, list-recording `run` and NEVER touch the developer's real
`gui/<uid>` launchd session — this plan's own Task 1 is the ONLY place in the whole phase a real
`launchctl bootstrap`/`bootout` round trip is exercised, and it does so against a distinctly
test-scoped label, always torn down.

**No `clear_decided` function exists.** Unlike `installer/omz.py`'s `_clear_owned` (needed
because a full uninstall must fully reset omz's ownership so a later re-enable starts clean),
the daemon's "decided" marker is intentionally permanent once set: RESEARCH's Pitfall 2 design
is that ONE deliberate decision (auto-default OR an explicit toggle) should never be silently
un-recorded, or the on-by-default logic 11-04 builds on this marker could re-apply itself after
a user's explicit disable. This phase does not wire the daemon into the full-uninstall sweep
(`installer/uninstall.py`'s `active_policies`/`sweep_policies`) — doing so would require a new
Uninstall-view checkbox/decision field distinct from the existing `remove_tweaks` lever (which is
explicitly labeled "shell tweaks" / "blocks + helpers" in `installer/wizard_app.py`, a copy that
would misdescribe a plist+LaunchAgent teardown), which is new user-facing surface beyond this
phase's five ROADMAP success criteria and three REQs. Noted here as a deliberate exclusion, not a
silent gap: a full `make uninstall` today leaves an enabled daemon's LaunchAgent registered and
running (removable via the Policies toggle, exactly like leaving `ban` or any `tweak:*` policy
enabled through an uninstall already behaves for every OTHER lever not selected in that view).
</design_decisions>
