<design_decisions>
**`ProgramArguments` invokes an apply-time-resolved, absolute `uv` executable running the
installed WRAPPER via `uv run --no-project --script`, exactly mirroring `installer/tweaks.py`'s
own `_COUNTDOWN_BODY` invocation shape (`uv run --no-project --script "<path>" "$@"`), live-
verified working: `uv run --no-project --script FILE --script /tmp/s --log /tmp/l --cap-bytes 5
-- --apply --days 3` forwards every trailing token — including a literal `--`— verbatim as
`sys.argv[1:]` inside FILE.** `install.sh` guarantees only `uv` on a bare machine (it bootstraps
`uv` itself, then `exec uv run setup.py "$@"` — line 88); it makes zero guarantee about a bare
`python3` being on `PATH`, let alone being the SAME interpreter this project's own dependencies
resolve against. A LaunchAgent's `ProgramArguments` has no shell and no `PATH` search beyond
what `EnvironmentVariables.PATH` supplies, so a bare `#!/usr/bin/env python3` shebang invoked
directly is exactly as fragile as the countdown helper would be without `tweaks.py`'s own `uv
run` wrapping — this plan closes the same gap 11-REVIEWS.md cycle 1 finding #1 named. `uv_path`
is resolved once, by the caller (11-02's `daemon_policy`, populated by 11-04's composition root
via `shutil.which("uv")`), never re-derived inside this module — this module only validates and
serializes it, exactly like every other path argument.

**TMPDIR is resolved into `EnvironmentVariables.TMPDIR`, not baked into `ProgramArguments` as a
`--tmpdir` flag.** This mirrors the SAME fix RESEARCH already recommends for `fd`/`rg` discovery
(`EnvironmentVariables.PATH`) rather than inventing a second mechanism, and it means the wrapper
needs no special-case handling: `subprocess.run` inherits the wrapper's OWN process environment
by default (no explicit `env=` kwarg), so setting `TMPDIR` once in the plist reaches
`scripts/prune-user-tmpdir.sh`'s own `${TMPDIR:-}` read with zero wrapper-side plumbing. This is
the plan's own finding (RESEARCH's Pitfall 3 enumerates the PATH gap but not this one) — grounded
directly in reading `scripts/prune-user-tmpdir.sh` line 24 (`TMP_ROOT="${TMPDIR:-}"`, hard error
if empty) against RESEARCH's own live-verified finding that a freshly bootstrapped LaunchAgent's
default environment is `{PATH => /usr/bin:/bin:/usr/sbin:/sbin}` and nothing else.

**`render_plist` validates every path/schedule argument and raises `DaemonScheduleError` — a new
`OSError` subclass — the instant any is invalid, BEFORE building the returned dict.** This
single choke point is what makes 11-REVIEWS.md cycle 1 finding #5 unconditionally true for every
caller in every later plan: `write_plist` calls `render_plist` first and only performs filesystem
IO after it returns successfully, so an invalid `TMPDIR` (empty, relative, or otherwise not an
absolute path), an unresolved `uv` (modeled identically — `shutil.which("uv")` returning `None`
becomes an empty, non-absolute `uv_path` the SAME validation rejects, no second code path), an
out-of-range hour/minute, or `days < 1` can NEVER reach a written plist file or a `launchctl
bootstrap` call. `DaemonScheduleError` subclasses `OSError` specifically so
`installer/ui_common.py::run_live` — which already catches `OSError` by design (architecture rule
3) — surfaces a rejected apply/reschedule on the Policies status line with ZERO new `except`
clauses anywhere in `wizard_app.py`, mirroring `installer/omz.py::OmzPluginsError`'s exact
precedent for the same reason. This is also what makes 11-04's `ensure_daemon_default` (which
already plans to catch `(OSError, CommandError)`) safe against a genuinely broken environment
with no code changes there at all.

**Cross-AI review cycle 3, finding #4 (MEDIUM) — one shared atomic-write helper cannot force
`0o644` for the plist AND preserve the existing file's mode for the `~/.myshellrc` marker at the
same time.** The pre-cycle-3 plan text said `write_plist` "chmods that temp file `0o644`
(explicit...)" while `record_decided` (Task 3) said it "carr[ies] over the existing file's mode
via `shutil.copymode` when present" — both correct requirements individually (`write_plist` needs
`installer/omz.py`'s Tampering-mitigation posture for a LaunchAgent config nobody else should be
able to edit; `record_decided` needs `installer/omz.py::_atomic_write`'s OWN mode-preservation
behavior, since `state_path` is the exact same `~/.myshellrc` file that function already protects,
live-re-read this session at `installer/omz.py:190`-`:223`: `if target.exists():
shutil.copymode(target, tmp)`, with NO explicit chmod at all when the target does not yet exist)
— but Task 3's own pre-cycle-3 action text asked for "one shared atomic-write code path" without
reconciling the two. The fix: `_atomic_write(path: Path, data: bytes, *, mode: int | None = None)
-> None` (defined once, in THIS task, since `write_plist` needs it first) takes an explicit `mode`
keyword: when `mode` is given, it `chmod`s the temp file to exactly that value before the
`os.replace` (the plist's own forced-`0o644` policy, unconditional and umask-independent); when
`mode` is `None` (the default), it mirrors `installer/omz.py::_atomic_write` exactly —
`shutil.copymode(target, tmp)` when `target` already exists, otherwise no explicit chmod at all (a
first-ever write falls back to the process's own umask, matching `omz.py`'s own first-write
behavior byte for byte). `write_plist` calls `_atomic_write(plist_path, plistlib.dumps(plist_dict),
mode=0o644)`; Task 3's `record_decided`/`clear_decided` call this SAME function (never a second,
independently-defined helper) with `mode=None` — an explicit, named parameter rather than one
hardcoded mode silently applied to both call sites.

**Cross-AI review cycle 3, finding #1 (HIGH) — the live `launchctl` round-trip test cannot go
through `render_plist`/`write_plist` at all, since `render_plist` HARD-CODES `ProgramArguments` to
the uv-routed wrapper invocation with no override parameter.** Re-reading this plan's own
`render_plist` signature confirms there is no seam that accepts a caller-supplied
`ProgramArguments` — every real caller in every later plan (11-02's `daemon_policy`) always wants
the SAME uv-routed shape, so adding a production-facing override parameter purely to let one test
substitute `["/bin/echo", "hello"]` would be a test-only widening of a function every other caller
must never misuse (this project's own architecture rule against speculative parameters nothing
production ever passes). The fix (option (b) of the two the review itself proposed): the live test
builds its OWN throwaway plist dict by hand — `{"Label": test_label, "ProgramArguments":
["/bin/echo", "hello"], "RunAtLoad": False}` (no `StartCalendarInterval`/`EnvironmentVariables`
needed, since this test's only job is exercising `bootstrap`/`bootout`'s own `launchctl`
subcommands, not re-proving the argv shape the dict-level tests in this same task already pin
exhaustively) — serializes it via `plistlib.dumps(...)`, and writes it via
`daemon._atomic_write(plist_path, plistlib.dumps(the_dict), mode=0o644)` directly: the SAME
private, crash-safe persistence path `write_plist` itself calls internally (see the next finding
below), just without going through `render_plist`'s content-shaping/validation. The test therefore
still exercises this module's real atomic-write mechanics (a regression there is still caught
here), while never claiming to prove anything about `render_plist`'s own argv shape.

**The wrapper's own process always exits 0 and never raises, regardless of the wrapped script's
outcome.** `launchd` has no one watching a scheduled job's exit code interactively; a wrapper that
propagates the script's failure as its own crash would leave nothing in the log at all for that
run (the log-write step never runs), which is strictly worse than a logged failure. The script's
real exit code is recorded as a `(exit N)` line inside the logged block instead, so a failure is
visible without crashing anything downstream.

**The wrapper's own defensive `log_path.parent.mkdir(...)`/file-creation stays in the wrapper
(belt-and-suspenders) but is no longer the AUTHORITATIVE creation point.** `installer.daemon.
ensure_log_path(log_path)` is a new, separate mechanism-tier function this plan adds, called by
11-02's `daemon_policy.apply()`/`.set_schedule()` at APPLY TIME — before `write_plist`/
`bootstrap` — because launchd needs `StandardOutPath`/`StandardErrorPath`'s parent directory to
already exist when the job is registered, not merely by the time it first runs (11-REVIEWS.md
cycle 1 finding #2). Leaving the wrapper's own creation in place costs nothing and keeps the
wrapper safely self-contained for a manual/direct invocation (e.g. a future CLI debug path, or
this plan's own unit tests that import and call `main()` directly against a `tmp_path` log file
that was never `ensure_log_path`-created first).

**Truncation decodes the WHOLE log once and cuts only on `\n` line boundaries, never a raw byte
offset.** The file this module's own wrapper writes is always valid UTF-8 (every append is a
`str`, encoded by the normal text-mode file write), so decoding it in full can never raise; every
cut this function makes afterward is therefore guaranteed to land between two complete lines,
which is always a valid UTF-8 boundary (a `\n` byte can never appear inside a multi-byte UTF-8
continuation sequence). The ORIGINAL byte-window design sliced raw bytes to a fixed size FIRST
and only searched for the `=== ` header afterward — in the documented "no header found in the
window" fallback case (a single run wider than the cap), that raw slice's own START byte could
land mid-sequence, and the file `last_run_summary`/11-03's log-view toggle later read via
`Path.read_text()` (which raises `UnicodeDecodeError` on invalid UTF-8) would then be corrupt.
Deciding on decoded text FIRST removes this failure mode structurally rather than special-casing
it (11-REVIEWS.md cycle 1 finding #4).

**Cross-AI review cycle 3, finding #2 (MEDIUM) — the cycle-1 fix above stopped a raw byte-offset
UTF-8 split but never actually enforced `cap_bytes` as a HARD ceiling, and could drop the log's
own trailing newline on truncation.** The backward-accumulation loop as originally specified adds
lines UNTIL `size >= cap_bytes` — meaning the single line that finally crosses the threshold is
always included in full, so one abnormally large line (or, if the very first line considered is
itself already larger than `cap_bytes`, that line alone) can leave the retained file substantially
larger than the stated cap; separately, `"\n".join(kept)` produces a string with NO trailing `\n`,
so the wrapper's own NEXT append (`=== <timestamp> ===\n...`) concatenates directly onto the
truncated file's last line with no separator, corrupting that block's own header. The fix: (1) the
accumulation loop now STOPS BEFORE adding a line that would push the total over `cap_bytes`
(`if size + line_size > cap_bytes and kept: break`), so the retained window never exceeds the cap
once at least one line is already kept; (2) a single line that is ALREADY larger than `cap_bytes`
on its own (the case that can occur before ANY line has been kept) is hard-truncated in place —
its own UTF-8-encoded bytes are sliced to keep only the trailing `cap_bytes - 1` bytes (preserving
the most RECENT content, consistent with this function's whole "keep what's recent" purpose), then
re-decoded with `errors="ignore"` to silently drop any incomplete leading multi-byte sequence the
byte-level slice may have introduced at the cut point — this is the one place in this function a
raw byte slice is still used, and it is immediately followed by a decode-with-recovery specifically
because slicing an ALREADY-A-SINGLE-LINE string can only ever reintroduce the exact hazard
finding #4 (cycle 1) fixed for the file as a whole, so it needs its own local safeguard; (3) the
header-boundary snap (unchanged in shape) can now only ever SHRINK the already-capped window,
never grow it, so the hard cap survives snapping too; (4) the final write always ends with a
single trailing `\n` (`"\n".join(kept) + "\n"` when `kept` is non-empty, empty string when it is
not), guaranteeing the wrapper's next append always starts on its own line. New tests cover: an
oversized single line (larger than `cap_bytes` on its own) is hard-truncated rather than kept
whole; an oversized single RUN (a multi-line block whose own total size already exceeds
`cap_bytes`, with no OTHER block's header inside the retained window) is still capped at
`cap_bytes`, keeping its own most-recent tail rather than growing past the cap; and the truncated
file always ends with exactly one trailing newline, verified by writing a second, real (non-test-
injected) append afterward and asserting the two blocks' `=== ` headers never concatenate.

**Cross-AI review cycle 3, finding #3 (MEDIUM) — `_truncate` cannot live in `installer/daemon.py`,
because the wrapper that needs to call it is invoked via `uv run --no-project --script` from
`~/.local/bin`, which cannot assume this repository's `installer` package is importable at all.**
`--no-project` deliberately skips resolving this project's own `pyproject.toml`/virtual
environment — the wrapper script runs in whatever bare interpreter `uv run --script` provisions
for it, with no guarantee the `installer` package (or this repository's checkout) is anywhere on
that interpreter's `sys.path`. Putting `_truncate` in `installer/daemon.py` and having the wrapper
`import installer.daemon` would make every scheduled run depend on an import that has no reason
to succeed outside a developer's own checkout. The fix: `_truncate` moves into
`installer/helper_assets/prune_daemon_runner.py` itself — the standalone script — as a
self-contained, dependency-free function using only the standard library, mirroring the same
self-containment `wait_time.py` already has as this package's OTHER `uv run --script`-invoked
helper. `installer/daemon.py` itself never defines or imports `_truncate`; this plan's own tests
import it the SAME way `tests/test_wait_time.py` already imports `wait_time` —
`from installer.helper_assets import prune_daemon_runner` — which works from the TEST process
(running inside this project's own `uv`-managed venv, where `installer` genuinely is importable)
without implying anything about the PRODUCTION wrapper's own invocation, which never imports
`installer` at all.

**The real `launchctl bootstrap`/`print`/`bootout` round-trip test requires an explicit opt-in
environment variable, `TOOLS_INSTALLER_RUN_LAUNCHCTL_TESTS=1`, in addition to the existing

deterministic and offline" rule and this project's precedent for platform-gated tests
(`@pytest.mark.skipif(sys.platform != "darwin", ...)`) both point the same direction: a test that
mutates the developer's real GUI launchd domain — even one that tears itself down — has no place
running by default inside `uv run pytest`/`make test`/CI, where nobody is watching for a stray
registration left behind by an interrupted run (a killed test process skips its own `finally`).
This is `pyproject.toml`'s existing bare `addopts = "-q"` with no `--strict-markers`/marker
registry, so an env-var gate (rather than inventing and registering a new pytest marker) is the
lower-friction fix consistent with what is already in this codebase (11-REVIEWS.md cycle 1
finding #3). Every OTHER test added by this plan (and by 11-02/11-03/11-04) exercises `bootstrap`/
`bootout` exclusively through the injected `run` seam.

**`clear_decided` exists (post cycle-2 revision) but has exactly one caller, and it is not
`daemon_policy.remove()`.** The cycle-1 reasoning above — that the "decided" marker must be
intentionally permanent so 11-04's on-by-default logic never re-applies itself after a user's
explicit disable — remains correct for the ORDINARY case: `daemon_policy.remove()` (11-02),
called by the Policies screen's own `space` toggle, still calls `record_decided`, never
`clear_decided`, exactly as before. 11-REVIEWS.md cycle 2 finding #17 identifies the ONE case
that reasoning does not cover: a FULL uninstall is meant to return the machine to a state
indistinguishable from one this tool was never installed on, so that a LATER fresh reinstall
behaves like a genuinely fresh machine (matching `installer/omz.py`'s own `remove_plugins`
precedent, which unconditionally calls `_clear_owned` on every removal — including a
full-uninstall-triggered one — because omz's ownership record exists to answer the SAME "did we
ever touch this machine" question the daemon's marker answers). Since `daemon_policy.remove()`
is the SAME closure the ordinary Policies-screen toggle calls (architecture invariant: "full
uninstall" and "toggle off" are the same operation by construction), `clear_decided` cannot live
inside that closure without also firing on an ordinary toggle-off, which must keep the marker.
The fix is therefore composition-root-only: `clear_decided(state_path)` is called from
`installer/app.py::run_uninstall`/`perform_uninstall` (11-04's own layer) AFTER their respective
sweep completes, and ONLY when the daemon's policy id is actually present in the sweep's own
`SweepResult.swept` (never on a failed removal, and never merely because the daemon was
*offered* — the same "report the sweep's own result, never the preview" discipline
`installer/wizard_app.py::UninstallScreen._applied_summary` already documents). Running this
AFTER the sweep (not before) is load-bearing: `daemon_policy.remove()` itself still calls
`record_decided` internally as part of that same sweep call, so calling `clear_decided` BEFORE
the sweep would have its effect immediately undone by the sweep's own `record_decided` call
running afterward — exactly the "marker recreated after being cleared" ordering bug
11-REVIEWS.md cycle 2 finding #17 warns against. See 11-04's `<design_decisions>` for the exact
call-site wiring.

## Trust Boundaries

| Boundary | Description |
|----------|--------------|
| Code-authored plist body (this module's own `render_plist` output, never derived from user input or a registry TOML) → the real `launchd`/`launchctl` scheduling substrate | Every plist field is either a code constant, a caller-supplied integer (hour/minute/days), or a `Path`/environment string resolved by this project's own composition root — never text typed by an end user at run time. |
| The installed wrapper's own argv → `subprocess.run([script_path, *forwarded])` | `forwarded` is the literal tail of the plist's own `ProgramArguments`, itself code-authored at apply time; there is no live-user-input path into this argv at all. |
| `~/.myshellrc`'s "decided" marker block (comments only) → any shell that sources it | Inert by construction — the block contains no executable shell syntax, mirroring `installer/omz.py`'s own ownership-record shape. |
| `render_plist`'s validation gate → every downstream write/registration | The single choke point every caller (11-02, 11-04) passes through before a plist can ever be written or `launchctl bootstrap` ever called; a validation bypass here would reopen 11-REVIEWS.md cycle 1 finding #5 for every consumer at once. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-11-01 | Tampering | `render_plist`'s XML serialization of a path containing an XML-special character (e.g. a `HOME` with `&`/`<` in it) | low | mitigate | `plistlib.dumps` handles escaping correctly by construction — live round-tripped in Task 1, replacing this codebase's usual hand-rolled-string convention (`_DOCKER_BODY`-style) specifically because a plist embeds real filesystem paths, not fixed placeholders. |
| T-11-02 | Tampering | A world/group-writable generated plist letting another local user on a shared machine alter what a scheduled job runs at next login | low | mitigate | `write_plist` calls the shared `_atomic_write(plist_path, ..., mode=0o644)` helper, which explicitly `chmod`s the file `0o644` after writing, independent of the invoking process's umask or any pre-existing mode (`man launchctl`'s own "must disallow group and world writes" guidance for LaunchAgents, quoted in 11-RESEARCH.md), and writes it atomically (temp file + `os.replace`) so a crash mid-write never leaves a partially-written, permission-ambiguous plist. | T-11-03 | Tampering (argument injection) | `ProgramArguments`/the wrapper's own forwarded argv being built via shell string concatenation instead of a literal array | medium | mitigate | Both the plist's `ProgramArguments` and the wrapper's own `subprocess.run` call use literal argv lists end to end — no shell (`/bin/sh -c`) anywhere in this module, mirroring `installer/run.py`'s existing array-argv discipline used everywhere else in this codebase. |
| T-11-04 | Denial of Service | A schedule change silently not taking effect because `bootstrap` on an already-loaded label fails without reloading it, leaving the OLD schedule running indefinitely | medium | mitigate | The verified bootout-then-bootstrap idempotent sequence (RESEARCH Pitfall 4, Task 1's `bootstrap` implementation) — a real failure on the second call still raises, so a silently-stale schedule is not possible; Task 1's own live test exercises this exact sequence. |
