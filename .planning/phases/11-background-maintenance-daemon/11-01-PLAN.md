<design_decisions>
**`ProgramArguments` invokes an apply-time-resolved, absolute `uv` executable running the
installed WRAPPER via `uv run --no-project --script`, exactly mirroring `installer/tweaks.py`'s
own `_COUNTDOWN_BODY` invocation shape (`uv run --no-project --script "<path>" "$@"`), live-
verified working: `uv run --no-project --script FILE --script /tmp/s --log /tmp/l --cap-bytes 5
-- --apply --days 3` forwards every trailing token — including a literal `--`— verbatim as
`sys.argv[1:]` inside FILE.** `install.sh` guarantees only `uv` on a bare machine (it bootstraps
`uv` itself, then `exec uv run setup.py "$@"` — line 88); it makes zero guarantee about a bare
`python3` being on `PATH`, let alone being the SAME interpreter this project's own dependencies
resolve against. A LaunchAgent's `ProgramArguments` has no shell and no `PATH` search beyond
what `EnvironmentVariables.PATH` supplies, so a bare `#!/usr/bin/env python3` shebang invoked
directly is exactly as fragile as the countdown helper would be without `tweaks.py`'s own `uv
run` wrapping — this plan closes the same gap 11-REVIEWS.md cycle 1 finding #1 named. `uv_path`
is resolved once, by the caller (11-02's `daemon_policy`, populated by 11-04's composition root
via `shutil.which("uv")`), never re-derived inside this module — this module only validates and
serializes it, exactly like every other path argument.

**TMPDIR is resolved into `EnvironmentVariables.TMPDIR`, not baked into `ProgramArguments` as a
`--tmpdir` flag.** This mirrors the SAME fix RESEARCH already recommends for `fd`/`rg` discovery
(`EnvironmentVariables.PATH`) rather than inventing a second mechanism, and it means the wrapper
needs no special-case handling: `subprocess.run` inherits the wrapper's OWN process environment
by default (no explicit `env=` kwarg), so setting `TMPDIR` once in the plist reaches
`scripts/prune-user-tmpdir.sh`'s own `${TMPDIR:-}` read with zero wrapper-side plumbing. This is
the plan's own finding (RESEARCH's Pitfall 3 enumerates the PATH gap but not this one) — grounded
directly in reading `scripts/prune-user-tmpdir.sh` line 24 (`TMP_ROOT="${TMPDIR:-}"`, hard error
if empty) against RESEARCH's own live-verified finding that a freshly bootstrapped LaunchAgent's
default environment is `{PATH => /usr/bin:/bin:/usr/sbin:/sbin}` and nothing else.

**`render_plist` validates every path/schedule argument and raises `DaemonScheduleError` — a new
`OSError` subclass — the instant any is invalid, BEFORE building the returned dict.** This
single choke point is what makes 11-REVIEWS.md cycle 1 finding #5 unconditionally true for every
caller in every later plan: `write_plist` calls `render_plist` first and only performs filesystem
IO after it returns successfully, so an invalid `TMPDIR` (empty, relative, or otherwise not an
absolute path), an unresolved `uv` (modeled identically — `shutil.which("uv")` returning `None`
becomes an empty, non-absolute `uv_path` the SAME validation rejects, no second code path), an
out-of-range hour/minute, or `days < 1` can NEVER reach a written plist file or a `launchctl
bootstrap` call. `DaemonScheduleError` subclasses `OSError` specifically so
`installer/ui_common.py::run_live` — which already catches `OSError` by design (architecture rule
3) — surfaces a rejected apply/reschedule on the Policies status line with ZERO new `except`
clauses anywhere in `wizard_app.py`, mirroring `installer/omz.py::OmzPluginsError`'s exact
precedent for the same reason. This is also what makes 11-04's `ensure_daemon_default` (which
already plans to catch `(OSError, CommandError)`) safe against a genuinely broken environment
with no code changes there at all.

**The wrapper's own process always exits 0 and never raises, regardless of the wrapped script's
outcome.** `launchd` has no one watching a scheduled job's exit code interactively; a wrapper that
propagates the script's failure as its own crash would leave nothing in the log at all for that
run (the log-write step never runs), which is strictly worse than a logged failure. The script's
real exit code is recorded as a `(exit N)` line inside the logged block instead, so a failure is
visible without crashing anything downstream.

**The wrapper's own defensive `log_path.parent.mkdir(...)`/file-creation stays in the wrapper
(belt-and-suspenders) but is no longer the AUTHORITATIVE creation point.** `installer.daemon.
ensure_log_path(log_path)` is a new, separate mechanism-tier function this plan adds, called by
11-02's `daemon_policy.apply()`/`.set_schedule()` at APPLY TIME — before `write_plist`/
`bootstrap` — because launchd needs `StandardOutPath`/`StandardErrorPath`'s parent directory to
already exist when the job is registered, not merely by the time it first runs (11-REVIEWS.md
cycle 1 finding #2). Leaving the wrapper's own creation in place costs nothing and keeps the
wrapper safely self-contained for a manual/direct invocation (e.g. a future CLI debug path, or
this plan's own unit tests that import and call `main()` directly against a `tmp_path` log file
that was never `ensure_log_path`-created first).

**Truncation decodes the WHOLE log once and cuts only on `\n` line boundaries, never a raw byte
offset.** The file this module's own wrapper writes is always valid UTF-8 (every append is a
`str`, encoded by the normal text-mode file write), so decoding it in full can never raise; every
cut this function makes afterward is therefore guaranteed to land between two complete lines,
which is always a valid UTF-8 boundary (a `\n` byte can never appear inside a multi-byte UTF-8
continuation sequence). The ORIGINAL byte-window design sliced raw bytes to a fixed size FIRST
and only searched for the `=== ` header afterward — in the documented "no header found in the
window" fallback case (a single run wider than the cap), that raw slice's own START byte could
land mid-sequence, and the file `last_run_summary`/11-03's log-view toggle later read via
`Path.read_text()` (which raises `UnicodeDecodeError` on invalid UTF-8) would then be corrupt.
Deciding on decoded text FIRST removes this failure mode structurally rather than special-casing
it (11-REVIEWS.md cycle 1 finding #4).

**The real `launchctl bootstrap`/`print`/`bootout` round-trip test requires an explicit opt-in
environment variable, `TOOLS_INSTALLER_RUN_LAUNCHCTL_TESTS=1`, in addition to the existing
`shutil.which("launchctl") is None` skip.** `.claude/testing.md`'s own "Tests must be
deterministic and offline" rule and this project's precedent for platform-gated tests
(`@pytest.mark.skipif(sys.platform != "darwin", ...)`) both point the same direction: a test that
mutates the developer's real GUI launchd domain — even one that tears itself down — has no place
running by default inside `uv run pytest`/`make test`/CI, where nobody is watching for a stray
registration left behind by an interrupted run (a killed test process skips its own `finally`).
This is `pyproject.toml`'s existing bare `addopts = "-q"` with no `--strict-markers`/marker
registry, so an env-var gate (rather than inventing and registering a new pytest marker) is the
lower-friction fix consistent with what is already in this codebase (11-REVIEWS.md cycle 1
finding #3). Every OTHER test added by this plan (and by 11-02/11-03/11-04) exercises `bootstrap`/
`bootout` exclusively through the injected `run` seam.

**No `clear_decided` function exists.** Unlike `installer/omz.py`'s `_clear_owned` (needed
because a full uninstall must fully reset omz's ownership so a later re-enable starts clean),
the daemon's "decided" marker is intentionally permanent once set: RESEARCH's Pitfall 2 design
is that ONE deliberate decision (auto-default OR an explicit toggle) should never be silently
un-recorded, or the on-by-default logic 11-04 builds on this marker could re-apply itself after
a user's explicit disable. 11-04 (post-revision) DOES now wire the daemon into the full-uninstall
sweep (11-REVIEWS.md cycle 1 finding #18 — see 11-04's `<design_decisions>`), reusing the SAME
`Policy.remove()` closure the Policies view already calls, exactly as every other policy's
teardown already works; that removal still calls `record_decided` (an explicit disable, even one
triggered by a full uninstall, is itself a decision — 11-02's `<design_decisions>`), so no
`clear_decided` is needed even with that sweep wired in.
</design_decisions>

## Trust Boundaries

| Boundary | Description |
|----------|--------------|
| Code-authored plist body (this module's own `render_plist` output, never derived from user input or a registry TOML) → the real `launchd`/`launchctl` scheduling substrate | Every plist field is either a code constant, a caller-supplied integer (hour/minute/days), or a `Path`/environment string resolved by this project's own composition root — never text typed by an end user at run time. |
| The installed wrapper's own argv → `subprocess.run([script_path, *forwarded])` | `forwarded` is the literal tail of the plist's own `ProgramArguments`, itself code-authored at apply time; there is no live-user-input path into this argv at all. |
| `~/.myshellrc`'s "decided" marker block (comments only) → any shell that sources it | Inert by construction — the block contains no executable shell syntax, mirroring `installer/omz.py`'s own ownership-record shape. |
| `render_plist`'s validation gate → every downstream write/registration | The single choke point every caller (11-02, 11-04) passes through before a plist can ever be written or `launchctl bootstrap` ever called; a validation bypass here would reopen 11-REVIEWS.md cycle 1 finding #5 for every consumer at once. |
