<design_decisions>
**`hard_requires` defaults to `True`, and NO existing `Policy(...)` construction site
(`ban_policy`, `tweak_policy`, `omz_plugins_policy`) passes it.** This is the entire fix: the
default preserves every currently-shipped policy's hard-block behavior byte-for-byte, so
`test_policy_missing_required_tool_blocks_enable` (which constructs a raw `Policy(...)` with no
`hard_requires` kwarg at all) keeps testing exactly what it tests today, unmodified. Only
`daemon_policy` passes `hard_requires=False`.

**`log_path` and `set_schedule` are added to `Policy` in this plan, not deferred to 11-03, even
though nothing consumes them until then.** `Policy` is a single frozen dataclass every screen
constructs against; adding a field later, after 11-03 already has code depending on it existing,
would mean editing this same dataclass twice across two plans touching the same lines for no
benefit — grounding both new fields here, alongside `hard_requires`, in the one plan that already
owns this exact edit, is strictly simpler. Both default to values that are inert for every other
policy (`None`).

**`daemon_policy`'s `.apply()` preserves an EXISTING plist's `StartCalendarInterval` (via
`daemon.read_schedule`) rather than always resetting it to the default hour/minute.** A user who
has already picked a custom time via 11-03's picker must not have that choice silently reverted
the next time `.apply()` runs for an unrelated reason (e.g. re-applying after `fd`/`rg` become
installed, or 11-04's on-by-default path re-running against an already-once-decided machine).
Only a genuinely first-ever apply (no plist on disk yet) falls back to `daemon.DEFAULT_HOUR`/
`DEFAULT_MINUTE`.

**`.remove()` also calls `daemon.record_decided`.** Per 11-RESEARCH.md Pitfall 2: an explicit
disable IS a decision, and 11-04's on-by-default logic must never re-enable a daemon the user
just turned off. This is the one place in `daemon_policy` where `.remove()`'s behavior is NOT a
mechanical inverse of `.apply()` — `.apply()` records decided on success, `.remove()` records it
unconditionally on its own success too (there is no "undecided disable" state).

**`daemon_policy` takes an injectable `run` parameter, threading 11-01's seam through to `daemon.
bootstrap`/`bootout`.** Every test in this plan constructs `daemon_policy(..., run=<fake>)` and
never touches real `launchctl` — the ONE real-subprocess test in the whole phase is 11-01's
Task 1, already committed and torn down before this plan runs.
</design_decisions>
