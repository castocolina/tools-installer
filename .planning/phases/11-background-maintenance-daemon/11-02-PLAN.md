<design_decisions>
**`hard_requires` defaults to `True`, and NO existing `Policy(...)` construction site
(`ban_policy`, `tweak_policy`, `omz_plugins_policy`) passes it.** This is the entire fix: the
default preserves every currently-shipped policy's hard-block behavior byte-for-byte, so
`test_policy_missing_required_tool_blocks_enable` (which constructs a raw `Policy(...)` with no
`hard_requires` kwarg at all) keeps testing exactly what it tests today, unmodified. Only
`daemon_policy` passes `hard_requires=False`.

**The soft-dependency copy is a NEW branch inside `_requires_cell`/`_policy_detail`, not a
rewording of the shared hard-block strings.** 11-REVIEWS.md cycle 1 finding #6 is specifically
that "Missing required tool(s): X, Y. Install from Catalog before enabling." is FALSE for a
`hard_requires=False` policy — the tool is not, in fact, required before enabling. The fix keeps
the EXISTING strings completely unchanged for `hard_requires=True` (verified by the untouched
`test_policy_missing_required_tool_blocks_enable`) and adds a parallel, calmer "recommended, not
required" branch for `hard_requires=False`, so both truths stay simultaneously representable in
the SAME two functions — no new rendering mechanism, per REQ-daemon-dependency-gating's own
"surfaced via the existing missing_requires UI with no new mechanism" text.

**`log_path` and `read_schedule` are added to `Policy` in this plan, even though `read_schedule`
has no UI consumer until 11-03.** `Policy` is a single frozen dataclass every screen constructs
against; adding a field later, after 11-03 already has code depending on it existing, would mean
editing this same dataclass twice across two plans touching the same lines for no benefit —
grounding all four new fields here, in the one plan that already owns this exact edit, is
strictly simpler. All default to values that are inert for every other policy (`None`/`True`).
`read_schedule` specifically exists because `set_schedule`'s own `PolicyResult` only reports the
outcome of the call that just happened — nothing else in `Policy` lets a LATER render (e.g. after
navigating away from and back to the Policies row) know what the currently-registered schedule
actually is (11-REVIEWS.md cycle 1 finding #13).

**`daemon_policy`'s apply/remove/set_schedule closures mirror `installer/omz.py::write_plugins`'s
reserve-then-write-then-roll-back-on-failure shape, extended for a case `omz.py` has no
equivalent of: a best-effort RE-REGISTRATION on `set_schedule`'s own rollback.** `write_plugins`
reserves the ownership record BEFORE the risky `.zshrc` edit and restores it to its exact prior
value on a refused write — there, "restoring the record" is the whole rollback, since a `.zshrc`
edit has no second, separately-registered side effect. Here, `bootstrap` both writes a
registration AND (per its own internal idempotent bootout-then-bootstrap sequence, 11-01's
Pitfall-4 mechanism) UNREGISTERS the OLD one as part of registering the new one — so restoring
just the plist FILE on a `set_schedule` failure is not enough; the daemon would then be actually
un-registered with a plist file that (once restored) claims the OLD schedule but is not backed by
a real registration until something re-`bootstrap`s it. `set_schedule`'s rollback therefore makes
a best-effort call to `daemon.bootstrap` again with the restored (old) plist content — recovering
the machine to its exact prior WORKING state, not merely its prior FILE state — before re-raising
so the UI still reports the failure (11-REVIEWS.md cycle 1 finding #9). `.apply()`'s own rollback
needs no such re-bootstrap step: on a first-ever apply there was nothing running before, and on a
reapply, `bootstrap`'s internal pre-clear only fires once the SECOND (real) `bootstrap` call is
about to run — the exact case that just failed — so there is no successfully-unregistered "old"
state left dangling the way `set_schedule`'s two-calls-in-a-row shape can leave one.

**`.remove()`'s ordering — `bootout` BEFORE deleting the plist or recording the decision — is
what makes 11-01's revised `bootout` (which now raises on a real, non-"already absent" failure)
actually protective.** A real bootout failure now propagates straight out of `.remove()` before
either the plist unlink or `record_decided` runs, so `active = plist_path.exists()` still
correctly reports `True` (the plist is still there, matching a still-loaded — or at least
not-provably-unloaded — real service) instead of lying that the daemon was removed
(11-REVIEWS.md cycle 1 finding #8). `.remove()` also still calls `daemon.record_decided` on
success, per 11-RESEARCH.md Pitfall 2: an explicit disable IS a decision, and 11-04's on-by-
default logic must never re-enable a daemon the user just turned off.

**A marker-write (`record_decided`) failure after a SUCCESSFUL `bootstrap`/`bootout` is left
unguarded (no rollback of the already-successful real side effect).** Unlike a `bootstrap`/
`bootout` failure — which leaves the plist/registration pair genuinely disagreeing and therefore
must be rolled back — a `state_path` write failure happens AFTER the real launchd side effect
already succeeded, so the plist and the actual registration still agree with each other; only the
bookkeeping "decided" marker trails. Rolling back a successful `bootstrap` just to keep the
marker in lockstep would mean tearing down a daemon that is now correctly running, which is a
worse outcome than a bookkeeping gap that self-heals: `decided(state_path)` reads `False`, so
11-04's on-by-default logic will simply attempt `.apply()` again on the next `make setup` run — an
idempotent no-op given the daemon is already correctly applied. This is documented explicitly
(rather than left as an unexamined gap) and covered by Task 2's marker-write-failure test.

**`daemon_policy` takes an injectable `run` parameter, threading 11-01's seam through to `daemon.
bootstrap`/`bootout`.** Every test in this plan constructs `daemon_policy(..., run=<fake>)` and
never touches real `launchctl` — the ONE real-subprocess test in the whole phase is 11-01's own
opt-in Task 1 test, already committed (and, when not opted in, skipped) before this plan runs.
</design_decisions>
