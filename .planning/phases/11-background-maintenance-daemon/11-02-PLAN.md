<design_decisions>
**`hard_requires` defaults to `True`, and NO existing `Policy(...)` construction site
(`ban_policy`, `tweak_policy`, `omz_plugins_policy`) passes it.** This is the entire fix: the
default preserves every currently-shipped policy's hard-block behavior byte-for-byte, so
`test_policy_missing_required_tool_blocks_enable` (which constructs a raw `Policy(...)` with no
`hard_requires` kwarg at all) keeps testing exactly what it tests today, unmodified. Only
`daemon_policy` passes `hard_requires=False`.

**The soft-dependency copy is a NEW branch inside `_requires_cell`/`_policy_detail`, not a
rewording of the shared hard-block strings.** 11-REVIEWS.md cycle 1 finding #6 is specifically
that "Missing required tool(s): X, Y. Install from Catalog before enabling." is FALSE for a
`hard_requires=False` policy — the tool is not, in fact, required before enabling. The fix keeps
the EXISTING strings completely unchanged for `hard_requires=True` (verified by the untouched
`test_policy_missing_required_tool_blocks_enable`) and adds a parallel, calmer "recommended, not
required" branch for `hard_requires=False`, so both truths stay simultaneously representable in
the SAME two functions — no new rendering mechanism, per REQ-daemon-dependency-gating's own
"surfaced via the existing missing_requires UI with no new mechanism" text.

**`log_path` and `read_schedule` are added to `Policy` in this plan, even though `read_schedule`
has no UI consumer until 11-03.** `Policy` is a single frozen dataclass every screen constructs
against; adding a field later, after 11-03 already has code depending on it existing, would mean
editing this same dataclass twice across two plans touching the same lines for no benefit —
grounding all four new fields here, in the one plan that already owns this exact edit, is
strictly simpler. All default to values that are inert for every other policy (`None`/`True`).
`read_schedule` specifically exists because `set_schedule`'s own `PolicyResult` only reports the
outcome of the call that just happened — nothing else in `Policy` lets a LATER render (e.g. after
navigating away from and back to the Policies row) know what the currently-registered schedule
actually is (11-REVIEWS.md cycle 1 finding #13).

**`daemon_policy`'s apply/remove/set_schedule closures mirror `installer/omz.py::write_plugins`'s
reserve-then-write-then-roll-back-on-failure shape, extended for a case `omz.py` has no
equivalent of: a best-effort RE-REGISTRATION on `set_schedule`'s own rollback.** `write_plugins`
reserves the ownership record BEFORE the risky `.zshrc` edit and restores it to its exact prior
value on a refused write — there, "restoring the record" is the whole rollback, since a `.zshrc`
edit has no second, separately-registered side effect. Here, `bootstrap` both writes a
registration AND (per its own internal idempotent bootout-then-bootstrap sequence, 11-01's
Pitfall-4 mechanism) UNREGISTERS the OLD one as part of registering the new one — so restoring
just the plist FILE on a `set_schedule` failure is not enough; the daemon would then be actually
un-registered with a plist file that (once restored) claims the OLD schedule but is not backed by
a real registration until something re-`bootstrap`s it. `set_schedule`'s rollback therefore makes
a best-effort call to `daemon.bootstrap` again with the restored (old) plist content — recovering
the machine to its exact prior WORKING state, not merely its prior FILE state — before re-raising
so the UI still reports the failure (11-REVIEWS.md cycle 1 finding #9). **(Corrected post cycle
2 — see finding #5 below.) `.apply()`'s own rollback on a REAPPLY needs the identical
re-bootstrap step, for the exact same reason `set_schedule`'s does.** Cycle 1's original
reasoning here — quoted above for the record, since it shaped the pre-cycle-2 code shape — was
that "on a reapply, `bootstrap`'s internal pre-clear only fires once the SECOND (real) `bootstrap`
call is about to run — the exact case that just failed — so there is no successfully-unregistered
'old' state left dangling." Re-reading `bootstrap`'s own 11-01 implementation directly disproves
this: `bootstrap` ALWAYS runs its inline, unconditional `bootout` pre-clear FIRST, before EVERY
attempt at the real `bootstrap` call, regardless of whether this is the daemon's first-ever
registration or its hundredth reapply. On a reapply, that means the OLD, working registration is
ALREADY torn down by the pre-clear the instant `.apply()`'s own `daemon.bootstrap(...)` call
begins — so if the SECOND, real `bootstrap` call inside that same invocation then fails, nothing
is registered at all, exactly the same dangling state `set_schedule`'s rollback already guards
against. Restoring only the plist FILE's bytes (the pre-cycle-2 behavior) makes
`active = plist_path.exists()` a false positive: the file says "the old, working config" while
the real launchd registration behind it is gone. The fix, symmetric with `set_schedule`: `.apply()`'s
rollback restores the snapshot bytes and, ONLY when a prior snapshot existed (a reapply — a
first-ever apply has nothing to re-register, since nothing was running before it ran), makes the
SAME best-effort `daemon.bootstrap` call with the restored content before re-raising
(11-REVIEWS.md cycle 2 finding #5).

**`.remove()`'s ordering — `bootout` BEFORE deleting the plist or recording the decision — is
what makes 11-01's revised `bootout` (which now raises on a real, non-"already absent" failure)
actually protective.** A real bootout failure now propagates straight out of `.remove()` before
either the plist unlink or `record_decided` runs, so `active = plist_path.exists()` still
correctly reports `True` (the plist is still there, matching a still-loaded — or at least
not-provably-unloaded — real service) instead of lying that the daemon was removed
(11-REVIEWS.md cycle 1 finding #8). `.remove()` also still calls `daemon.record_decided` on
success, per 11-RESEARCH.md Pitfall 2: an explicit disable IS a decision, and 11-04's on-by-
default logic must never re-enable a daemon the user just turned off.

**A marker-write (`record_decided`) failure after a SUCCESSFUL `bootstrap`/`bootout` degrades
`.apply()`'s result to a warning; it is never a rollback trigger and never a propagated exception
(corrected post cycle 2 — see finding #7 below).** Unlike a `bootstrap`/
`bootout` failure — which leaves the plist/registration pair genuinely disagreeing and therefore
must be rolled back — a `state_path` write failure happens AFTER the real launchd side effect
already succeeded, so the plist and the actual registration still agree with each other; only the
bookkeeping "decided" marker trails. Rolling back a successful `bootstrap` just to keep the
marker in lockstep would mean tearing down a daemon that is now correctly running, which is a
worse outcome than a bookkeeping gap that self-heals: `decided(state_path)` reads `False`, so
11-04's on-by-default logic will simply attempt `.apply()` again on the next `make setup` run — an
idempotent no-op given the daemon is already correctly applied. Cycle 1's own test for this case
asserted the failure PROPAGATES as an `OSError` out of `.apply()` — cycle 2 finding #7 identifies
why that shape is itself a bug, not merely "documented behavior": `run_live` DOES catch `OSError`
(returning `(None, message)`), and `installer/wizard_app.py::action_toggle_policy` (read live
this session, lines 1038-1044) only updates `self.active_state[policy.id]` when that result is
non-`None` — so a propagated marker-write failure would make the Policies screen report the
daemon as OFF and the toggle as FAILED, while the real launchd registration (and the plist file)
both correctly say it is ON. The fix: `.apply()` wraps its OWN `record_decided` call in
`try/except OSError`, and on failure still returns its normal SUCCESSFUL `PolicyResult` (the same
schedule-naming layer the happy path returns) with `PolicyResult.warning` set to a message naming
the marker-write failure — `installer/policy.py:73`'s `PolicyResult.warning: str | None` field
already exists for exactly this, and `PoliciesScreen._summary` (read live this session) already
renders it (`if result.warning: parts.append(result.warning)`) with zero UI-layer changes needed.
This is covered by Task 2's updated marker-write-failure test.

**`daemon_policy`'s shared apply helper validates the COMPLETE prospective plist (via
`daemon.render_plist`) BEFORE `install_wrapper`/`ensure_log_path` run, not only inside
`write_plist` itself (corrected post cycle 2 — see finding #6 below).** The pre-cycle-2 design
called `install_wrapper(wrapper_bin_dir)` and `ensure_log_path(log_path)` FIRST, then
`write_plist(...)` — which itself validates before writing, per 11-01. But `write_plist`'s own
"zero filesystem side effects on invalid input" guarantee is scoped to `write_plist` alone: by
the time `write_plist` raises `DaemonScheduleError` for, say, an empty `tmpdir_value`, the
wrapper has ALREADY been copied into `wrapper_bin_dir` and the log file ALREADY created — real
filesystem side effects from a call this plan's own text claimed had none. The fix: the shared
helper calls `daemon.render_plist(**the exact kwargs write_plist would use)` FIRST, purely as a
validation gate (its return value is discarded — `write_plist` still performs its own, cheap,
redundant validation internally when it runs moments later, which is harmless), and only once
that call returns successfully does it proceed to `install_wrapper`, `ensure_log_path`, and
`write_plist` (11-REVIEWS.md cycle 2 finding #6).

**`.remove()` guards its own plist unlink and gains a call to `daemon.remove_wrapper` (corrected/
extended post cycle 2 — see findings #8/#9 below).** Cycle 1's design stopped at "`bootout` before
unlink" — correct as far as it went, but left the unlink itself unguarded: a real unlink failure
(e.g. a read-only parent directory) AFTER a successful `bootout` leaves the service unloaded with
its OLD, still-on-disk plist now describing a registration that no longer exists — the inverse of
the false-positive `active` this plan already guards `.apply()`/`.set_schedule()` against. The
fix: `.remove()` wraps its `plist_path.unlink(missing_ok=True)` call, and on a real `OSError`,
makes a best-effort re-`bootstrap` of the plist that is STILL on disk (its unlink just failed, so
its old content is still there and still valid) before re-raising the unlink error — restoring
the machine to its prior WORKING state exactly like `.apply()`/`.set_schedule()`'s own rollbacks
do (11-REVIEWS.md cycle 2 finding #8). Separately, `.remove()` also now calls
`daemon.remove_wrapper(wrapper_bin_dir)` as part of its own sequence (after the plist is handled,
before `record_decided`) — `remove_wrapper` had no production caller anywhere in the pre-cycle-2
plan set, unlike `tweak_policy._remove`'s own call to `remove_tweak_executables` on every disable
(`installer/policy.py:224`, read live this session), which the architecture doc's "no orphan
helpers" rule (rule 5) flags as exactly the gap to close (11-REVIEWS.md cycle 2 finding #9). This
single fix ALSO resolves 11-REVIEWS.md cycle 2 finding #16 (Plan 11-04): because 11-04's
full-uninstall teardown reuses this SAME `.remove()` closure (the architecture invariant that
"full uninstall" and "toggle off" are one operation), a full uninstall now removes the wrapper
too, with no separate 11-04-side change required — see 11-04's `<design_decisions>` for the
cross-reference.

**`Policy.is_active` is a live re-check closure, added alongside this plan's other four new
`Policy` fields, because the frozen `active: bool` field cannot answer "is this policy active
RIGHT NOW" once a `Policy` instance has been constructed and something else (11-04's on-by-default
worker, running on a separate thread after construction) may have changed the real, on-disk
state.** `installer/uninstall.py::active_policies` (read live this session) already solves this
exact problem for `tweak_policy`/`omz_plugins_policy` by RE-CONSTRUCTING those `Policy` objects
fresh, at read time, inside `active_policies` itself — `_omz_policy(...)`'s own `active=
plugins_owned(state_path)` is evaluated the moment `active_policies` calls it, never reused from
an earlier construction. `daemon_policy` cannot be cheaply re-constructed the same way at that
call site without re-deriving `tmpdir_value`/`uv_path`/etc. a second time outside the composition
root that already resolved them once (11-04's own "one construction, multiple consumers"
discipline, kept to avoid config drift) — so instead of re-constructing, `daemon_policy` exposes
one more trivial closure, `is_active = lambda: plist_path.exists()`, the SAME fact `.active` was
computed from, just re-evaluated on demand rather than snapshotted once. Every other policy's
`is_active` stays `None`, meaning "no live check available, the frozen `active` field already IS
the live answer for this policy" — unchanged behavior everywhere except the one call site 11-04
updates to prefer `is_active()` when present (11-REVIEWS.md cycle 2 finding #13).

**`daemon_policy` takes an injectable `run` parameter, threading 11-01's seam through to `daemon.
bootstrap`/`bootout`.** Every test in this plan constructs `daemon_policy(..., run=<fake>)` and
never touches real `launchctl` — the ONE real-subprocess test in the whole phase is 11-01's own
opt-in Task 1 test, already committed (and, when not opted in, skipped) before this plan runs.
</design_decisions>
