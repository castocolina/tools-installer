<objective>
Wire `daemon_policy` into the real composition root (`setup.py::_build_app`), gated to macOS
only, and implement ROADMAP SC#1's on-by-default requirement (CONTEXT.md D-01: the user

the auto-apply real while keeping every pre-existing test in this codebase's large `setup.py`/
`wizard_app.py` test suites completely unaffected, by construction rather than by monkeypatching
around the new behavior.

`UnifiedApp.daemon_default`/`on_mount` wiring.

<design_decisions>
**`ensure_daemon_default` is called from the REAL `UnifiedApp.on_mount`, never from `_build_app`'s
own synchronous body.** This is the single design decision that makes an eager, real-subprocess
auto-apply safe to ship in a codebase whose entire test suite is built around `_build_app` running
"for real" against a fake `UnifiedApp` stand-in (`tests/test_setup.py`'s `_capture_app`). If the
auto-apply lived inside `_build_app` itself, EVERY existing `setup.py` test using `_capture_app`
— dozens, spanning uninstall/policies/link-mode wiring — would eagerly trigger a real `launchctl
bootstrap` against the developer's actual `gui/<uid>` session the moment this plan's daemon-
policy construction became macOS-gated-true (`_sandbox`'s own `_platform()` fixture already
returns `os="macos"`). Placing the trigger inside `UnifiedApp.on_mount` — a method the fake
`_capture_app` class never defines at all, since it is a lightweight stand-in, not a `Screen`/
`App` subclass — means the auto-apply is structurally unreachable from any test using that
pattern, with zero new monkeypatching required anywhere in `tests/test_setup.py`. Only a REAL,
running `UnifiedApp` (a genuine end-user session, or a headless `run_test()` pilot that
deliberately constructs the real class) ever reaches it. This mirrors this codebase's own
established discipline for the ONE other real-subprocess-spawning mechanism in the whole app
(`DoctorScreen`'s pnpm-globals audit, deferred to a thread worker started from a real screen's
`on_mount`, never from `_build_app`'s synchronous construction).

**`ensure_daemon_default` records nothing on failure.** Per RESEARCH's own Open Question 1
recommendation: a transient `launchctl bootstrap` failure (e.g. a restricted/managed Mac) should
retry on the next `make setup` run rather than permanently marking the machine "decided" with
`active=False` forever. `decided(state_path)` is only ever set to `True` inside `daemon_policy`'s
own `.apply()`/`.remove()` closures, both of which only reach their `record_decided` call after
their real side effect (bootstrap / bootout+unlink) has already succeeded — `ensure_daemon_
default` adds no separate record-on-failure path of its own.

**The four new `setup.py` path constants are computed the same way `_MYSHELLRC`/`_DEFAULT_BIN_
DIR` already are — module-level, `Path.home()`-derived, at import time — specifically so `tests/
test_setup.py`'s existing `_sandbox` fixture can override them with `monkeypatch.setattr` exactly
like it already does for the other three.** A function-scoped `Path.home()` call inside
`_build_app` itself would not need this treatment, but would break the established pattern this
file already uses everywhere else for real-machine paths, and would make `_sandbox`'s existing
override mechanism inapplicable without inventing a second one.
</design_decisions>

|----------|--------------|
