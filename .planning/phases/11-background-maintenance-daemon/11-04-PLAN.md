<objective>
Wire `daemon_policy` into the real composition root (`setup.py::_build_app`), gated to macOS
only, and implement ROADMAP SC#1's on-by-default requirement (CONTEXT.md D-01: the user
explicitly chose on-by-default over the initially-recommended opt-in default) — the one
genuinely new shape this phase introduces, since every existing `Policy.active` in this codebase
is presence-based and none is ever proactively applied without the user pressing space
(11-RESEARCH.md Pitfall 2).

This revision (post cross-AI review cycle 1) closes five findings scoped to this plan: on-by-
default must run in a worker, never synchronously on the event loop, and its success must
EXPLICITLY refresh the Policies screen's own `active_state` (#16); the auto-apply callback must
never be wired for the interactive uninstall flow's own `_build_app` call (#17); a full uninstall
must actually tear down the daemon like every other active policy, on both the CLI and TUI paths
(#18); the real per-user TMPDIR must be resolved and validated at THIS composition-root call site
too, never a blind empty-string default (#19); and integration tests must exercise the real
worker/message/uninstall-suppression/teardown paths, not just the composition-only wiring (#20).

Task 1 is this plan's tracer: the smallest slice proving the daemon reaches the real Policies
list on macOS and is absent on Linux — pure composition, no on-by-default logic yet, but with the
real, validated TMPDIR/`uv` resolution this whole phase's safety depends on. Task 2 adds
`ensure_daemon_default` and wires it into `UnifiedApp.on_mount` via a worker + explicit UI
refresh, suppressed for the uninstall flow. Task 3 wires the SAME daemon policy into both
uninstall paths' teardown sweep, so a full uninstall never leaves it running unattended.

Purpose: REQ-launchd-prune-policy (macOS-only gating, the real `--days 3` default, on-by-default,
safe teardown).
Output: `setup.py`'s daemon wiring (`_build_daemon_policy`); `installer/policy.py::
ensure_daemon_default`; `UnifiedApp.daemon_default`/`on_mount` worker wiring +
`PoliciesScreen.refresh_daemon_state`; `installer/uninstall.py`/`installer/app.py`'s daemon-aware
teardown sweep.
</objective>

<design_decisions>
**`_build_daemon_policy(platform, installed) -> Policy | None` is a single, shared helper — not
inlined separately into `_build_app` and `_run_uninstall`.** 11-REVIEWS.md cycle 1 finding #18
requires the daemon to be torn down through BOTH the interactive TUI uninstall path and the
non-interactive CLI uninstall path; constructing two independent `daemon_policy(...)` calls (one
per path) with the same four path constants would work today but invites the two constructions
drifting apart later (e.g. one call site gets a `path_value`/`tmpdir_value` fix the other misses).
A single helper, called from both `_build_app` and `_run_uninstall`, removes that risk
structurally — this mirrors the SAME "one construction, multiple consumers" discipline
`installer/uninstall.py::active_policies` already uses for the omz/tweak policies it builds once
and hands to both the preview and the sweep.

**TMPDIR and `uv_path` are resolved into NAMED LOCAL VARIABLES inside `_build_daemon_policy`,
with a comment explaining the fail-closed backstop, rather than inlined as anonymous
`os.environ.get(...)`/`shutil.which(...)` expressions passed directly as kwargs.** 11-01's
`DaemonScheduleError` validation already makes an empty/invalid value fail closed wherever
`daemon_policy` is actually applied — but 11-REVIEWS.md cycle 1 finding #19 is specifically that
the COMPOSITION ROOT itself (this plan) must not treat resolving these values as a one-line
afterthought the way the original `os.environ.get("TMPDIR", "")` draft did; naming them and
commenting the fail-closed contract they rely on makes the intent legible to a future editor
without requiring a second read of `daemon.py`. On a normal interactive macOS session `TMPDIR` is
always set (macOS's own per-user-session launchd populates it at login, live-verified on this
development machine: `/var/folders/.../T/`) and `uv` is always resolvable (this project's own
`install.sh` guarantees it before `setup.py` ever runs) — this validation is a defensive
backstop for a genuinely broken/minimal environment, not a normal-case concern.

**`ensure_daemon_default` is called from a WORKER started by the REAL `UnifiedApp.on_mount`,
never from `_build_app`'s own synchronous body and never synchronously inside `on_mount`
itself.** This is the design decision that makes an eager, real-subprocess auto-apply safe AND
non-blocking. Two separate hazards are both closed by the same fix: (1) if the auto-apply lived
inside `_build_app` itself, EVERY existing `setup.py` test using `_capture_app` — dozens, spanning
uninstall/policies/link-mode wiring — would eagerly trigger a real `launchctl bootstrap` against
the developer's actual `gui/<uid>` session the moment this plan's daemon-policy construction
became macOS-gated-true; (2) if it ran synchronously inside `on_mount` (even the real one), a slow
or hung `launchctl bootstrap` call (`run_captured`'s underlying `subprocess.run` has no timeout)
would freeze the whole TUI's frame rendering and keypress handling for its duration — exactly the
reason `DoctorScreen`'s pnpm-globals audit already runs in a `@work(thread=True, ...)` worker
rather than synchronously, per that screen's own docstring precedent. Placing the trigger inside
a worker STARTED BY `UnifiedApp.on_mount` — a method the fake `_capture_app` class never defines
at all, since it is a lightweight stand-in, not a `Screen`/`App` subclass — means the auto-apply
is structurally unreachable from any test using that pattern, with zero new monkeypatching
required anywhere in `tests/test_setup.py`, AND never blocks the event loop even when it does run
(11-REVIEWS.md cycle 1 findings #1/#3).

**The worker posts a message; `UnifiedApp` handles it by calling a NEW, explicit
`PoliciesScreen.refresh_daemon_state` method — the auto-apply's own boolean result is never
silently discarded.** `PoliciesScreen.active_state` is a plain `dict[str, bool]` snapshotted once
in `__init__`, which — per `.claude/architecture.md`'s own screen-install-on-mount rule — happens
BEFORE `UnifiedApp.on_mount`'s body (and therefore before this worker) ever runs. Without an
explicit call reaching back into that already-constructed screen's own state, a successful
auto-apply would be real on disk (the plist exists, `daemon.decided` is `True`) but invisible on
the very screen a user would check to confirm it — 11-REVIEWS.md cycle 1 finding #16's own
description of the bug. `refresh_daemon_state` is intentionally idempotent/defensive (it is a
no-op if the state did not actually change, and only touches live widgets when the screen is
mounted and/or the affected row is the one currently highlighted), so it is safe to call
unconditionally from the message handler with no extra guard logic at the call site.

**`daemon_default`/`daemon_default_policy_id` are suppressed (left `None`) specifically for
`initial_view == "uninstall"`, while the daemon `Policy` OBJECT itself is still constructed and
still appended to `PolicyInputs.policies` regardless.** Suppressing the whole daemon `Policy` for
that view would make the Uninstall flow's own teardown sweep (Task 3) unable to see or remove it
— the opposite of what finding #18 asks for. The two concerns are orthogonal: "should this
process auto-apply a policy the user has not decided on yet" (no, whenever the user's very next
screen might be the one where they remove things) versus "should the Policies screen and the
uninstall sweep both still see the real, current state of this policy" (yes, always) — this plan
resolves them independently rather than conflating "suppress auto-apply" with "hide the policy."

**`installer/uninstall.py::sweep_policies`'s except clause is widened to `(OSError,
CommandError)`.** This is this plan's own finding, discovered while wiring `daemon_policy` into
the sweep loop: every OTHER `Policy.remove()` in this codebase today can only ever raise an
`OSError`-family exception (a real filesystem failure, or `OmzPluginsError`, itself an `OSError`
subclass), which is what `sweep_policies`'s original `except OSError:` was written against.
11-02's `daemon_policy.remove()` can now ALSO raise `installer.run.CommandError` (a real,
non-"already absent" `bootout` failure, `RuntimeError`-based per `installer/run.py`, NOT an
`OSError` subclass) — left unguarded, that single per-policy failure would propagate straight out
of the whole sweep loop, aborting every LATER bundle/`omz-plugins` teardown behind it, which is
exactly the "a read-only bin dir... letting the first one propagate abandoned every later bundle"
failure mode `sweep_policies`'s own docstring already says it exists to prevent. Widening the
except tuple restores that isolation guarantee for the newly-possible exception type, with zero
behavior change for every existing policy kind.

**The `UninstallScreen`'s existing `#tweaks` lever (`remove_tweaks`) is REUSED for the daemon,
not given a new checkbox/lever.** 11-01's ORIGINAL (pre-revision) `<design_decisions>` argued
against this — reasoning that the lever's "shell tweaks"/"blocks + helpers" copy would misdescribe
a plist+LaunchAgent teardown, and that a new lever was surface beyond this phase's scope.
11-REVIEWS.md cycle 1 finding #18 overturns that call on safety grounds: leaving a real,
unattended background deletion daemon running after a user explicitly chose "full uninstall" is a
worse outcome than an imperfectly-worded existing lever. This plan reuses `#tweaks` (so no new
UI surface is added, keeping the fix minimal) AND fixes the row's own copy to stop claiming it
covers only "shell tweaks" once a background job is also included — `installer/wizard_app.py`'s
`_tweak_entry` and `installer/app.py::run_uninstall`'s CLI preview line both become
daemon-aware, appending "+ background jobs" / naming the LaunchAgent explicitly only when a
`daemon:`-prefixed id is actually among the ids being offered, leaving the copy byte-identical
when it is not (e.g. on Linux, or on macOS with the daemon never enabled).
</design_decisions>
