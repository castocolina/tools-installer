<objective>
Wire `daemon_policy` into the real composition root (`setup.py::_build_app`), gated to macOS
only, and implement ROADMAP SC#1's on-by-default requirement (CONTEXT.md D-01: the user
explicitly chose on-by-default over the initially-recommended opt-in default) — the one
genuinely new shape this phase introduces, since every existing `Policy.active` in this codebase
is presence-based and none is ever proactively applied without the user pressing space
(11-RESEARCH.md Pitfall 2).

This revision (post cross-AI review cycle 1) closes five findings scoped to this plan: on-by-
default must run in a worker, never synchronously on the event loop, and its success must
EXPLICITLY refresh the Policies screen's own `active_state` (#16); the auto-apply callback must
never be wired for the interactive uninstall flow's own `_build_app` call (#17); a full uninstall
must actually tear down the daemon like every other active policy, on both the CLI and TUI paths
(#18); the real per-user TMPDIR must be resolved and validated at THIS composition-root call site
too, never a blind empty-string default (#19); and integration tests must exercise the real
worker/message/uninstall-suppression/teardown paths, not just the composition-only wiring (#20).

This revision (post cross-AI review cycle 2) closes six findings scoped to this plan on top of the
cycle-1 shape above: auto-apply is restricted to the genuine interactive setup-wizard entry point
via a new, explicit `apply_daemon_default` allowlist flag, not merely `initial_view != "uninstall"`
— the pre-cycle-2 blocklist wrongly let `make doctor`'s read-only flow auto-apply too (#14); a
`self._daemon_default_in_flight` lock/pending-state flag serializes the background worker with
manual toggle/uninstall-removal actions (#15); the Uninstall sweep's daemon-inclusion check reads
`daemon_policy.is_active()` (11-02's new live-check field) instead of the frozen `active` snapshot,
so an on-by-default worker's enable is never invisible to a later Uninstall visit (#13, a 11-02
field this plan consumes); `daemon_policy.remove()` now removing the wrapper (11-02's own fix)
automatically closes the "full uninstall leaves the wrapper behind" gap with no separate change
here (#16); a new `clear_decided` call, composition-root-only and post-sweep, makes a full
uninstall+reinstall genuinely fresh without touching the ordinary toggle-off marker (#17); and
`tests/test_uninstall_e2e.py`'s two `perform_uninstall(...)` call sites are updated for the new
required `daemon_policy` parameter (#18), alongside making every uninstall preview/confirmation/
success/failure string daemon-aware, not only the preview row (#19), and hardening the
auto-apply-suppression test to assert against `_capture_app`'s captured kwargs across every
`initial_view` entry point, not merely that a callback was never invoked (#20).

Task 1 is this plan's tracer: the smallest slice proving the daemon reaches the real Policies
list on macOS and is absent on Linux — pure composition, no on-by-default logic yet, but with the
real, validated TMPDIR/HOME/`uv` resolution this whole phase's safety depends on. Task 2 adds
`ensure_daemon_default` and wires it into `UnifiedApp.on_mount` via a worker + explicit UI
refresh, gated by the new `apply_daemon_default` allowlist flag and serialized against manual
actions by the new in-flight lock. Task 3 wires the SAME daemon policy into both
uninstall paths' teardown sweep — reading its LIVE activity, not a frozen snapshot — so a full
uninstall never leaves it running unattended, never leaves its wrapper behind, and treats a
full uninstall+reinstall as genuinely fresh.

<design_decisions>
**`_build_daemon_policy(platform, installed) -> Policy | None` is a single, shared helper — not
inlined separately into `_build_app` and `_run_uninstall`.** 11-REVIEWS.md cycle 1 finding #18
requires the daemon to be torn down through BOTH the interactive TUI uninstall path and the
non-interactive CLI uninstall path; constructing two independent `daemon_policy(...)` calls (one
per path) with the same four path constants would work today but invites the two constructions
drifting apart later (e.g. one call site gets a `path_value`/`tmpdir_value` fix the other misses).
A single helper, called from both `_build_app` and `_run_uninstall`, removes that risk
structurally — this mirrors the SAME "one construction, multiple consumers" discipline
`installer/uninstall.py::active_policies` already uses for the omz/tweak policies it builds once
and hands to both the preview and the sweep.

**TMPDIR, `HOME`, and `uv_path` are resolved into NAMED LOCAL VARIABLES inside
`_build_daemon_policy`,
with a comment explaining the fail-closed backstop, rather than inlined as anonymous
`os.environ.get(...)`/`shutil.which(...)` expressions passed directly as kwargs.** 11-01's
`DaemonScheduleError` validation already makes an empty/invalid value fail closed wherever
`daemon_policy` is actually applied — but 11-REVIEWS.md cycle 1 finding #19 (and, for `HOME`
specifically, cycle 2 finding #1's composition-root half) is specifically that
the COMPOSITION ROOT itself (this plan) must not treat resolving these values as a one-line
afterthought the way the original `os.environ.get("TMPDIR", "")` draft did; naming them and
commenting the fail-closed contract they rely on makes the intent legible to a future editor
without requiring a second read of `daemon.py`. On a normal interactive macOS session `TMPDIR`/
`HOME` are
always set (macOS's own per-user-session launchd populates them at login, live-verified on this
development machine: `TMPDIR=/var/folders/.../T/`, `HOME=/Users/<user>` — and, separately, a real
bootstrapped `gui/<uid>` LaunchAgent's own environment was live-verified this session to already
inherit `HOME` from the login session even after explicit `EnvironmentVariables.PATH`/`TMPDIR`
overrides, per 11-01's own `<design_decisions>`; this composition-root resolution is a defensive,
version-independent guarantee, not a fix for an observed failure) and `uv` is always resolvable
(this project's own
`install.sh` guarantees it before `setup.py` ever runs) — this validation is a defensive
backstop for a genuinely broken/minimal environment, not a normal-case concern.

**`ensure_daemon_default` is called from a WORKER started by the REAL `UnifiedApp.on_mount`,
never from `_build_app`'s own synchronous body and never synchronously inside `on_mount`
itself.** This is the design decision that makes an eager, real-subprocess auto-apply safe AND
non-blocking. Two separate hazards are both closed by the same fix: (1) if the auto-apply lived
inside `_build_app` itself, EVERY existing `setup.py` test using `_capture_app` — dozens, spanning
uninstall/policies/link-mode wiring — would eagerly trigger a real `launchctl bootstrap` against
the developer's actual `gui/<uid>` session the moment this plan's daemon-policy construction
became macOS-gated-true; (2) if it ran synchronously inside `on_mount` (even the real one), a slow
or hung `launchctl bootstrap` call (`run_captured`'s underlying `subprocess.run` has no timeout)
would freeze the whole TUI's frame rendering and keypress handling for its duration — exactly the
reason `DoctorScreen`'s pnpm-globals audit already runs in a `@work(thread=True, ...)` worker
rather than synchronously, per that screen's own docstring precedent. Placing the trigger inside
a worker STARTED BY `UnifiedApp.on_mount` — a method the fake `_capture_app` class never defines
at all, since it is a lightweight stand-in, not a `Screen`/`App` subclass — means the auto-apply
is structurally unreachable from any test using that pattern, with zero new monkeypatching
required anywhere in `tests/test_setup.py`, AND never blocks the event loop even when it does run
(11-REVIEWS.md cycle 1 findings #1/#3).

**The worker posts a message; `UnifiedApp` handles it by calling a NEW, explicit
`PoliciesScreen.refresh_daemon_state` method — the auto-apply's own boolean result is never
silently discarded.** `PoliciesScreen.active_state` is a plain `dict[str, bool]` snapshotted once
in `__init__`, which — per `.claude/architecture.md`'s own screen-install-on-mount rule — happens
BEFORE `UnifiedApp.on_mount`'s body (and therefore before this worker) ever runs. Without an
explicit call reaching back into that already-constructed screen's own state, a successful
auto-apply would be real on disk (the plist exists, `daemon.decided` is `True`) but invisible on
the very screen a user would check to confirm it — 11-REVIEWS.md cycle 1 finding #16's own
description of the bug. `refresh_daemon_state` is intentionally idempotent/defensive (it is a
no-op if the state did not actually change, and only touches live widgets when the screen is
mounted and/or the affected row is the one currently highlighted), so it is safe to call
unconditionally from the message handler with no extra guard logic at the call site.

**`daemon_default`/`daemon_default_policy_id` are gated by a NEW, EXPLICIT `apply_daemon_default:
bool = False` parameter — an ALLOWLIST, not the pre-cycle-2 `initial_view != "uninstall"`
BLOCKLIST — while the daemon `Policy` OBJECT itself is still constructed and
still appended to `PolicyInputs.policies` regardless (corrected post cycle 2 — see finding #14
below).** The pre-cycle-2 design's blocklist reasoning (quoted below for the record) was
otherwise sound: suppressing the whole daemon `Policy` for the uninstall view would make the
Uninstall flow's own teardown sweep (Task 3) unable to see or remove it — the opposite of what
finding #18 asks for, so the daemon `Policy` object staying visible/appended for EVERY
`initial_view` is UNCHANGED by this fix. What cycle 2 finding #14 identifies is that
`initial_view != "uninstall"` is the WRONG shape of gate: reading `setup.py` directly (live this
session) shows `initial_view` takes the values `"doctor"` (BOTH `_run_doctor`'s and `_run_fix`'s
interactive paths), `"uninstall"`, `"policies"` (the `--guard`/`--unguard` interactive branch),
and the DEFAULT `BASE_VIEW` (`_select_catalog`'s call — the one, genuine, normal `make setup`
wizard flow) — a blocklist that only excludes `"uninstall"` WRONGLY includes `"doctor"` and
`"policies"`, meaning simply running `make doctor` (which the Makefile explicitly promises is
READ-ONLY, `Makefile:19`, read live this session) would silently register and start a background
deletion LaunchAgent. The fix replaces the blocklist with an explicit allowlist flag,
`apply_daemon_default: bool = False`, threaded through `_build_app`'s own signature; ONLY
`_select_catalog`'s call site passes `apply_daemon_default=True` — every other call site
(`_run_doctor`, `_run_fix`, `_run_uninstall`, the `--guard`/`--unguard` branch) either omits the
kwarg (defaulting `False`) or passes it explicitly for clarity, so a FUTURE new entry point added
to `setup.py` defaults to NOT auto-applying unless someone deliberately opts it in — the safer
failure direction than a blocklist, which defaults new entry points to auto-applying unless
someone remembers to add them to the exclusion list. The two concerns this fix keeps orthogonal:
"should this
process auto-apply a policy the user has not decided on yet" (only for the genuine setup wizard
flow) versus "should the Policies screen and the
uninstall sweep both still see the real, current state of this policy" (yes, always, from every
entry point) — this plan
resolves them independently rather than conflating "gate auto-apply" with "hide the policy."

**`installer/uninstall.py::sweep_policies`'s except clause is widened to `(OSError,
CommandError)`.** This is this plan's own finding, discovered while wiring `daemon_policy` into
the sweep loop: every OTHER `Policy.remove()` in this codebase today can only ever raise an
`OSError`-family exception (a real filesystem failure, or `OmzPluginsError`, itself an `OSError`
subclass), which is what `sweep_policies`'s original `except OSError:` was written against.
11-02's `daemon_policy.remove()` can now ALSO raise `installer.run.CommandError` (a real,
non-"already absent" `bootout` failure, `RuntimeError`-based per `installer/run.py`, NOT an
`OSError` subclass) — left unguarded, that single per-policy failure would propagate straight out
of the whole sweep loop, aborting every LATER bundle/`omz-plugins` teardown behind it, which is
exactly the "a read-only bin dir... letting the first one propagate abandoned every later bundle"
failure mode `sweep_policies`'s own docstring already says it exists to prevent. Widening the
except tuple restores that isolation guarantee for the newly-possible exception type, with zero
behavior change for every existing policy kind.

**The `UninstallScreen`'s existing `#tweaks` lever (`remove_tweaks`) is REUSED for the daemon,
not given a new checkbox/lever.** 11-01's ORIGINAL (pre-revision) `<design_decisions>` argued
against this — reasoning that the lever's "shell tweaks"/"blocks + helpers" copy would misdescribe
a plist+LaunchAgent teardown, and that a new lever was surface beyond this phase's scope.
11-REVIEWS.md cycle 1 finding #18 overturns that call on safety grounds: leaving a real,
unattended background deletion daemon running after a user explicitly chose "full uninstall" is a
worse outcome than an imperfectly-worded existing lever. This plan reuses `#tweaks` (so no new
UI surface is added, keeping the fix minimal) AND fixes the row's own copy to stop claiming it
covers only "shell tweaks" once a background job is also included — `installer/wizard_app.py`'s
`_tweak_entry` and `installer/app.py::run_uninstall`'s CLI preview line both become
daemon-aware, appending "+ background jobs" / naming the LaunchAgent explicitly only when a
`daemon:`-prefixed id is actually among the ids being offered, leaving the copy byte-identical
when it is not (e.g. on Linux, or on macOS with the daemon never enabled).

**The Uninstall sweep's daemon-inclusion check in `active_policies` reads `daemon_policy.
is_active()` when that closure is not `None`, never the frozen `daemon_policy.active` field
alone (post cycle 2 — see finding #13 below).** `Policy` is a frozen dataclass; `_build_daemon_
policy`/Task 1 constructs ONE daemon `Policy` instance, shared between the Policies list and
(via Task 2's worker closure) the on-by-default auto-apply — the SAME instance `active_policies`
later reads when the user visits Uninstall. If the daemon was undecided (OFF) at construction
time and the worker enables it AFTER construction (running on its own thread, possibly seconds
into the same session), the frozen `active` field on that already-constructed instance never
updates — `active_policies` would silently exclude a daemon that is, in reality, now running.
`installer/uninstall.py::active_policies` already solves this exact class of problem for
`tweak_policy`/`omz_plugins_policy` by re-constructing those `Policy` objects FRESH inside itself
at read time; `daemon_policy` cannot be cheaply re-constructed the same way at that call site
without re-deriving TMPDIR/HOME/`uv_path` a second time, so 11-02 instead added a trivial live-
check closure, `is_active`, to exactly this end. The fix here is one line: `active_policies`'s
daemon-inclusion predicate becomes `daemon_policy.is_active() if daemon_policy.is_active is not
None else daemon_policy.active` — every OTHER policy kind is unaffected, since `is_active`
defaults to `None` for all of them.

**A `self._daemon_default_in_flight: bool` flag on `UnifiedApp` serializes the background worker
with manual actions on the SAME policy (post cycle 2 — see finding #15 below), rather than a
full mutex/thread-lock around `daemon_policy.apply`/`remove` themselves.** 11-REVIEWS.md cycle 2
finding #15 names a real race: the on-by-default worker's `.apply()` call runs on its OWN thread
(that is the whole point of `@work(thread=True, ...)`), so it can be genuinely IN FLIGHT — mid
`bootout`/`bootstrap` — at the exact moment a user, on the main/event-loop thread, presses `space`
to toggle the SAME policy (`action_toggle_policy`'s own `run_live(policy.apply)` call would then
run CONCURRENTLY with the worker's), or opens Uninstall and confirms a removal that would delete
the very plist the worker is still writing. A full mutex around `daemon_policy`'s own closures
would need to span a real `subprocess.run` call from two different call sites with different
failure-handling shapes — a larger, riskier change for a MEDIUM-severity, narrow-window race. The
lighter fix: a single boolean flag, set `True` the instant the worker is dispatched (in
`__init__`, before `on_mount`'s worker-start call even runs, so there is no window where it reads
`False` while the worker is merely about to start) and cleared, unconditionally, the moment
`on_daemon_default_applied` processes the worker's completion message (which — per the
ALWAYS-post-a-message fix above — is now guaranteed to eventually fire for every outcome,
success, no-op, or failure). `action_toggle_policy` and `UninstallScreen._apply_removal` both
check this ONE flag before acting on the ONE policy it names, refusing with a "try again in a
moment" status message rather than proceeding — every OTHER policy's toggle, and any uninstall
selection that does not include the daemon, is completely unaffected, since the flag only ever
gates the one policy id `_daemon_default_policy_id` names.

**`installer/daemon.py::clear_decided` (added, unused, in 11-01) gets its ONE production caller
here, in `installer/app.py`, called AFTER the sweep, never before, and never from
`daemon_policy.remove()` itself (post cycle 2 — see finding #17 below).** 11-01's own permanent-
marker design remains correct for the ORDINARY case: an explicit Policies-screen toggle-off must
never silently un-record itself, or the on-by-default logic could re-enable a daemon the user
just disabled. A FULL uninstall is the one case that reasoning does not cover: it is meant to
return the machine to a state indistinguishable from a fresh install, so a LATER reinstall should
see `decided(state_path)` read `False` again, exactly mirroring `installer/omz.py::remove_plugins`'s
own unconditional `_clear_owned` call on every removal. Since `daemon_policy.remove()` is the
SAME closure the ordinary toggle calls, `clear_decided` cannot live inside it without also firing
on an ordinary disable — so this plan calls it from the COMPOSITION ROOT, `installer/app.py::
run_uninstall`/`perform_uninstall`, immediately after their respective sweep call returns, and
ONLY when the daemon's id is present in that sweep's OWN `SweepResult.swept` (never on a failed
removal). The ordering is load-bearing: `daemon_policy.remove()` itself still calls
`record_decided` as part of the SAME sweep call that is about to complete — calling
`clear_decided` BEFORE the sweep, rather than after, would have its effect immediately undone by
that `record_decided` call running moments later, recreating the very marker the fix was trying
to clear.

**`tests/test_uninstall_e2e.py` is added to this plan's scope specifically because it constructs
real `perform_uninstall(...)` calls outside `setup.py`'s own composition root (post cycle 2 — see
finding #18 below).** This file's own `_build_real_app`/`_build_real_app_with_tweaks` helpers
(read live this session) each define a `_remove` closure calling `perform_uninstall(decision,
bin_dir=..., myshellrc_path=..., rc_paths=..., bundles=..., zshrc_path=...)` with no
`daemon_policy=` kwarg at all — once `perform_uninstall` gains that REQUIRED keyword-only
parameter, both closures raise `TypeError` the instant they are called, breaking two currently-
passing e2e tests with no relation to this phase's own new behavior. Both are Linux-platform
tests (`_LINUX = Platform(os="debian", ...)`), so the fix is simply `daemon_policy=None` at both
call sites — the daemon is macOS-only and was never going to be constructed for these tests
regardless.

**Every uninstall preview/confirmation/success/failure string is made daemon-aware, not only the
preview row this plan's pre-cycle-2 design already covered (post cycle 2 — see finding #19
below).** The pre-cycle-2 design fixed `UninstallScreen._tweak_entry`'s PREVIEW label/detail and
`run_uninstall`'s CLI PREVIEW line — both shown BEFORE the user confirms. Cycle 2 finds the
SUCCESS-reporting strings shown AFTER confirmation were missed: `UninstallScreen._applied_summary`
(current source, read live this session) still unconditionally appends "shell tweaks disabled
({ids}) — open a new shell so functions and aliases refresh" whenever `decision.remove_tweaks` was
selected, and `run_uninstall`'s own CLI success line still unconditionally prints "Shell tweaks
disabled: {ids}." — both wordings are misleading (a LaunchAgent needs no shell reload at all) when
the daemon is the ONLY id actually swept, and incomplete when it is swept alongside real tweaks.
The fix keys off `swept.swept` — the sweep's OWN result, never the offered/preview ids, per this
codebase's existing "report the sweep's own result, never the preview" discipline
(`_applied_summary`'s own existing comment) — appending daemon-specific wording when a
`daemon:`-prefixed id is present in `swept.swept`, and appending the shell-reload hint only when
`swept.swept` ALSO contains at least one non-`daemon:` id; when no `daemon:` id is present, both
strings stay byte-identical to today.

**The auto-apply-suppression test asserts against `_capture_app`'s own captured `_build_app`
kwargs, across every `initial_view` `setup.py` uses, not only that an injected callback was never
called (post cycle 2 — see finding #20 below).** The pre-cycle-2 test proved `UnifiedApp`'s OWN
suppression behavior when constructed DIRECTLY with `daemon_default=None` — it never drove
`setup.py::_build_app` itself, so a bug in `_build_app`'s OWN gating condition (exactly the
`!= "uninstall"` blocklist bug finding #14 identifies) would have passed that test's own
assertions completely undetected, since the test never exercised the code path that decides
WHETHER to pass `daemon_default` in the first place. The fix uses `_capture_app` (this codebase's
existing "stand in for `UnifiedApp` so `_build_app` runs for real" test seam, `tests/
test_setup.py:93`, read live this session) to inspect the ACTUAL kwargs `_build_app` constructed
`UnifiedApp` with, for `initial_view="doctor"`, `"uninstall"`, `"policies"`, and the DEFAULT
`BASE_VIEW` path — this is the ONLY way to catch a composition-wiring bug at the layer it
actually lives, independent of whether anything downstream (a worker, an `on_mount`) ever
executes.
