## Confirmed

### X-01 [MEDIUM, reported HIGH] The guard allows checkout script bodies, whether sourced or run directly

- **Location:** `tests/sandbox.py:385-398` (`_ScriptChecker.source`), `tests/sandbox.py:150-159`
  (`_under_checkout_roots` / `_file_allowed`), `tests/sandbox.py:445-448` and `:500-501`.
- **Evidence:** `source()` only collects function names from a checkout file (`for match in
  _FUNCTION_NAMES.finditer(text): self.functions.add(...)`). It never sends the sourced text
  through `check_script`. `install.sh:91-93` runs `main "$@"` unless `TI_SOURCED` is set, and
  `main` calls `ensure_uv` (curl) and `fetch_repo` (git).
- **Reproduced (pure check, PATH=/usr/bin:/bin):** `check_launch(["/bin/sh","-c",". <checkout>/install.sh"])`
  is ALLOWED. `check_launch(["/bin/sh","<checkout>/install.sh"])` is also ALLOWED.
  `check_launch(["/bin/sh","-c","curl …"])` is REFUSED (`/usr/bin/curl`).
- **Why it is downgraded:** the reviewer frames sourcing as a special bypass. It is not:
  running a checkout script directly gets the same pass, because D-20 makes
  `scripts/`, `install.sh` and `setup.py` trusted roots, and D-18 explicitly allows sourcing
  checkout files to collect function names. The guard is in-process, so a script it allows
  runs its body in a child process the guard cannot see. The PATH keeps `/usr/bin`, so that
  child can reach curl or git. No current test sources `install.sh` without `TI_SOURCED`.
  This is a real gap in the guard's coverage, but it is a documented trust boundary, not a
  regression.
- **Fix direction:** close both routes the same way, or leave both open. Option A: set
  `TI_SOURCED=1` / `TI_NO_RUN=1` in the test env, and check the bodies of checkout scripts
  with `check_script` when they are run or sourced. Option B: keep D-20 and record the limit
  as a `shortcut:` comment on `_under_checkout_roots`.

### X-02 [HIGH] A retired receipt can authorize a recursive delete of any `~/.local/opt/<N>` or any `~/Applications/*` bundle

- **Location:** `installer/uninstall.py:123-147` (`_placement_shape`), `installer/uninstall.py:167-179`
  (retired branch of `_receipt_proof`), `installer/uninstall.py:463-500` (`_remove_dir`),
  `installer/receipts.py:564-591` (`scan_retired`).
- **Evidence:** for a retired tool, the registry formula is replaced by a placement shape. A
  download `dir` is proven when `path == opt_dir(path.name) and path.name in link_names`.
  `link_names` comes from the receipt's own `link` artifacts in the bin dir, and nothing
  requires that link to resolve inside the opt dir. An `app` `dir` is proven when
  `path.parent == applications_dir()`, with no further coupling. `receipts.matches` proves a
  dir by one recorded key file (`_key_file` + `_file_matches`). `_remove_dir` then runs
  `shutil.rmtree` on the whole captured tree. `scan_retired` turns any well-formed
  `<id>.json` in the receipts dir whose id is not in the catalog into a removable retired tool.
- **Failure scenario:** a receipts file that was edited or planted (the codebase's own threat
  model says the receipt is user-writable JSON and "never the authority on its own",
  `_receipt_proof` docstring, L-19-06, Pitfall 8, review H6) names `~/Applications/Foo.app`,
  with the sha256 of a file the user already has inside it. `--uninstall --yes` (or one
  confirm on the listed preview) then deletes the whole bundle, including files the receipt
  never recorded. The same works for any `~/.local/opt/<N>` together with a matching link
  `~/.local/bin/<N>`. For a catalog tool, the formula limits the dir to that tool's own
  `artifact_paths`. The retired branch widens that authority to every name.
- **Precondition:** a forged or edited receipt, plus an existing matching link for the opt
  case. With `--yes` there is no human check. The TUI and the CLI preview do list the paths.
- **Fix direction:** in the retired branch, require the recorded link to resolve inside
  `opt_dir(N)` (the rule `is_still_proven` already applies), and require each app/opt dir to
  be proven by more than one key file, or list retired dirs as `yourself` (never deleted).
  Only the receipt-only retire would remain automatic.

## Refuted

### X-03 [MEDIUM reported] "The HOME net only watches a fixed list": refuted as a defect

- **Location:** `tests/home_fingerprint.py:13-43`, `tests/conftest.py:169-195`.
- **Fact check:** true. The fingerprint covers six rc dotfiles, `WATCHED_DIRS`, the three
  toolchain dirs and the `*.tools-installer.old` names in the home root. A write to
  `~/.ssh/...` would not be caught.
- **Why refuted:** this is exactly the list SPEC R9 requires (`23.1-SPEC.md:68-69`). It is a
  metadata-only net under the primary protection, which is the per-test `HOME` redirect
  (`conftest.py:247-261`) plus the rerooted `setup.py` constants. A listing of the whole
  home root is deliberately avoided: the home's own mtime moves with every write
  (`home_fingerprint.py:113-120`), and agents run at the same time on this host. At most this
  is a LOW follow-up: also record the names of the top-level home entries.

### X-04 [MEDIUM reported] "The GSD tracer passes when GSD is simply not installed": refuted as framed

- **Location:** `scripts/container-e2e-verify.sh:341-354`, `tests/test_container_e2e_receipts.py:475-516`.
- **Why refuted:** SPEC R11 (`23.1-SPEC.md:73-74`) and D-26 define the tracer as a
  regression check after each pass: no global GSD tree in the tester's home. It passing on a
  catalog with no GSD is the intended result. It fails if anything brings a GSD install back
  (the host test plants `gsd-core` and expects `TRACER_GSD_PRESENT`). The source-level
  "removed install path is gone" proof is a separate check: R1's tests grep `installer/` and
  `setup.py` for `@opengsd/gsd-core` and load the registry.
- **A related real gap, not reported by the lane (found during verification):** at
  `:344`, `if exec_tester "test -e … || test -L …"` treats any non-zero exit as "absent". A
  failed `ct exec` or `su` (container gone, runtime error) prints `TRACER_GSD_ABSENT_OK`.
  This is a narrow chance of a vacuous pass, because the earlier steps in the same pass would
  usually fail first. Fix: run one `exec_tester` that prints `present`/`absent` per path, and
  fail on any other output or a non-zero exit. Rated LOW.
