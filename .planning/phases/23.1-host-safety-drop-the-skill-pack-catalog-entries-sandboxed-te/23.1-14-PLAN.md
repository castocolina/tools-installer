The fixture names stay (`toolchain_allowed_root`, `no_host_toolchain_exec`) so nothing else needs renaming; their docstrings describe the allowlist.
- Orchestrator decision 2 (binding; review R1-06): ANY refused launch fails the test even when production code catches `Exception` around it. Mechanism, chosen because a teardown check cannot be swallowed by code under test: `tests/sandbox.py` holds a process-wide refusal registry (a module-level list; appends are atomic under the GIL, so refusals raised in Textual worker threads are recorded too) with `record_refusal(message: str) -> None`, `take_refusals() -> tuple[str, ...]` (returns and clears), `fail_on_refusals() -> None` (calls `pytest.fail(..., pytrace=False)` naming the count and the first refusal, with the hint `a broad except in the code under test caught a guard refusal; plant a fake under tmp_path instead`, when anything was recorded) and a context manager `refused(match: str)` that requires an `AssertionError` matching `match` inside its block and then removes the refusals it raised from the registry (and fails when none matching was recorded). Every guard (this plan's `GuardedPopen`; 23.1-18's socket and os-launcher guards) calls `record_refusal(str(exc))` and then re-raises the same `AssertionError` (raising stays the first line of defense: nothing starts). The autouse fixture `refusals_fail_the_test` takes the registry before the test (dropping leftovers) and calls `fail_on_refusals()` after the yield, so pytest reports the test as an error at teardown. The pure `check_launch` / `check_script` do not record (the 23.1-04 unit tests call them directly and keep `pytest.raises`); only the wired guards record. Tests that expect a wired refusal use `refused(...)`, never a bare `pytest.raises` (a bare one would leave the entry and fail the test at teardown). Raising a `BaseException` subclass instead was rejected: it breaks the existing `pytest.raises(AssertionError, match=...)` contract and a bare `except:` would still swallow it.
