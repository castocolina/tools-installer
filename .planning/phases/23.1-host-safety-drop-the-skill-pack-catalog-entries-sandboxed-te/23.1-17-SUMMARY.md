## Accomplishments

- A retired receipt appears as a selectable row under the heading `retired — no longer in the catalog`, after the catalog sections and before the environment section; the heading renders for one or more rows and never for none.
- The retired list is re-read through `run_live` on construction, on `enter_view` and on every publish (`state_refreshed`), beside the environment predicates; painting reads only the stored pairs.
- Confirming a retired row removes its proven files and its receipt through `perform_uninstall` / `remove_tool`; the row and heading go on the next publish.
- Every receipt kind has its UI-SPEC detail clause: proven files (`recorded files re-checked before deletion`), leftovers (`remove it yourself: …`), manager packages (`remove it yourself: brew rtk`), and nothing to delete.
- A receipt-only retirement reports `Retired the rtk receipt; brew rtk stays installed — remove it yourself.` or `Retired the rtk receipt; there was nothing to delete.` at ok, through `SweepResult.receipt_retired`.
- A file rewritten after its row was painted is refused and kept by the existing re-proof; no install, update or reinstall wording appears in the section, detail bars or results.

## Deviations from Plan

### Halt: Task 3 stopped before any work (plan/source contradiction)

- **Found during:** Task 3 planning, after Task 2 was committed
- **Issue:** Task 3's test `test_confirm_lists_retired_lines_in_the_existing_blocks` and the truth "ConfirmUninstall adds only lines to the existing blocks" require three blocks, `What is removed`, `What runs` and `remove it yourself`, in the ConfirmUninstall text. The source has none of them. `ConfirmUninstall` (installer/wizard_app.py) shows the summary line, the `runs` lines, the settings and shell-init change lines, `Config deleted too:` / `Config kept`, and co-install warnings. The three block names occur nowhere in the repository (code, planning or docs). Adding them would add new blocks for catalog rows too and would break `test_an_empty_review_reads_as_before` (it pins an empty review). That is not a small faithful change, and the UI-SPEC forbids a new block.
- **Action:** Per the executor's stop rule, Task 3 was halted before any Task 3 test or code was written. Nothing from Task 3 is committed. The remaining Task 3 items are listed under Known gaps.
- **Status effect:** `status: halted`, which the template uses for an intentional stop. HOST-01 is not complete, so `requirements-completed` is empty. REQUIREMENTS.md, STATE.md and ROADMAP.md were not touched.

### Notes on the implemented plan (not Rule 1-3 auto-fixes)

1. `_UninstallEntry.retired_plan` was not added (plan decision). Nothing needs it: `paths`, `argv` and `unregister` hold what the removal reads, and the detail string is built when the row is built.
2. The retired heading key is `#retired — no longer in the catalog` (the title is the section key), not `#retired`. The browser shows the first tuple element as the visible label, and the plan's visible heading text needs the title there.
3. `_nothing_to_uninstall` was not changed (see key-decisions). The truth holds without a code change.
4. The receipt-only count is excluded in `on_removal_finished` by decision (no paths, no argv). The plan's "alone when nothing else was removed" needs this: otherwise the status reads `1 removed` before the sentence.

**Total deviations:** 1 halt (Task 3, plan/source contradiction), 4 implementation notes as listed. **Impact on plan:** HOST-01 is not closed. Tasks 1 and 2 are complete and committed. Task 3 needs a decision on the confirm blocks before it can be resumed.
