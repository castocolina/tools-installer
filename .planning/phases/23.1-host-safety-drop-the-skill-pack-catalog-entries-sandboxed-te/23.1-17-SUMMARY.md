# Phase 23.1 Plan 17: Retired receipts in the Uninstall view Summary

**Retired receipts render as their own Uninstall section with per-kind detail bars, their facts as lines in the existing confirm review, removal through the shared remover, `c` refused with the no-config line, and pinned refresh, order and scroll behavior.**

## Accomplishments

- A retired receipt appears as a selectable row under the heading `retired — no longer in the catalog`, after the catalog sections and before the environment section; the heading renders for one or more rows and never for none.
- The retired list is re-read through `run_live` on construction, on `enter_view` and on every publish (`state_refreshed`), beside the environment predicates; painting reads only the stored pairs.
- Confirming a retired row removes its proven files and its receipt through `perform_uninstall` / `remove_tool`; the row and heading go on the next publish.
- Every receipt kind has its UI-SPEC detail clause: proven files (`recorded files re-checked before deletion`), leftovers (`remove it yourself: …`), manager packages (`remove it yourself: brew rtk`), and nothing to delete.
- A selected retired row shows its facts as lines in the existing confirm review: `rtk: deletes <path>`, `rtk: remove it yourself: <path>`, `rtk: remove it yourself: brew rtk`, or `rtk: nothing to delete; confirming retires the receipt`. No block heading is added and the catalog review is unchanged.
- A receipt-only retirement reports `Retired the rtk receipt; brew rtk stays installed — remove it yourself.` or `Retired the rtk receipt; there was nothing to delete.` at ok, through `SweepResult.receipt_retired`.
- `c` on a retired row is refused with `This row has no config to delete.`
- Retired name and detail text is sanitized; receipt-derived path text with markup and an escape renders literally.
- A file rewritten after its row was painted is refused and kept by the existing re-proof; no install, update or reinstall wording appears in the section, detail bars or results.

## Deviations from Plan

### Dropped requirement: confirm block headings (orchestrator decision)

- **Found during:** Task 3, the plan's confirm test and truth expect three block headings in the ConfirmUninstall text: `What is removed`, `What runs` and `remove it yourself`. The source has none of them, and the names occur nowhere in the repository. The ConfirmUninstall review shows the `runs` lines, the settings and shell-init change lines, `Config deleted too:` / `Config kept`, and co-install warnings. Adding the blocks would add new blocks for catalog rows too and would break `test_an_empty_review_reads_as_before`.
- **Decision (orchestrator):** dropped. The requirement is replaced by retired-specific lines inside the existing review, in the same placement and `<id>: ...` shape as a catalog row's runs line, with no block heading. Pinned by `test_confirm_lists_retired_lines_in_the_existing_structure`. `test_an_empty_review_reads_as_before` is unchanged.
- **Status:** this drop is the recorded resolution. The plan's status is flipped to `complete` on this basis; the dropped requirement is not implemented as written.
- **Halt history:** Task 3 was first halted before any work on this contradiction (after Task 2). The orchestrator's decision resumed it. The halt commit `4d023fb` records the halt; this SUMMARY supersedes its status.

### Implementation notes (not Rule 1-3 auto-fixes)

1. `_UninstallEntry.retired_plan` is present. An earlier note said it was not needed; Task 3 needed the plan for the confirm lines, so the entry now carries it.
2. The retired heading key is `#retired — no longer in the catalog` (the title is the section key), not `#retired`. The browser shows the first tuple element as the visible label, and the plan's visible heading text needs the title there.
3. `_nothing_to_uninstall` was not changed. A retired entry has no group, and `None` is not idle, so the truth holds without a code change.
4. The receipt-only count is excluded in `on_removal_finished` by decision (no paths, no argv). The plan's "alone when nothing else was removed" needs this, otherwise the status reads `1 removed` before the sentence.
5. Retired confirm lines use the detail-bar wording for nothing to delete (`nothing to delete; confirming retires the receipt`), not the post-removal result sentence. The result sentence appears only after removal, as pinned in Task 2.
6. The hostile-id rendering test uses a receipt-derived path segment, not an id. Ids are limited to `TOOL_ID_RE` before they reach the view, so the orchestrator's "hostile id" case cannot occur through the receipts path. The name cell is still sanitized as defense in depth.

**Total deviations:** 1 dropped requirement (orchestrator decision), 6 implementation notes as listed. **Impact on plan:** all three tasks are complete; HOST-01 is closed by this plan's work.
