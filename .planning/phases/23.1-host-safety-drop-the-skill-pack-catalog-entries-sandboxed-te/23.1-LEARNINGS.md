# Phase 23.1 Learnings: Host safety: drop the skill-pack catalog entries, sandboxed tests

## Decisions

### Move host detection first, then delete the pack module whole
`present_harnesses`, `_HARNESS_COMMANDS` and the 17-host `HARNESS_PRESENCE` table moved verbatim into `installer/postinstall.py` (plan 02) before `installer/skill_lifecycle.py` was deleted (plan 15). No re-export shim; every importer was repointed.

**Rationale:** Hook registration needed host detection, not the pack module. A verbatim move keeps `HARNESS_PRESENCE` keys equal to `HARNESS_MARKER_DIRS` ("one denylist governs both"), and the invariant test moved with it.
**Source:** 23.1-CONTEXT.md D-01, 23.1-02-SUMMARY.md

---

### Freeze the removed pack entries as a test fixture until the code that reads them is deleted
Plan 01 removed the eight entries from `registry.toml` but copied the seven pack blocks byte for byte into `tests/retired_skill_packs.toml`. The pack tests read it until plan 15 deleted the code and the fixture together.

**Rationale:** The still-present pack code kept its tests green with no assertion changing meaning, so each plan stayed a valid, green commit. Cycle-1 plan review had flagged that shipped-pack tests in other files would break when the entries went (R1-01).
**Source:** 23.1-01-SUMMARY.md, 23.1-REVIEWS.md (R1-01)

---

### An unknown method kind and a targeted refusal replace pack-specific loader code
`kind = "skill_pack"` now fails through the existing "unknown method kind" error. A leftover `[tool.skill_lifecycle]` table gets one named refusal; other unknown top-level keys keep the lenient reading.

**Rationale:** No special case to maintain, and the user who still has the old table gets the exact key to delete.
**Source:** 23.1-CONTEXT.md D-05, 23.1-15-SUMMARY.md

---

### Retired receipts become synthetic tools on the existing removal path
A receipt whose id left the catalog is a synthetic `Tool` with an explicit retired flag and goes through `removal_plan` / `remove_tool` / `run_uninstall`. Only `_receipt_proof` branches on the flag. Manager-kind receipts (brew, cask, uv-tool, node) run no manager command; the row says "remove it yourself" and confirming retires the receipt.

**Rationale:** Reuses removal order, preview and confirm re-checks and quarantine; avoids a second delete path that could remove unproven files.
**Source:** 23.1-CONTEXT.md D-06, D-08; 23.1-13-SUMMARY.md

---

### Only delete what a placement-shape proof covers; list the rest as "remove it yourself"
A retired path is proven only if it is a direct child of the bin dir, or an `opt_dir(N)` paired with a recorded link named N. Drifted files prove nothing, and a path another readable receipt records is neither proven nor listed.

**Rationale:** A stale receipt must never delete an unrecorded or drifted file or a live tool's files. Listing a live tool's link as "remove it yourself" would tell the user to break it and would block the receipt-only retire.
**Source:** 23.1-CONTEXT.md D-07, 23.1-13-SUMMARY.md (R1-04), 23.1-REVIEW-FIX.md (C-02)

---

### The npx shim is an npx-only translator that refuses everything it cannot translate
`-y/--yes` is dropped, `-p/--package/--package=` become `--package=X` before the command, and every other option (a bare `--` included) exits 127 with one stderr line and runs nothing. Tokens print through `printf` with a fixed format.

**Rationale:** Root cause of HOST-02 was `pnpm dlx` running a package's default bin instead of the named bin. Failing closed beats forwarding unknown options to pnpm.
**Source:** 23.1-CONTEXT.md D-11, D-12; 23.1-03-SUMMARY.md

---

### Drop the interactive `npx` alias; the PATH shim is the only npx layer
`ban_alias_block()` holds no `alias npx=` line, and `rewrite_outdated_ban_aliases` repairs an old block but never adds one.

**Rationale:** A one-line alias cannot reproduce the translator. This was orchestrator decision 1 (R1-19) and amended HOST-02.
**Source:** 23.1-03-SUMMARY.md, 23.1-VERIFICATION.md

---

### Strict, fail-closed shell parser for the test launch guard
`tests/sandbox.py` parses `sh/bash/zsh -c` scripts word by word with `shlex`, is function-aware, and refuses command and process substitution, `eval`/`trap`/`alias` and PATH assignments instead of modelling them. Judged by resolved real path: member, linuxbrew, missing, roots, refuse.

**Rationale:** An allowlist is only meaningful if it refuses what it cannot model. The allowlist was never widened to make a failure pass (SPEC prohibition: fix with a fake under `tmp_path`, never widen or skip).
**Source:** 23.1-04-SUMMARY.md, 23.1-CONTEXT.md D-18, D-23

---

### Replace blanket checkout roots with a reviewed `CHECKOUT_SCRIPTS` table
Instead of allowing every `scripts/*`, `install.sh` and `setup.py` by location (D-20), the table names each reviewable checkout file and the toolchain it may reach (`install.sh`: curl, wget, git, uv; the prune scripts: none). That toolchain must resolve to a fake under the base temp or to nothing.

**Rationale:** Location-based allowance let `setup.py` and the e2e script run from tests, contradicting the rule that `make test` never runs them. Same rule for direct run, shell script argument and `source`.
**Source:** 23.1-REVIEW.md (C-06), 23.1-REVIEW-FIX.md

---

### Keep the strict "any watched change fails the run" real-HOME fingerprint
The user kept D-25 as locked ("anything of GSD should not exist, and tests must be kept from interacting with system folders"). The fingerprint uses only `os.stat`, `os.lstat` and `os.listdir` and never opens a file.

**Rationale:** The risk of false failures from concurrent agent writers was flagged to the user and accepted.
**Source:** 23.1-CONTEXT.md D-24, D-25; 23.1-VERIFICATION.md (human verification resolution)

## Lessons

### Pin tests that derive their cases from the module under test cannot catch an omission
The first coverage test for the fingerprint was parametrized from `WATCHED_DIRS`. Removing `.oh-my-zsh` made its test case vanish (36 items, exit 0) instead of failing.

**Context:** Found by a temporary mutation. Fix: spell the SPEC R9 paths, listings and dotfiles out as literals in the test; the mutant then failed.
**Source:** 23.1-05-SUMMARY.md

---

### A guard that refuses on "nothing can run" must resolve the path the way the launcher does
`check_launch` searched `env.get("PATH", "")`, so a PATH-less `env=` searched nothing and was allowed, while `Popen` fell back to `os.defpath` and ran the host program. Fix: `os.get_exec_path(env)`, with relative entries taken relative to the child's cwd.

**Context:** Found independently by the deep reviewer (CR-01) and ponytail (PT-01); the only BLOCKER in the consolidated review.
**Source:** 23.1-REVIEW.md (C-01), 23.1-REVIEW-FIX.md

---

### Raising from a guard is not enough when production code catches `Exception`
Cycle-1 plan review found that guard refusals are `AssertionError`s that production `except Exception` blocks swallow (`download.py`, `version_status.py`, `session.py`, `engine.py`), so a test could pass after being refused. The plan was changed to record each refusal and fail the test at teardown.

**Context:** Counted HIGH R1-06, applied to plans 14 and 18. A residual remains: a refusal from a leftover thread can fail the wrong test (C-14).
**Source:** 23.1-REVIEWS.md (R1-06), 23.1-REVIEW-FIX.md (C-14)

---

### A guard must cover every route to the same capability, not only the obvious one
Review found gaps after the first implementation: functions collected up front (call before definition), `bash -s <path>` and `--rcfile` hiding a `-c`, shells under another name (`bash5.2`, busybox), Python children with no guard, and five unpatched name resolvers (`gethostbyname` and others).

**Context:** Each was reproduced with a failing test before its fix (C-04, C-05, C-07, C-08).
**Source:** 23.1-REVIEW.md, 23.1-REVIEW-FIX.md

---

### A fail-open "absent" check hides real problems
`assert_gsd_absent` treated any non-zero exec exit as "absent" and checked two paths. It became one in-container probe of four GSD paths that must end with a completion token, with `TRACER_GSD_PROBE_FAILED` otherwise. The older `exec_tester "test -e ..."` leftover checks keep the weak shape (residual R-10).

**Context:** The external reviewer's "passing without GSD is intended" framing was refuted, but the fail-open gap it pointed at was real.
**Source:** 23.1-REVIEW.md (C-10, C-21), 23.1-SECURITY.md (R-10)

---

### Line-number-keyed tables break when a script grows
Adding `assert_gsd_absent` (17 lines) moved two classified `export PATH` hits in `tests/test_shell_scripts_path.py` from lines 346/548 to 363/566, failing the suite until the keys were updated. The plan's file list did not name that file.

**Context:** Surfaced by the first full `make test` after the change; the table's designed update path was used, no check relaxed.
**Source:** 23.1-06-SUMMARY.md

---

### Deleting code ripples into tests outside the plan's file list
Plans 07, 08, 12 and 15 each had to delete or retarget tests the plan did not enumerate (engine pack-handoff test, six UI skill-probe tests, `test_app.py` monkeypatch of a removed method, `tests/test_session.py`, `tests/test_version_status.py`). Plan 15 recorded a coordinator decision to widen scope.

**Context:** Cycle-1 review had already flagged the same pattern for plans 01/02 and 12 (R1-01, R1-05). Plans should grep for readers of what they delete, tests included.
**Source:** 23.1-07-SUMMARY.md, 23.1-08-SUMMARY.md, 23.1-12-SUMMARY.md, 23.1-15-SUMMARY.md, 23.1-REVIEWS.md

---

### A plan's own text can contradict the source, so verify named artifacts before building
Plan 17 required three confirm-block headings (`What is removed`, `What runs`, `remove it yourself`) that appear nowhere in the repo; adding them would also change catalog rows and break an existing test. The orchestrator dropped the requirement and replaced it with retired-specific lines inside the existing review. A related mismatch (quoted vs unquoted `{opt}`) existed between UI-SPEC and the plan.

**Context:** Task 3 halted before any work until the orchestrator decided.
**Source:** 23.1-17-SUMMARY.md, 23.1-03-SUMMARY.md

---

### Parallel worktree executors hit the same tooling limits and missed process artifacts
Executors repeatedly had compound shell commands refused by the worktree guard, could not write the plan-head ledger and spawn sentinel under the shared `.git`, and used a scratchpad ledger or measured commit counts directly. Plan 01 committed with a stale message file and had to amend. Plan 10 did not produce the RED classifier record.

**Context:** Workarounds were plain commands and scratchpad scripts; no gate was relaxed.
**Source:** 23.1-01-SUMMARY.md, 23.1-05-SUMMARY.md, 23.1-07-SUMMARY.md, 23.1-10-SUMMARY.md, 23.1-15-SUMMARY.md

## Patterns

### Verbatim move with an invariant test that moves with it
Move a table or function without editing it, keep the expected dict in the moved test, and pin the moved data to the denylist it must equal.

**When to use:** Splitting an owner module (here, host detection out of the pack module) when a hidden coupling must survive the move.
**Source:** 23.1-02-SUMMARY.md

---

### Frozen test fixture for data deleted from the shipped registry
Copy the removed blocks byte-identically into a temporary test fixture, verify with `cmp`, and delete fixture and reader together later.

**When to use:** Staged removal of shipped data whose consumer code is removed in a later plan.
**Source:** 23.1-01-SUMMARY.md

---

### Remove consumers first, producers later
Plan 08 removed every UI reader of skill-pack state and kept the producers (`refresh_skills`, pack state) until plan 12; plan 07 did the same for the engine.

**When to use:** Deleting a feature across layers so each commit stays green and reviewable.
**Source:** 23.1-07-SUMMARY.md, 23.1-08-SUMMARY.md

---

### Fixed-format message with the untrusted token as a `%s` argument
Shim messages live in module constants and print the token through `printf '%s'`, so hostile tokens print literally. On the Python side, receipt-derived text goes through `sanitize_log_line` with `markup=False, soft_wrap=True`.

**When to use:** Any output that includes a receipt, path or option token the program did not author.
**Source:** 23.1-03-SUMMARY.md, 23.1-REVIEW-FIX.md (C-12)

---

### Identity-bound snapshot before replacing a file
`rewrite_outdated_npx` uses its own `lstat` and `S_ISREG`, an `O_NOFOLLOW` read, requires the sentinel and an `exec` target, and re-checks the snapshot right before the atomic replace. A hand-edited target survives because pnpm is never re-resolved.

**When to use:** Launch-time rewrites of files the user's tools also write.
**Source:** 23.1-09-SUMMARY.md, 23.1-REVIEW-FIX.md (C-15)

---

### One launch-repair composition for every route
`_launch_repairs()` returns the legacy strip plus the shim and alias rewrites, and every route calls it once through `_print_repairs`. Uninstall and unguard routes keep the repair but print only its warnings (C-13).

**When to use:** Repairs that must happen regardless of which entry point the user launches.
**Source:** 23.1-09-SUMMARY.md, 23.1-REVIEW-FIX.md

---

### Mutation check and RED-before-fix for guards and review fixes
Where a regression guard passed at first run, a temporary mutation (remove a watched entry, remove the `CONTAINER_TOOL` guard) showed it fails. Every CONFIRMED review finding had a failing test written before its fix, and each fix was its own commit with `make validate` and `make test` green.

**When to use:** Tests that pin a guard or tripwire, and review-fix rounds.
**Source:** 23.1-05-SUMMARY.md, 23.1-06-SUMMARY.md, 23.1-REVIEW-FIX.md

## Surprises

### The plan-review cycles converged but the code review still found one BLOCKER and many guard holes
Three plan-review cycles went from 5 current HIGH to 0 (cycle 1: 5, cycle 2: 0, cycle 3: 0 with 2 actionable). The consolidated code review of the implementation still reported 22 rows: 18 confirmed, including BLOCKER C-01 and several HIGH or WARNING guard bypasses.

**Impact:** 15 rows were fixed in 15 commits; 7 were residual, refuted or by design. Plan review does not substitute for review of the built guard.
**Source:** 23.1-REVIEWS.md, 23.1-REVIEW.md, 23.1-REVIEW-FIX.md

---

### The default plan reviewer lane was down for every cycle
`opencode-referee-one` failed its probe ("Combo has no executable targets") in all three cycles, so review failed over to referee-two (and referee-three in cycle 1). Referee-three's two halves hit the 60-minute timeout with no output and were recovered by resuming their sessions.

**Impact:** Single-reviewer HIGHs had to be adjudicated against source; five of the HIGHs raised in cycle 1 were refuted.
**Source:** 23.1-REVIEWS.md

---

### Three of plan 10's four RED failures were missing-symbol errors and the zsh link code could not wait for Task 2
`pytest_configure` could not strip PATH without the interpreter link dir, because this host's only zsh lives under linuxbrew and Task 1 alone would have skipped every zsh test. The link machinery landed in Task 1 and Task 2's tests passed at first run as regression guards.

**Impact:** The plan's TDD ordering for Task 2 could not be honoured.
**Source:** 23.1-10-SUMMARY.md

---

### The widened fingerprint failed once in a full run with no recorded path
Plan 05's first `make test` reported `1 error` from `real_home_untouched`; the captured output did not list the changed entry, and a rerun was clean. A parallel agent worktree was running `make test` at the time.

**Impact:** Cause likely a concurrent writer but not proven; the rule was not relaxed. This is the false-positive risk D-25 accepted.
**Source:** 23.1-05-SUMMARY.md

---

### The 23.1 npx rewrite design was later superseded
The 2026-11-14 amendment to CONTEXT (phase 24.4 D-04) keeps the `_launch_repairs()` composition but says its guard part now removes installer-written shims and the ban block instead of rewriting them. D-11 through D-14 are superseded by the guard's retirement.

**Impact:** Much of the shim translator and rewrite work (plans 03 and 09, which implement D-11 to D-14) is superseded by the guard's retirement.
**Source:** 23.1-CONTEXT.md (amendment note at D-15)

---

### The container e2e exposed a pre-existing fnm line in the tester's `.bashrc`
During the e2e rerun every new bash printed `fnm: command not found`. fnm's installer appends an `eval "$(fnm env ...)"` line that `rcclean` does not remove (it removes only plain `export PATH=` lines), so it runs before the managed PATH block.

**Impact:** Not a 23.1 gap; handed to Phase 23.2.
**Source:** 23.1-VERIFICATION.md (Human verification resolution)
