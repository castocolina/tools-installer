Output: `Tool.retired`, `receipts.RetiredScan` and `receipts.scan_retired`.
</objective>

Decisions for this plan:
- D-06: `Tool.retired: bool = False` is a new dataclass field and an `__init__` keyword (default False); nothing in the registry loader sets it.
- D-10 / Claude's discretion (names): `@dataclass(frozen=True) class RetiredScan` with `tools: tuple[Tool, ...] = ()` and `warnings: tuple[str, ...] = ()`; `scan_retired(catalog_ids: Collection[str]) -> RetiredScan` in receipts.py:
  - `os.listdir(receipts_dir())`: `FileNotFoundError` / `NotADirectoryError` gives an empty scan; any other `OSError` gives one warning `Could not read the receipts folder {path}: {exc.strerror or first line of str(exc)}.` and no tools.
  - For each name in sorted order: only `*.json`; the stem must fully match `TOOL_ID_RE` and not be in `catalog_ids`; `read(stem)` None while the file still exists (`os.path.lexists`) gives the corrupt warning `Ignored the corrupt receipt {path}: it is kept; remove it yourself if it is stale.`; None after the file vanished is skipped silently; otherwise `Tool(id=stem, name=stem, category="retired", cmd=stem, methods=(), retired=True)`.
  - `{path}` is `sanitize_log_line(locations.display_path(path))`. Nothing is ever deleted or written here.
- The retired tool carries no receipt data: removal re-reads the receipt (23.1-13), so a receipt edited after the scan is judged as it is at removal time.
- Wave 1, no dependency (23.1 reviews round 1): this plan used to wait for 23.1-02 only because both edited `installer/model.py`; 23.1-02 no longer touches `model.py` (its comment edit moved to 23.1-15) and moved to wave 2 behind 23.1-01 (review R1-01), so this plan runs in wave 1, file-disjoint from the other wave-1 plans. `test_registry_tools_are_not_retired` reads the shipped registry, which 23.1-01 edits in parallel; it asserts only `retired is False`, which holds before and after the drop.
