## What this change does

It removes the eight catalog entries (rtk and seven skill packs) and the whole skill-pack machinery. It
turns the `npx` redirect shim into a translator that refuses unknown options, and it repairs an old shim
or an old guard alias block at every launch. A receipt whose tool left the catalog shows up as a
"retired" row that can only be removed. In tests, it adds a subprocess allowlist, a cleaned-up PATH and
environment, a block on internet sockets, and a wider check that the real HOME was not touched.

Checked and found sound: the npx translator (probed under `sh` and `bash`: `-y -p pkg bin`, repeated
`--package`, `-p` after the command, `--`, `-yp`, an empty `--package`, and arguments with spaces, `$` or
`*`), the repair being atomic and keeping symlinks, the retired-row shape proof, the fingerprint never
opening a file, the socket guard, and the parser for `sh -c` scripts.

## Must fix

### PT-01 — The test launch guard lets a host program run when `env=` has no PATH
- **Severity:** Medium (a hole in the phase's main promise, R6; no test uses it today)
- **Where:** `tests/sandbox.py:471`
- **What this is:** `check_launch` looks up a bare program name with
  `shutil.which(program, path=env.get("PATH", ""))`. When the lookup finds nothing, the guard counts the
  launch as "nothing can run" and lets it through (`missing_ok`).
- **Problem:** When `env` is given without a `PATH` key, `which(..., path="")` returns None, so the guard
  allows the launch. `Popen` does not use an empty path, though. It falls back to `os.defpath`
  (`/bin:/usr/bin`) and runs the real program. Verified with a pure probe:
  `check_launch(["curl", "-V"], env={}, ...)` and `env={"HOME": "/x"}` are both ALLOWED, and
  `os.get_exec_path(env)` resolves `/bin/curl`. So `subprocess.run(["uv", "tool", "install", x], env={"HOME": tmp})`
  in a test would run the host's uv.
- **Fix:** Resolve with the same search path `Popen` uses:
  `found = shutil.which(program, path=os.pathsep.join(os.get_exec_path(env)))`. This one line covers
  `env=None` (reads `os.environ`) and a missing PATH (uses `os.defpath`). Add one case to
  `tests/test_sandbox.py`: `["curl", "-V"]` with `env={}` must raise.
- **If we skip it:** A future test that passes a minimal env runs real toolchains on the developer's
  machine, which is the exact accident this phase exists to prevent.

## Should fix

### PT-02 — A retired receipt that cannot be removed still triggers the full teardown
- **Severity:** Medium
- **Where:** `installer/app.py:924-967` (the `retired` list and the "nothing to uninstall" check),
  `installer/app.py:1001`
- **What this is:** `run_uninstall` adds every retired row to the "is there anything to uninstall?" check.
  That includes rows whose plan is `level == "none"` and that only list files under "remove it yourself"
  (a recorded file the user edited).
- **Problem:** Suppose the only footprint is such a drifted retired receipt. The user still gets the
  "Remove these artifacts?" prompt, and confirming runs the whole sweep: `remove_managed_block` on
  `~/.myshellrc`, `remove_shims` and `remove_ban_aliases`. Nothing in the preview names any of these.
  Verified with a probe (throwaway HOME, one edited `rtk` file plus a PATH block): the prompt is asked,
  the PATH block is gone afterwards, and the receipt and the file are kept. A drifted *catalog* tool in
  the same situation gets "nothing to uninstall" and no prompt.
- **Fix:** Count only rows that can act: change the check to
  `and not any(plan.level != "none" for _tool, plan in retired)`. In the nothing-to-uninstall branch,
  also call `_print_retired_preview(retired, console)` so the user still sees the "remove it yourself"
  lines. Add a test: drifted retired receipt only, so no confirm, and the PATH block is kept.
- **If we skip it:** A user who runs `--uninstall --yes` on a machine with only a stale rtk receipt loses
  their PATH wiring without being told.

### PT-04 — The e2e "no GSD tree" check passes when the container command itself fails
- **Severity:** Low
- **Where:** `scripts/container-e2e-verify.sh:344`
- **What this is:** `assert_gsd_absent` runs `exec_tester "test -e … || test -L …"` and reads a non-zero
  exit as "absent".
- **Problem:** A failed `podman exec` or `su` also exits non-zero (125, 126, or 1 for a dead container
  or a broken login shell). The check then prints `TRACER_GSD_ABSENT_OK`, so a safety assertion passes
  without testing anything. (The older `:313` and `:719` checks share this shape.)
- **Fix:** Check absence inside the container, so that only a clean exit 0 counts as absent:
  `if ! exec_tester "test ! -e \$HOME/${rel} && test ! -L \$HOME/${rel}"; then … TRACER_GSD_PRESENT …`.
  The host-side test `tests/test_container_e2e_receipts.py` needs one more case: a failing `exec_tester`
  stub must fail the assert.
- **If we skip it:** In a broken container run, the tracer claims GSD is absent when nothing was checked.

### PT-06 — One retired plan reads the same receipt up to five times
- **Severity:** Low (lean, speed)
- **Where:** `installer/uninstall.py:217-233, 414-420`, `installer/app.py:797`
- **What this is:** For a retired tool, `removal_plan` reads the receipt in `receipt_exists`,
  `_receipt_proof`, `_retired_leftovers`, `removal_plan` itself and `retired_manager_package`.
  `remove_tool` then reads it once more to build its sentence.
- **Problem:** This is harmless at the expected load, but it is extra code. The sentence data is already
  in `fresh.hint`, or in the `receipt` that `removal_plan` holds.
- **Fix:** Have `retired_manager_package` and `_retired_leftovers` take the `Receipt` that is already in
  hand. In `remove_tool`, read `managed` once before `receipts.delete`, or build the sentence from
  `fresh.hint`. About −5 lines.
- **If we skip it:** Nothing breaks.
