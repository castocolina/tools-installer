<design_decisions>
**One `TweakBundle` for both `cursor-agent` and `cursor`, id `cursor-agent-model` (distinct
from the catalog tool id `cursor-agent`).** Resolves 10-RESEARCH.md's Open Question 1: a
single bundle whose body defines both functions guarantees they are always co-installed —
independently toggleable halves (Assumption A3's failure mode) could let a user enable
`cursor-agent`'s injection while `cursor` stays on stock behavior, or vice versa, which
REQUIREMENTS.md treats as one requirement (REQ-cursor-agent-default-model-wrapper). `cursor()`
purely delegates to `cursor-agent "$@"` rather than re-implementing its own `"$@"` scan, per
10-RESEARCH.md's own recommendation.

**`opencode-auto`'s label is `"opencode auto-approve"`, never `"...skip-permissions"`.**
`claude-skip`/`codex-skip` both use "skip-permissions" because that is literally what they do;
reusing that wording for `opencode-auto` would misrepresent it as a full bypass before a user
even opens the detail panel, undermining REQ-opencode-auto-tweak's honesty requirement at the
label level, not only in the expanded copy.

**The 1M-context re-verification finding (CONTEXT D-01) is recorded as a Python-level dated
comment above `_CURSOR_DEFAULT_MODEL` in `installer/tweaks.py`, not inside the shell body
text.** A shell comment would be duplicated verbatim into every enabling user's own
`~/.myshellrc` for no functional benefit; a source comment is where a future maintainer
reading this bundle's definition will actually find it, mirroring how `installer/registry.toml`
records its own "Verified {date}: ..." findings next to the entry they justify.

**Bundle placement in the `BUNDLES` tuple:** `codex-skip` is inserted directly after
`claude-skip` (grouping the two full-bypass "-skip" tweaks together for a reader scanning the
file top-to-bottom); `opencode-auto` and `cursor-agent-model` are appended after the existing
final entry (`apt-upgrade`), since neither is a natural neighbor of the Linux-only
`apt-upgrade` bundle. This changes `BUNDLES`' declared order, so the existing order-sensitive
`test_four_bundles_with_stable_ids` is renamed ONCE, in Task 1, to the count-agnostic
`test_bundles_have_stable_ids_and_order` (corrected during cross-AI review cycle 1 — see the
numbered list below: the original draft of this decision deferred the rename AND the
assertion update to Task 3, which meant Tasks 1 and 2 could not pass their own stated test
gates on their own commits). Each task then updates only the list literal to its own running
total (5 in Task 1, 6 in Task 2, 7 in Task 3) in the same commit that appends its bundle.

**Copy for `cursor-agent-model` says "requests", never "guarantees"/"verifies", the model's
context.** Per 10-RESEARCH.md's Pitfall 4/Assumption A2: the changelog fix is real and
official (MEDIUM confidence) but was not independently re-proven by spending a live API call
in this research session. The Policies detail panel must not overstate what this installer
can actually confirm.

**Cross-AI review cycle 1 (10-REVIEWS.md, codex/gpt-5.6-sol) findings and their resolutions,
all re-grounded against the current source tree before being applied:**

1. **Bundle-count/order test updated in the SAME task that appends the bundle, not deferred.**
   `tests/test_tweaks.py`'s `test_four_bundles_with_stable_ids` (line 30) asserts the exact
   4-entry list; the original plan deferred updating it to Task 3, so Tasks 1 and 2's own
   stated gate (`uv run pytest tests/test_tweaks.py ... -q`, `make validate && make test`)
   could not pass on their own commits. Fixed by renaming the test ONCE, in Task 1, to a
   count-agnostic `test_bundles_have_stable_ids_and_order`, then having each task update only
   the list literal to that task's own final count (5 in Task 1, 6 in Task 2, 7 in Task 3) —
   never a second rename.

2. **Split PATH link mode: pre-existing `TweakBundle`/`tweak_policy` limitation, confirmed
   NOT a regression Phase 10 introduces, documented rather than silently shipped.**
   Re-read `setup.py` (`_build_app`, lines 216-224) and `installer/app.py`
   (`configure_path`, the `link_mode == "split"` branch) directly: every `tweak_policy(...)`
   call in `_build_app` is unconditionally constructed with `rc_path=_MYSHELLRC`, for EVERY
   bundle `applicable_bundles(platform)` returns, regardless of `link_mode`. `configure_path`'s
   split branch (`installer/app.py`) writes the managed PATH block straight into each rc file
   and explicitly never creates or sources `~/.myshellrc` — pinned by the existing
   `tests/test_app.py::test_configure_path_split_inlines_block_and_skips_myshellrc`
   (`assert not myshellrc.exists()`). This means `claude-skip` — already shipped, untouched by
   this phase — goes through the EXACT SAME `rc_path=_MYSHELLRC` call site and is EQUALLY inert
   under split mode today. Grepping `tests/test_policy_tweaks.py` and `tests/test_tweaks.py`
   for `split` returns zero hits: no existing test claims otherwise. This is therefore a
   pre-existing gap in the whole bundle mechanism (also affects `docker`/`countdown`/
   `apt-upgrade`), not something the three new tweaks introduce, and REQ-agent-tweak-
   self-update-durability's actual text (REQUIREMENTS.md) only speaks to the alias/function-vs-
   file-shim distinction — it says nothing about link-mode wiring. Rewiring `tweak_policy`'s
   `rc_path` to be link-mode-aware (mirroring `ban_policy`'s own already-correct
   `ban_rc_paths(link_mode, shell)` precedent) is real, valuable work, but it is a fix to
   pre-existing, cross-cutting infrastructure that every bundle shares — out of scope for a
   phase whose four REQs are about three specific new tweaks, and it should be filed as its own
   follow-up rather than folded silently into this plan. What Task 1 DOES add, cheaply and in
   scope, is honesty: a one-line caveat in `_policy_detail`'s shared preamble, shown for every
   `tweak:*` Policy id (old and new alike), stating plainly that the tweak only takes effect
   once `~/.myshellrc` is sourced and naming split mode as the case where it is not. This
   requires no link-mode plumbing (the sentence is true regardless of which mode is actually
   active) and is pinned by a new test asserting the caveat appears for both `tweak:claude-skip`
   and `tweak:codex-skip` — proof the fix is uniform, not new-tweaks-only.

3. **`cursor()`/`cursor-agent()` contradiction resolved: only `cursor-agent()`'s OWN calls to
   the real binary need `command`; `cursor()`'s one delegation to the `cursor-agent` FUNCTION
   must stay bare.** The prior action text required "both functions" to always call through
   `command`, then separately required `cursor()` to "simply delegate to `cursor-agent \"$@\"\"`
   — a bare call — which its own proposed regression test then rejected. The corrected
   invariant (verified against 10-RESEARCH.md Pattern 2 and Pitfall 3 directly): self-recursion
   can only happen when a function calls its OWN name bare, so `cursor-agent()`'s two internal
   calls to the vendor binary must use `command cursor-agent "$@"` (bypassing its own function
   definition), while `cursor()` calling bare `cursor-agent "$@"` reaches a DIFFERENT function
   name — not itself — which is exactly how `cursor` inherits `cursor-agent`'s argv-scan/
   injection logic. If `cursor()` used `command cursor-agent "$@"` instead, `command` forces
   PATH-only resolution, so it would call the real binary directly and SKIP the injection
   entirely — breaking the plan's own required behavior that bare `cursor chat hello` gets
   `--model gpt-5.6-sol-high` injected. Task 3's action and its structural regression test are
   rewritten to state and check this exact, corrected invariant.

4. **Reload hint corrected for alias/function tweaks; `hash -r` reserved for the ban's PATH
   shims.** Re-read `installer/policy.py` directly: `_RELOAD_HINT` (line 35, "Open a new shell
   or run `hash -r`...") is shared verbatim by `ban_policy` (legitimately — it writes PATH
   shims, and `hash -r` really does refresh bash's PATH lookup cache for those) and by
   `tweak_policy` (incorrectly — `hash -r` does nothing for a freshly written alias or shell
   function; only opening a new shell or re-sourcing the rc file loads it). Task 1 adds a
   second, tweak-specific constant used only by `tweak_policy`'s `_apply`/`_remove`, and updates
   the one existing test that hardcoded the old, wrong expectation
   (`tests/test_policy_tweaks.py::test_apply_writes_block_and_returns_result`, line 70). This
   fixes the hint for `docker`/`countdown`/`claude-skip`/`apt-upgrade` too, for free, since
   `tweak_policy` is one shared function — not a new-tweaks-only patch.

5. **Fresh-shell tests extended to cover a pre-existing conflicting alias and zsh execution
   (not just bash syntax).** The originally proposed `_run_cursor_agent` subprocess helper only
   ever sources the tweak block into a clean bash process with no prior aliases, and the only
   existing zsh coverage (`test_blocks_parse_in_bash_and_zsh_when_present`) is a `-n` syntax
   check, never an execution. In bash/zsh, alias expansion is textual and happens at parse time,
   before function-name dispatch — so a user with a pre-existing `alias cursor-agent=...` (or
   `alias cursor=...`) defined earlier in their own shell config would have that alias silently
   win over this tweak's function on every invocation, and neither the original test suite nor
   the plan's proposed new tests would ever catch or document that. Task 3 adds one test that
   defines such a conflicting alias (with `shopt -s expand_aliases` set, since bash disables
   alias expansion by default in non-interactive scripts — the property under test would not
   even reproduce without it) before sourcing the tweak block, asserts the actual resulting
   behavior, and a matching Policies detail-panel caveat naming the limitation. It also adds a
   zsh execution variant (not just `-n` syntax) of the core injection/override/delegation cases,
   skipped gracefully when zsh is unavailable on the machine, mirroring
   `test_blocks_parse_in_bash_and_zsh_when_present`'s own skip pattern.
</design_decisions>
