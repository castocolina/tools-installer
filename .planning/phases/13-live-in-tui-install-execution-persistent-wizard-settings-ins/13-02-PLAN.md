<objective>
Build the two pure-core capabilities the in-TUI execution screen needs, with no Textual code
involved, so both are fully unit-testable before any screen exists.

Today every Runner in `installer/run.py` (`run_command`, `run_captured`, `run_output`,
`run_query`) blocks on `subprocess.run(...)` and returns only after the child exits, so none of
them can feed a live log widget while a `curl | sh` or a `pnpm add -g` is still running. D-03
requires execution to run live inside a log widget, not be summarised after the fact. This plan
adds `StreamingRunner`, a `subprocess.Popen`-based Runner that hands each line to a callback as it
arrives and attributes it to the tool currently installing (D-05.2 — the abandoned branch's
attribution vanished whenever its optional `captured_runner` was `None`, `session.py:182` there;
see D-04, reference only, never ported).

It also adds DD-1's weak cancellation to `installer/session.py::run_installs`: an optional
`should_continue` predicate checked between tools, so a batch can stop queuing new work without
this phase taking on `subprocess.terminate()` lifecycle management.

Purpose: get the risky I/O primitive right, in isolation, against a fake child process.
Output: `StreamingRunner`, `STREAM_DETAIL_LINES`, `run_installs(..., should_continue=...)`, and
their tests.
</objective>

## Design decisions this plan implements

- **DD-1 (failure handling / cancel)** — the batch continues past a failed tool and reports a
  per-tool status list; cancellation is weak (stop queuing, let the in-flight tool finish). This
  plan supplies the `should_continue` half; the keybind and the "not attempted" rendering are
  plan 13-05.
- **D-05.2 (unconditional attribution)** — enforced structurally: `StreamingRunner`'s `emit`
  callback is a REQUIRED constructor argument with no default and no `None` branch, and
  `__call__`/`method_started` raise `RuntimeError` when no tool has been set. There is no
  "plain runner" fallback path for the interactive TUI to accidentally take.

## Wave-1 dead-code standing (cycle-1 HIGH finding, corrected and answered)

Cycle 1 raised a HIGH concern that this plan's Wave-1 commit cannot pass `make validate`, because
`StreamingRunner` and `STREAM_DETAIL_LINES` have no production caller until plan 13-04 in Wave 2
while `[tool.vulture] paths = ["installer"]` scans `installer/` and vulture never looks at tests.
The direction of the concern is right and the mechanism named is wrong; both halves matter, so both
are written down here rather than silently acted on.

**The vulture half is measured, not assumed, and it does not fire.** `pyproject.toml`'s vulture
block is three lines, and the concern quoted the first two: `paths = ["installer"]` AND
`min_confidence = 80`. Vulture scores an unused class, function, method, attribute or module-level
constant at 60% confidence and an unused *import* at 90%. At a floor of 80 the 60%-confidence
findings are below threshold and are never reported, so a new-but-uncalled `class StreamingRunner`
and `STREAM_DETAIL_LINES` do not trip `uv run vulture`. This was verified against this exact tree by
dropping a throwaway `installer/` module holding an unused constant, class, method and attribute:
`uv run vulture` exited 0, and the same probe re-run with `--min-confidence 60` reported all five
symbols. What WOULD fail the Wave-1 gate is an unused *import* in either edited file (ruff `F401` at
90% and vulture at 90%), which is a real defect rather than a sequencing artifact. Task 1's
acceptance criteria therefore assert `uv run vulture` exits 0 on this plan's own tree — the property
the concern asked for, proven rather than presumed.

**Neither remedy the concern proposed may be used.** A `[tool.vulture] ignore_names` /
allowlist entry and a lowered `min_confidence` are both gate-silencing, which `CLAUDE.md` forbids
outright ("Never bypass a quality gate. Fix the root cause; never silence a check to make it
pass."). If `uv run vulture` or `ruff` ever does flag a symbol this plan adds, the only permitted
fixes are to delete the symbol or to move it into the plan that first calls it (13-04) — never to
widen an ignore list.

**The half of the concern that is real is `.claude/architecture.md` rule 5, not vulture.** Rule 5
says a shared helper with zero production callers is deleted or adopted, never kept "for later",
and plan 13-01's objective cites exactly that rule as its reason for creating no production symbol.
This plan does create two, and their first production caller lands one wave later. That is accepted
deliberately: rule 5 targets a helper kept for later *indefinitely*, and here the adopting plan,
task and call site are named in advance (13-04 Task 1 builds the `StreamingRunner` inside the
execute worker; 13-05 Task 2 binds the cancel key to `should_continue`). The inversion the rule
would otherwise force — building the execute screen before the runner it streams through — is a
worse order and would put the phase's riskiest I/O primitive behind a Textual screen instead of in
front of it. Because "named in advance" is a promise rather than a proof, plan 13-07 Task 2 now
carries a phase-close gate asserting that every symbol this plan and plan 13-03 introduce has a real
production caller by the end of the phase. Rule 5 is enforced at the phase boundary, not waived.

Add `STREAM_DETAIL_LINES = 20` and `class StreamingRunner` to `installer/run.py`, below
`run_captured` and above `QUERY_TIMEOUT`, with a docstring that says what it is for (feeding a live
log widget while the child runs) and why it exists beside `run_captured` rather than replacing it

Constructor takes `emit: Callable[[str, str], None]` positionally and stores it plus
`self._tool_id: str | None = None`. `set_tool(tool_id: str) -> None` assigns it. A private
`_current()` returns the id or raises `RuntimeError("StreamingRunner.set_tool must be called
before running a command")` — this is the structural guarantee behind D-05.2: there is no
attribution-free branch to fall into, unlike the abandoned branch's `captured_runner=None` (D-04,
audit finding B).

`method_started(method: str) -> None` emits a single header line reading `-- trying {method} --`,
so `installer/engine.py`'s existing ladder dispatch produces per-method section headers with zero
engine change.

`__call__(cmd: list[str]) -> None` launches `subprocess.Popen` with `stdin=subprocess.DEVNULL`,
`stdout=subprocess.PIPE`, `stderr=subprocess.STDOUT`, `text=True`, `bufsize=1`. Per 13-RESEARCH.md
Pitfall 3, all three of those are load-bearing: DEVNULL because a script that reads stdin would
otherwise wedge a worker thread with no recoverable input path while Textual holds the terminal in
raw mode; STDOUT-merged because it gives one ordered stream and makes line ordering trivially
correct; and the read loop must run in the same thread that owns the `Popen` object, never handing
it across threads. Iterate `proc.stdout` line by line, `rstrip` the trailing newline only, emit
each line, and keep the tail in a `collections.deque(maxlen=STREAM_DETAIL_LINES)` so a verbose
installer cannot grow an unbounded buffer just to build an error message. After the loop, `wait()`
for the return code and raise `CommandError(cmd, returncode, detail="\n".join(tail))` on a non-zero
code, mirroring `run_output`'s existing detail-carrying shape so `run_live` keeps catching it
unmodified. This `wait()` and the one in the `finally` below are not a conflict: on the normal path
the stream is already at EOF and the child already reaped, so both the drain and the second `wait()`
return immediately with the same code — the `finally` exists for the paths that never reach here. Wrap the
`Popen` construction in `except OSError` raising `CommandError(cmd, 127)`, exactly like
`run_command` and `run_output` already do. Deliberately set no timeout — the `run_output` docstring
already records why a side-effecting install child must be allowed to take minutes.

Put the read loop inside a `try` whose `finally` DRAINS the child's pipe and only then reaps it, in
that order: read whatever remains in `proc.stdout` through to EOF and discard it (never re-entering
`emit`), close the stream, then `proc.wait()`. Guard the drain for `proc.stdout` being `None` and
wrap it in its own `except OSError: pass`, so a failure there can never replace an exception already
propagating out of the `try`.

The ordering is the entire point, and waiting without draining is a deadlock rather than a fix. The
path that matters is `emit` raising: `emit` is caller-supplied and, in plan 13-04, posts a Textual
message, so an exception there leaves the loop early with a live child nobody is reading from. An OS
pipe holds roughly 64 KiB; once it fills, the child blocks inside its own `write()`, never exits, and
a bare `wait()` never returns. That would hang plan 13-04's worker thread before its `try/finally`
could post `InstallRunFinished`, leaving the UI stuck on "Installing..." with no completion and no
error — exactly the mode 13-04's threat T-13-07 exists to prevent. The drain is load-bearing, not
tidying.

Drain all the way to EOF; do NOT bound the drain and close the pipe early underneath a still-running
child. Closing a pipe under a writing child hands it EPIPE (and, unhandled, SIGPIPE), which is
killing it by another name, and DD-1 deliberately keeps child termination out of this phase.
Draining to EOF costs exactly the time the child was already going to take, which is the same
"no timeout for a side-effecting install" posture the `run_output` docstring already justifies.
Record in a comment that this `finally` only reads and waits — it never signals the child and never
closes the pipe out from under it — and phrase that comment without writing the attribute-call
spellings of the termination verbs, because the acceptance gate greps this file's own code for them.

Also record, in the `__call__` docstring, the limit of what `bufsize=1` buys. It line-buffers the
PARENT's reads; it cannot make a child line-buffer its own writes. A vendor installer that detects a
non-TTY — `pnpm`, SDKMAN, and most progress-bar-drawing scripts do — will block-buffer and burst its
output at exit no matter what this runner does, so the streaming guarantee is honestly "as live as
the child allows", not "always line-by-line". D-03's requirement is that this module never be the
thing that batches output; making a hostile child stream is out of reach for any Runner and is not
promised here.

Extend `tests/test_run.py` with the cases in `<behavior>`. Follow the file's existing convention:
drive real children with `sys.executable -c "..."` for the streaming/ordering/exit-code cases
rather than mocking `subprocess.Popen`, because the property under test is genuine incremental
reads from a real pipe, and reserve `monkeypatch` for the missing-binary case. The incremental-
delivery case is the one place that convention is not enough: launch it as
`[sys.executable, "-u", "-c", ...]` and have the script `print(..., flush=True)`, so the child is
genuinely unbuffered and the measured timestamp gap proves live delivery instead of proving nothing.

`test_streaming_runner_reaps_child_when_emit_raises` is the second exception to the file's plain

is plenty on Linux's 64 KiB default) — a small child fits entirely in the buffer, exits on its own,
and would let a drain-less `finally` pass while proving nothing.
