<objective>
Build the two pure-core capabilities the in-TUI execution screen needs, with no Textual code
involved, so both are fully unit-testable before any screen exists.

Today every Runner in `installer/run.py` (`run_command`, `run_captured`, `run_output`,
`run_query`) blocks on `subprocess.run(...)` and returns only after the child exits, so none of
them can feed a live log widget while a `curl | sh` or a `pnpm add -g` is still running. D-03
requires execution to run live inside a log widget, not be summarised after the fact. This plan
adds `StreamingRunner`, a `subprocess.Popen`-based Runner that hands each line to a callback as it
arrives and attributes it to the tool currently installing (D-05.2 — the abandoned branch's
attribution vanished whenever its optional `captured_runner` was `None`, `session.py:182` there;
see D-04, reference only, never ported).

It also adds DD-1's weak cancellation to `installer/session.py::run_installs`: an optional
`should_continue` predicate checked between tools, so a batch can stop queuing new work without
this phase taking on `subprocess.terminate()` lifecycle management.

Purpose: get the risky I/O primitive right, in isolation, against a fake child process.
Output: `StreamingRunner`, `STREAM_DETAIL_LINES`, `run_installs(..., should_continue=...)`, and
their tests.
</objective>

## Design decisions this plan implements

- **DD-1 (failure handling / cancel)** — the batch continues past a failed tool and reports a
  per-tool status list; cancellation is weak (stop queuing, let the in-flight tool finish). This
  plan supplies the `should_continue` half; the keybind and the "not attempted" rendering are
  plan 13-05.
- **D-05.2 (unconditional attribution)** — enforced structurally: `StreamingRunner`'s `emit`
  callback is a REQUIRED constructor argument with no default and no `None` branch, and
  `__call__`/`method_started` raise `RuntimeError` when no tool has been set. There is no
  "plain runner" fallback path for the interactive TUI to accidentally take.

  <behavior>
    - `StreamingRunner(emit)` where `emit` is `Callable[[str, str], None]` taking `(tool_id, line)`; `emit` is positional-required, has no default and is never checked for `None`.
    - `set_tool("rg")` then `runner(["python", "-c", "print('a'); print('b')"])` calls `emit` with `("rg", "a")` then `("rg", "b")`, in order, with no trailing newline on either line.
    - Lines arrive incrementally: a child that prints, then sleeps, then prints again causes the first `emit` before the child exits (assert by recording a monotonic timestamp per emitted line and asserting the gap between the two is at least the child's sleep).
    - `method_started("brew")` emits `("rg", "-- trying brew --")` under the current tool.
    - Calling the runner or `method_started` before any `set_tool` raises `RuntimeError` whose message contains `set_tool`.
    - A child exiting non-zero raises `CommandError` with `.cmd` equal to the argv, `.returncode` equal to the child's code, and `.detail` containing the child's last output line — and every line it printed was still emitted first.
    - A missing binary raises `CommandError` with `.returncode == 127`, matching `run_command`.
    - stderr is folded into the same stream in source order (a child printing to stdout then stderr emits both).
    - `.detail` is bounded: a child printing 500 lines yields a `.detail` with at most `STREAM_DETAIL_LINES` lines, while `emit` still received all 500.
    - `isinstance(StreamingRunner(emit), MethodAwareRunner)` is True.
  </behavior>
  <action>
Add `STREAM_DETAIL_LINES = 20` and `class StreamingRunner` to `installer/run.py`, below
`run_captured` and above `QUERY_TIMEOUT`, with a docstring that says what it is for (feeding a live
log widget while the child runs) and why it exists beside `run_captured` rather than replacing it
(the console path still wants a blocking, non-streaming runner).

Constructor takes `emit: Callable[[str, str], None]` positionally and stores it plus
`self._tool_id: str | None = None`. `set_tool(tool_id: str) -> None` assigns it. A private
`_current()` returns the id or raises `RuntimeError("StreamingRunner.set_tool must be called
before running a command")` — this is the structural guarantee behind D-05.2: there is no
attribution-free branch to fall into, unlike the abandoned branch's `captured_runner=None` (D-04,
audit finding B).

`method_started(method: str) -> None` emits a single header line reading `-- trying {method} --`,
so `installer/engine.py`'s existing ladder dispatch produces per-method section headers with zero
engine change.

`__call__(cmd: list[str]) -> None` launches `subprocess.Popen` with `stdin=subprocess.DEVNULL`,
`stdout=subprocess.PIPE`, `stderr=subprocess.STDOUT`, `text=True`, `bufsize=1`. Per 13-RESEARCH.md
Pitfall 3, all three of those are load-bearing: DEVNULL because a script that reads stdin would
otherwise wedge a worker thread with no recoverable input path while Textual holds the terminal in
raw mode; STDOUT-merged because it gives one ordered stream and makes line ordering trivially
correct; and the read loop must run in the same thread that owns the `Popen` object, never handing
it across threads. Iterate `proc.stdout` line by line, `rstrip` the trailing newline only, emit
each line, and keep the tail in a `collections.deque(maxlen=STREAM_DETAIL_LINES)` so a verbose
installer cannot grow an unbounded buffer just to build an error message. After the loop, `wait()`
and raise `CommandError(cmd, returncode, detail="\n".join(tail))` on a non-zero code, mirroring
`run_output`'s existing detail-carrying shape so `run_live` keeps catching it unmodified. Wrap the
`Popen` construction in `except OSError` raising `CommandError(cmd, 127)`, exactly like
`run_command` and `run_output` already do. Deliberately set no timeout — the `run_output` docstring
already records why a side-effecting install child must be allowed to take minutes.

Extend `tests/test_run.py` with the cases in `<behavior>`. Follow the file's existing convention:
drive real children with `sys.executable -c "..."` for the streaming/ordering/exit-code cases
rather than mocking `subprocess.Popen`, because the property under test is genuine incremental
reads from a real pipe, and reserve `monkeypatch` for the missing-binary case.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| child process stdout -> StreamingRunner -> caller callback | untrusted bytes from an arbitrary vendor install script cross into the caller's renderer |
| child process stdin | a script that reads stdin can wedge the calling thread indefinitely |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-13-02 | Tampering | `StreamingRunner.__call__` emitted lines | low | mitigate | emit raw text only; the widget-side escape-sequence stripping is `installer/execute_screen.py::sanitize_log_line` in plan 13-04 — this module never writes to a terminal itself |
| T-13-03 | Denial of Service | a child waiting on stdin never exits | medium | mitigate | `stdin=subprocess.DEVNULL`; no install command in the catalog reads stdin (every side effect is a `ctx.runner(argv)` call in `installer/download.py`/`installer/executors.py`/`installer/apps.py`) |
| T-13-08 | Denial of Service | a child emitting unbounded output exhausts memory while building `CommandError.detail` | medium | mitigate | the retained tail is a `deque(maxlen=STREAM_DETAIL_LINES)`; emitted lines are handed off and not accumulated |
| T-13-09 | Repudiation | output that cannot be attributed to the tool that produced it | high | mitigate | `emit` is a required constructor argument and `_current()` raises when no tool is set — there is no `None` branch, which is the exact defect D-05.2 names in the abandoned branch |
| T-13-SC | Tampering | npm/pip/cargo installs | high | accept | no external package is introduced; 13-RESEARCH.md records the Package Legitimacy Gate as not applicable and `subprocess`/`collections` are stdlib |
</threat_model>
