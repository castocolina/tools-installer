## Design decisions this plan records

DD-1 (continue with a running per-tool status list; weak cancel), DD-2 (`link_mode` only, folded
into `PoliciesScreen`, no new view), and DD-3 (`--link-mode` overrides for one run only) were made
during planning because CONTEXT.md left them open and this is an unattended run. They are recorded
in `13-VALIDATION.md` by plan 13-01; this plan carries the two with lasting architectural
consequence — DD-1's cancel semantics and DD-2's no-new-view choice — into
`.claude/architecture.md`, where the next contributor will actually look.

Add a `## Phase 13: live in-TUI install execution and persisted wizard settings` section to
`.claude/architecture.md`, after the Phase 12.4 section, covering six things a future contributor
cannot infer from the code alone.

First, ownership: `installer/execute_screen.py` is an IO adapter, not a second decision layer —
`resolve_dependencies`, `audit`, `run_installs`, `install_tool`, `configure_path` and `run_doctor`
remain the sole owners of install control flow, and the screen only formats and streams. Name the
reason: the abandoned `feat/install-experience` branch split that responsibility across three
modules with no owning seam, and this phase's audit rated it a real defect.

Second, why the execute screen is a `ModalScreen` and not a registered view: `AppScreen` requires a
`VIEWS` row, a row would give the screen a number key and a palette entry, and a navigable
execution screen breaks the `[catalog] / [catalog, <view>]` stack invariant `UnifiedApp._navigable`
protects. State that a pushed non-navigable screen is the established shape here
(`ConfirmUninstall`, `NavScreen`, `TimePickerScreen`).

Third, the streaming seam: `installer/run.py::StreamingRunner` is the only `Runner` in this project
that reads a child's output incrementally, it is installed through the same single `Runner` seam
every executor already calls, and attribution is structural — `attributed_install` sets the tool
through `run_installs`' existing `Install` parameter, so there is no optional argument whose
absence can drop it.

Fourth, DD-1's cancellation semantics: a failure never aborts the batch, `should_continue` is
checked between tools and never during one, an in-flight child is always allowed to finish, and
"not attempted" is derived by differencing the resolved ids against the returned outcomes rather
than by adding an `InstallStatus` member. Say why the weak form was chosen: killing a half-written
install is worse than a slow one, and terminating children would pull subprocess lifecycle
management into a phase that otherwise needs none.

Fifth, DD-2 and DD-3: the link mode lives in `installer/settings.py`, is asked at most once inside
the app, is adjustable from `PoliciesScreen` with no new view, and an explicit `--link-mode`
overrides for one run without rewriting the stored value.

Sixth, the live-read rule: every consumer of the link mode re-reads it rather than capturing it at
construction time — the Doctor preview and fix, the execute screen's PATH wiring, `ban_policy`'s
alias targets and `tweak_policy`'s source targets. Name the failure this prevents: a ban enabled
after switching to split mode would otherwise write aliases into a `~/.myshellrc` nothing sources,
with nothing on screen to reveal it. Note that this is the same predicate-not-its-result reasoning
the `guard_state` parameter already carries.
