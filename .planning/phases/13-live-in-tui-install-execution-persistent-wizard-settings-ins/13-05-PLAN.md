## Design decisions this plan implements

- **DD-1 — continue with a running per-tool status list, plus a weak cancel.** A failed tool never
  aborts the batch. The screen shows a live list of every tool in the resolved order with its
  state: not-yet-reached, running, done, or not-attempted. Cancel stops new tools being queued and
  lets the in-flight one finish; it never kills a child process, because a half-written install is
  worse than a slow one.
- **D-05.3 — a dismissed prompt is never a silent no-op.** The mismatch prompt's `escape` path
  writes an explicit log line naming the tool, the fact the prompt was dismissed, and the resulting
  outcome, and sets a status line. `installer/session.py`'s `MismatchChoice` is a closed
  `Literal["retry", "skip", "fallback"]` with no cancelled member, so a dismissal must resolve to
  one of the three: it resolves to `skip`, the conservative choice for a download whose checksum
  did not match, and says so.
- **Mechanism** — `ask_from_worker` implements exactly the mechanism recorded under
  `## Worker-to-modal mechanism` in `13-VALIDATION.md` by plan 13-01. Do not re-derive it.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| a failed checksum -> the user's decision -> the install ladder | the answer decides whether an unverified download is installed anyway |
| worker thread -> modal -> worker thread | a lost or defaulted answer silently changes the security outcome |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-13-13 | Tampering | a dismissed mismatch prompt defaulting to `fallback` or `retry` | high | mitigate | the `None` branch resolves to `skip`, the only option that does not install an unverified artifact, and says so in the log and the status line |
| T-13-14 | Repudiation | a mismatch resolved without the user seeing why | medium | mitigate | every mismatch and every dismissal writes an attributed log line naming the tool and the resulting choice |
| T-13-05 | Elevation of privilege | `unattended` suppressing the security prompt | low | accept | mirrors `installer/app.py::run_wizard` line 157's existing rule: `--yes` implies unattended and a mismatch hard-fails rather than silently continuing |
| T-13-07 | Denial of Service | worker blocked forever on a modal the user cannot reach | medium | mitigate | the mechanism proven in plan 13-01 keeps the event loop running while the worker waits; a Pilot test asserts it |
| T-13-15 | Denial of Service | a cancel that cannot stop a long batch | low | mitigate | `should_continue` is checked between every tool, so the worst case is one in-flight tool, which is the deliberate DD-1 trade rather than owning child-process termination |
| T-13-SC | Tampering | npm/pip/cargo installs | high | accept | no external package is introduced; 13-RESEARCH.md records the Package Legitimacy Gate as not applicable |
</threat_model>
