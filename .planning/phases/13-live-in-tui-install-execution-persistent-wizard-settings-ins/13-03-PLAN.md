<objective>
Give this project a persisted wizard setting, mirroring `installer/version_cache.py` exactly rather
than inventing a second persistence mechanism.

Today `setup.py::_resolve_link_mode` (lines 601-613) asks "How should PATH be wired into your
shells?" through `questionary.select` on **every** interactive run, remembers nothing, and there is
no screen anywhere in `installer/wizard_app.py` that exposes the answer afterwards. This plan
builds the pure-core half: a `{"version": 1, "link_mode": ...}` JSON envelope under
`~/.local/state/tools-installer/settings.json`, written through the same
`installer/atomic.py::atomic_write_text` that `versions.json` already uses, read defensively, and a
small live-owner object the TUI can mutate.

Per `.claude/architecture.md` rule 4 the decision functions live here in `installer/` where
pyright-strict, coverage and tests apply — `setup.py` will only compose them (plan 13-06).

Purpose: one module, fully tested, with no TUI and no `setup.py` coupling.
Output: `installer/settings.py` and `tests/test_settings.py`.
</objective>

## Design decisions this plan implements

- **DD-2 — `link_mode` only.** The envelope carries a `"version": 1` field (mirroring
  `version_cache.py`) precisely so a later default-shell or headless-flag preference is an additive
  key rather than a migration. Those keys are NOT added now: CONTEXT.md raises neither as a bug in
  this phase.
- **DD-3 — flag overrides for one run, never overwrites.** Expressed as two pure functions,
  `resolve_link_mode(flag=..., stored=...)` and `link_mode_needs_choice(flag=..., stored=...)`, so
  the precedence rule is a tested property of `installer/` rather than an if-chain inside
  `setup.py`. Persisting is a separate, explicit `SettingsStore.set_link_mode` call that only the
  in-TUI picker makes.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| `~/.local/state/tools-installer/settings.json` -> `load_settings` | an on-disk file any local process or a hand-edit can change, feeding a value that selects which shell rc files get written |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-13-01 | Tampering | `load_settings` -> `installer/locations.py::rc_paths_for_mode` / `ban_rc_paths` | medium | mitigate | membership check against the closed `LINK_MODES` tuple on load; anything else degrades to `Settings()` and therefore to `DEFAULT_LINK_MODE` |
| T-13-10 | Tampering | a torn write leaving a half-written settings file | low | mitigate | `installer/atomic.py::atomic_write_text` only (sibling temp + `os.replace`); the module opens no file itself |
| T-13-11 | Information disclosure | the settings file recording anything sensitive | low | accept | the envelope carries one enum-valued string and a schema version; no path, token or hostname is stored |
| T-13-SC | Tampering | npm/pip/cargo installs | high | accept | no external package is introduced; `json`, `pathlib` and `dataclasses` are stdlib and 13-RESEARCH.md records the Package Legitimacy Gate as not applicable |
