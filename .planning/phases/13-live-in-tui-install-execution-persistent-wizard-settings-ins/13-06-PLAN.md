<objective>
Replace the pre-TUI link-mode prompt with a persisted preference that is asked once, inside the
app, and adjustable from inside the app afterwards.

Today `setup.py::_resolve_link_mode` (lines 601-613) runs `questionary.select` before the Textual
app opens, on every single interactive run, stores nothing, and no screen in
`installer/wizard_app.py` exposes the answer. This plan deletes that function, resolves the value
through `installer/settings.py` (plan 13-03) instead, and surfaces it on the existing
`PoliciesScreen` — the closest precedent this codebase has for "a screen where installer-level
settings are changed live".

It also closes a correctness hole the persistence creates: `setup.py::_build_app` currently bakes
the link mode into `rc_paths`, the Doctor fix preview, `ban_policy`'s alias targets and
`tweak_policy`'s source targets at construction time. If the user can now change the mode while the
app is running, every one of those has to re-read it, or enabling the pip/npm ban after switching
to split mode would write aliases into a `~/.myshellrc` that nothing sources — a silent, invisible
no-op. Making them live reads is the point of Task 1.

Purpose: honour DD-2 and DD-3 without adding a view, a navigation path, or a stale snapshot.
Output: the settings composition in `setup.py`, the `m` picker on `PoliciesScreen`, and the
one-time first-run prompt.
</objective>

## Design decisions this plan implements

- **DD-2 — `link_mode` only, folded into `PoliciesScreen`.** No new `installer/ui_common.py::VIEWS`
  row, so no seventh number key, no seventh palette entry, and no second navigation mechanism
  (`.claude/architecture.md` rules 1 and 2). The picker mirrors the already-shipped
  `TimePickerScreen` + `action_pick_time` + `_time_picked` trio exactly. Default-shell preference
  and headless-flag defaults are out of scope — CONTEXT.md raises neither as a bug in this phase.
- **DD-3 — `--link-mode` overrides for one run only.** `resolve_link_mode` honours the flag,
  and `setup.py` never calls `set_link_mode` on the flag's behalf. Only the in-app picker persists,
  because only that is the user asking for a new standing preference.
- **D-05.3 — no silently-swallowed cancellation.** Both link-mode prompts (first-run and the
  Policies picker) write an explicit message on dismissal naming what did not change and how to
  change it later. This is the exact defect the audit records at the abandoned branch's
  `wizard_app.py:946-968`, where a dismissed `PathLinkModePrompt` fell through an
  `if link_mode is not None:` guard and returned the user to the catalog with no explanation
  (D-04: reference only, never ported).
- **Why `13-05` is in `depends_on` even though no file is shared.** This plan and 13-05 touch
  disjoint files, but Task 3's gate is the whole-repo `uv run pytest --cov -q` against
  `fail_under = 90`, and `[tool.coverage.run] source = ["installer"]` means that number moves with
  `installer/execute_screen.py` — 13-05's module. Run in the same wave, each plan's coverage gate
  would be measuring a tree half-built by the other, and a green or red result would depend on
  which agent committed first. Declaring the edge makes the gate deterministic: 13-05 measures a
  tree without this plan's new code, this plan measures the complete one. The ordering is a
  verification dependency, not a code one — nothing here reads a symbol 13-05 creates, which is why
  `13-05-SUMMARY.md` is deliberately absent from `<context>`.
- **`.claude/architecture.md` rule 1 applied to the new key.** The `m` binding is registered in the
  `VIEWS` table's `policies` row, not only in `BINDINGS`, for the reason Phase 12 already recorded
  about the `u` key: this project renders its footer from `View.actions`, so a binding added
  without the registry row is an action the user is never told about.
