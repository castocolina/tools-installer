<objective>
Split the single flat Catalog view into three tier-scoped top-level views (System / User / AI)
that land FIRST in the nav per D-01, backed by ONE shared staged selection so a batch assembled
across tiers commits as a single result -- and make a cross-tier `requires` drag-in visible from
whichever tier view the user happens to be standing in.

Purpose: ROADMAP Phase 2 SC#1-SC#3. Browsing must match how the user walks a fresh machine
(system prerequisites, then personal picks, then agent tooling), and a tier-filtered view must
never hide the fact that an ai-tier pick needs a system-tier prerequisite. This plan is also
the load-bearing half of the phase: plan 02-02's `recommends` prompt adds tools into the
shared staged batch this plan creates.

Output: three `View` rows replacing the single `catalog` row; a derived `BASE_VIEW` constant and
a derived `GLOBAL_NAV` string; `ToolBrowser` accepting an injected, shared selection set and
mutating it in place; `CatalogScreen` parameterised by view name / full catalog / shared staged
set; `UnifiedApp` hosting three tier `CatalogScreen`s; a new pure `deps.missing_requires`
preview; and the migrated test suite.
</objective>

<design_decisions>
02-PATTERNS.md flags two open design points with no existing precedent. This plan resolves the
first; plan 02-02 resolves the second.

**Open point 1 -- how three `CatalogScreen` instances reduce their `Decided` messages to one
result.** They do not need reducing, because they never hold three separate selections. All
three share ONE `set[str]` owned by `UnifiedApp` (`self._staged`), handed down to each
`CatalogScreen` and on to each `ToolBrowser` as its `selected` attribute. Only the ACTIVE screen
receives key events, so only one `Decided` is ever posted; whichever screen posts it reports the
whole shared batch, ordered against the full catalog via the existing
`installer/selection.py::select_tools`. The existing single `on_catalog_screen_decided` handler
is unchanged.

Two consequences make this safe rather than clever:
- `ToolBrowser.action_select_all` / `action_invert` currently REBIND `self.selected` to a fresh
  set built from that browser's own items, which would silently discard the other two tiers'
  marks. Both are changed to mutate in place (`|=` and `^=` over this browser's selectable ids).
  For a browser that owns its whole set -- the Uninstall view, and any single-view catalog --
  the result is bit-for-bit identical, because `selected` is then always a subset of that
  browser's selectable ids; for a shared set it becomes exactly the wanted "act on the active
  tier view only" semantic.
- `ToolBrowser.selected_ids()` and `_refresh_marks`/`refresh_marks` already filter by this
  browser's own adapter items, so a shared set carrying foreign tier ids is inert in both.

**Why the ROADMAP's `claude` -> `pnpm` example is proved with `mmdc` -> `pnpm` instead.**
ROADMAP SC#2 names "`claude` (ai tier) ... surfaces the `pnpm` (system tier) drag-in notice".
`claude` in `installer/registry.toml` installs via `kind="script"` (`https://claude.ai/install.sh`)
and `kind="cask"` (`claude-code`) and declares no `requires` at all -- it does not depend on
`pnpm`, and inventing that edge would put a false fact in the catalog. The only real cross-tier-
VIEW `requires` edge in the catalog today is `mmdc` (tier `user`) -> `pnpm` (tier `system`);
`java`/`gradle`/`maven`/`groovy`/`springbootcli` -> `sdkman` are all system->system, so they
cross no view boundary. This is the same documented substitution STATE.md already records for
Phase 1 ("REQ-dependency-chain-requires' illustrative examples ... name tools not yet in
registry.toml"), and Phase 8 is where agent hosts gain real cross-tier relationships. Task 2
therefore proves SC#2/SC#3 with the real `mmdc` -> `pnpm` edge plus a synthetic ai->system
fixture that stays valid even if Phase 5 retargets `mmdc.requires`.

**Why the in-view notice is a preview, not a second resolver.** `deps.missing_requires` names
what will be dragged in; it deliberately makes no availability judgement (a `CatalogScreen` has
no `Platform`). The authoritative verdict -- including the "not available on this platform --
skipped" wording SC#3 mentions as the alternative -- stays with
`resolve_dependencies` + `render_dependency_notice` on the post-TUI path in
`installer/app.py::run_wizard`, unchanged.
</design_decisions>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Terminal keypress -> `ToolBrowser` selection state | The only writer of the staged batch. Every id that reaches the installer originates from a keypress on a selectable row; nothing else may add one. |
| Shared `UnifiedApp._staged` set -> three `CatalogScreen` instances | One mutable object now crosses three screens. A defect here stages a tool the user never marked, which later becomes a real install. |
| Staged ids -> `select_tools` -> `resolve_dependencies` -> install engine | The tier filter must narrow what is displayed and never what is resolved, or a needed system-tier prerequisite is silently dropped from a real install. |
