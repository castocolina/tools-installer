<objective>
Add `Tool.recommends`, the soft-dependency signal that is deliberately NOT `requires`: a flat,
one-hop, never-resolved, never-auto-installed list surfaced as a one-line, non-blocking prompt the
moment its tool is space-marked, which one keypress folds into the same staged batch plan 02-01
built.

Purpose: ROADMAP Phase 2 SC#4 -- "Selecting `claude` or `opencode` surfaces a one-action prompt
naming its `recommends` that the user can accept or dismiss; nothing in that list is ever installed
automatically." This is the half of Phase 2 that plan 02-01 explicitly deferred, and it is the
mechanism Phase 8 (`REQ-recommends-wiring-agent-hosts`) instantiates with real data.

Output: a `recommends` field on `Tool` plus its registry parse; one new pure function
`installer/selection.py::unstaged_recommends`; a second `StatusLine` on `CatalogScreen` carrying the
prompt, two screen bindings (`r` accept / `d` dismiss), a `on_screen_resume` mark re-stamp, and a
`pairs well with ...` detail-bar clause; illustrative `recommends` data on `claude` and `opencode`
using tools that already exist in the catalog; and a shipped-registry integrity test.
</objective>

<design_decisions>
02-PATTERNS.md flags the prompt widget as having no analog ("genuinely new UI, left to
planner/implementer discretion"). These are the resolutions.

**The prompt is a second `StatusLine`, not a new widget and not a modal.** D-05's constraint is
"the same table, one more row got checked" -- a modal would break the staged-selection flow, and
`NavScreen`'s `ModalScreen` is the wrong shape. `ui_common.StatusLine` already is a docked,
severity-coloured line with the exact `.text` seam the tests need, so the screen composes a SECOND
instance under the browser. This costs zero new widget code and keeps the two lines visually
identical, which matters because they are shown together.

**Why the prompt cannot reuse `self.status`.** Plan 02-01 Task 3 writes the cross-tier `requires`
notice to `self.status` on the very same `SelectionChanged` event this plan hooks. Marking a tool
that has both a missing `requires` and unstaged `recommends` would make one silently overwrite the
other. They are different in kind -- the requires notice is informational ("this will happen
anyway"), the recommends prompt is actionable ("press r") -- so they get two lines and both stay
visible. `tests/test_ui_common.py`'s `len(screen.query(StatusLine)) == 1` assertion is on a
synthetic `_Demo` screen, not on `CatalogScreen`, so a second instance breaks nothing.

**Keys: `r` accepts, `d` dismisses, both on `CatalogScreen`.** `space`/`enter`/`left`/`right`/`a`/`i`
belong to `ToolBrowser`, `1`-`6`/`q`/`escape`/`ctrl+p`/`ctrl+c` to `UnifiedApp`; `r` and `d` are
free everywhere in the app. They live on the screen, not on `ToolBrowser`, because `ToolBrowser` is
the reusable data-agnostic widget the Uninstall view also mounts -- it must not learn what a
`recommends` is (02-PATTERNS.md is explicit about this).

**The prompt names its own keys instead of the footer advertising them.** `FooterBar` renders the
static `actions` string from the `VIEWS` table, which plan 02-01 owns and which is shown all the
time; adding `r add recommended` there would be permanent noise for a prompt that is almost never
up. The prompt line says "press r ... , d to dismiss" in its own text, so the keys appear exactly
when they are actionable. This also keeps `installer/ui_common.py` out of this plan's diff entirely.

**Surfacing cadence (REQUIREMENTS.md's open question, resolved here).** The prompt is transient and
stateless: it appears on every fresh mark of a tool that still has unstaged, uninstalled
recommendations, and it is cleared by the next selection change, an unmark, a dismiss, or an accept.
A dismissal is NOT remembered. Rationale: a remembered dismissal is invisible state the user cannot
inspect or undo, and the natural suppression already covers the annoying case -- once accepted, the
ids are staged, so `unstaged_recommends` returns empty and re-marking never re-prompts. No
per-session bookkeeping, no new state, less code.

**Why `unstaged_recommends` lives in `installer/selection.py`.** 02-PATTERNS.md is explicit that it
must NOT be a `deps.py` addition: putting it next to `resolve_dependencies` invites exactly the
transitive/drag-in/cycle-checked shape `recommends` must never grow. `selection.py` is the module
about the staged selection and turning ids back into tools (`select_tools`), and the function's
whole meaning is "what does this selection not yet include". Plan 02-01 already added
`from installer.selection import select_tools` to `catalog_tui.py`, so this is an extension of an
import that exists rather than a new coupling.

**Unknown recommended ids are skipped, and that is not a tolerance feature.** D-03 says Phase 2 is
not scoped to make an unresolvable recommended id gracefully tolerated end-to-end. The one-line
`rec_id in known` filter in `unstaged_recommends` is a lookup guard that keeps a typo from raising
`KeyError` inside a Textual message handler (which wedges the message loop); it is not a claim that
a dangling id is handled anywhere else, and no UI, warning, or registry lint is built for it.
Phase 8 owns that when it adds ids for tools it is landing in the same phase.

**Why `claude`/`opencode` carry the illustrative data.** ROADMAP SC#4 names them by id, so the
criterion is not satisfiable without `recommends` data on those two rows. The Deferred Idea and D-03
defer the CONTENT (`codegraph`/`graphify`/`rtk`, which do not exist in the catalog until Phase 8),
not the CARRIER. D-02 resolves the conflict directly: build the mechanism now and prove it with
tools that already exist in `registry.toml`. `rg`, `fd` and `jq` are the pick -- all three are real
catalog entries, all three are `audience = "ai"` (tools whose primary beneficiary is an agent), and
an agent host genuinely pairs with a fast searcher, a fast finder and a JSON filter without needing
any of them to run. Each declaration carries a TOML comment saying it is Phase 2 illustrative data
that Phase 8 extends, so no future reader mistakes it for the final list.

**Why `jq` is in the list on purpose.** `rg` and `fd` are `tier = "ai"` (visible in the AI view);
`jq` is `tier = "user"` (not visible there). Accepting from the AI view therefore stages a row this
screen cannot even draw, which is the whole reason `unstaged_recommends` is handed
`self._catalog` (the WHOLE catalog from 02-01) rather than the tier-filtered `self.tools`, and the
reason `on_screen_resume` exists. A single-tier demo pair would have hidden both bugs.

**Why `on_screen_resume` is required and is this plan's problem, not 02-01's.** 02-01's `a`/`i`/
`space` always act on the ACTIVE browser and stamp their own cells, so no tier screen can go stale.
The accept path is the first and only writer that adds an id to the shared set on behalf of a
DIFFERENT screen, whose `DataTable` was already built and stamped. `refresh_marks` iterates only its
own rows and is inert for foreign ids, so calling it on resume is both sufficient and safe (it
carries 02-01's `NoMatches` and empty-columns guards).

**The cross-tier test must VISIT the owning view before the accept, or it proves nothing.** Cycle-1
review found the originally-specified sequence (`3`, `space`, `r`, `2`) would pass with
`on_screen_resume` deleted: the User screen is pushed for the FIRST time only at the final `2`, and a
first mount builds its `DataTable` from `_row_cells`, which already reads `tool.id in
self._browser.selected` -- by then the shared set contains the accepted id, so the checkbox paints
`[x]` for a reason that has nothing to do with resume. The corrected sequence opens User first
(stamping it while the id is NOT staged), leaves for AI, accepts there, and only then returns. Task 2
specifies that order explicitly, and the test is worthless without it -- if it passes with
`on_screen_resume` commented out, the sequence regressed.
</design_decisions>
