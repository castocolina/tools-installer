## Design decisions this plan implements

- **DD-1** — the batch continues past a failure and reports a per-tool status list. The worker
  passes `should_continue` (built in plan 13-02) but binds the cancel keypress in plan 13-05.
- **D-01 interpretation — `ExecuteScreen` is a `ModalScreen[None]`, not an `AppScreen`.**
  `installer/ui_common.py::AppScreen.__init__` requires a `view` name that exists in
  `VIEW_BY_NAME`, because `ModeBadge` and `WayfindingHeader` both index it — so an `AppScreen`
  subclass would force a seventh `VIEWS` row and hand the execution screen a number key and a
  nav-palette entry, i.e. a destination the user could jump to mid-install, breaking the
  `[catalog] / [catalog, <view>]` stack invariant `UnifiedApp._navigable` protects. `ModalScreen`
  is this codebase's established shape for a pushed, non-navigable screen (`ConfirmUninstall`,
  `NavScreen`, `TimePickerScreen`) and makes `_navigable()` return False while it is on top, so
  the App's priority number keys and `q` are inert during a run with no new guard. D-01's
  requirement is `push_screen`/`pop_screen` rather than an overlay, and this satisfies it.
- **D-02 interpretation — "a key" is `escape` (and `enter`), not any key.** A named key avoids an
  accidental dismissal of exactly the failure detail D-02 exists to protect, and the screen states
  the key on screen.
- **13-RESEARCH.md Pitfall 2, option (b)** — the interactive path gets its own top-level function
  and never calls `run_wizard`, so the headless path's behaviour and tests are provably untouched
  by this diff.
- **13-RESEARCH.md assumption A1 accepted** — `installer/app.py::clean_rc_duplicates` (the
  destructive rc-duplicate cleanup) stays a console step and is NOT rebuilt as a third in-TUI
  confirm surface. It is still reached after the app exits on the interactive path, so today's
  capability is preserved rather than dropped.

Create `installer/execute_screen.py`. Its module docstring states that this screen is a thin IO
adapter over unchanged pure core — `resolve_dependencies`, `audit`, `run_installs`, `install_tool`,

is deliberate, because audit finding C records three modules independently deciding control flow in
the abandoned branch. Name the file's relationship to that branch explicitly: design reference
only, never a code source (D-04).

Define `sanitize_log_line(line: str) -> str`, which strips ASCII control characters other than tab
(the C0 range and DEL) from a child process's output before it is rendered, and say why: an install
script's escape sequences must not be able to reposition the cursor or recolour the running frame.

Define `attributed_install(runner, install=install_tool)` returning a callable matching
`installer/session.py::Install`. It calls `runner.set_tool(tool.id)` and then forwards every
argument unchanged. This is the structural half of D-05.2: attribution is driven by the tool
`run_installs` is about to install, through the `Install` seam that already exists, so there is no
optional parameter whose absence can silently drop it — the exact defect audit finding B records at
`session.py:182` on the abandoned branch.

Define two `Message` subclasses mirroring `GlobalsAudited`'s shape and docstring style:
`InstallLogLine` carrying `tool_id` and `line`, and `InstallRunFinished` carrying `summary`,
`outcomes`, `not_attempted`, `path_text`, `verify_text` and `error`.

Define a frozen dataclass `ExecuteInputs` with `catalog`, `platform`, `wire_path` (a zero-argument
callable returning the captured console text of the PATH wiring), `verify` (the same shape for the
read-only PATH audit), and defaulted `installed`, `resolve_tag`, `install` and `unattended` fields.
Defaults follow this repo's existing optional-closure convention so a test can construct one
without a composition root.

Define `ExecuteScreen(ModalScreen[None])` taking the selected ids and an `ExecuteInputs`. Give it
an opaque full-screen background in `DEFAULT_CSS` and three bindings: `enter` -> `action_start`,
`escape` -> `action_close`, and nothing else this task. Its docstring records the D-01
interpretation from this plan's design-decisions section (why `ModalScreen` and not `AppScreen`).
`compose` yields a `Static` with id `execute-head`, a `RichLog` with id `execute-log` constructed
with markup and highlighting disabled and auto-scroll enabled, a `StatusLine` from
`installer/ui_common.py`, and a `Static` with id `execute-keys` carrying the key hints. Expose
`started`, `finished` and `summary` as public attributes, following the public-test-seam convention
`DoctorScreen` already uses for `applied`, `globals_running` and friends.

`on_mount` resolves the batch with the same four pure calls `run_wizard` makes in that order —
`select_tools`, `order_for_install`, `resolve_dependencies` with `available` built from
`resolve_methods` and `is_installed` from the inputs — and stores the resolved order plus a
`{id: tool}` map of the full catalog. It renders the confirm line into `execute-head` and starts
NOTHING. No subprocess may run before a keypress; this is D-05.1, and audit finding A records the
old branch setting its started flag before showing modals with no visible sign anything was queued.

`action_start` returns early when `started` is already True, sets it, writes a "Installing N
tools..." status, and calls the worker. The worker is
`@work(thread=True, exclusive=True, group="install-execute", exit_on_error=False)` — its own group
so it can neither cancel nor be cancelled by `globals-reinstall`, `globals-audit`,
`version-refresh`, `tool-update` or `daemon-default`, and `exit_on_error=False` for the same reason
`_apply_daemon_default_worker` carries it: a worker exception must not take the whole app down.
Wrap the whole body in try/finally so `InstallRunFinished` is posted on every path, mirroring that
same worker's documented guarantee — a screen stuck on "Installing..." forever is the worst failure
mode here.

Inside the worker: build a `StreamingRunner` whose emit callback does
`self.post_message(InstallLogLine(tool_id, line))` — the worker never touches a widget from its own
thread, which is the established rule in this codebase. Call `run_installs` through
`installer/ui_common.py::run_live` (architecture rule 3, never a screen-local try/except), passing
the resolved order, the platform, the streaming runner, the inputs' `resolve_tag`, the
`attributed_install` wrapper, `on_mismatch=None` for now (plan 13-05 wires the modal),
`catalog=` the id map, and `should_continue=` a predicate that is always True for now (plan 13-05
binds the cancel key to it). Summarise with `summarize`. Then, in the SAME worker, call
`inputs.wire_path()` and `inputs.verify()` through `run_live` as well, so confirm -> run -> wire ->
verify is one continuous flow with no state left half-applied between two workers. Compute
`not_attempted` as the resolved ids minus the ids present in the returned outcomes. Post
`InstallRunFinished`.

Specify the install step's failure path explicitly rather than leaving it to the happy path's shape.
`run_live` returns `(result, None)` on success and `(None, message)` on `OSError` or `CommandError`
(`installer/ui_common.py:41-50`), and `install_tool` already swallows `CommandError` per tool
(`installer/engine.py:136`), so a `(None, message)` here means the batch itself broke rather than a
tool failing — a torn state with no outcome list at all. When `run_live(run_installs)` returns
`None`, the worker must still post `InstallRunFinished`, carrying `outcomes=[]`, a `summary` built
by calling `summarize([])` (never `None` — `on_install_run_finished` and `UnifiedApp` both read it,
and a `None` there would trade a reported failure for an `AttributeError` inside a message handler),
`not_attempted` equal to every resolved id in order, and `error` set to the returned message. The
same rule holds for the `wire_path` and `verify` steps: a `None` result fills `path_text` /
`verify_text` with nothing and puts the message in `error`, rather than pretending those sections
succeeded. The finished screen then shows the error and a zero-outcome summary, which is the honest
rendering of "nothing was installed and here is why" and keeps the exit-code path working.

`on_install_log_line` writes to the `RichLog`. When the tool id differs from the last one seen it
first writes a section divider naming the new tool, then writes the line prefixed with the tool id
and a separator glyph, passing the text through `sanitize_log_line`. Both halves matter: audit
finding B records the old branch dumping every tool's output into one shared log with no section
break, so per-line attribution AND a per-tool section are required, not either one.

`on_install_run_finished` sets `finished`, records `summary`, renders `render_summary` into the log
through a small private helper that builds a `rich.console.Console` over an `io.StringIO` and
returns its text (the same redirect `setup.py:473-486`'s `_apply_fix` already uses), appends the
captured `path_text` and `verify_text` sections, and sets a status line naming the key that
returns. It must NOT call `event.stop()`: the message has to keep bubbling to `UnifiedApp`, which
records the summary for the process exit code. Say so in a comment, because a future `stop()` added
for tidiness would silently break the exit code.

`action_close` dismisses when the run has not started or has finished. While a run is in flight it
instead sets an explicit status line saying the installation is still running and naming what the
user can do — never a silent no-op (D-05.3's principle, applied to the close key).

Name what ctrl+c does during a run, in that same status line and in `ExecuteScreen`'s docstring,
because it is NOT the weak cancel and the difference is the user's data. `UnifiedApp.action_hard_abort`

mitigation is disclosure, not a code change: the mid-run status line must say that ctrl+c aborts the
