# Phase 15.4: Code Review Report

**Reviewed:** 2026-09-17
**Depth:** deep (cross-file: resolver → service → two screens → composition root)
**Files Reviewed:** 21 (9 production, 12 test) over `a6bca98~1..HEAD`
**Status:** issues_found

## Summary

The phase's headline mechanisms are, on their own terms, sound. I traced each of the
five high-risk areas the brief named and could NOT break three of them:

- **Race fix (`version_status.refresh`, item 1):** the raced branch genuinely publishes
  neither a record nor an epoch. `_refresh_versions_worker`'s `exclusive=True` plus
  the per-tier disjoint tool sets mean I could not construct a reachable same-epoch
  last-writer-wins overwrite in production topology. Confirmed correct.
- **Package-name propagation (item 3):** `removal_hint` cannot emit a backticked
  command without `ownership.package`, and every path that sets `package` sets it from
  verified evidence. I specifically chased the split-package case: `_native_owner`'s
  `package_owns_path` guard and `path_owner_package` read the *same* `rpm -qf` output,
  so the guard's declared name and the hint's discovered name cannot diverge; a
  genuinely split package (`git`/`git-core`) fails the guard and correctly falls
  through to `_os_package_owner`. Confirmed correct.
- **13-site `rows` migration (item 4):** all 13 real sites migrated; no stale list
  literal reaches `UninstallInputs` (see WR-05 for the test-helper caveat).

The three defects I *did* confirm are all at the seams those mechanisms touch rather
than inside them, and all three are reproducible:

1. The new `_resync` failure branch reintroduces an unguarded filesystem read and
   **raises OSError out of the single nav path** (proven by execution).
2. The now-epoch-gated `ownership_of`, combined with `UpdateService`'s own
   `invalidate`, makes **the entire Owner column go blank and the `u` key a silent
   no-op** for every other tool after one in-catalog update (proven by execution).
3. Rendering `row.hint` verbatim into the "Installed via" cell pushes the
   **"What gets removed" column completely off a supported 80-column terminal**
   (measured: x=180 in an 80-wide viewport; mutation-verified against the pre-change
   cell, which put it at x=71).

On item 6 (deferred Round-3 findings): **two deferral rationales were silently
invalidated by what shipped.** The "three environment predicates are cheap in-memory
reads" rationale used to defer widening `run_live` is factually false and is the
direct cause of CR-01. The Uninstall hint-width deferral required the executor to
check rendered width at the minimum tested size and record the result in the SUMMARY;
no such check is recorded, and the width is in fact broken (CR-03).

Every finding below was verified against the current source and, where the finding is
behavioural, by executing it. `make test` passes on the reviewed tree (2398 passed,
1 skipped, 95.68% coverage) — none of the findings below are caught by it, which is
itself part of the point.

## Critical Issues

### CR-01: `_resync`'s rows-failure branch calls three filesystem predicates unguarded and crashes the nav path

**File:** `installer/wizard_app.py:898-910` (branch), `setup.py:516-525` (the bindings)
**Issue:**
When `run_live(self._live_state)` catches an OSError from the rows predicate,
`_resync` re-derives the other three predicates **bare**:

```python
if error is not None:
    refreshed = (
        self._rows,
        self._ban_names_of(),      # -> guard_state(): reads ~/.local/bin
        self._has_path_block_of(), # -> has_managed_block(): Path.read_text()
        self._tweak_ids_of(),      # -> active_tweak_ids(): reads rc files + bin_dir
    )
```

The in-code justification — "they are cheap, non-failing in-memory reads (Round-3
review's accepted scope -- only rows touches the filesystem)" — is wrong on all three
counts. `installer/shellrc.py:163-168`'s `has_managed_block` does `path.read_text()`;
`active_tweak_ids` → `active_policies` → `tweak_present`/`tweak_executables_present`
read rc files and stat the bin dir; `guard_state(_DEFAULT_BIN_DIR, ...)` reads the bin
dir. All four predicates read the *same* filesystem, so the trigger for this branch
(a permission/IO fault under `$HOME`) is precisely the condition that makes the other
three fail too — they are correlated, not independent.

The consequence is not a bad status line, it is a crash on the single nav path:
`show_view` (`installer/wizard_app.py:1954-1977`) awaits `pop_screen()` *before*
calling `entering.enter_view()`, so an exception escaping `enter_view` leaves the
screen stack popped, `self.current_view` un-updated, and the exception propagating out
of an async Textual message handler. This is exactly what `.claude/architecture.md`
rule 3 / `run_live`'s own docstring ("a failed core action is surfaced, never a silent
crash (PRD)") exists to prevent.

`ownership_refreshed()` reaches the same branch, so the crash is also reachable from a
background repaint the user did not initiate.

**Verified by execution** (screen constructed with a working `rows`, then both `rows`
and `has_path_block` made to raise, then `enter_view()`):

```
enter_view raised OSError out of the nav path: has_path_block: EACCES on ~/.myshellrc
```

**Relation to the Round-3 ledger (item 6):** `15.4-04-PLAN.md`'s Round-3 "Review
Feedback Deferred" table defers *"Route all four predicates through `run_live`, not
only the rows predicate"* on the rationale quoted above. The shipped code did not just
inherit that gap — it added a **new** unguarded call site inside the very branch that
handles filesystem failure. The deferral's premise is invalidated by what shipped.

**Fix:** wrap the fallback re-derivation in the same seam, and keep the last known
values on failure:

```python
if error is not None:
    fallback, env_error = run_live(
        lambda: (self._ban_names_of(), self._has_path_block_of(), self._tweak_ids_of())
    )
    if fallback is None:
        fallback = (self._ban_names, self._has_path_block, self._tweak_ids)
        error = f"{error}; {env_error}"
    refreshed = (self._rows, *fallback)
```

Then delete the "cheap, non-failing in-memory reads" comment — it is the load-bearing
false claim. Consider applying the same seam to `__init__:642-644`, which has had the
identical unguarded shape since before this phase (proven: constructing
`UninstallScreen` with a raising `has_path_block` raises out of `__init__`).

### CR-02: one in-catalog update blanks the whole Owner column and makes `u` a silent no-op for every other tool

**File:** `installer/version_status.py:424-443` (the new epoch gate),
`installer/catalog_tui.py:739-741` and `:471-488` (the two consumers),
`installer/update.py:459-461` (the invalidate that triggers it)
**Issue:**
15.4-04 changed `ownership_of` from an unconditional `dict.get` to an epoch-gated read.
`UpdateService.run` calls `invalidate()` after every successful update, and
`_update_tool_worker` then re-refreshes **only the single updated tool**
(`catalog_tui.py:772`). The result is a map in which exactly one tool carries the
current epoch and every other tool carries the previous one, so `ownership_of` answers
`None` for the entire rest of the catalog.

Two user-visible consequences, both on the same screen the user is still looking at:

1. `on_tool_updated` calls `self._browser.reload(self._adapter())` (`:783`), repainting
   every row through `_owner_cell`, which returns `Text("")` for every `None`. **The
   whole Owner column blanks** — the exact failure D-02's governing principle forbids
   ("a blank cell should only ever mean 'genuinely don't know'"). `_version_detail`
   loses its ownership sentence for every row at the same time.
2. `action_update_tool` does `if ownership is None: return` (`:740-741`) — **no status
   line, no message**. Pressing `u` on any other tool is a silent no-op until the user
   navigates away and back to force a full `_start_version_refresh`.

**Verified by execution** against a real `VersionRefreshService`:

```
after full refresh: alpha=True beta=True
after invalidate + refresh([alpha]):
  alpha -> True
  beta  -> False        <-- record still present, reported as unavailable
```

This is a regression introduced by this phase: before 15.4-04, `ownership_of` was
`return self._ownership.get(tool_id)` and `beta` would have answered.

`installer/execute_screen.py:594-600` already carries the compensating shape (on
`None`, re-refresh that one tool and retry); the catalog has no equivalent.

**Fix:** two changes, both small.

```python
# installer/catalog_tui.py — on_tool_updated: an update invalidated the shared map,
# so every OTHER tool's record is now epoch-stale. Re-run the full pass rather than
# leaving the column blank until the user navigates away and back.
def on_tool_updated(self, message: ToolUpdated) -> None:
    ...
    if outcome is not None and outcome.status == "updated":
        self._start_version_refresh()
```

```python
# installer/catalog_tui.py — action_update_tool: never a silent return.
ownership = self._version_refresh.ownership_of(tool_id)
if ownership is None:
    self.status.set(
        f"cannot update {tool_id}: ownership data is being refreshed — try again in a moment",
        "warn",
    )
    return
```

### CR-03: the Uninstall "Installed via" cell renders the full hint and pushes "What gets removed" entirely off an 80-column terminal

**File:** `installer/wizard_app.py:675-677`
**Issue:**
D-03 asked for the *real manager* in the cell instead of the four-value enum. What
shipped puts `row.hint` **verbatim** into the cell — including the trailing
`— found at /abs/path` that `_managed_hint` appends (`installer/uninstall.py:220-221`)
and the `· required by a, b, c` suffix `classify_tools` appends
(`installer/uninstall.py:294-303`). The same string is already the row's `detail`
(`_tool_entry` passes `detail=row.hint`), so the cell is now a duplicate of the detail
bar, sized to the longest hint in the catalog.

Measured at the project's own minimum tested terminal size (80×24), with one removable
row carrying a `required by` suffix and one managed row carrying a linuxbrew cask hint
plus a `found at` path:

| column | width | starts at |
|---|---|---|
| Sel | 27 | 0 |
| Tool | 19 | 27 |
| Cat | 8 | 46 |
| **Installed via** | **126** | 54 |
| **What gets removed** | 29 | **180** |

viewport = 80, virtual = 209.

**Mutation-verified**: reverting `_tool_entry`'s `installed_via` to the pre-phase enum
and re-measuring the identical rows gives virtual = 100 with "What gets removed"
starting at x=71 — i.e. this change is what moved it from partly-visible to 100 columns
past the right edge.

The column is not merely truncated, it is **unreachable**:
`installer/tool_browser.py:103-104` binds `left`/`right` to view switching with
`priority=True`, so those keys never reach the `DataTable` for horizontal scrolling.
On a screen whose Enter key deletes files, the user cannot see what an entry will
remove.

**Relation to the Round-3 ledger (item 6):** `15.4-05-PLAN.md`'s Round-3 deferral
reads: *"Task 3 already instructs the executor to check the rendered width and, if the
removes column becomes unreadable at the minimum tested size, keep the full text in
`detail` and render a shortened form in the cell — recording whichever way it went in
the SUMMARY."* `15.4-05-SUMMARY.md` records only "renders `row.hint` verbatim"
(`:158`) — no width check, no decision. The deferral's acceptance condition was not
met, and the condition it guarded against is what shipped.

**Fix:** render a terse cell and keep the full sentence in `detail` — the same split
15.4-01/15.4-03 already established for the catalog (`OWNER_LABELS` for the ~12-char
cell, `OWNER_DETAIL_LABELS` for prose). Minimum change: strip the path/dependency
suffixes from the cell.

```python
# installer/wizard_app.py::_tool_entry
_CELL_MAX = 28
if row.state in (UninstallState.REMOVABLE, UninstallState.MANAGED):
    # The cell is a LABEL; the full sentence (manager + command + path +
    # "required by") stays in `detail`, which is where it already goes.
    head = row.hint.split(" — ")[0].split(" · ")[0]
    installed_via = head if len(head) <= _CELL_MAX else f"{head[: _CELL_MAX - 1]}…"
else:
    installed_via = "—"
```

Better: have `installer/ownership.py` expose a terse `removal_label(ownership)` beside
`removal_hint` and bind it through a second seam, so the Uninstall cell reads the same
declared register the Owner column does. Whichever is chosen, add a layout test at
(80, 24) asserting the "What gets removed" column's start offset is inside the
viewport — the existing `test_nine_column_table_mounts_and_renders_at_the_minimum_size`
deliberately asserts nothing about position and would not have caught this.

### WR-01: a same-session uninstall degrades the Uninstall screen's own attribution with nothing to restore it

**File:** `installer/wizard_app.py:1094-1108`, `setup.py:526`, `setup.py:414-443`
**Issue:**
`_apply_removal` calls `invalidate()` unconditionally after any successful sweep —
including a sweep that removed only the pip/npm ban or the PATH block and no tool at
all. The epoch bump makes `_uninstall_owner_hint`'s `ownership_of` answer `None` for
every tool, so the next `rows()` call degrades every managed row to the generic
platform-filtered registry phrase.

Nothing restores it from this screen. `OwnershipRefreshed` is posted only from
`CatalogScreen.on_version_status_refreshed`, and `UnifiedApp.on_ownership_refreshed`
only forwards it while `current_view == "uninstall"`. A user who goes
Uninstall → remove → Policies → Uninstall never visits a catalog tab and therefore
sees generic phrases for the rest of the session.

This partially defeats D-05's stated goal ("returning from any install/update/uninstall
run leaves both screens showing current data"). `tests/test_setup.py::
test_build_app_uninstall_hint_reverts_after_the_service_is_invalidated` pins the
degradation as intended behaviour but nothing pins the *recovery*.

**Fix:** have `_apply_removal` (or `UnifiedApp`) kick a refresh after invalidating, so
the invalidate is paired with the pass that replaces it — e.g. add an optional
`refresh: Callable[[], None]` seam to `UninstallInputs` bound in `setup.py` to a
thread-worker call of `version_refresh.refresh(tools)`, and have the completion post
`OwnershipRefreshed` the same way the catalog worker does. Alternatively, only
invalidate when the sweep actually removed a tool (`tool_count > 0`), which at least
removes the env-lever-only case.

### WR-02: the "atomic read" test cannot fail — the two-parallel-maps design it rejects still passes it

**File:** `tests/test_version_status.py::test_ownership_of_never_returns_a_record_paired_with_the_wrong_epoch`
**Issue:**
The test is named and documented as the proof for Round-3 HIGH #2 (the single
epoch-tagged map replacing two parallel maps, `version_status.py:392-405`). But its
`committed`/`invalidated`/`sampled` events **fully serialize** the writer and the
reader: the reader only samples after the writer has finished a commit and signalled,
and the writer only proceeds after the reader has signalled back. There is never a
window in which a read overlaps a write, so a torn read is structurally impossible to
observe — which is exactly the failure mode the map collapse exists to prevent.

**Mutation-verified:** I restored the rejected design (`self._ownership: dict[str,
ManagerOwnership]` plus a parallel `self._ownership_epoch: dict[str, int]`, with
`ownership_of` reading both) and ran the test:

```
tests/test_version_status.py -k "atomic or never_returns_a_record_paired"  ->  1 passed
```

The only thing in the suite that notices the revert is an incidental
`TypeError: cannot unpack non-iterable ManagerOwnership object` raised by a *different*
test's private-attribute assertion (`test_a_superseded_refresh_publishes_no_ownership_
over_a_newer_pass:1064`) — a shape accident, not a semantic guard.

So the invariant is currently protected by a private-attribute unpack, not by the test
that claims to protect it. The design itself is correct; the evidence for it is not.

**Fix:** either rename/redocument the test for what it actually covers (fail-closed
sequencing across commit/invalidate boundaries), or make it a real concurrency test:
drop the `sampled` handshake, let reader and writer run free for a bounded iteration
count, and assert the returned record's own identity matches what the current epoch
should hold. Add an explicit structural gate for the invariant that matters, e.g.:

```python
def test_service_holds_exactly_one_ownership_map() -> None:
    service = _installer_owned_service(...)
    epoch_maps = [
        name for name, value in vars(service).items()
        if name != "_ownership" and isinstance(value, dict)
        and all(isinstance(v, int) for v in value.values())
    ]
    assert epoch_maps == [], epoch_maps
```

### WR-03: the new Owner column pushes the catalog table past the 80-column minimum, and the shipped min-size test asserts nothing about it

**File:** `installer/catalog_tui.py:174-187`, `tests/test_catalog_tui.py:1897-1914`
**Issue:**
Measured at (80, 20) with the suite's own three-tool `_catalog()` fixture, the nine
columns total 84 rendered columns against an 80-wide viewport — already over budget
with short ids and no rendered Owner text. The real registry has ids up to
`jetbrains-toolbox` (17 chars), `Ver` cells like `1.2.3 -> 1.2.4 ~`, and Owner labels
up to `Homebrew cask` (13), all of which sit *before* `What it does`.

`test_nine_column_table_mounts_and_renders_at_the_minimum_size` deliberately asserts
only `len(table.columns) == 9` and `table.size.height >= 6`, with a docstring warning
future readers not to strengthen it. That reasoning is defensible for *character*
assertions, but it also means the phase shipped its headline visible column with no
check that it is on screen at the supported minimum — and, as CR-03 shows on the
sibling screen, `left`/`right` are taken by view switching so there is no horizontal
scroll to fall back on.

**Fix:** add a deterministic geometry assertion (not a rendered-text one) that the
Owner column's start offset plus its render width fits inside `table.size.width` at
(80, 20) over the real registry:

```python
offsets = {}
total = 0
for column in table.columns.values():
    offsets[column.label.plain] = total
    total += column.get_render_width(table)
assert offsets["Owner"] < table.size.width, offsets
```

If it does not fit, budget for it explicitly (e.g. drop `Cat` or shorten `For` at
narrow widths) rather than shipping an invisible column.

### WR-04: `_manager_hint`'s platform filter under-reports brew ownership for arch/min_os_version-gated methods, and the ownership seam cannot cover the same rows

**File:** `installer/uninstall.py:183-201`
**Issue:**
The Round-2 fix (scan `resolve_methods(tool, platform)` instead of `tool.methods`) is
correct for the codex/Linux-cask case it was written for, and its own docstring flags
the "tool declaring only a brew method on a host with no brew" narrowing as
intentional. But there is a second narrowing it does not name: `_applies`
(`installer/resolve.py:38-47`) also filters on `arch` and `min_os_version`. The
registry has three such rows today:

```
brew  os=['macos'] arch=['amd64']                 -> gnu-bash
brew  os=['macos'] arch=['arm64']                 -> gnu-bash
brew  os=['macos'] arch=['arm64'] min_os_version  -> container
```

On a macOS arm64 host below `container`'s `min_os_version` floor, a genuinely
brew-installed `container` now reports "managed outside this installer — remove with
your package manager" instead of `brew uninstall container`.

Critically, the ownership seam cannot rescue these rows either:
`resolve_ownership` builds candidates from the *same* `resolve_methods(tool, platform)`
list (`installer/ownership.py:462-465`), so the excluded brew method produces no
candidate, the record resolves to `unknown`, and `removal_hint` returns `None` — the
fallback is the only thing left. The `_ownership_only_methods` escape hatch built in
15.4-02 covers exactly one kind (`cask`) and is gated on `platform.os != "macos"`.

**Fix:** either add `brew` to `_OWNERSHIP_ONLY_KINDS` so an inventory-verified brew
formula can attribute regardless of the install-time arch/version gate (the same
argument 15.4-02 made for cask, and `_method_targets_platform` already mirrors all
three dimensions), or narrow `_manager_hint`'s filter to the `os` dimension only,
since `arch`/`min_os_version` bear on *installability*, not on whether a formula is
currently installed. Note the second option alone leaves the ownership-side gap open.

### WR-05: the test helper reintroduces the exact `list | Callable` union `UninstallInputs` documents as rejected, so the AST gate sees only 13 of ~45 sites

**File:** `tests/test_wizard_app.py:114-136`
**Issue:**
`UninstallInputs`'s docstring (`installer/wizard_app.py:82-88`) states the union was
rejected because it "would keep the stale-snapshot shape representable and
type-checkable forever, so the next construction site would get to reintroduce exactly
the bug this migration removes." `tests/test_wizard_app.py::_uninstall_inputs` then
declares:

```python
rows: list[ToolRow] | Callable[[], list[ToolRow]] | None = None
```

and normalises through `_predicate`. Roughly 30 call sites in that file still pass
frozen list literals. The `ALL-SITES-MIGRATED` AST gate greps for
`UninstallInputs(rows=[...])`, which these are not, so it does not see them.

The practical effect is coverage, not correctness: D-06's whole point is that the row
list must be re-read, and almost every `UninstallScreen` test still hands it a snapshot
that can never change. A regression that re-froze the rows (e.g. caching `_rows_of`'s
result) would be caught only by the handful of tests that pass a real live callable.

**Fix:** keep the helper's ergonomics but make the snapshot shape visibly a test-only
convenience, and add a gate that at least one `UninstallScreen` test drives a rows
predicate whose *return value changes between calls*:

```python
def _uninstall_inputs(*, rows: Callable[[], list[ToolRow]] = list, ...) -> UninstallInputs:
    ...
def _frozen(rows: list[ToolRow]) -> Callable[[], list[ToolRow]]:
    """TEST-ONLY: an explicitly frozen row list, for tests that are not about D-06."""
    return lambda: rows
```

so a reader can see at the call site which tests deliberately opt out of the live
behaviour.

## Info

### IN-01: `_OS_PACKAGE_DETAIL` can interpolate the literal string `None`

**File:** `installer/update.py:118-121`, `:265-266`
**Issue:** `_OS_PACKAGE_DETAIL.format(package=ownership.package)` has no `None` guard,
so an `os-package` record with `package=None` renders "an OS package (None) provides
this tool". `_os_package_owner` guarantees a non-`None` package in production, but the
sibling code that formats the same field — `removal_hint`
(`installer/ownership.py:1177-1184`) and `owner_detail` (`:1052-1054`) — both guard it
explicitly and document why. The inconsistency is the finding.
**Fix:** `package = ownership.package or "an unnamed package"` before the `.format`,
matching `owner_detail`'s existing wording.

### IN-02: `removal_hint`'s `prefix` is typed `str | None` and would render "managed by None"

**File:** `installer/ownership.py:1168-1176`
**Issue:** `label = owner_label(ownership)` is `str | None`; `prefix` inherits that and
is interpolated into an f-string. It is unreachable today (`owner_label` returns `None`
only for `unknown`, which `_NO_REMOVAL_HINT` already returned for), but the invariant
is implicit across two functions rather than expressed at the use site.
**Fix:** `prefix = "Homebrew" if owner in _LABEL_AGREEMENT_EXEMPT else (label or owner)`
— cheap, and makes pyright's narrowing match the documented contract.

### IN-03: a committed refresh can go unannounced when an invalidate lands inside the worker's epoch-sampling window

**File:** `installer/catalog_tui.py:394-419`
**Issue:** `_refresh_versions_worker` samples `epoch = service.epoch` (`:400`) *before*
`service.refresh()` reads its own `started_epoch` (`version_status.py:545`). An
`invalidate` landing between those two reads makes `refresh` commit correctly under the
new epoch while the posted message still carries the old one, so
`on_version_status_refreshed`'s `message.epoch != service.epoch` guard (`:412`) discards
a pass that actually committed. `_version_statuses` keeps its old values and — since
`OwnershipRefreshed` is posted only past that guard — no consumer learns the map changed.
Self-heals on the next catalog entry; the window is narrow.
**Fix:** have `refresh` return (or expose) the epoch it actually committed under, and
post that, rather than the worker's independently-sampled one:

```python
result, _error = run_live(lambda: service.refresh(self.tools))
epoch = service.epoch  # sample AFTER the pass, not before
```
