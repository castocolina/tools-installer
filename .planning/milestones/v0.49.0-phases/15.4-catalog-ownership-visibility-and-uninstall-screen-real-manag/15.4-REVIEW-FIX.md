### CR-01: `_resync`'s rows-failure branch calls three filesystem predicates unguarded

**Files modified:** `installer/wizard_app.py`, `tests/test_wizard_app.py`
**Commit:** `5e5357f`

**Applied fix.** The three environment predicates are extracted into one
`_env_state()` seam, and BOTH call sites now evaluate it through `run_live`:

- `_resync`'s failure branch retries `_env_state` through a second `run_live`,
  keeps the last known values when that also fails, and reports both messages
  together. The load-bearing false comment ("cheap, non-failing in-memory
  reads (Round-3 review's accepted scope -- only rows touches the
  filesystem)") is deleted and replaced with what is actually true: all three
  read the same `$HOME` the rows predicate does, so they fail *correlated*
  with it, which is precisely why routing them bare inside the branch that
  handles a filesystem fault was wrong.
- `__init__` gets the same treatment. The review listed this as "consider";
  it had the identical unguarded shape and took `_build_app` down on a raising
  predicate, so it is fixed rather than deferred. `_rows_error` becomes
  `_startup_error` since it now stashes either construction-time failure, and
  the one-time status reads "Could not read the uninstall state at startup".

**Mutation verification.** Reverting both call sites to bare calls fails all
three new tests:
`test_uninstall_construction_survives_a_raising_environment_predicate`,
`test_env_predicate_failure_inside_the_rows_failure_branch_never_escapes_nav`
(which asserts the app is still on `uninstall` and both messages reached the
status line), and
`test_env_predicate_failure_during_a_background_repaint_never_escapes`
(the `ownership_refreshed()` path the user never initiated).

### CR-02: one in-catalog update blanks the whole Owner column and makes `u` a silent no-op

**Files modified:** `installer/catalog_tui.py`, `tests/test_catalog_tui.py`
**Commit:** `a0a886f`

**Applied fix.** Three changes, the first two as the review prescribed and the
third to close the window they leave open:

1. `on_tool_updated` kicks `_start_version_refresh()` on a successful update —
   the full pass that replaces the `invalidate` the update performed, rather
   than leaving every untouched tool's record epoch-stale until the user
   navigates away and back.
2. `action_update_tool` reports `cannot update {id}: ownership data is being
   refreshed — try again in a moment` instead of the bare `return`.
3. `_owner_cell` renders `checking…` while `version_refreshing` is set.
   Without this the column is still blank for the duration of the replacing
   pass, and D-02 reserves blank for "genuinely don't know". The label is
   `_ver_cell`'s own `_VER_CHECKING`, already decoded by `_LEGEND`, so this
   needs no legend budget — which the legend's own comment block has none of.

On the prompt's alternative framing ("scope the epoch bump to just the
invalidated tool(s)"): that was considered and rejected. The epoch is what
makes `refresh`'s raced branch discard a superseded pass (Round-3 HIGH #1) and
what `invalidate` uses to drop the shared manager snapshot; making it
per-tool would re-open that race for a display-only benefit. The chosen fix
keeps the fail-closed epoch and pairs the invalidate with its replacing pass —
the same shape `installer/execute_screen.py:594-600` already carries.

**Mutation verification.** Reverting all three fails
`test_owner_column_says_checking_while_a_pass_is_in_flight`,
`test_action_update_tool_reports_an_in_flight_refresh_instead_of_a_silent_noop`,
and the end-to-end
`test_an_in_catalog_update_restores_the_whole_owner_column` (two tools, a
real `u` press through the real worker and `UpdateService.run` with
`invalidate` wired as setup.py wires it; the untouched tool's
`ownership_of` goes back to `None` without the fix).
`test_a_single_tool_refresh_after_invalidate_strands_every_other_record` pins
the service-level map state so that end-to-end test is provably exercising a
real condition.

### WR-01: a same-session uninstall degrades attribution with nothing to restore it

**Files modified:** `installer/wizard_app.py`, `setup.py`,
`tests/test_wizard_app.py`, `tests/test_setup.py`
**Commit:** `45e00b6`

**Applied fix.** Both arms the review offered, not just the cheap one:

- The `invalidate` is gated on `tool_count`. A sweep that removed only the
  pip/npm ban or the PATH block changes nothing any ownership record
  describes, so bumping the epoch for it was a pure loss. The invariant
  `version_status.py` states is "every MUTATION calls invalidate"; an
  env-lever sweep is not a mutation of tool ownership.
- `UninstallInputs.refresh` is the replacing pass, bound in setup.py to the
  same `VersionRefreshService` the catalog's worker uses and run by
  `_apply_removal` on a thread worker (`_refresh_ownership_worker`, blocking:
  it re-probes every manager). On commit it posts `OwnershipRefreshed`,
  exactly as `CatalogScreen` does, so the repaint travels the one path that
  already exists — and via `clear_applied=False`, so it never wipes the
  sentence describing the removal the user just performed. Failure is
  deliberately silent: the honest degraded phrase is the fallback, and a
  second error line about a background repaint would bury the result the user
  is reading.

The seam is optional; the `--uninstall` direct start builds no version service
and leaves it `None`, which behaves exactly as before.

**Mutation verification.** Removing the `tool_count` gate fails
`test_an_env_lever_only_sweep_does_not_invalidate_ownership`; removing the
worker call fails
`test_a_same_session_removal_refreshes_the_attribution_its_invalidate_dropped`
(which also asserts the applied summary survives the repaint); removing the
setup.py binding fails
`test_build_app_wires_a_refresh_seam_that_restores_the_invalidated_hint`,
written as the recovery arm of the existing
`test_build_app_uninstall_hint_reverts_after_the_service_is_invalidated`.
`test_a_removal_with_no_refresh_seam_still_completes` pins the optional case.

### WR-02: the "atomic read" test cannot fail

**Files modified:** `tests/test_version_status.py`
**Commit:** `d4e9b2c`

**Applied fix.** All three of the review's suggestions, because they cover
different things:

- Renamed to
  `test_ownership_of_answers_fail_closed_across_commit_and_invalidate_boundaries`
  and redocumented. The property it actually proves — fail-closed sequencing
  across both boundaries — is real and worth keeping; the "atomic read" claim
  it could never have supported is gone, along with the reason it could not
  (its events fully serialize reader and writer).
- `test_the_service_holds_one_epoch_tagged_ownership_map_not_two` is the new
  DETERMINISTIC gate. The invariant is a property of the data structure — one
  key lookup returns both halves of the pair or neither — so it is asserted as
  one: every value in `_ownership` is an `(int, ManagerOwnership)` pair, and
  no other attribute is a dict covering the same tool ids with `int` values.
- `test_ownership_of_under_an_unsynchronized_reader_never_serves_a_superseded_record`
  runs the same reader/writer pair with the handshake removed, so reads
  genuinely overlap writes. With the epoch sampled either side of a call and
  unchanged, a non-`None` answer must be the record that epoch's own pass
  committed. It carries a `time.sleep(0)` GIL yield (not a wall-clock sleep):
  without one the writer runs commit→invalidate as one uninterrupted stretch
  and the reader is never scheduled inside the committed window at all.

The stress test is documented as probabilistic — the window is two adjacent
dict writes, so a passing run is not proof — and as never able to fail
spuriously, since every branch is guarded on information the reader
established itself. The deterministic proof is the structural gate.

**Mutation verification.** The reviewer's exact revert (a plain
`dict[str, ManagerOwnership]` plus a parallel `dict[str, int]`, with
`ownership_of` reading both) now FAILS
`test_the_service_holds_one_epoch_tagged_ownership_map_not_two`. The gate's
second clause (a redundant epoch map added alongside a correct tuple map) was
exercised separately and fires. The two timing tests were run 8x for
flakiness; all passed.

### WR-04: `_manager_hint` under-reports brew ownership for arch/min_os_version-gated methods

**Files modified:** `installer/ownership.py`, `installer/uninstall.py`,
`tests/test_ownership.py`
**Commit:** `a9a3913`

**Applied fix.** The review's first option (the ownership side), which it notes
is the only one that closes the gap — the second "leaves the ownership-side
gap open". Implementing it required the per-kind declaration the table was
already shaped for:

- `_OWNERSHIP_ONLY_KINDS` gains a `brew` row declaring `("os",)` — the
  dimensions it MIRRORS — so `arch`/`min_os_version` are a declared bypass,
  not an accident. Those two bear on installability; this module answers what
  owns the installed copy. The `os` dimension is still mirrored, so a
  macOS-only formula is never evidence of anything on Linux.
- `_method_targets_platform` takes the dimension subset to check, defaulting to
  all three so the existing `resolve._applies` parity gate still compares like
  with like.
- `_ownership_only_methods`' blanket `platform.os == "macos"` gate is replaced
  by the thing it was a proxy for: excluding, by identity, any method
  `resolve_methods` already returned. That was the gate's stated purpose
  ("`_collect_candidates` would see the same cask method twice"), and the
  proxy also excluded macOS wholesale — which is exactly where the brew bypass
  has to work. The cask verdict is unchanged on every platform.

The widening stays evidence-gated: a candidate produced here must still be
confirmed by the real `brew list --versions` inventory before it becomes
ownership. `_manager_hint` is deliberately left as the narrower of the two,
per its own docstring's rule that a registry-only guess must be narrower than
an inventory-backed attribution; its docstring now names the second narrowing
and points at the seam that covers it.

**Mutation verification.** Removing the `brew` row fails
`test_brew_ownership_survives_an_unmet_min_os_version_gate` (the registry's
real `container` shape on a macOS arm64 host below its floor: `resolve_methods`
returns `[]`, and ownership resolves `brew` / `brew uninstall container`
instead of `unknown`) and
`test_ownership_only_kinds_declaration_matches_helper_reach`. Three further
tests pin the boundaries: the widening produces nothing when the inventory
does not claim the formula, the `os` dimension is still mirrored, and a method
already returned by `resolve_methods` is never repeated.
