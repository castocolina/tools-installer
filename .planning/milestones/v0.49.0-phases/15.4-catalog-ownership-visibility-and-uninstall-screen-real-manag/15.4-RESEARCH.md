### Locked Decisions

**Main catalog: Owner column**
- **D-01:** Add a visible "Owner" column to the main catalog table (`_COLUMNS`/
  `_row_cells` in `catalog_tui.py`), reading the same ownership data
  `_version_detail` (`catalog_tui.py:385-429`) already computes via
  `service.ownership_of(tool.id)` — no new data plumbing, only a new rendered cell.
  — **Reversibility:** reversible.

  **Correction (2026-09-16, live UAT finding during Phase 15.1 closure — READ BEFORE
  PLANNING):** D-01's "no new data plumbing" premise is disproven on this real host.
  Live investigation (subagent, this session) confirmed `service.ownership_of()` /
  `resolve_ownership` genuinely returns `owner='unknown'` today for at least two real,
  legitimately-owned tools:
  - **git** — OS base-image RPM (`/usr/bin/git`, `rpm -qf` confirms `git-core-...`),
    not in the booted deployment's `requested-packages` (only explicitly-layered
    packages are tracked by `_rpm_ostree`, `installer/install_ownership.py:130-170`
    — a base-image package is invisible to it by design). **No "OS base image" owner
    concept exists in the current model at all.**
  - **jetbrains-toolbox** — installed via linuxbrew cask (`jetbrains-toolbox-linux`),
    but `installer/registry.toml`'s `cask` method for this tool is gated
    `os = ["macos"]` (dropped on Linux), AND the declared cask name
    (`jetbrains-toolbox`) doesn't match the actual installed cask name
    (`jetbrains-toolbox-linux`) — a registry data gap, not just a resolver gap.
  Implementing D-01 as originally locked (render whatever `ownership_of()` already
  returns) would ship an Owner column reading "unknown" for exactly the cases D-02's
  governing principle ("blank should only ever mean genuinely don't know") forbids
  treating as acceptable. **This phase's planning MUST include:** (a) a base-image/OS
  owner resolution path for immutable hosts (e.g. `rpm -qf <active_path>` against the
  live filesystem, independent of `_rpm_ostree`'s layered-only evidence — note
  `install_ownership.py:178`'s `_rpm_owns_path` already exists and may be reusable),
  and (b) a Linux-cask registry/path-attribution fix (the `jetbrains-toolbox-linux`
  naming mismatch, and casks not being categorically unmodeled on Linux). This is new
  resolver/registry work, not "just a rendered cell" — budget planning accordingly.

- **D-02:** Display rule: show an explicit label whenever the owner is knowable —
  including `dnf`/`apt`/`pacman`/`rpm-ostree`/`brew`/`cask`/`pnpm`/`uv` — regardless of
  whether the tool was originally installed through this app or found already present
  on the machine. Only genuinely `unknown`/not-yet-installed rows show blank/dash.
  — **Reversibility:** reversible.
  **Rationale (user, verbatim intent):** "todo lo que está en el catalog debería ser
  rastreable porque si está aquí es porque es importante para el usuario" — everything
  in the catalog should be traceable; a blank cell should only ever mean "genuinely
  don't know," never "didn't bother labeling this case."
  **Correction note:** per D-01's correction above, "knowable" must now be read as
  requiring the base-image-owner and Linux-cask fixes to actually exist — otherwise
  git/OS-package tools and Linux-cask tools stay incorrectly "unknown" and this
  decision's own principle is violated in practice, not just in wording.

- **D-02a (revision, same session):** When `owner == "installer"` — i.e. this app
  placed the artifact directly with no package manager mediating (e.g. a
  `github_release` binary drop or a `curl|sh` script) — do NOT render the bare word
  "installer" as if it were a manager peer to dnf/brew/pnpm. Instead render the actual
  placement mechanism (e.g. "github release" / "script") so the label is genuinely
  informative rather than a vague catch-all that implies a real package manager exists
  behind it. — **Reversibility:** reversible.
  **Rationale (user, verbatim):** "al final esta tools es un forwarder, no es que
  mantenga su propia BD o manage de tools, así que si es el mismo campo para decir
  this|others[dnf,pacman,pnpm] realmente no me sirve de nada" — a same-field
  this-app-vs-everyone-else label carries no actionable information given this app is
  not itself a package manager. Confirmed this does NOT require new persisted state:
  ownership resolution (`installer/ownership.py:1-37`) — including the `"installer"`
  case — is already computed live from the active binary path each refresh, so
  attaching the concrete method-kind label at render time introduces no new staleness
  surface beyond what D-05 already fixes for the owner value itself.

**Uninstall screen: real manager attribution**
- **D-03:** `UninstallScreen`'s "Installed via" table cell (`wizard_app.py`'s
  `_tool_entry`, currently a static 4-value `UninstallState`-keyed dict) must derive
  from the real per-tool hint — the same rich string `uninstall.py`'s `_manager_hint`/
  `_managed_hint` already compute into `ToolRow.hint` (today only reaching the
  focused-row detail bar via `detail=row.hint`), not a generic enum-keyed string.
  — **Reversibility:** reversible.

- **D-04:** `uninstall.py`'s manager detection (`_manager_hint`, currently checks only
  `method.kind in {"cask", "brew"}`) must be wired to the fuller ownership resolution
  already proven for the catalog — reuse `installer/ownership.py`'s
  `resolve_ownership`/the `install_ownership.py`/`ownership.py` machinery, so
  pnpm/volta/sdkman/uv/dnf/apt/pacman/rpm-ostree-owned tools get a real, specific
  manager name instead of the generic "managed outside this installer" fallback.
  — **Reversibility:** reversible.

**Ownership data source and freshness**
- **D-05:** Uninstall reuses the catalog's already-computed ownership map (not a
  fresh, duplicate probe on every Uninstall-screen open) — for speed. **But this must
  not repeat Phase 15.1's staleness bug**: the ownership data feeding both the Owner
  column (D-01) and the Uninstall attribution (D-03/D-04) must be refreshed on the
  same trigger Phase 15.1's D-01 established (the `ExecuteScreen`-close callback in
  `wizard_app.py`), so returning from any install/update/uninstall run leaves both
  screens showing current data, not a stale snapshot from before the run.
  — **Reversibility:** reversible — the reuse-vs-fresh-probe choice is a local
  wiring decision, not a data-model commitment.
  **Rationale (user):** explicitly required — "que no caigamos en el mismo problema
  del stale una vez que se instala/desinstala y volvamos al catalog o uninstall."

**Uninstall screen row-list staleness (scope addition, user-approved)**
- **D-06:** `UninstallScreen._rows` (`wizard_app.py:600`, set once from
  `inputs.rows` at app construction, from `setup.py:408`'s one-time `classify_tools`
  call) must be re-derived — not just the environment rows (`_ban_names`,
  `_has_path_block`, `_tweak_ids`) that `enter_view()` (`wizard_app.py:773-791`)
  already re-checks on every entry — whenever the underlying install state could have
  changed. In scope for THIS phase (explicit user decision, not deferred): an install
  performed elsewhere in the session must make a newly-installed tool appear in
  Uninstall, and a tool's ownership label must reflect its current real state, the
  next time the Uninstall screen is entered. — **Reversibility:** reversible.
  **Rationale (user):** same domain (UninstallScreen), same refresh trigger being
  touched for D-05 — fixing it now avoids a second UAT round-trip on the same screen
  later.

## Summary

This phase closes two visibility gaps that both boil down to the same root cause:
ownership data the installer already half-computes is either not rendered
(catalog table) or rendered from a stale/weaker source (Uninstall screen), and
in two concrete real-machine cases the *underlying resolver itself* returns
`unknown` for a tool that is genuinely, verifiably owned by something. This is
not a pure UI phase — `15.4-CONTEXT.md`'s dated correction (2026-09-16) is
authoritative and re-scopes D-01 from "render an existing value" to "fix two
resolver/registry gaps, then render the value."

This session independently re-verified both CONTEXT.md findings live on this
host: `rpm -qf --qf '%{NAME}\n' /usr/bin/git` returns `git-core`
`[VERIFIED: live command, this session]`, which is absent from
`rpm-ostree status --json`'s booted `requested-packages`
(`['amdgpu_top', 'coolercontrol', 'liquidctl', 'podman-compose']`)
`[VERIFIED: live command, this session]` — confirming `_rpm_ostree`
(`installer/install_ownership.py:130-175`) cannot and structurally will never
attribute a base-image package. Separately, `brew list --cask` on this host
lists the cask as `jetbrains-toolbox-linux`
`[VERIFIED: live command, this session]`, while `installer/registry.toml:2162-2166`
declares `cask = "jetbrains-toolbox"` gated `os = ["macos"]`
`[VERIFIED: installer/registry.toml:2162-2166]` — so even fixing the name would
not help, because `installer/resolve.py:67-69`'s `_applies` function hardcodes
`return platform.os == "macos" and platform.has_brew` for the `cask` kind
`[VERIFIED: installer/resolve.py:66-69]`, categorically excluding every cask
method from `resolve_methods`'s output on Linux regardless of the method's own
declared `os` list. `ownership.py`'s candidate collection (`_collect_candidates`,
`competing_owners`) only ever looks at `resolve_methods`'s output
(`installer/ownership.py:340, 319-327`), so a Linux cask is invisible to
ownership resolution twice over: once by the categorical `_applies` gate, once
by the declared-vs-actual name mismatch.

On the Uninstall side, the fix is more mechanical: `uninstall.py`'s
`_manager_hint` (`:137-145`) already computes a rich string but only for
brew/cask methods, falling back to a generic "managed outside this installer"
line for every dnf/apt/pacman/pnpm/uv/sdkman-owned tool — confirmed by the
existing test `test_classify_managed_generic_hint_when_no_brew_method`
(`tests/test_uninstall.py:383-395`) `[VERIFIED: tests/test_uninstall.py:383-395]`.
`ToolRow.hint` already reaches the screen (`wizard_app.py:625-656`'s
`_tool_entry` reads `row.hint` into `detail=`, `:568` shows `installed_via` is
built from a static 4-value dict instead) but the table CELL discards it. And
`UninstallScreen._rows` is a plain list frozen at `__init__` (`:600`), never
touched by `enter_view()` (`:773-799`, which only re-derives the three
environment predicates), so a tool installed elsewhere in the session never
appears, and a tool's Uninstall-screen manager label never updates, until the
whole app restarts.

**Primary recommendation:** Split this phase's work into two layers that can
be planned and tested independently: (1) a resolver/registry layer — extend
`install_ownership.py`/`ownership.py` with a base-image-owner evidence source
gated on `platform.immutable` and a Linux-cask evidence path independent of
`resolve_methods`'s categorical macOS-only gate, both fail-closed exactly like
every existing probe in that module; (2) a rendering/plumbing layer — add the
Owner column to `catalog_tui.py`, replace `UninstallScreen`'s static
`installed_via` dict with `row.hint`, wire `uninstall.py`'s hint builder to
`resolve_ownership`, and extend `UninstallInputs`/`enter_view()` with a fourth
re-derivable predicate for `rows` (mirroring the existing `ban_names`/
`has_path_block`/`tweak_ids` pattern at `wizard_app.py:69-76`), triggered from
the same `_install_closed` (`:1844-1930`) callback Phase 15.1 already
extended for the catalog's `set_installed`.

### Pattern 1: Reuse `resolve_ownership`, never re-implement a probe

`installer/ownership.py`'s own module docstring states the governing rule
explicitly: `[VERIFIED: installer/ownership.py:13-20]`

```python
# Source: installer/ownership.py:13-20
# Phase 15 (D-05) closes that gap with an ADAPTER, not a native probe:
# `_native_owner` below calls `install_ownership.detect_owner` -- which
# already has working `apt`/`dnf`/`pacman`/`rpm-ostree` probes of its own --
# and maps its `"verified"` confidence to this module's `"direct"`.
```

D-04 explicitly names this same rule for `uninstall.py`: wire it to
`resolve_ownership`, do not write a second brew/dnf/pnpm-probing function
inside `uninstall.py`. `.claude/architecture.md` rule 5 (cited at
`installer/ownership.py:45-46`) forbids the duplicate.

**When to use:** any time `uninstall.py`'s `_manager_hint`/`_managed_hint`
need a manager name beyond brew/cask.

**What it needs (the call shape D-05 asks the planner to follow), already
proven at `installer/version_status.py:521-529`
`[VERIFIED: installer/version_status.py:520-529]`:**
```python
# Source: installer/version_status.py:520-529
ownership = resolve_ownership(
    tool,
    platform=self._platform,
    inventory=inventory,
    artifacts=self._artifacts(tool),
    which=self._which,
    managed_bin_dir=self._managed_bin_dir,
    native_probe=self._native_probe,
)
```
Note `inventory` (a `ManagerInventory` — one `read_inventory(has_brew=...)`
call per refresh pass, not per tool) and `native_probe` (a `ProbeRunner`,
`installer.install_ownership.run_probe` in production, `None` in every test
construction — `installer/version_status.py:378-385`'s own comment explains
why: a real default would put `rpm -q`/`dpkg-query`/`pacman -Qq`/
`rpm-ostree status` subprocess calls inside every unit test that builds this
service, which `.claude/testing.md` forbids). `setup.py:574-583` is the one
production call site wiring the real `run_probe` in
`[VERIFIED: setup.py:574-583]`.

### Pattern 2: One coordination point for cross-screen freshness

Phase 15.1 established `UnifiedApp._install_closed` (`wizard_app.py:1844-1930`)
as the single place that re-derives another screen's snapshot of install state
after a run closes. `[VERIFIED: installer/wizard_app.py:1844-1930]` Its own
extensive inline comment block documents WHY it re-derives against
`self._catalog_tools` (the whole catalog, not the active tier) and why the map
is a plain replacement (`screen.set_installed(fresh)`), never a merge.

Today `_install_closed` only touches `self._catalogs` (the three tier
screens) — `active = self._catalogs.get(self.current_view)` returns `None`
for `"uninstall"`/`"doctor"`/`"policies"`, so nothing in `_install_closed`
currently reaches `UninstallScreen` directly. This is not itself a bug: an
install run can only be *launched* from a catalog tier (`ExecuteScreen` is
only ever pushed from `on_catalog_screen_decided`, `wizard_app.py:1841-1842`,
which only fires on `CatalogScreen.Decided`), so `current_view` at
`_install_closed` time is always a tier, never `"uninstall"`.

The natural extension point for D-06 is therefore `show_view`
(`wizard_app.py:...`, the single nav path per `.claude/architecture.md` rule
2), which already calls `entering.enter_view()` on every transition INTO a
screen, including Uninstall — `UninstallScreen.enter_view()` (`:773-799`)
already exists and already re-derives the three environment predicates on
every entry; it simply does not yet re-derive `_rows`. Two implementation
shapes both satisfy D-06 and match the "Claude's Discretion" note in
CONTEXT.md:

1. **Cheap, matches the existing predicate shape exactly:** add a fourth
   predicate to `UninstallInputs` (e.g. `rows: Callable[[], list[ToolRow]]`,
   mirroring `ban_names`/`has_path_block`/`tweak_ids` at
   `wizard_app.py:69-76`), call it inside `enter_view()`'s existing
   `_live_state()` tuple comparison (`:786-791`), and rebuild `_entries`/
   `_by_key` only when it actually changed — exactly the pattern already
   proven for the other three rows.
2. **Dirty-flag variant:** `_install_closed` sets a `self._uninstall_dirty =
   True` flag (or bumps an epoch) instead of calling anything on
   `UninstallScreen` directly; `enter_view()` checks the flag and only then
   re-runs `classify_tools`.

Both require `classify_tools` to be re-callable with a FRESH `installed: dict`
(re-reading `is_installed(tool)` per catalog tool, mirroring what
`_install_closed` already does at `wizard_app.py:1901-1904` for the catalog
maps) — `setup.py:408-414`'s one-time call
`[VERIFIED: setup.py:407-414]` is the template to turn into a closure.

### Anti-Patterns to Avoid
- **A second brew/dnf/pnpm subprocess-probing function inside `uninstall.py`:**
  `resolve_ownership`/`detect_owner` already exist and are extensively tested
  (`tests/test_ownership.py` has 892 lines, `tests/test_install_ownership.py`
  514 — including 9 tests specifically for the native-owner adapter's
  precedence/immutable-host rules). Re-deriving manager names inside
  `uninstall.py` from `tool.methods` directly (as `_manager_hint` does today
  for brew/cask only) is exactly the pattern D-04 asks to retire, not extend
  to more managers.
- **Fixing only the registry cask name for jetbrains-toolbox:** confirmed
  live and by reading `resolve.py:66-69` — even a perfectly-named
  `cask = "jetbrains-toolbox-linux"` method row would never reach
  `_collect_candidates` on Linux, because `resolve_methods` drops every
  `cask` method before ownership code ever sees it. A registry-only fix is
  necessary but not sufficient; see Common Pitfall #2.
- **A per-tool registry field for the base-image probe's target package
  name:** `_rpm_ostree`'s own docstring already rejected this shape for the
  layered-package case ("inventing a second registry field for the same

## Common Pitfalls

### Pitfall 1: A base-image probe that requires knowing the package name in advance can't work for `git`
**What goes wrong:** The obvious first instinct is to reuse
`install_ownership.py:178`'s existing `_rpm_owns_path(package, path, probe)`
verbatim — it already does "does `rpm -qf <path>` say `<package>` owns it".
But `git`'s registry entry declares `package = "git"` for its `dnf` method
(`registry.toml:268-269` `[VERIFIED: installer/registry.toml:267-269]`), while
the RPM database's real answer is `git-core`
`[VERIFIED: live command, this session — rpm -qf --qf '%{NAME}\n' /usr/bin/git
→ git-core]`. `_rpm_owns_path`'s exact-match contract (`package in
_lines(output)`) would return `False` for git even after this fix — the
"declared name" and "actual RPM package name" are genuinely different
strings for split packages like git/git-core, and there is no reliable way to
know that mapping ahead of time from the registry's `dnf` method alone.
**Why it happens:** `_rpm_owns_path` was designed for `package_owns_path`'s
use case — CONFIRMING a specific candidate (found via a name match in some
inventory) actually owns the live path — not for DISCOVERING an unknown
owner from a path with no prior candidate.
**How to avoid:** A base-image probe needs the inverse query shape: ask "what
package owns this path" (no expected name), accept whatever name comes back,
and attribute a new owner category (e.g. an "OS package"/base-image Owner
value) from that answer directly — never gated on matching the `dnf` method's
declared `package` string. This is a genuinely new function, not a call to
the existing `_rpm_owns_path`.
**Warning signs:** A test asserting `git` resolves to a NATIVE `dnf`-family
owner using package name `"git"` specifically will fail against the real rpm
database; any implementation that string-compares against the registry's
declared `package` param for this new base-image path is repeating this bug.

### Pitfall 2: Linux-cask ownership is blocked at TWO independent layers, not one
**What goes wrong:** Fixing only `registry.toml`'s cask name
(`jetbrains-toolbox` → `jetbrains-toolbox-linux`, gated for Linux) looks like
a complete registry-data fix but changes nothing, because
`resolve.py:66-69`'s `_applies` function for `kind == "cask"` is:
```python
# Source: installer/resolve.py:66-69 — verbatim, this is the WHOLE branch
if kind == "cask":
    # Casks are a macOS-only brew concept; --appdir keeps them in ~/Applications.
    return platform.os == "macos" and platform.has_brew
```
`[VERIFIED: installer/resolve.py:66-69]` This unconditionally excludes EVERY
cask method on Linux, regardless of that method's own declared `os` field.
`ownership.py::resolve_ownership` calls `resolve_methods(tool, platform)`
FIRST (`ownership.py:340`) and only ever builds candidates
(`_collect_candidates`) and competing-owner sets (`competing_owners`) from
that filtered, already-macOS-only list (`ownership.py:319-327`,
`:510-524`). So a Linux cask method is invisible to ownership resolution
before the name-mismatch question is even reached.
**Why it happens:** `resolve_methods` answers "what could this INSTALLER
install here" (a deliberate, documented macOS-only restriction — casks are a
genuine macOS-brew concept per the comment above), while ownership needs to
answer a different question — "does something ALREADY own this" — and this
phase is the first time those two questions have needed different answers
for the same method kind.
**How to avoid:** This is a design fork the planner must choose explicitly,
not one research can resolve on its own:
  - **(a)** Add a SECOND, Linux-gated `cask` method row to jetbrains-toolbox's
    registry entry (`cask = "jetbrains-toolbox-linux"`, `os =
    ["debian","fedora","arch"]`) AND loosen `resolve.py`'s cask `_applies`
    branch to also return true when `platform.has_brew` regardless of OS —
    this changes INSTALL behavior too (the installer would now offer to
    `brew install --cask` on Linux), which may be an intentional, welcome
    side effect (linuxbrew genuinely supports a subset of casks) or an
    unwanted scope expansion.
  - **(b)** Build an ownership-ONLY evidence path in `ownership.py` that
    checks `inventory.brew_casks` for a per-tool Linux-cask name WITHOUT
    going through `resolve_methods`/`_applies` at all — narrower blast
    radius (install behavior on Linux is untouched), but is a second
    "declare a method-like fact but only for ownership" shape alongside the
    existing `owner_probes` registry field, worth checking against
    `.claude/architecture.md`'s "one X per Y" rules before choosing.
**Warning signs:** A plan that only touches `registry.toml` for this tool and
calls D-01's jetbrains-toolbox case closed; a plan that touches `resolve.py`
without an explicit note about the INSTALL-behavior side effect on Linux.

### Pitfall 3: `uninstall.py`'s hint builder has no access to `platform`/`inventory`/`native_probe` today
**What goes wrong:** `_manager_hint(tool)` (`uninstall.py:137-145`) and
`classify_tools` (`:169-223`) currently take only `tool`, `default_bin_dir`,
`installed`, `platform`, and `which` — no `ManagerInventory`, no
`ProbeRunner`. Wiring D-04 means either threading those two new params all
the way from `setup.py` into `classify_tools`/`_managed_hint`, or having
`classify_tools`'s caller (`setup.py` and, per D-06, `UninstallScreen`'s
re-derivation predicate) call `resolve_ownership` itself and pass the
resulting `ManagerOwnership` INTO `classify_tools`/`ToolRow` construction
rather than having `classify_tools` compute it internally.
**Why it happens:** `classify_tools` predates the native-owner work (Phase
15's D-05/D-06); its signature was never updated for the richer resolver.
**How to avoid:** Per D-05, do not have `uninstall.py` build its own
`ManagerInventory`/run its own native probes — reuse the SAME
`VersionRefreshService`-computed `ownership_of(tool.id)` map the catalog
already populates (see Pattern 1/2), passed in as a lookup callable, so
`classify_tools`/`_managed_hint` become consumers of an already-resolved
`ManagerOwnership` rather than a second resolution path.
**Warning signs:** A plan that adds `native_probe`/`inventory` parameters
directly to `classify_tools`'s signature and has it call
`resolve_ownership` itself — this duplicates the resolution pass the catalog
already ran this session and reintroduces exactly the "fresh probe on every
Uninstall open" cost D-05 explicitly rejects for speed.

### Pitfall 4: `UninstallState`'s 4-value model doesn't have a slot for "removable but also has a known other owner"
**What goes wrong:** `_tool_entry`'s `installed_via` dict
(`wizard_app.py:625-634`) is keyed by `UninstallState`
(`REMOVABLE`/`MANAGED`/`ABSENT`/`UNAVAILABLE`), a 4-value enum. D-03 asks for
`row.hint` (a free-text string) to REPLACE this dict's output for the "via"
cell — that is a strictly richer replacement for `MANAGED` rows (where
`_managed_hint` already builds a real manager name + path), but for
`REMOVABLE` rows `row.hint` is currently always the fixed string "installed
in userspace — removable here" (`uninstall.py:197`), which conveys nothing a
"userspace" label didn't already say. This is fine (D-03 does not ask for
`REMOVABLE`-row wording to change), but a naive full-string swap must not
accidentally regress the `REMOVABLE` case to something less informative, and
must keep `removes` (the "What gets removed" cell, separately built at
`_tool_entry:635-643`) unaffected — only the `installed_via` cell moves to
`row.hint`.
**Why it happens:** `_tool_entry` currently builds BOTH `installed_via` and
`removes` from `row.state`; only `installed_via` is in scope for D-03.
**How to avoid:** Confirm the plan's diff touches only the `installed_via`
local/cell, not `removes`, and that `ABSENT`/`UNAVAILABLE` rows (which have
no meaningful `row.hint` beyond "not installed"/"not available on {os}",
per `uninstall.py:206, 210`) still render sensibly as the dash/short label
they show today — D-03 doesn't ask those to change either.

### Known Threat Patterns for this stack

| Pattern | STRIDE | Standard Mitigation |
|---------|--------|---------------------|
| A planted/corrupted `rpm`/`brew` binary earlier in PATH returning attacker-controlled stdout to a new probe | Spoofing / Tampering | Already-established pattern: every probe runs via the injected `ProbeRunner` (`run_probe`, `subprocess.run` with `capture_output=True, text=True, check=True, stdin=subprocess.DEVNULL, timeout=5`), parses defensively, and fails closed to `None`/`unknown` on any parse error — the new base-image probe must be written the same way, never trusting the returned package name for anything beyond a display label (it must never gate a MUTATING action like update/uninstall without also matching `MUTATION_GRADE`'s existing confidence discipline, per `ownership.py:76` and its surrounding docstring) |
| A new Owner value silently bypassing the existing update-refusal set | Elevation of Privilege (this installer gaining apparent authority to mutate an OS package it cannot safely touch) | `NATIVE_OWNERS` (`ownership.py:84`) is the single declared refusal set `update.py` consumes (`update.py:240`) — any new base-image-owner value MUST be added there (or an equivalent set), per the Code Examples note above; this is a correctness requirement, not just a UX one, since `MUTATION_GRADE` confidence combined with an unrefused native owner would let `u` (update) attempt to mutate a system package with no privilege escalation mechanism this installer has |
