## Codex Review

## 15.4-01

### Summary

Strongly grounded plan that correctly expands D-01 beyond UI rendering into resolver behavior. It identifies the inverse RPM query, preserves active-path safety, updates mutation refusal, and wires the result through the catalog. The main implementation risk is low and mostly concerns maintaining consistency with later plans’ owner-label vocabulary.

### Strengths

- Correctly distinguishes package discovery from package verification. The existing `_rpm_owns_path` requires a caller-supplied package name, while the planned inverse query does not; this is necessary because `/usr/bin/git` may be owned by `git-core`, not the registry’s `git` package (`installer/install_ownership.py:178-204`, `installer/registry.toml:257-275`).

- Preserves the existing fail-closed ownership ordering. `resolve_ownership` currently checks active-path candidates, native ownership, unknown-path handling, and inference in a deliberate order (`installer/ownership.py:330-425`). The proposed placement is appropriate.

- Correctly updates update refusal. `update.py` currently refuses only `NATIVE_OWNERS` (`installer/update.py:215-269`), so adding the new OS-package owner to a centralized unmanageable set is necessary.

- Good end-to-end proof target: resolver → `VersionRefreshService` → `ownership_of` → catalog row. The catalog currently has no Owner cell and has exact column-length tests that must change (`installer/catalog_tui.py:148-166`, `tests/test_catalog_tui.py:896-908`).

- The plan respects the existing dependency direction. `ownership.py` already imports `manager_name` from `uninstall.py` (`installer/ownership.py:61-69`), so keeping removal-hint construction out of `uninstall.py` is sensible.

### Concerns

- **LOW — Validation is somewhat brittle.** Exact owner-count or exact source-shape assertions can make future legitimate owner additions fail for mechanical reasons. The semantic exhaustiveness tests are valuable, but fixed counts should be avoided unless they are explicitly part of the contract.

- **LOW — The temporary label plumbing is complex.** This plan seeds a local placeholder in `_version_detail`, which Plan 03 later extracts. The cross-plan contract is documented, but it creates an intermediate implementation state where two label registries must remain synchronized (`installer/catalog_tui.py:494-517`).

### Suggestions

- Test the split-package case with both a matching and non-matching declared registry package, proving that the inverse probe never compares against the registry name.

- Add an explicit test that an OS-package-owned tool cannot reach any update executor, including SDKMAN and native dispatch branches (`installer/update.py:215-269`).

- Prefer semantic checks such as “every `Owner` has exactly one label” over fixed `Owner` cardinality checks.

### Risk Assessment

LOW. The plan is technically coherent and directly addresses the confirmed resolver gap. Its main risks are cross-plan vocabulary coordination and brittle validation details.

## 15.4-02

### Summary

The plan correctly identifies that Linux cask support is blocked at both registry/application resolution and ownership attribution. Choosing an ownership-only path avoids changing Linux install behavior, which is a reasonable conservative choice. The main concern is maintaining platform semantics consistently across all ownership evidence paths, not just the new cask-specific path.

### Strengths

- Correctly identifies the two independent gates: the current cask resolver is macOS-only (`installer/resolve.py:65-69`), and the JetBrains registry entry is both macOS-gated and incorrectly named (`installer/registry.toml:2153-2177`).

- The ownership-only approach avoids silently making Linux casks installable. This respects the distinction between install applicability and ownership attribution documented in `installer/ownership.py:1-47`.

- The plan preserves existing Linux install behavior while allowing inventory-backed attribution for a live Linuxbrew cask.

- It includes the important empty, unreadable, and mismatched-inventory cases. This matches the existing fail-closed behavior in `install_ownership.py:_run` and `_brew` (`installer/install_ownership.py:62-109`).

### Concerns

- **MEDIUM — The ownership-only platform predicate risks duplicating resolver semantics.** The existing install predicate checks OS, architecture, and minimum OS version (`installer/resolve.py:38-77`). A new ownership-specific method-targeting helper can drift from those rules, especially as method metadata expands.

- **MEDIUM — The plan should account for other raw-method consumers.** `install_ownership._brew` currently scans `tool.methods` directly rather than `resolve_methods(tool, platform)` (`installer/install_ownership.py:101-109`). Adding a Linux cask method could therefore affect declared owner probes differently from the new ownership-only path. The plan should explicitly prove that no existing `owner_probes` behavior changes unexpectedly.

- **LOW — Registry coverage is narrow.** The plan fixes the confirmed JetBrains case, but does not clearly state whether Linuxbrew casks are a general supported ownership category or merely a targeted exception. That distinction matters for future registry entries.

### Suggestions

- Share the OS/architecture/min-version predicate with `resolve.py`, parameterized only for the cask install-vs-ownership distinction, instead of maintaining an independent dimension table.

- Add parity tests covering `os`, `arch`, and `min_os_version`, not only `kind="script"` and cask-specific cases.

- Add a regression test showing that adding the Linux cask method does not make `resolve_methods` offer Linux cask installation.

- Test a tool with an `owner_probes = ["brew"]` declaration after the registry change, confirming the raw probe path and ownership-only path do not disagree.

### Risk Assessment

MEDIUM. The chosen scope is appropriately conservative, but duplicated platform applicability logic could create subtle attribution inconsistencies later.

## 15.4-03

### Summary

This plan gives the Owner column a useful vocabulary and addresses the important distinction between package managers, direct installer mechanisms, and unknown ownership. Its testing strategy is good for label completeness, but the plan does not fully prove that the new column remains practically visible and usable at the project’s minimum terminal size.

### Strengths

- Correctly treats `installer` as a placement mechanism rather than a peer package manager. The available method information is already carried by `OwnershipCandidate.method` (`installer/ownership.py:115-145`, `installer/ownership.py:510-574`).

- A centralized label register with exhaustiveness and pairwise-distinctness checks is appropriate. The current detail labels are a local dictionary with a `.get()` fallback (`installer/catalog_tui.py:494-517`), so silent omissions are currently possible.

- The cask exception is explicitly documented instead of being hidden in a skipped test.

- Preserving the existing 78-column legend constraint is correct: that constraint applies to the legend text, not directly to table columns (`installer/catalog_tui.py:219-228`).

### Concerns

- **MEDIUM — Terminal usability is not actually verified.** The catalog currently defines columns without explicit widths (`installer/catalog_tui.py:148-166`), and the browser delegates sizing to Textual’s `DataTable` (`installer/tool_browser.py:149-159`). Adding a long Owner label can affect horizontal layout, but the plan mainly relies on source-level assertions.

- **LOW — The detail and column vocabularies may diverge semantically.** The detail view currently adds longer explanatory text, including native-manager update restrictions (`installer/catalog_tui.py:506-517`). Pairwise-distinct column labels alone do not guarantee that the focused-row detail remains equally clear.

- **LOW — Source-inspection gates are fragile.** Assertions such as exact local-dictionary removal or exact occurrence counts can fail after harmless refactoring without detecting a behavioral regression.

### Suggestions

- Add a deterministic UI test at the minimum supported size, such as 80×20, asserting that the Owner column is present, selectable, and not silently omitted.

- Add a human check for long labels such as `Homebrew cask` and `github release`, especially alongside the existing `What it does` column.

- Test both normal and unavailable catalog rows, ensuring the Owner cell is blank only for genuine unknown/unresolved cases.

- Prefer behavioral tests over source-text-count tests wherever possible.

### Risk Assessment

MEDIUM. The vocabulary design is sound, but the phase goal is user-visible ownership and the plan does not yet provide strong evidence for minimum-size usability.

## 15.4-04

### Summary

This is the highest-risk plan. It correctly finds the stale row-list bug and the missing uninstall invalidation, and its completion signal addresses the asynchronous refresh window. However, the proposed epoch implementation has a serious concurrency flaw: publishing raced, older ownership results can overwrite newer current results. The plan also needs a precise atomicity and message-success contract.

### Strengths

- Correctly identifies that `UninstallInputs.rows` is frozen at construction (`installer/wizard_app.py:57-76`, `installer/wizard_app.py:584-612`) while only the environment predicates are refreshed on entry (`installer/wizard_app.py:766-794`).

- Migrating all 13 construction sites is necessary. A strict callable type prevents the stale snapshot shape from reappearing.

- The production closure is well-scoped: recompute `is_installed`, reuse one `reverse_dependencies` map, and let the screen’s `run_live` seam handle failures. This respects the setup wiring-only rule.

- Adding an invalidate seam after a successful removal is correct. The current removal path succeeds and sets `applied` without invalidating version/ownership state (`installer/wizard_app.py:864-898`), while install and update paths already use invalidation (`installer/wizard_app.py:1920-1948`, `installer/update.py:352-371`).

- The mounted-screen completion signal is a good response to the asynchronous gap. Catalog refresh is worker-based (`installer/catalog_tui.py:345-373`), so navigation alone cannot repaint an Uninstall screen entered before the worker commits.

### Concerns

- **HIGH — The raced refresh branch can overwrite newer ownership data.** The plan explicitly instructs `refresh` to write `_ownership` and `_ownership_epoch` in both commit branches. Current refresh commits under the lock at `installer/version_status.py:555-569`. Consider:

  1. Refresh A starts at epoch 0.
  2. `invalidate()` increments to epoch 1 (`installer/version_status.py:410-417`).
  3. Refresh B starts at epoch 1 and commits current ownership.
  4. Refresh A later enters the raced branch and writes epoch-0 ownership over B’s epoch-1 records.

  `ownership_of` would then return `None` until another refresh, and the completion signal could repaint the screen with no usable ownership data. The raced branch should not publish ownership results, or should publish them only with a monotonic per-tool generation/version check.

- **HIGH — `ownership_of` must read ownership and epoch atomically.** The current reader is a plain dictionary lookup (`installer/version_status.py:396-408`), while writers use `_lock` (`installer/version_status.py:386`, `installer/version_status.py:555-569`). Two parallel dictionaries create a possible mismatch if `ownership_of` reads one before a writer updates and the other afterward. Either lock the complete read or store an immutable `(epoch, ownership)` record in one dictionary.

- **MEDIUM — The completion signal may be emitted after a failed refresh unless success is explicitly tracked.** `_refresh_versions_worker` always posts `VersionStatusRefreshed` in its `finally` path (`installer/catalog_tui.py:361-373`). `run_live` can return `(None, error)`, yet the plan says to post `OwnershipRefreshed` from the accepted commit path without specifying a committed-success marker. Add a test and an explicit condition ensuring failed refreshes never signal ownership availability.

- **MEDIUM — The `applied`/status precedence is internally ambiguous.** The plan says a background resync with `clear_applied=False` preserves the removal summary, but also says a changed comparison writes ordinary standing status. `_show_standing_status` clears status for nonempty entries (`installer/wizard_app.py:796-800`). The implementation must explicitly distinguish:

  - navigation resync: changed rows clear `applied` and replace the summary;
  - background ownership resync: changed rows rebuild but preserve the summary;
  - failure: warning wins while `applied` remains unchanged.

- **LOW — Failure isolation is asymmetric.** The plan routes the rows predicate through `run_live`, but the other three predicates are currently direct calls (`installer/wizard_app.py:766-771`). If the stated guarantee is that all live reads are failure-isolated, all four need the same treatment. Otherwise scope the guarantee explicitly to the rows predicate.

### Suggestions

- Do not update `_ownership` in the raced refresh branch. Preserve status behavior if required, but discard or quarantine ownership results produced under an obsolete epoch.

- Change `ownership_of` to lock around the combined lookup, or replace the two maps with one map of epoch-tagged records.

- Add a failure-path test proving `OwnershipRefreshed` is not emitted when `service.refresh` fails or returns no committed result.

- Add barrier-based concurrency tests for:
  - old refresh finishing after new refresh;
  - invalidate racing a reader;
  - two refreshes committing in reverse order.

- Define `_resync` as a state machine with explicit status outcomes rather than relying on call order. The current `applied` behavior is too subtle to leave implicit.

### Risk Assessment

HIGH. The plan addresses real bugs, but the epoch publication and atomic-read design can introduce a new, intermittent freshness regression unless corrected before implementation.

## 15.4-05

### Summary

The plan has the right overall architecture: inject a callable hint, reuse the catalog’s ownership service, keep uninstall free of subprocess probing, platform-filter registry fallbacks, and render `row.hint` in the table. The largest functional risk is that native ownership records currently do not retain the actual package name, so the planned removal commands can be confidently wrong for split-package cases such as `git` and `ripgrep`.

### Strengths

- Correctly removes the lossy enum-based `installed_via` mapping while leaving the “What gets removed” cell unchanged (`installer/wizard_app.py:625-643`).

- Preserves dependency direction. `uninstall.py` already imports `resolve_methods` but not ownership resolution (`installer/uninstall.py:7-22`), and the injected callable avoids creating a cycle with `ownership.py`’s existing import of `manager_name` (`installer/ownership.py:61-69`).

- Platform-filtering `_manager_hint` is necessary. The current implementation scans raw methods (`installer/uninstall.py:137-145`), so a macOS-only cask can produce a Homebrew uninstall command on Linux. `resolve_methods` already owns that applicability logic (`installer/resolve.py:38-77`).

- Keeping SDKMAN as a registry-derived fallback is reasonable given that the current `Owner` type does not include SDKMAN and the SDKMAN owner probe is only activated through `owner_probes` (`installer/model.py:55-65`, `installer/install_ownership.py:277-320`).

- The plan correctly makes hints display-only; removal paths come from `ToolRow.paths`, not hint text (`installer/uninstall.py:188-223`, `installer/wizard_app.py:864-898`).

### Concerns

- **HIGH — Native removal commands may use the wrong package name.** The plan proposes using `ownership.package` or the tool command as fallback. But native ownership is synthesized with `package=None` (`installer/ownership.py:479-507`), while native probes currently return only manager/detail strings and do not preserve the verified package name (`installer/install_ownership.py:112-127`). For example, the registry’s `rg` command may correspond to the `ripgrep` package, and `/usr/bin/git` may correspond to `git-core` (`installer/registry.toml:257-275`). A generated command such as `dnf remove rg` or `dnf remove git` may fail or target nothing.

- **MEDIUM — SDKMAN uninstall syntax and version handling are under-specified.** The registry provides a candidate (`installer/registry.toml:1749-1761`), but the plan does not establish whether the uninstall command requires a version, how to obtain it, or whether `ManagerOwnership.current_version` is populated for SDKMAN records.

- **MEDIUM — “Every hint is the registry phrase” overstates direct-uninstall behavior.** `classify_tools` gives removable rows a userspace-removal hint and absent/unavailable rows their own state-specific text (`installer/uninstall.py:188-210`). The guarantee should apply only to managed rows, not every row.

- **LOW — Full hints may make the table unwieldy.** The current Uninstall table has fixed conceptual columns but no explicit width policy (`installer/wizard_app.py:728-737`). A hint containing manager, command, path, and reverse-dependency information could crowd out “What gets removed.” The plan leaves shortening conditional on a rendering test, but the acceptance behavior should be more explicit.

- **MEDIUM — Volta is dismissed too narrowly.** The current registry explicitly describes Volta as owning global Node CLIs (`installer/registry.toml:1968-1996`), and the install guard redirects global npm/pnpm installs through `volta install` (`installer/app.py:342-348`). It is true that no registry method kind represents Volta as another tool’s owner, but the phase goal names Volta-owned tools. The plan needs an explicit accepted limitation or a future-proof ownership relation, rather than relying only on the absence of a `volta` method kind.

### Suggestions

- Preserve the verified native package name in the ownership record, or make native removal hints non-commandable and state that removal must be performed through the host package manager.

- Add tests for `git`/`git-core` and `rg`/`ripgrep` proving the displayed command or non-commandable wording is correct.

- Research and pin SDKMAN’s actual uninstall syntax, including version selection, before generating a runnable command.

- Narrow the direct-uninstall requirement to managed rows and separately assert the existing removable/absent/unavailable hints remain unchanged.

- Add an explicit policy test for Volta:
  either Volta ownership is intentionally not attributable in this phase, or redirected global tools receive a documented owner classification.

- Define a compact cell format and retain the full hint in the detail panel if the rendering test shows the table becomes too wide.

### Risk Assessment

HIGH. The seam and rendering work are sound, but incorrect native package commands would undermine the “truthful attribution” goal and could mislead users about how to remove tools.

## Cross-plan comparison

- The plan ordering is generally sensible: resolver and labels first, screen state/freshness next, then Uninstall hint consumption.

- Plan 04 is a dependency bottleneck. Plans 05’s fallback behavior and freshness guarantees depend on its epoch protocol, so the race and atomicity issues must be resolved before Plan 05 begins.

- The phase currently has several ownership vocabularies: `Owner`, column labels, detail labels, removal phrases, update refusal sets, and registry-derived fallback hints. Centralizing these is good, but the number of cross-plan contracts increases integration risk.

- The Volta question should be resolved at phase level. The source confirms both that Volta is a real runtime owner path and that it is not represented as an ownership method kind. That is a product/model decision, not merely a grep result.

- Validation should end with the repository’s actual gates, `make validate && make test`, not only repeated subsets of `pyright`, Ruff, and pytest.

## Overall assessment

Overall risk: HIGH.

The phase goals are achievable and the plans are unusually well-grounded in the current implementation. Before execution, fix Plan 04’s stale-refresh overwrite and atomic-read design, and resolve Plan 05’s native package-name problem. With those addressed, the remaining risks are mostly UI sizing, vocabulary coordination, and clarifying Volta’s intentional scope.
