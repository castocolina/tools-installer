<objective>
Make a run that hits a failed prerequisite honest. `run_installs` currently walks its tool list with
zero memory: when `sdkman` fails, `java` is still handed to the installer, fails again for a reason
that has nothing to do with `java`, and the user reads two unrelated failures instead of one cause
and one consequence. This plan gives the loop a one-line memory and a distinct outcome for the
consequence.

Purpose: ROADMAP Phase 3 SC#1 -- "When a tool's dependency failed earlier in the same run, the tool
is reported as skipped with a clear 'dependency failed' reason -- never silently attempted, never
silently dropped from the summary." This is REQ-install-failure-propagation, which
`.planning/PROJECT.md` records as a code-review finding against commit `431a0a9`: "soft-warn + skip
dependents on failure" was the original spec and was never implemented.

Output: a new `InstallStatus.DEPENDENCY_FAILED`; a `blocked_by` field on `InstallOutcome` naming
which dependency ids did it; a failed-id set threaded through `run_installs`; a
`Summary.dependency_failed` bucket; a `render_skipped` console reporter wired into `run_wizard`; and
an `.claude/architecture.md` note separating run-time failure propagation from the resolver's
pre-flight platform-availability check.
</objective>

<design_decisions>
CONTEXT.md leaves one item to the planner: "the exact new `InstallStatus`-family value (or
equivalent) used to represent 'dependency failed' in `run_installs`'/`summarize`'s output, and its
color/label in the wizard summary". These are the resolutions.

**A new member of the existing `InstallStatus` enum, not a parallel type.** `InstallOutcome.status`
is typed `Status = InstallStatus`, `summarize` keys a dict on it, and `render_verification` branches
on it. A parallel "skipped" type would need a second outcome shape, a second bucket pass and a
second render path. One more member costs one line in the enum and one line in `summarize`'s table,
and pyright's exhaustiveness over a `StrEnum` makes every unhandled site a type error rather than a
silent drop. The value string is `"dependency-failed"` because every other member is a lowercase
hyphenated string (`already-installed`, `no-method`, `checksum-mismatch`) and `InstallOutcome.__init__`
accepts `Status | str`, so tests can write the literal exactly as the existing ones do.

**`summarize`'s `KeyError` is the designed failure mode and must not be softened.** The existing
docstring says so explicitly: "an out-of-range status is impossible under pyright and would surface
as a KeyError if one ever slipped through, rather than being silently dropped". Adding the enum
member without adding the bucket key would therefore CRASH rather than silently lose the tool --
which is exactly the behaviour SC#1 asks for. Do not add a `buckets.setdefault(...)`, a
`defaultdict`, or a `.get(status, [])` anywhere in this plan; that would convert the guard into the
bug the requirement exists to fix.

**`blocked_by` on `InstallOutcome`, not a message string.** The reason must survive as data from
`run_installs` to the renderer, because `Summary` deliberately carries only ids. A pre-rendered
sentence in `errors` would mean the session layer decides console wording, which belongs to
`installer/render.py` (the module docstring is "Render the pre-flight audit and the post-install
summary to a Console"). `errors: tuple[Exception, ...]` is also the wrong carrier: no exception was
raised, and `render_verification` reads `errors[0]` as a `ChecksumMismatch` for one specific status.
A typed `tuple[str, ...]` of ids lets the renderer say the sentence and lets a test assert the
mechanism.

**The set is "unresolved", not "failed".** REQ-install-failure-propagation says "which tool ids
failed", but three statuses other than `FAILED` mean the tool is not on the machine when its
dependent runs: `NO_METHOD` (nothing applicable on this platform), `CHECKSUM_MISMATCH` (the download
was refused) and `DEPENDENCY_FAILED` itself. Attempting a dependent after any of them reproduces
exactly the confusing downstream error the requirement is about. Including `DEPENDENCY_FAILED` in
the set is what makes propagation transitive, and it is the single most deletable line in this plan
-- Task 2 pins it with a three-link chain test for that reason. `INSTALLED` and `ALREADY_INSTALLED`
are the only success statuses and never enter the set.

**One forward pass, and the ordering invariant that makes it sufficient.** `run_wizard` hands
`run_installs` the output of `deps.resolve_dependencies`, which is deps-first topologically sorted,
so a dependency is always visited before anything that requires it and a single forward pass sees
every relevant failure. `run_installs` does not re-derive that order and must not: `.claude/architecture.md`
records `requires` + `resolve_dependencies` as the sole ordering mechanism, and a second sort here
would be a second resolver. The docstring states the invariant plainly, and Task 2 pins the
degradation: given a hand-built list in the wrong order the skip simply does not fire and the
dependent is attempted exactly as it is today -- never worse than current behaviour, never a crash.

**Why this is not `deps.resolve_dependencies`' job.** The resolver already drops a branch whose
dependency is unavailable ON THIS PLATFORM and warns about it, before anything runs. That is a
pre-flight judgement made from the registry. This plan handles a dependency that WAS available and
then failed while installing -- information that exists only mid-run. The two mechanisms answer
different questions at different times and share no code. Task 2 pins that separation in code with a
source-level check that `run_installs` never sorts; the prose version is written into
`.claude/architecture.md` by plan 03-03's consolidated phase doc task, not here, so the three Phase 3
plans never contend for that one file.

**Color/label.** The summary counts line gains `Dependency failed: N` in the existing plain style
(that line is uncoloured today and stays uncoloured -- adding markup to one field would make the
others look broken), and the per-tool reason line printed by `render_skipped` uses `[yellow]⚠ ...[/]`,
matching `render_dependency_notice`'s existing warning line exactly. Yellow, not red: the dependent
did not fail, and the red-worthy event -- the dependency's own failure -- is already listed under
`failed`.

**No `checkpoint:human-verify` task.** `.planning/config.json` sets
`workflow.human_verify_mode: "end-of-phase"`, so verification consolidates at phase close. This
plan also touches no Textual surface -- its only user-visible output is the Rich console summary
`run_wizard` prints after the TUI has exited -- so ONESHOT checklist item 7's `tmux` TUI check does
not apply here. Plans 03-02 and 03-03 carry the TUI checks for this phase.

**The two docstrings the cycle-1 review asked for are now GATED, not advisory.** A docstring that
records a boundary is only useful if it cannot silently vanish in a later edit, so both are pinned by
literal-substring checks in the verify blocks rather than left to the executor's judgement. See
`<review_dispositions>` for what each one must say and where it is asserted.
</design_decisions>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| `InstallOutcome.status` -> `summarize`'s bucket table | A status with no bucket key is the one path by which a tool could vanish from the run report. The existing code makes this a `KeyError` on purpose. |
| `run_installs`' skip decision -> the install engine | The branch that decides a tool is NOT executed. Getting it wrong in one direction attempts a doomed install; in the other it silently refuses a healthy one. |
| `InstallOutcome.blocked_by` -> `render_skipped` -> the user's terminal | Tool ids from the trusted registry reach a Rich console that interprets `[...]` markup. |
