<objective>
Give Oh-My-Zsh's bundled `git` and `docker` plugins the same one-keypress toggle every other shell
tweak already has, by editing the `plugins=(...)` array the user's own `.zshrc` already contains --
never by adding a catalog entry, and never by writing a marker block into a file this installer does
not own.

Purpose: ROADMAP Phase 3 SC#3 -- "Toggling the Oh-My-Zsh plugins tweak in Policies enables the
bundled `git` and `docker` plugins by editing the `plugins=(...)` array in `.zshrc`, with no separate
catalog entry required." This is REQ-oh-my-zsh-plugin-config, and `.planning/STATE.md` records the
governing PRD decision: "Oh-My-Zsh's `git`/`docker` plugins are a config-array edit to `.zshrc`, not
new `Tool` entries."

a typed error, and the Oh-My-Zsh presence probe); a new `omz_plugins_policy` factory in
`installer/policy.py` parallel to `ban_policy`/`tweak_policy`; a detail-panel entry in
`PoliciesScreen`; the `setup.py` wiring; and an `.claude/architecture.md` note recording why this one

<design_decisions>
**The REQUIREMENTS.md wording versus CONTEXT.md D-02 -- and why D-02 wins.**
`REQUIREMENTS.md` says REQ-oh-my-zsh-plugin-config is satisfied "reusing the existing
`apply_block`/`strip_block` tweak mechanism". CONTEXT.md D-02, locked in the 2026-09-04 discuss-phase
that came after, says the opposite in explicit terms: "This is a genuinely new capability, not a
reuse of `installer/shellrc.py`'s `apply_block`/`strip_block` -- that mechanism owns and rewrites an
entire marker-delimited block in a file `tools-installer` controls (`~/.myshellrc`); Oh-My-Zsh's
`plugins=(...)` line lives in a file the user's own setup already populated, and must be edited in
place, not replaced wholesale." The user's locked decision governs, and it is also the only
technically possible reading: `apply_block` REPLACES everything between two markers, so applying it
to `plugins=(...)` would require writing tools-installer markers into the user's `.zshrc` around a
line oh-my-zsh's own installer wrote, and would clobber any edit the user made to that line between
runs. The requirement's real intent -- reuse the tweak TOGGLE, do not create a catalog entry -- is
fully honoured: this ships as a `Policy` in the same Policies table, on the same `space` key, through
the same `ui_common.run_live` workflow, with the same `requires`/`missing_requires` gating. Only the
file primitive underneath differs. Execution must not "restore" the block mechanism here.

**Not a `TweakBundle`, and not a new field on `TweakBundle` -- a third `Policy` factory.**
CONTEXT.md leaves the carrier to the planner. `TweakBundle` is defined as "one curated shell snippet"
with a `body` that `tweaks.py` writes as a marker block into `~/.myshellrc`, plus `platforms`,
`requires` (PATH binaries) and `executables`. This feature has no body, writes to a different file,
writes no block, and gates on a directory rather than a binary -- four of the six fields would be
dead and the fifth (`body`) would be a lie. Adding a presence-predicate field to `TweakBundle` would
put a field on every bundle for the benefit of one. Instead `installer/policy.py` gains a third
factory beside `ban_policy` and `tweak_policy`, which is exactly the extension point that module's
own docstring advertises ("future env tweaks slot in with no screen changes") and the same shape
ROADMAP Phase 11 already plans for (`a new daemon_policy factory parallel to existing Policy
factories`). Crucially, `Policy` ALREADY has `requires` and `missing_requires` fields, and
`PoliciesScreen` already renders and enforces them -- so D-05's "mirroring the existing `requires`
pattern" and D-06's "no new UX pattern needed, just a new detection predicate feeding the existing
mechanism" are satisfied literally, with zero screen logic added.

**`OmzPluginsError` subclasses `OSError` so the existing single apply workflow surfaces it.**
`.claude/architecture.md` rule 3 says every live core mutation from a screen goes through
`ui_common.run_live` and "screens supply the closure and the messages, never their own try/except".
`run_live` catches `OSError` by design. Widening it to catch a new exception type would change
behaviour for the doctor, uninstall and ban screens too. Subclassing `OSError` is both the minimal
edit and semantically honest: "this file does not contain the line I need to edit" is an
environment/file-state problem, which is what `OSError` means. The payoff is concrete -- when a
user's `.zshrc` uses the multi-line form, `PoliciesScreen.action_toggle_policy` gets
`result is None`, shows the error on the status line, and does NOT flip the row to ON. A silent
no-op would have shown ON while nothing changed, which is the single worst outcome available here.

**Enable raises on a missing array; disable never does.** The asymmetry is deliberate. Enabling and
doing nothing is a lie the UI would repeat; disabling and doing nothing is the correct end state.
Disable must also stay total because plan 03-03's full-uninstall sweep calls it unconditionally
against a machine whose `.zshrc` may not exist at all.

**Last matching line wins.** `_PLUGINS_LINE` may match more than once in a hand-edited `.zshrc`;
the editor takes the LAST match, mirroring `shellrc.apply_block`'s documented last-begin rule and
matching zsh semantics, where the final assignment before `source $ZSH/oh-my-zsh.sh` is the one that
takes effect. A commented-out `# plugins=(...)` never matches, because the pattern anchors the
optional indent to spaces and tabs only.

**What the regex tolerates, and what it refuses.** It matches `^[ \t]*plugins=\(<no parens or
newlines>\)[ \t]*(#...)?$` -- so leading indentation, an empty array, arbitrary internal whitespace
and a trailing comment all round-trip, and the rewritten line restores the original indentation and
trailing comment verbatim while normalising the plugin separators to single spaces. It refuses a
multi-line array (the closing paren is not on the line), which is D-03's out-of-scope form
surfacing loudly instead of being half-parsed. Normalising internal whitespace is an accepted,
documented side effect of a rewrite; the alternative is a positional splice that is far more code
for a cosmetic gain.

**Disabling removes `git` even if the user had it before -- and the detail panel says so.** D-01
specifies "remove only those two if present (toggle-off)" with no memory of the prior state, and
this project bans introducing a state database for exactly this kind of bookkeeping (see ROADMAP
Phase 9 SC#3, "no new state-tracking database anywhere in the codebase"). Rather than invent
tracking or quietly diverge from D-01, the consequence is disclosed where the user decides: the
policy's detail-panel copy states plainly that disabling removes both names from the array,
including one that was already there. Task 3's container check demonstrates the real-world instance
of this (upstream's default `.zshrc` ships `plugins=(git)`), so the behaviour is proven and visible
rather than discovered later.

**`~/.zshrc` is passed in from `setup.py`, not derived inside `installer/`.** `setup.py` already owns
the real home-path constants (`_MYSHELLRC`, `_RC_PATHS`) and `.claude/architecture.md` rule 4 lets
the composition root read the real environment. Adding a `zshrc_path()` helper to
`installer/locations.py` would create a function with exactly one production caller for no decision
it makes. The policy factory takes the path as a keyword argument, which is also what makes every
test sandboxable.

**Row order: appended after the tweak bundles.** `PolicyInputs.policies` order is the Policies table
order. Appending keeps every existing row where it is, so no existing test or terminal expectation
about row position changes.

**Platform gating: none, by design.** The policy is listed on Linux and macOS alike and gates on the
presence probe rather than on `Platform.os`. Oh-My-Zsh is a real Linux target for this project
(ROADMAP Phase 7's `REQ-linux-bazzite-shell-parity`), and a machine without it is already handled
correctly and visibly by the `missing_requires` path. A `platforms` filter would hide the row from
Linux users who do have it.

**`plugins_enabled` requires ALL managed names -- and the partial state that follows is disclosed,
not designed away.** `active` is recomputed from the file on every read, and `plugins_enabled` is True
only when the array contains every name in `MANAGED_PLUGINS`. So a user who enables the toggle
(`plugins=(git docker)`) and then hand-removes `git` gets a row that reads OFF while `docker` is still
loaded by their shell. Cycle-1 review flagged that as potentially confusing, and it is -- but every
alternative is worse. An any-of predicate would read ON after a manual removal and then, on toggle-off,
"disable" a state it never established. A per-plugin tri-state would need two rows or a partial mark,
inventing UI for a hand-edit case. Remembering what we wrote would be exactly the state database this
project bans (ROADMAP Phase 9 SC#3). The all-of predicate is the honest one -- it is the only reading
under which ON means "this policy's full effect is present" -- so the fix is disclosure at the point of
decision, in the same detail panel that already discloses the toggle-off consequence, and the
disclosure line is pinned by a source check so it cannot be dropped. The user is told what the row
means; they are not silently left to infer it.
</design_decisions>
