## Warnings

### WR-01: `MANUAL_REQUIRED` outcomes are summarized by id/count but the actual handoff instructions are never rendered anywhere

**File:** `installer/render.py:48-69`, `installer/session.py:123-149`, `installer/app.py:158`
**Issue:** The fix threads `InstallStatus.MANUAL_REQUIRED` through `Summary` and
`render_summary` "on the same footing as every other bucket" (count + id
list), which correctly closes the crash. But `InstallOutcome.handoff` — the
tuple of "reviewed console instructions to run after the installer releases
the terminal" (`installer/engine.py:41-44`) that is the entire point of the
`MANUAL_REQUIRED` status — is dropped on the floor. `run_installs` returns the
full `list[InstallOutcome]` (each carrying its own `.handoff`), but
`installer/app.py`'s `run_wizard` only calls `summarize(outcomes)` →
`render_summary(summary, console)`, and `Summary` itself only stores tool ids
(`tuple[str, ...]`), never the handoff text. Grepping the full codebase
(`installer/wizard_app.py`, `installer/catalog_tui.py`, `installer/app.py`)
confirms there is no code path, CLI or TUI, that ever prints
`outcome.handoff`. A user who runs a real install of `pi` or any of the 7
`skill_pack` rows (`ponytail`, `openspec`, `superpowers`,
`softaworks-agent-toolkit`, `matt-pocock-skills`, `opengsd`, `spec-kit`) will
see `Manual setup required: 1` and `  manual setup required: pi` — and
nothing else. They are told something needs manual attention but never told
what to actually do. This is not a new regression from this diff (`git diff
b9a8876..a570bf3 -- installer/session.py` was empty, so this gap predates the
reconciliation too), and the round-2 cross-AI review that drove this task
explicitly scoped the fix to "completing with a manual-handoff summary line"
— so the delivered fix matches its reviewed scope. Flagging it because the
resulting behavior is still a real, user-visible gap: the crash is gone, but
the feature the crash was guarding (showing the user their manual next steps)
still doesn't work end-to-end.
**Fix:** Add a `render_handoff_instructions(outcomes, console)` (or extend
`render_summary`) that, for each outcome with `status ==
InstallStatus.MANUAL_REQUIRED` and a non-empty `handoff`, prints the
tool id followed by its instruction lines, e.g.:
```python
def render_manual_setup_instructions(outcomes: list[InstallOutcome], console: Console) -> None:
    for outcome in outcomes:
        if outcome.status is not InstallStatus.MANUAL_REQUIRED or not outcome.handoff:
            continue
        console.print(f"[cyan]{outcome.tool_id} — manual setup required:[/]")
        for line in outcome.handoff:
            console.print(f"  {line}")
```
and call it from `installer/app.py`'s `run_wizard` alongside
`render_postinstall_warnings`/`render_verification`.

### WR-02: D-04's "`make validate`/vulture stays green" claim is not meaningful evidence for the orphan-module classification it's cited to support

**File:** `pyproject.toml:59-61` (`[tool.vulture]`, `min_confidence = 80`); `installer/agent_env.py`, `installer/agent_policy.py`, `installer/install_actions.py`, `installer/install_ownership.py`
**Issue:** Both the PLAN (Task 3 acceptance criteria) and the SUMMARY cite
"`make validate` (ruff/pyright/bandit/vulture) ... stays green" as part of the
evidence that the five ported-but-unwired modules remain correctly classified
as orphans. I re-ran vulture at a lower confidence threshold
(`uv run vulture installer --min-confidence 60`) and it flags exactly the
functions this task's own audit is about: `agent_env.py:21 unused function
'adapters'`, `agent_policy.py:231/278 unused function
'apply_agent_policy'/'audit_agent_policy'`, `install_actions.py:85/288 unused
function 'default_action_context'/'apply_actions'`,
`install_ownership.py:30/179 unused function 'run_probe'/'detect_owner'`. None
of these appear at the project's actually-configured `min_confidence = 80`
threshold. This means vulture provides zero signal, positive or negative, for
this specific class of finding at the project's current configuration — "make
validate stays green" would be equally true whether these five modules were
correctly orphaned, newly wired in with a real caller, or had drifted further
out of sync, as long as no *other* unrelated 80%-confidence dead-code pattern
appeared. Citing it as corroborating evidence for D-04's audit overstates what
that gate actually checks.
**Fix:** Either lower `min_confidence` for a project-specific vulture
allowlist scoped to these five files (documenting why), or — simpler and
consistent with this phase's own D-02 precedent (a permanent
`test_reconciliation_tier_audit_...` regression test rather than a one-time
audit claim) — add a small pinned regression test analogous to
`tests/test_ownership.py::test_abandoned_drift_helpers_are_absent` that
asserts (via `grep`/AST or a hardcoded caller-count) these five modules still
have zero production callers outside their own tests, so future drift is
caught by `pytest`, not silently missed by a vulture threshold that already
doesn't see it.
