## Fixed Issues

### CR-01 (BLOCKER): the `_silence_generation` guard was verified by no test

**Files modified:** `tests/test_execute_screen.py`
**Commit:** `894ceaf`

`_transient_is_current` ANDs five conditions, and every test that claimed to
exercise the generation token invalidated one of the other four at the same
time, so the comparison was never the reason a message was dropped. Plan 02
Task 1 required the opposite and named the trap explicitly.

`test_stale_generation_alone_drops_the_transient` holds the in-flight tool, the
prompt state, the finished flag and `_silence_noted` **identical** between two
messages and changes nothing but the token. It asserts the positive baseline
first — `screen._transient_is_current(current)` is True — so the negative
assertion cannot pass because some other condition happened to be false.

**Mutation (the review's own):** delete
`message.generation == self._silence_generation` from `_transient_is_current`.
Before: 83 tests green. After this fix: exactly one failure, and it is this test
(`assert not ... where True = _transient_is_current(InstallLogLine())`).

Two Info findings were folded in because CR-01's claim rests on them:
- **IN-02:** the indicator copy is now imported as `_WAITING_OUTPUT` rather than
  hand-written twice. Load-bearing here — "only the generation differs" is only
  true if the constructed message is byte-identical to production's.
- **IN-03:** `_captured_transient`'s docstring now names which of the five
  conditions each of its four callers invalidates, so the next reader can tell
  an isolated test from a conflated one without tracing.

### CR-02 (BLOCKER): the "wrapped failure names the caller's command" test never wrapped

**Files modified:** `tests/test_run.py`
**Commit:** `76b4ea9`

The test passed `[sys.executable, "-c", ...]`, which `_is_python_child`
deliberately excludes from wrapping, so it exercised the **unwrapped** path
under a wrapped-path name and its `"/usr/bin/stdbuf" not in exc.value.cmd` was
trivially true. Its `Popen` double also ignored its `argv` parameter entirely.
No test in the suite covered a wrapped command exiting non-zero.

Now uses `["brew", "install", "rg"]`, records what `Popen` received, and asserts
the stdbuf prefix **was** applied *before* asserting `CommandError` still names
the caller's argv — so a future change that stops wrapping fails loudly instead
of quietly making the rest of the test vacuous.

**Mutation:** `CommandError(cmd, returncode, ...)` -> `CommandError(launch_argv,
returncode, ...)` — the exact regression the test exists to prevent, and the one
that would show a user a `stdbuf -oL brew install rg` they never typed. Before:
whole suite green. After: this test fails.

### CR-03 (BLOCKER): mandated acceptance-criteria tests were never written

Four separate gaps; each closed by its own commit.

**(a) The `ExecuteScreen`-level sentinel end-to-end test** — `b286863`
(`tests/test_execute_screen.py`)

`grep -n "sentinel" tests/test_execute_screen.py` returned nothing, so review
round 2's MEDIUM finding — *no test observes the widget before the child exits*
— was still unanswered. Written to plan 01 Task 1's specification verbatim:
child prints one unflushed line then polls for a `tmp_path` sentinel with its
own ~30s ceiling; the install closure drives the **handed-in** runner (a freshly
constructed one raises from `_current()` on its first line); `delenv` first;
`await pilot.pause(0.02)` rather than a bare idle pause, with the reason
recorded beside the loop; sentinel created in a `finally`.

"While the child still runs" is true by **construction**, not by clock: at the
assertion the child is blocked on a file that does not exist, so its second line
cannot be in the log either.

**Mutation:** `env = unbuffered_env()` -> `env = dict(os.environ)`. Fails as the
genuine deadlock-then-timeout the plan predicted:
`AssertionError: the child's first line never reached the widget while it was
still running / assert 'child line 1' in ''` after ~9s of bounded polling.

**(b) `both-attempts-fail-is-still-127-with-the-caller's-argv`** — `9b1a028`
(`tests/test_run.py`, `installer/run.py`)

`installer/run.py`'s `except OSError as retry_exc` branch was executed by no
test in the 2189-test suite. The new test asserts the 127, the caller's argv,
that exactly two launches happened (wrapped then unwrapped, no retry loop), and
that both failures are named.

**Mutation:** make the nested raise report `launch_argv`. Fails on
`exc.value.cmd == cmd`.

**(c) `knob-off-makes-exactly-one-Popen-attempt`** — `9b1a028`

The only guard for the fragile `launch_argv is not cmd` **identity** check.

**Mutation:** rewrite `unbuffered_argv`'s skip branch to `return list(cmd)` — a
natural defensive tidy-up that silently gives every default-constructed runner a
second `Popen` attempt on `OSError`. Before: green (including
`test_streaming_runner_missing_binary_is_127`, whose double raises
unconditionally and which asserts only on the final error). After: this test
fails on `attempts == [["nope"]]`.

**(d) The SUMMARY reported zero code deviations** — `5f22822`
(`15.2-01-SUMMARY.md`)

"Total deviations: 1 discarded stale-worktree attempt (infrastructure, not a
code deviation)" while three of its own acceptance criteria were unmet. The
deviations section now records what was missing, which review finding caught it,
and the commits that closed it — a summary the next phase's planner reads as
ground truth must not under-report.

### WR-04: `_arm_silence_timer` replaced a live timer without stopping it

**Files modified:** `installer/execute_screen.py`, `tests/test_execute_screen.py`
**Commit:** `6449ef0`

The invariant that made the unconditional overwrite safe was implicit and
fragile — it held only because the sole caller other than `action_start` nulls
the attribute on its own first line after its own timer has fired. Any future
second arming site orphans a live `Timer` that `on_install_run_finished` can no
longer stop, because it only ever holds the newest reference. Now enforced, with
the reason in the docstring so it is not tidied away again.

The regression test pins `Timer.stop` rather than an internal flag: stopping is
the observable obligation, and the attribute swap alone cannot prove it
happened.

**Mutation:** restore the unguarded body. Fails on
`assert Timer(2.0, ...) in []`.

### WR-09: the unwrapped retry discarded the original launch failure

**Files modified:** `installer/run.py`
**Commit:** `9b1a028`

Correction to the finding's premise, verified rather than assumed: the first
`OSError` was **not** dropped. An exception raised inside an `except` block gets
the handled exception as its `__context__` implicitly, so `retry_exc.__context__`
already **is** `exc` and the traceback keeps why the wrapper broke. Confirmed
with a standalone reproduction before changing anything.

What was genuinely missing is the half a user sees: the path raised a bare
`CommandError(cmd, 127)`, so the message said nothing about which of the two
launches failed. The detail now names both, and a comment records the implicit
chaining so nobody "fixes" it by assigning `__context__` by hand. The CR-03(b)
test asserts both the detail text and the surviving chained context.

### WR-10: `_is_python_child` disabled the stdbuf rung for any binary named `python*`

**Files modified:** `installer/run.py`, `tests/test_run.py`
**Commit:** `5fd66a9`

`Path(argv0).name.startswith("python")` excluded `pythonpy`,
`python-lsp-server`, `pythonic-cli` and any wrapper script named `python-tool`
— real non-Python binaries `PYTHONUNBUFFERED` does nothing for, i.e. exactly the
kind of tool this phase exists to unblock would silently keep bursting. The
docstring admitted the false-negative direction but not this one.

Now matches `sys.executable` or a basename that is exactly `python`, `python3`,
`python3.12`. The residual gap is in the safe direction and is documented: an
interpreter the pattern misses (`uv run python` presents as `uv`; a `python3.14t`
free-threaded build) is merely wrapped **as well as** env-configured, which is
harmless.

Tests cover both directions, plus the previously uncovered empty-`cmd` guard
(`installer/run.py`'s `return False` for `[]`), which the full suite never
executed. That line is no longer in the coverage miss list.
