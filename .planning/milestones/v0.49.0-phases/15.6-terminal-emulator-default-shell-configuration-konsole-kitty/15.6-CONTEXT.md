# Phase 15.6: Terminal-emulator default-shell configuration - Context

**Gathered:** 2026-09-15
**Status:** Ready for planning

<domain>
## Phase Boundary

The actual solution to "zsh should just work as my shell, without touching
chsh/system login shell" — the capability Phase 15.5 identified but explicitly
deferred out of its own scope. Configures Konsole, kitty, and WezTerm to launch zsh
(with oh-my-zsh's plugins loaded, when installed) as their working shell, without ever
touching `chsh`/`/etc/passwd`. Scoped to Linux/immutable hosts, where this problem
actually exists — macOS is explicitly out of scope (chsh works normally there via the
existing Phase 14 flow; user confirmed no such problem on macOS).

</domain>

<decisions>
## Implementation Decisions

### When the configuration is (re-)applied
- **D-01:** Idempotent, re-applied on every relevant state change — not a one-time
  event fired only at install time. Recompute/reassert the terminal-emulator shell
  configuration whenever: zsh is installed or updated, a new terminal emulator
  (kitty/WezTerm/Konsole) is installed, or oh-my-zsh is activated later via the
  Policies screen (not necessarily at the same time zsh itself was installed).
  — **Reversibility:** reversible.
  **Rationale (user):** selected the idempotent/always-synced option explicitly,
  matching the same "never stale" pattern already established in Phase 15.1
  (catalog refresh) and Phase 15.4 (Uninstall ownership refresh) — this phase should
  follow that same precedent rather than reintroduce a one-shot staleness bug.

### Configuration method
- **D-02:** Write directly into each terminal emulator's own config file — `shell` in
  `kitty.conf`, `default_prog` in `wezterm.lua`, the relevant key in Konsole's profile
  file — rather than a launcher/`.desktop`-level override.
  — **Reversibility:** reversible (config file edit, revertible).
  **Rationale (user):** chose the config-file approach explicitly over the
  `.desktop`-wrapper alternative that was investigated in Phase 15.5's research leads.
  Persists regardless of how the terminal is launched (dock, app menu, taskbar pin,
  keyboard shortcut, an IDE's integrated terminal) — a `.desktop` Exec= edit only
  applies to that one specific launcher and can be silently reset by a package update.

### oh-my-zsh sourcing gap (confirmed live, folded in after initial discussion)
- **D-04:** Confirmed live on this exact host (2026-09-15, reported by the user while
  reviewing the Policies screen — see screenshot evidence below): `~/.oh-my-zsh/`
  exists (the install genuinely happened) but is never loaded — neither `~/.zshrc` nor
  `~/.myshellrc` contains a `source $ZSH/oh-my-zsh.sh` line (or any `ZSH_THEME`/
  `plugins=(...)` template line at all). Root cause: `oh-my-zsh`'s registry entry sets
  `KEEP_ZSHRC=yes` (`installer/registry.toml`) specifically to avoid clobbering a
  user's existing `.zshrc` — correct in principle, but the installer never separately
  verifies/ensures the minimal required sourcing line exists when the pre-existing
  `.zshrc` (in this case, a minimal file this installer itself created, sourcing only
  `~/.myshellrc` plus unrelated wezterm-setup lines) never had it. The net effect:
  oh-my-zsh installs successfully and is completely inert. This is also the direct
  cause of the `installer/omz.py` "Policy change failed: No single-line
  plugins=(...) array to edit" error the user hit on the Policies screen — there is no
  such array because there is no oh-my-zsh template in `.zshrc` at all, not because
  the array is in some unsupported form.
  **Fix direction (this phase must ensure, not merely investigate):** the installer
  must guarantee `.zshrc` sources oh-my-zsh after a successful install, regardless of
  `KEEP_ZSHRC`'s file-preservation behavior — e.g. append the minimal
  `export ZSH="$HOME/.oh-my-zsh"` + `source $ZSH/oh-my-zsh.sh` (+ a default
  `plugins=(git)` single-line array, so `installer/omz.py`'s plugin-toggle feature has
  something to edit) idempotently if and only if no such sourcing already exists —
  never overwriting a `.zshrc` that already sources it correctly by hand.
  — **Reversibility:** reversible (an appended, idempotent .zshrc edit).
  **Rationale (user):** this is the same underlying "zsh + oh-my-zsh should just work"
  outcome this phase already exists to deliver — the user's original framing
  explicitly included "si seleccioné oh-my-zsh sea parte de zsh y cargue mis plugins"
  (Phase 15.6's own `<specifics>` section) — sourcing is a strict prerequisite for
  plugin-loading, so this was already implicitly in scope and is now a confirmed,
  locked decision rather than an open research question.

### Konsole scope (Claude's Discretion, confirmed with user)
- **D-03:** Configure Konsole too, even though it has no `registry.toml` entry (it
  ships with KDE, this app never "installs" it) — detect its presence live (e.g.
  `shutil.which("konsole")` or KDE-session detection) and configure it if found,
  since it is plausibly the user's actual daily-driver terminal on a Bazzite/KDE host.
  — **Reversibility:** reversible.
  **Rationale:** user did not select this as a discussion area, explicitly delegating
  it to Claude's discretion; the proposed default (configure it if present, regardless
  of catalog-managed status) was stated plainly and not objected to.

### Claude's Discretion
- Exact re-application trigger wiring (piggyback on Phase 15.5's `_install_closed`-style
  refresh hook vs. a dedicated post-install/post-policy-change hook) — implementation
  shape for research/planning to resolve.
- Exact Konsole profile-file target (default profile vs. all profiles) and detection
  mechanism for "is Konsole present" (binary presence vs. KDE plasma session detection).
- Exact idempotent-append mechanism for D-04's `.zshrc` sourcing fix (reuse
  `installer/atomic.py`'s atomic-write pattern `installer/omz.py` already uses;
  detect "already sources oh-my-zsh" via a simple substring/regex check before
  appending, to stay safe against re-runs and hand-edited files).
- Whether D-04's fix belongs in the `oh-my-zsh` registry entry's own install method
  (e.g. a new `post_install` action, extending the same `installer/post_install.py`
  mechanism Phase 15.5 also extends) or as a one-off fix inside `installer/omz.py`
  itself — implementation shape for research/planning to resolve.
- Exact `kitty.conf`/`wezterm.lua`/Konsole-profile write mechanism (idempotent
  upsert of a single line/key vs. a dedicated managed block with markers, to avoid
  clobbering user customizations already in those files).

## Existing Code Insights

### Reusable Assets
- None yet directly reusable for terminal-config file writing (new territory for this
  codebase) — `installer/locations.py`'s existing rc-path resolution machinery
  (`rc_paths_for_mode`, referenced in prior phases) may offer a useful pattern for
  "find the right config file path per platform," even though it currently only
  targets shell rc files, not terminal-emulator configs.

### Established Patterns
- `post_install.py`'s closed-dispatch-table doctrine and `installer/host_setup.py`'s
  "never launch what needs a real terminal from the worker thread" doctrine both
  likely constrain how this phase's config-writing action is triggered and executed —
  research should confirm whether writing a config file (not running a shell command)
  falls under the same constraints or is meaningfully different (no subprocess launch
  involved, just a file write).
- `wizard_app.py`'s `_install_closed` refresh-trigger pattern (established in Phase
  15.1/15.4) is the established shape for "resync something whenever install state
  changes."

### Integration Points
- `installer/wizard_app.py`'s `_install_closed` and the Policies screen's activation
  path (where oh-my-zsh could be turned on after the fact) are the two integration
  points D-01's idempotent-refresh requirement needs to hook into.
