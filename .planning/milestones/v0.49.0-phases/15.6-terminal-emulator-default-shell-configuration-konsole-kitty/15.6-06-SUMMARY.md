# Phase 15.6 Plan 06: Remaining terminal-synchronization call sites Summary

**Interactive completion, unattended installation, the command-line uninstall route, and interactive Uninstall removal now all reapply Linux terminal-emulator zsh configuration through the exact same composition-root closure Plans 04/05 established for Policies and the direct `u` update — completing D-01 across every Phase 15.6 lifecycle route, with a follow-up warning always reaching a visible surface and never falsifying a completed primary outcome.**

## Performance

- **Duration:** ~75 min
- **Completed:** 2026-09-21T21:30:48-03:00
- **Tasks:** 3
- **Files modified:** 4

## Accomplishments
- `UnifiedApp._install_closed` now calls an optional, injected `terminal_sync: Callable[[], str | None] | None` closure after every close event, unconditionally (never gated on a selected tool id or a successful outcome), through the existing `run_live` seam so a raised `OSError` is a secondary, non-fatal warning.
- The active-screen resolution that used to be catalog-tier-only (`self._catalogs.get(self.current_view)`) is generalized (`self._visible_app_screen()` falling back to `self.screen`) so a warning is rendered on whichever `AppScreen` is genuinely visible — Doctor, Uninstall, or Policies included — never dropped merely because `current_view` names a non-tier key. A named `self._pending_warnings` queue, flushed from `show_view` on the next navigation, covers the structurally-unreachable case where no `AppScreen` is resolvable at all.
- `setup.py` extracted `_build_app`'s inline `_sync_omz_terminals` body into a module-level `_sync_terminals(platform) -> str | None`, reused by a new `_sync_terminals_and_report(console, platform)` helper that both `main()`'s noninteractive `--all`/category route and `_run_uninstall`'s command-line teardown route call after their own primary completion — printing any warning to the console without ever flipping an already-determined exit code.
- `UninstallInputs` gained an optional `terminal_sync` field; `UninstallScreen._apply_removal` invokes it unconditionally on every successful sweep (after the primary removal summary is assembled, never gated on `tool_count` since `sync_terminal_shells`' own no-zsh reversion branch matters even for an env-lever-only sweep), appending a caught `OSError` as a warning without ever changing `applied` or downgrading the primary removal outcome.
- `_build_app` wires the identical `_sync_omz_terminals` closure into `UnifiedApp`'s `terminal_sync` kwarg, `omz_plugins_policy`'s `terminal_sync`, `UpdateService`'s `terminal_follow_up`, and now `UninstallInputs.terminal_sync` — one composition-root closure, four call sites, proven by direct object-identity assertions in tests.

## Decisions Made
- Generalized `_install_closed`'s screen lookup rather than adding a second, Doctor/Uninstall/Policies-specific code path — one lookup (`self._catalogs.get(...) or self._views.get(...)`, exposed as `_visible_app_screen()` for the `self.screen` fallback) covers all six views uniformly, matching this project's "one navigation path" convention (`.claude/architecture.md` rule 2).
- Kept the pending-warning queue even though the generalized lookup makes the `active is None` branch structurally unreachable today — the plan explicitly calls for "a named pending-warning queue," and a future caller pushing `ExecuteScreen` from an as-yet-unbuilt view would otherwise silently regress T-15.6-13's guarantee.
- Reordered `setup.py`'s `uninstall_inputs` construction (a pure reordering, no behavior change) rather than deferring the reference through a lambda, keeping `terminal_sync=_sync_omz_terminals` the same direct-reference style every other `_sync_omz_terminals` call site already uses.

- The Bash sandbox's `rtk` wrapper intermittently refuses plain `git` invocations inside this worktree when a command mixes `git` with other shell constructs (`cd &&`, multi-line scripts, pipelines) — a known, previously-flagged environment issue in this project. Worked around by invoking `/usr/bin/git` directly and splitting compound commands into single, plain `git <verb>` calls.
- `make test`'s coverage report is sensitive to source-file edits landing while pytest-cov is still running: two background `make test` runs launched while I was actively editing `setup.py`/`installer/wizard_app.py` for a *later* task reported a spuriously low coverage percentage (89.52%) with the same pass count — a measurement artifact from coverage recomputing line counts against a moving source file, not a real regression. Resolved by re-running `make test` sequentially with no concurrent edits once each task's code was final; the clean re-run (and a second independent clean run) both reported 95.58% coverage with 2483 passed, 1 skipped.
- Applied manual mutation-testing verification (no mutmut/cosmic-ray configured in this project) on three load-bearing guards: (1) `_install_closed`'s `self._terminal_sync is not None` guard — inverted to `is None`, confirmed the two directly-relevant tests fail, restored; (2) `_apply_removal`'s implicit "only after a successful sweep" ordering — moved the synchronizer call before the `swept is None` early return, confirmed `test_uninstall_apply_never_calls_the_terminal_synchronizer_after_a_failed_sweep` fails, restored; (3) `_sync_terminals_and_report`'s `try/except OSError` wrapper — removed it, confirmed both CLI-route OSError-survival tests fail with an uncaught `OSError` traceback, restored.
