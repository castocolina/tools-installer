# Phase 12.4 — D-04 Full-Catalog Onboarding Checklist Audit

**Scope:** all 89 `[[tool]]` entries in `installer/registry.toml`, checked against `.claude/architecture.md`'s
"Tool onboarding: tier, dependencies, and postinstall classification" checklist (Plan 12.4-03). Confirmed
89/89 via `python3 -c "import tomllib; ... len(tools)"` against the committed registry at this plan's start.

**Methodology:** Pass 1 (postinstall-mechanism classification) manually reads every `ai`-tier entry (the tier
where an agent-integration-shaped gap is structurally possible) plus live spot-checks of the 7 `skill_pack`
entries' current upstream install docs. Pass 2 (tier/dependency correctness) runs a full programmatic sweep
over all 89 entries — every method-kind requiring a manager tool (`node`→pnpm, `uv-tool`→uv, `sdkman`→sdkman)
is checked against `requires`, catching the exact shape rtk/graphify's own gap would have taken if it were a
dependency-declaration miss rather than a postinstall miss — plus a manual read of the two entries the sweep
alone can't judge (tier *rationale* correctness, not just dependency completeness). Passes 3 and 4 are the
two named pre-existing/deferred findings this plan's `<read_first>` directed.

## Pass 2 — Tier correctness and dependency declaration (full 89-entry sweep)

Programmatic sweep (`python3` + `tomllib`) checked every entry with a `node`/`uv-tool`/`sdkman`-kind method
against its own `requires` list for the corresponding manager tool (`pnpm`/`uv`/`sdkman`). **Zero missing
manager-dependency declarations found** across all 89 entries — every `node`-kind entry (`mmdc`, `puppeteer`)
already declares `pnpm`; every `uv-tool`-kind entry (`graphify`, `spec-kit`'s `specify-cli` target, and others)
already declares `uv`; no `sdkman`-kind entry is missing `sdkman` in `requires`.

Manual spot-check of tier *rationale* (not just presence) on the two entries this phase's own work touched
most directly: `rtk`/`graphify` remain correctly `ai`-tier (agent-facing tooling an agent host consumes) — no
change from their existing classification. No `system`/`user`-tier entry was found misclassified as lacking
an agent-host relationship it actually has, or vice versa.

**Pass 2 closing statement:** no tier or dependency-declaration gap found across the full 89-entry sweep. The
existing `tests/test_registry.py` tier-distribution and dependency-integrity tests already CI-pin the
aggregate counts this sweep re-derived independently and matched exactly (26/41/22).

## Pass 3 — Pre-existing dead-code finding (noted, intentionally unfixed)

`installer/model.py`'s `Tool.post_install` (plural, line 268), `POST_INSTALL_ACTIONS` (line 46), and
`SENSITIVE_POST_INSTALL_ACTIONS` (line 54) — confirmed this session via
`grep -rn "\.post_install\b" installer/ tests/` (zero hits outside `model.py`'s own declaration/parsing code)

## Pass 4 — graphify output-location question (12.4-CONTEXT.md, noted, no-code-change)

12.4-CONTEXT.md's `canonical_refs` flagged "graphify output-location unification" as research never yet
done. Confirmed this session that 12.4-RESEARCH.md never investigated it (`grep -in "graphify-out\|gsd-graphify\|output.location" 12.4-RESEARCH.md` returns nothing).

Direct investigation: the currently-installed `~/.claude/skills/gsd-graphify/SKILL.md` already runs

```
graphify update . \
  && cp graphify-out/graph.json .planning/graphs/graph.json \
  && cp graphify-out/graph.html .planning/graphs/graph.html \
  && cp graphify-out/GRAPH_REPORT.md .planning/graphs/GRAPH_REPORT.md
```

— an already-coordinated, intentional two-stage design (build once into graphify's own default
`graphify-out/`, then copy the specific artifacts GSD consumes into `.planning/graphs/`), not "two separate,
uncoordinated locations" as 12.4-CONTEXT.md feared.

Three reasons no code change is warranted or possible:
1. The underlying concern is already addressed by the currently-installed GSD version's own copy-based design.
2. `gsd-graphify`'s `SKILL.md` lives at `~/.claude/skills/` — a global, cross-project GSD asset, not a file
   this repository's git history tracks. No change to `installer/*.py`/`registry.toml` could influence it
   either way.
3. This question concerns graphify's knowledge-graph BUILD subcommand (`graphify update .`), entirely
   distinct from the per-host agent-integration `install` subcommand (`graphify <host> install`) D-02's own
   `_graphify_register` hook (Plan 12.4-02) actually wires.

**No new todo logged** — this is a closed, no-action finding, not a deferred one.
