## Summary

This phase has two deliverables: (1) a reusable onboarding checklist + skill
for future `registry.toml` additions, and (2) using that same rigor to close a
real, already-diagnosed gap — `rtk` and `graphify` are fully installable
catalog tools (Phase 8) whose per-agent-host setup commands were researched
but never wired into `installer/postinstall.py` (Phase 9 built the mechanism
and wired only `codegraph`, deliberately deferring graphify's registration
step to "Phase 9" in 08-RESEARCH.md's own Open Question 2 — a deferral that
was never picked back up).

The codebase already has **three, architecturally distinct** postinstall
mechanisms, not one: (a) `Tool.postinstall` — a closed, code-owned hook-name
dispatch table in `installer/postinstall.py`, automatic and non-interactive,
today only `codegraph-mcp-register`; (b) `skill_lifecycle` on `skill_pack`-kind
tools — per-operation `mode = "manual-required"` (display instructions) or
`mode = "command"` (dispatch a reviewed `operation_id`, e.g.
`codex_plugin_status`), used by `opengsd`/`ponytail`/`openspec`/etc.; (c)
`host_setup`-kind methods — a closed `HOST_SETUPS` registry of reviewed
console handoffs for tools needing a terminal or project target (`pi` is the
only current entry). D-02 correctly targets mechanism (a): rtk and graphify
are real, already-on-PATH binaries after install (not `skill_pack`s, not
interactive-only), exactly matching codegraph's shape. The new checklist's
core deliverable is a decision tree routing any *new* tool into one of these
three mechanisms (or none).

This session live-verified rtk (installed locally, v0.44.1; upstream latest
is **v0.49.0, published today** 2026-09-11) and graphify (installed locally,
v0.9.54) by actually running them in an isolated scratch sandbox with seeded
pre-existing config files, not just reading documentation. The results
diverge from what 08-RESEARCH.md/12.4-CONTEXT.md carried forward in two
load-bearing ways: rtk's flag syntax has changed shape since Phase 8
(`--agent cursor`, not `--agent-cursor`; no `--claude` flag — Claude is the
unflagged default) and rtk has a real, reproduced bug where `--agent cursor`
*also* unconditionally attempts to write Claude-Code-specific files even when
Claude Code was never selected or installed — a direct D-01a hazard that must
be designed around, not assumed away. Graphify, by contrast, was empirically
proven merge-safe on every file it touches (`CLAUDE.md`, `.claude/CLAUDE.md`,
`.claude/settings.json`) via a real, adversarial seeded-content test.

**Primary recommendation:** Ship the checklist as a new subsection of
`.claude/architecture.md`'s existing "Registry-authoring guidelines", ship the
skill as `.claude/skills/tool-onboarding/SKILL.md` (this project's first
project-authored skill — reuse `superpowers:writing-skills` rather than
hand-authoring the SKILL.md frontmatter/trigger convention from scratch), add
`_rtk_register()`/`_graphify_register()` to `installer/postinstall.py`'s
`POSTINSTALL_HOOKS` table using the exact live-verified commands in "Code
Examples" below, extract a shared `present_agent_hosts()`-style helper that
`_codegraph_mcp_register()` is refactored to call too (D-03), and treat D-04's
audit as "checklist applied to all 89 entries, findings logged" rather than
"fixes shipped in this phase" — the grep-scan performed this session found no
third MCP/per-host gap beyond codegraph/rtk/graphify, but did find one
adjacent, unrelated dead-code finding worth a one-line mention to the planner
(see "Don't Hand-Roll").

## Architecture Patterns

### The three existing postinstall/setup mechanisms (the checklist's decision tree)

```
New registry tool needs post-install setup?
│
├─ Is the tool a fully-installable, on-PATH binary/CLI after a normal
│  Method (github_release/brew/uv-tool/node/...) succeeds, AND does it need
│  a non-interactive, host-detection-aware follow-up step (register an MCP
│  server, patch a per-agent config file)?
│      └─ YES → Tool.postinstall = "<hook-name>"
│               installer/postinstall.py::POSTINSTALL_HOOKS (closed dispatch
│               table). Registry can only select a hook NAME, never a literal
│               command. THIS is the mechanism D-02 uses for rtk/graphify.
│
├─ Is the tool delivered as a "skill" into one or more AI-assistant hosts
│  (not a standalone binary — e.g. an npx-installed skill pack, a
│  marketplace plugin) where install/status/update/removal are each either
│  fundamentally interactive (choosing which harness/project) or need a
│  human trust-review step (reviewing hook code before trusting it)?
│      └─ YES → [[tool.method]] kind = "skill_pack"
│               [tool.skill_lifecycle] with per-operation mode =
│               "manual-required" (show instructions, do nothing automated)
│               or mode = "command" (dispatch one of a closed
│               operation_id set: codex_plugin_status, pi_package_status —
│               these are READ-ONLY status probes, not installers)
│
└─ Does the tool's own setup require a live terminal / user-selected
   project target that cannot be safely scripted from a Textual worker
   thread (interactive prompts with no non-interactive flag)?
       └─ YES → [[tool.method]] kind = "host_setup", setup_id = "<id>"
                installer/host_setup.py::HOST_SETUPS (closed registry of
                reviewed console handoffs, displayed not executed) — today
                only "pi"
```

`installer/model.py`'s `POST_INSTALL_ACTIONS` tuple (`configure_path`,
`source_shell_init`, `set_login_shell`, `enable_corepack`, `pnpm_setup`,
`write_agent_reference`) and the parallel `Tool.post_install` field are a
**fourth, textually similar but semantically distinct** name — see "Don't
Hand-Roll" below; it is not relevant to D-02's decision and should not be
confused with `Tool.postinstall` (singular).

### Pattern: `_rtk_register()` / `_graphify_register()` — mirroring `_codegraph_mcp_register()`

**What:** New functions in `installer/postinstall.py`, registered in
`POSTINSTALL_HOOKS` under new names (e.g. `"rtk-register"`,
`"graphify-register"`), added to `installer/model.py`'s
`POSTINSTALL_HOOK_NAMES` frozenset (duplicated, not imported — matching the
existing layering comment there), and wired via `postinstall = "rtk-register"`
/ `postinstall = "graphify-register"` on the two `[[tool]]` entries at
`installer/registry.toml:1582` and `:1541`.

**Key structural difference from codegraph that the plan must account for:**
codegraph has exactly one *kind* of method (`github_release`, two OS-scoped
variants) so `bin_dir(method.params.get("bin_dir")) / "codegraph"` always
resolves correctly. **`rtk` has FOUR methods across TWO kinds**
(`github_release` ×3 arch/OS-gated + `brew` ×1 fallback). The hook receives
whichever `Method` actually succeeded (`install_tool`'s existing
Method-awareness, `installer/engine.py:150-154`), so `_rtk_register()` must
branch:
- `method.kind == "github_release"` → resolve via
  `bin_dir(method.params.get("bin_dir")) / "rtk"` (codegraph's pattern; PATH
  is not guaranteed wired yet for a fresh `~/.local/bin` install).
- `method.kind == "brew"` → resolve via `shutil.which("rtk")`. This is safe
  because `resolve_methods` only offers a `brew` method when `brew` itself is
  already resolvable, and Homebrew symlinks a newly installed formula's
  binary into the *same* prefix `bin` directory `brew` itself lives in — the
  same directory that must already be on this process's PATH for `brew` to
  have been invocable at all. `graphify` has only one method kind
  (`uv-tool`), so this branch is unnecessary there — `uv tool install`'s shim
  lands in the same default `~/.local/bin` this project's `bin_dir(None)`
  already assumes (confirmed: `installer/executors.py::_uv_tool` does no
  custom bin-dir management, `graphify`'s registry entry declares no
  `bin_dir` param).

**Exact per-host commands — live-verified this session (see "Code Examples"
for the full evidence and caveats):**

| Host (catalog id) | `rtk` command | `graphify` command |
|---|---|---|
| `claude` | `rtk init -g --auto-patch` | `graphify claude install` |
| `opencode` | `rtk init -g --opencode --auto-patch` | `graphify opencode install` |
| `codex` | `rtk init -g --codex` (no `--auto-patch` — see Pitfall) | `graphify codex install` |
| `cursor-agent` | `rtk init -g --agent cursor --auto-patch` (see Pitfall — this call ALSO touches Claude's files) | `graphify cursor install` |

Both tools' scope defaults to **global** with no extra flag needed for
graphify (bare `graphify <host> install`, no `--project`, is global/user-scope
by design — confirmed via README's own Step 1/2 framing and this session's
own scratch runs); rtk needs the explicit `-g`/`--global` flag on every
invocation (its default without `-g` is project-local).

### Pattern: shared host-presence utility (D-03)

**Recommendation:** add a small, pure function next to (or inside)
`installer/postinstall.py` — e.g. `present_agent_hosts(tools: Mapping[str,
Tool]) -> frozenset[str]` — that computes `is_installed` exactly once per
catalog id over the canonical four-host set (`claude`, `codex`, `opencode`,
`cursor-agent`; the same set `_CODEGRAPH_TARGETS` already hardcodes) and
returns which of them are present. `_codegraph_mcp_register`,
`_rtk_register`, and `_graphify_register` all call this ONE function instead
of each re-deriving the CSV/host-presence loop
`_codegraph_mcp_register` currently inlines (`installer/postinstall.py:84-88`).
This satisfies D-03's literal ask ("not reimplemented per-tool") without
inventing new caching machinery: `installer.status.is_installed` is already a
cheap, synchronous, no-subprocess call (`shutil.which` plus a few `Path.exists`
checks — see `installer/status.py:16-40`), so the "cached for the duration of
a postinstall run" framing in CONTEXT.md matters more for **consistency**
(every hook in the same `run_installs` batch sees the identical host set)
than for raw performance. `installer/session.py::run_installs` threads the
*same* `catalog` mapping object into every `install_tool()` call within one
batch (`installer/session.py:96-99, 108`), so a plain
`functools.lru_cache`-style memo keyed on `id(tools)` would work if actual
caching (not just DRY) is wanted — but this is optional; recomputing four
cheap `is_installed` calls up to 3 times per batch (codegraph + rtk +
graphify) is negligible. **Recommend: DRY the function, skip literal caching
unless a future phase's tool count makes it worth it** — do not over-engineer
a cache invalidation story CONTEXT.md's own discretion clause does not
require.

Per-tool target-id *mapping* tables (which external flag/subcommand each
catalog host id maps to) must stay **separate per tool** — they are
genuinely different vocabularies (codegraph: `--target cursor`; rtk:
`--agent cursor`; graphify: `cursor install` subcommand) and merging them
into one shared table would force an artificial coupling between three
independently-versioned upstream CLIs.

### Anti-Patterns to Avoid

- **Passing `--target auto`-equivalent flags:** already-established anti-pattern
  from Phase 9 (codegraph); rtk/graphify have no direct equivalent of `--target
  auto`, but the parallel risk is calling `rtk init -g` (bare, defaults to
  Claude) when the intent was actually "register whichever hosts are present" —
  always pass an explicit per-host flag/subcommand per the table above, never
  rely on a tool's own default-target behavior.
- **Assuming `--auto-patch` is universally required or universally safe:**
  it is required for claude/opencode/cursor (settings.json patching can
  prompt without it) but **rejected outright** (`rtk: --codex cannot be
  combined with --auto-patch`) for codex, since codex's rtk integration never
  touches `settings.json`. A hook that blindly appends `--auto-patch` to every
  invocation will hard-fail on the codex branch.
- **Reusing codegraph's single-CSV-invocation shape for rtk:** codegraph
  accepts one `--target claude,cursor` call for multiple hosts; rtk requires
  **one separate invocation per host** (no CSV/multi-target flag exists in
  rtk's CLI). Graphify is the same — one subcommand-per-host, no CSV.

## Common Pitfalls

### Pitfall 1: rtk's `--agent cursor` unconditionally also writes Claude Code files — reproduced live

**What goes wrong:** Running `rtk init -g --agent cursor --auto-patch`
against a fresh home directory that has `.cursor/` but has **never had Claude
Code configured** fails with:
```
rtk: Failed to write RTK.md: <home>/.claude/RTK.md: Failed to create temp
file in <home>/.claude: No such file or directory (os error 2)
```
This is not a documentation gap — it is the CLI attempting a **second,
unrequested** write (Claude Code's `RTK.md`/`settings.json`) as a side effect
of any `--agent cursor` invocation, confirmed by running the exact same
command against a home directory that already *had* `.claude/` pre-populated:
the output showed rtk printing a full "RTK hook registered (global) ...
Command: rtk hook claude ... settings.json: hook already present" block
**before** the actual Cursor-targeted block. `[VERIFIED: live execution, rtk
0.44.1, this session, isolated $HOME override]`.

**Why it happens:** Unknown from the outside — not documented in rtk's
README or `--help` text; appears to be an internal implementation detail of
rtk's Cursor integration path (possibly: Cursor's hook mechanism is modeled
as "install Claude's hook too, since Cursor is Claude-hook-compatible" by
rtk's own author, given both integrations use the same `preToolUse`-family
mechanism per the README's own integration table).

**How to avoid:** This must be resolved **at implementation time against the
exact rtk version the registry will actually install** (`v0.49.0`, not the
locally-cached `0.44.1` this session tested) before `_rtk_register()` calls
`--agent cursor` on any machine where Claude Code is absent. Two honest
options, neither verified safe yet: (a) always ensure `~/.claude/` exists
before calling the cursor branch (creates minimal Claude scaffolding even on
a machine where Claude Code was never installed or selected — a real,
debatable violation of "never configure an unselected host"); (b) skip rtk's
Cursor registration entirely unless Claude Code is *also* present on the same
machine (narrows the feature, documented as a caveat, mirroring the project's
own precedent for rtk's weaker Codex integration in
`installer/registry.toml:1321-1325`). **Recommend the planner treat this as an
explicit open question requiring a fresh live-verification pass against
v0.49.0 before the `_rtk_register` task is considered done** — do not ship a
guess.

**Warning signs:** A checksum-verified `install_tool` call for a
Cursor-only machine unexpectedly leaves files under `~/.claude/`.

### Pitfall 2: `--auto-patch` is not universally combinable — reproduced live

**What goes wrong:** `rtk init -g --codex --auto-patch` exits nonzero:
`rtk: --codex cannot be combined with --auto-patch`. `[VERIFIED: live
execution, rtk 0.44.1, this session]`.

**Why it happens:** `--codex` mode never patches `settings.json` (`--codex`'s
own `--help` text: "no Claude hook patching") — there is nothing for
`--auto-patch` to apply to, and rtk treats the combination as a usage error
rather than a silent no-op.

**How to avoid:** `_rtk_register()`'s codex branch must omit `--auto-patch`
entirely: `rtk init -g --codex`. Confirmed this alone completes non-interactively
(exit 0, no hang) with no flag needed — REQ-postinstall-noninteractive-only is
satisfied for codex without any extra flag.

**Warning signs:** A generic "always append `--auto-patch`" implementation
will hard-fail specifically on the codex branch — easy to miss if codex is
tested last or not at all.

### Pitfall 3: `rtk init -g --agent cursor` requires `~/.cursor/` to pre-exist; does not create it

**What goes wrong:** In a fresh `$HOME` with no `.cursor/` directory at all,
`rtk init -g --agent cursor` fails with the same "Failed to create temp
file... No such file or directory" pattern as Pitfall 1, but for `.cursor/`
itself. `[VERIFIED: live execution, rtk 0.44.1, this session]`. Note the
*default* (bare, Claude-targeted) `rtk init -g` does **not** have this
problem — it successfully created `~/.claude/` from nothing in the same
session's tests. The directory-creation behavior is inconsistent across
rtk's own agent-target code paths.

**How to avoid:** In practice this is unlikely to bite in production: a
machine with Cursor CLI actually installed has almost certainly already had
Cursor create its own `~/.cursor/` directory (e.g. on first run, or via
`cursor-agent`'s own install script). Still, this should be verified — not
assumed — against a genuinely fresh Cursor install before this phase's tests
are considered a full proof, and is a candidate for a defensive
`ensure_dir(Path.home() / ".cursor")` call before invoking rtk's cursor
branch (cheap, has no destructive effect on an existing directory,
`installer.locations.ensure_dir` already exists for exactly this).

### Pitfall 4: graphify and rtk both need PER-HOST invocations, not one CSV call

**What goes wrong:** A `_rtk_register()`/`_graphify_register()` implementation
copy-pasted from `_codegraph_mcp_register()`'s shape will try to build one
composed multi-target string (codegraph's `--target claude,cursor` CSV
pattern) and pass it to rtk or graphify — neither tool supports that syntax;
each host needs its own separate command invocation (see the table under
"Pattern: `_rtk_register()`/`_graphify_register()`" above).

**How to avoid:** Loop over present hosts and invoke the runner once per
host, matching each host's row in the command table. Accumulate
per-host failures into one combined warning string (mirroring
`_codegraph_mcp_register`'s single `CommandError → str` pattern, but for N
calls instead of one) rather than aborting on the first failed host — a
failure on one host's registration should not prevent the others from
succeeding, consistent with `postinstall_warning`'s own "never fails the
tool's own install" framing.

### Pitfall 5 (D-01a, resolved by direct test, not a pitfall to avoid — recorded for completeness): graphify's writes ARE merge-safe

**What was tested:** A scratch project directory was seeded with a
`CLAUDE.md` containing marker content and a `.claude/settings.json`
containing a pre-existing `permissions.allow`, an unrelated `PreToolUse` hook
on a different matcher, and a custom `statusLine` entry (the exact GSD
statusline-overwrite failure mode D-01a is worried about, deliberately
reproduced as an adversarial test). `graphify claude install --project` was
run twice. Result: the marker content in `CLAUDE.md` was preserved verbatim
with a new `## graphify` section appended; `.claude/settings.json`'s
`permissions`, the unrelated hook, and `statusLine` were all preserved
byte-for-byte while graphify's own two `PreToolUse` matchers were added
alongside them; the second run added zero duplicate entries (idempotent).
`[VERIFIED: live execution, graphify 0.9.54, this session, adversarial seeded
content]`. The same test, adapted for rtk's global (non-`--project`) scope via
an isolated `$HOME` override, produced the same result for rtk's Claude Code
integration: `settings.json`'s pre-existing `permissions`/hook/`statusLine`
were preserved, rtk's own hook was appended, and rtk additionally writes a
`.bak` backup of `settings.json` before patching it. **Both tools' Claude Code
integration path is empirically confirmed D-01a-compliant** — this is the one
genuinely de-risked finding in this research; the planner does not need to
treat "does this overwrite user config" as an open question for the `claude`
host specifically, only for the cursor-implies-claude coupling in Pitfall 1.

## Code Examples

### `_rtk_register()` skeleton (new, `installer/postinstall.py`)

```python
# Illustrative skeleton, not a literal patch — the planner's plan should
# re-derive exact error handling from _codegraph_mcp_register()'s own
# CommandError-to-string pattern (installer/postinstall.py:95-109).

_RTK_HOST_ARGS: dict[str, tuple[str, ...]] = {
    # claude: bare "-g" is the documented default; no "--claude" flag exists.
    "claude": ("-g", "--auto-patch"),
    "opencode": ("-g", "--opencode", "--auto-patch"),
    # --codex rejects --auto-patch outright (rtk: "--codex cannot be
    # combined with --auto-patch") -- it never touches settings.json, so
    # there is nothing to auto-patch. See Pitfall 2.
    "codex": ("-g", "--codex"),
    # See Pitfall 1: this ALSO writes Claude-Code-specific files even when
    # claude is not present/selected on this machine, as of rtk 0.44.1 --
    # MUST be re-verified against v0.49.0 before shipping.
    "cursor-agent": ("-g", "--agent", "cursor", "--auto-patch"),
}


def _rtk_register(method: Method, runner: Runner, tools: Mapping[str, Tool]) -> str | None:
    present = present_agent_hosts(tools)  # D-03 shared helper
    if not present:
        return None
    rtk_bin = _resolve_rtk_binary(method)  # branches on method.kind, see below
    errors: list[str] = []
    for host_id in _RTK_HOST_ARGS:  # fixed, declared order -- deterministic
        if host_id not in present:
            continue
        try:
            runner([rtk_bin, "init", *_RTK_HOST_ARGS[host_id]])
        except CommandError as exc:
            errors.append(f"{host_id}: {exc}")
    return "; ".join(errors) if errors else None


def _resolve_rtk_binary(method: Method) -> str:
    if method.kind == "brew":
        # brew's own bin dir is already on PATH -- brew itself had to be
        # resolvable to run this install in the first place, and Homebrew
        # symlinks a formula's binary into that same prefix bin dir.
        found = shutil.which("rtk")
        if found:
            return found
    bin_dir_param = method.params.get("bin_dir")
    override = bin_dir_param if isinstance(bin_dir_param, str) and bin_dir_param else None
    return str(bin_dir(override) / "rtk")
```

### `_graphify_register()` skeleton

```python
_GRAPHIFY_HOST_SUBCOMMANDS: dict[str, str] = {
    "claude": "claude",
    "opencode": "opencode",
    "codex": "codex",
    "cursor-agent": "cursor",
}


def _graphify_register(method: Method, runner: Runner, tools: Mapping[str, Tool]) -> str | None:
    present = present_agent_hosts(tools)
    if not present:
        return None
    bin_dir_param = method.params.get("bin_dir")
    override = bin_dir_param if isinstance(bin_dir_param, str) and bin_dir_param else None
    graphify_bin = str(bin_dir(override) / "graphify")  # uv-tool's only kind
    errors: list[str] = []
    for host_id, subcommand in _GRAPHIFY_HOST_SUBCOMMANDS.items():
        if host_id not in present:
            continue
        try:
            runner([graphify_bin, subcommand, "install"])
        except CommandError as exc:
            errors.append(f"{host_id}: {exc}")
    return "; ".join(errors) if errors else None
```

### Shared host-presence helper (D-03)

```python
# Source: pattern extracted from installer/postinstall.py's existing
# _CODEGRAPH_TARGETS-driven loop (installer/postinstall.py:84-88).
_AGENT_HOST_IDS: tuple[str, ...] = ("claude", "codex", "opencode", "cursor-agent")


def present_agent_hosts(tools: Mapping[str, Tool]) -> frozenset[str]:
    """Which of this project's four agent-host catalog ids are installed.

    Computed fresh each call (cheap: shutil.which + a couple of Path.exists
    checks, no subprocess) -- callers within one run_installs batch share
    the same `tools` mapping object, so this is the single place all
    _*_register hooks read host presence from (D-03), never re-derived
    per-tool.
    """
    return frozenset(
        host_id
        for host_id in _AGENT_HOST_IDS
        if (tool := tools.get(host_id)) is not None and is_installed(tool)
    )
```
