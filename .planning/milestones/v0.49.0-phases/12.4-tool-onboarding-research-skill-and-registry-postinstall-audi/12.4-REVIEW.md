## Warnings

### WR-01: `_resolve_rtk_binary`'s brew-fallback path resolves to a location the binary can never be at

**File:** `installer/postinstall.py:158-168`

**Issue:** When the succeeded `Method.kind == "brew"` and `shutil.which("rtk")` returns `None` (rtk not yet on this process's PATH — e.g. Homebrew's `shellenv` was never sourced into the running installer process, or brew's own bin dir was added to the *shell*'s PATH but not re-exported into this already-running Python process), `_resolve_rtk_binary` falls back to `bin_dir(override) / "rtk"`, i.e. `~/.local/bin/rtk` by default:

```python
def _resolve_rtk_binary(method: Method) -> str:
    if method.kind == "brew":
        found = shutil.which("rtk")
        if found:
            return found
    bin_dir_param = method.params.get("bin_dir")
    override = bin_dir_param if isinstance(bin_dir_param, str) and bin_dir_param else None
    return str(bin_dir(override) / "rtk")
```

A brew-installed `rtk` is written to Homebrew's own prefix (`/opt/homebrew/bin/rtk` on Apple Silicon, `/usr/local/bin/rtk` on Intel macOS / Linuxbrew), never to `~/.local/bin`. `bin_dir(None)` (`~/.local/bin`) is this project's own userspace install location for `github_release`-installed tools — it has no relationship to where brew puts a binary. So the fallback branch, which exists specifically to cover "brew just installed it but it's not resolvable via PATH yet," resolves to a path that is *guaranteed* not to contain the binary in exactly that scenario.

This is reachable in production, not merely theoretical: `rtk`'s registry entry (`installer/registry.toml:1618-1642`) declares three `github_release` methods (macOS, Linux amd64, Linux arm64) ranked ahead of a `brew` fallback method (`_RANK["github_release"] == 20` < `_RANK["brew"] == 40` in `installer/resolve.py:16,26`), and `installer/engine.py`'s method loop (`installer/engine.py:130-137`) falls through to the next-ranked method on any `ChecksumMismatch`/`CommandError`/`ExecutorError`/`VersionError` from an earlier one — so a GitHub-release hiccup (rate limit, transient network failure, upstream asset rename) legitimately lands `brew` as the *succeeding* method, at which point this bug fires.

The project already has the correct pattern for this exact "just-installed-via-brew, not yet on PATH" problem, documented in the very same repository: `installer/shellrc.py:40-46`'s `collect_bin_dirs` explicitly rejects PATH-probing for this reason ("Disk presence — not PATH probing — avoids the bootstrap chicken-and-egg: right after installing brew, `brew` is not on PATH yet but `/opt/homebrew/bin` exists"), and `installer/ownership.py` has a `_query_brew_prefix` helper (via `brew --prefix`) for resolving brew's actual install prefix. `_resolve_rtk_binary` reintroduces the very failure mode the codebase already has institutional memory about, instead of reusing either existing pattern.

The failure is silent and non-fatal by the hook contract (caught as `CommandError` -> per-host warning string, never crashes the install or marks it failed — confirmed via `run_command`'s `OSError` -> `CommandError(cmd, 127)` wrapping in `installer/run.py:48-49`), but it means: on any machine where `rtk`'s `github_release` methods fail and brew is the fallback, **all four agent-host registrations silently no-op** with no indication beyond a buried warning string, defeating the entire feature this phase shipped.

The existing test locks in the wrong value as correct, rather than flagging it:
```python
def test_resolve_rtk_binary_brew_falls_back_to_bin_dir_when_not_on_path(...):
    ...
    expected = str(Path.home() / ".local" / "bin" / "rtk")
    result = pi._resolve_rtk_binary(method)
    assert result == expected
```
(`tests/test_postinstall.py:311-318`) — this test proves the *current* behavior, not that the behavior is *correct*.

**Fix:** Resolve brew's actual prefix instead of falling back to the unrelated userspace `bin_dir`. Reuse the existing `brew --prefix` pattern (`installer/ownership.py::_query_brew_prefix`) or check well-known brew bin dirs by disk presence, mirroring `collect_bin_dirs`'s own reasoning:

```python
_BREW_BIN_CANDIDATES: tuple[Path, ...] = (
    Path("/opt/homebrew/bin/rtk"),  # Apple Silicon
    Path("/usr/local/bin/rtk"),      # Intel macOS / Linuxbrew
)


def _resolve_rtk_binary(method: Method) -> str:
    if method.kind == "brew":
        found = shutil.which("rtk")
        if found:
            return found
        for candidate in _BREW_BIN_CANDIDATES:
            if candidate.exists():
                return str(candidate)
        # last resort: still prefer a brew-shaped guess over the unrelated
        # userspace bin_dir, which a brew install never writes to
    bin_dir_param = method.params.get("bin_dir")
    override = bin_dir_param if isinstance(bin_dir_param, str) and bin_dir_param else None
    return str(bin_dir(override) / "rtk")
```
and update `test_resolve_rtk_binary_brew_falls_back_to_bin_dir_when_not_on_path` to assert against a brew-shaped path rather than `~/.local/bin/rtk`.

### WR-02: `bin_dir` override-resolution snippet is duplicated verbatim three times

**File:** `installer/postinstall.py:111-113` (`_codegraph_mcp_register`), `166-168` (`_resolve_rtk_binary`), `229-231` (`_graphify_register`)

**Issue:** The exact same two-line pattern appears three times in this one file:
```python
bin_dir_param = method.params.get("bin_dir")
override = bin_dir_param if isinstance(bin_dir_param, str) and bin_dir_param else None
```
(variable named `bin_dir_override` in the codegraph copy). This is a direct copy-paste — the rtk and graphify copies added in this phase reproduce the pre-existing codegraph pattern instead of factoring it out. `.claude/architecture.md`'s stated architecture bias is explicit on this: "prefer deleting to organizing, one data structure over parallel copies" and rule 5, "No orphan helpers... never kept 'for later'" (the inverse failure mode here: a helper that should exist but was never extracted, so the duplicate sites drift independently over time).

**Fix:** Extract a shared helper and use it at all three call sites:
```python
def _resolve_bin_override(method: Method) -> str | None:
    """A method's declared `bin_dir` param, or None to fall back to the default."""
    raw = method.params.get("bin_dir")
    return raw if isinstance(raw, str) and raw else None
```
then each call site becomes `bin_dir(_resolve_bin_override(method)) / "<name>"`.

### IN-01: `present_agent_hosts()`'s PATH-detection lag caveat isn't restated where it now matters

**File:** `installer/postinstall.py:29-39`

**Issue:** `present_agent_hosts()` is built on `installer.status.is_installed`, which itself PATH-probes via `shutil.which(tool.cmd)` (`installer/status.py:24`). The known limitation — "a P0 agent host installed EARLIER IN THE SAME wizard run may not yet be on PATH" — is documented today only in `installer/registry.toml`'s `codegraph` entry comment (around line 1502-1509), the call site that originally motivated the caveat. Now that `present_agent_hosts()` is shared by three hooks (`_codegraph_mcp_register`, `_rtk_register`, `_graphify_register`, per D-03), the caveat logically applies to all three, but a reader of `present_agent_hosts()`'s own docstring in `installer/postinstall.py` has no way to discover it without independently finding the `codegraph` registry comment.

**Fix:** Move (or duplicate a one-line pointer to) the same-run PATH-lag caveat into `present_agent_hosts()`'s own docstring, since it is now the single shared entry point for that judgment call rather than an implementation detail local to one hook.
