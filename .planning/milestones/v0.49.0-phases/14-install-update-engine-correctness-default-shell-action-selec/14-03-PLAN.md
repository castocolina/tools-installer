Two things make this more than a table lookup.

First, `oh-my-zsh`'s install script is deliberately run with its own auto-chsh disabled, because
changing the login shell to zsh has a documented Bazzite/KDE-SDDM login-failure mode
(ublue-os/bazzite#4159 — closed "not planned", with no maintainer root-cause analysis, so the
mechanism is unknown and the symptom is all that is established). D-04 makes `Platform.immutable` a
hard block, checked before anything else. That registry `CHSH = "no"` stays exactly as it is: it is
the install-script-level guard, and `set_login_shell` is a separate, explicit, opt-in step layered
on top of it — never a relaxation of it.

Second, the shell-change command itself is a PAM-authenticating, terminal-owning command. Every
runner this codebase has either discards a child's stdin outright or hands it a terminal that
Textual has already put into raw mode. This codebase already has a documented answer for exactly

leaving Textual and never launches them from its worker thread."* This plan follows that precedent:
the action produces reviewed instructions, and the installer never runs the command. The
`App.suspend()`-based in-process alternative is real (verified against the installed textual 8.2.7)
and is recorded below as a follow-up, not silently dropped.

## Design decisions this plan implements

- **D-04 — the immutable guard is first, unconditional, and not overridable.** The action returns
  nothing on an immutable host before it ever consults a confirmation callback, mirroring
  `installer/resolve.py:70-76`'s `if platform.immutable: return False` idiom. "Never offered" and
  "never executed" are both satisfied only if the guard precedes the prompt.
- **D-05 — an explicit yes, or nothing.** The action takes an optional confirmation callback and
  does nothing when it is `None` or returns false. "No callback" is the unattended case and must be
  the safe choice, mirroring `installer/session.py:85`'s documented "No callback = unattended mode:
  the hard-fail outcome stands". A registry `default_enabled_sensitive_actions` declaration must not
  be able to bypass this — CONTEXT.md is explicit that the confirmation is required even off atomic
  distros.
- **D-06 — dispatched from the existing install ladder.** The dispatch goes at
  `installer/engine.py::install_tool`'s post-success point, immediately after the existing singular
  `postinstall` hook block and before the INSTALLED outcome is constructed. It never fires on the
  already-installed short-circuit and never on the reviewed-handoff/manual-required return — the
  same single-direction trigger property the singular hook already has.
- **A consequence of D-06, stated on purpose so it is not "fixed" later.** A host that already has
  `oh-my-zsh` — which the registry detects by path (`detect_path = "~/.oh-my-zsh/oh-my-zsh.sh"`,
  `installer/registry.toml:542`), producing the ALREADY_INSTALLED short-circuit at
  `installer/engine.py:116-117` — will never be offered the login-shell action at all, because the
  short-circuit returns before the dispatch point. That is correct, not a gap: D-06 puts the action
  on the install ladder, and the single-direction trigger is exactly what makes it impossible for a
  re-run to re-propose a system mutation the user already declined once. A user who wants it after
  the fact runs the reviewed command themselves, which is the only thing the installer would have
  shown them anyway. Task 1's module docstring states this, and the SUMMARY repeats it, so the next
  reader meets it as a decision rather than as a bug report.
- **D-07 — zsh only.** One action, one tool, no shell parameter. A second shell does not exist in
  this registry, and inventing a parameter for it now would be speculative design.
- **The two similarly-named mechanisms stay disjoint.** `installer/postinstall.py`'s singular
  `Tool.postinstall` hook and this new plural `Tool.post_install` action list are validated against
  two different closed sets (`POSTINSTALL_HOOK_NAMES` versus `POST_INSTALL_ACTIONS`) and must stay
  that way. `.claude/architecture.md`'s "Phase 9: postinstall hooks" section already names this
  confusion. Put the new table in a new module; never grow the existing one.

## Chosen execution style, and the alternative not taken

`set_login_shell` produces reviewed handoff text and executes nothing. This follows
`installer/host_setup.py`'s shipped doctrine and the `HOST_SETUPS["pi"]` worked example, where a
literal tuple of reviewed command strings is shown and never launched.

The alternative — Textual's `App.suspend()` context manager, which really does release and restore
the terminal, verified present in the installed textual 8.2.7 — is viable but is a new interaction
pattern nothing else in this codebase uses, would need a `call_from_thread` hand-off to the main
thread, and rests on an unverified assumption about `chsh`'s PAM behaviour on each target distro
(14-RESEARCH.md, Assumption A1). On the machine this project is developed on, D-04's hard block makes
that path unreachable anyway. Record it in the SUMMARY as a follow-up idea; do not build it here.
