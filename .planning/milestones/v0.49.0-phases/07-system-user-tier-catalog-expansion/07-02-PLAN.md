<objective>
Add `gnu-bash` and Apple Containers (`container`) as verified `tier="system"` registry
entries — the remaining half of ROADMAP Phase 7 SC#1 — and IMPLEMENT, not just
conceptually resolve, D-01's "shows disabled when unavailable" requirement: Apple
Containers must always appear in the catalog, and while merely browsing (before any
selection or install attempt), an unavailable machine must see it rendered disabled.

This plan's first draft proposed that `Method.arch=["arm64"]`/`os=["macos"]` producing
`install_tool`'s `NO_METHOD` outcome would, by itself, satisfy D-01. Cross-AI review
(codex, cycle 1, HIGH) found this architecturally wrong for how this codebase's
interactive TUI actually decides what is selectable: `installer/app.py::run_wizard`
calls `resolve_dependencies` (`installer/deps.py`), which evaluates
`available(tool) = bool(resolve_methods(tool, platform))` and filters an unavailable
SELECTED tool out — with a "not available on this platform — skipped" warning —
*before* `install_tool` (and therefore `NO_METHOD`) is ever reached. Separately,
`installer/catalog_tui.py::CatalogScreen` never receives any platform/availability data
at all, so every tool's row is always rendered selectable regardless of platform —
confirmed by reading `_row_cells`, `_adapter()`, and `installer/tool_browser.py`'s
`BrowserAdapter` (whose `selectable` field defaults to "everything selects" and is
never overridden by the catalog). So the original plan's premise would have shipped
Apple Containers either silently filtered out of a real install run with no catalog
signal at all, or — for an even simpler browsing pass with no install attempted —
shown as ordinarily selectable with no visible difference from an available tool.
Neither is D-01's "visible AND disabled."

This IS real UI/architecture work, not a registry-data-only fix, but it is bounded:
`.claude/architecture.md`'s existing "Tier is a browsing label" section already states
the reason `CatalogScreen` has never taken a `Platform` — "a screen with no `Platform`
must not make a judgement it cannot make correctly" — and the Uninstall view already
broke exactly that limitation for its own purposes: `setup.py::_build_app` already
computes `classify_tools(tools, ..., platform=platform, ...)`, which already derives a
`UninstallState.UNAVAILABLE` state via `elif resolve_methods(tool, platform): ... else:
UNAVAILABLE` (`installer/uninstall.py`), and `UninstallScreen._tool_entry` already
renders a non-selectable row dimmed with a `selectable=False` `BrowserAdapter` field
that `ToolBrowser`'s already-generic bulk actions (`action_select_all`/`action_invert`/
`action_toggle_selected`) already honor. This plan threads that exact same,
already-shipped, already-tested pattern into `CatalogScreen` too — the "existing
unmet-requires/unavailable-dependency display pattern" D-01 asked to reuse turns out to
be the Uninstall view's dim/inert rows, not `NO_METHOD`.

This plan also fixes a real correctness gap found while grounding `gnu-bash`'s design
against this codebase (not flagged by 07-RESEARCH.md): macOS ships `/bin/bash` (ancient
3.2, SIP-protected) on every Mac, always. If `gnu-bash`'s `cmd` were the literal
string `"bash"`, `installer/status.py::is_installed`'s first line
(`shutil.which(tool.cmd)`) would return that system binary and report the entry
"already installed" on every Mac, forever — before Homebrew's newer build is ever
installed. The install action would then never run, on any machine, permanently,
which would make SC#1's "installs cleanly" claim false by construction for this one
entry. This is distinct from `zsh`'s case (07-01-PLAN.md): macOS's bundled `zsh` is a
real, modern build that genuinely satisfies `zsh`'s stated purpose, but macOS's bundled
bash 3.2 is explicitly what `gnu-bash`'s own purpose ("coexists with macOS's ancient
system bash") exists to supplement, so "any bash present" cannot be treated as
satisfying it the way "any zsh present" can.

Cross-AI review (codex, cycle 2) rejected this plan's prior "accept the macOS-version
gap, document it" resolution a SECOND time — the same HIGH finding was raised in cycle
1 and cycle 2, both times as "documented but unimplemented." This revision genuinely
implements it rather than deferring again: `installer/platform.py::Platform` gains a
real `os_version` field (from `platform.mac_ver()`, stdlib-only) and
`installer/resolve.py::_applies` gates any method declaring `min_os_version` against
it, reusing the existing, already-tested `installer/versions.py::meets_minimum` — no
new version-parsing code. Cross-AI review also found a second HIGH defect this
revision fixes: a bare `not resolve_methods(tool, platform)` (the prior draft's
catalog-availability expression) cannot tell "genuinely unsupported here" apart from
"just needs Homebrew installed first," and would dim `gnu-bash`/Apple Containers on
every fresh Mac — breaking the installer's own bare-machine bootstrap path. This
revision replaces it with `installer/resolve.py::platform_could_support`, a new,
tested predicate that resolves against a hypothetical `has_brew=True` platform to
answer "would this ever work here" rather than "does it work this exact instant." Two
MEDIUM findings are also fixed: the availability decision now lives in
`installer/resolve.py`, not inlined in `setup.py` (which stays wiring-only, per
`.claude/architecture.md` rule 4); and `installer/selection.py::unstaged_recommends`
plus `CatalogScreen.action_accept_recommends`/`on_tool_browser_accepted` now all
filter through the same availability signal, closing a staging bypass where an
unavailable recommendation could reach the final install selection despite its
disabled row.
