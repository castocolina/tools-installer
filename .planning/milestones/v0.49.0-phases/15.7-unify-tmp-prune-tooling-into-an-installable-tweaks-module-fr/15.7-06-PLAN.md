**Construction point, named (resolved during replanning round 2; review HIGH 15.7-06).** The
previous revision named the SEAM the closure travels through but never the PLACE it is built.
That gap is not cosmetic: in `setup.py::_run_interactive_wizard`, `_execute_inputs(...)` is
evaluated as an ARGUMENT of the `_build_app(...)` call, so there is no point in the current code
where one object could be handed to both — and this plan's identity assertions were therefore
unsatisfiable as written. Resolved by decoupling the closure from the constructed Policy and
hoisting it:

- **`setup.py::_disk_pressure_probe(platform, *, timer_cache) -> Callable[[], DiskPressure]`** is
  THE construction point. One named module-level helper, one call per route.
- It deliberately does NOT take the daemon `Policy`. "Is a background cleanup running on this
  machine" is a property of the machine, resolvable from the platform plus the module-level
  artifact path constants — the launchd plist path on macOS, the systemd unit dir plus the
  INJECTED `TimerStateCache` on Linux, and `DaemonState.UNAVAILABLE` when `systemctl` does not
  resolve. Because it needs no `Policy`, it does not need `_build_app`'s internal `installed` map
  either, so it can be built BEFORE `_build_app` is called. That decoupling is what makes the
  identity requirement satisfiable at all; hoisting `_build_daemon_policy` out of `_build_app`
  instead would have duplicated an `is_installed` pass over the whole catalog at every route.
- **`timer_cache` is a REQUIRED keyword, and the probe never constructs one
  (resolved during replanning round 3; review HIGH cycle 3).** The previous revision said the
  Linux answer came from "plan 15.7-01's `TimerStateCache`" while also saying the probe takes no
  `Policy` — which left no path by which the shared instance could reach it, so the probe would
  have imported `TimerStateCache` from `installer/systemd_daemon.py` and built a SECOND one,
  breaking the very invariant both plans assert. Plan 15.7-01's **D-01e** resolves it: the cache
  is built by `setup.py::_timer_state_cache(platform, which=…, read_output=…)` — which returns
  None on macOS and on a Linux host without `systemctl`, reusing the D-01b gate — and is handed to
  both this probe and `_build_daemon_policy`. Required rather than defaulted, for the same reason
  `_execute_inputs`'s `disk_pressure` is required: a default would silently reinstate the
  two-caches state. A None `timer_cache` is a meaningful value here (macOS, or no systemd), not a
  missing one.
- `_run_interactive_wizard` calls `_timer_state_cache(...)` once into a named local, then
  `_disk_pressure_probe(platform, timer_cache=cache)` once into a second named local, and passes
  the probe into `_execute_inputs(..., disk_pressure=probe)` and into
  `_build_app(..., disk_pressure=probe, timer_cache=cache)`. Two references to one probe and two
  to one cache, all asserted by identity — including against `Policy.state_cache`, which plan
  15.7-01's D-01e adds precisely so this assertion has something to look at.
- `_build_app` takes both `disk_pressure` and `timer_cache` as optional parameters. When BOTH are
  None it builds ONE cache via `_timer_state_cache` and uses that single object for both
  `_build_daemon_policy` and its fallback `_disk_pressure_probe` call — so `_run_doctor`'s TTY
  branch, `_run_fix` and `_run_uninstall` get a working Doctor screen AND the one-cache invariant
  without each growing wiring. The parameters are the explicit path; the internal call is the
  default, exactly the real-defaulted-seam convention `_build_daemon_policy`'s own
  `which`/`run`/`read_output` already use. What `_build_app` must never do is call
  `_timer_state_cache` twice, or call it once for the policy and let the probe default to another.
- `_run_doctor`'s non-TTY branch and `_verify_and_clean` each call `_timer_state_cache` once and
  `_disk_pressure_probe(platform, timer_cache=…)` once, and pass the result to `run_doctor`. Those
  two routes build no `Policy` at all, so their cache has exactly one consumer — which is fine and
  is why the helper is called per route rather than memoized at module scope.
