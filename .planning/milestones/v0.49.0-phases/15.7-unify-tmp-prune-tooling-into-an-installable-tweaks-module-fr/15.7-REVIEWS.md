# Cross-AI Plan Review — Phase 15.7

## Codex Review

## 15.7-01

Summary: Strong tracer plan. The previous HIGH findings around runtime-truthful activity, bounded queries, rollback reloads, systemd availability, and Linux defaults are now explicitly addressed. The main remaining risk is incomplete service lifecycle handling during removal and an under-specified way to expose the shared `TimerStateCache`.

Strengths:

- Correctly replaces unit-file presence with runtime state via `systemctl --user is-active`, matching the existing Policy activity seam at `installer/policy.py:100-117`.
- The bounded query adapter fits the existing `run_query` contract at `installer/run.py:304-339`.
- Rollback and compensating `daemon-reload` behavior is explicitly tested.
- The Linux availability gate correctly accounts for the actual platform values (`debian`, `arch`, `fedora`, `macos`) in `installer/platform.py:19-28`.
- The plan genuinely addresses the prior duplicate-script concern through plan 15.7-07.

Concerns:

- **MEDIUM:** Removal disables/stops the timer but does not clearly stop an already-running oneshot service. The planned end-to-end sequence only records `disable --now <timer>` before deleting both files (`15.7-01-PLAN.md:187-199`). A service already executing can survive timer removal and unit-file deletion.
- **HIGH:** The “same `TimerStateCache`” requirement is not implementable as currently described. The plan says the cache is “exposed on the factory’s return” (`15.7-01-PLAN.md:414-421`), but the factory currently returns a `Policy`, and `Policy` has no cache field (`installer/policy.py:100-117`). Plan 15.7-06 separately constructs a probe without receiving that Policy.

Suggestions:

- Add an explicit service-stop step to Linux `bootout`, or prove that removal cannot occur while the service is active.
- Define the cache seam concretely: construct it in `setup.py` and pass it to both `linux_daemon_policy` and `_disk_pressure_probe`, or add a typed Policy-owned runtime-state callable.

Risk Assessment: **HIGH**, primarily because the cache-sharing contract is a cross-plan architectural dependency that currently has no concrete wiring mechanism.

Strengths:

- Root and temp mounts are measured independently, including on macOS (`15.7-02-PLAN.md:208-215`).

Concerns:

- **LOW:** The plan relies on plan 15.7-06 to prove all composition and rendering paths. That dependency is documented, but the pure-layer plan can still pass while integration wiring is absent.

Suggestions:

- Keep the explicit cross-plan integration checklist in the final summary and ensure plan 15.7-06 verifies both CLI and TUI output.

Risk Assessment: **LOW**. The plan is focused, testable, and its prior HIGH concern is genuinely resolved.

## 15.7-03

Summary: The D-02a privilege-boundary correction is now correctly reflected: user-scope mechanisms can be taken over, system-scope mechanisms are only disclosed, and no privilege escalation is attempted. The remaining concern is fail-open detection when systemd queries are unreadable.

Strengths:

- System-scope mutation is structurally rejected with `ValueError` before any command is issued (`15.7-03-PLAN.md:297-308`).
- Detection probes both scopes while keeping mutations userspace-only.
- Exact-name matching is appropriately constrained to the confirmed `ai-kit` units.
- The plan distinguishes enabled, disabled-but-active, inactive, and masked units (`15.7-03-PLAN.md:191-203`).
- Warning text correctly names `disable --now` and explicit service stopping where needed (`15.7-03-PLAN.md:310-323`).

Concerns:

- **MEDIUM:** Detection errors are treated as “nothing found.” `detect_competing` swallows `CommandError` and `OSError` and contributes an empty result (`15.7-03-PLAN.md:274-280`), with tests explicitly requiring that behavior (`15.7-03-PLAN.md:212-215`). A transient systemd/user-bus failure can therefore leave a real competitor undisclosed while the new daemon is installed. This conflicts with D-02a’s requirement to detect and disclose system-scope competitors.

Suggestions:

- Return a distinct “scope unreadable” result and surface a warning, while retaining the no-systemd/no-policy behavior for genuinely unavailable hosts.
- At minimum, distinguish “systemctl absent” from “systemctl present but query failed.”

Risk Assessment: **MEDIUM**. The privilege model is correct, but fail-open detection can violate the phase’s disclosure guarantee.

## 15.7-04

Summary: This plan successfully incorporates the prior review’s exact-path, export, ownership, validation, and coverage-caveat fixes. It has one remaining file-ownership risk: apply-time writes do not explicitly protect an existing same-named foreign configuration file.

Strengths:

- Bun’s target is pinned to the concrete path `~/.cache/bun/transpiler-cache` (`15.7-04-PLAN.md:196-206`).
- macOS uses `export`, while Linux uses systemd’s bare assignment grammar (`15.7-04-PLAN.md:240-248`).
- Variable names use an allowlist rather than an incomplete blocklist.
- Applied-state and removal share an ownership predicate (`15.7-04-PLAN.md:259-266`).
- The coverage caveat is centralized and reused across UI surfaces.

Concerns:

- **MEDIUM:** `write_linux_redirect` is required to create and atomically write the target file, but the action does not explicitly require refusing to overwrite a same-named non-owned file. The existing wrapper mechanism refuses such collisions at `installer/daemon.py:301-320`; the redirect writer should follow the same rule. The plan only specifies refusal during removal (`15.7-04-PLAN.md:121-126`).
- **LOW:** The macOS implementation intentionally leaves shared `source` lines in place, following the existing tweak behavior documented at `installer/policy.py:331-341`. The uninstall success criteria should make clear that “no rc block” does not mean “no source line.”

Suggestions:

- Add an apply-time ownership check and a test for a foreign file at the exact configured basename.
- State explicitly that shared source wiring may remain when other tweaks depend on it.

Risk Assessment: **MEDIUM**, due to possible clobbering of a same-named environment configuration.

## 15.7-05

Summary: The previous HIGH warning-delivery race is genuinely addressed by the synchronized collector, bounded wait, `finally` completion, and placement before the abort branch. The uninstall composition is otherwise solid, but one existing end-to-end test file is omitted from the modification manifest, and the warning guarantee is not absolute if `app.run()` itself raises.

Strengths:

- `extra_policies` is correctly required at composition-root uninstall functions while remaining defaulted in low-level helpers (`15.7-05-PLAN.md:349-377`).
- The collector design addresses the Textual worker race and the `summary is None` path (`15.7-05-PLAN.md:206-225`).
- Linux/macOS uninstall wording is explicitly separated.
- The same Policy instances are used for preview and sweep.
- The cache redirect’s coverage caveat is required to flow from the declaration rather than being retyped.

Concerns:

- **MEDIUM:** `tests/test_uninstall_e2e.py` directly calls `perform_uninstall` at `tests/test_uninstall_e2e.py:53-61` and `:111-119`, but it is absent from plan 15.7-05’s `files_modified` list (`15.7-05-PLAN.md:7-17`). Since `extra_policies` becomes required, those calls must be updated or the suite will fail.
- **MEDIUM:** The collector wait is specified immediately after `app.run()`, but no `try/finally` is required around `app.run()`. The normal Textual abort path is covered, but an unexpected exception from `app.run()` can bypass warning delivery entirely. The current route has a direct `app.run()` followed by the abort branch in `setup.py:861-888`.
- **MEDIUM:** The plan says existing reload-hint logic is sufficient, but Linux environment.d changes require a new login/systemd-manager restart, not merely a new shell. The current Policy UI’s generic post-sweep behavior is built around shell refresh semantics (`installer/wizard_app.py:1502-1507`), so removal wording may be inaccurate for Linux.

Suggestions:

- Add `tests/test_uninstall_e2e.py` to the manifest and explicitly update both direct calls.
- Wrap `app.run()` and warning collection in a bounded `try/finally`, preserving the abort result.
- Add platform-aware reload guidance for environment.d removal, or explicitly document why the existing hint is acceptable.

Risk Assessment: **MEDIUM**. The prior race concern is fixed, but the manifest omission will likely cause immediate test failures and the exception path remains under-specified.

## 15.7-06

Summary: The previous construction-point and wiring concerns are clearly addressed in prose: `_disk_pressure_probe` is named, hoisted, and passed through `PolicyInputs` without changing `UnifiedApp`’s signature. However, the plan still depends on the unresolved cache-sharing problem from 15.7-01 and places potentially 20-second systemd queries on the Textual render path.

Strengths:

- The single construction point and identity requirement are explicit (`15.7-06-PLAN.md:63-91`).
- `PolicyInputs` is the correct existing seam; `UnifiedApp` already receives it and constructs `DoctorScreen` at `installer/wizard_app.py:2017-2030`.
- The plan correctly preserves macOS temp-directory measurement rather than substituting root free space.
- `DaemonState.UNAVAILABLE` prevents advice to enable a policy that does not exist.
- The named `render_disk_pressure` path preserves the renderer’s existing organization.

Concerns:

- **HIGH:** The cache identity requirement remains unsatisfied. The plan explicitly says `_disk_pressure_probe` does not take the daemon Policy and instead resolves state from platform/constants plus “plan 15.7-01’s `TimerStateCache`” (`15.7-06-PLAN.md:71-80`, `:254-261`). But no shared cache construction or injection is defined. A new cache inside the probe would violate 15.7-01’s “SAME instance” claim; a global cache would be implicit and difficult to test safely.
- **MEDIUM:** The Policies row performs the probe during `_policy_detail`, which runs on every highlighted row (`installer/wizard_app.py:1547-1553`). A cache miss or TTL expiry can execute `systemctl`; the real query timeout is 20 seconds (`installer/run.py:301-329`). Thus “no process per keypress” is true only after a warm cache, while the UI can still freeze for a full timeout on first entry or expiry.
- **LOW:** The plan’s guards catch `OSError` and `ValueError`, while the pure probe contract also includes `TypeError` for malformed injected results (`15.7-02-PLAN.md:70-74`). The production probe should not need this, but the composition-layer behavior should either catch the complete documented conversion set or explain why `TypeError` cannot escape there.

Suggestions:

- Make the cache an explicit composition object: create it once in `setup.py`, pass it to the daemon Policy factory and the disk-pressure probe, and test object identity.
- Avoid subprocesses on render/highlight paths. Use the last known state and schedule an asynchronous refresh, or make the cache refresh happen only at view entry/explicit refresh with a much shorter bound.
- Align outer guards with the exact D-03b exception contract.

Risk Assessment: **HIGH**. The shared cache is a required cross-plan invariant but has no concrete implementation seam, and the UI responsiveness claim is too strong for a synchronous 20-second query.

## 15.7-07

Summary: The characterization-first structure is excellent and directly addresses the prior duplication finding. However, the proposed age-unit conversion contradicts both the current macOS script and the plan’s own byte-for-byte compatibility requirement. The plan also does not explicitly preserve macOS’s open-file exclusion safety behavior.

Strengths:

- Characterization tests are written before refactoring.
- The shared library owns traversal, refusal checks, age filtering, formatting, and summary generation.
- Wrapper-relative sourcing addresses scheduled-job working-directory issues.
- Shellcheck coverage is correctly widened through `Makefile:34-45`.
- The plan keeps the macOS `--days` interface and default intact.

Concerns:

- **HIGH:** The new `--days 1` assertion—delete a 25-hour-old file but spare a 23-hour-old file—does not match the current fallback behavior. The existing macOS script uses `find -mtime +"$DAYS"` at `scripts/prune-user-tmpdir.sh:105`, `:115`, and `:150-154`, not minute arithmetic. Converting `1 day` to `1440 minutes` changes boundary behavior, while the plan simultaneously promises byte-for-byte behavior (`15.7-07-PLAN.md:25-26`). This is an internal contradiction and likely a failing characterization contract.
- **MEDIUM:** The current macOS script gathers open paths with `lsof` and skips them during deletion (`scripts/prune-user-tmpdir.sh:192-221`). The shared-core action lists refusal, traversal, age, formatting, and summary responsibilities (`15.7-07-PLAN.md:207-219`) but does not explicitly preserve the open-file skip. Omitting it would weaken the shipped macOS daemon’s safety.
- **LOW:** The plan claims output behavior is byte-for-byte preserved but instructs tests not to assert full stdout, only the `deleted: N` line (`15.7-07-PLAN.md:190-204`). That proves the parser contract, not byte-for-byte output compatibility.

Suggestions:

- Decide whether compatibility or minute-granularity is authoritative. If compatibility wins, preserve the existing `-mtime` semantics and change the 25-hour assertion. If the boundary behavior is intentionally corrected, update the plan’s success criteria and characterize the change as a deliberate behavior change.
- Make open-file detection/filtering an explicit shared-core responsibility or a required macOS safety hook, with tests for an open matching path.
- Narrow the claim from “byte-for-byte” to “flag, safety, deletion, and summary contract” unless stable output lines are asserted.

Risk Assessment: **HIGH**. The age semantics conflict directly with the existing implementation and the plan’s non-regression promise.

## Cross-plan assessment

The dependency ordering is generally sound: 15.7-01 establishes the Linux daemon, 15.7-03 adds competitor detection, 15.7-04 adds redirects, 15.7-05 composes teardown/UI, and 15.7-06 integrates Doctor. The prior review’s HIGH findings are not merely repeated in prose; most now have concrete tests and ownership of the relevant behavior.

The two issues that should block execution planning approval are:

1. The unresolved `TimerStateCache` construction/sharing between 15.7-01 and 15.7-06.
2. The age-semantics contradiction in 15.7-07.

Secondary fixes should address system-scope detection failures, redirect-file ownership on apply, the omitted uninstall end-to-end test updates, and synchronous systemd queries on the Textual render path.

## Overall Risk Assessment

**HIGH.** The phase is thoughtfully decomposed and substantially improved after the previous review, but two remaining issues can produce either incorrect behavior or an implementation that cannot satisfy its own tests: shared runtime-state wiring and prune age compatibility. Resolve those before execution.
