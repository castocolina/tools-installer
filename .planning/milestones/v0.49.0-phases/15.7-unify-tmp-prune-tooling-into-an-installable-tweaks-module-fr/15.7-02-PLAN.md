<objective>
Build D-03's disk-pressure detection and wording as a pure, IO-injected layer: a probe module,
a guidance function covering every threshold combination, and one render-layer emphasis
mechanism.

Purpose: D-03 — a red Doctor warning when the cleanup daemon is inactive AND free disk is below
15% (or, on Linux, /tmp usage is above 70%), with extra visual weight when the daemon-inactive
and low-space conditions coincide.

Output: `installer/diskusage.py`, a `disk_pressure_guidance` function in `installer/guidance.py`,
and an `emphasis` flag on `Guidance` honoured by `render.guidance_text`.

**Decision D-03a — low space with the daemon RUNNING is reported as an ordinary warning
(resolved during replanning; review MEDIUM 15.7-02).** D-03 asks for a red finding on the
daemon-inactive AND low-space conjunction, with "extra visual weight when both are true at once".
Reporting nothing at all when the daemon is running would hide a genuinely nearly-full disk from
`make doctor`, whose whole job is to report what it measured; reporting it at the same red weight
would make the emphasis meaningless. So: low space alone is a plain `warn`, the conjunction is an
emphasised `error`, and no pressure is silence. This is a product decision, not an implementation
detail — it is stated here so a later reader does not have to infer it from a test.

**Decision D-03b — one total probe contract, stated in words that do not contradict themselves
(resolved during replanning; re-worded in round 2, review MEDIUM 15.7-02).** The earlier wording
said `probe_disk_pressure` "never raises for any input" while the same plan required a deliberately
raised `RuntimeError` to propagate. Both cannot be true, and a contract a reader has to reconcile
is a contract nobody relies on. The contract is therefore stated exactly once, in these words, and
plans 15.7-05 and 15.7-06 quote them rather than paraphrasing:

> `probe_disk_pressure` is TOTAL over filesystem and probe-conversion failure. It catches
> `OSError` (including `PermissionError`), `ValueError` and `TypeError` raised by the injected
> usage callable, and converts a zero-total or non-numeric result into a `None` percentage. It
> raises for no mount-read outcome a real filesystem can produce. Any other exception — a
> programming error inside this module — propagates uncaught.

That is a total function over the failure domain callers actually face, not a blanket swallow.
Callers therefore do not each invent their own exception guard set; plan 15.7-06's render-path
guards remain, but as a second, defence-in-depth layer over an already-total probe, exactly the way
`installer/wizard_app.py` already double-guards `last_run_summary`.

**Decision D-03c — "no cleanup daemon available" is a distinct state from "daemon off"
(resolved during replanning; review MEDIUM 15.7-06).** The report previously carried a
`daemon_active: bool`, which forces a host with no systemd — where plan 15.7-01's D-01b gate
deliberately builds no policy and no Policies row — into the same bucket as a host where the user
turned the row off. The finding's next step on that host would read "enable the background cleanup
through setup", pointing at a control that does not exist. So the report carries
`daemon: DaemonState` (the closed ACTIVE / INACTIVE / UNAVAILABLE enum plan 15.7-01 adds to
`installer/enums.py`) and the wording branches on it:

- **INACTIVE** + pressure -> the emphasised red finding, next step "turn on the background cleanup
  row". This is D-03's actual failure scenario, unchanged.
- **ACTIVE** + pressure -> an ordinary warning (D-03a), unchanged.
- **UNAVAILABLE** + pressure -> an ordinary warning, NOT emphasised, whose next step is the one-off
  manual prune script, and whose meaning says no managed background cleanup could be confirmed on
  this machine. Deliberately not red: the user has no control to fix it with, and a red finding
  someone cannot act on is the noise D-03's conservative thresholds were chosen to avoid.

Three members, not four: a systemd host whose state query fails is folded into UNAVAILABLE rather
than given its own UNKNOWN member, because the advice is identical — we cannot confirm a cleanup
is running and we cannot promise a row will fix it — and a fourth state would buy a distinction no
consumer acts on differently.

**Decision D-03d — measure the temp directory everywhere, apply the threshold only on Linux
(resolved during replanning; review MEDIUM 15.7-06).** The earlier design skipped the temp read
entirely when `check_tmp` was False, so on macOS the report carried no temp percentage at all, and
plan 15.7-06's Policies row — which the source todo asks to show "current tmp/TMPDIR usage %" —
had to substitute the root filesystem's free percentage and label it honestly as something else.
Measuring and thresholding are now separate concerns: the temp mount is read on every platform,
and a `tmp_threshold` flag (True only on Linux, derived in the composition root) governs ONLY
whether `high_tmp` can be True. D-03's tmpfs-quota rule stays Linux-only, and macOS gets a real
`$TMPDIR` number to display.
