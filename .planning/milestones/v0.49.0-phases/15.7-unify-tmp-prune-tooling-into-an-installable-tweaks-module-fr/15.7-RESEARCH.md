## User Constraints (from CONTEXT.md)

### Locked Decisions

**D-01 — Daemon architecture: reuse the Policy pattern, new systemd backend.**
The Linux daemon follows the exact same `Policy` shape `installer/policy.py`'s `daemon_policy` already established for macOS — same ownership-marker convention ("has any decision ever been recorded for this policy"), same Policies-screen wiring, same wrapper-executable pattern (`uv run --script` with a `requires-python` PEP 723 constraint, mirroring `helper_assets/prune_daemon_runner.py`'s own documented reason for that constraint). Only the backend differs: a systemd user timer + oneshot service (unit files, INI format, `systemctl --user`) instead of a launchd plist (`launchctl bootstrap/bootout`). Reversibility: reversible.

**D-02 — Daemon architecture: detect and replace pre-existing mechanisms.**
On Linux, before installing this project's own systemd units, detect whether an equivalent mechanism is already active on the machine (specifically: the `ai-kit` bundle's `cleanup-bun-tmp-cache.service`/`.timer`) and disable/remove it, replacing it with this repo's own managed daemon — never running two competing cleanup mechanisms simultaneously. The already-provided `ai-kit` scripts are the tested baseline pattern for the new systemd-backed daemon's own cleanup logic. Reversibility: reversible (detection+takeover is itself an install-time step, not a one-way migration).

**D-03 — Doctor warning thresholds.**
Red warning when the cleanup daemon/service is inactive AND: general disk space is below **15%** free (not 30%), OR (Linux-specific, tmpfs-quota case) `/tmp` usage exceeds **70%** (not 50%). Extra visual weight (bold/red) when both the daemon-inactive and low-space conditions are true at once. Reversibility: reversible (a threshold constant).

**D-04 — Env-var cache-redirect: generalized mechanism, Bun as the first target.**
Build a reusable, generalized mechanism for redirecting a tool's cache directory off the OS temp dir (Linux: `~/.config/environment.d/`, systemd-user convention, matching `ai-kit`'s `51-bun-cache-redirect.conf`; macOS: find/confirm the equivalent, since `launchd` doesn't support `environment.d`-style env vars the same way — likely needs to go through shell rc files directly there) — not a Bun-only, one-off patch. Bun's `BUN_RUNTIME_TRANSPILER_CACHE_PATH` is the first, concrete, already-confirmed-necessary target that drives and validates the mechanism's design. Reversibility: reversible.

### Claude's Discretion
- Exact systemd unit file naming/labeling convention (parallel to `daemon.py`'s `LABEL = "com.tools-installer.prune-tmpdir"` for launchd).
- Exact detection mechanism for the pre-existing `ai-kit` units (service/timer name match via `systemctl --user list-unit-files`, or a more general "any enabled service matching this cleanup's file-pattern signature" heuristic) — **research below found the real units are SYSTEM-level, not user-level, which changes the shape of this decision; see Open Questions.**
- Exact shape of the generalized env-var-redirect mechanism's API (a registry-level declaration a tool can opt into, vs. a small dedicated module with one entry per known tool) — implementation detail, not a product decision, as long as Bun is the first wired-up case.
- Tweaks-view UI details (toggle label wording, status line format for "daemon active: yes/no, current tmp usage: X%") — follows the same established Policies-row pattern already used for `daemon:prune-tmpdir` and `omz-plugins` on macOS.

## Summary

This phase ports an already-shipped, well-tested macOS-only background-cleanup mechanism
(`installer/daemon.py` + `installer/policy.py::daemon_policy`, launchd-backed) to Linux via
systemd, adds a generalized environment-variable cache-redirect mechanism (Bun's
`BUN_RUNTIME_TRANSPILER_CACHE_PATH` as the concrete first case), and adds a `make doctor`
warning for the daemon-inactive + low-disk-space combination. All three pieces of prior art
this phase must port from are fully read and understood: `installer/daemon.py` (454 lines,
launchd plist generation/parsing, bootstrap/bootout via an injectable `Runner` seam, the
"decided" ownership marker, the wrapper-executable install/remove mechanism),
`installer/policy.py::daemon_policy` (transactional apply/remove/set_schedule, snapshot-before-
mutate, rollback on real backend failure), and `installer/helper_assets/prune_daemon_runner.py`
(the standalone `uv run --script` wrapper with its PEP 723 `requires-python` constraint and
crash-safe log rotation). All three are cleanly separable into a "mechanism layer" (systemd
verbs) that mirrors `daemon.py`'s launchd verbs, composed by a **new** Policy factory (not a
literal generalization of `daemon_policy`, since the plist/launchctl and unit-file/systemctl
argument shapes genuinely differ) — this is exactly what D-01 asks for.

The single most important finding of this research session is a **real, live discrepancy from
CONTEXT.md's own assumption**: the `ai-kit` cleanup units this phase must detect-and-replace are
confirmed on **this exact host** to be **SYSTEM-level** units (`/etc/systemd/system/cleanup-bun-
tmp-cache.{service,timer}`, root-owned, enabled via `systemctl` not `systemctl --user`), **not**
user-level units as CONTEXT.md's Claude's-Discretion clause assumed ("detected via
`systemctl --user list-unit-files`"). `systemctl --user list-unit-files` returns **zero** matches
for `bun` on this host; `systemctl list-unit-files` (system scope) shows the real units. This
matters structurally: this project's entire install model is userspace-only (no `sudo` anywhere
in the existing codebase — confirmed by the complete absence of `sudo`/privilege-escalation calls
in `daemon.py`, `policy.py`, or any `Runner` invocation this research read), but disabling/removing
a system-level `systemctl` unit requires root. This is a genuine open question for the planner,
not a research gap to paper over — see Open Questions below.

The env-var redirect mechanism (D-04) has a real, live, already-working reference file on this
host: `~/.config/environment.d/51-bun-cache-redirect.conf`, one line
(`BUN_RUNTIME_TRANSPILER_CACHE_PATH=/var/home/bazzite/.cache/bun/transpiler-cache`), confirmed to
already be exported into this shell's environment. A live probe found a real subtlety worth
flagging to the planner: `systemctl --user show-environment` does **not** show this variable even
though the interactive shell's own `printenv` does — `environment.d` files are read by the
systemd user manager's environment generator, and that generator only re-runs on user-manager
(re)start / new login, not live. This is a real pitfall for any Doctor/status messaging this
phase adds: a freshly-written `.conf` file will not take effect (and will not show as applied)
until the next login, not merely a new shell.

Doctor's rendering path for a new warning is fully mapped: `installer/guidance.py`'s pure
`Guidance` dataclass (`title`/`meaning`/`next_step`/`severity: Severity`, where `Severity` is a
closed `OK`/`WARN`/`ERROR` `StrEnum`) is what both the CLI (`installer/render.py::guidance_text`)
and the TUI (`wizard_app.py::DoctorScreen._tui_guidance`) render, colored by
`installer/ui_common.py::SEVERITY_STYLE`. There is **no** severity level above `ERROR` for D-03's
"extra visual weight when both conditions are true" — this must be achieved either by wording
(a distinct title, e.g. prefixing "URGENT:") or by a render-layer style override on top of the
existing `SEVERITY_STYLE` map; it cannot be a new enum member added casually, since `Severity` is
consumed structurally (as a dict key) in at least `ui_common.py` and `render.py`.

**Primary recommendation:** Build a new `installer/systemd_daemon.py` module mirroring
`installer/daemon.py`'s shape 1:1 (same public function names where the semantics line up:
`write_unit`/`bootstrap`/`bootout`/`ensure_log_path`/`install_wrapper`/`remove_wrapper`/
`decided`/`record_decided`/`clear_decided`/`last_run_summary`), a new Linux-only wrapper asset
(`installer/helper_assets/prune_daemon_runner_linux.py` or reuse the existing cross-platform
wrapper if its `_run_script` shape already works — it does, since it just execs `script_path` with
forwarded argv and doesn't care about the backend), a `linux_daemon_policy` factory in
`installer/policy.py` parallel to `daemon_policy`, and a `_build_linux_daemon_policy` construction
point in `setup.py` parallel to `_build_daemon_policy`, gated on `platform.os in
("debian", "arch", "fedora")` (never a generic `"linux"` string — `Platform.os` has no such value;
see Architecture Patterns).

### Pattern 1: Injectable Runner seam for all subprocess calls
**What:** Every external-process call (`launchctl ...`, and the new `systemctl ...`/`loginctl ...`)
goes through `installer/run.py`'s `Runner` protocol (`run_captured` in production, a `_FakeRun`
recording argv in tests), never a bare `subprocess.run` call inline in `daemon.py`/`policy.py`.
**When to use:** Every new systemd/loginctl call this phase adds.
**Example:**
```python
# Source: installer/daemon.py:246-259 (this repo, read in full this session)
def bootstrap(
    uid: int, plist_path: Path, *, label: str = LABEL, run: Runner = run_captured
) -> None:
    with contextlib.suppress(CommandError):
        run(["launchctl", "bootout", f"gui/{uid}/{label}"])
    run(["launchctl", "bootstrap", f"gui/{uid}", str(plist_path)])
```
The Linux equivalent should follow the identical injected-`run` signature so
`tests/test_policy_daemon.py`'s existing `_FakeRun`/`_AlreadyAbsentRun` test-double pattern
(`tests/test_policy_daemon.py:28-56`, read this session) can be reused nearly verbatim for the
new systemd tests.

### Pattern 2: Transactional apply/remove/set_schedule with snapshot-before-mutate rollback
**What:** `policy.py::daemon_policy`'s `_apply`/`_remove`/`_set_schedule` closures each read the
prior on-disk artifact (or its absence) BEFORE mutating, and on a real backend failure restore
that snapshot and re-register with it — a marker-write failure (the "decided" record) degrades to
a `PolicyResult.warning`, never a rollback, since the real backend state and the artifact already
agree by that point.
**When to use:** The new `linux_daemon_policy` factory's `_apply`/`_remove`/`_set_schedule` must
follow this exact shape — this is the single hardest-won piece of correctness in the existing
macOS mechanism (11-REVIEWS.md's cycle 1-3 findings, all visible as inline comments in
`policy.py`'s `daemon_policy` body) and re-deriving it from scratch for systemd risks
reintroducing bugs already found and fixed once.
**Example:**
```python
# Source: installer/policy.py:600-621 (this repo, read in full this session)
try:
    _validate_and_write(hour, minute)
    daemon.bootstrap(uid, plist_path, run=run)
except (CommandError, OSError):
    if previous is not None:
        daemon._atomic_write(plist_path, previous, mode=0o644)
        with contextlib.suppress(CommandError):
            daemon.bootstrap(uid, plist_path, run=run)
    else:
        plist_path.unlink(missing_ok=True)
        if not wrapper_existed_before:
            daemon.remove_wrapper(wrapper_bin_dir)
        if not log_existed_before:
            log_path.unlink(missing_ok=True)
    raise
```

### Pattern 3: "Decided" ownership marker, not artifact-presence alone
**What:** `daemon.decided(state_path)`/`daemon.record_decided(state_path)`/`daemon.clear_decided
(state_path)` answer "has ANY decision (auto-default or explicit toggle) ever been recorded for
this policy on this machine" via a guarded comment block in `~/.myshellrc` — distinct from
whether the plist/unit file currently exists, because a machine where the artifact is absent
because the user explicitly disabled it, and one where it's absent because setup never ran, are
otherwise indistinguishable.
**When to use:** The Linux daemon needs the identical concept so `ensure_daemon_default`-style
auto-apply-once logic (`policy.py:703-727`) can be reused/mirrored without re-enabling a daemon
the user just turned off.
**Example:**
```python
# Source: installer/daemon.py:359-379 (this repo, read in full this session)
def decided(state_path: Path) -> bool:
    if not state_path.exists():
        return False
    found = False
    inside = False
    for line in state_path.read_text().split("\n"):
        if line == _DECIDED_BEGIN:
            inside = True
        elif line == _DECIDED_END and inside:
            inside, found = False, True
    return found
```
Recommend a **separate** marker block (distinct `_BEGIN`/`_END` sentinel strings) for the Linux
daemon rather than reusing `daemon._DECIDED_BEGIN`/`_DECIDED_END` verbatim — the two daemons are
mutually exclusive per-OS (never both constructed in the same process, since `_build_daemon_policy`
and the new Linux gate are OS-exclusive), but a shared marker string would make it structurally
impossible to ever offer both independently in the future, and it costs nothing to keep them
distinct now.

### Pattern 4: Guarded case-idiom for self-deduping PATH lines (D-04 rc-file fallback precedent)
**What:** `installer/rcclean.py:61-70`'s `find_duplicate_path_lines` explicitly recognizes and
skips pnpm's own `case`-guarded PATH block (`*) export PATH="$PNPM_HOME:$PATH" ;;`) as
"self-deduping … nothing safe or necessary to strip" — i.e. this codebase already has a convention
for treating a guarded shell idiom as structurally different from a plain `export`.
**When to use:** Only relevant to D-04 if the macOS env-redirect fallback needs an rc-file
mechanism that must coexist safely with rc-cleanup tooling — CONTEXT.md flags this as "worth the
planner's awareness," not a requirement. If the macOS redirect is written via
`installer/shellrc.py::apply_block`'s existing managed-block convention (recommended — it is
already dedupe-safe by construction, since `apply_block` never writes the same block twice), this
pattern likely does not need to be invoked at all.
**Example:**
```python
# Source: installer/rcclean.py:61-70 (this repo, read in full this session)
def find_duplicate_path_lines(
    rc_text: str, managed_dirs: set[Path], env: Mapping[str, str]
) -> list[int]:
    """... pnpm's own case-guarded block is intentionally NOT flagged: it is not a
    plain assignment, and its own guard already skips adding a dir that is
    present — so there is nothing safe (or necessary) to strip."""
```

### Anti-Patterns to Avoid
- **Assuming `Platform.os == "linux"` is a value that exists:** `[VERIFIED: installer/platform.py:20-21]` `Platform.os` is one of `"debian" | "arch" | "fedora" | "macos"` — there is no generic `"linux"` value. The Linux daemon's construction gate must check `platform.os != "macos"` (matching the existing inverse check's own style at `setup.py:358`) or an explicit `platform.os in ("debian", "arch", "fedora")` allowlist — never `platform.os == "linux"`, which would silently never match.
- **Reaching for `subprocess.run` directly instead of the injected `Runner` seam:** breaks the existing test-double pattern and the CommandError-based control flow every rollback path in `policy.py` depends on.
- **Treating `systemctl --user show-environment` as authoritative for "is the env-redirect live right now":** live-verified on this host (Bash session 2026-09-22) that this command does **not** show `BUN_RUNTIME_TRANSPILER_CACHE_PATH` even though the interactive shell's own `printenv` does — the systemd user manager only re-reads `environment.d` at (re)start/login, not live. A Doctor/status check that shells out to `systemctl --user show-environment` to answer "is the redirect active" would produce a false negative on a freshly-applied redirect until next login.
- **A single shared "decided" marker string for both daemons:** see Pattern 3 above.

| Injectable subprocess execution with a typed failure | A bespoke `subprocess.run(..., check=True)` wrapper | `installer/run.py::Runner`/`run_captured`/`CommandError` (existing) | Already the seam every other mutating action in this codebase uses; a second seam would fragment the test-double convention |
| Atomic, crash-safe file writes | Ad-hoc `path.write_text(...)` | `installer/atomic.py::atomic_write_bytes` (existing, used by `daemon.py::_atomic_write`) | A truncated unit file or `environment.d` conf left by a crash/disk-full mid-write would be silently re-read on the next scheduled run or next login — exactly the bug class `daemon.py`'s own comments document fixing (WR-01) |
| Guarded/marker-block text editing | Regex string surgery on `~/.myshellrc`/rc files | `installer/shellrc.py::apply_block`/`strip_block`/`ensure_source` (existing) | Idempotent by construction, already covers the "last-closed-block-wins" discipline `daemon.decided()` itself relies on |
| Disk free-space / tmpfs usage percentage | A hand-rolled `df`-parsing subprocess call | `shutil.disk_usage(path)` (stdlib) | Returns `(total, used, free)` in bytes with zero subprocess spawn or locale-dependent `df` output parsing; `/tmp`'s tmpfs usage is queryable the same way (`shutil.disk_usage("/tmp")`) since tmpfs is a normal mounted filesystem for this purpose |

**Key insight:** This phase's entire mechanism layer already exists once, correctly, with three
review cycles of hardening behind it (`daemon.py`/`policy.py`'s inline comments cite specific
`11-REVIEWS.md` cycle/finding numbers throughout). The job here is disciplined mirroring — same
seams, same transactional shape, same ownership-marker discipline — onto a different backend
verb set, not a fresh design.

## Common Pitfalls

### Pitfall 1: The real `ai-kit` units are SYSTEM-scoped, not USER-scoped
**What goes wrong:** A detection routine written against `systemctl --user list-unit-files`
(as CONTEXT.md's Claude's-Discretion text explicitly suggests) will find **nothing** on this
exact host, because the real units are registered system-wide.
**Why it happens:** The source todo's own `install.sh` (referenced but not directly read this
session — it lives in the sibling `ai-kit` repo, outside this repo's tree) uses `sudo install` +
system-scope `systemctl enable --now`, per the todo's own text. CONTEXT.md's discretion clause
assumed user-scope without live-checking.
**How to avoid:** Detection must probe BOTH scopes: `systemctl --user list-unit-files
'cleanup-bun-tmp-cache.*'` AND `systemctl list-unit-files 'cleanup-bun-tmp-cache.*'` (the latter
needs no special privilege to READ — only to disable/remove). Live-verified this session:
`[VERIFIED: live `systemctl`/`systemctl --user` commands, this host, 2026-09-22]`
```
$ systemctl --user list-unit-files | grep -i bun
(no output)
$ systemctl list-unit-files | grep -i bun
cleanup-bun-tmp-cache.service                         static          -
cleanup-bun-tmp-cache.timer                           enabled         disabled
```
**Warning signs:** A "detected and disabled" success message that never actually removes the
real unit is worse than no detection at all — it tells the user the takeover happened when it
did not, leaving both cleanup mechanisms running.

### Pitfall 2: `environment.d` changes are not live — they need a new login, not a new shell
**What goes wrong:** A Doctor check or a "redirect is active" status line that shells out to
`systemctl --user show-environment` (or checks the CURRENT process's own env) to answer "is the
Bun redirect live" will report stale/false state right after `apply()` writes a fresh
`.conf` file.
**Why it happens:** `environment.d(5)` files `[CITED: https://man.archlinux.org/man/environment.d.5.en]`
are read by `systemd-environment-d-generator` `[CITED: https://man7.org/linux/man-pages/man8/systemd-environment-d-generator.8.html]`,
"a systemd.environment-generator(7) that reads environment configuration ... and passes it to the
systemd(1) user manager instance" — this only runs when the user manager (re)starts, i.e. at
login (or `systemctl --user daemon-reexec`/a fresh session), not on every new shell and not
instantly on file-write.
**How to avoid:** State the redirect's "applied" status as "written to disk, takes effect on next
login" rather than implying it is immediately live; do not build a Doctor check that probes live
process environment as proof of correctness — the file's mere presence (plus a content check) is
the honest signal, mirroring how `daemon.py`'s own `active` field is `plist_path.exists()`, never
a parsed runtime probe.
**Warning signs:** A user reports "I applied the tweak and Bun is still writing to /tmp" without
having opened a new terminal session (not just a new shell tab) since applying it.

### Pitfall 3: A `systemctl --user` timer does not fire when the user is logged out — unless lingering is enabled
**What goes wrong:** Unlike the real ai-kit units (system-scope, always running regardless of
login state) and unlike macOS's `launchd` LaunchAgent (which, per `daemon.py`'s own docstrings,
also only runs in a logged-in `gui/<uid>` session — so this is actually PARITY with the existing
macOS mechanism, not a regression from it, but IS a regression from the ai-kit baseline this
phase is asked to match/replace), a bare `systemctl --user enable --now` timer will silently stop
firing once the user's last session ends, unless `loginctl enable-linger <user>` has been run.
**Why it happens:** `[VERIFIED: live `loginctl show-user`, this host, 2026-09-22]` — this exact
host already has `Linger=yes` set (likely from an unrelated prior configuration), so a
naive local test of "does my new Linux daemon keep running" would pass here even without the
policy itself ever calling `loginctl enable-linger` — masking the gap on THIS machine while
leaving it unaddressed on a fresh install.
**How to avoid:** The planner should explicitly decide whether `linux_daemon_policy.apply()`
should also invoke `loginctl enable-linger $(whoami)` (a machine-wide, not per-policy, systemd
setting — reversibility and scope of this side effect need explicit sign-off, since it affects
every user-scoped systemd unit for that account, not just this one) or whether the daemon should
be documented as "runs while logged in" (matching the macOS LaunchAgent's own actual behavior)
and this parity gap versus ai-kit's system-level always-on behavior accepted and stated plainly
to the user. This is a genuine product decision, not an implementation detail — see Open
Questions.
**Warning signs:** `/tmp` usage climbing again specifically overnight/while logged out on a
machine that otherwise shows the daemon as "active."

### Pitfall 4: `Severity` is a closed 3-value enum consumed structurally — do not add a 4th value casually
**What goes wrong:** D-03 asks for "extra visual weight (bold/red) when both conditions are true
at once," which might tempt adding a `Severity.CRITICAL` value.
**Why it happens:** `[VERIFIED: installer/enums.py:79-85]` `Severity` is a `StrEnum` with exactly
`OK`/`WARN`/`ERROR`. `[VERIFIED: installer/ui_common.py:27]` `SEVERITY_STYLE = {Severity.OK:
"green", Severity.WARN: "yellow", Severity.ERROR: "red"}` — a plain dict keyed on all three
members, consumed at `installer/render.py:186` (`text.append(item.title,
style=SEVERITY_STYLE[item.severity])`) and referenced similarly in `wizard_app.py`.
**How to avoid:** Adding a 4th enum member is possible but touches every exhaustive-looking
consumer of `Severity`/`SEVERITY_STYLE` across the CLI and TUI render paths — a wider blast
radius than the feature needs. Prefer achieving "extra visual weight" at the render layer (e.g. a
title string prefix, or a style override applied only for this specific `Guidance` instance's
title) while still assigning `severity=Severity.ERROR`. Flag this choice explicitly to the
planner rather than deciding it here — it is UI wording/rendering discretion CONTEXT.md already
delegates.
**Warning signs:** A `KeyError` on `SEVERITY_STYLE[Severity.CRITICAL]` if a 4th value is added to
the enum but not to every consuming dict.

### The exact "decided" marker pattern to mirror (new sentinel strings, same shape)
```python
# Source: installer/daemon.py:59-61, 347-356 (this repo, read in full this session)
_DECIDED_BEGIN = "# >>> tools-installer daemon:decided >>>"
_DECIDED_END = "# <<< tools-installer daemon:decided <<<"

def _decided_block() -> str:
    return "\n".join(
        (
            _DECIDED_BEGIN,
            "# This installer has made an on/off decision (auto-default or an",
            "# explicit user toggle) for the background maintenance daemon on",
            "# this machine. Comments only: nothing here is executed.",
            _DECIDED_END,
        )
    )
```

daemon-linux:decided >>>`) written into the SAME `~/.myshellrc` state file
(`_DAEMON_STATE_PATH = _MYSHELLRC` at `setup.py:109`) — never a new state file — matching
`daemon.py`'s own stated rationale for reusing that one file.

### The exact wrapper-installation ownership-check pattern to mirror
```python
# Source: installer/daemon.py:294-322 (this repo, read in full this session)
def _is_our_wrapper(path: Path) -> bool:
    try:
        return _WRAPPER_SENTINEL in path.read_text()
    except (OSError, UnicodeDecodeError):
        return False

def install_wrapper(bin_dir: Path) -> Path:
    bin_dir.mkdir(parents=True, exist_ok=True)
    target = bin_dir / WRAPPER_COMMAND
    if target.exists() and not _is_our_wrapper(target):
        raise OSError(f"{target} exists and is not managed by tools-installer")
    source = importlib.resources.files("installer").joinpath(_WRAPPER_ASSET).read_text()
    _atomic_write(target, source.encode("utf-8"), mode=0o755)
    return target
```
The existing `prune_daemon_runner.py` wrapper is OS-agnostic in its own body (it just execs
`script_path` with forwarded argv) — recommend reusing `WRAPPER_COMMAND =
"tools-installer-prune-daemon"` for Linux too (one shared wrapper executable, since the two
daemons never coexist on the same OS) rather than installing a second, near-identical wrapper
under a different name. This needs explicit confirmation from the planner since `daemon.py`'s
`WRAPPER_COMMAND`/`_WRAPPER_ASSET` constants are currently declared in the macOS-specific module;
if genuinely shared, they may need to move to a neutral module (or simply be imported from
`daemon.py` by the new systemd module, matching how `policy.py` already imports
`daemon.WRAPPER_COMMAND` at `policy.py:52` to avoid drift).

## Open Questions

1. **Should D-02's "detect and disable/remove the pre-existing `ai-kit` mechanism" reach into a SYSTEM-scope unit, given this project's install model is otherwise entirely userspace/no-`sudo`?**
   - What we know: The real units on this host are confirmed system-scope
     (`/etc/systemd/system/cleanup-bun-tmp-cache.{service,timer}`, root-owned 644, enabled via
     `systemctl` not `systemctl --user`). Reading their existence needs no privilege
     (`systemctl list-unit-files` is readable by any user); *disabling/removing* them
     (`systemctl disable`, deleting the unit files) needs root.
   - What's unclear: Whether this phase should (a) attempt the system-scope disable via a
     `sudo systemctl disable ...` call — a first-ever privilege-escalation path in this codebase,
     a meaningful architectural change — (b) detect-and-warn only (tell the user a competing
     system-level mechanism exists and how to remove it themselves, never touching it), or
     (c) detect via both scopes but only ever actually take over a USER-scope competing unit,
     treating a SYSTEM-scope one as "detected, left alone, warned about" since D-02's own
     reversibility note describes takeover as "an install-time step," not a mandate to escalate
     privileges this project has never needed before.
   - Recommendation: (b)/(c) — detect-and-warn for system-scope, take over silently for
     user-scope — is the option most consistent with this project's existing zero-`sudo`
     architecture and the safest default; flag this explicitly to the user during
     `/gsd-plan-phase` or `/gsd-discuss-phase` follow-up rather than the planner silently picking
     one, since it changes what "detect and replace" means from CONTEXT.md's original wording.

2. **Should the Linux daemon's `apply()` call `loginctl enable-linger`, making it match ai-kit's "runs even while logged out" behavior, or should it accept "runs only while logged in" as the honest, disclosed Linux-mirrors-macOS-LaunchAgent behavior?**
   - What we know: This dev host already has `Linger=yes` (pre-existing, unrelated to this
     phase), so a naive functional test here would not surface the gap. `loginctl enable-linger`
     is a per-user, systemd-wide setting — it is not scoped to this one daemon and would affect
     every user-level systemd unit for that account.
   - What's unclear: Whether the phase's success criteria implicitly require login-independent
     operation (the source todo's whole motivating scenario is "day-long autonomous run," which
     plausibly spans logout/login cycles on a headless or remotely-driven machine) or whether
     "matches the existing macOS LaunchAgent's own actual behavior" (also login-session-scoped)
     is an acceptable, disclosed parity target.
   - Recommendation: Surface this explicitly during planning/discuss-phase rather than deciding
     silently — it is a real behavior/scope decision, not an implementation detail.

3. **Exact `ai-kit` unit detection heuristic: name-match vs. content/pattern-match?**
   - What we know: CONTEXT.md's Claude's-Discretion clause leaves this open. The real unit names
     on this host are the literal strings `cleanup-bun-tmp-cache.service`/`.timer`.
   - What's unclear: Whether detection should match these exact names (brittle if `ai-kit` ever
     renames its units) or a more general heuristic (e.g. any enabled unit whose `ExecStart`
     references a script matching a Bun-tmp-cleanup file-naming pattern).
   - Recommendation: Exact-name match for `cleanup-bun-tmp-cache.{service,timer}` is sufficient
     for this phase (matches the one real, confirmed case) — a more general heuristic is
     speculative generalization ahead of a second real case, the same anti-pattern D-04's own
     rationale already rejected for the redirect mechanism.
