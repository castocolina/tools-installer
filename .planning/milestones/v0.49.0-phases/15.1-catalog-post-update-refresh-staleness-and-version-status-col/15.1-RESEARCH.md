# Phase 15.1: Catalog post-update refresh staleness and version-status color disambiguation - Research

**Researched:** 2026-09-15
**Domain:** Internal TUI state-refresh wiring + Rich/Textual text rendering (no external libraries, no new dependencies)
**Confidence:** HIGH

## Summary

This is a two-bug, no-new-dependency UI-polish phase entirely inside three existing
files: `installer/wizard_app.py`, `installer/catalog_tui.py`, and the shared
`installer/tool_browser.py` / `installer/ui_common.py` widgets they already use. Both
fixes are narrow, mechanical, and every reusable piece D-01 through D-04 need already
exists in the codebase — this research found the exact call sites, confirmed the exact
line numbers CONTEXT.md cited, and located the exact existing tests that assert today's
(pre-fix) `_ver_cell` behavior and will need updated assertions.

**Bug 1 (D-01, refresh staleness):** `UnifiedApp.show_view()` is "the one navigation
path" (comment at `wizard_app.py:1740-1742`) and is the *only* place that calls
`entering.enter_view()` before showing a screen — but only for **non-base** views
(`if name != BASE_VIEW: entering.enter_view()`). The base-tier `CatalogScreen` (the one
never popped off the bottom of the stack) is revealed again purely by Textual's own
screen-resume mechanism when `ExecuteScreen` (a `ModalScreen` pushed on top of whichever
catalog tier was active) is popped — and `CatalogScreen.on_screen_resume()`
(`catalog_tui.py:648-656`) deliberately calls only `self._browser.refresh_marks()`, never
`_start_version_refresh()`. `UnifiedApp._install_closed` (`wizard_app.py:1833-1834`)
currently only does `self._staged.clear()`. `self.current_view` is never mutated by
`push_screen(ExecuteScreen(...))` / its pop, so it still correctly names whichever
catalog tier was on-screen before the run started, for **all three** tiers (base
included) — `self._catalogs` is keyed by the same tier-value strings as `current_view`.
The fix is one line: call `self._catalogs[self.current_view].enter_view()` from
`_install_closed`, which internally guards on `is_mounted` and calls
`_start_version_refresh()` — the exact "equivalent of enter_view()/
_start_version_refresh()" CONTEXT.md's D-01 asks for, and it is uniform across all
three tiers (no special-casing base vs. non-base needed).

**Bug 2 (D-02/D-03/D-04, color/text disambiguation):** `_ver_cell` (`catalog_tui.py:299-323`)
has exactly the branches CONTEXT.md describes. Two of its three "gray" return paths
currently render the *literal string* `"unknown"` (line 304, line 318) — collapsing "no
data yet / still probing" (status absent or `installed is None`) and "unparseable
version" (`outdated is None` while `latest is not None`) into the same text. The third
gray path (line 310, `latest is None`) currently renders the bare installed version
string with no marker at all — this is the "not tracked for updates" case D-02 wants a
stable marker for. The codebase already has a reusable, already-multi-tier legend
mechanism: `_LEGEND` (`catalog_tui.py:168-172`) is a module-level markup string passed
as `legend=_LEGEND` into every `BrowserAdapter` built by `_adapter()` — and because
`_adapter()` is called once per `CatalogScreen` instance (one per `Tier`, i.e. once per
System/User/AI tab), the resulting `Static(..., id="browser-legend")`
(`tool_browser.py:127-128`, docked bottom, height 1, inside `ToolBrowser.compose`) is
already rendered on all three top-level catalog views — exactly D-03's placement
requirement, satisfied by extending the existing constant, not building new UI.

**Primary recommendation:** Fix D-01 with a single added line in `_install_closed`
calling `self._catalogs[self.current_view].enter_view()`. Fix D-02 by rewriting
`_ver_cell`'s three gray-producing return statements to use three distinct label
strings, one of them (`latest is None`) formatted as a suffix appended to the real
version rather than replacing it entirely (matching CONTEXT.md's D-01/prior-code note
that discarding the real probed version was already flagged as a regression once).
Fix D-03/D-04 by appending new entries to the existing `_LEGEND` constant — do not
create a second legend widget or a new footer row.

### Recommended change: `_install_closed`

```python
# Source: installer/wizard_app.py:1833-1834 (current)
def _install_closed(self, _result: None) -> None:
    self._staged.clear()

# Recommended (D-01) — reuses the existing, already-tested refresh mechanism;
# self._catalogs is keyed by the same tier-value strings as self.current_view,
# for ALL three tiers including BASE_VIEW, so no base/non-base special case:
def _install_closed(self, _result: None) -> None:
    self._staged.clear()
    self._catalogs[self.current_view].enter_view()
```

`enter_view()` (`catalog_tui.py:264-266`) already guards on `self.is_mounted`, so this
is safe to call unconditionally — no new guard logic needed in `wizard_app.py`.

### Recommended change: `_ver_cell` gray-state disambiguation

```python
# Source: installer/catalog_tui.py:299-323 (current — verbatim)
def _ver_cell(self, tool: Tool) -> Text:
    if not self._installed.get(tool.id, False):
        return Text("")
    status = self._version_statuses.get(tool.id)
    if status is None or status.installed is None:
        return Text("unknown", style="dim")
    if status.latest is None:
        return Text(status.installed, style="dim")
    if status.outdated is True:
        base = f"{status.installed} -> {status.latest}"
        color = "yellow"
    elif status.outdated is False:
        base = status.installed
        color = "green"
    else:
        return Text("unknown", style="dim")
    if status.stale:
        return Text.assemble((base, color), (" ~", "dim"))
    return Text(base, style=color)
```

The three gray/dim branches to disambiguate (exact source lines this session verified):
- `catalog_tui.py:303-304` — `status is None or status.installed is None` → today's
  literal `"unknown"`. This is "no data yet / still probing" per CONTEXT.md D-02.
- `catalog_tui.py:305-310` — `status.latest is None` → today's bare
  `status.installed` with no marker at all. This is "not tracked for updates" per
  CONTEXT.md D-02 (the dnf/apt/pacman/rpm-ostree-owned case; see
  `_version_detail`'s existing `"managed by dnf — this installer will not update
  it"`-style prose at `catalog_tui.py:401-404` for the tone precedent, though that
  fuller explanation stays in the detail bar, not the cell — Phase 15.4's scope per
  CONTEXT.md's Deferred Ideas).
- `catalog_tui.py:317-318` — the `else` branch (`status.outdated is None` while
  `status.latest is not None`) → today's literal `"unknown"`, same text as the first
  branch. This is "unparseable version" per CONTEXT.md D-02 — reachable via
  `is_outdated()` (`installer/versions.py:211-234`) returning `None` when either side
  fails `parse_status_version`, confirmed `[VERIFIED: installer/versions.py:217-220]`:
  `if left is None or right is None: return None`.

D-02 requires distinct **text** for each, not new colors. A minimal, internally
consistent labeling that keeps every existing "the version we know is real information"
guarantee (the code comment at `catalog_tui.py:306-309` explicitly says discarding a
real probed version here was already flagged once as a regression — see the test named
below) is:

```python
# Illustrative only — exact wording is Claude's discretion per CONTEXT.md, as long as
# all three branches render visibly different text.
if status is None or status.installed is None:
    return Text("…", style="dim")                      # still probing
if status.latest is None:
    return Text.assemble((status.installed, "dim"), (" (unmanaged)", "dim"))
...
else:
    return Text("unknown ver.", style="dim")            # or similar — unparseable
```

Whatever exact strings are chosen, they must each get a corresponding `_LEGEND` entry
(D-03) and must stay distinguishable from the `~` stale suffix, which is an orthogonal
decorator applied via `Text.assemble` regardless of which branch produced `base`
(`catalog_tui.py:321-322`) — do not conflate the stale suffix with any of the three
gray-branch labels; D-04 requires the `~` suffix to have its own legend line.

### Recommended change: `_LEGEND`

```python
# Source: installer/catalog_tui.py:168-172 (current — verbatim)
_LEGEND = (
    "[bold red]P0[/] essential · [bold yellow]P1[/] recommended · [blue]P2[/] nice-to-have"
    " · [dim]P3[/] niche  |  for [bold cyan]AI[/] / [magenta]human[/] / both"
    "  |  [green]✓ installed[/] · [yellow]○ missing[/]"

```

This is `Text.from_markup`-rendered (`tool_browser.py:128`) inside a `Static(...,
id="browser-legend")`, docked bottom, height 1, already present under the `DataTable` in
`ToolBrowser.compose` (`tool_browser.py:124-129`) for every `CatalogScreen` — extend
this same string with a `Ver:` segment covering: `[green]` up to date, `[yellow]` update
available (CONTEXT.md's decision text calls this "orange", but the actual Rich style
token already used throughout this file for the same semantic — `_PRIORITY_STYLE[P1] =
"bold yellow"`, `_ver_cell`'s `color = "yellow"` — is `yellow`, not `orange`; use
`[yellow]` in the legend to match the real rendered color exactly, not the CONTEXT.md
prose word), each of the three new gray-state labels chosen for D-02, and the trailing
` ~` stale suffix. A single-line append keeping the existing `·`/`|` separator
convention is the simplest change; wrapping/ordering is explicitly Claude's discretion
per CONTEXT.md.

### Anti-Patterns to Avoid

- **Building a second legend widget or a new status-bar region for D-03:** `_LEGEND` /
  `browser-legend` already satisfies "visible, always-on, present across all three
  top-level views" — a second mechanism would duplicate state and risk the two legends
  drifting apart.
- **Narrowing D-01's refresh to only the ids that were in the just-finished run:**
  CONTEXT.md's D-01 explicitly rejects this ("not a narrower per-tool refresh") in favor
  of the full `enter_view()`/`_start_version_refresh()` path, for robustness against
  dependency drag-in. Do not hand-roll a per-tool diff/patch of `_version_statuses`.
  Reusing the existing full-refresh mechanism means also reusing its coalescing behavior:
  because `_start_version_refresh()` bumps `_version_refresh_generation` on this call,
  any version-refresh worker already in flight from the *previous* `enter_view()` (e.g.
  the initial `on_mount()` refresh, if it happens to still be running) is silently
  discarded by the generation check in `on_version_status_refreshed`
  (`catalog_tui.py:289-291`) — this is existing, already-tested behavior
  (`test_epoch_guard_drops_a_superseded_version_refresh`), not a new race this phase
  introduces.
- **Using a new color for the gray-state disambiguation:** CONTEXT.md D-02 explicitly
  rejects new colors ("avoids introducing new colors that would need to work across
  light/dark themes and constrained terminals") — text only.
- **Reusing the literal string `"unknown"` for more than one branch:** doing so
  reproduces the exact ambiguity D-02 exists to fix; verify by grep after editing that
  `"unknown"` (or whatever single label is kept) appears in only one `_ver_cell` return
  path.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Triggering a refresh when a screen becomes visible again | A new `ExecuteScreen`→`CatalogScreen` message/callback protocol | `CatalogScreen.enter_view()` (already exists, already called by the one navigation path for non-base views) | It is the established, tested "re-derive anything this view must not read from a stale snapshot" hook (docstring at `ui_common.py:325-335`); D-01 only needs one more call site, not a new mechanism |
| An always-visible explanatory legend line | A new footer widget, tooltip, or `?`-triggered help overlay | The existing `_LEGEND` string / `BrowserAdapter.legend` / `ToolBrowser`'s `#browser-legend` `Static` | Already rendered, already always-on, already present on all three catalog tiers — a toggle or overlay is explicitly what CONTEXT.md's D-03 rationale rejects |

**Key insight:** every piece D-01 through D-04 need was built in a prior phase for a
different purpose (Phase 12/13's `enter_view()` navigation-refresh contract, the
existing `_LEGEND`/`browser-legend` widget). This phase is pure wiring/text, not new
architecture.

## Common Pitfalls

### Pitfall 1: Fixing D-01 only for the base tier, or only for non-base tiers
**What goes wrong:** A fix that special-cases `if self.current_view == BASE_VIEW: ...
else: self._views[self.current_view].enter_view()` mirrors `show_view`'s existing
`if name != BASE_VIEW` branching, but `show_view`'s asymmetry exists because *pushing a
screen* differs by tier (base is never pushed/popped); `_install_closed` does not push
or pop anything — it only needs `enter_view()` called, and `self._catalogs` (not
`self._views`, which excludes the base tier) already has a uniform entry for all three
tiers under the same key `self.current_view` uses. Using `self._catalogs[...]` avoids
needing any special case at all.
**Why it happens:** Copying the nearby `show_view` pattern without noticing it solves a
different problem (stack mutation) than `_install_closed` has (no stack mutation, just
a stale snapshot).
**How to avoid:** Use `self._catalogs[self.current_view]`, not `self._views.get(...)`.
**Warning signs:** A test that runs the update-from-base-tier flow (tier == `BASE_VIEW`,
e.g. `"system"`) still shows the stale Ver cell after the fix, while non-base tiers work.

### Pitfall 2: D-02's rewrite accidentally changing the `latest is None` case back to discarding the real version
**What goes wrong:** `catalog_tui.py:306-309`'s comment and the test
`test_ver_cell_shows_probed_version_with_no_latest_to_compare`
(`tests/test_catalog_tui.py:915-931`) record that this exact regression ("showing
'unknown' here threw away a version we already have") was already fixed once. A D-02
rewrite that replaces `status.installed` with a bare marker string (rather than
appending the marker to the real version) reintroduces that regression.
**Why it happens:** The three branches look superficially similar (all "return some dim
Text"), inviting a uniform rewrite that loses the one branch's extra payload (the real
version string).
**How to avoid:** Keep `status.installed` in the rendered text for the `latest is None`
branch; append/prefix the new marker rather than replacing the whole string.
**Warning signs:** `test_ver_cell_shows_probed_version_with_no_latest_to_compare` (and
its sibling assertions at `tests/test_catalog_tui.py:1076`,
`tests/test_catalog_tui.py:1256-1261`) failing after the D-02 change — these three
existing tests currently assert `.plain == "14.1.0"` / `== "unknown"` for this exact
scenario and MUST be updated to match the new label, not simply deleted, since they
also assert the underlying "real version is preserved" guarantee this pitfall protects.

### Pitfall 3: Legend text drifting from the actual Rich style token
**What goes wrong:** CONTEXT.md's own decision prose calls the update-available color
"orange"; the real style token used everywhere in `_ver_cell` and `_PRIORITY_STYLE` is
`"yellow"`. A legend that says `[orange]...[/]` either renders nothing special (Rich
doesn't have a built-in `orange` markup name it will silently no-op on, or errors,
depending on Rich version) or visually mismatches the actual cell color, defeating the
whole point of the legend.
**Why it happens:** Copying the CONTEXT.md decision's human-readable color name instead
of grepping the actual style string used in the code being disambiguated.
**How to avoid:** Use `[yellow]` in the legend markup, matching `color = "yellow"` at
`catalog_tui.py:313`.
**Warning signs:** Manually running the TUI (`make setup`) and comparing the legend
swatch color against an actual outdated-tool row.

### Pitfall 4: Not updating the three existing tests that assert today's (pre-D-02) `_ver_cell` text
**What goes wrong:** `make validate && make test` fails after the D-02 rewrite because
`tests/test_catalog_tui.py:931`, `:947`, `:1076`, and the detail-text-adjacent assertion
around `:1256-1261` hard-assert the exact literal strings `"14.1.0"` and `"unknown"`
that D-02 intentionally changes.
**Why it happens:** These tests were written to pin down the *previous* fix (preserving
the real version) and were never updated for a *text-label* change because no such
change existed until this phase.
**How to avoid:** Grep `tests/test_catalog_tui.py` for `_ver_cell(` before starting (this
session found 8 call sites: lines 907, 909, 931, 947, 1071-1073, 1256) and update each
literal-string assertion to the new label, preserving each test's original intent (e.g.
`test_ver_cell_shows_probed_version_with_no_latest_to_compare` must keep asserting the
real version string `14.1.0` is present in the cell, just with the new marker appended).
**Warning signs:** `make test` failures naming these exact test functions.

## Code Examples

### Existing, already-correct refresh mechanism (reuse, do not reimplement)
```python
# Source: installer/catalog_tui.py:264-273 (verbatim, unchanged by this phase)
def enter_view(self) -> None:
    if self.is_mounted:
        self._start_version_refresh()

def _start_version_refresh(self) -> None:
    if self._version_refresh is None:
        return
    self._version_refresh_generation += 1
    self.version_refreshing = True
    self._refresh_versions_worker(self._version_refresh_generation)
```
