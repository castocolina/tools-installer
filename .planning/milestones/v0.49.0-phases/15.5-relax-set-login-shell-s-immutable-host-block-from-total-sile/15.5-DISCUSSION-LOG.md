## Live investigation triggered by user's pushback

User asked, verbatim: "por ultimo el bug de zsh con el login, sucede solo cuando zsh
fue instalado desde ostree y se hace el default? ... no me sirve de nada si no lo uso
default ... estuve buscando issues en github y no vi nada especifico o no se si
hablamos del mismo issue."

**Investigation performed:**
1. `which chsh` on this live host → not found. `rpm -q util-linux-user` → not
   installed. Confirms `chsh` is genuinely absent, not merely undiscovered.
2. `python3 -c "tomllib..."` read of `zsh`'s registry entry — methods are
   dnf/apt/pacman/brew, no rpm-ostree-specific method.
3. Read `installer/resolve.py:70-77` — confirms `dnf` (which would trigger rpm-ostree
   layering) is skipped on immutable hosts by design; zsh installs via `brew` here.
4. `gh issue view 4159 --repo ublue-os/bazzite --json title,body,state,comments` —
   fetched the full issue thread. Confirmed it is the same issue Phase 14 cited.
   Maintainer `KyleGospo` (MEMBER): "chsh is not included. This is because if you layer
   a shell and chsh to it, then unlayer it or rebase you would end up w/ an issue...
   My recommendation would be to set zsh as your shell in Ptyxis and not touch
   bashrc. You can also install zsh with brew instead of layering it." Maintainer
   `m2Giles` (MEMBER): general recommendation to never change the login shell at all,
   use a terminal-emulator profile instead.

**This superseded the original phase framing entirely** — the plan to "show chsh
instructions with a warning" was actively wrong on this host (chsh doesn't exist to
run). Captured as the new "Root-cause finding" section in CONTEXT.md.

## Rejected approach: re-add chsh via rpm-ostree layering

**User's question (verbatim):** "no podemos agregar chsh y hacer uninstall si esta
bajo ostree layer e instalar con brew y hacer el change? ... si el problema es zsh +
ostree, o eso no cura el problema?"

**Claude's answer:** No — re-layering `util-linux-user` via `rpm-ostree` requires the
same "layer + reboot, breaks atomicity" pattern this installer already avoids by
design (`resolve.py:70-73`'s disabled `rpm_ostree` method), and conflicts with this
installer's own doctrine of never requiring privilege escalation. It also doesn't
match Bazzite's own stated position (avoid touching the login shell at all, regardless
of the binary's origin) — not purely a technical workaround away.

**Resolution:** Explicitly ruled out, captured as "Rejected approach" in CONTEXT.md.

## Scope split: this phase vs. a new "real solution" phase

**User's actual want (verbatim):** "Mas que una advertencia quiero una solucion, no
quiero estar abriendo wezterm u otro terminal emulator y estar seleccionando
manualmente el shell." They want zsh (+ oh-my-zsh plugins) to just work as the default
shell in Konsole/kitty/WezTerm (Linux) and iTerm2/kitty/WezTerm (macOS), without
manual per-session shell selection and without touching chsh.

| Option | Description | Selected |
|--------|-------------|----------|
| Dividir: 15.5 arregla lo roto, nueva fase construye la solución real | 15.5 stays scoped to correctness of the chsh-instruction mechanism; a new phase builds actual terminal-emulator auto-configuration | ✓ (with a caveat) |
| Todo junto en 15.5 | Fold terminal-emulator auto-config into 15.5 itself | |

**User's choice:** Split (option 1), with an added clarification: "sabemos en macOS no
hay esos problemas, son problemas de bazite, ni siquiera se si son de fedora" —
macOS is explicitly unaffected and needs no changes; the new phase should focus on the
Linux/immutable case where the problem actually exists.

**Follow-up technical question (user):** whether terminal emulators installed as
packages (wezterm, kitty) could take a launcher-level flag/env-var for their default
shell instead of editing their config files.

**Claude's answer (feasibility only, not designed):** `kitty -o shell=<path>` and
`wezterm start --config 'default_prog={"<path>"}'` both work as CLI-level overrides
without touching `kitty.conf`/`wezterm.lua`. Konsole has no equivalent single flag but
supports the more universal `-e <command>` launch pattern. Captured as a research lead
in the new phase's roadmap description, not a locked design decision.

**Resolution:** Captured as the "Deferred Ideas" new-capability entry in CONTEXT.md,
with an explicit next action to run `/gsd-phase --insert 15.5 "..."` after this
phase's context is committed.
