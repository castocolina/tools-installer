<objective>
Declare where tools actually land: kitty's real Linux method, and a location audit of the
own-installer tools (D-19, D-07), plus the sdkman `version_file`.

Purpose: CONTEXT.md Specifics. kitty was found during discussion to be installed by its own
official userspace installer (`~/.local/kitty.app`), which the registry never declared. On Bazzite
kitty therefore had zero applicable methods and sat dim with no explanation. D-19 asks for the
real method and an audit of other tools for the same gap. The audit was run during planning with
`platform_could_support`:
- On immutable Fedora the zero-method set is `gnu-bash`, `container`, `kitty` and `alacritty`.
- gnu-bash and container are macOS-only by upstream design.
- alacritty is already documented in docs/catalog-unsupported-tools.md as having no Linux userspace
  method.
So kitty is the only row the registry can fix. The other three get a reason in plan 16-14. A second
audit dimension is script methods declaring no location at all, which blocks D-07's own-installer
proof. Those are codex, claude, opencode, cursor-agent and antigravity.

kitty's installer launches kitty when it finishes unless passed `launch=n` (vendor docs:
https://sw.kovidgoyal.net/kitty/binary/). The script executor has no argument support today, so
this plan adds a validated `args` param.

Follow `.claude/skills/tool-onboarding/SKILL.md` and the architecture.md per-tool per-OS
verification checklist for each registry edit.

Output harness note: if `uv run pytest` prints a false "No tests collected", re-run via `.venv/bin/pytest`.
</objective>
