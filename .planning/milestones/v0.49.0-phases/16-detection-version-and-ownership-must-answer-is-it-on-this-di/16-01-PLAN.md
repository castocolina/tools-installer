<objective>
Make ownership answer "who put it on this disk" for SDKMAN and own-installer tools, using the location
each method already declares (`bin_dir`), and fix the dead `_sdkman` probe.

Purpose: Today a pure-SDKMAN tool (java/groovy/gradle/maven/springbootcli) and an own-installer tool
outside the managed bin dir (bun at ~/.bun/bin) both fall through every branch of
`resolve_ownership` to `unknown`. RESEARCH.md Pitfall 2 verified that even a tool installed ONLY
through SDKMAN reads unknown, because `ownership.py` has no sdkman owner at all. D-19 asks for
per-method install-location declarations that double as ownership proof. The registry already
carries them as `bin_dir`, and `status.py::is_installed` already reads them. This plan makes
ownership read the same field.

Output: `sdkman` Owner end to end (literal, kind map, candidate order, four label/removal tables), a
location-proof candidate branch, the `own installer` column label (D-07), the `_sdkman` probe
kind/key fix, and an honest SDKMAN update refusal sentence.

Design choices (Claude's discretion, recorded):
- **D-19 schema shape:** reuse `bin_dir`, no new field. RESEARCH.md Open Question 2 / Pitfall 7
  recommend this, and a second field is the anti-pattern CONTEXT.md's own D-19 reversibility note
  warns about.
- **SDKMAN mutation:** research Assumption A1 recommends treating SDKMAN as mutation-eligible, and
  D-05 needs that. It works because `direct`/`by-elimination` confidence is already
  `MUTATION_GRADE` and `sdkman` is NOT added to `UNMANAGEABLE_OWNERS`. Actually running
  `sdk upgrade` stays the existing `status="unsupported"` refusal with a real command in the text.
  A brownfield SDKMAN may have `sdkman_auto_answer=false` (see executors.py `_sdkman` comment) and
  would hang on an interactive prompt inside the Textual worker. An honest refusal naming the
  command beats a hang.
- **`own installer` label:** `_INSTALLER_KIND_LABELS["script"]` changes from `install script` to
  `own installer` (D-07 wording). This is one table value, so `owner_label`/`owner_detail` and
  `removal_label` stay in lockstep.

Output harness note: if `uv run pytest` prints a false "No tests collected", re-run the same args
via `.venv/bin/pytest` before concluding anything.
</objective>
