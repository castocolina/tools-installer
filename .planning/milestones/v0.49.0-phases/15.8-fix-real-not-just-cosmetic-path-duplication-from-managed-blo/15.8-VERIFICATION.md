# Phase 15.8: Fix real (not just cosmetic) PATH duplication from managed-block sourcing — Verification Report

**Phase Goal:** Every PATH entry this installer writes into a shell rc file is self-deduping at runtime. A nested or child shell that re-sources the file N times ends up with exactly one copy of each managed directory, proven by running real shells rather than by asserting on the emitted string. Existing installations migrate automatically the next time apply/fix runs, through the block-replacement mechanism that already exists. No PATH-writing code in the repo emits a plain unconditional export any more. A machine carrying a generic ~/.shellrc ends up with one canonical file (~/.myshellrc) plus a marked stub, with the foreign content copied forward before anything is replaced.

### HV-1: a real `~/.shellrc` consolidates correctly. RESOLVED

**Evidence (orchestrator container, Fedora, non-root `tester`):** `uv run setup.py --fix` was run on a hand-written `~/.shellrc` in a real HOME. That command is exactly what `make fix` runs (`Makefile:22-23`). The file held aliases, two plain PATH exports, a conditional `.` source and an `EDITOR` export.
- `~/.shellrc` became exactly the marked stub, sourcing `/home/tester/.myshellrc`.
- `~/.myshellrc` holds the original content verbatim inside the `consolidated shellrc` marker pair, followed by the guarded `path` block. The single blank line before the end marker is the original's trailing newline: `consolidation_block` does `body.split("\n")` (`shellrc.py:267`), so nothing was rewritten.
- The backup's sha256 equals the original's (`aa20dbfd...`), so one `mv` restores it byte-for-byte.
- A second `--fix` changed no bytes in any of the three files, so the run is idempotent through the real CLI.
- The real `~/.bashrc` gained one direct `.` route. Fedora's stock `.bashrc` has an unresolvable `~/.bashrc.d` loop, so the classifier answered "unprovable" and kept the ordinary route, which is the documented branch.
- "Runs the canonical file once" is confirmed by arithmetic. `/opt/myapp/bin` reads 6 both after sourcing `~/.myshellrc` directly 5x (check 2) and after sourcing `~/.bashrc` 5x (check 3). So each `.bashrc` source runs `~/.myshellrc` exactly once, with no second route.

**Not exercised here, already proven elsewhere:** The transcript does not report the backup's mode bits; the 0640 preservation is proven by the earlier live sandbox run and the 15.8-04 tests. The rewriter path, where `.bashrc` already sources `~/.shellrc`, did not occur because Fedora's stock `.bashrc` does not do that; it is proven by the 15.8-05/06 named tests and the real-shell `__N=1` counter in the previous report. The test file was written by the orchestrator, not by the developer, but it goes through the real entry point with realistic content. That was the one thing the earlier fixture-only proof lacked.

### HV-3: the originating symptom is attributed correctly. RESOLVED

The item asked for confirmation that any directory still at 2x after a new login traces to a foreign writer and never to `~/.myshellrc`. It was not asking whether this host has zero duplicates; foreign writers are outside 15.8's scope. That attribution now follows from verified parts:
1. The guard adds a directory only when neither of its spellings is already on PATH. That has now been proven in bash, `/bin/sh`, zsh and dash, with 1 and 5 sources and with both spellings seeded.
2. A read-only check on the real host `~/.myshellrc` found that every line mentioning `PATH` is a `case`-guarded line. There is no unguarded writer in the installer's canonical file. The D-02 invariants keep the rest of the repo clean.
3. So the managed block can never be the second writer of any PATH string. Any count of 2 or more must involve a non-guard writer, which is foreign by (2).

The container confirms this through the real wired login-chain file. Sourcing `~/.bashrc` 5x gave identical counts under bash, zsh and dash: the managed dir stayed at 1, and every duplicate (`~/bin` x7, `/opt/myapp/bin` x6) came from the user's own carried-forward plain exports. Those are deliberately left as they are, and the 15.8-05 pin documents that.

**Residual, not blocking:** No genuinely interactive `bash -l -i` was driven on this host itself, because that would execute the host's foreign rc lines, such as fnm's state writes, against the real HOME. Any duplicate that such a session showed would be foreign by the argument above and belongs to Phase 16 or later rc-hygiene work, not to 15.8.
