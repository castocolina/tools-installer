<objective>
Build the SAFE HALF of D-04's `~/.shellrc` consolidation: every precondition that must hold before
a single byte is written, a backup that genuinely makes the operation reversible on the user's
machine, and the one happy path proven end-to-end in a real shell.

The source-line classifier (what to do about a line inside `~/.shellrc` that sources
`~/.myshellrc`, and the refusals that surround it) is plan 15.8-05. Wiring into
`configure_path`/`setup.py` is plan 15.8-06.

Purpose: D-04 — some machines carry a generic `~/.shellrc` (a different, conventional name some
other tool or base system created) alongside or instead of this project's `~/.myshellrc`. Two
shell-config files with ambiguous sourcing order can independently export the same PATH entries,
which is the same class of duplication D-01/D-02/D-03 fix. The requirement is "the end state has
one canonical file", not a specific merge algorithm.

Output: `consolidate_shellrc()`, its precondition helpers, the `ShellrcConsolidation` result type
and the `ShellrcRefusal` exception in `installer/shellrc.py`, plus unit and real-shell tests.

**Why this plan is split out from 15.8-05.** Cross-AI plan review round 1 landed three HIGH and
one MEDIUM finding on what was previously one plan. Two of them — the symlink-following write and
the insufficient backup — are preconditions that must be settled before any write exists at all;
the other two are about rewriting text inside the copied content. Merging them would have made a
five-concern plan whose tracer could not be satisfied. This plan owns "never write into the wrong
file, and always be able to undo the write you do make".

**The design, resolved.**

- Detection trigger: `~/.shellrc` merely EXISTS. No ownership check on it is needed or possible;
  this project has never written that filename (confirmed by grep over `installer/`).
- PRECONDITIONS FIRST, before any read-modify-write. The same-file check and the symlink check
  below run before the copy-forward, not between the writes.
- The content is copied forward VERBATIM into `~/.myshellrc`, inside its own new marker pair,
  applied through the existing `apply_block`. Its own markers — not the PATH block's — are what
  keeps foreign content out of the span `write_myshellrc` rewrites, and what makes a repeat run
  idempotent instead of appending a second copy.
- Research Open Question 3 is resolved as option (b) with its gate: `~/.shellrc` is replaced by a
  MARKED stub that sources `~/.myshellrc`. Option (a), leaving the file untouched, would leave two
  live files with ambiguous precedence — exactly the state D-04 exists to end. The marker is what
  makes the stub recognizable on the next run and reversible later.
- Ordering: copy forward FIRST, backup SECOND, stub THIRD. This is the inversion of `omz.py`'s
  record-before-write, and it is deliberate: the exposed state after a crash between the writes is
  content present in more than one place, which the next run resolves idempotently. There is no
  rollback branch because the failure state is already the safe one.

**Why the two symlink preconditions exist, stated at full weight (review HIGH-03).**
`installer/atomic.py:42` is literally `target = path.resolve() if path.is_symlink() else path`.
`atomic_write_text` deliberately FOLLOWS a symlink — correct for the dotfiles this project owns,
because it keeps a dotfile-manager's `~/.zshrc -> repo/zshrc` link intact. Applied to a foreign
file this project is about to REPLACE, it is a content-destroying defect:

- With `~/.shellrc -> ~/.myshellrc`, the copy-forward write lands in `~/.myshellrc`, and then the
  stub write — aimed at `~/.shellrc` — resolves to `~/.myshellrc` and REPLACES it. The end state
  is a single file consisting of a stub that sources itself. Catastrophic and recursive.
- With `~/.shellrc -> ~/somewhere/else`, the stub replaces that unrelated file while the backup is
  written beside the LINK. `mv ~/.shellrc.tools-installer.old ~/.shellrc` would then replace the
  symlink with a plain file — not a restoration of the original state, so D-04's `reversible`
  claim would be false.

Both are REFUSALS. Refusing is safe, reportable and testable; guessing is not. A dotfile-manager
user whose `~/.shellrc` is a symlink gets a reason naming the link and keeps both files exactly as
they were.

**Why the backup rules changed (round 1 review MEDIUM-01).** The original design wrote the backup
with `read_text()` + `atomic_write_text()` and claimed the result was byte-identical. It is not:
`Path.read_text()` opens in universal-newline mode, so a CRLF file comes back with bare newlines
and is written back that way — verified this planning session (`b"a\r\nb\r\n"` reads as
`'a\nb\n'`). It also preserved an existing backup while still replacing the current `~/.shellrc`,
so "reversible with one `mv`" was false whenever that pre-existing backup came from another tool
or from an older original. Both are fixed below: bytes in, bytes out, no-clobber creation, and a
mismatching pre-existing backup is a refusal rather than a shrug.

**Why matching bytes are NOT enough to accept a backup (round 2 review HIGH-03).** The resumed-run
rule above compares the existing backup's bytes to the current `~/.shellrc`. Two shapes pass that
comparison while destroying the thing it exists to protect:

- **A SYMLINK at the backup path pointing at `~/.shellrc`.** It reads byte-equal, so it is
  accepted as a resumed run. The stub write then replaces `~/.shellrc` — and the "backup" now
  resolves to the stub. The original bytes are gone, and the promised
  `mv ~/.shellrc.tools-installer.old ~/.shellrc` would point a link at itself. The single most
  destructive way to pass this check is to not be a file at all.
- **A regular file with matching bytes but DIFFERENT permission bits.** D-04's recorded promise,
  and this plan's own Task 2 assertion, is that a restoring `mv` reproduces the original's bytes
  AND its mode. A backup that matches on bytes alone cannot keep that promise — a `0600` original
  restored as `0644` is a disclosure, and a `0755` original restored as `0644` breaks a file the
  user executes.

So the backup is `lstat`-ed — not `stat`-ed — before anything else, must be a REGULAR FILE, is
read through an `O_NOFOLLOW` descriptor so the check and the read cannot disagree under a race,
and must match on bytes AND `S_IMODE`. Anything else refuses. This is the same discipline
`installer/daemon.py::_is_our_wrapper` applies to a same-named file it did not create: when
ownership of a path is unclear, stop.

**Why a non-UTF-8 `~/.shellrc` is a refusal, not a decoding trick (round 2 review MEDIUM-02).**
The plan promises raw-byte handling and then derives the copy-forward body with
`original_bytes.decode("utf-8")`. On invalid bytes that raises `UnicodeDecodeError`, which is
neither `OSError` nor `ShellrcRefusal` — so it would escape every handler this phase installs and
surface as a traceback from `make fix`. The two honest options are a `surrogateescape` round trip
or a typed refusal. **This plan refuses**, for three reasons: this project already made exactly
this call once (`installer/omz.py:172` raises `… is not valid UTF-8; refusing to rewrite it`);
a `surrogateescape` round trip would carry undecodable bytes through `apply_block`'s line
splitting and plan 15.8-05's classifier, neither of which has any idea what to do with them; and a
refusal tells the user precisely what to do by hand, which is a shippable outcome, while a
half-correct encoding path is a liability. The check runs BEFORE any write, in the precondition
pass, so a refusing file is a byte-exact no-op like every other refusal here.

**Why the live file is revalidated before the stub write (round 2 review MEDIUM-01).**
`~/.shellrc` is read once, then two writes happen, then it is replaced. An edit landing in that
window exists in neither the backup nor the copied-forward block, and the stub write would destroy
it silently. `O_EXCL` protects only the backup PATHNAME, not the original's content. So the read
takes an identity-bound snapshot — an `O_RDONLY|O_NOFOLLOW` descriptor, its `fstat` device and
inode, and the bytes read from that same descriptor — and immediately before the stub write the
file is re-opened and both identity and bytes are compared. A mismatch refuses, and the refusal is
made a byte-exact no-op by undoing only what THIS call created: `~/.myshellrc` is restored to the
bytes captured before the copy-forward, and the backup this call created with `O_EXCL` is removed.
That is a narrow, provable undo of two known writes, not a general rollback branch — the
crash-safety reasoning below is unchanged, because a crash still leaves the content in more than
one place and nothing is undone by a process that is no longer running.

**THE FIXED STEP ORDER, stated once and repeated verbatim by every task (round 3 review HIGH-01).**
Earlier revisions put the backup validation inside the precondition pass, ahead of the check that
recognizes this project's own stub — while Task 2 simultaneously asserted the already-check came
first. Two tasks of one plan contradicting each other is not a stylistic problem: following the
action literally destroys idempotency. After a successful run the backup holds the ORIGINAL bytes
and `~/.shellrc` holds the STUB, so a backup-versus-current-file byte comparison reached on the
second run ALWAYS differs, and the run returns `refused` where it must return `already`. Plan
15.8-06 reads that outcome and would add a second direct route to `~/.myshellrc` on every later
run — the exact duplication this whole phase exists to remove.

So there is exactly one order, and nothing may be moved within it:

1. **Absence** — no `~/.shellrc` (or a dangling link): return `absent`.
2. **Hazards** — `~/.shellrc` or `~/.myshellrc` is a symlink, or the two resolve to one file:
   return `refused`. This is the HIGH-03 work, and it stays first because every later step reads
   or writes through one of those two paths.
3. **Snapshot and decode** — one `O_RDONLY|O_NOFOLLOW` descriptor, its `fstat` `(st_dev, st_ino)`
   and `S_IMODE`, the bytes from that same descriptor, and a UTF-8 decode whose failure is a typed
   refusal. This is the MEDIUM-01/MEDIUM-02 work, and it moves AHEAD of the stub check so that
   check reads the same bytes everything else does, rather than taking a second, racy read.
4. **Owned stub** — the decoded snapshot is a well-formed stub this project wrote: return
   `already`. No backup work, no `stat` of the backup path, no writes. This is a completed run
   being re-run, and the only correct answer is "nothing to do".
5. **Backup validation** — only now, and only against a snapshot that is guaranteed NOT to be a
   stub, is an existing backup checked for usability. This is the round 2 HIGH-03 work, unchanged
   in content and moved in position.

Steps 4 and 5 are ordered by a fact about the world, not by preference: the backup and the live
file are SUPPOSED to differ once consolidation has succeeded. A check that treats that difference
as a conflict is asking the wrong question of a finished job.
