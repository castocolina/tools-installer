# Phase 15.8: Fix real (not just cosmetic) PATH duplication from managed-block sourcing - Research

**Researched:** 2026-09-22
**Domain:** Shell rc-file generation (Python string builders) + POSIX shell semantics
**Confidence:** HIGH

## Summary

The fix is small and low-risk: replace the one f-string in `managed_block()` and the
one f-string in `write_pnpm_home()` with a shared, pure `Path -> str` emitter that
produces the same `case ":$PATH:" in *":{dir}:"*) ;; *) export PATH="{dir}:$PATH";;
esac` idiom pnpm's own installer already uses and this codebase already documents as
self-deduping (`installer/rcclean.py:61-70`). Everything downstream of that one change
— `apply_block`'s idempotent replace, `rcclean.py`'s duplicate-line detector, Doctor's
`audit_path`/`guidance.py` — needs **zero code changes**, verified live in this
session, not assumed. The only genuinely new code is: (1) the shared emitter itself,
(2) `existing_managed_bin_dirs()`'s parser, which must learn the new line shape (a
research finding below: it currently has **zero production callers**, changing the
regression-risk framing in CONTEXT.md's canonical refs), and (3) D-04's `~/.shellrc`
consolidation, which has no exact precedent in this codebase and must be assembled
from three partial analogs.

Two important corrections to CONTEXT.md's canonical-refs framing, both verified this
session and neither contradicting any locked decision:

1. **`installer/status.py` is NOT the PATH-audit generator.** It answers "is this
   tool installed" (`is_installed`). The actual PATH-duplication audit lives in
   `installer/doctor.py::audit_path` + `installer/guidance.py`. Point the planner's
   verification task there, not at `status.py`.
2. **`existing_managed_bin_dirs()` (the function CONTEXT.md names as "will need
   updating in lockstep... A wrong answer here silently breaks Doctor's audit and
   the uninstall path") has zero production callers today** — Doctor's audit reads
   bin dirs from the registry via `collect_bin_dirs`, not by parsing the rc file
   back, and the uninstall path removes the block wholesale via `strip_block`,
   never via `existing_managed_bin_dirs`. Neither breaks if this function is left
   unfixed. It should still be fixed (see Q2), just with lower urgency/blast-radius
   than CONTEXT.md's framing implies.

**Primary recommendation:** add one pure helper — `path_export_guard(directory:
Path) -> str` — beside `managed_block()` in `installer/shellrc.py`, emit its output
per-directory in both `managed_block()` and `write_pnpm_home()`, fix
`existing_managed_bin_dirs()`'s parser to extract the directory from the new line
shape via a regex search (not prefix/suffix slicing) rather than exact-line
matching, and implement D-04 as a new pure `shellrc.py` function called once from
each of the 4 existing `configure_path()` call sites in `setup.py`.

### Pattern 1: The shared self-deduping emitter

**What:** One pure function, `path_export_guard(directory: Path) -> str`, returning
the single-line case-guard fragment for one directory. `managed_block()` calls it in
a loop (one per `bin_dirs` entry); `write_pnpm_home()` calls it once for `pnpm_home`.

**When to use:** Any time this codebase needs to add a directory to `$PATH` from a
shell rc file that may be re-sourced by a nested/child shell.

**Verified-live reference shape** (bash, zsh, and this host's `/bin/sh` — a bash
binary invoked as `sh`, not `dash`; see Environment Availability — all produced
identical, single-copy PATH after 5 re-sources):
```sh
# Source: installer/rcclean.py:61-70's own docstring (already in this repo),
# cross-checked live against bash 5.3.9, zsh 5.9.2, and /bin/sh here (2026-09-22).
case ":$PATH:" in *":/home/u/.local/bin:"*) ;; *) export PATH="/home/u/.local/bin:$PATH";; esac
```

```python
# installer/shellrc.py — proposed addition, beside managed_block()
def path_export_guard(directory: Path) -> str:
    """One self-deduping PATH-prepend line: a no-op if `directory` is already
    on PATH, else prepends it. Re-sourcing this line N times in a child shell
    adds `directory` to PATH at most once — this is the property managed_block()
    and write_pnpm_home() both need and neither had before this phase.

    Paths are double-quoted but not otherwise escaped: they come only from the
    trusted registry and Path.home(), never from user input — same trust
    boundary managed_block() already documented.
    """
    return f'case ":$PATH:" in *":{directory}:"*) ;; *) export PATH="{directory}:$PATH";; esac'
```

`managed_block()` becomes:
```python
def managed_block(bin_dirs: list[Path]) -> str:
    lines = [_PATH_BEGIN]
    lines.extend(path_export_guard(directory) for directory in bin_dirs)
    lines.append(_PATH_END)
    return "\n".join(lines)
```

`write_pnpm_home()`'s PATH line becomes `path_export_guard(pnpm_home)` in place of
`f'export PATH="{pnpm_home}:$PATH"'` — the `export PNPM_HOME="{pnpm_home}"` line is
untouched (it's a plain assignment, not a PATH mutation, and is idempotent by
construction — re-assigning the same value has no accumulation effect).

### Pattern 2: `existing_managed_bin_dirs()`'s reader must change from exact-match to extraction

**What:** Today (`installer/shellrc.py:89-97`) the reader does exact prefix/suffix
string slicing on the WHOLE line:
```python
prefix = 'export PATH="'
suffix = ':$PATH"'
for line in lines[start + 1 : stop]:
    if not (line.startswith(prefix) and line.endswith(suffix)):
        continue
    candidate = Path(line[len(prefix) : -len(suffix)])
```
Once `managed_block()` emits `case ":$PATH:" in *":{dir}:"*) ;; *) export
PATH="{dir}:$PATH";; esac`, the line no longer *starts with* `export PATH="` (it
starts with `case`), so this exact match silently returns `[]` for every
freshly-written file.

**Fix shape (verified live this session):** switch from `startswith`/`endswith` to
a `re.search` for the embedded fragment, which matches regardless of what wraps it —
proven against the exact proposed guard line:
```python
import re
_DIR_FRAGMENT = re.compile(r'export PATH="(.+):\$PATH"')
...
for line in lines[start + 1 : stop]:
    match = _DIR_FRAGMENT.search(line)
    if match is None:
        continue
    candidate = Path(match.group(1))
```
This also still matches the OLD plain-export shape from a not-yet-migrated file (the
fragment `export PATH="{dir}:$PATH"` is a literal substring of both the old line and
the new guard line), so a mid-migration file — old shape on disk, not yet re-applied
— parses identically either way. No dual-shape branching needed.

**When to use:** Only if the planner decides to keep `existing_managed_bin_dirs()`
(see Open Questions — it has 0 production callers today; rule 5 says "deleted or
adopted", and CONTEXT.md's canonical refs name it for lockstep update).

### Pattern 3: D-04's `~/.shellrc` → `~/.myshellrc` consolidation

**No exact precedent in this codebase** for "merge file A's content into file B and
leave one canonical file" (confirmed — grep found zero `.shellrc` references
anywhere in `installer/`). Assembled from three partial analogs, each verified live
this session:

1. **`installer/omz.py::write_plugins`** (`installer/omz.py:432-478`) — the
   content-merge-with-provenance half. Verified shape: read existing content
   (`_read_rc`), compute the diff, **write a transactional record before the
   mutating write** (`_record_owned(state_path, tuple(owned))` at line 466, BEFORE
   `_atomic_write(zshrc_path, updated)` at line 469), and roll the record back on a
   failed write:
   ```python
   # installer/omz.py:463-477 (verified read in full)
   previous = _record(state_path)
   owned = list(previous or ())
   owned.extend(name for name in added if name not in owned)
   _record_owned(state_path, tuple(owned))
   try:
       if updated != original:
           _atomic_write(zshrc_path, updated)
   except OSError:
       if previous is None:
           _clear_owned(state_path)
       else:
           _record_owned(state_path, previous)
       raise
   ```
   Apply to D-04: record (comment block or state) that `~/.shellrc`'s content was
   consolidated, THEN write `~/.myshellrc`, with rollback on failure.

2. **`installer/daemon.py::_is_our_wrapper`/`install_wrapper`**
   (`installer/daemon.py:294-321`) — the ownership-sentinel discipline, verified
   read in full:
   ```python
   # installer/daemon.py:301-319
   def install_wrapper(bin_dir: Path) -> Path:
       ...
       target = bin_dir / WRAPPER_COMMAND
       if target.exists() and not _is_our_wrapper(target):
           raise OSError(f"{target} exists and is not managed by tools-installer")
   ```
   D-04 needs the **inverse**: `~/.shellrc` is, by construction, always foreign (this
   project has never written that filename — confirmed by the same grep above), so
   no sentinel check on `~/.shellrc` itself is needed; the sentinel discipline
   applies instead to `~/.myshellrc` (the file this project DOES own and already
   writes marker blocks into via `apply_block`) — never silently overwrite or delete
   `~/.shellrc` without copying its content forward first (D-04's own reversibility
   note).

3. **`installer/env_redirect.py::competing_conf_paths`**
   (`installer/env_redirect.py:265-291`) — the closest match for *detecting* a
   competing file, verified read in full: a pure, read-only scan returning the list
   of other files carrying the same responsibility, as data for the caller to act
   on — it does not itself delete or merge. D-04's detection half (does `~/.shellrc`
   exist) should follow this shape: a pure predicate/scanner, called once per the
   same 4 `configure_path()` call sites, with the actual merge as a separate step.

**Design recommendation (synthesizing all three, for the planner to finalize):**
- A pure `shellrc_needs_consolidation(home: Path) -> bool` (or equivalent) checks
  `(home / ".shellrc").exists()`.
- The merge itself preserves `~/.shellrc`'s content **verbatim**, copied into
  `~/.myshellrc` — CONTEXT's own discretion note's first option ("a preserved
  verbatim copy above the managed markers, to avoid losing any of the user's own
  non-managed customizations"). This is the only structurally safe option: appending
  raw foreign content directly into the space `apply_block` manages could corrupt a
  future re-apply if that foreign content happens to contain a marker-shaped line.
  Copy it in **above** `_PATH_BEGIN`/`_SOURCE_BEGIN`, the same way `apply_block`
  already preserves arbitrary user content above/below its own managed span.
- Sourcing-loop check (flagged explicitly in the research prompt): before copying
  `~/.shellrc`'s content in, scan it for a line that sources `~/.myshellrc` (or
  vice versa — scan `~/.myshellrc` for a line sourcing `~/.shellrc`). If found,
  either strip that specific line before merging, or refuse the automatic merge and
  surface a manual-action message — a merge that silently created a self-sourcing
  loop would be a strictly worse regression than leaving two files in place. This
  case is unverifiable on this host (`~/.shellrc` does not exist here, per CONTEXT.md)
  — flagged `[ASSUMED]`, needs either a synthetic-fixture test or explicit
  acknowledgment as a residual risk at plan time.
- What to do with the original `~/.shellrc` file: per D-04's reversibility note
  ("not a deletion of anything without first copying it forward"), leave it in place
  (do not delete). Two sub-options for the planner to choose between: (a) leave it
  completely untouched (now-orphaned/unsourced content, since nothing changes what
  sources `~/.shellrc` itself — a no-op file), or (b) overwrite it with a one-line
  stub `. "$HOME/.myshellrc"` so anything still sourcing `~/.shellrc` directly still
  picks up the consolidated content. Option (b) is more complete (closes the "two
  files with ambiguous precedence" gap D-04's own rationale names) but is a second,
  separate mutation of a foreign file the ownership-sentinel discipline (analog 2)
  argues against touching without a marker. Recommend (b) but gated behind writing a
  tools-installer marker comment into the stub first (`# >>> tools-installer stub >>>`)
  so a later uninstall/re-consolidation can recognize and safely remove/replace it —
  this is a genuine open design point for the planner, not fully resolved by
  precedent.

### Anti-Patterns to Avoid

- **Do not add `dash`/`[[ ]]`-based checks** (bash/zsh-only `[[` test, or arrays) —
  breaks under `/bin/sh` on any distro where `sh` is genuinely POSIX `dash`/`ash`
  rather than bash-as-sh (this host's `/bin/sh` happens to be bash; do not rely on
  that being universal — see Environment Availability).
- **Do not collapse all directories into one `case` with multiple `|`-joined
  patterns.** Loses per-directory line attribution needed by any future reader and
  diverges from the pnpm precedent this phase is explicitly matching.
- **Do not silently overwrite `~/.shellrc`.** D-04 explicitly requires
  copy-forward-before-touch; the file is foreign, unowned content by construction.
- **Do not let D-04's merge write directly into the space `apply_block` manages**
  for `~/.myshellrc`'s own marker block — foreign content containing a marker-shaped
  line would corrupt future re-applies.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Detecting whether a directory is already on PATH before adding it | A custom `$PATH.split(':')` Python-side check, or a bespoke shell conditional | The `case ":$PATH:" in *":$dir:"*) ;; *) ...` idiom, byte-for-byte matching pnpm's own installer output | Already the exact form this codebase's own `rcclean.py` documents and skips; inventing a different shape risks `rcclean.py` no longer recognizing it (regression, verified NOT to happen with this exact shape — see Q1) |
| Crash-safe multi-file merge (D-04) | A bespoke read-modify-write with no rollback | `installer/atomic.py::atomic_write_text` (sibling-temp + `os.replace`), the project's one shared atomic-write primitive, already used by `omz.py`/`daemon.py`/`systemd_daemon.py` | `write_myshellrc`'s own plain `path.write_text()` is a lower-stakes precedent (single well-understood managed block); D-04's merge is a higher-stakes, harder-to-reconstruct operation (foreign content) and should follow the atomic-write convention those other higher-stakes files already use, not `shellrc.py`'s own lower-stakes one |

**Key insight:** Every piece of this fix already has a live, already-shipped analog
somewhere in this codebase except D-04's file-merge (no exact match, 3 partial
analogs synthesized above). Nothing here is novel shell-scripting territory — the
correct idiom, the correct block-replace mechanism, and the correct dead-line
recognizer are all already written and tested; this phase wires the first correctly
and verifies the second two need no change.

## Common Pitfalls

### Pitfall 1: Assuming `existing_managed_bin_dirs()` is load-bearing when it is dead code today

**What goes wrong:** A plan that treats fixing this function as equally urgent/
high-blast-radius as fixing `managed_block()` itself, because CONTEXT.md's canonical
refs describe it as something "Doctor's audit and the uninstall path" depend on.

**Why it happens:** That description was accurate when the function's sibling
caller (a since-deleted `installer/install_actions.py`, removed in commit `67d29c3`,
"retire install-actions") existed. It no longer is — verified via exhaustive
`grep -rn "existing_managed_bin_dirs"` across the whole repo (source + tests):
one match, the definition itself.

**How to avoid:** Fix it anyway (consistent with CONTEXT's explicit lockstep-update
framing and this codebase's own "no orphan helpers, deleted or adopted" rule), but
do not gate the phase's risk assessment on it, and do not spend disproportionate
plan effort hardening it beyond matching the new shape.

**Warning signs:** A plan task titled something like "critical: fix
existing_managed_bin_dirs to prevent Doctor audit regression" — the actual Doctor
audit (`doctor.py::audit_path`) reads the registry via `collect_bin_dirs`, never this
function.

### Pitfall 2: `write_pnpm_home()` is also dead code today — D-02's "second site" has zero production callers

**What goes wrong:** Assuming fixing `write_pnpm_home()`'s shape alone closes D-02's
"no second known site left behind" — it removes the *defect* from that function's
own output, but the function is never called in production, so the actual live PATH
duplication for pnpm's bin dir the user observed (confirmed: "3 each of ...pnpm...
bin dirs" in CONTEXT.md's live evidence) comes from a **different** mechanism:
`registry.toml`'s `pnpm` tool entry declares `bin_dir = "~/.local/share/pnpm/bin"`
(`installer/registry.toml:1941`), which `collect_bin_dirs()` folds into
`managed_block()`'s own dir list — i.e., pnpm's bin dir is *already* covered by
fixing `managed_block()` alone, through the normal per-tool `bin_dir` mechanism, not
through `write_pnpm_home()`.

**Why it happens:** `write_pnpm_home()` was added in commit `56a399d` ("run typed
post-install actions", 2026-07-25) as part of `installer/install_actions.py`'s
now-deleted pnpm setup action, and was never re-wired to any caller when that module
was retired in `67d29c3` (2026-09-11, ~6 weeks later). `vulture --min-confidence 60`
(the project's own dead-code tool, run below its own configured `min_confidence =
80` threshold) confirms:
```
installer/shellrc.py:72: unused function 'existing_managed_bin_dirs' (60% confidence)
installer/shellrc.py:200: unused function 'write_pnpm_home' (60% confidence)
```
— both silently pass `make validate` today because the project's own vulture
threshold (80) is set above the confidence level (60%) vulture assigns to an unused
function, a pre-existing gap in the dead-code gate unrelated to this phase.

**How to avoid:** Still apply D-03's shape fix to `write_pnpm_home()` — it is a
locked decision (D-02 names it explicitly) and leaving broken dead code around
(returning the old plain-export shape forever) is worse than fixing it. But the
planner should explicitly decide, and record the decision, on one of: (a) fix the

deleted or adopted"). (a) is the minimal-risk choice consistent with D-02's literal

**Warning signs:** A plan that describes wiring `write_pnpm_home()` into a new
caller as in-scope — that would be new functionality beyond D-02's literal ask
("apply [the mechanism] to... the pnpm_home export") and should be flagged for
discussion rather than silently added.

### Pitfall 3: Coverage floor interaction

**What goes wrong:** `existing_managed_bin_dirs()` and `write_pnpm_home()` currently
have zero test coverage (confirmed: no test file references either name) while the
project enforces `fail_under = 90` (`pyproject.toml:56`) and the whole suite still
passes — meaning other files are carrying enough coverage margin that these two
untested functions don't sink the aggregate. Adding the case-guard rewrite to both
functions without adding tests would keep this blind spot; the phase should add
direct unit tests for both (not just for the new shared emitter), closing a
pre-existing gap while touching this code anyway.

**How to avoid:** New tests in `tests/test_shellrc.py` for `path_export_guard()`
directly, plus updated/new tests for `write_pnpm_home()`'s new output shape and
`existing_managed_bin_dirs()`'s new parser (or their removal, if the planner
chooses (c) above).

### Pitfall 4: Conflating the systemd/launchd `Environment=PATH=...`/`EnvironmentVariables["PATH"]` sites with the rc-file bug

**What goes wrong:** Treating `installer/systemd_daemon.py:261`
(`f"Environment={_quote(f'PATH={path_value}')}"`) or `installer/daemon.py:175`
(`"EnvironmentVariables": {"PATH": path_value, ...}`) as additional D-02 sites.

**Why it doesn't apply:** Both are single-assignment directives inside a generated
systemd unit / launchd plist file that is written whole (not appended-to or
re-sourced by nested processes) each time the daemon schedule is (re)applied —
verified by reading `render_service`/`render_plist` in full. There is no "re-source
N times, accumulate N copies" mechanism for a `.service`/`.plist` file the way there
is for a shell rc file sourced by every nested shell. **Confirmed out of scope; no
change needed.**
