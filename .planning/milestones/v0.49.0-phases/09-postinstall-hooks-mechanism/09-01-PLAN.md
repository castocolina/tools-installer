<objective>
Add the postinstall-hooks mechanism this phase's ROADMAP goal names: "A catalog tool can
declare a one-time, non-interactive follow-up action that runs immediately after its own
successful install, proven end-to-end via codegraph's MCP registration for whichever agent
hosts are already present." This plan builds and wires the whole mechanism — the registry
field, the closed dispatch table, the engine hook, the failure-visibility surface, and
`codegraph`'s own real hook — as one cohesive tracer, using `codegraph` (the phase's one
proving case) as the real end-to-end path rather than a synthetic placeholder.

09-RESEARCH.md (this session's live `codegraph --help`/source-reading pass against v1.2.0)
resolved REQUIREMENTS.md's Open Question 3 and found two things CONTEXT.md's D-02
discussion did not know when it was written: codegraph's real target id for Cursor is
`cursor`, not this project's own catalog id `cursor-agent` — a literal id mismatch this
mechanism must translate, not just naming — and `--target auto` (the seemingly obvious
"detect what's installed" flag) is UNSAFE for this purpose: reading codegraph's own
`installer/targets/registry.js::resolveTargetFlag` found it silently falls back to
registering `claude` when it detects ZERO installed hosts. Naively wiring
`codegraph install --target auto --location global --yes` as this phase's postinstall
command would write a Claude MCP config entry even on a machine where Claude Code is not
installed — a direct violation of REQ-codegraph-mcp-postinstall's "never installing those
hosts as a side effect... a documented no-op when none are installed." This plan's hook
computes its own explicit `--target` CSV from this project's own live host-presence check
and never passes `--target auto`; that invariant is the single most important thing this
plan pins with tests, not merely documents.

09-RESEARCH.md also found `codegraph install` is naturally idempotent (it merges into each
target's own config file rather than duplicating an entry), so
REQ-postinstall-idempotency-live-check is satisfied by this hook's own host-PRESENCE check
(never re-registering an absent host) plus that upstream idempotent merge — no new
state-tracking database on either side.

<design_decisions>
**Registry field shape: a closed dispatch-hook NAME, not a literal command string or a
`postinstall_script` file.** REQ-postinstall-field's own wording offers "inline (short
command string)" or a file reference "for anything multi-line." Neither fits: codegraph's
invocation is short, but its `--target` value cannot be known at registry-authoring
time — it depends on the machine's live state — so a literal string would need its own
templating micro-language for a single tool's one-off dynamic composition (09-RESEARCH.md's
own reasoning). Instead this plan reuses a pattern ALREADY IN THIS FILE:
`installer/model.py::SMOKE_CHECK_NAMES` + `installer/executors.py::SMOKE_CHECKS` — "the
registry selects a check by NAME from a closed, code-owned set... a registry edit cannot
introduce arbitrary post-install execution" (`.claude/architecture.md`). `postinstall`
follows the identical shape: a short registry string, but a HOOK NAME, validated against
`installer/model.py::POSTINSTALL_HOOK_NAMES` at load time, dispatched through
`installer/postinstall.py::POSTINSTALL_HOOKS`. This is safer than a literal command (no
new supply-chain-shaped surface where registry data becomes shell text) and needs no new
templating engine.

**Reconciling this against REQ-postinstall-field's literal wording (cycle-1 cross-AI
review HIGH 1; formally closed per cycle-2 HIGH 1, which correctly rejected a
plan-prose-only reconciliation as insufficient).** REQ-postinstall-field's original text
offered exactly two shapes: an inline command string, or a `postinstall_script` file
reference "for anything multi-line." A closed dispatch-hook NAME was neither of those
literally, so this is not merely explained here — `.planning/REQUIREMENTS.md`'s
REQ-postinstall-field entry and `.planning/ROADMAP.md`'s Phase 9 SC#1 have BOTH been
amended (in this same commit) to name the closed dispatch-hook-name shape as a third
accepted form, with the rationale recorded directly in the requirement text: `codegraph`'s
one proving case cannot be expressed as a static inline string (its `--target` value
depends on which agent hosts are live on THIS machine at install time), and a
`postinstall_script` file adds a whole new script-invocation surface for a one-line,
one-tool need. This is a genuine, normative-document amendment, not a plan-level
workaround — the requirement itself now says what this plan implements. What is also fixed
here is the requirement's OTHER literal demand — that dispatch be "aware of which
Method/kind actually installed the tool" — satisfied by actually passing the succeeded
`Method` into the dispatch call, not merely by having `method.kind` incidentally in
lexical scope at the call site.

**`postinstall` lives on `Tool`, not `Method`.** REQ-postinstall-field says "declared per
tool/Method (not kind-agnostic)" — read as "not tied to `kind`", not "must be declared
twice." codegraph's postinstall command is identical regardless of which of its two
`github_release` methods (macOS/Linux) succeeds (09-RESEARCH.md finding #1), so a
Tool-level field is simpler and sufficient, mirroring where `requires`/`recommends`
already live. "Aware of which Method/kind actually installed the tool"
(REQ-postinstall-execution-timing) is satisfied literally, not just structurally (cycle-1
review HIGH 1): the dispatch call passes the succeeded `Method` itself into
`run_postinstall`/the hook signature, so a future hook COULD branch on `method.kind`
directly, even though codegraph's own hook does not need to.

**Host-presence check uses `installer/status.py::is_installed(Tool)` against real,
loaded catalog `Tool` objects — never bare `shutil.which(tool_id)` (cycle-1 review
HIGH 2).** REQ-postinstall-idempotency-live-check's own text names the mechanism this
project already uses for every other live-check purpose: `installer.status.is_installed`,
not a hook-local re-implementation of PATH lookup. `is_installed` is itself a synchronous
`shutil.which(tool.cmd)` call (plus `detect_path`/app-bundle fallbacks that never fire for
these four hosts today) — confirmed not to hang or block the Textual event loop, same as a
bare `shutil.which` call would be, but going through the ONE seam this codebase already
uses for "is this tool present" keeps the postinstall mechanism from silently drifting out
of sync if `is_installed`'s detection logic is ever extended (a new `app` param, a new
`detect_path`) for one of these four hosts later. Rather than reloading the registry
inside the hook (redundant I/O, a second source of truth for what a `Tool` is), the four
host `Tool` objects are threaded through as a `tools: Mapping[str, Tool]` parameter on
`install_tool` itself.

**The `tools` mapping reaches `install_tool` through the REAL production call chain, not
a nonexistent direct call (cycle-2 cross-AI review HIGH 2).** Cycle-1's fix described
`run_wizard` calling `install_tool` directly; that is factually wrong — `installer/app.py
::run_wizard` never calls `install_tool` itself, it calls `installer/session.py
::run_installs`, which calls `install_tool` at THREE separate call sites (the initial
attempt, a checksum-mismatch retry, and a checksum-mismatch fallback) through its
`Install` Protocol. The fix now threads the mapping through that REAL chain: `run_installs`
gains a new `catalog: Mapping[str, Tool] | None = None` parameter (named `catalog`, not
`tools` — `run_installs` already has its own `tools: list[Tool]` parameter meaning "the
tools to install this run," a materially different thing from "the full catalog by id";
reusing the name would silently shadow it) and passes `tools=catalog` into all three
`install(...)` call sites; the `Install` Protocol's `__call__` signature gains the matching
`tools: Mapping[str, Tool] | None = ...` keyword-only parameter so it stays structurally
compatible with `install_tool`'s own signature. `run_wizard` builds `{t.id: t for t in
tools}` from the catalog list parameter it ALREADY receives (its own `tools: list[Tool]`
first argument — no new load, no new file I/O) and passes it as `run_installs(...,
catalog=...)`. This is the one and only new plumbing this mechanism needs, corrected to go
through every real hop.

**A postinstall hook's exception is isolated from the method ladder's own exception
handling by an actual `try/except/else` structure, not a same-`try`-block placement that
only claimed separation (cycle-1 review HIGH 3, corrected again per cycle-2: the cycle-1
fix inserted its `try/except Exception` textually AFTER `_perform(method, ctx)` but STILL
inside the SAME outer `try` that the method ladder's own `except (CommandError,
ExecutorError, VersionError)` clause guards — reading the real `installer/engine.py`
confirms the success branch, including the `return InstallOutcome(...)` line, sits inside
that one `try` body, so the cycle-1 prose describing the fix as sitting "after" that block
was not true of the actual code shape it specified).** The corrected structure replaces
the `try/except` with `try/except/else`: `_perform(method, ctx)` stays the ONLY statement
in the `try` body; the two existing `except` clauses are unchanged; a NEW `else` clause —
syntactically a sibling of `try`/`except`, never nested inside either — runs only when
`_perform` raised nothing, and is where the postinstall dispatch (in its OWN `try/except
Exception`) and the `return InstallOutcome(...)` now live. An unexpected hook exception is
therefore caught by the `else` clause's own inner `try/except Exception` before it could
ever reach — because Python never re-enters a `try`'s `except` clauses for an exception
raised in the `else` clause — the outer `except (CommandError, ExecutorError,
VersionError)` clause; this is now true both textually (a distinct clause, not a nested
block) and structurally (the two exception-handling regions can never fire for the same
raised exception). `install_tool` converts any such caught exception to
`f"postinstall hook {tool.postinstall!r} crashed: {exc}"` on `postinstall_warning`, exactly
like a hook's own well-behaved returned warning string.

**The postinstall hook invokes the freshly-installed `codegraph` binary by its resolved
absolute path, never a bare `"codegraph"` relying on PATH (cycle-2 cross-AI review
HIGH 4).** `installer/download.py::install_download` places a fresh `github_release`
binary's symlink at `installer.locations.bin_dir(method.params.get("bin_dir")) /
binname` — typically `~/.local/bin/codegraph` — and PATH wiring for that directory is a
SEPARATE, later step (`configure_path`/`make fix`), never guaranteed to have already run
by the moment this hook fires immediately after a fresh install. A bare `runner(["codegraph",
...])` would therefore rely on `codegraph` already being resolvable on the CURRENT
process's PATH, which is not guaranteed on a real machine (only accidentally true in a
container recipe that happens to pre-export `~/.local/bin`). `_codegraph_mcp_register`
already receives the succeeded `method` (per the HIGH 1 fix above) and uses it to compute
the exact same `bin_dir(method.params.get("bin_dir")) / "codegraph"` path
`install_download` just wrote to, and invokes THAT absolute path instead of the bare name
— correct regardless of whatever the current process's PATH happens to contain at this
exact moment.

**D-01's "no re-trigger later" is structural, not a guard.** `install_tool`'s
`ALREADY_INSTALLED` early return (`if is_installed(tool): return
InstallOutcome(tool.id, InstallStatus.ALREADY_INSTALLED)`) sits BEFORE the method ladder;
the postinstall dispatch call sits only inside the per-method success branch AFTER that
early return. A tool already on the machine never reaches the dispatch call at all —
D-01's limitation falls out of the existing control flow with zero new code, and Task 2
pins it with a test rather than trusting the reasoning alone.

**The `InstallOutcome`-five-file-surface flag from 09-RESEARCH.md does not apply literally
here.** That note (mirroring Phase 3's `blocked_by` addition, `tests/test_engine.py` +
whatever renders it) is the correct analog, not ONESHOT-RULES Rule 7's five-file "new
method `kind`" mirror (`test_model.py`/`test_executors.py`/`test_resolve.py`/
`test_registry.py`/`test_status.py`) — this plan introduces no new method `kind`, no new
executor, no new resolver rank. The actual mirror-coverage surface this mechanism touches
is `installer/model.py`, `installer/postinstall.py` (new), `installer/engine.py`,
`installer/render.py`, `installer/app.py`, and `installer/registry.toml`'s `codegraph`
entry — each with its own test file, exactly the `files_modified` list in this plan's
frontmatter. `installer/session.py`, `installer/deps.py`, `installer/resolve.py`,
`installer/status.py`, `installer/uninstall.py`, and `installer/policy.py` are NOT
modified: `Summary`/`summarize` bucket on `.status` only, unaffected by the new
`postinstall_warning` field on a successful outcome.
