# Phase 24.3 Learnings: Catalog audit skill (INSERTED)

## Decisions

### The fact gatherer is gated Python in `installer/`, the skill holds only text
`installer/catalog_audit.py` (run as `python -m`, `make audit-catalog`) prints facts and validates and stores reports; the skill under `.claude/skills/catalog-audit/` carries the judgment rules, with no Python.

**Rationale:** ruff, pyright, coverage and vulture cover only `installer/`, `tests/` and `setup.py`, and a `__main__` entry point is the production caller; verify-registry is the precedent.
**Source:** 24.3-CONTEXT.md (D-01), 24.3-04-SUMMARY.md

---

### Resume uses no state file: whole-file report plus a footer line
A report is written whole and is complete only when it ends with `<!-- catalog-audit:complete -->`; `SUMMARY.md` is rebuilt from the reports every run. A complete report is immutable.

**Rationale:** disk-only resume survives an interrupted run and keeps the tool read-only apart from the run directory; the cost is that report imperfections stay as written and late facts go to `findings.toml`.
**Source:** 24.3-CONTEXT.md (D-04), 24.3-02-SUMMARY.md, 24.3-05-SUMMARY.md, 24.3-REVIEWS.md (R1-05)

---

### `dispositions.toml` maps every drift key to a commit, a backlog item or `proposed`
`summarize --require-disposition IDS` exits 1 naming each unmapped drift key of those entries. Drift is sticky: no later finding clears it, and an `unknown` becomes `ok` only through a same-key `container:` `ok`.

**Rationale:** the review showed a gate that reads only the effective status can hide a report `drift` under a later `ok` or `unknown`; a key has one disposition so an open change is not hidden behind a commit.
**Source:** 24.3-REVIEWS.md (R2-03, R3-01, R3-02), 24.3-03-SUMMARY.md, 24.3-11-SUMMARY.md

---

### npm latest goes through its own `resolve_npm` seam, not an `npm:` prefix in the GitHub resolver
An installer-owned script method declares `latest_npm = "<package>"`; `VersionRefreshService(resolve_npm=...)` reads the npm `latest` dist-tag, budgeted and backed off like the GitHub source.

**Rationale:** the GitHub `TagResolver` resolves download tags and digests at six sites behind an identity check in `release_resolver`; only the version-status refresh needs an npm latest, so research option A1 was rejected.
**Source:** 24.3-CONTEXT.md (D-10 amendment), 24.3-01-SUMMARY.md

---

### OpenCode update re-runs the v2 installer; removal uses the `opencode2 service stop` recipe
The script method drops its `update` key, installs `https://opencode.ai/v2/install --no-modify-path`, and records both `opencode` and `opencode2`. The remove recipe head is the v2-only `opencode2` shim, bound only when a receipt proves that leaf, so an OpenCode 1 receipt skips it.

**Rationale:** v1's `upgrade --major` pipes the v2 installer without `--no-modify-path`, which edits shell rc files; v2's own `uninstall` deletes `~/.cache/opencode` and may edit rc files. A plain `service stop` recipe would fail on a v1 binary (review R1-03).
**Source:** 24.3-CONTEXT.md (D-07, D-08), 24.3-06-SUMMARY.md, 24.3-REVIEWS.md (R1-03)

---

### The retired `permission` key stays in a revert-only table, and a ledger-recorded one counts as ours
The `auto-approve` tuning writes only `permissions = [{action, resource, effect}]`. `RETIRED_KEYS` keeps `permission = "allow"` so old ledger entries still revert; a recorded `permission` reads `already`, an unrecorded one is the user's and blocks the write.

**Rationale:** a plain key swap would leave pre-24.3 entries unrevertable, and a naive sibling check would read every pre-24.3 install as "set by you" forever. Marked "needs confirmation"; the owner kept it in UAT.
**Source:** 24.3-CONTEXT.md (D-11), 24.3-07-SUMMARY.md, 24.3-UAT.md (test 1)

---

### Pi registers for codegraph only behind a capability probe; copilot needs a real CLI footprint
`pi` joins the target map gated by `HookPair.supported` (`codegraph install --print-config pi` must exit 0), so it stays dormant until codegraph ships the target. `copilot` maps to `copilot-cli` and counts as present only with a real footprint (not a `~/.copilot` holding only `ide/`); review F11 later identified the CLI by its `--version` signature and ignored dotfiles.

**Rationale:** the VS Code extension creates `~/.copilot/ide/` alone, and an explicit `--target copilot-cli` would write config for a CLI the user lacks; an older codegraph must neither write under `~/.pi` nor show a drift mark.
**Source:** 24.3-CONTEXT.md (D-12, D-13), 24.3-08-SUMMARY.md, 24.3-REVIEW.md (F11)

---

### Container proof is a wave-5 gate and per-distro, not per-entry
The landing container check ran as a gate before the push of the wave that changes the registry; the first audit ran one `all` pass per distro (fedora, debian, arch) instead of one container per flagged entry, within a 10-container budget.

**Rationale:** one pass per distro covered install, rerun, uninstall, leftover and reinstall for every Linux entry inside the 6 h budget; the host-safety claim rests on the fingerprint comparison and a clean `git status`. The owner kept both choices.
**Source:** 24.3-05-SUMMARY.md (Deviation 1), 24.3-10-SUMMARY.md, 24.3-UAT.md (test 1)

## Lessons

### Plan-level fakes and pins break with every signature change; name them in the plan
Review cycles 1 and 2 found HIGH gaps that were only unlisted test pins: `tests/test_postinstall.py:258`, `:245`, `:392-394`, `tests/test_agent_settings.py:974-995`, `tests/test_versions.py:596/609/616`. Executors then found stale line numbers and moved pins anyway (24.3-02 fakes, 24.3-09 `export PATH=` pins).

**Context:** the cross-AI review gate was the cheapest place to catch them; execution still needed re-location by symbol.
**Source:** 24.3-REVIEWS.md (R1-01, R1-02, R2-01, R2-02), 24.3-02-SUMMARY.md, 24.3-09-SUMMARY.md

---

### A write path that takes a user-supplied path needs a guard before any review
The code review's only HIGH (F1): `verify --state` accepted any existing JSON outside the repo (such as `~/.claude/settings.json`), and verify-registry then rewrote it whole. The fix refused symlinks, HOME dotdirs and non-flat-string JSON, and symlink refusal was extended to every path component down to the run directory (F7).

**Context:** plan review had required only a path inside the repo to be refused (R1-19, LOW).
**Source:** 24.3-REVIEW.md (F1, F7), 24.3-REVIEWS.md (R1-19), 24.3-SECURITY.md (T-24.3-04)

---

### A staleness check keyed on the wrong token reads almost every row stale
The stale-citation check took the first backticked span, which in reports is the citation itself, so 44 of 50 rows read stale; a fixed line whose comment still mentions the token read `current`. Fixes: a declared evidence token, comments ignored for py/sh/toml (F2). One scan row still reads `current` because a comment keeps the word `permission`.

**Context:** the plan-review whole-word fix (R1-24, R2-05) did not touch the token choice.
**Source:** 24.3-REVIEW.md (F2), 24.3-11-SUMMARY.md (Deviation 2), 24.3-VERIFICATION.md

---

### A rate limit must not become a permanent `unknown` in an immutable report
A GitHub 403/429 wrote `latest: unknown` into a report that can never be rewritten. `facts` now exits 75 on a rate limit so the writer waits and retries (F9); the skill's rate-limit eval and "rate limit stays unspent" line were corrected.

**Context:** immutable reports (decision above) make any transient failure recorded at write time permanent.
**Source:** 24.3-REVIEW.md (F9), 24.3-04-SUMMARY.md

---

### Resuming a multi-step loop must resume from recorded findings, not from "file missing"
The skill ran container checks only when `scripts.md` was missing, so an interrupted container step was skipped on resume; it now resumes from the findings still lacking a `container:` finding (F10). A related gap: re-running `scan` or `verify` for the same date overwrote the record and dropped drift rows from the gate (F3), so both now refuse to overwrite (exit 73).

**Context:** resume correctness was reviewed in the skill text, not just in the tool.
**Source:** 24.3-REVIEW.md (F3, F10)

**Context:** F12 also made removal proceed when the registered pid is gone or a zombie.
**Source:** 24.3-11-SUMMARY.md (Task 2), 24.3-REVIEW.md (F12, F13)

The landing container record sat on `394fa836`, before product fixes F11, F12, F13, F18, F19, F20, F21; the security audit carried it forward as C1 until the check was re-run on `eb9c2ea5`. ## Patterns

### Test and artifact tied by a test, so they cannot drift
The report template's example is extracted from its first fenced block and passed to `validate_report`; each tool-onboarding step heading the skill quotes is checked by a test; a test refuses `ARGS="..."` examples with a backtick or `$`; a test pins that every landing step the script runs is accepted by the driver's parser.

**When to use:** any documentation or template that mirrors a grammar or a command the code enforces.
**Source:** 24.3-04-SUMMARY.md, 24.3-09-SUMMARY.md, 24.3-SECURITY.md

---

### Verdict functions host-tested, verbs proven only by a real container run
The landing driver's verdicts (`remove_verdict`, `tuning_verdict`, named `TRACER_*` lines, `_UNPROVEN` for unproven claims) are unit-tested on the host; the verbs that drive installer code run only in a disposable container, and the driver refuses to run outside one.

**When to use:** harnesses that mutate a host (installs, `rmtree`) and must never run on the developer machine.
**Source:** 24.3-09-SUMMARY.md, 24.3-11-SUMMARY.md

---

### Whole-file atomic write with the completion marker last, plus refuse-on-symlink at every component
Reports, `findings.toml` and run records are written whole in one atomic write; completeness is the marker on the last non-empty line; every write refuses a symlinked leaf and the run dir refuses a symlink from the date directory up to `.planning`.

**When to use:** agent-authored files that a later run must trust without a state file.
**Source:** 24.3-02-SUMMARY.md, 24.3-SECURITY.md (T-24.3-04, T-24.3-06), 24.3-REVIEW.md (F7)

---

### Telemetry opt-out in the child environment of every probe
The version probe, the Pi gate's `codegraph_query` and the first audit session set `CODEGRAPH_TELEMETRY=0` and `DO_NOT_TRACK=1` (the second described only as a convention) so a read-only audit stays host-silent.

**When to use:** any probe that runs a third-party CLI during an audit.
**Source:** 24.3-02-SUMMARY.md, 24.3-08-SUMMARY.md, 24.3-REVIEWS.md (R1-13, R2-12)

---

### Fingerprint before and after the run, with named concurrent writers
The first audit compared 200 installer-relevant labels (digests of receipts and config ledgers, binary paths, MCP and tuned keys); 0 changed. The comparison names writers it excludes by design (agent sessions, `~/.codegraph`) instead of claiming whole-home byte identity.

**When to use:** proving "the audit changed nothing" on a host with other live writers.
**Source:** 24.3-05-SUMMARY.md, 24.3-REVIEWS.md (R1-08)

---

### Never mutate real state to produce a value: scratch copy, then port only the block
The drawio-desktop pin bump ran `make verify-registry --write` against a scratch registry and state, then a port script asserted that only `version`, `sha256` and `verified` lines differ inside the drawio block and every byte outside is unchanged.

**When to use:** applying one tool-generated change to a hand-annotated registry.
**Source:** 24.3-06-SUMMARY.md

---

### Prove the tests bite when no organic RED exists
When the Task 1 implementation already satisfied Task 2's tests, the executor removed the `NPM_PACKAGE_RE.fullmatch` guard temporarily and showed seven refusal tests fail before restoring it.

**When to use:** a test-only task whose tests pass on first run.
**Source:** 24.3-01-SUMMARY.md

## Surprises

### The first audit's drift table had 72 rows from an untouched tree, and one was the user's SDKMAN correction
The first run of the 86-entry registry produced 72 drift rows (removal recipe and paths 35, install method 19, script 9, update argv 4, postinstall hook 4, tuning 1). Four java/groovy/springbootcli/gradle rows described SDKMAN's designed handoff; the user pointed out SDKMAN can uninstall, and the installer prints that exact command by design, so they were dispositioned `proposed` with a `no change` note (no `no-change` value exists in the grammar).

**Impact:** 30 rows went to new Backlog 999.14, 22 to 999.15, 1 to 999.16; the grammar gap was recorded, not fixed.
**Source:** 24.3-05-SUMMARY.md, 24.3-11-SUMMARY.md (Deviation 1)

---

### The brew tap formula and `opencode` latest disagree: GitHub's latest was v1.19.5 while npm's was 2.x
GitHub `releases/latest` stayed on v1.19.5 (and its list mixes in `process-daemon-v*` tags) while the npm `latest` was 2.2.6 then 2.3.0; the tap's `opencode.rb` stayed 1.19.5 and ownership code reads a tap formula by its last segment, so tap hosts stay on 1.19.5.

**Impact:** forced the `latest_npm` source and left a recorded limit (hosts that installed through the tap) rather than a fix.
**Source:** 24.3-CONTEXT.md (D-09, D-10), 24.3-06-SUMMARY.md

---

### The installer's own wiring edits the rc files on a first install in a fresh home
UAT expected `~/.zshrc` and `~/.bashrc` unchanged by OpenCode's install, but on a fresh home the installer's centralized shell wiring added its `tools-installer source` block and created `~/.myshellrc`; a reinstall with the wiring in place left both hashes identical, and no `.opencode/bin` line went into either rc file.

**Impact:** the Expected text was corrected to "unchanged by OpenCode" rather than judged a failure.
**Source:** 24.3-UAT.md (test 3)

---

### `opencode service start` leaves a credential file the removal footprint never listed
Uninstall after `service start` left `service.json` (64 bytes, mode 600, in the state dir, not `~/.config/opencode`) behind. Fixed in a075242d: the file is removed after the stop succeeds or is moot, keeping the rest of the state dir.

**Impact:** a footprint gap found only by real use in a container; unit tests added.
**Source:** 24.3-UAT.md (test 3 side finding), 24.3-VERIFICATION.md

---

### A plan rule and a tool habit contradicted: the "no codegraph command" executor rule
Plans 01, 02, 03 said "start with `codegraph sync`" while the same plans forbade any `codegraph` command; executors resolved it differently (01, 02 read code directly; 03 ran `sync` once; 06 ran `sync` and `explore`).

**Impact:** a binding prohibition won where it was noticed; the plan text itself stayed contradictory.
**Source:** 24.3-01-SUMMARY.md, 24.3-02-SUMMARY.md, 24.3-03-SUMMARY.md, 24.3-06-SUMMARY.md

---

### The UAT's "no container on the host" expectation contradicted the skill's own design
The skill's step 5 runs disposable `podman run --rm` probes; the UAT Expected said "runs no container on the host." The owner set the criterion: done is the report plus the clean host with nothing left running. The agent-run UAT of the skill took 20m 15s on one entry (lazygit), made 37 tool calls, and proposed a `config_paths` addition it did not apply.

**Impact:** the UAT Expected was corrected, not the skill; test 5 (drawio-desktop 32.6.10 on macOS) stays deferred for lack of a Mac.
**Source:** 24.3-UAT.md (test 6, test 5), 24.3-VERIFICATION.md
