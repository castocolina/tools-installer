# Phase 24.5 Learnings: JavaScript install priority brew then bun then volta (INSERTED)

## Decisions

### Brew first for every tool, no exception list
`_RANK` puts `brew` and `cask` at 5, `bun` at 6 and `node` (pnpm on volta) at 7; every other value keeps its relative order. The owner confirmed on 2026-11-14, after seeing the measured fallout, that this applies to every tool and not only JavaScript ones.

**Rationale:** The roadmap goal and TypeSafe (0.83) read the owner that way, and the owner chose "Brew primero para todo" over "JS/Node only" and "everything except the base system". Measured fallout: 51 tools change first method on macOS, 57 on Fedora with Linuxbrew; claude, codex and kitty move to casks; docker, git, glab, jq, podman, unzip, watch, zip and zsh move from dnf to Linuxbrew.
**Source:** 24.5-CONTEXT.md (D-01 and its "Confirmed (owner, 2026-11-14)" note), 24.5-07-SUMMARY.md

---

### Golden first-method table plus a frozen pre-phase rank invariant
The resolver is pinned by a literal per-platform table of every catalog tool's first method (4 fixtures) and a second test that keeps a frozen copy of the old rank table, asserting that with `has_brew=False` every tool without a bun method sorts as before.

**Rationale:** A generated snapshot is easy to regenerate without reading, and spot checks do not meet "pins every tool". The invariant proves a host without Homebrew is unaffected.
**Source:** 24.5-CONTEXT.md (D-03), 24.5-07-SUMMARY.md, 24.5-VERIFICATION.md (truths 1-2)

---

### The bun method kind shares the node floor gate and package-name validation
`bun` joins `METHOD_KINDS` with `node`'s params, takes the same Node-floor clause in `_applies` and a mirror clause in `_rejection`, rejects `allow_build`, and regex-checks `npm_pkg` and every `co_install` entry at load.

**Rationale:** Without the `_rejection` clause the blocked reason would read a false "<os> not supported". Without the load regex a value starting with `-` would reach bun's option parser.
**Source:** 24.5-CONTEXT.md (D-02, D-05), 24.5-01-SUMMARY.md

---

### A smoke failure after `bun add -g` returned ends the ladder (D-06 amended)
Failures before or during `bun add -g` fall through to pnpm; a failed smoke afterwards raises `MethodLeftInstalled` and ends the install, instead of falling through.

**Rationale:** Falling through would run `pnpm add -g --allow-build=puppeteer` and leave a second copy, which contradicts SPEC PRIO-06 and its ordering edge. SPEC outranks CONTEXT, so D-06 was amended with a dated note in plan review cycle 1.
**Source:** 24.5-CONTEXT.md (D-06 amendment), 24.5-02-SUMMARY.md, 24.5-REVIEWS.md (R1-03/R1-04)

---

### The installer never passes `--trust` and never writes bun's manifest
The failure line names `bun add -g --trust puppeteer@^25` only when the user's own `trustedDependencies` list exists and lacks puppeteer; bun's output is not parsed and the manifest is read-only.

**Rationale:** On a manifest without the key, `--trust` would replace bun's default allowlist. Live check: `--trust` appended puppeteer to the user's list.
**Source:** 24.5-CONTEXT.md (D-21), 24.5-02-SUMMARY.md, 24.5-SECURITY.md (T-24.5-03, T-24.5-06)

---

### bun inventory is read from files, never from bun's CLI
Owner `bun` is attributed from the global tree: names from the manifest's `dependencies`, versions from each member's `package.json`. An unreadable manifest gives `unknown`; `owner_dirs` names the global tree only, so `~/.bun/bin/bun` is never bun-owned.

**Rationale:** `bun list -g --json` prints text, and an auto-installed peer is not in the manifest, so scanning `node_modules` would over-claim.
**Source:** 24.5-CONTEXT.md (D-11), 24.5-03-SUMMARY.md

---

### Updates use `bun update -g`, and an exact user pin refuses the update
The install executor is not reused for updates. An exact version in bun's manifest refuses the update with zero commands; `--latest` is never used.

**Rationale:** Live in a container: `bun add -g semver@^7` kept 7.5.0, while `bun update -g semver` moved it to 7.8.6 within the major.
**Source:** 24.5-CONTEXT.md (D-13), 24.5-04-SUMMARY.md

---

### mmdc installs puppeteer explicitly in the same invocation
mmdc's bun method keeps `co_install = ["puppeteer"]` with `versions = { puppeteer = "^25" }`, so one `bun add -g @mermaid-js/mermaid-cli puppeteer@^25` writes both names into bun's manifest.

**Rationale:** Installed alone, mmdc made puppeteer an auto-installed peer with no manifest entry and no bin link, and the peer survived mmdc's removal.
**Source:** 24.5-CONTEXT.md (D-19), 24.5-09-SUMMARY.md

---

### pi becomes an executed bun install with a pnpm fallback; the host_setup handoff leaves the registry
pi declares a bun method then an executed `node` fallback, with `min_node = 22.19.0`. The `host_setup` kind, `HOST_SETUPS`, its probe and the update branch stay in code, and their removal is handed to Phase 25 (LEAN-01).

**Rationale:** One JavaScript shape for all three tools and an installer-verifiable install ("best design over easiest"). The package declares no install scripts, so the old handoff's `--ignore-scripts` protected nothing.
**Source:** 24.5-CONTEXT.md (D-17), 24.5-06-SUMMARY.md

## Lessons

### Verify tests that run the new path for the wrong reason
When brew began winning first, tests listing `github_release` then `brew` on a Homebrew platform still passed, because brew now won first. They were rewritten to use a no-Homebrew platform so they still prove what they name.

**Context:** Found while changing the rank table in plan 07.
**Source:** 24.5-07-SUMMARY.md (Deviation 2)

---

### Test seams must be hermetic against the developer's real tool trees
The offline version-service double did not inject a bun reader, so a host with a bun-owned pi made about 25 catalog TUI tests try the network. Code review then found the sandbox did not clear `BUN_INSTALL*` at all (CR-01), so tests read the real `~/.bun`. Fixed with the three env names added to the sandbox, a home guard, and a test that `bun_dirs()` stays under the scratch HOME.

**Context:** AGENTS.md requires scratch-HOME tests; a bun installer exports `BUN_INSTALL` into the shell rc, so most developers have it set.
**Source:** 24.5-06-SUMMARY.md (Deviation 1), 24.5-REVIEW.md (CR-01), 24.5-SECURITY.md (Test isolation)

---

### Fail-closed inventory reads can be over-broad
One foreign global with a non-lowercase name (a legacy `JSONStream`) made the whole bun inventory unreadable, so every bun tool read `unknown` and updates were refused (WR-01). A bun-only host without pnpm read `unknown` when the command was not on this process's PATH (WR-02). Both were fixed after the review.

**Context:** Review noted that `pnpm` was removed from `requires`, so a bun-only host became the normal case.
**Source:** 24.5-REVIEW.md (WR-01, WR-02), 24.5-VERIFICATION.md (Code Review Findings), 24.5-SECURITY.md (R1)

---

### A status that compares against the registry's latest can stay outdated forever inside a range
`bun update -g` stays inside the manifest range, but the registry's `latest` can be an out-of-range major, so a row could read outdated while `u` reported success and changed nothing (WR-03). Fixed in the review commits with `test_bun_row_is_outdated_inside_its_own_major`.

**Context:** Derived from the code during review; the example is puppeteer 26 against the `^25` pin.
**Source:** 24.5-REVIEW.md (WR-03), 24.5-VERIFICATION.md

---

### Plan review caught container-harness defects before any code ran
Cycle 1 confirmed three HIGH findings, all in plan 07 and plan 09 harness assumptions: audit-landing's container bootstraps Homebrew so opencode would move off its script route; the teardown verdict printed to stdout only; and plan 09's lifecycle steps had no inventory reader, so no manager receipt would be written and the kept-peer and removal steps could not pass (R2-01).

**Context:** Findings 27 unresolved (cycle 1), 14 (cycle 2), 6 (cycle 3), 0 after the cap fixes.
**Source:** 24.5-REVIEWS.md (cycle 1 ledger R1-01..R1-03, cycle 2 R2-01, convergence outcome)

---

### A planned real-node pytest cannot run in this sandbox
The planned strict-loader test needed `node`, which is in `FORBIDDEN_PROGRAM_NAMES`, so the guarded launcher would fail the test at teardown. Replaced by a host-side source-shape test, and the real-node cases moved to the container `strict-loader` step.

**Context:** Raised by all three lanes in cycle 3 (R3-01) as the one confirmed HIGH.
**Source:** 24.5-REVIEWS.md (R3-01), 24.5-02-SUMMARY.md

---

### Exit status is not the removal verdict; and a finding label must name what was checked
bun's own tree is re-read after `bun remove --global` to decide removed, kept-peer, or already-removed. Doctor findings were prefixed `pnpm audit: ` / `bun audit: ` rather than "pnpm's copy:", because the pnpm check keeps a loader fallback and another copy can answer.

**Context:** Plan 05; review cycle 3 (R3-03).
**Source:** 24.5-05-SUMMARY.md, 24.5-REVIEWS.md (R3-03)

### Container runs dominate wall-clock time
Plan 09's duration was about 6 hours, almost all dnf bootstraps of about 520 packages at 100 to 400 KiB/s; one bootstrap took 50 minutes, and the first herdr receipts attempt hit the agent's own 3000 s timeout.

**Context:** The estimate is the executor's own, since the start time was not captured.

## Patterns

### One helper computes a derived directory for every reader
`bun_globals.method_bin_dir(method)` replaces every declared-`bin_dir` read, so a computed directory needs no registry param. The helper imports only stdlib and `installer.model`, so status, engine, executors, shellrc and ownership can import it acyclically.

**When to use:** A new manager whose directories come from the environment rather than the registry.
**Source:** 24.5-01-SUMMARY.md

---

### Skip and report an unsafe value instead of quoting it
A bun dir containing `"`, `$`, a backtick, a backslash, a newline or `os.pathsep` is skipped on both spellings (declared and resolved) and named once through an `on_skip` callback.

**When to use:** Any directory interpolated into generated shell code.
**Source:** 24.5-01-SUMMARY.md, 24.5-SECURITY.md (T-24.5-04)

---

### Strict own-tree loader: a manager-owned check never borrows another manager's tree
The bun puppeteer check resolves only inside the realpath of bun's `node_modules/puppeteer`, with no catch and no plain `require`; a missing copy fails without starting node. The check takes the owning manager as an argument, with typed test doubles (`tests/launch_doubles.py`) for pyright strict.

**When to use:** Any health check where a second manager can hold a copy of the same package.
**Source:** 24.5-02-SUMMARY.md, 24.5-SECURITY.md (T-24.5-07)

---

### Live per-pass inventory field that is never persisted
`ManagerInventory.bun_globals` is replaced on every refresh pass through an injectable reader and never enters the cached snapshot or the retry gate. Doctor evidence is keyed by `(tool_id, source)` and an audit replaces only the sources it read.

**When to use:** Inventory that is cheap to read from files and must not go stale in a cache.
**Source:** 24.5-03-SUMMARY.md, 24.5-05-SUMMARY.md

---

### A container verb reuses the landing harness and owns its identity
`bun-lifecycle` swaps only the driver module and the container identity (`tools-installer-e2e-bun-$$`, with `CONTAINER_NAME`, `IMAGE` and `DISTRO` set itself), traps teardown on EXIT, and appends the verdict to the transcript. Each negative step checks its precondition (mmdc absent, expected receipt present) before the call it judges.

**When to use:** Adding another disposable-container e2e verb.
**Source:** 24.5-09-SUMMARY.md, 24.5-REVIEWS.md (R1-10, R1-12)

---

### Pin doc claims by phrase and first-mention order
Doc tests check load-bearing phrases and the order of first mention inside one README section, plus a no-overclaim grep ("bun CLIs run under node"; bun "comparable to pnpm, not stricter").

**When to use:** Documentation that must stay in step with a ladder or a verified-facts list.
**Source:** 24.5-08-SUMMARY.md, 24.5-UAT.md (test 4)

## Surprises

### bun CLIs run under node, and an exit-0 reinstall does not update
Bun-installed CLIs start with `#!/usr/bin/env node`, so a node must be on PATH. Re-running `bun add -g semver@^7` (even `--force`) kept 7.5.0.

**Impact:** The install executor could not be reused for updates, and the docs had to avoid claiming bun runs without node or is stricter than pnpm.
**Source:** 24.5-CONTEXT.md (D-13, D-22), 24.5-08-SUMMARY.md

---

### Brew-first broke the container receipts probe
The e2e box bootstraps Homebrew, so `yq` (the receipts probe) now installs through brew and leaves no receipt or `~/.local/bin/yq`. The probe moved to `herdr`, which has only raw github_release methods.

**Impact:** An unplanned edit to `scripts/container-e2e-verify.sh` and tests; the receipts route was later confirmed with herdr in a real container.
**Source:** 24.5-07-SUMMARY.md (Deviation 1), 24.5-09-SUMMARY.md

---

### The stranded peer after mmdc removal was observed as true
After bun removed mmdc, puppeteer stayed in bun's tree; it left only when puppeteer's own removal ran next. Removing both through the Uninstall path (mmdc first) ends clean.

**Impact:** The plan's "known residual" holds only for a peer kept after its dependent is removed alone, which no run exercised. A single sample, not proof.
**Source:** 24.5-09-SUMMARY.md (Observations), 24.5-UAT.md (test 1)

---

### A failed `bun add -g` left the manifest unchanged in the one sample taken
`bun add -g semver@^7 @tools-installer-e2e/absent-package` exited 1 and left semver out. It may fail during resolution before any linking.

**Impact:** The R1-05 residual (T-24.5-32, an accepted risk) stays open; no D-06 amendment was shown necessary.
**Source:** 24.5-09-SUMMARY.md, 24.5-SECURITY.md (T-24.5-32), 24.5-REVIEWS.md (R2-09)

---

### Non-interactive `zsh -lc` from a bare environment does not see `~/.bun/bin`
The installer wires `~/.zshrc`, which a non-interactive zsh never reads. Interactive login zsh (`zsh -lic`) and `bash -lc` pass.

**Impact:** No PRIO criterion fails, but a script run as `zsh -lc` from an empty environment would not find bun-installed commands. The owner was told in the UAT notes.
**Source:** 24.5-UAT.md (test 3), 24.5-VERIFICATION.md (Human Verification)

---

### Test files pinned shape in places the research did not list
RESEARCH's list of files to change came from reading, not a run: the full suite also needed `tests/state_doubles.py`, `tests/test_ownership.py`, `tests/test_version_status.py`, and four classified line numbers in `tests/test_shell_scripts_path.py` shifted by 12 added usage lines.

**Impact:** Several out-of-plan file edits across plans 06 and 09; none changed the acceptance criteria.
**Source:** 24.5-06-SUMMARY.md (Deviation 3), 24.5-09-SUMMARY.md (Deviation 1)
